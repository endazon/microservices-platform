# 環流: PR サイズの目安 400 行と、必須文書の量が両立しない

## 対象

| | 出典 |
| --- | --- |
| 規範 A | `docs/ai-implementation-workflow-guide.md` §1 —— **1 issue の見込み diff は 400 行以内**。超える見込みなら起票時点で分割する |
| 規範 B | `tools/impl-handoff-kit/repo-template/CLAUDE.md` —— **着手前に作業仕様書が必須**。**重要な実装判断は実装 ADR に必ず残す** |

**どちらもキット／ガイドが定めた確定記述**である。

## 実測 —— **必須文書だけで枠をほぼ使い切る**

`microservices-platform` の `develop` 直近 **30 PR**（squash 1 件 = 1 PR）で、
**`docs/` と `feedback/` の追加行数だけ**を数えた（基準 `1f2cc2a`）。

| | 行数 |
| --- | ---: |
| 中央値 | **393** |
| p75 | **443** |
| 最大 | **567** |

**規範 A の枠は 400 行である。**
**必須文書だけで中央値 393 行に達し、4 回に 1 回は「コードを 1 行も書かずに超える」。**

PR 全体（生成物・lock を除く。キット `pr-size.yml` の既定 `EXCLUDES` そのもの）では
**30 件中 23 件（76%）が 400 行を超える**。**しきい値は事実上ほぼ全 PR に当たる。**

## 何が問題か

**「規範 A を守れていない」のではない。** **A と B を同時に満たす経路が無い。**

- **A に合わせて分割する**と、**分割するほど B が要求する仕様書と IADR が増える**
  （1 PR ごとに 1 組）。**割るほど文書の総量が増え、A から遠ざかる**
- **B を薄くする**のは、本リポが繰り返し「記録が無いと後から根拠を追えない」として
  積み上げてきた統制を崩す（実装側では採らない）
- **A の 400 を実装 diff に限る**と読めば両立するが、**ガイドはそう限定していない**

## 実装側で採った暫定（[IADR-0181](../docs/adr/IADR-0181_pr-size-check-calibration.md) 決定 2）

**しきい値 400 は動かさず、`pr-size.yml` の `EXCLUDES` へ `docs/` `feedback/` を足した。**
根拠は「**文書量は複数 issue の混在という検査目的に対して指標にならない**」ことである
（PR を細かく割るほど文書は増えるので、混在の兆候とは逆向きに動く）。
**警告率は 76% → 23% になった。**

> **★ 吸収はできたが、黙って吸収すると「400 行以内を守っている」という誤った像が残る。**
> **暫定であることを明示するために環流する。**

## 裁定してほしいこと

1. **§1 の 400 行は何を数えた値か。** 実装 diff だけか、必須文書を含む PR 全体か
2. 文書を含む場合、**規範 B（1 PR ごとに仕様書＋IADR）との両立方法**はあるか
   （例: 仕様書・IADR を数えない／束ねる単位を変える／400 を実測で引き直す）
3. **キットの `pr-size.yml` 既定 `EXCLUDES` を、文書を除く形へ改める**ことの可否

## 併せて報告（キットの小さな不整合 2 件）

1. **`pr-size.yml` は `permissions: pull-requests: write` を宣言しているが、
   コメントを投稿するステップが無い。** **宣言だけ残った未使用権限**である
   （実装側の `#623` は「警告コメント」と書いており、当初はコメント投稿の想定だったと読める）
2. **既定 `EXCLUDES` の `**/orval/**` は、少なくとも本リポでは 1 ファイルも当たらない。**
   orval の出力先は設定ファイル（`orval.config.ts`）が決めるため、
   **パターンではなく「設定ファイルが指す出力先を書く」旨の注記があるとよい**
3. サマリに**除外前／除外後の両方**を出すと、除外の妥当性がその場で確かめられる
