# フィードバック: キット `traceability.md` の別紙移設が配布先で取り込めない

## 種別

その他（キット配布物の取り込み条件が配布先で満たせない）

## 起点となる計画書

- 機能要求（FR）: なし
- ユースケース（UC）: なし
- 画面（SC）: なし
- 関連 ADR: `IADR-0173` / `IADR-0190`（必読の余白・別紙化）/ `IADR-0192` / `IADR-0204`（キット追随の分類）
- 計画書リンク: 運用ガイド §8（必読規約の予算）/ planning#406 / planning#407

## 現状（計画書の記述 / As-Is）

planning#407 がキット `repo-template/.claude/rules/traceability.md` を **25,963 B → 25,207 B（−756 B）へ純減**させた。削除ではなく `repo-template/docs/ai-workflow.md` への**移設**であり、移設元は相対リンク `../../docs/ai-workflow.md` で参照するだけになった。

方向は正しい（必読から非必読へ移す＝運用ガイド §8 と `IADR-0173` / `IADR-0190` の考え方そのもの）。

## 問題点 / あるべき姿（To-Be）

### 1. 純減の量が「上限」しか解いていない

本リポの実測（pin `b095b8f` 時点）:

| 判定 | 値 |
| ---: | --- |
| 現在の必読合計 | **50,132 B** / 余白 **1,068 B** |
| 取り込みコスト | 25,207 − 24,592 = **+615 B** |
| 取り込み後 | 50,747 B / 余白 **453 B** |
| **上限 51,200 B** | ✅ 収まる（planning#407 の前は 302 B 超過） |
| **下限 1,000 B**（`scripts.repo.test.js` の `#730` `FLOOR`） | ❌ **547 B 不足** |

**ブロッカーが「上限の超過」から「下限の不足」へ移っただけ**で、取り込めない状態は変わらない。**上限だけを見ると「これで取り込めるようになった」と誤読できる** —— 実際、本作業で一度そう誤読し、#853 で自己是正した。

### 2. 取り込みが 2 ファイルの原子的操作になったことが、配布物のどこにも書かれていない

移設後の `traceability.md` は内容を持たずリンクするだけなので、**片方だけ取り込むとリンク先に中身が無い**（本リポの `docs/ai-workflow.md` は分類 B・種 2 で独自デルタを持つ別物）。**バイト一致検査は `traceability.md` 単体を見るため、片方だけ取り込んでも緑になる。**

## 実装で判明した経緯

計画 pin を `f216783` → `b095b8f` へ進める作業（#853 の `43d2cfa`）で、分類 X の理由（旧: 「+1,371 B で上限を 302 B 超過」）が pin 追随により**そのままでは誤りになる**ため引き直したところ判明した。

`scripts/kit-sync-classification.json` の `.claude/rules/traceability.md` の記録を実測へ更新済み。

## 提案（計画への反映案）

- 反映先候補: **運用ガイド更新** / **キット HOWTO 更新** / キット配布物のさらなる純減
- 提案内容:
  1. 運用ガイド §8 に**「必読集合の増減は上限と下限の両方に照らす」**を明記する。
  2. 配布物を別紙へ分割したときは、**「取り込みは移設元と移設先の同時適用である」**ことを HOWTO へ明記し、移設が起きた pin では影響を受けるファイルの組を列挙する。
  3. `traceability.md` の**さらなる純減**を検討する（本リポでは分類 A へ戻すのに**あと 547 B**）。
  4. （任意）バイト一致検査が「対になるファイルの片側だけ取り込まれた」状態を検出できるかを検討する。

## 影響範囲

- **他の実装リポジトリにも同じ形で効く**（運用ガイド §11 のパリティ維持の対象）。下限ラチェットを持つ配布先はすべて同じ壁に当たる。
- 本リポの `traceability.md` を分類 X に留め置く期間が延びる（`IADR-0204` の期限つき暫定のラチェットが効き続ける）。追跡: #793 系の減量。
