実測はすべて対象コミット `cf0a0b0`（`origin/develop`）に対するものである。

| # | 画面 | 計画の記述 | 現在の API 契約（実測） |
| --- | --- | --- | --- |
| 1 | SC-09 | §主要素「**タグ辞書**」。§タグ辞書の削除・改名（2026-08-02 確定）「参照が 1 件でもあるタグは削除を拒否し、改名は許して既存の文書が新しい名前へ追随する。削除前に『このタグは N 件で使われている』と**件数を示す**」 | `/bff/admin/authz` にあるのは `attributes` と `policies` の **2 群だけ**で、**タグ辞書の値集合を返す口が無い**。`AttributeDefinitionDto(Id, Key, Label, AllowedValues, Required, Scope, …)` の `AllowedValues` は**属性の許可値**であってタグ辞書ではなく、**使用件数**も**改名時に既存文書へ追随させる仕組み**も契約に無い。計画が確定した規則は**そのすべてが契約側の機能**であり、画面だけでは満たせない |
| 2 | SC-09 | hi-fi 430 のボタン「**検証**」（保存とは別に置かれている）／§アクション「**保存前にポリシーを検証し**、矛盾はエラー表示」 | 検証は `POST /bff/admin/authz/policies` の応答（400 `ValidationProblem`）としてのみ得られる。**保存せずに検証だけ行う（dry-run）エンドポイントが無い**。ローカルで代用すると「検証は通ったのに保存で矛盾が出る」ことになり、かえって誤解を生む |
| 3 | SC-09 | §入力「**ポリシー条件｜必須｜条件式｜構文・矛盾検証に合格**」。hi-fi 429 は `user.dept == "開発" && doc.tags には "設計" を含む` という**自由記述の式**を描く | `AbacPolicyDto.UserConditions` / `DocumentConditions` はいずれも `Dictionary<string, List<string>>` ＝ **属性キー → 許可値の集合所属**だけを表現する。**`<=`（機密区分の順序比較）も「含む」も表現できない**。実装は構造化エディタ（属性 `Select` × 許可値 `Select`）を採り、計画の入力表 2 行目（「対象属性｜選択｜**定義済み属性のみ**」）は満たすが 1 行目は**部分的にしか満たさない** |
| 4 | SC-10 | §主要素「KPI カード（**SLO 達成率**…）」。hi-fi 419「SLO 99.7% / 検索 p95 820ms」 | `DashboardSummaryDto(TotalSearches, TotalAnswers, UsageTrend, TopSearchTerms, Quality)` に**該当項目が無い**。レイテンシは可観測性基盤（Prometheus / Grafana）側にあり、BFF は集約していない |
| 5 | SC-10 | §主要素「KPI カード（… **LLM コスト**）」。hi-fi 421「LLMコスト ¥184k / 今月（予算内）」 | 同上。**コスト情報を返す口が無い**（モデル呼び出しの課金情報の集約が必要） |

## 提案（To-Be）

| # | 提案 | 影響先 |

| 1 | **タグ辞書の契約**を定める——(a) 値集合の照会・追加、(b) **タグごとの使用件数**、(c) **改名時に既存文書を追随させる仕組み**（辺と同じく「識別子を参照し表示名を複写しない」形）。定めないなら §SC-09 §主要素 から「タグ辞書」を外し、2026-08-02 に確定した削除・改名の規則の適用先をタグ辞書から外す | 05_screens §SC-09・07_abac-attribute-model |

| 3 | **ポリシー条件の表現力**を定める——計画が描く条件式（`<=` による機密区分の順序比較、`doc.tags には "設計" を含む`）を**契約で表現するのか、それとも集合所属だけに留めるのか**。前者なら `AbacPolicyDto` の条件表現の拡張（演算子つき）が要る。後者なら §入力表 1 行目の「条件式」と hi-fi 429 の例示を**集合所属の形へ**改める | 05_screens §SC-09・02_requirements（FR-05 / FR-09） |

## 影響範囲

- **裁定までは画面に当該要素を実装しない。** 「常に『—』の KPI カード」「押しても何も起きない検証ボタン」
  「中身の無いタブ」は、計画が画面へ与えた役割（管理者・運用者が状況を正確に把握する）をむしろ損なう
  （#502 が確立した「動かない UI を置かない」）。
- 実装しないことは各画面仕様書の「hi-fi モックアップとの対応」表へ**行番号つきで明記**した
  （`docs/screens/SC-09_admin-abac-settings.md` / `SC-10_operations-dashboard.md`）。
  **二値判定の外側にある部分未実装（#3 の条件式・#6 の指標の意味）も同じ表の備考に併記した。**
- 提案 7 が「運用者も含む」と裁定された場合、実装側は
  (a) `/bff/dashboard/summary` の認可を `ConfigViewer` 相当へ、(b) 後段 `DashboardService` の認可も同様に、
  (c) 画面の `RequireRole` とナビの `requiresAnyRole` を、(d) テスト仕様書 SC-10 の A2 と
  `opsFlow.test.tsx` の 2 本目を、**同時に**改める。片側だけ変えると #503 が SC-07 で踏んだ
  「画面と API の権限がずれている」形になる。
