# feedback — 計画へのフィードバック記録

実装中に判明した**計画書（`project-planning`）の誤り・不足・新たな制約**を計画側へ環流（フィードバック）するための記録置き場である。

## いつ使うか

- 計画書（要求・UC・画面）の記述が実態と異なる、または不足している。
- 実装で新たな技術・設計上の制約が判明し、ADR を起こすべき。
- 計画書に未登録の用語が頻出する。

## 手順

1. `/plan-feedback <FR-xx|topic>` を実行する（`plan-feedbacker` エージェントが起票を補助）。
2. `feedback/TEMPLATE.md` を雛形に、`feedback/<YYYYMMDD>_<概要>.md` に記録が作成される。
3. 計画リポジトリへ伝達する（両経路に対応）。
   - **記録ファイル経路**: 作成した記録を計画リポジトリの `draft/feedback/` にコピー（submodule/隣接クローン経由）。
     計画側で `/triage-feedback` がトリアージする。
   - **GitHub Issue 経路**: `/plan-feedback` が生成した Issue 本文を、`endazon/project-planning` の
     「計画へのフィードバック」Issue テンプレートに貼り付けて起票する（GitHub MCP / `gh` でも可）。
4. 計画側でトリアージされ、要求更新 / 新 ADR / 用語追加などに反映される。

## 【最重要】記録を作るだけでは計画へ届かない

**手順 2（記録の作成）と手順 3（計画リポジトリへの伝達）は別の作業であり、3 が漏れる事故が繰り返し起きている。**

2026-08-06 の棚卸しでは、**6 件の記録が「未送付」のまま最長 1 か月近く実装リポに滞留していた**（うち 1 件は実装コードのコメントが「計画へ環流済み」と述べていたのに該当ファイルすら無かった）。**いずれも PR はマージ済みであり、記録には `status: open` と「未送付。計画リポジトリへ issue として起票する」と書かれたままだった。** PR がマージされても検出されない点で、通常の未反映よりも見つけにくい。

**手順 3 まで完了させて初めて `/plan-feedback` は終わる。** 起票したら**記録に issue への URL を残す**こと（後から到達を確認できるようにするため）。

### CI による検出（警告のみ）

<!-- 固有デルタ（IADR-0115 決定 2 の 2. 技術スタックとその CI 配線）: キット原文は検出を `doc-links`
     ジョブが行うと書くが、本リポは独立ジョブ `feedback-dispatched` である（IADR-0184 決定 3）。
     必須チェックの context がジョブ名であるため相乗りにできない。環流は不要（本リポ固有の配線）。 -->

`scripts/check-feedback-dispatched.js` が CI（`feedback-dispatched` ジョブ）で次を警告する。**ジョブは落とさない。**

- `status: open` で、**計画リポジトリの issue への参照が無い**記録
- 本文に**「未送付」**がある記録（`status` を問わない）

**警告に留めるのは、起票が人手の判断を伴うためである。** ブロックにすると「記録を作らない」という回避策を誘発し、統制の目的（環流の取りこぼしを無くす）と逆の結果になる。厳格化したい場合は `STRICT_FEEDBACK_DISPATCH=1` を設定する。

> **自リポジトリの issue URL は起票の証拠にならない。** 計画リポジトリ（別リポジトリ）の issue へのリンク、またはフロントマターの `planning_issue:` が要る。

## `status` の語彙

<!-- ★ 暫定デルタ（IADR-0115 が第 12〜13 ラウンドで確立した運用）: 本節はキット `repo-template` に
     存在しない。語彙の定義は IADR-0115 決定 2 の固有デルタ 4 種のどれにも当たらないため、
     同 決定 3 に従い **planning#323 としてキットへ環流済み**である（記録は
     `feedback/20260813_kit-feedback-status-vocabulary.md`）。
     ★ キット側へ反映されたら本節を撤去し、キット準拠へ戻すこと。
     判断の根拠は docs/adr/IADR-0185_feedback-status-vocabulary.md。 -->

**`status` は「その記録を計画リポジトリへ伝達したか、伝達の結果どう裁定されたか」の 1 軸を表す**（[IADR-0185](../docs/adr/IADR-0185_feedback-status-vocabulary.md)）。**記録の重要度や実装側の対応状況ではない。**

| 値 | 意味 | 誰が遷移させるか |
| --- | --- | --- |
| `open` | 記録は作ったが、**計画リポジトリへまだ伝達していない**（`TEMPLATE.md` の既定値） | —— |
| `triaged` | **伝達済み**（issue 起票、または `draft/feedback/` へのコピー）。**計画側の裁定を待っている** | **実装側**が、伝達した事実を書く |
| `accepted` | 計画側が**受け入れた**（計画書・ADR へ反映される／された） | **計画側の裁定**を実装側が転記する |
| `rejected` | **採らないと決まった** | 同上 |

**遷移は `open` → `triaged` → `accepted` / `rejected` の一方向である。**

> **`open` は「未伝達」であって「裁定待ち」ではない。** 伝達した時点で `triaged` へ進めること ——
> **伝達済みのまま `open` に留め置くと `triaged` と同義になり、どちらの語も意味を失う。**
> 上記の検査器も **`status: open` を「未伝達の疑い」と読む**ので、置き去りにすると警告が鳴り続ける。
>
> **`accepted` / `rejected` は計画側の裁定結果であり、実装側の判断ではない。** 実装側が「もう要らない」と
> 取り下げる場合も、**計画側へ伝達済みなら計画側の裁定を待つ**（伝達前なら記録ごと消してよい）。

## 注意

- 記録は事実と提案を分けて書く。確定は計画側（人間 + `/triage-feedback`）が判断する。
- この `feedback/` ディレクトリは実装リポジトリ側の控えである。原典の反映先は計画リポジトリ。
