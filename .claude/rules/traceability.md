# トレーサビリティ（追跡可能性）の規約

計画書と実装を相互に追跡できるよう、実装の起点となる計画書の ID を以下に残す。コミット・PR・コードを編集する際は本ルールに従う。

> **本ファイルはキットの配布物である。直接編集しないこと。**
> リポジトリ固有の規約は **`traceability.repo.md`（同じディレクトリ）** へ書く。同ディレクトリの
> `*.md` は自動適用されるため、companion 側も同じように効く。
>
> **直接編集するとバイト一致が崩れ、キットを同期するたびに手動マージが要る**
> （`scripts.repo.test.js` / `action-versions.repo.json` と同じ理由）。実測では、配布物へ
> 固有節を直接足していたリポジトリが **10.8 KB** 分の差分を抱え、**必読規約の総量予算を
> 超過する原因**にもなっていた。
>
> **companion が無くても壊れない。** 未作成なら固有規約が無いだけである。

## 起点 ID の種別

- `FR-xx`: 機能要求（計画リポ `02_requirements/`）
- `NFR-xx`: 非機能要件（計画リポ `02_requirements/` の非機能要件表の ID 列）。**個別 ID で参照する。粒度なしの `NFR` だけを書かない** —— どの非機能要件を実装した変更なのかが区別できず、機械集計もできなくなる。**無採番の `NFR` を許すのは次の 2 つの場合に限る。**
  1. **計画側が ID 列を持たない場合。** この場合は**計画へ ID の付与を環流する**。
  2. **ID 列はあるが、その作業に当たる番号が無い場合**（確定・2026-08-11。planning#311）。**規約整備・検査器の追加・必読規約の減量・文書統制といったメタ作業**が典型である —— 計画側の非機能要件は**稼働する製品**の要件であり、**工程の管理は別の軸**だからである。
     - **無理に近い番号を付けない。** 実在しない対応づけを作ると、**監査が「その NFR の実装」として数えてしまい、無採番より劣化する**。
     - **この場合は環流しない**（1 と違い、計画側に不足があるわけではない）。**メタ作業のための番号を計画の非機能要件表へ新設することは、計画側で明示的に採らないと裁定した**（工程の規律を製品の品質要件の表へ混ぜないため）。
     - **どちらの場合かは、作業を始める前に計画の ID 列を見て判断する。**「面倒だから無採番」は 2 に当たらない。
- `UC-xx`: ユースケース（`03_usecases/`）
- `SC-xx`: 画面（`05_screens/`）
- `ADR-xxxx`: 計画ADR（計画リポ `07_adr/`）
- `IADR-xxxx`: 実装ADR（本リポ `docs/adr/`。計画ADR とは別系統）

上記の裸（無修飾）の ID は、**本リポジトリが主に実装するプロジェクトの計画書の名前空間**を指す。

## 複数プロジェクトを跨ぐ場合の ID 修飾

1 つの実装リポジトリが複数プロジェクトの計画書を参照する場合（基盤リポに別プロジェクトを
submodule で取り込む等）、**計画 ID はプロジェクトごとに独立採番のため衝突する**。裸の ID で
書くと、機械的な突合（監査・`trace-check`）が「計画書に存在しない ID の参照」「誤帰属」を
誤検出する（例: 一方にしか存在しない `FR-17`、双方に存在し意味の異なる `SC-01`）。

- **書式**: `<PROJ>/<ID>`。例 `AST/FR-17`・`AST/SC-01`。`<PROJ>` は短縮プロジェクト名。
- **機械検査**: `scripts/check-plan-id-qualification.js` が**空白区切りの形**（`AST` と ID が空白・TAB・
  wiki リンク括弧・バッククォート・全角括弧で離れる形）を検出する。**配布時に冒頭の 置換点
  `PROJECT_PREFIXES` を書き換えること。空のままなら skip する**（他プロジェクトを参照しない
  リポジトリでは対象が無い）。`maskCode` を `check-cross-repo-refs.js` から借りているため
  **2 本セットで配布する**。**文脈から裸の ID を推測する形は検出しない**（偽陽性が避けられず、
  1 件でも出すと検査そのものが外されるため）。
- **適用箇所**: コード内コメント・IADR / 仕様書の本文・テスト名、およびコミット / PR 件名の説明文。
- **キット配布物（本ファイル・`scripts/` 等）の中では、他リポジトリの `ADR` / `IADR` を番号で引かない。**
  **配布物には「自リポジトリ」が無く、裸の番号は配布先ごとに別の決定を指す。** 出典を示すなら**決定の内容を
  1 行で書く**か `<PROJ>/<ID>` で修飾する。**機械検査は無い** —— 配布先では裸の `IADR-NNNN` が正しい参照で
  あり、区別できない（実測: planning#354。キットの docstring が引いた `IADR-0140` は、配布先では無関係な
  ADR を指し、それを裏取りせず引き写した記述が 2 ファイルへ入った）。
- **コミット / PR 件名のスコープ `()`**: `check-commit-messages.js` の実在性検査は本リポジトリの
  名前空間しか解決できない。よって**スコープには自プロジェクトが所有する ID を置き**、他プロジェクトの
  ID は説明文で修飾して参照する。例:
  `feat(IADR-0072): AST/SC-02 監視銘柄の /bff/monitor プロキシを登録`
- **監査 / trace-check の扱い**: `<PROJ>/<ID>` は外部プロジェクトへの参照であり、自名前空間に対する
  「参照切れ」ではない。監査は修飾付き ID を突合対象から**除外**する
  （`.claude/agents/traceability-auditor.md` に同じ規約を書くこと）。
- **既存履歴は不変**: 過去コミット件名の裸 ID は書き換えない（force-push 禁止）。CHANGELOG 生成時の
  `changelog-overrides.json`（`remap`・後述）または今後の編集で生成物 / 本文のみ是正する。

## 残す箇所と書式

- **ブランチ名**: `<種別>/<起点ID>-<概要のケバブケース>`。例 `feat/FR-012-login-validation`。
- **コミットメッセージ**: 先頭に `<種別>(<起点ID>): <要約>`。例 `feat(FR-012): ログイン画面のバリデーションを実装`。
  - 種別: `feat` / `fix` / `refactor` / `test` / `docs` / `chore` 等。
  - 1 コミット = 1 論理変更。複数 ID にまたがる場合は `feat(FR-012,UC-03): ...` のように併記する。
- **コード内コメント**: 計画書由来の実装箇所に ID を残す。例 `// FR-012, UC-03: 入力バリデーション`。
- **テスト**: テスト名またはコメントに起点 ID を残す。
- **PR**: PR テンプレートの該当欄に、実装した FR/UC・関連 ADR・受け入れ基準のチェックを記入する。

## 守ること

- 起点 ID を持たない大きな変更を作らない（雑多な変更は理由を明記する）。
- 計画書に存在しない ID を参照しない（誤記・廃止に注意）。
- ADR の制約に反する実装をしない。逸脱が必要なら新 ADR の起票を提案する。

## コミットメッセージの機械チェック（CI・再発防止）

PR で追加されるコミット（`base..HEAD`）の件名を `scripts/check-commit-messages.js` が検査し、規約
`種別(起点ID): 要約` に違反していれば CI を失敗させる。既存履歴は書き換えず、再発防止のみを目的とする。

- **許可する種別**: `feat` / `fix` / `perf` / `refactor` / `docs` / `test` / `build` / `ci` / `style` / `chore`。
- **起点 ID の書式**: `FR-\d+` / `NFR-\d+`（計画側が ID 列を持たない場合に限り `NFR`）/ `UC-\d+` / `SC-\d+` / `ADR-\d{3,4}` / `IADR-\d{3,4}` / `P0`〜`P3`。
  複数 ID はカンマ区切りで併記。スコープ `()` は省略可。
- **末尾の PR 番号**: 半角スペース + `(#123)` はスカッシュマージ既定件名として許容。
  **この `(#123)` は、その PR 自身の番号である。** GitHub がスカッシュ時に自動付加するものであり、
  **起点 issue の番号ではない**（起点 issue は本文の `Closes #NNN` で示す）。
  **通常、PR タイトルへ番号を書く必要はない。**
  - **書くと二重に付く。** UI からマージすると自動付加が重なり `… (#123) (#456)` になる。
    **force push 禁止のため事後修正できない。**
  - **前提を書いていなかったため、実測した配布元では「末尾に番号を持つ PR のうち、自番号と
    一致するものが 1 件も無かった」**（起点 issue の番号だと解釈されていた）。
    `pr-title.yml` が `PR_NUMBER` を渡す構成では、`check-commit-messages.js` が一致を検査する。
- **ADR / IADR の実在性**: 書式に加え、スコープの `IADR-xxxx` は本リポ `docs/adr/` に、`ADR-xxxx` は
  planning submodule の `projects/<name>/07_adr/` に該当ファイルが実在することを検査する
  （PR コミットと PR タイトルの両方）。読めない環境（submodule 未 populate 等）では該当検査を
  skip する（`check-doc-links.js` と同じ扱い。ローカル環境差で CI を落とさない）。
  **注**: PR の CI が submodule を取得しない構成の場合、実効的に働くのは IADR 検査のみである。
  計画 ADR 検査まで CI で効かせたい場合は、submodule を取得するジョブ（例: 夜間の planning 系
  ジョブ）に結線すること。
- **`FR` / `UC` / `SC` の実在性**: 同様にスコープの計画レンジも実在を検査する。**この検査が無い間、
  `feat(SC-99)` は exit 0 で受理され、スカッシュ後件名として恒久履歴へ載れた**（force push 禁止で
  事後修正できない面である）。**レンジの正はリポジトリ固有**（配布先ごとに計画プロジェクトが違う）の
  ため、キットはパーサを持たず**拡張点 `scripts/check-test-traceability.js` の `readPlanIds()` を探す**。
  - **持たない構成では skip し、skip したことを notice で出す**（黙って 0 件検査へ落ちない）。
  - **拡張点は在るが節をパースできない場合は fail** させる。追跡下の必ず読めるファイルを読めないのは
    環境差ではなく**規約側の破壊**（節の改名・書式変更）であり、黙って通すと**単一情報源が壊れたまま
    「違反 0 件」で緑になる**。
- **他リポジトリ番号の修飾を 3 つの面で見る**: **件名・本文（`%b`）・PR タイトル**。判定器は
  `check-cross-repo-refs.js` から借りる（規約の単一情報源は同スクリプト側）。**本文を見るのは、
  列挙形の修飾漏れが本文にも出るためである** —— 件名だけでは足りない。この 3 面は**裸の `#NNN` が
  本リポジトリの issue へ自動リンクする**面であり、`.md` と違って**誤リンクという実害が出る**。

### 採番衝突時の改番手順

並行実装では IADR 番号の採番衝突が起こり得る。**番号は先にマージした側が確保する（先着尊重）**。
後発は次の空き番号へ改番し、欠番を作らない。改番時は以下を**すべて**追随させる。

1. ファイル名（`docs/adr/IADR-xxxx_*.md`）と本文中の自番号
2. 索引（`docs/adr/README.md`）・関連仕様書（`docs/specs/` の `related_ids` / 本文）
3. コード内コメント・テスト名の起点 ID
4. **PR タイトル**（= スカッシュ後にコミット件名として統合ブランチへ載る。ここだけが人手の追随に
   依存するため最も漏れやすい。ブランチ名は既 push なら変更不要だが、タイトルは必ず直す）
5. **計画リポジトリが引く自番号**（`projects/<name>/07_adr/*.md` の地の文）。**ここは fail-open で
   ある** —— 探さなければ何も起きない。**主たる担保は計画側の機械検査**（planning#395）。

### クロスリポジトリの issue / PR 番号の修飾

計画 ID と同様に、**issue / PR 番号にも名前空間衝突**がある。裸の `#NNN` は GitHub 上で
**本リポジトリの** issue / PR へ自動リンクされるため、他リポジトリの番号を裸で書くと無関係な
issue / PR へ誤リンクする（コミット footer の `Refs #NNN` で実際に発生する）。

**規約**: 他リポジトリの issue / PR 番号は必ず修飾する（例: `<短縮リポ名>#NNN`）。適用箇所は
コード内コメント・IADR / 仕様書の本文・コミット件名 / footer・PR 本文。GitHub の自動リンクを
効かせたい箇所ではフルパス形式（`<owner>/<repo>#NNN`）を用いてもよい。裸の `#NNN` は常に
本リポジトリの issue / PR を意味する。**プロジェクト内で短縮形とフルパス形式のどちらに
寄せるかを最初に決め、混在させない**（機械的突合の揺れを避けるため）。

**面によって壊れ方が違う。** 同じ違反でも、書く場所によって実害の性質が変わる（実測）。

| 面 | 裸の `#NNN` の扱い | 違反の実害 |
| --- | --- | --- |
| **issue / PR の本文・コミットメッセージ** | **本リポジトリの issue / PR へ自動リンクする** | **誤リンク**（無関係な issue を指す）。実害が出る |
| **`.md` ファイル** | **自動リンクにならない**（`.md` でリンクになるのはフルパス形式だけである） | **表記ゆれ**（機械的突合が不安定になる）。誤リンクは起きない |

- したがって、**優先して直すのは issue / PR / コミットメッセージ側**である。`.md` 側は突合の安定
  のために揃える。
- **山括弧のプレースホルダ（`<owner>` の形）を `.md` にそのまま書かない。** `.md` のファイル上は
  正しく読めるが、**issue 本文へ転記した時点で GitHub が HTML タグとみなして黙って除去する**
  （実際に起票済みの issue 本文が意味の通らない記述になった）。バッククォートで囲むか、
  山括弧を使わない書き方にする。**転記先の面ごとに壊れ方が違うことを前提に書くこと。**

**機械検査**: `scripts/check-cross-repo-refs.js` が 4 つの型（長い表記の裸書き／列挙形の
修飾漏れ／修飾語と番号が空白で離れる形／**フルパス形式の owner 誤り**）を検査する。
**owner 誤りだけは上の表の外にある** —— フルパス形式は `.md` でも自動リンクするため、
owner を誤ると**表記ゆれではなく死んだリンク**になる。

**関連番号を添える注記 `〔〕` の中も列挙として見る。** `PR planning#244〔裁定依頼 planning#237〕`
のように**中の番号も修飾する**こと。**全角丸括弧 `（` は区切りとして扱わない** —— 日本語の地の文で
従属節を開く記号であり、その直後の裸 `#NNN` が本リポジトリを指すのは正しいためである。

**走査は追跡下の全ファイルである**（`*.md` に限らない）。人が読む散文は `docs/` だけでなく
`.github/` や `deploy/` にもあり、`*.md` だけを見ていた頃はワークフロー YAML の中の違反を
誰も見ていなかった（実測）。**置換点 `EXCLUDED_DIRS` のディレクトリの非 Markdown だけ**を外し、
**除外件数をログに出す**（「検査していない」と「違反 0 件」を読み分けるため）。

**配布時に同スクリプト冒頭の置換点を必ず書き換える**（`SELF_NAMES` の書き忘れは正当な自リポ参照を
大量に違反として上げ、検査そのものを外させる。実測 22 件）。置換点の一覧と各々の失敗の形は[別紙](../../docs/traceability-appendix.md)。検査していないことは実行時に notice で出す。

**意図的に誤例を書く場合は、インラインコードかコードフェンスに入れる。** 検査対象は表示テキスト
のみであり、**literal な引用は表記規約の対象外**という定義である。これにより、規約自身が反例
（「誤: …」）を書けなくなる問題が除外リスト無しで解ける。

### PR タイトル（スカッシュ後件名）の検査（再発防止）

スカッシュマージで develop に載る件名は「**PR タイトル + 半角スペース + `(#番号)`**」であり、PR コミット
（`base..HEAD`）の範囲に含まれないため、上記のコミット件名チェックだけではすり抜ける
（ブランチ名由来の規約外件名がそのまま統合ブランチへ載る事象が実際に起きている）。これを防ぐため `pr-title.yml` が PR タイトルを規約
`種別(起点ID): 要約` に照合し、違反ならマージ前に CI を失敗させる。

- **`PR_NUMBER`（`github.event.pull_request.number`）を渡すこと。** 渡すと、末尾の `(#NNN)` が
  **PR 自身の番号**かどうかまで検査される。**渡さないと形状しか見られず、起点 issue の番号を
  書いた PR が素通りする**（上記「末尾の PR 番号」参照）。**未設定なら従来どおり形状のみを見る** ——
  コミット件名モードには PR 番号が無く、必須にするとスカッシュ後の履歴コミットが全滅するためである。
- 検査ロジックは `check-commit-messages.js` の単一件名モード（`--title` 引数 / `PR_TITLE` 環境変数）で、
  `validateSubject` を再利用する（規約の単一情報源）。
- `pull_request` の `opened/edited/reopened/synchronize` で起動し、タイトル後編集も再検査する。
- **bot 作成 PR の除外はスクリプト側（`BOT_AUTHORS` への完全一致）が担う**。Revert・`[skip ci]` も同様にスクリプト側で除外する。
  **ワークフローの条件で `user.type != 'Bot'` により弾いてはならない**（GitHub App の PR も `Bot` であり、
  AI に委ねる経路でだけ検査が skipped になる）。配線の詳細は [別紙](../../docs/traceability-appendix.md)。

**事前防止と事後補正の使い分け**: `pr-title.yml` は**マージ前**の予防（規約外件名を止める）。
万一すり抜けて develop に規約外件名が入った場合は、履歴不変の原則（force push 禁止）に従い、
下記 CHANGELOG 生成時の `changelog-overrides.json`（`action: "remap"`）で**生成物のみ**是正する。
前者が第一防衛線、後者が最終手段という役割分担。

### 検査対象から除外する自動コミット

- **自動コミットの著者**: `dependabot[bot]` / `renovate[bot]` / `github-actions[bot]` 等の bot 著者。
- **マージコミット**: `--no-merges` により除外。
- **自動生成・リバート**: 件名に `[skip ci]` を含むコミット、および `Revert "..."`。

除外リストは `scripts/check-commit-messages.js` の `BOT_AUTHORS` と同時に更新する。

## CHANGELOG 生成時の誤記補正・除外規定

トレーサビリティは**既存の git 履歴を書き換えないこと**を大前提とする。過去コミットの起点 ID や
スコープに誤記があっても `rebase`／force push で修正してはならない。代わりに `scripts/gen-changelog.js`
が**生成時のみ**補正（`remap`）／除外（`exclude`）を適用する。宣言先は `scripts/changelog-overrides.json`。

**補正・除外はいずれも「履歴は不変・生成物のみ是正」という原則に従い、その根拠を各エントリの
`reason` に必ず残す。** 🔴 **配布時の `overrides` は空である**（`hash` は前方一致のため、他リポジトリの
SHA を引き継ぐと無関係なコミットを誤って差し替える）。書き方は
[`docs/traceability-appendix.md`](../../docs/traceability-appendix.md)。

## 是正・追随の母集合の取り方

表記の是正・ID の追随・条文の更新はいずれも「**どこまでが対象か**」を先に決める作業である。
**母集合の取り違えは、実装作業で最も繰り返し起きている事故**であるため、引き方を規則として定める
（実装リポジトリからの環流。planning#307）。

| # | 規則 | 破れたときに起きること |
| --- | --- | --- |
| 1 | **誤りの側から引く。** 正しい表記だけを検索語にしない | 正しい表記だけで引くと、**誤った表記を構造的に取りこぼす**（探しているのは誤りのほうである） |
| 2 | **あり得る形をすべて列挙してから引く** | 区切りは空白だけではない（TAB・バッククォート・全角括弧・wiki リンク）。**1 つの形だけで引くと、同一行で片方だけ直る** |
| 3 | **拡張子で絞らない。** パスの除外だけで取る | `--include` で絞ると対象言語のファイルが落ち、**一部だけ直して赤が入れ替わる**（直った気になる） |
| 4 | **行フィルタで絞らない。パスから引く** | 走査の末尾に `grep -i` を継ぐと、**該当行が語を含まないファイル**が落ちる |
| 5 | **軸を 1 本で終わらせない** | 軸を変えると出続ける（実測では 1 軸目 8 件に対し、2 軸目 +4、3 軸目 +7） |
| 6 | **引いた結果と、除外したものとその理由を作業仕様書に書く** | 事故は引き漏らしだけでなく「**黙って除外した**」ことでも起きる。除外の理由が残らないと、次の走査が同じ判断を再現できない |
| 7 | **数値・名前を 1 つ直したら、その値を持つファイルを全走査し直す。走査の出力を加工して読まない** | **指摘された 1 件だけ直すと、同じ値を持つ他の箇所が残る。**加えて「引き直したのに落とす」事故が 2 度実測されている —— **`head` で切った**（planning#317。ジョブ ID を check 名として転記した）と、**`sed 's/:.*#/: ...#/'` で潰した**（planning#318。`.*` の貪欲一致で各行がその行の**最後の `#`** まで潰れ、末尾に別番号を持つ 1 行が表示から消えた）。**切る・潰す・整形するのいずれも「見なかった行を見たことにする」同じ事故である。判断は生の出力に対して行う** |
| 8 | **走査対象に自分の記録が入るときは、記録を書く行為が母集合を動かす。走査がそのまま返す数を先に出し、除外と時点を明示する** | 数えたのは**書く前**、公開したのは**書いた後**になり、**手順どおり追試しても再現しない数**が残る。実測（planning#350）: 「26 行」と書いた**当の表が検索語を 1 つ含んでおり**、公開時点では 27 行だった。**「27 行 → 自己参照 1 行を引く → 26 行」と引き算を見せ、値はコミットで固定する** |

> **この規則を守っているかを見る機械は無い。** 規則 6 を提案した PR 自身が規則 6 を破っており
> （除外表を「全数」と称して 3 件を黙って落としていた。監査が検出）、**規則として書くだけでは
> 守られない**ことが実証されている。**作業仕様書のレビューで人が見る**前提で運用すること。
