## コンテキストと課題

ADR-0078 決定 1 は、存在秘匿の統制を「**応答の区別不能性**（HTTP ステータス・応答本文・**所要時間**）」と
定め、**射程に認証系の経路（ログインとパスワードリセット申請）を含める**と明文化した。
同 §残るもの は次のように書いている。

> **ログイン（SC-15 L573）のステータスコードは実測していない。** 決定 1 の射程には入るが、
> **リセット申請と同じ形の漏洩があるかは確かめていない。** 実装が実測して環流する。

**リセット申請側には門が 3 つ在る**（IADR-0347 ＋ `check-password-reset-mail.js` の T-10 / T-20）。
**ログイン側には 0 である。** `docs/screens/SC-13_login.md` は存在秘匿を
「**する**／理由: **Keycloak 既定挙動**」の 1 行で済ませている。

🔴 **「Keycloak 既定だから大丈夫」は導出であって実測ではない。** リセット申請側も同じ既定のままで
漏れていた —— 送出先が使えない状態では**実在する利用者名だけ 500、実在しないものは 200** を返し、
その差で利用者名を列挙できた（ADR-0078 のコンテキスト表・#1143 の実測）。
**ログイン側だけが導出で安全だと言える理由は無い。**

## 検討した選択肢

### ① どこで測るか

| 案 | 評価 |
| --- | --- |
| A. SPA の単体テストで測る | **不採用**。ログイン画面は **Keycloak のテーマ**であり SPA に無い（SC-13）。測っても本物の経路ではない |
| B. realm 宣言の静的検査（`check-realm-constraints.js`）へ足す | **不採用**。宣言は「文言を変えない」までしか言えず、**ステータス・所要時間は宣言に現れない**。加えてリセット申請側で「宣言が正しくても稼働状態は脆弱な組へ戻り得る」ことが実測されている |
| **C. 稼働クラスタに対して**、利用者が通る経路そのものを叩く門を置く | **採用**。リセット申請側（`check-password-reset-mail.js`）と同じ形にする。**同じ統制は同じ形で測る** |

### ② 比較器をどこから持ってくるか

| 案 | 評価 |
| --- | --- |
| A. 新しい正規化規則を書く | **不採用**。**同じ統制の比較器が 2 つになると、片方だけが直る。** リセット側で「フローの識別子と入力の再表示だけを伏せる」規則は既に練られている |
| **B. `check-password-reset-mail.js` から require して借りる** | **採用**。`normalizeConcealmentBody` ／ cookie ／ HTTP 器 ／ エッジ URL ／ ローカル CA を借りる。**足したのは export だけで、判定ロジックは 1 行も変えていない** |
| C. 共通ライブラリへ切り出す | 不採用。**利用箇所は 2 つで、切り出しは移動の diff を生むだけ**である。「同型の事故が 2 回起きたら」の条件も満たしていない |

### ③ 所要時間をどう扱うか

| 案 | 評価 |
| --- | --- |
| A. 閾値を置いて判定する | **不採用**。**ADR-0078 決定 1 が「本 ADR は閾値を定めない」と明記している。** 実装側で数字を置けば、それが確定値として固まる |
| B. 測らない | 不採用。**決定 1 が挙げた 3 面のうち 1 つを黙って落とすことになる。** #1245 の実測は、リセット申請側で**所要時間だけが判定器として働いた**ことを示している |
| **C. 測って出す。判定しない** | **採用**。IADR-0421 決定 6 が暫定閾値へ「暫定」と書き続けたのと同じ姿勢である |

## 決定

### 決定 1: 対にするのは「**失敗するログイン**」であり、**両側に同じ誤った資格情報**を使う

成功するログインは実在側にしか起こり得ないので対にならない（L1）。
実在する利用者名 ＋ 誤った資格情報 と 非実在の利用者名 ＋ **同じ**誤った資格情報 を対にする。
片側だけ別の文字列にすると、**その長さと内容の差が本文比較へ混入する**。

### 決定 2: 🔴 対の利用者名は**バイト長を一致させる。合わなければ測る前に落とす**

申請した利用者名は応答へそのまま反映されるので、**長さの違う名前を比べれば本文長は必ず違う**。
それは存在の漏れではなく**測り方の誤り**である（L6 で 1 度踏んでいる）。

既存の `makeAbsentUsername` は固定接頭辞つきで長さを選べないため、**長さを指定できる生成器**を
本スクリプトに持つ。生成した名前は realm 宣言と突き合わせて**不在を確認する**
（偶然の一致で「非実在のつもりが実在していた」測定になるのを防ぐ）。

🔴 **これは「測ってから気付く」形にしない**という決定である。長さの不一致は**前提の失敗**として、
1 リクエストも投げる前に落とす。

### 決定 3: 判定するのは**ステータス・リダイレクト先・本文**の 3 面。**所要時間は出すだけ**

| 面 | 扱い |
| --- | --- |
| HTTP ステータス | **判定する**（ADR-0078 決定 1 が明文化した面。**PR-0 の主題**） |
| リダイレクト先（`Location`） | **判定する**（#1245 本文の受け入れ基準が名指ししている） |
| 応答本文（正規化後） | **判定する** |
| **所要時間** | 🔴 **出すだけ。判定しない**（決定 1 が閾値を定めていない） |

出力には「**この標本数では所要時間から結論を出さない**」と明記する。
**書かなければ、出した数字が判断に使われる。**

### 決定 4: 🔴 標本数と間隔は **realm の宣言から導く。書き写さない**

失敗するログインを重ねると **実在側の利用者だけが一時ロックされる**（L3）。これは
①測定が途中から別の状態を測ることになり、②その利用者でログインする後段の門を巻き込む。

- 標本数 = **`failureFactor - 1`**（`bruteForceProtected` が true のとき）。**ロックの手前で止まる。**
- `bruteForceProtected` が false なら導ける上限が無いので、**測定の都合で決めた数**であることを
  定数のコメントに書く。
- `failureFactor` が読めない／1 以下なら **1（保守側）へ倒す**。
- 連続する失敗の間隔は `quickLoginCheckMilliSeconds`（宣言が無ければ**上流既定値を出典つきで**）＋ 余裕。
- **両側を交互に測る** —— 片側をまとめて測ると、実行機の負荷変動が片方だけに乗る。

### 決定 5: 🔴 CI では**最後**に置く。順序そのものを統制にする

本門は**意図的に認証を失敗させる**ので brute-force の計数を消費する。
既存の最後の門（`verify-oidc-edge-flow.sh`）は**成功する**ログインを通す。
本門をその後ろへ置けば、計数の消費が他の門へ波及しない。
自己試験は既存 2 つと同じく **k3d 起動の前**（門が壊れていれば測る意味が無い）。

### 決定 6: 空回りを緑にしない

- 片側でもログイン画面へ到達できなければ **fail**（「両方エラーだったので一致」を作らない）。
  🔴 **到達不能を報告したときは、それだけを名指しする** —— 後続の判定（標本 0 件・本文が違う）まで
  並べると原因の切り分けを誤らせる。
- **同じ側でステータスが測定中に変わったら fail。** 途中で状態が変わっている（一時ロック等）ので、
  その実行の結論は採れない。**平均して均さない。**
- 非実在名を作れなければ fail（陰性対照を置けない）。標本 0 件も fail。

### 決定 7: 🔴 **ロックアウトそのものは測らない**（導出として記録し、実測は PR-D へ送る）

`failureFactor` 回目の失敗を作れば「**実在する利用者だけがロックされる**」という
**もう 1 つの存在判定器**を測れる。**が、使い捨てスタックで意図的にロックを作ると後段と再実行の
前提が変わる。** 稼働クラスタでの意図的な状態作りは **#1245 PR-D の形**（利用者の手が要る）である。

**本門は realm の宣言から読める事実として出力に書くだけにする。**
🔴 **「測っていない」と書く** —— 書かなければ、この経路が確かめられたと読まれる。

### 決定 8: しないこと

- **所要時間の閾値を置くこと**（決定 3）。
- **realm を緩めて測りやすくすること** —— `bruteForceProtected` を切れば計数の制約は消えるが、
  **測る対象そのものを変えてしまう**（ADR-0026 の統制）。
- **リセット申請側の T-10 へ所要時間の軸を足すこと** —— #1245 のコメントが「筋である」と書いているが、
  **閾値が無いので判定にはできず**、本 PR の射程（ログイン経路）でもない。**残件**（フォローアップ (3)）。
- **PR-B（近接 MTA の観測）へ触れること** —— 着地済みであり、IADR-0421 決定 8 が
  「SC-10 の画面へキューの数字を出さない」と定めている。**触れば無断で覆すことになる。**
- **`check-password-reset-mail.js` の判定ロジックを変えること** —— 足したのは export だけである。

## 理由

- **同じ統制を同じ形で測ることにしたのは、比較器が 2 つあると片方だけが直るからである。**
  正規化規則（何を伏せて比べるか）は存在秘匿の判定そのものであり、**綴りの正本は 1 つ**でなければ
  「リセット側だけ直っている」状態が静かに生まれる。
- **長さの一致を前提条件にしたのは、同じ失敗が既に 1 度起きているからである。** #1245 の実測は
  「本文長が 16 バイト違う」という**もっともらしい結果**を出した。もっともらしいから危ない ——
  **測り方の誤りは、赤ではなく「発見」の顔で出てくる。**
- **所要時間を判定しなかったのは、計画が「実測してから定める」と言っているからである。**
  実装側が数字を置くと、それが**実測されないまま確定値として固まる**。
  出して、暫定であることを書き、判断は計画へ返す。
- **CI の順序を統制にしたのは、副作用が波及する形を仕組みで塞ぐためである。** 「後ろに門を足さない」と
  規約に書いても守られない。**最後に置けば、後段が無い。**
- **ロックアウトを測らなかったのは、測る行為が測定環境を壊すからである。** 導出は書ける。
  **書いたうえで「測っていない」と書く**ほうが、測って壊すより良い。

## 結果

- **良い影響**: ADR-0078 §残るもの が名指しした「ログインのステータスコードの実測」に**器が付いた**。
  ログイン経路の存在秘匿が、**文言の宣言 1 行**から**3 面の機械判定**になる。
  実在／非実在の応答が分かれたら CI が落ちる。
- **悪い影響 / トレードオフ**:
  integration-stack のジョブに 1 ステップ（標本数 × 2 × 往復 ＋ 間隔）が増える。
  brute-force の計数を**意図的に消費する**（ロックの手前で止めるが、消費はする）。
  所要時間の標本が少ない（`failureFactor` に縛られる）ので、**この門だけでは時間差を論じられない**。
- **測っていて、直していないこと**:
  🔴 **稼働で 1 度も走らせていない**（作業機にクラスタが無い）。自己試験 25 件と変異 13 本だけが実測である。
  L1〜L6 はリポジトリ内の走査と既存の実測コメントからの読みであり、本 PR の**稼働での確認ではない**。
  🔴 **所要時間は測っても判定していない**（決定 3）。
  🔴 **ロックアウト経路は導出であって未実測**（決定 7）。
  🔴 **測定対象の利用者は `pickTargetUser` が選ぶ 1 人だけ**であり、
  「利用者ごとに応答が違う」形は測っていない。
- **フォローアップ**:
  (1) **実測値を計画へ環流する**（ADR-0078 §環流 5）。**develop へのマージが起こす
  integration-stack の run が最初の実測になる。** その出力を #1245 と計画リポジトリの issue へ載せる。
  (2) **ロックアウト経路（実在側だけが一時ロックされる）を稼働クラスタで実測する**（#1245 PR-D）。
  (3) 所要時間の反復測定と閾値の確定（**計画の裁定を待つ**。#1245 PR-D）。
  (4) 閾値が定まったら、リセット申請側の T-10 にも所要時間の軸を足す（#1245 のコメントの指摘）。
