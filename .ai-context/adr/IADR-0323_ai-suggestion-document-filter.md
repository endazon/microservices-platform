# IADR-0323: AI 提案一覧の `documentId` 絞り込み

- 状態: Accepted
- 日付: 2026-08-31
- 決定者: claude（実装判断。#1104 の実測で確定）

## 起点・関連

- 起点: #1104「AI 提案一覧に `documentId` の絞り込みが無く、SC-03 が権限内 pending 全件を取得している」
- 出所: [[IADR-0300]] 決定 6（「SC-03 の文書での絞り込みは**当面クライアント側**に置く」）
  ＋ 同 §フォローアップ 2（追随 issue）。**本 IADR は決定 6 を予告どおり撤回するものである。**
- 関連する作業仕様書: [`20260831_issue-1104_suggestion-document-filter.md`](../specs/20260831_issue-1104_suggestion-document-filter.md)

## コンテキストと課題

`GET /graph/suggestions` は `state` と `kind` しか受けず、SC-03（文書詳細）の承認欄は
**利用者が読めるすべての `pending` 提案**を取得してブラウザ側で `sourceDocumentId` /
`targetDocumentId` を比較していた。

**着手前の実測（`develop` `9a4d1a9a`）**:

| # | 問い | 実測 |
| --- | --- | --- |
| 1 | ABAC は誰が評価しているか | **サーバのみ。** スコープを 1 回解決し、**提案 1 件ごとに両端の文書を引いて `AuthorizedNode.Authorize`（deny-closed）** を通す。クライアントは権限判定を 1 行も持たない |
| 2 | 件数の上限 | **どの層にも無い。** GraphService は `ToListAsync`（`Take` なし）、BFF は全件を読み直し、SPA は `filter` のみ。**取りこぼしは起きていない** |
| 3 | `documentId` の所属 | **文書の ID**（`GraphDocument.DocumentId` ＝ DocumentService の文書 ID の複製）。辺の ID でも提案の ID でもない。タグ提案は `SourceDocumentId` だけを持つ |

したがって欠陥は**秘匿ではなく規模**である —— 文書を 1 件開くたびに無関係な提案が全件転送され、
可視性解決の N+1（提案 1 件あたり両端 2 回の照会）がその全件に対して回る。

## 決定

### 決定 1: 絞り込みは**サーバ側**に置き、**可視性判定の前段**に入れる

`state` / `kind` と同じ層（DB の `Where`）に足す。可視性解決のループは 1 行も変えない。

- **判定の後ろに置かない・迂回しない。** 秘匿の実施点は端点の文書属性による ABAC だけであり、
  `documentId` は**転送量を減らす絞り**である。両者を混ぜると、絞りの不具合が秘匿の穴になる。
- 述語は `Source == id || Target == id`。**タグ提案も自然に拾える**（終点を持たないため）。
- ADR-0034 決定 1（ホップごと判定・終端でまとめて濾さない）に反しない ——
  絞りは**判定対象の集合を減らす**だけで、判定の位置も単位も動かさない。

### 決定 2: 権限外・不存在の文書 ID は **200 ＋ 空配列**（404 に倒さない）

- 単票（承認・却下）が権限外を 404 に倒す（ADR-0034 決定 2 / [[IADR-0272]]）のと矛盾しない。
  **単票は 1 件の資源への操作、一覧は集合への問い合わせ**であり、集合で存在を隠す形は**空集合**である。
  一覧だけ 404 を返すと、**そこだけが「その文書は在る／無い」を語る口**になってしまう。
- 実装は「述語を足すだけ」で自然にこの形になる ——
  存在しない ID なら一致 0 件、見えない文書なら可視性解決で全件落ちる。**文書の存在確認を先に行わない**
  （行った時点で「無い」と「0 件」を分ける分岐がコードに生まれる）。
- 3 通り（権限外 / 実在するが提案 0 件 / 不存在）が**同じ状態コードと同じ本文**を返すことを
  テストで固定する。**検出力のために「漏れ得る中身」を同じ DB に置く**（置かないと空の DB でも緑になる）。

### 決定 3: 値域の検査は `Guid?` の束縛に任せ、独自の error コードを足さない

`state` / `kind` は列挙であり `invalid_state` / `invalid_kind` を返すが、`documentId` は**列挙ではない**。
形式不正（UUID でない）は ASP.NET Core の束縛失敗による 400 でよい。
**`invalid_document_id` を新設しない** —— 値域の概念が無いところに検査の語彙を増やすと、
「どこまでが後段の値域検査か」が読めなくなる。形式不正は存在を漏らさない。

### 決定 4: BFF は `string?` のまま透過する（既定の補完も検証もしない）

`state` / `kind` と同じ作法（[[IADR-0276]] 決定 3 の系）。**BFF で `Guid` へ束縛しない** ——
束縛すると形式不正の 400 の出所が BFF と GraphService の 2 か所になり、片方が腐っても気付けない。

### 決定 5: SC-03 は client 側の間引きを**撤去**し、クエリキーを文書ごとに分ける

- `touches()` を消す。**サーバが返した行をそのまま描く**（SC-21 の `useAiSuggestions` と同じ作法）。
  間引きを残すと表示件数と取得件数がずれ、0 件が「無い」のか「絞られた」のか読めなくなる。
- 🔴 **クエリキーが文書ごとに分かれる**ため、承認・却下後の無効化も文書ごとになる。
  `useSuggestionActions(documentId)` へ引数を足した。**プレフィックス無効化は採らない** ——
  SC-21 は本 mutation を使わず（書き込みを一切しない）、広げる利得が無い。
- **SC-21 は変更しない。** `documentId` を送らない＝従来どおり権限内の全件が返る。

### 決定 6: 上限（`Take`）を新設しない

実測 2 のとおり上限はどこにも無い。導入するなら「打ち切ったこと」を利用者へどう示すかを
決める必要があり、SC-21 アクセス制御の「**件数にも現れない**」と衝突しないかの検討が要る。
**本作業の射程外**とし、作業仕様書 §未決事項 1 に残す。

## 理由

- 決定 1 の「前段に置く」は、**秘匿の実施点を 1 つに保つ**ためである。絞りと秘匿を同じ層に
  混ぜると、性能のための変更が秘匿の退行を招く経路ができる。
- 決定 2 は [[IADR-0009]]（Wiki 閲覧の 404 で存在を隠す）と同じ向きである。
  「無い」と「見えない」と「0 件」を**応答として同一にする**ことが目的であり、
  どの状態コードを選ぶかは資源の単位（単票か集合か）で決まる。
- 決定 5 の「間引かない」は [[IADR-0300]] 決定 6 が採れなかった形である。
  同決定は「後段の変更を伴うため射程外」と述べており、**本 IADR はその条件が満たされたので実行する**。

## 結果

- 一覧の N は「その文書に触れる提案の数」へ縮む。可視性解決の N+1 もそれに比例する。
- **一括承認の不変条件に触れない** —— 増えたのはクエリパラメータだけで、ルートは増減しない
  （FR-18 / [[IADR-0276]] 決定 1。GraphService と BFF の両方のルート表走査テストが緑のまま）。
- SC-03 の承認欄は文書ごとに独立したキャッシュを持つ。文書を跨いだ再取得は起きない。

- フォローアップ:
  1. **一覧の件数上限**（決定 6）。打ち切りの表示を決める裁定が要る。
  2. `docs/api/BFF_bff-surface.md` の `/bff/graph/*` 群の欠落（[[IADR-0300]] フォローアップ 4）は
     未着手のまま。本作業の宣言ファイル領域の外である。
