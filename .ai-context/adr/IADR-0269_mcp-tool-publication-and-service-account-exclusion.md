# IADR-0269: MCP ツールの公開経路を 1 本に閉じ、サービスアカウントの個人資料除外を 2 層で強制する

- 状態: Proposed
- 日付: 2026-08-23
- 決定者: claude（実装担当）

## 起点・関連

- 関連する計画書 ID: FR-16 / UC-08 / UC-09 / SC-12 / ADR-0024 / ADR-0034 決定 9 / ADR-0054
- 関連する実装仕様書: `.ai-context/specs/20260823_issue-445_mcp-server-integration.md`

## コンテキストと課題

計画は MCP 統合について次を確定させている。

1. 公開は**許可リスト方式**（既定は非公開）。ツール定義はサービスの自己申告から動的に構成する（ADR-0024 §決定）。
2. **サービスアカウント実行では個人資料（`private-note`）を一律で対象外とする**（ADR-0034 決定 9）。**探索系に限らず検索系・文書取得系にも適用する**（11_mcp-server-integration §6）。
3. ツール応答は**外部 LLM へ渡る前提**で扱い、**MCP サーバーが文書単位に送信可否を判定してフィルタする**（UC-08 基本フロー 5）。

一方で計画は「ツール定義スキーマ・自己申告エンドポイント規約・C# SDK 選定の詳細は実装リポジトリで設計する」と明示的に委任している（ADR-0024 §結果）。委任された範囲で決めるべきことが 4 つある。

- (a) 公開ツールをどう表現し、どこで解決するか（コードへ固定するか、動的に解くか）
- (b) 個人資料の除外をどの層に置くか
- (c) ツール応答の形（文書単位のフィルタを成立させる足場）
- (d) 申告スキーマの置き場所（共有契約か、サービス内か）

## 検討した選択肢

### (a) ツールの解決方法

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A-1 | 公式 SDK の属性ベース登録（`[McpServerTool]`）でツールを宣言する | **却下。** 公開ツールがコンパイル時に決まり、サービス追加のたびに MCP サーバーの改修が要る。これは ADR-0024 が案A（静的実装）として**明示的に却下した形**である |
| A-2 | 公式 SDK の**動的ハンドラ**（`WithListToolsHandler` / `WithCallToolHandler`）で、実効ツール一覧から解決する | **採用。** 「自サービスに `/internal/mcp-tools` を実装」＋「公開構成へ追記」の 2 手順でコア改修を不要にする（ADR-0024 §決定） |

### (b) 個人資料の除外の置き場所

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B-1 | 要求側だけ（下流へ「個人資料を除け」と伝える） | **却下。** 下流の実装を信用することになる。**下流は 1 つも実装されていない**（`/internal/mcp-tools` は実測 0 件）ので、信用する相手が存在しない |
| B-2 | 応答側だけ（返ってきた文書から落とす） | **却下。** 下流が個人資料を実際に検索・探索する処理を行ってしまう。ADR-0034 決定 1 が「中間結果・ログ・キャッシュ経由の漏洩面」を理由にホップごと判定を選んだのと同じ論法で、下流に持たせない方がよい |
| B-3 | **両方**（要求側の制約 ＋ 応答側の fail-closed フィルタ） | **採用。** 下流が制約を無視しても応答側で止まる |

### (c) ツール応答の形

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C-1 | 下流の応答を素通しする（MCP サーバーはプロキシ） | **却下。** UC-08 基本フロー 5 が「MCP サーバーが文書単位に送信可否を判定し応答をフィルタする」と定めており、MCP サーバーが文書のメタデータを読めなければ成立しない。統制が各サービスの実装頼みになる |
| C-2 | **共通エンベロープ**（`documents[] { document_id, title, attributes, body?, reference_url? } / total_count / truncated`）を申告規約の一部にする | **採用。** 個人資料の除外・越境判定・件数の是正がすべて 1 箇所で成立する |

### (d) 申告スキーマの置き場所

| 案 | 内容 | 評価 |
| --- | --- | --- |
| D-1 | `Platform.Shared.Contracts` へ置く | **今は却下。** プロセス内の生成側が 1 つも無く、利用者が 1 人（MCP サーバー）しかいない契約を全ユニットへ配ることになる |
| D-2 | `McpServer.Api` 内に置き、**最初の生成側が実装された時点で昇格**させる | **採用。** 昇格の条件を本 ADR に明記して先送りの根拠を残す |

## 決定

**決定 1**: 公開ツールは**動的ハンドラ**で解決する。`ToolCatalog` が「サービスの自己申告 ∩ 宣言的公開構成」を保持し、`tools/list` と `tools/call` の両方がそこだけを見る。**既定は非公開**であり、突合は**公開構成を起点に申告を探す向き**で書く（申告を起点にすると構成の書き漏れが「公開されてしまう」側へ倒れる）。

**決定 2**: **ツール呼び出しの経路は `ToolInvocationService` 1 本に閉じる。ツール名で分岐しない。** ADR-0034 決定 9 の除外は「探索系・検索系・文書取得系のすべて」に適用されるため、経路が分かれていると 1 本の入れ忘れで静かに破れる。

**決定 3**: 個人資料の除外は**要求側（`ToolInvocationScope.ExcludePrivateNote`）と応答側（`ServiceAccountDocumentFilter`）の 2 層**で強制する。応答側は主体がサービスアカウントのときだけ働き、**除外した文書は件数からも外す**（ADR-0034 決定 2・4 の存在秘匿）。

**決定 4**: 個人資料の判定は **`doc_scope == "private-note"` の集合帰属**で書く。**否定（`!= "organization"`）で書かない。** `doc_scope` は新設で実データ 0 件・既存文書へ遡及付与しない方針（ADR-0054 §結果）であり、否定で書くと属性を持たない組織文書が一斉に落ちる。WikiService（ADR-0046 D-01 の実装）と同じ向きである。

**決定 5**: ツール応答は共通エンベロープ（決定 (c) の C-2）とする。

**決定 6**: 申告スキーマは当面 `McpServer.Api` 内に置く。**昇格の条件は「いずれかのサービスが `GET /internal/mcp-tools` を実装したとき」**であり、そのとき `Platform.Shared.Contracts` へ移す。

**決定 7**: 初期公開範囲外のツール（`ai.*` および `get_cluster_summary`）は**公開構成に書けない**ようスキーマ検証で弾く。公開範囲を広げるには計画の後続 ADR が要る（ADR-0024 §決定）。

**決定 8**: サービスアカウントへ `doc_scope=private-note` を割り当てる要求は、**公開構成のスキーマ検証と管理 API の両方**で拒否する。検証関数は 1 つを共用する（2 箇所に書くと片方だけが緩む）。

## 理由

- 決定 1・2 は「統制の適用点を数えられる状態に保つ」ためである。適用点が 1 つなら、そこにテストを置けば全経路を覆える（実際に 3 経路を `[Theory]` で回している）。
- 決定 3 は ADR-0034 §理由 決定 1 の論法（中間結果・ログ・キャッシュの漏洩面を構造的に消す）をそのまま持ち込んだものである。
- 決定 4 の代償は「`doc_scope` を持たない個人資料が漏れる」ことだが、ADR-0054 決定 3（必須属性）・決定 5（システム投入経路の既定は `organization`）により計画上そのような文書は生じない。**既存実装と向きを揃えることを優先した。**
- 決定 6 は「利用者が 1 人しかいない契約を共有物にしない」ためである。共有契約は破壊的変更の検査対象になり、変更のたびに全ユニットが影響を受ける。

## 結果

- 良い影響:
  - 個人資料の除外が**全ツールに構造的に適用**され、ツール追加時に入れ忘れが起こり得ない。
  - 公開範囲が Git 管理の構成 1 枚に集約され、逸脱（`ai.*` の公開）が起動時に止まる。
    ［2026-08-23 追記 / #445］**起草時点の実装ではこれが成立していなかった。** 検証は
    `ToolCatalogRefresher`（`BackgroundService`）の定期実行の中だけで走り、そこで例外が
    握り潰されていた。`BackgroundService` の開始は要求の受け付けを塞がないため、**壊れた構成でも
    Web サーバーは起動し、カタログは空のまま、周期ごとにエラーログを吐き続ける**——
    「公開されているつもりの公開されていない」状態がヘルスチェック緑のまま継続する。
    是正: **要求を受ける前に一度だけ同期的に検証する**（`Program.cs`）。あわせて常駐処理側でも
    「構成の破損」と「収集の一時失敗」を分け、前者は伝播させてホストを止める。
    `ToolPublicationFailFastTests` が A-8（落ちる）と A-9（正しい構成では落ちない）の対で固定する。
  - 除外の向き（集合帰属か否定か）が**陽性対照テストで判別できる**（否定に書き換えると陽性対照が落ちることを実測した）。
- 悪い影響 / トレードオフ:
  - 下流サービスは共通エンベロープに合わせた `/internal/mcp/...` を実装する必要がある。素通しのプロキシより制約が強い。
  - 申告スキーマが当面 `McpServer.Api` にあるため、最初の生成側を実装する issue が昇格作業を負う。
  - `notifications/tools/list_changed` の**配信は未実装**である（カタログの版は進むが、セッションへ通知しない）。
- フォローアップ:
  - `notifications/tools/list_changed` の配信を実装する。
  - `RetrievalService` / `DocumentService` / `GraphService` に `GET /internal/mcp-tools` と共通エンベロープの実行口を実装する（それぞれの再実装 issue の射程）。
    - ［2026-08-28 追記 / #1020］**申告端点は 3 サービスとも実装した**（実効カタログは空でなくなった）。
      **共通エンベロープの実行口は実装していない** —— 権限伝播の方式が未決であり、本文で渡された
      `ToolInvocationScope` を信じる形（方式 B）は「そこへ到達できる誰もが任意の scope を主張できる」
      口になる。方式の裁定は別 issue へ切り出した（IADR-0292 決定 5）。
      **これに伴い決定 6 の昇格条件（最初の生成側の実装）は満たされたが、昇格は追随 issue へ回している**
      （`*.Contracts` への型追加は `scripts/contract-schema-baseline.json` の更新を伴い、#1020 の
      領域宣言の外だった。IADR-0292 決定 4）。**決定 6 そのものは変えていない。**
  - Istio Ingress の `/mcp` ルーティングとレート制限初期値（`deploy/` 配下）。
