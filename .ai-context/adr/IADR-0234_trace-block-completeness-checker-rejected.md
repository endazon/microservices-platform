# IADR-0234: trace ブロックの網羅性検査器は追加しない

## 状況

`docs/**/*.md` の trace ブロック（`<!-- trace: ... -->`）へ、本文改稿の根拠となった記録（実装ADR・作業仕様書）の ID を足し忘れる事故が 2 回続いた。`scripts/check-trace-blocks.js` は ID の**実在性と構造**だけを検査し、**網羅性**を検査しない——「この文書はどの ID を引くべきか」を機械が知らないためである。

本リポジトリの規約は「検査器・規約の追加は**同型の事故が 2 回起きたら**を条件とする」であり、**条件は満たされた**。#885 はこれを受けて判定規則の設計を求めた。同 issue は同時に「偽陽性が多いと判明したら『足さない』という結論も可。その場合はなぜ足さないかを記録して閉じる」と明記している。

🔴 **欠落は「誤りの側の文字列」では引けない。** 足りていない ID はそもそも文字列として存在しないので、`traceability.repo.md` 規則 9・10（誤りの側の語で全文書を走査する）では原理的に捕まらない。**新設した ID の側から逆に引く**必要がある。これが候補 A・B の共通の出発点である。

### 事故の帰属を訂正する（#885 本文の誤り）

| # | issue #885 の記載 | 実測による訂正 |
| --- | --- | --- |
| 1 | 「PR #883 の `iadrs:` に `IADR-0231` が無い」 | **PR #881 / `6c1185c` が正しい。** `git log -S "IADR-0231" 8abff2e -- docs/` のヒットは `6c1185c` **ただ 1 件**で、`74b0f99`（#883）は差分のどこにも `IADR-0231` を含まない |
| 2 | 「PR #884 で `tech-requirements.md` の `specs:` に**本作業の**仕様書 2 件が無い」 | 欠落は 2 件だが、**うち 1 件（`20260821_issue-455_wolverine-phase0-preconditions`）は前 PR #883 が追加した仕様書**である。「本作業の 2 件」ではない |

誤りの出所も特定した。`.ai-context/specs/20260821_issue-455_integration-tests-production-wiring.md` が「1 回目は PR #883 の `iadrs:` に `IADR-0231` を足し忘れた件」と書き、#885 がそれを転記している。**確定済み記録は書き換えない**ため、訂正は本 ADR に置く。

### 🔴 再現には PR ブランチの是正前コミットが要る（マージ後の履歴には残らない）

2 件とも**マージ前に AI レビューの指摘で是正された**。マージは squash（全コミットが単一親）であるため、**是正前の姿は develop の履歴に一切残らない**。`git log --first-parent` だけを見て「再現できない」と結論すると誤る。再現は `refs/pull/<n>/head` を fetch し、是正コミットの**直前**を見る。

| 事故 | PR | 是正コミット | 是正前の姿 |
| --- | --- | --- | --- |
| 1 | #881 | `2963742`（「本文を書き換えた 2 文書の trace ブロックへ IADR-0231 を足す」） | `41e067b` |
| 2 | #884 | `93d086a` | `144c0ff` |

## 決定

### 決定 1: trace ブロックの網羅性を検査する機械検査器は**追加しない**

`check-trace-blocks.js` の射程（実在性・構造）は変更しない。網羅性検査の不在は、以後「未着手」ではなく**本 ADR を根拠とする既知の設計判断**として扱う。

### 決定 2: 再発防護は PR 時の AI レビューに置き、その観点を明文化する

2 件とも AI レビューが捕捉し、CI は 2 件とも素通りした。防護をここへ置くのは能力の適所配置である（弁別に要るのは意味的関連の読解であり、それは LLM ができて正規表現ができないことである）。`claude-code-review.yml` のレビュー観点 1（トレーサビリティ）へ「新規 `.ai-context/` 記録の追加と `docs/**/*.md` の本文改稿が同居する PR では、改稿の根拠となった記録 ID が当該文書の trace ブロックへ追記されているかを確認する」を足す。

⚠️ **本 PR では実装しない。** `.github/workflows/**` は IADR-0230 の M-A（ファイル領域が検査器領域に閉じる）から外れ、単独 PR を要する。**別 issue #906 として起票済み**（決定 4）。

### 決定 3: 規約の裁定を先に仰ぐ。現存する同型の「欠落」は遡及是正しない

「本文を改稿した文書は、改稿根拠の記録 ID を trace ブロックへ追記する義務があるか」は**まだ裁定されていない**。裁定が下るまで、現存する欠落（下記「規約が未裁定である」節）は遡及是正しない。

### 決定 4: 追随作業は 2 件を別 issue として起票する

1. `claude-code-review.yml` のレビュー観点へ決定 2 の 1 行を足す（`.github/**` のため単独 PR）。**起票済み: #906。**
2. 上記の規約裁定を仰ぐ（planning への環流 issue）。**未起票**——裁定の依頼先と粒度は利用者の判断を要するため、本 PR では起票していない。

## 理由

### 理由 1: 候補 A は精度 2.6%（実測）

候補 A ＝「同一差分内で `.ai-context/specs/` または `.ai-context/adr/IADR-*.md` に**新規追加**があり、かつ `docs/**/*.md` が**変更**されているのに、その文書の trace ブロック `specs:`／`iadrs:` に新規記録が**含まれていない**なら違反」。

**有効母集合は全数で取った。** trace ブロックを導入した `7b6a234`（#872）以降、HEAD `8abff2e` までの first-parent **全 19 コミット**である。標本抽出はしていない。

| 指標 | 実測値 |
| --- | --- |
| 母集合 | 19 コミット（`7b6a234..8abff2e` の first-parent 全数） |
| 違反 | **38 件** |
| 赤コミット | **7 / 19（37%）** |
| 確認済み真陽性 | **1 件** |
| **精度** | **1 / 38 ≈ 2.6%** |

唯一の真陽性は `74b0f99`（#883）——仕様書 `20260821_issue-455_wolverine-phase0-preconditions` を新規追加しつつ `docs/tech/tech-requirements.md` を改稿し、`specs:` へ足さなかった。**この 1 件だけは是正されないままマージされ**、次の PR #884（`745da0f`）が事後に足している。

### 理由 2: 偽陽性の主因は調整で消せない構造である —— 束ね PR の直積

38 件のうち **32 件が単一の束ね PR `d61c5b9`（#878）** から出る。同 PR は新規記録 8 件（仕様書 6 ＋ IADR 2）を追加し docs 4 件を改稿するため、規則は**直積 8 × 4 = 32** を吹き出す。少なくとも 28 対は記録と文書に何の関係も無い（例: deploy マニフェスト CI の仕様書 × ユニット submodule 追加の how-to）。

**束ねは異常系ではない。** IADR-0230 がメタ作業について公認した運用であり、以後も定常的に起きる。つまりこれは「たまたま大きな PR があった」ではなく、**差分単位の直積という規則の形が、公認された束ね運用と直交している**ということである。

### 理由 3: 「過去 2 件の再現」と「偽陽性の許容」は両立しない（本 ADR の核心）

直積爆発への自明な対処は絞り込みである。最も効く絞り「**新規記録がちょうど 1 件のコミット／PR だけ発火**」を掛けると、実測で違反は 38 → **5 件**、赤は 7 → 5 コミットへ落ちる（発火対象 11 コミット）。32 件は一撃で消える。

**しかしこの絞りは事故 1 を再現不能にする。** 事故 1 の PR #881 は**仕様書 2 件＋ IADR 1 件＝新規記録 3 件**を追加した複数記録 PR だからである。実測：

```
### 事故 1 再現: PR #881 是正前 (41e067b)  (6c1185c^..41e067b)
  新規記録 3 件 (specs 2 / IADR 1) × 変更 docs 2 件 → 違反 6 件
    - docs/tech/tech-requirements.md  : iadrs に IADR-0231 が無い   ← 事故 1
    - docs/tests/TEST_STRATEGY.md     : iadrs に IADR-0231 が無い   ← 事故 1
    （他 4 件は仕様書 2 件 × 文書 2 件の直積）
単一記録制限を掛けた場合: 事故 1 の PR は新規記録 3 件 → 発火しない（再現不能になる）
```

したがって二者択一になる。

- **絞らない** → 事故 1・2 とも発火するが、精度 2.6%。しかも 32 件を生む束ね運用は公認済みで、再生産が止まらない。
- **単一記録に絞る** → 偽陽性は 5 件まで落ちるが、**検査器導入の根拠である 2 件のうち 1 件を検出できない**。

中間の絞りが成立するには、束ね差分の中で真の対（`74b0f99` の仕様書 × `tech-requirements.md`）と偽の対（deploy CI の仕様書 × submodule how-to）を分ける機械的特徴量が要る。**両者は差分上まったく同型である**——どちらも「同一差分に新規記録と docs 改稿が同居している」。分けているのは**記録と文書の意味的関連の有無だけ**であり、これは `check-trace-blocks.js` が「機械には分からない」として射程外に置いた「この文書はどの ID を引くべきか」問題そのものである。**検査器を書けなかった理由が、検査器の精度を上げられない理由としてそのまま再登場している。**

### 理由 4: そもそも是正した PR すら赤のままである

決定的な補強がある。事故 1 を**是正した後**の PR #881 head（`2963742`）へ候補 A を当てても、**違反は 1 件残る**。

```
### 事故 1 是正後: PR #881 head (2963742) → 違反 1 件
    - docs/tests/TEST_STRATEGY.md : specs に 20260821_issue-455_awesome-assertions-knowledge が無い
```

**事故を正しく直しても緑にならない検査器は、ゲートとして機能しない。** 作者は「直したのにまだ赤い」という状態に置かれ、残った赤を無視する以外の出口が無い。これは赤の常態化の最短経路である。

### 理由 5: 候補 A は PR を跨いだ欠落に原理的に盲目である

事故 2 の実測が示した。是正前 `144c0ff` で `tech-requirements.md` に欠けていた仕様書は 2 件だが、候補 A が指せたのは**当該 PR が新規追加した 1 件だけ**である。もう 1 件は前 PR #883 が追加した仕様書であり、「同一差分内の新規追加」を起点にする候補 A の視野に**構造的に入らない**。

```
### 事故 2 再現: PR #884 是正前 (144c0ff) → 違反 1 件
    - docs/tech/tech-requirements.md : specs に 20260821_issue-455_integration-tests-production-wiring が無い
    （20260821_issue-455_wolverine-phase0-preconditions は前 PR 由来のため検出不能）
```

PR を赤にするという意味では事故 2 も再現できる。しかし**欠落の全量は指せない**。「仕様書を先の PR で足し、文書を後の PR で直す」は普通の進め方であり、この盲点も定常的である。

### 理由 6: 候補 B（逆引き）は辺が無くて成立しない

候補 B ＝「新設した ID の本文が名指す文書を引き、その文書の trace ブロックに ID が無ければ違反」。事故 1 で辺が消える。

```
$ git show 8abff2e:.ai-context/adr/IADR-0231_xunit-v3-simultaneous-switch.md | grep -c "docs/"
0
```

**`IADR-0231` の本文は `docs/` を 1 件も名指していない。** 記録本文に影響先文書を名指す義務は無く、義務が無い以上、辺の欠落は仕様であって違反ではない。辿る辺が無いので事故 1 は再現できない。

これは特殊例でもない。`8abff2e` 時点の IADR **234 件のうち 47 件（20%）が本文に `docs/` という文字列を 1 度も含まない**（自分で全数走査した。「`docs/**/*.md` を具体的に名指す」というより厳しい基準を採れば盲目な集合はさらに広がるので、**47 件は下限**である）。候補 B は新規 ID の約 2 割に対して構造的に盲目であり、その中に事故 1 の当事者が含まれている。

「名指しを義務化する」案は、`trace` ブロックへの追記漏れを本文への列挙漏れに**置き換えるだけ**で、漏れの発生点が移動する。

### 理由 7: 規約自体が未裁定である —— 裁定が機械化に先行する

HEAD 時点で、**同型の欠落が現行文書に是正要求のないまま現存する**。走査して数えた結果は次のとおりである（数え方の単位で数字が変わるので明示する）。

- **作業（仕様書）単位で 5 件** —— `.ai-context/specs/` に記録がありながら、どの `docs/` の trace ブロックにも現れない仕様書が 5 件。
- **文書単位で 7 件** —— うち 1 件（#440 の作業）は 3 文書を改稿しているため。

代表例が `docs/functional/FR-11_llm-egress-routing.md` である。#440 の作業（`d61c5b9`）が本文を実質的に書き換え、**同じ差分で trace ブロックの `issues:` へ `#440` を足していながら、`specs:` は `[]` のまま**にした。ブロックを放置したのではない——**維持されているブロックの中で、1 つのキーだけが取り残された**。当該仕様書は自身の追随表で `docs/functional/FR-11`・`docs/operations/llm-model-pin-runbook.md`・`docs/tests/FR-11` の 3 文書を名指しているが、**3 文書のいずれもその仕様書を引いていない**。

さらに、規約導入時に遡及しなかった分の在庫がある。**`docs/` 118 文書のうち 61 文書が `specs:` を空または欠いたまま**であり、資料再編（`7b6a234`）以前には 1 文書 × 1 仕様書の曖昧さの無い対だけでも 66 件が残る。

**規則が実在し合意されているなら、これらはバグとして扱われているはずだが、誰もバグとして扱っていない。** AI レビューも人も要求したことがない。含意は順序の問題である。

> **裁定されていない規則を機械化すると、検査器は規約を執行するのではなく規約を発明する。**

発明された規則が精度 2.6% で赤を出し続ければ、本リポジトリが明示的に警告する事態——`check-backend-libraries.js` の「**赤の常態化は『赤を無視する学習』を生み、検査の目的そのものを壊す**」——へ直行する。しかも検査の射程（PR 差分か、木全体か）によっては最初から 61 文書ぶんの在庫の上で赤が点く。

### 理由 8: 「2 回起きた」への正対

検査器追加の条件が満たされたのは事実である。しかしこの規約の機能は**1 回目での過剰装備を止めること**であり、2 回目が生むのは「検査器を設計し、実測し、判断する」義務であって「追加する」義務ではない。#885 自身がその読みを明記している。

本 ADR はその義務の履行である。候補 2 案を設計し、有効母集合の**全数**に適用し、変異試験で検出力を確かめ、過去 2 件を PR ブランチの是正前コミットから再現し、そのうえで否と判断した。**怠慢の弁ではなく、実測に基づく棄却である。**

## 変異試験の作法（記録として残す）

候補 A の検出力は変異試験で確かめた。**この作法自体を記録に残す**——手順よりも、事故の防ぎ方に価値があるためである。

🔴 **変異を「文字列置換したから当たったはず」で済ませない。変異の前後を `parse` 結果で assert する。**

```
before の parse 結果に対象 ID を含む  かつ  after の parse 結果に含まない
```

が成り立たなければ **throw して止める**。置換の成否を戻り値や目視で判断すると、**変異が当たっていないのに別の理由でテストが落ち、変異試験が成功したように見える**事故が起きる。緑・赤・件数の増加はいずれも「当たった証拠」にならない。

この作法は実際に事故を捕まえた。試作の変異注入器は、キー名から正規表現を組み立てる際にエスケープが 1 段落ち（`\\s` → `\s` → 実質 `s`）、`^specs:\s*\[.*\]$` のつもりで `^specs:s*[.*]s*$` を当てていた。**素朴な実装なら「置換できなかった＝変異なし」のまま先へ進み、後段が別の理由で落ちて成功に見えた**可能性が高い。前後 assert が「変異注入に失敗: `specs:` の行が見つからない」で即座に止めたため、正規表現を組み立てない行単位の置換へ作り替えて解決した。

確認した挙動は 4 つである。

| # | 変異 | 期待 | 実測 |
| --- | --- | --- | --- |
| 0 | 変異なし（陰性対照） | 違反 0 件 | 0 件 |
| 1 | `specs:` から新規仕様書を落とす | 違反 1 件・当該 ID を指す | 一致 |
| 2 | `iadrs:` から新規 IADR を落とす | 違反 1 件・当該 ID を指す | 一致 |
| 3 | **当たらない変異**（存在しない ID を落とす） | **throw して止まる** | throw（「前提が不成立」） |

変異 3 が作法の本体である。**当たらない変異が黙って通る余地を残さない。** 併せて、変異が対象以外の ID を巻き添えにしていないことも残存集合の比較で assert した。

**候補 A に検出力が無いのではない**（変異 1・2 は確実に捕まる）。棄却の理由は再現性ではなく**精度**である。この切り分けを混同しないこと。

## 影響

- `scripts/` に変更は無い。CI ジョブの追加も無い。`scripts/README.md` への登録も無い（登録すべき検査器が無い）。
- `check-trace-blocks.js` の射程は据え置く。網羅性の不在は本 ADR が根拠を持つ。
- 現存する欠落（作業単位 5 件・文書単位 7 件、および遡及分 61 文書）は**是正しない**。裁定待ちである。
- #885 は「足さない」結論で閉じる。

## 却下した案

### 却下 A: 候補 A をそのまま入れる

精度 1/38 ≈ 2.6%、19 コミット中 7 赤。主因の 32 件は IADR-0230 が公認する束ね PR の直積であり、運用が続く限り再生産される。加えて、**事故を是正した PR ですら赤が残る**（理由 4）。棄却。

### 却下 B: 候補 A ＋ 単一記録制限

偽陽性は 38 → 5 件へ落ちるが、事故 1（新規記録 3 件の PR）を再現できない。「2 回起きたから作る」検査器が、その 2 回のうち 1 回を検出できないのでは導入根拠が崩れる。中間の絞りに必要な弁別子は意味的関連であり機械化できない（理由 3）。棄却。

### 却下 C: 候補 B（本文からの逆引き）

`IADR-0231` は `docs/` を 0 件しか名指さず、IADR 234 件中 47 件（下限）が同様に盲目。辺が無く事故 1 を再現できない。名指しの義務化は漏れの発生点を移すだけ。棄却。

### 却下 D: `error` ではなく `warn` にする

19 コミットで 38 回鳴る警告は、`error` と**同じ精度 2.6% のノイズにラベルを貼り替えただけ**である。`error` の赤の常態化が「赤を無視する学習」を生むのに対し、`warn` は**最初から「対応不要」という学習を制度として組み込む**——常態化を待つまでもなく、導入初日から無視されるものとして生まれる。真陽性 1 件を 37 件のノイズに沈めて提示する装置は、強度をどう呼ぼうと検出器として機能せず、レビュー時の注意資源を 37 回空費させる分だけ純粋に害である。棄却。

### 却下 E: baseline / ratchet を敷いて既存分を凍結し、新規分だけ見る

在庫 61 文書を凍結する発想自体は本リポジトリの他の検査器（カバレッジ床・ライブラリ ratchet）と同型で、検討に値する。しかし**在庫は問題の一部でしかない**。ratchet は「既存を許し新規を止める」装置であって、**新規分の精度 2.6% を 1% も改善しない**——束ね PR の直積は新規分としてそのまま鳴る。**加えて、規約が未裁定のまま baseline を切ると、「現状が正しい」という裁定を機械が既成事実として作ってしまう**（理由 7）。裁定より先には置けない。棄却。

## 残余リスク

本 ADR の論証で自覚しておくべき弱点を挙げる。**将来この決定を覆す人はここから読むこと。**

1. **標本が小さい。** 真陽性 1 件からの精度 2.6% は点推定であり、母集合 19 コミットでは分散が大きい。「AI レビュー 2/2 捕捉」も n=2 で、防護の実効性の主張としては弱い。ただし**本 ADR の核心（直積の構造・両立不能・未裁定）は標本サイズに依存しない論証**であり、精度が 2.6% でも 8% でも結論は変わらない。数字が動いたら結論も動く、と読まないこと。
2. **「両立不能」は悉皆証明ではない。** 実測で棄却したのは候補 A の素朴な族（無制限／単一記録制限）だけである。中間的な代理特徴（issue 番号の共有、仕様書ファイル名の slug と文書パスの語彙一致など）は実測していない。「意味的関連の代理はすべて失敗する」は演繹であって実証ではない。**有望な代理を持ち込む提案を門前払いする根拠は本 ADR には無い。**
3. **「事故」と「未裁定」の間に緊張がある。** 2 回を事故と数えながら規約は未裁定だと言うのは一見矛盾する。整合させる線引きはこうである——**改稿の直接の根拠となった記録の引用漏れ**（#881・#883 型。書き手自身が漏れと認め是正した）は狭義の事故。**本文が間接的に影響を受けた文書への追記義務**（FR-11 型）は未裁定。**そしてこの線引き自体が意味的である**——それが理由 3 の弁別問題と同じものだという点が、本 ADR の一貫した所見である。
4. **再開条件 1（下記）は検出手段を持たない。** 「AI レビューをすり抜けた漏れの事後発見」は、まさに機械検出できない事象なので、発見は後続作業での気付きに依存する。再発が起きても観測されない可能性がある。定期棚卸しの点検項目に入れれば緩和できるが、それ自体のコストとの見合いである。

## フォローアップ（反証可能な再開条件）

次のいずれかが観測されたら本決定は誤りであり、issue を起票して再検討する。

1. **同型の引用漏れが AI レビューを通過して develop へマージされ、事後に発見される。** これは決定 2 の防護の実効性への反証であり、この場合は「精度 2.6% の検査器でも無いよりましか」の再計算からやり直す。
2. **規約が裁定で確定し、かつ意味的弁別を要しない機械化可能な下位規則が定義された場合。** 🔴 **裁定の確定だけでは再開しない**——理由 3 の弁別問題は裁定後も残るためである。
3. **残余リスク 2 の代理特徴が具体的に提案された場合。** 本 ADR と同じ母集合（`7b6a234..8abff2e` の全数）で実測し、精度を突き合わせる。
