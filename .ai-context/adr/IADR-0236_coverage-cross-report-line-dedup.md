# IADR-0236 カバレッジ集計のレポート跨ぎ重複排除

## 状況

`scripts/check-coverage-floor.js` は **レポート内は行単位（`<class>` ごとの `<line>` 走査）で
重複排除しているのに、レポート間はレポート単位の集計値を単純加算していた**。
行単位のパーサは既にあるのに、行の同一性はレポートを跨いだ瞬間に捨てられていた。

| 場所 | していたこと |
| --- | --- |
| `parseCobertura()` | クラスを回して `classLineStats()` の結果を `totals` へ畳むだけ。**行番号を返り値に残さない** |
| `mergeTotals()` | 数値 4 本（`lines` / `covered` / `branches` / `coveredBranches`）を加算するのみ |
| `aggregateReports()` | `mergeTotals(parsedList)` を呼ぶだけ |

その結果、**共有ライブラリの行は、それを参照するテストプロジェクトの数だけ重複して分母に載る**。

### 実害（`#899` で実際に床が割れた）

`#897` が `Platform.Shared.Infrastructure.Tests` を 1 本新設したところ、develop の `Integration` が
落ちた。被覆の実態は 1 行も悪化していない —— **分母だけがふくらんだ**。

| | `b93d469`（OK） | `071e356`（NG） | 差 |
| --- | --- | --- | --- |
| レポート件数 | 15 | 16 | +1 |
| `platform` 行数 | 12275（被覆 2962） | 13224（被覆 2971） | **+949 行 / 被覆 +9** |

🔴 **テストプロジェクトを増やすと床が下がる。** 新しいテストを書くほど分母が水増しされ、
**テストを増やす行為が床判定では罰になる**。ratchet の意図と逆である。

### 重複の規模（依存グラフからの実測。cobertura 実測ではない）

作業ツリーに `coverage.cobertura.xml` は 0 件のため、`.csproj` の `ProjectReference` 推移閉包と
`.cs` の行数概算で規模を推定した。

| プロジェクト | 到達するテストプロジェクト数（＝分母に載る部数） | 行数 |
| --- | ---: | ---: |
| `Platform.Shared.Contracts` | 15 | 122（概算） |
| `Platform.Shared.Infrastructure` | 14 | **772**（`Platform.Shared.Infrastructure.Tests` 単独レポートの `lines-valid`。独立概算 768・差 0.5%） |
| `Knowledge.Contracts` | 12 | 284（概算） |

`772 × 14 = 10,808` は分母 25,896 の 41.7% に当たるが、**14 部のうち 1 部は正当な計上である。
過剰計上は 13 部ぶん = 10,036 行（38.8%）。** これは上限の算術であって cobertura 実測ではない。

## 決定

### 決定 1: `parseCobertura` の返り値に行の同一性を持たせ、`aggregateReports` で畳む

パーサを作り替えるのではない。`classLineStats()` に行の配列を返させ、`parseCobertura()` は
**集計対象として残った行**（ユニット除外・生成コード除外を通り抜けた行）を `included.entries` として
返す。`aggregateReports()` が `foldLineEntries()` でレポート間の重複を畳む。

行数は CI 実測で全レポート合計 25,896 行・レポート 16 件の規模であり、
数万件の小さなオブジェクトを持つだけなのでメモリ上の問題にはならない。

### 決定 2: 🔴 キーは `(class name, 正規化した filename, 行番号)` の 3 つ組

**`(filename, 行番号)` では駄目である。** `IADR-0123` が選択肢 C を明示的に退けた理由がそのまま当たる ——
`Foo` と `<Foo>d__2`（非同期ステートマシン）のように**同一行を異なる観点で計測している行**を潰して
しまう。潰す際にどちらの `hits` を採るかは恣意的であり、coverlet や reportgenerator のどの集計とも
一致しなくなる。`<class name>` をキーへ含めれば、レポート跨ぎの重複だけを畳み、
同一レポート内の `Foo` / `<Foo>d__2` は別エントリのまま残る。

#### 🔴 生の `filename` をキーにしてはならない

`unitOfFilename()` は**同じファイルをレポートごとに違う文字列で返す**（`relative` / `absolute` /
`source-joined`）。`IADR-0123` 決定 4 の CI 実測は「そのまま(相対) 645 / `<sources>` 結合 1391」であり、
**同一 CI 実行の中で両形が混在している**。生パスをキーにすると重複排除が一部にしか効かず、
しかも診断には何も出ない（**無音の部分適用**）。

キーは `attribution.resolved` を `SRC_UNIT_RE` の最初のマッチ位置＝`src/<unit>/` の先頭以降へ
切り詰めた経路とする（`dedupFileKey()`）。**大文字小文字は潰さない** —— CI は Linux で大小が意味を
持ち、潰すと「別ファイルを畳む＝分母過小＝床が甘くなる」方向に壊れる。畳み残し（分母過大）は
保守的な壊れ方であり、その逆は退行を隠す。

帰属できない行（`unit === null`）は正規化できないので**生パスをキーにし、その行数を診断へ出す**。

#### 既知の限界: 内側の `src/` に食い付く

`Services/<X>/src/<X>.Api/…` のように**内側にも `src/` を持つ**経路では、最初のマッチが内側 `src/` に
当たる（`unitOfFilename` の帰属も同じ位置で当たっており、本決定はその規則を変えない）。
内側 `src/` に当たる場合、切り出される接尾辞は `<sources>` の深さに依らず同一なのでレポート間で
キーは揃う。揃わないのは**絶対パス形**が混在したときだけで、その場合は先頭側の `src/<unit>/` に
当たってキーが割れる —— 方向は**畳み残し（分母過大＝保守的）**であり、決定 5 の診断に変動として
現れる。`IADR-0123` 決定 4 の CI 実測では絶対形は 0 件だった。

### 決定 3: 被覆は OR、分岐は `max`。🔴 これは分岐の測定定義の変更である

同じキーの行が複数レポートに出たら、フィールドごとに `max` を採る。

| フィールド | 畳み方 | 意味 |
| --- | --- | --- |
| `hits` | `max` | `max > 0` なら被覆＝**OR**。`countLinesUnique()` が class 内で既に採っている規則と同じ |
| `branches` | `max` | 分岐分母 |
| `coveredBranches` | `max` | 分岐分子 |

各レポートで `coveredBranches <= branches` なので `max(coveredBranches) <= max(branches)` が成り立ち、
分子が分母を超えることはない。

🔴 Cobertura の `<line>` が分岐について持つのは `condition-coverage="50% (1/2)"` という**個数だけ**で、
**どの分岐が通ったかの識別子が無い**。レポート A が分岐 1 を、B が分岐 2 を被覆していても
（真の和集合は 2/2）合成できず `1/2` にとどまる。`max` は真の和集合の**下界**であり、
誤差は常に「実際より低く見える」方向にしか出ない（床の検査としては fail-safe）。

`IADR-0123` 決定 4 の 2026-08-04 追記により、**分岐の定義の変更は床の置き直しとセットでしか
行えない**。よって本 IADR は `src/coverage-floor.json` の置き直しを同一 PR で行う（決定 6）。

`source: 'methods-fallback'` のクラス（class 直下に `<lines>` が無く `<methods>` から拾ったもの）は
特別扱いしない。クラス内で行番号重複を排除済みの行が同じキー規則で登録される。

### 決定 4: 🔴 重複排除するのは `totals` だけ。`beforeExclusion` は単純和のまま

| 値 | 畳み方 | 理由 |
| --- | --- | --- |
| `totals`（**床が判定に使う**） | **重複排除後** | 本改修の目的 |
| `excluded` / `generated` | 単純和 | `IADR-0123` の混入行数（133 行）等の**既存の診断値の意味を変えない** |
| `beforeExclusion` | **単純和** | 🔴 下記 |
| `beforeGeneratedExclusion` | 単純和 | `#571` の前後比較は同一の測定基盤同士でしか意味を持たない |
| `diagnostics.unitTotals` / `raw` / `orphan` | 単純和 | 定義上レポート単位の観測 |
| `beforeCrossReportDedup`（**新設**） | 単純和 | 重複排除の前後比較用の観測点 |

`beforeExclusion` を畳んではならない。`IADR-0123` 決定 4 の照合相手（`diagnostics.reported`）は
**レポートごとの `lines-valid` を単純加算した値**であり、**coverlet はレポート間の重複を知らない**。
ここを畳むと、行側で唯一の反証装置が恒常的に「乖離・要調査」を出すようになり、
本当の前提破れと区別できなくなる。

そのため `aggregateReports` は重複排除**前**の単純和（`summed`）を保持し、
`beforeExclusion` を `summed + excluded + generated` から組む（**従来と同値**）。

#### 適用順: 除外が先、重複排除が後

除外（ユニット・生成コード）はレポートごとに従来どおり先に適用し、生き残った行だけを畳む。
順序で `totals` は変わらない —— 除外の述語は解決経路の純関数であり、同じキーの行はどのレポートでも
同じ側に分類されるからである。順序が効くのは診断量だけで、先に畳むと `excluded` / `generated` が
重複排除後の量になり、上表の決定と矛盾する。

#### 同一レポート内の同キーは畳まない

出現順の連番をキーへ足して衝突を避ける。これにより**レポート 1 件のときは重複排除が恒等になり**、
`IADR-0123` 決定 3・決定 4 の非退行が**構成上**保証される。畳むのはレポートを跨いだぶんだけである。

### 決定 5: 重複排除量を毎回診断へ出し、0 行なら notice

🔴 **`<class name>` がレポート跨ぎで安定していることは未確認である**（実装時に手元へ実レポートが
0 件だった）。`IADR-0138` 決定 3・`IADR-0195` 決定 2 と同じ「除外量 0 = フィルタ素通り」の作法で
可視化する。

毎回出す: 重複排除の前後の値・落とした行数（行 / 被覆 / 分岐）・重複していたキー数・
**出現レポート数の内訳**（2 部 n1 / 3 部 n2 / …）・正規化できなかった行数・
行番号を持たず畳めなかった行数。

**レポートが 2 件以上あるのに 0 行なら notice。** 正常に 0 行になり得るので fail でも warn でもない
（`IADR-0118` 決定 6 の段階ポリシー）。**1 レポートのときは出さない** —— 定義上恒等であり、
ローカル実行や単一フィクスチャで恒常ノイズになる。

### 決定 6: 床を置き直す

新定義での**全量実測**（`integration.yml`）から切り下げて置き直す。これは ratchet の引き下げでは
なく**測定定義の変更に伴う置き直し**であり、`IADR-0138` 決定 4 / `IADR-0195` 決定 3 と同じ性質である。
旧定義の床と新定義の床は分母・分子が違うため直接比較できない。

切り下げが機能する床を与えないときは `IADR-0195` 決定 3 の例外規則（1 つ下の整数）を当てる。
**分岐も必ず測り直す** —— 現行 27 に対し `#899` 時点の実測は 27.32% で余裕 0.32pt しかない。

> 実測値と測定条件は `src/coverage-floor.json` の `$comment` を正とする（**値の単一情報源**。
> ここへ数値を書くと置き直しのたびに自己矛盾する）。

## 影響

- **テストプロジェクトを増やしても分母が水増しされなくなる** —— ratchet の意図どおりに働く。
- 分母が大きく縮むため、床の絶対値は新定義で置き直しになる。
- 🔴 **`IADR-0232` が踏んだ「同じテストプロジェクトを 2 回実行すると分母が倍になり床が割れる」事故は、
  本改修後は fail ではなく無音になる。** 重複が畳まれて分母が倍にならないからである。
  その検知は**レポート件数の期待値**（`integration.yml` のコメント）と、決定 5 の
  「出現レポート数の内訳」に依存することになる。**`--filter` を足す変更をするときはそちらを見ること。**
- `excluded` / `generated` / `beforeExclusion` は単純和のままなので、CI ログ上で `totals` と桁が違う。
  診断文へ「レポート跨ぎの重複込み・単純和」と明記して取り違えを防ぐ。

## 検出しないこと

- **同じ行が別のクラス名でレポート間に現れる場合**（コンパイラが生成する型名が版で変わる等）。
  キーが割れて畳み残す。方向は分母過大（保守的）で、決定 5 の診断に現れる。
- **絶対パス形の filename が混在した場合**の畳み残し（決定 2 の「既知の限界」）。
- **分岐の真の和集合**。Cobertura に識別子が無いため原理的に取れない（決定 3）。
- **行番号を持たない `<line>`** と **class の外にある `<line>`**。畳めないため単純和で残し、件数を出す。

## 代替案

- **`(filename, 行番号)` をキーにする** —— `IADR-0123` が選択肢 C として退けた形。`Foo` と
  `<Foo>d__2` を潰し、どちらの `hits` を採るかが恣意的になる。**採らない。**
- **生の `filename` をキーにする** —— 同一 CI 実行の中で表記が混在するため重複排除が一部にしか
  効かず、しかも無音で壊れる。**採らない。**
- **`reportgenerator` に合算させる** —— tool restore のぶん CI が遅くオフラインで動かない
  （`IADR-0118` が同じ理由で退けている）。
- **テストプロジェクトごとに床を持つ** —— 床が 16 個並び、横断の退行を表現できない。
- **共有ライブラリをレポートから除外する** —— 被覆すべき手書きコードを測らなくなる。
  重複しているのは計測の仕方であって、コードが対象外なのではない。
