# IADR-0302: fan-out の待ち合わせは購読開始と実処理へ分ける

- 状態: Accepted
- 日付: 2026-08-29
- 決定者: 実装（#1038）

## 起点・関連

- 関連する計画書 ID: FR-02 / FR-06 / FR-13 / FR-14 / UC-04 / ADR-0018 / ADR-0027
- 関連する実装 ADR: IADR-0232 決定 1（統合テストを PR から後段へ移した判断）／IADR-0245（Wolverine 移行）
- 対象: `Knowledge.IntegrationTests.Messaging.DocumentUpdatedFanOutTests` /
  `QueueOverrideFanOutTests`

## 背景

fan-out の統合テスト 2 件が**非決定的に**落ちる（#1038）。**同一コードで結果が違う**ことが
証拠として記録されている —— ラウンド間の差分が `docs/` と `.ai-context/` だけで、
製品コードもテストコードも 1 バイト変わっていないのに 1 Failed → 3 Failed へ変わった。
失敗する購読者もフル実行と再実行で入れ替わっていた。

機序はコードから読める。両テストとも「発行 → 終端の副作用」を **30 秒**で待っており、
この 30 秒が

1. ブローカへの接続確立
2. コンシューマの購読開始
3. 実処理（Postgres への書き込み）

の**3 つをひとまとめに覆っていた**。全 70 件を並行実行すると Testcontainers の Postgres ＋
RabbitMQ ＋ 2 つのホストが同時に立ち上がるため、①② が予算を食い潰し、**実装が正しいのに落ちる**。

**#1032（`ConnectionStrings:DefaultConnection` 未設定で 28 件がホスト起動に失敗）を直したことで
初めてテスト本体に到達し、隠れていた脆さが露出した**という経緯も記録されている。

### 🔴 走査で分かった真因 —— 一度塞いだ起動レースが移行で開き直っていた

`FromSeconds(30)` を引き直したところ、#1038 が挙げていない 1 件が出た ——
`Knowledge.IntegrationTests/Fixtures/IntegrationTestFactory.cs` の
`MassTransitHostOptions.WaitUntilStarted = true` である。そのコメントはこう書いていた:

> WaitUntilStarted=true で レシーブエンドポイントのバインド完了までホスト起動を待機させ、
> **購読確立後に Publish されることを保証する**（Issue #33 の Bus 起動レース対策）

**この保証は ADR-0027 の Wolverine 移行で失効していた。** 実測:

| ホスト | 実測 | 帰結 |
| --- | --- | --- |
| `WikiService` | MassTransit を**参照していない**（csproj に無い） | 本設定は**完全な no-op** |
| `IngestionService.Worker` | `AddMassTransit` は残るが `UsingRabbitMq` ＋ `ConfigureEndpoints` のみで**コンシューマ登録が 0 件** | 待つべきレシーブエンドポイントが無い |
| 両者の `DocumentUpdated` 購読 | `AddWolverineStep` 側にある | `WaitUntilStarted` の射程外 |

**Issue #33 で一度塞いだ起動レースが、購読を MassTransit から Wolverine へ移したときに
黙って開き直り、「塞いだ」と読める記述だけが残っていた。** #1032 を直して
テスト本体へ到達するようになり、開いていた穴が観測にかかった。

本 IADR の決定 1 は、**失われた保証を Wolverine 側で復元するもの**である
（新しい仕掛けの発明ではない）。

## 決定

### 決定 1: 待ち時間を伸ばさない。**①② を独立した待ち合わせへ切り出す**

30 → 60 秒にすればおそらく落ちなくなる。**採らない。** #1038 が明示的に禁じているとおり、
それは**測らずに待ち時間を延ばすだけ**であり、**本当に遅くなっているのか（＝製品側の劣化）を
見逃す**。

代わりに、発行の前に**購読が `Accepting` になるまで待つ**。すると

- テスト本体の 30 秒は**実処理（③）だけ**を覆う予算になる → **据え置く**
- 購読開始（①②）は別枠・別の予算（120 秒）で待つ
- **落ちた場所がそのまま「どの段が遅いか」の答えになる**

🔴 **これは「合計の待ち時間を 30 秒から 150 秒へ伸ばした」のとは違う。** 伸ばすだけの変更は
どの段が遅いのかを一切教えないが、この形は**失敗した段が名前を持つ**。#1038 の切り分け要求
（受け入れ基準②）は、この分割そのものである。

### 決定 2: 購読開始の判定は `WolverineTracker.WaitForListenerStatusAsync` を使い、**期限切れで落とす**

`IWolverineRuntime.Tracker` が `ListeningStatus` の遷移を追っている。キューの Uri は
`rabbitmq://queue/<キュー名>` である。

**Docker 無しで確かめられる範囲を実測した**（記憶で書かない）:

| 確かめたこと | 実測 |
| --- | --- |
| キューエンドポイントの Uri 形 | `RabbitMqTransport.Queues["ingestion-service.DocumentUpdated"].Uri` = `rabbitmq://queue/ingestion-service.DocumentUpdated` |
| 未知のエンドポイントの状態 | `Tracker.StatusFor(uri)` = `ListeningStatus.Unknown` |
| 期限切れの挙動 | 存在しない Uri に 2 秒で待つと **2.0 秒後に `TimeoutException`** |

🔴 **3 つ目が決定的である。** この API が「待って諦めて何事もなく返る」型だったら、
購読していないのに緑になる **fail-open** を仕込むことになっていた。**投げると実測できたから採った。**

### 決定 3: 実到達時間を**緑のときも**出力へ残す

#1038 の受け入れ基準①は「fan-out の実到達時間をフル実行時に計測し、記録する」である。
**落ちてからでは測れない**ので、通った実行でも購読開始と実処理の秒数を
`TestOutputHelper` へ書き、失敗時は assert のメッセージにも載せる。

### 決定 4: 失効した保証の記述を、**効いている範囲だけを述べる形へ**書き直す

`MassTransitHostOptions` の設定そのものは残す（ConversionService の発行側は今も
MassTransit である）。**消すのはコメントの誤りであって設定ではない。**
「起動レースは塞いだ」と読める記述が、実際には塞いでいない状態で残っている —— これは
本 PR が繰り返し扱っている「**統制を定めた**と**統制が働いている**が読み分けられない書き方」
そのものであり、同じ扱いで是正する。

### 決定 5: `QueueOverrideFanOutTests` では、待ち合わせが**自己検証も兼ねる**

宣言 `queue` が効いていなければ、購読者はここで待っているキュー（前置つきの宣言値）を
聴かない。従来は「発行しても誰も受け取らない」という形で 30 秒後に落ちていたが、
本変更後は**「そもそも購読していない」段階で落ちる**。失敗の意味が 1 段はっきりする。

## 検討した代替案

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 30 → 60 秒へ延長 | ✕ | #1038 が禁じている。製品側の劣化を見逃す |
| `ActiveListeners()` を自前でポーリング | ✕ | Tracker が同じことを正しくやる。自前は「見つからないときどうするか」を毎回決める羽目になる |
| リトライ属性でテストを再実行 | ✕ | フレークを隠すだけで、遅さの出どころは分からないままになる |
| テストを `Skip` にする | ✕ | 手順 3 の退行を機械で捕まえられる**唯一の場所**である |

## 🔴 ［2026-08-29 追記 / #1038］**決定 1 の前提だった仮説は、実測で否定された**

本 IADR を起草した時点では「①② が③の予算を食い潰していた」を原因と見ていた。
**AI レビューの環境に Docker が在り**（過去 7 回のレビューが「無い」と記録していたのは誤り）、
対象 2 件を実コンテナで **3 回**走らせた結果、その仮説は否定された。

| 実測 | 結果 |
| --- | --- |
| `Knowledge.IntegrationTests` 全件 | **72 件 Passed / 対象 2 件が毎回 FAIL**（30〜34 秒） |
| 単独実行 / 同時実行 | **どちらでも同じ 2 件が失敗** |
| `_ingestionReady` / `_wikiReady` | 🔴 **どちらも 0.0 秒**（購読開始は即座に `Accepting`） |
| 失敗した購読者 | **実行ごとに入れ替わる** |

**①② を独立させて 0.0 秒で通過してもなお、③ の 30 秒で終端へ届いていない。**

### それでも本 IADR の決定を撤回しない

🔴 **決定 1 は「原因を直す」ためではなく「切り分ける」ために採った**（本文のとおり）。
#1038 の受け入れ基準②は「**遅さの出どころを切り分ける**」であり、
**①② が原因でないと測定で確定したこと自体がその基準を満たしている。**
待ち時間を 60 秒へ伸ばす直し方を採っていたら、テストは緑になり **切り分けは永久に得られなかった。**

決定 2〜5 も同様に有効である（失効した保証の是正・期限切れで落とす作法・実測値の記録）。
**変わったのは「これで直る」という見込みだけである。**

### 追加で否定した 3 つの筋（Docker 不要の範囲で実測）

レビューが示唆した「exchange の束縛が publish と競合しているのでは」を、Wolverine の実物を
反射して確かめた。**3 つとも否定された。**

| # | 疑い | 実測 | 判定 |
| --- | --- | --- | --- |
| 1 | 発行側と購読側のキュー宣言が食い違い `PRECONDITION_FAILED` でチャンネルが落ちる | 両者とも `durable=True` / `autoDelete=False` / `exclusive=False` / `args=[]` で**完全一致** | ✕ |
| 2 | `BindQueue` を 2 回呼んでも束縛が 1 本しか残らない | キュー 2 本それぞれに束縛 1 本ずつ（束縛は exchange 側ではなく**キュー側**に載る） | ✕ |
| 3 | 自動生成される束縛キー（`<exchange>_<queue>`）が違うので片方にしか届かない | exchange の既定型は **`Fanout`**。**ルーティングキーは無視される** | ✕ |

**メッセージは両方のキューへ届いているはずであり、残るのは消費側である。**

### 次の仮説（**まだ測っていない。断定しない**）

🔴 **Wolverine のハンドラは実行時に Roslyn でコンパイルされる**（[[IADR-0217]] が
「事前 codegen ＋ `TypeLoadMode.Static` は採らない」と決めている）。**その代金は
「最初の 1 通を受けたとき」に払われる。** 片方のコンパイルが 30 秒に間に合わないなら、
症状は観測と一致する —— 購読は始まっている／メッセージは届いている／終端の副作用だけが出ない／
**どちらが負けるかは実行ごとに変わる**／負荷が高いほど起きやすい。

**切り分けは 3 段ではなく 4 段だった可能性がある**: ①接続 ②購読開始 ③**コンパイル** ④実処理。

**確かめ方**: 計測用の 1 通を先に流して終端まで待ち、**そのあとで**検査対象を時間つきで流す。
前者が長く後者が短ければ支持される。`TypeLoadMode.Static` への切替も同型の対照になるが、
**[[IADR-0217]] の決定を覆すことになるので、測るためだけに変えてはならない。**

## 結果

- ✅ 30 秒の予算が**実処理だけ**を意味するようになり、負荷に依存する窓が 1 つ減る
- ✅ 落ちた段が名前を持つ（購読開始 / 実処理）
- ✅ 通った実行でも実到達時間が記録に残る
- 🔴 **#1038 は本変更では閉じない。** 受け入れ基準①③（フル実行時の計測・複数回の安定確認）と
  ④（`integration.yml` が緑）は **Docker のある環境でしか測れない**。本変更は
  **測定を可能にするものであって、測定そのものではない。** 実走の場は `integration.yml`
  （develop への push と日次）である
- 🔴 **①② が 120 秒でも足りない場合は、本変更では救えない。** そのときは
  「購読開始が遅い」という**別の問題**として現れる —— それが狙いである
- 🔴 **［2026-08-29］対象 2 件は依然として赤である。** 上の追記のとおり仮説は否定された。
  **本 IADR は「切り分けの器を置いた」ことの記録であって、「直した」ことの記録ではない。**

## フォローアップ

1. 🔴 **次の仮説（ハンドラの実行時コンパイル）を、Docker のある環境で測る。**
   上の「確かめ方」のとおり、計測用の 1 通を先に流してから検査対象を流す。
   **測らずに 2 つ目の仮説へ賭けない**（#1038 が明示的に禁じている）
2. `integration.yml` の次の develop 実行で出力された秒数を #1038 へ記録し、
   どの段が支配的かを判定する
3. 同型の待ち合わせは他の実ブローカ経路（`WolverineBrokerEdgeTests` /
   `RawDocumentFetchedEdgeTests`）にもある。**同型の事故が 2 回起きたら**共通化する
   （1 回目は記録に留める、が本リポジトリの規約である）
