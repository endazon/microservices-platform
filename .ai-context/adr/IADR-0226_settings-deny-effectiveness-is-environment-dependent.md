# IADR-0226: settings.json の自己書き換え防止 deny の実効性は実行環境依存である

- 状態: Accepted
- 日付: 2026-08-18
- 決定者: claude（PR #870 の AI レビュー 🔴 指摘への対応。利用者レビューは同 PR で受ける）

## 起点・関連

- 関連する計画書 ID: NFR（無採番。工程の統制＝ガードレールの実効性に関する記録）
- 関連する実装仕様書: [`docs/specs/20260818_issue-869_planning-pin-179a69a.md`](../specs/20260818_issue-869_planning-pin-179a69a.md) §7

## コンテキストと課題

`.claude/settings.json` は `deny` に `Edit(./.claude/settings.json)` / `Write(./.claude/settings.json)` を列挙し、末尾コメントは「deny は…本設定自体の書き換えも塞ぐ」と述べる。AI セッションが自分の許可設定を書き換えられないようにする第 1 層である（Bash 経由のすり抜けは `hooks/guard-bash.js` が第 2 層で塞ぐ）。

PR #870 の作業中、**利用者の明示依頼**を受けて本ファイルの【暫定デルタ】節（コメントのみ・撤去条件成立済み）を撤去した際、**リモート実行環境（Claude Code のクラウドセッション）では Edit がこの deny に遮られず適用できた**。同環境はプロジェクト `settings.json` の `permissions` を自セッションの権限判定に読み込んでいない。

一方で同環境には**独自の安全層（オートモードの権限分類器）**があり、次を実測した:

| 試行 | 結果 |
| --- | --- |
| コメントのみの Edit（権限の増減なし） | **許可**（本件の適用） |
| `permissions.allow` へのツール追加を含む Edit | **拒否**（権限拡張として遮断） |
| 権限拡張を含む settings.json の `git commit` | **拒否**（2 回とも） |

つまり「deny そのもの」は環境非依存の保証ではないが、無防備でもない —— リモート側は**変更の中身（権限を広げるか）**で判定する別系統の防御を持つ。

## 検討した選択肢

1. **事実を記録し、deny を「ローカル Claude Code に対する第 1 層」と位置づけ直す**（採用）
2. リモート環境からの settings.json 編集を規約で全面禁止する — 利用者の明示依頼による無害な整備（本件）まで塞ぎ、利用者作業へ押し戻すだけになる。**却下**
3. 何もしない — 「塞がれている」という誤った前提が残り、レビュー・監査が実効性を過大評価する。**却下**

## 決定

1. **`settings.json` の deny（自己書き換え防止）は、ローカル Claude Code セッションに対する第 1 層と位置づける。** 環境非依存の保証と読まない。リモート実行環境ではプロジェクト `permissions` が読み込まれず、代わりに環境側の分類器が「権限を拡張する変更」を遮断する（上表の実測）。
2. **AI セッションによる `.claude/settings.json` の変更は、実効する deny の有無に関わらず、利用者の明示依頼がある場合に限る。** 依頼なく撤去・緩和しない（本件は明示依頼に基づく。コミットメッセージと仕様書 §7 に経緯を記録済み）。
3. **キットの settings コメント（「本設定自体の書き換えも塞ぎ」）が環境条件付きである点は計画側へ環流する**（配布物の記述であり本リポでは直せない。環流 issue は本 ADR の追記で追跡する）。

## 理由

ガードレールは「効いていると信じられているが効いていない」状態が最も危険である（「緑だが検査されていない」と同型）。実測を記録し、層ごとの守備範囲（ローカル= deny + hooks / リモート=環境側分類器）を明示することで、レビュー・監査が正しい前提で判定できる。

## 残余リスク

- リモート環境の分類器の判定基準は本リポの管理外であり、versions によって変わり得る（無害な編集まで拒否する・逆に広めの編集を通す、の両方向）。settings.json の変更 PR は内容の如何に関わらず人のレビューを必須とする既存運用（ブランチ保護）が最終防衛線である。
