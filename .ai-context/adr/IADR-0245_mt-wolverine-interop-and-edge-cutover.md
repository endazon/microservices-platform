# IADR-0245 MT ↔ Wolverine の相互運用は成立しない。辺の切替は排出を必須段にする

## 状況

### 1. 辺を原子的に移しても、実行時には混在の窓が開く

[IADR-0234](./IADR-0234_wolverine-migration-boundary-455-441.md) 決定 3 は移行の単位をイベント辺（発行元＋全購読先を一括）と定めた。
これは**ソース上の整合**を保証するが、**実行時の整合は保証しない**。実測:

- **順序制御が無い。** Helm チャートに `argocd.argoproj.io/sync-wave` も `depends-on` も無く、
  唯一の hook は `drift-postsync-job.yaml` の PostSync だけである。`strategy:` の上書きも無い。
  **全サービスが既定の RollingUpdate で同時に転がる。**
- **キュー名が違う。** MassTransit は既定の `ConfigureEndpoints(ctx)`（フォーマッタ上書き無し）で
  キュー `RawDocumentFetched` を使い、exchange は URN 由来の
  `Knowledge.Contracts.Events:RawDocumentFetched` である（`EventMessageUrnTests` が固定）。
  Wolverine 側の共通ヘルパは `conversion-service.RawDocumentFetched` を購読する。

したがって窓は 3 つ開く。

| # | 窓 | 性質 |
| --- | --- | --- |
| 1 | 発行側 pod が先に切り替わる（新 = Wolverine 発行 / 旧 = MT 購読） | レース |
| 2 | 購読側 pod が先に切り替わる（旧 = MT 発行 / 新 = Wolverine 購読） | レース |
| 3 | **切替時点で MT のキューに残っているメッセージ。新購読者は別のキューを見ているので永久に排出されない** | 🔴 **決定論的**（レースではない） |

🔴 **`transportMismatches()` は静的検査であり、この 3 つを 1 つも見ていない。**
PR 時点では両側が Wolverine で整合して見えるため**検査は満たされる**。
**検査が満たされている瞬間こそデプロイが危険**という構造であり、
これまで本チェーンで見つけてきた「緑なのは誰も見ていないから」と同じ形である。

### 2. 相互運用は実測するまで誰も知らなかった

走査の結果、リポジトリ全体に **MT ↔ Wolverine 相互運用の記述は 0 件**、
**試験も 0 件**であった。W3 の実ブローカ器（#924）は **Wolverine ↔ Wolverine のみ**を試験する。

一方 `WolverineExtensions` は相互運用を意識した設計になっている
（「exchange 名には前置しない。前置すると発行側の exchange と食い違い『誰にも届かない』形になる」）。
**経路の命名は揃う方向に作られているが、エンベロープが解釈できる保証はどこにも無かった。**

## 実測

クラスタの RabbitMQ へ `kubectl port-forward` し、実ブローカ越しに両方向を測った。
**MassTransit の entity 名を自前の一意名へ上書きし、本番 exchange には一切触れていない。**
全フィールドへ非既定値を詰め、受信側で全項目を照合する形にした。

| 方向 | キューへ到達 | ハンドラ実行 | 失敗の現れ方 | 復旧可能性 |
| --- | --- | --- | --- | --- |
| **MT 発行 → Wolverine 購読** | ✅ 到達する | ❌ されない | 🔴 **黙って捨てる**（キュー深さ **0** / consumer **1 本** / 例外なし / ログなし） | **不可**。再生すべきものが残らない |
| **Wolverine 発行 → MT 購読** | ✅ 到達する | ❌ されない | `<queue>_error` へ **1 件**（`_skipped` ではない） | **可**。本体と理由が保全される |

### 方向 1 の詳細 —— 最悪の失敗モード

生 AMQP タップで、エンベロープがキューへ**届いていること**を確認した。

```
ContentType = application/vnd.masstransit+json
"messageType": [ "urn:message:Knowledge.Contracts.Events:RawDocumentFetched" ]
"attributes": { "confidentiality": "internal", "owner": "probe-team" }
"tags": [ "tag-alpha", "tag-beta" ]
```

**失敗はルーティングではなくエンベロープの解釈である。** MassTransit は本体を自前の封筒
（`messageId` / `sourceAddress` / `messageType[]` / `message: {…}`）で包む。Wolverine は自分の
フレーミングを期待し、解釈できないものを**受け取ったうえで捨てる**。

🔴 **運用上の帰結: 移行窓の間、メッセージは痕跡なく消える。**
キュー深さのアラームは鳴らない —— **キューが空だから**である。
再生すべきバックログも残らない。

なお本件では `messageType` に URN が 1 件しか載らず、**複数 URN の解決に至る前に封筒ごと捨てられた**。
基底型・インタフェースを含む複数 URN の扱いは**未測定**である（採らない方針が決まったため深追いしない）。

### 方向 2 の詳細 —— 生き残るし、見える

`_error` キューのメッセージヘッダ（`BasicGet` で覗き、**`requeue: true` で戻した**）:

```
MT-Fault-ExceptionType = System.ArgumentNullException
MT-Fault-Message       = Value cannot be null. (Parameter 'envelope')
MT-Fault-StackTrace    = at MassTransit.Serialization.SystemTextJsonSerializerContext..ctor(… MessageEnvelope envelope …)
MT-Reason              = fault
```

`_skipped`（consumer 不在）ではなく `_error`（逆シリアライズ失敗）である。
**本体と失敗理由が保全されるため、運用者は数えられるし再生できる。**

### 🔴 測定器の教訓 —— 本番と同じ構成で測らないと、自分のバグを製品のバグとして報告する

最初の probe の生ダンプは `"attributes": { }` / `"tags": [ ]` を示し、
**MassTransit の本番データ欠落バグ（ABAC 属性が落ちる）を報告する一歩手前だった。**

MT → MT の対照を先に走らせたところ `Attributes.Count=2 Tags.Count=2` で保存された。
空だったのは **probe が `Bus.Factory.CreateUsingRabbitMq` を使い、本番の
`AddMassTransit` ＋ DI 構成を使っていなかった**ためのアーティファクトである。
**欠陥は製品ではなく測定器の側にあった。**

**次に同種の測定をする人へ: 本番と同じ構成で測ること。対照を先に置くこと。**

### 排出完了の検証手段は実在する（実測）

RabbitMQ 管理 API（読み取り専用 GET）で、自前の一意名キューに 3 件投入し 1 件を unacked のまま保持して観測した。

```
GET /api/queues/%2F/<queue>
  messages                = 3
  messages_ready          = 2
  messages_unacknowledged = 1     ← in-flight が見える
  consumers               = 0
```

🔴 **`messages_ready` だけを見てはならない。** in-flight（unacked）は `messages_ready` に現れない。
排出の判定に使うのは **`messages`（= ready + unacknowledged）** である。

⚠️ **`consumers` は「処理中が無いこと」の証拠にならない。** 上の観測では 1 件を unacked で保持したまま
`consumers = 0` であった（`BasicGet` はポーリングで consumer 登録を伴わないため）。
**`consumers == 0` を「誰も処理していない」と読まないこと。**

## 決定

### 決定 1: dual-subscribe を採らない

実測により、**MT 発行 → Wolverine 購読はメッセージを痕跡なく破棄する**。
二重購読は必ずこの経路を含むため、**採れない。**

### 決定 2: dual-publish も採らない

各スタックが自分のフレーミングを読む限り動くが、窓 1・2 のいずれかで交差配送が起きた瞬間に
方向 1（黙って消える）を踏み得る。**重複配送と冪等性の負担を払ってなお、最悪の失敗モードが残る。**

### 決定 3: 🔴 IADR-0234 状況 2 の「二重購読は移行手順である」は、実行時には成立しない

> 🔴 ［2026-08-22 追記 / #441］**計画側が dual-subscribe を「足場」として明示的に許している。差し戻し中。**
>
> 本 IADR の起票後、planning#438（刻み幅をイベント辺へ訂正する環流）が受理され、
> planning 側 `12_backend-application-stack.md` が訂正された（反映コミット `8928c4c`）。
> **結論（イベント辺が正しい単位）は本 IADR と一致する**が、訂正文が次の子箇条を新たに入れた。
>
> > **CI が緑になる最小単位**: サービス単位の「**二重購読の追加**」まで小さくできる
>
> **これは本 IADR の実測と衝突する。** MT 発行 → Wolverine 購読は
> **メッセージを黙って捨てる**（キュー深さ 0・例外なし・ログなし）。したがってこの子箇条は
> **「CI は緑になるがメッセージは失われる」足場を推奨している**ことになる。

> **以後この追記は経緯の記録であって、有効な警告ではない。**

同 IADR は `check-event-topology.js` が二重購読を意図的に違反にしないこと
（`:44-46` / `:303-305`「これが『切替』を『追加』に分解して 1 PR を小さく保つための前提になる」）を
分解の根拠にしていた。**検査器の設計判断そのものは変えない**（静的検査として二重購読を止めない、は正しい）。
**しかし「だから二重購読で安全に刻める」という含意は、実測により否定された。**
検査器が許すことと、実行時に安全であることは別である。

### 決定 4: 辺の切替は「排出 → 切替」を必須段とする 3 段手順にする

| 段 | 内容 | baseline |
| --- | --- | --- |
| **a. 停止** | 発行元の新規発行を止める（該当イベントのみ） | 変化なし |
| **b. 排出** | MT 側キューの `messages`（ready + unacked）が 0 になるまで待つ | 変化なし |
| **c. 切替** | 発行元と全購読先を Wolverine へ一括で切り替える | **ここで落ちる** |

**窓 1・2 は段 a により消える**（発行が止まっているので交差配送が起きない）。
**窓 3 は段 b が正面から扱う。**

### 決定 5: 排出完了の述語は `messages` である。`messages_ready` と `consumers` を使わない

**述語の選択は今ここで決められる**（未解決ではない）。いずれも実測で出た**偽陰性**であり、
将来 drain を実装する人が最初に踏む罠である。

- 🔴 **`messages_ready` は誤った述語である。** in-flight（unacked）のメッセージは
  `messages_ready` に**現れない**。処理中のものを残したまま「排出済み」と誤判定する。
  **判定に使うのは `messages`（= `messages_ready` + `messages_unacknowledged`）である。**
- 🔴 **`consumers == 0` は「処理中のものが無い」を意味しない。** `BasicGet` は
  コンシューマを登録せずにポーリングするため、**メッセージを unacked で保持したまま
  `consumers` は 0 を返す**（実測: `messages_unacknowledged=1` かつ `consumers=0`）。
  **`consumers` を排出完了の根拠にしない。** 補助情報に留める。

実測（自前の一意名キューへ 3 件投入し、1 件を unacked で保持して観測）:

```
GET /api/queues/%2F/<queue>
  messages                = 3
  messages_ready          = 2      ← これだけ見ると「あと 2 件」に見える
  messages_unacknowledged = 1      ← in-flight
  consumers               = 0      ← 保持中なのに 0
```

### 決定 6: 未解決として残すもの（E1 の作業仕様書で決める）

**断定しない。ただし先送りもしない** —— 下記 3 点は **E1 の作業仕様書で決着させる**ものとし、
「E1 の設計で決める」と書いたまま実装へ入ることを禁じる。

1. **再充填の防止を何が保証するか。** 段 a の「発行を止める」を機械的に強制する手段は現時点で無い。
   設定フラグ / デプロイ手順 / `enabled:false` の宣言経由のいずれを採るかを、根拠つきで決める。
2. 🔴 **見えない発行元を機械的に列挙する手段が現状で無い。**
   `RawDocumentFetched` は `ConversionJobEndpoints.cs:70` の `bus.Publish(ev, ct)` からも発行されるが、
   **型名が発行行に現れないため `check-event-topology.js` からは見えない**（IADR-0234 状況 4）。
   これは同検査器の publish 検出が持つ既知の取りこぼしであり、**#921（トランスポート ratchet）が
   対処として起票済み**である。E1 は **#921 の着地を待つのか、E1 の範囲で手作業により列挙して
   作業仕様書へ固定するのか**を決める。**「止め忘れやすい」という注意喚起では足りない。**
3. **観測の瞬間性。** `messages == 0` はその瞬間の値であり、直後に増えない保証にはならない。
   **「T 秒間に N 回連続で 0」の N と T を決める。決め方の根拠も示す**
   （たとえば観測されたメッセージ処理時間の最大値から導く）。

### 決定 7: チェーン算術を改める

[IADR-0234](./IADR-0234_wolverine-migration-boundary-455-441.md) 決定 3 の `13 → 11 → 9 → 9 → 3 → 2 → 1 → 0` は
**各辺が 1 PR で落ちる前提**だった。決定 4 により **各辺が 3 段**になるため、刻みは次のように変わる。

- **baseline の行が落ちるのは段 c だけである。** 段 a・b は行を動かさない。
- したがって**到達値の列は変わらない**が、**PR 数が辺ごとに増える**（1 → 最大 3）。
- 段 a・b を 1 PR に束ねるか、運用手順（PR を伴わない）にするかは**未決**であり、
  **決定 6 の 3 点と同じく E1 の作業仕様書で決着させる**（実装へ入る前に答えを書く）。

### ［2026-08-22 追記 / #441］窓の対応の是正、および ADR-0052 / ADR-0053 の裁定を受けた決定 8・9

計画側の裁定（`ADR-0052` / `ADR-0053`。ともに `Accepted`・`8cc12fb` 他）を受けて、
**本 IADR の記述 1 件を是正し、決定を 2 つ足す。** 上の決定 1〜7 は覆さない。

#### 是正: 決定 2 の「窓 1・2 のいずれか」は誤り。方向 1 を踏むのは窓 2 だけである

上の §状況 の窓の表と §実測 の方向の対応は、次のとおりである。

| 窓 | 実行時の交差配送 | 方向 | 帰結 |
| --- | --- | --- | --- |
| 1（発行側が先） | Wolverine 発行 → MT 購読 | **方向 2** | `<queue>_error` へ `MT-Fault-*` つきで保全。**復旧できる** |
| 2（購読側が先） | MT 発行 → Wolverine 購読 | **方向 1** | **黙って捨てられる**（キュー深さ 0 / consumer 1 / 例外・ログなし） |
| 3（残留分） | MT キューの残メッセージ | — | 決定論的。新購読者は別キューを見る |

**決定 2 は「窓 1・2 のいずれかで交差配送が起きた瞬間に方向 1 を踏み得る」と書いているが、
窓 1 は方向 2 であり、方向 1 は踏まない。** 方向 1 を踏むのは**窓 2 だけ**である。

🔴 **それでも決定 2（dual-publish を採らない）の結論は変わらない。**
dual-publish は**両方向の交差配送を同時に起こす**構成であり、窓 2 の側で方向 1 を踏むためである。
**変わるのは理由の精度であって、決定ではない。** 是正するのは、
**「2 つの窓がどちらも同じ危険度である」と読めると、窓 1 側にだけ効く緩和策（`_error` からの再投入）を
検討する価値が見えなくなる**ためである。**2 方向は対称ではない**（§実測）。

#### 決定 8: 発行の検出が網羅的であることの担保方法（`ADR-0052` 決定 2 が実装へ委ねた分）

`ADR-0052` 決定 2 は、**担保の方法を移行前に定めて記録する**ことを求め、方法そのものは実装に委ねた。
**本決定がその方法である。**（同 ADR §結果 フォローアップ 2 が求める「記録の IADR 番号」は本 IADR である。）

> **なぜ「列挙する」だけでは足りないか**（`ADR-0052` 決定 2 の理由・引用）:
> 検査は発行側トランスポートを和集合で取るため、**取りこぼしが 1 件あれば検査は通っても意味を持たない**。
> 列挙の網羅性が示されない限り、手順 7・9 の緑は「違反が無い」ではなく「見ていない」を意味する。

**方法（4 段）。辺ごとに定義し直さない —— 本決定が唯一の定義である。**

1. **呼び出し「名」で過剰包含に走査する。**
   `\.(Publish|PublishAsync|Send|SendAsync)\s*[<(]` を、テストを除く実装ソースに対して掛ける。
   🔴 **イベント型名では引かない。** 型名で引くと `bus.Publish(ev, ct)` が落ちる ——
   **「型名が発行行に現れない発行経路を覆う」という条件を満たすのは、この段が名前で引くからである。**
2. **バス発行でないものを、理由を書いて落とす。** 実測では 17 ヒットから 4 件を落とした
   （HTTP の `SendAsync` 3 件 ＋ ドメインの状態遷移メソッド `doc.Publish()` 1 件）。
   **件数だけ書いて理由を書かないと、次の担当が同じ判断を再現できない。**
3. **残った各ヒットのイベント型を、渡している式の型を読んで確定する。**
   `ToEvent(...)` や `PrepareRetryAsync(...)` の戻り値型を辿る ——
   **共通の変換ヘルパ経由の発行を覆うのはこの段である。**
4. **結果を「バス発行の総数 / 検査器に見える数 / 見えない数」の 3 値で記録する。**
   実測（2026-08-22 時点）: **13 / 6 / 7**。

**何をもって「取りこぼしが無い」と言えるか —— 2 つの条件。**

- **条件 A（較正。1 回限り）**: 本方法が、**別の手段で独立に確立された既知の値を、教えられずに復元する**こと。
  Phase 0 の実測は「publish 検出が**実在 13 箇所のうち 7 箇所**を取りこぼす」と記録していた。
  上の 4 段は、その記録を参照せずに **13 / 6 / 7** を再現した。
  🔴 **手順が既知の正解を復元できたことが、手順の妥当性の根拠である。**
  列挙そのものは根拠にならない —— 列挙は自分の網羅性を主張できない。
- **条件 B（各回）**: **バス発行の総数が保存される**こと。
  移行は発行箇所を**消さない**。トランスポートを移すだけである。
  したがって前回記録との差は、**個別のコミットで説明できなければならない**（発行箇所の新設・削除）。
  🔴 **説明のつかない減少は、移行の進捗ではなく列挙の取りこぼしである。**

**限界（恒久的な保証ではない）。**

- 本方法は `Publish` / `Send` という**名前**に依存する。
  将来ラッパ（例: `IEventPublisher.Emit(...)`）を噛ませると**段 1 が取りこぼす**。
  🔴 **そのようなラッパを導入する PR は、段 1 の走査キーへその名前を足す責任を負う。**
- 名前に依存しない列挙は**型解析**が要る。これは **#921** の射程であり、本方法では埋まらない
  （決定 6-2 の限界はそのまま残る。**本決定は決定 6-2 を覆さず、その上に担保条件を足すものである**）。
- 条件 A は**一度しか使えない**（既知の値は消費される）。以後を支えるのは条件 B である。

#### 実測の追加: 偽の緑は 2 種類あり、union はそのうち片方でしか働かない

決定 8 を書くにあたって、`transportMismatches()` の和集合が**実際に何を隠すか**を測った
（#441 E1。`buildTopology()` を直接呼んだ測定と、差分を 1 つに絞った 2 段の合成実験）。

- **リポジトリ内のどのイベントも、検査器から見える発行元は最大 1 である**（実測。6 イベント）。
  したがって `pubTransports` に 2 トランスポートが載る状態は**自然には起きない**。
- 合成すれば起きる: 購読側を masstransit の記法へ変えると違反 1 件（EXIT=1）、
  そこへ**可視な masstransit 発行元を 1 つ足すだけ**で**違反が消えて EXIT=0** になる。**機構は実在する。**

🔴 **しかし偽の緑には 2 種類ある。**

| 型 | 残った旧発行元 | `pubTransports` | 実害 |
| --- | --- | --- | --- |
| (i) union 型 | **可視** | 2 要素 | 購読者は旧発行元からは受け取れる（**部分的損失**） |
| (ii) 不可視型 | **不可視** | 1 要素 | 🔴 **その発行元のメッセージは誰にも届かない（全損）** |

**(ii) で隠しているのは和集合ではなく不可視性そのものである** —— 発行元が `pubTransports` に載らない。
**実測（#441 E1）: 発行 ② を MassTransit のまま残しても、検査の終了コード・報告行・
`--update` 後の baseline のバイト列が 1 つも動かなかった**（対照との差 0 バイト）。

**したがって決定 8 の担保方法は、union 対策としてではなく (ii) 対策として要る。**
(i) は検査器が原理的に見えている状態の話であり、(ii) は見えていない状態の話である。
**列挙の網羅性が効くのは後者に対してである。**

#### 副産物: 発行側と購読側でトランスポートの導出規則が違う

- **発行側**: `transportsOfFile()` が**ファイル先頭の `using` 行**から導く（粗い。ファイル単位）
- **購読側**: `findSubscribers()` が**記法**から導く（`IConsumer<T>` / `Handle(T x`。精密）

**同一ファイルに両方の `using` が並ぶと発行が両トランスポートとして記録される問題（E1 で実際に踏み、
ファイル分割で解いた）が発行側にだけ起きるのは、この非対称性のためである。**

#### 決定 9: デッドレターの宛先トポロジ（`ADR-0053` 決定 4 が記録を求めた分）

`ADR-0053` 決定 4 は**宛先トポロジを計画として指定せず**、**実装が選んだトポロジを実装側の記録に残すこと**を
条件とした（**再投入＝人手での復旧の手順が宛先に依存する**ため）。**本決定がその記録である。**

**選んだトポロジ: Wolverine の既定である共有 1 本 `wolverine-dead-letter-queue` をそのまま使う。**
`WolverineExtensions.UsePlatformMessagingDefaults` は `MoveToErrorQueue()` を指定するだけで、
**宛先を上書きしない**（実測）。エンドポイント別へ分けることはしない。

- **理由**: 検知はキュー名に依存しなくなった（`ADR-0053` 決定 1）ため、**分ける利得が無い**。
  分ければキューが購読エンドポイントの数だけ増え、**再投入の手順もその数だけ増える**。
- 🔴 **移行の窓の間は 2 系統が並存する。** MassTransit 側は従来どおりエンドポイント別 `<queue>_error`、
  Wolverine 側は共有 1 本である。**再投入時はどちらに入ったかを先に確かめること** ——
  辺がどちらのトランスポートで動いていたかで宛先が変わる。
- **再投入の手順**（人手での復旧）: 共有 1 本のため、**メッセージ単位で元の宛先を見分ける必要がある**。
  Wolverine のエンベロープはヘッダに元の宛先を保持するので、そこで選別してから戻す。

**この決定で「先送りの孤児」が閉じた。** 従前この差（エンドポイント別 対 共有 1 本）は
「W3 の射程」として先送りされたまま閉じていなかった。`ADR-0053` が**検知をキュー名から切り離した**ことで、
**差そのものが通知の成否に影響しなくなった** —— 残ったのは再投入手順の記録だけであり、それが本決定である。

#### 🔴 本 IADR の実測が共有クラスタへ残した滞留（**本番のデッドレターではない**）

本 IADR の相互運用実測（MT ↔ Wolverine の双方向）は、**共有クラスタの RabbitMQ にメッセージを残した**。
2026-08-22 時点の読み取り専用の照会（`rabbitmqctl list_queues name messages ...`）で確認した残存は次のとおりである。

| キュー | messages | 由来 |
| --- | --- | --- |
| `wolverine-dead-letter-queue` | **3** | 本 IADR の方向 2 の実測（Wolverine 発行 → MT 購読の失敗分を含む） |
| `interop-b-*-q_error` | **1** | 同上。`interop-a` / `interop-b` は本実測が作った使い捨てキューである |

🔴 **これらは試験由来であって、業務イベントの失敗ではない。**

**なぜ記録するか**: `ADR-0053` 決定 1・3 の**デッドレター到達カウンタが将来入ったとき、
この 3 通が「本番のデッドレター」として数えられると誤診断を生む**。
カウンタの契機は「自動再試行を使い切ったこと」であってキューの滞留ではない（同決定 2）ため、
**カウンタ自体はこれらを数えない**はずだが、**キュー深さを見る運用（現行の `alerts.yml` の
`queue=~".*_error|.*_dlq"` の形）を併用すると拾ってしまう。**

**掃除は行っていない** —— 共有クラスタへの破壊的操作は行わない方針であり、
**消してよいかは利用者の判断である**。掃除するまでは本節が「これは試験由来である」の出典になる。

#### `ADR-0053` 決定 2 が求めた「判定の作り直し」の状況

`ADR-0053` 決定 2 の注記は、判定が `context.GetRetryAttempt() + 1 >= MassTransitExtensions.MaxAttempts` で
**旧トランスポートの API と定数に依存している**と指摘し、**移行時に新トランスポート側で作り直す**ことを求めた。

- **辺 `RawDocumentFetched` については #441 E1 で完了した。**
  `envelope.Attempts >= WolverineExtensions.MaxAttempts` へ作り直してある
  （**Wolverine の `Attempts` は 1 始まり**であり、MassTransit の 0 始まりに対する `+1` は外した）。
  境界の両側（上限 -1 / 上限）を試験で固定し、変異試験（`>=` → `>`）で検出力を確認済みである。
- 🔴 **残る辺は未着手である。** 他の辺が Wolverine へ移るまで、それらの判定は旧 API のままである。
- **カウンタ（`ADR-0053` 決定 1・3）は未実装であり、本 IADR の射程外**である。
  手順 10 の射程として別単位で扱う（**通知は現時点で 1 つも動いていない** —— `ADR-0053` 決定 5 のとおり、
  当面の通知手段は SC-07 のデッドレター標識と「失敗のみ」フィルタによる人手確認である）。


## 結果

- **E1 は本 IADR の着地後に着手する。** 前提（相互運用の可否）が実測で確定したため、設計をやり直せる。
- W3 の実ブローカ器は **Wolverine ↔ Wolverine のみ**を覆う。**MT ↔ Wolverine の試験は追加しない** ——
  採らない方式を試験しても保守負担が増えるだけである。本 IADR が実測の記録を持つ。
- 🔴 **決定 6 の 3 点は E1 の作業仕様書で決着させる。** 先送りすると、実装時に誰も決めないまま
  「たぶん大丈夫」で切り替わる。**仕様書に答えが書かれていない状態で実装へ入らないこと。**
- 見えない発行元の機械的列挙は **#921** の射程であり、本 IADR はその依存関係を記録するに留める。
