# IADR-0425: クラスタ検出（Leiden 法）は依存を足さず自前で実装し、乱択を外して決定的にする。未要約クラスタ数はクラスタ同一性の追跡の上で数える

- 状態: Accepted
- 日付: 2026-09-11
- 決定者: 実装（issue #1363 の受け入れ基準に従う）

## 起点・関連

- 関連する計画書 ID: `ADR-0035` 決定 2・3・5・6・8／`ADR-0083` 決定 1〜4／`FR-17`・`FR-18`／
  `SC-10`（運用ダッシュボードの健全性指標）／`SC-18`（知識グラフ画面）
- 関連する実装仕様書: `.ai-context/specs/20260911_issue-1363_leiden-clustering.md`
- 先例: `IADR-0299`（ナレッジ健全性の生産者と単一書き手化）／`IADR-0353`（陳腐化の起点時刻の選択）／
  `IADR-0389`（観測値へ内訳の軸を足した形）

## コンテキストと課題

**クラスタリングの実装がリポジトリ全体で 0 件であり**、それが単一の欠落として 2 つの epic を
同時に塞いでいた（#1363）。

- #443: 健全性 7 指標のうち `unsummarized-clusters` の**生産者が無い**。
- #450: `SC-18` の**クラスタ表示が無い**（止めていたのは表示形式ではなく、表示すべきクラスタが 1 つも
  無いこと）。

🔴 **裁定は既に降りていた。** `ADR-0035` 決定 3 が 2026-08-07 の時点で**Leiden 法・日次バッチ**と
方式を確定しており、`ADR-0083`（2026-09-06）が「クラスタ ＝ その検出結果。**SC-18 の表示単位も
健全性の計数単位も同じもの**」と射程を確定させ、決定 3 が `unsummarized-clusters` の定義を与えていた。
**それにもかかわらず `KnowledgeHealthCollector` には「計画の裁定待ち」というコメントが残っており、
次の着手者を止める形になっていた**（#1363 が名指しした行）。

したがって本 ADR が決めるのは**方式の選択ではない**（それは計画が済ませている）。**計画が定めて
いない実装判断**、すなわち「Leiden をどう実装するか」「日次で再検出したときクラスタをどう同定するか」
「未要約をどの材料で判定するか」である。

## 検討した選択肢

### 実装手段

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | **自前実装**（採用） | 依存が増えない。段（局所移動・細分化・集約）が読め、決定性を自分で担保できる |
| B | 外部ライブラリを足す | .NET に定番の Leiden 実装が無く、あっても NuGet 依存 1 件と CPM への追加、`backend-library-baseline.json` の ratchet の更新を伴う。**入力は文書 ID と重み付き無向辺だけ**であり、汎用グラフライブラリの表現力は要らない |
| C | 外部サービス（Python 等）へ出す | サービスが 1 つ増える。日次バッチのためにプロセス境界を跨ぐのは過剰で、`ADR-0002`（DB-per-service）の読み取りも越境させることになる |

### 未要約の条件 3（「所属文書の更新」）で使う時刻

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | **`UpdatedAt`**（採用） | 計画の字義（`ADR-0035` 決定 6「文書のいずれかが前回生成以降に**更新**されたか」）。多く数える側＝安全側 |
| B | `BodyUpdatedAt` | タグだけの更新で要約を作り直さずに済む。ただし計画は本文更新に限るとは書いておらず、**要約生成の費用が実測されていない段階で計画より狭く読むことになる** |

## 決定

### 決定 1: Leiden 法は自前で実装する（依存を足さない）

`Domain/Clustering/LeidenCommunityDetector.cs`。段は原論文どおり 3 つ（局所移動 → 細分化 → 集約）で、
modularity を目的関数とする。**入力の重みは辺の型の `EdgeType.Weight`** であり、
`ADR-0035` 決定 2（辺の型による重み付け）をそのまま使う。

🔴 **細分化（2 段目）が Louvain との差である。** Louvain は 1・3 だけを回すため、集約の前に
コミュニティが内部で分断されていても、それを畳んで 1 節点にしてしまう（以後どの段でも直せない）。
`ADR-0035` 決定 3 が「Louvain は分断されたコミュニティを生じ得るため採らない」と書いた理由がこれである。

⚠️ **原論文からの簡約を 2 つ明記する。**

1. **細分化の併合先の選択は、確率的選択ではなく増分最大（θ→0）である**（決定 2 の帰結）。
2. **well-connectedness の判定条件（γ-separation 等）は入れていない。** 得ている保証は
   「畳む単位が連結である」ことであって、原論文のより強い保証ではない。

### 決定 2: 乱択を使わず、決定的にする

走査順は**文書 ID の昇順**で固定し、乱数生成器を持たない（種も持たない）。

🔴 **これは性能や再現性のためではなく、指標が読めなくなるのを防ぐためである。** 日次バッチで
同じグラフから毎回違う分割が出ると、`ClusterReconciler` が毎日「構成が変わった」と判定し、
**全クラスタが恒久的に `composition-changed` で未要約に数えられる** —— 件数が
「要約が追いついていない量」ではなく「バッチが走った回数」を表すようになる。

引き換えに、局所最適の質は乱択版よりわずかに劣り得る。**用途は `ADR-0083` 決定 4 が求める
「クラスタ数のオーダーの実測」**であり、この取引は受け入れる。

### 決定 3: クラスタの同一性は Jaccard 係数 0.5 以上の貪欲な対応づけで追跡する

`ADR-0083` 決定 3 の条件 2（「クラスタ構成が変わった**後に**再生成されていない」）を判定するには、
**昨日のクラスタと今日のクラスタが同じものか**が要る。検出結果は文書 ID の集合でしかなく、
識別子を自分では持たない。

- 既存クラスタ × 検出結果の全対で Jaccard 係数を出し、**降順に貪欲へ 1 対 1 で確定する**。
- 🔴 **0.5 未満は対応づけない。** 過半の構成員を共有しないものを「同じクラスタ」と呼ぶと、
  **生成済みの要約がまったく別の文書集合へ引き継がれる。**
- 対応がついて構成が変わったときだけ `CompositionChangedAt` を前進させる。
  **同一なら触らない**（触ると決定 2 と同じ壊れ方をする）。
- 対応のつかない検出結果は新規、対応のつかない既存クラスタは消滅（所属・要約ごと削除）。

**却下した案: 構成員集合のハッシュを ID にする。** 実装は最小になるが、**構成が 1 件変わるたびに
クラスタが別物になり**、要約の履歴が毎回捨てられる。`ADR-0035` 決定 6 が「変更のあったクラスタだけを
再生成する」と定めた差分再生成の前提（同一性が続くこと）が成り立たなくなる。

### 決定 4: 要約の**生成時刻だけ**を持つ表を、書き手が来る前に置く

`graph_cluster_summaries`（クラスタ × 機密区分 → 生成時刻）。**要約の本文は持たない**
（`ADR-0035` 決定 5「別系統として持つ・索引化しない」）。

🔴 **現時点で書き手が居ない。** 要約生成バッチ（`claude-opus-5` の呼び出し）は #1363 の受け入れ基準に
無く、本作業の射程外である。**それでも今置く**のは、これが無いと `ADR-0083` 決定 3 の条件 2・3 が
**実装不能**になり、「常に未要約」を焼き付けた生産者しか作れないためである
（そして「常に未要約」は試験でも本番でも区別がつかない）。

**空であることは「全クラスタが未要約」を意味し、それは現況として正しい。** これは
「生産者の無い指標を 0 件として並べる」ことの逆であり、**実測された件数**である。

### 決定 5: 未要約の条件 3 は `UpdatedAt` で測る（`BodyUpdatedAt` ではない）

計画の字義に従う（選択肢の表の A）。**`IADR-0353` が陳腐化文書数で `BodyUpdatedAt` を採ったのとは
向きが逆である**ことを明記する ——

- 陳腐化文書数で `UpdatedAt` が駄目だったのは、**棚卸し作業（タグ整理）そのものが指標を改善させる**
  からであった。**指標が自分の改善作業で消えるなら、それは測定ではない。**
- 未要約クラスタ数では、`UpdatedAt` を使うと**多く数える**（余分な再生成が起きる）だけで、
  「作業したら数字が減る」向きの事故は起きない。**安全側は多く数える側である。**

要約生成の費用が実測できたら計画へ環流する（作業仕様書 §未決事項 2）。

### 決定 6: 検出の排他リースは、ナレッジ健全性とは**別の口**にする

PostgreSQL の advisory lock。キーは `"GCLD"`（健全性の `"GKHP"` とは別値）。

🔴 **同じ口を共有してはならない。** 日次のクラスタ検出（長い）が毎時のナレッジ健全性の報告（短い）を
塞ぎ、**指標が丸ごと止まる**。リースそのものを省けないのは `IADR-0299` 決定 3 と同じ理由で、
2 レプリカが同時に入ると**互いのクラスタを「対応がつかない＝消滅」と判定して消し合う**
（要約の生成時刻もろとも消えるため自然回復しない）。steady state が `replicas: 1` でも、
ローリング更新の maxSurge で新旧 2 pod が同時に生きる。

### 決定 7: `SC-18` のクラスタ表示は本作業に含めない

`ADR-0083` 決定 4 が表示形式を**定めておらず**、着手条件を「**実測されたクラスタ数と要約の長さが
揃ったら**」としている。#1363 自身が順序を「**実装 → 実測 → 環流 → 裁定 → 表示**」と書いており、
**いま計画へ裁定を求める段ではない。** 力学レイアウトの空間的凝集による現行の表示は同決定 4 が
追認済みで、**要約・色分けは作らない**のが現在の正である。

**本作業が解いたのは「表示すべきクラスタが 1 つも無い」ことの方である。**

## 理由

- **自前実装を採ったのは、入力が単純だからである。** 文書 ID と重み付き無向辺しか渡さず、
  出力は集合の列である。汎用グラフライブラリの表現力は 1 つも要らない一方、依存を 1 件足せば
  CPM・ratchet・供給網の面が増える。
- **決定性を優先したのは、指標の意味が壊れるからである。** アルゴリズムの質より、
  「毎日同じ答えが出ること」の方がこの用途では重い（決定 2）。
- **同一性の追跡を入れたのは、`ADR-0035` 決定 6 の差分再生成がそれを前提にしているからである。**
  同一性が無ければ「変更のあったクラスタだけを再生成する」が表現できない。
- **書き手の無い表を置いたのは、置かないと判定が嘘になるからである**（決定 4）。

## 結果

- **良い影響**: `unsummarized-clusters` の生産者が立ち、健全性 7 指標のうち**観測値として生産される
  のは 5 件**になった（残る 2 件は OTel カウンタ → Grafana の別経路）。`ADR-0083` 決定 4 の
  「着手の条件」のうち**クラスタ数の実測が可能になった**。
- **悪い影響 / トレードオフ**:
  - 🔴 **クラスタ要約は 1 つも生成されない。** したがって当面 `unsummarized-clusters` は
    **全クラスタ**を返す。**これは異常ではなく現況の正確な報告である**が、
    「要約が追いついていない量」としては読めない（分子と分母が一致している）。
  - **変異検査で捕まえられなかった主張が 2 つある**（後述「試験で守れていないもの」）。
  - modularity の解像限界は残る（重すぎる橋 1 本が独立したコミュニティを作る。実測済み）。
    `ADR-0035` は解像度パラメータを定めていないため、**γ は 1 固定**にしてある。

### 試験で守れていないもの（正直な記録）

変異検査で**赤にならなかった**変異が 2 つある。**記録として残す**（次に触る人が「試験があるから安全」
と誤解しないため）。

| 変異 | 結果 | 判断 |
| --- | --- | --- |
| 細分化（2 段目）を丸ごと外す（＝ Louvain にする） | **全緑** | 分断が起きるのは論文 Figure 2 のような特定の形であり、合成した小グラフでは再現しなかった。**それでも 2 段目は残す** —— 計画が手法名で「Leiden 法」と確定しており、外せば実装は Louvain になる |
| 局所移動の候補を全コミュニティへ広げる | **全緑** | 辺の無いコミュニティは `k_i,in = 0` で増分が必ず負になり、そもそも選ばれない。**制限は枝刈りであって意味を変えない**（注記をその通りに直した） |

捕まえられた変異は 3 つである（未要約判定を常に真にする → 7 件赤／Jaccard の下限を 0 にする → 1 件赤／
個人資料の除外を外す → 1 件赤）。

### 残るもの

1. **クラスタ要約の生成**（`ADR-0035` 決定 3・5）。`graph_cluster_summaries` の書き手が来る。
2. **クラスタ数のオーダーの実測と環流**（`ADR-0083` フォローアップ 2）。稼働後の実データが要る。
   **10 通り以上なら `ADR-0035` 決定 3・6 の再評価が要る。**
3. **`SC-18` のクラスタ表示**（決定 7。2 の後）。
4. **未要約の条件 3 の時刻の選択**（決定 5）。要約生成の費用が実測できたら環流する。
