# IADR-0380: AI 提案の類似度候補は GraphService 内の語の共起を既定の供給元にし、「供給元が空」を本番 DI の回帰対照で赤にする

- 状態: Proposed
- 日付: 2026-09-05
- 決定者: claude（#1244。親 #454 の棚卸しで摘出）

## 起点・関連

- 関連する計画書 ID: FR-18 / UC-10 / SC-03 / SC-21 / ADR-0051（決定 1〜4）/ ADR-0034（決定 1・2・5）/ ADR-0033（決定 7・10）/ ADR-0050（決定 3）
- 関連する実装仕様書: [`20260905_issue-1244_similarity-candidate-source.md`](../specs/20260905_issue-1244_similarity-candidate-source.md)
- 前提の IADR: [[IADR-0266]] 論点 C-2（「ポートで切り、実装は交換可能にする。既定は空を返すアダプタ」）と §結果「類似度の実供給元が無いため、既定では提案が 0 件になる」。**本 IADR はその「既定」を差し替える。** 決定 1〜7 は変えない
- 前例: `LinkEdgeSynchronizer`（[[IADR-0281]]。本文指紋の変化を契機に本文を 1 回読む）、`CjkBigramPayload`（検索側の CJK 2-gram）

## コンテキストと課題

#1244 の実測（作業仕様書 §1）: `ISimilarityCandidateSource` の本番実装は「常に空を返す」`UnconfiguredSimilarityCandidateSource`
**1 つだけ**で、それが `Program.cs` の DI に刺さっていた。生成器は [2] 類似度が空なら `[]` で抜けるため、
**FR-18 の提案は構造的に 0 件**だった。状態機械・承認 UI・却下の永久保持はすべて緑のテストを持つが、
**守る対象が 1 件も生まれていなかった。** 生成経路のテストはすべて stub の類似度を注入しており、
**本番 DI が何を解決するかを見るテストが 1 本も無かった**（「テストも CI も緑のまま壊れている」型）。

決めるべきは 3 つ。

1. **類似度の供給元をどこに、何で作るか。** IADR-0266 は「RetrievalService に越境してよい口ができたら差し替える」としたが、
   稼働環境の埋め込み経路は不安定で（#1215 open）、供給元がそこに依存すると提案は再び 0 件へ戻る
2. **ADR-0051 決定 1（スコープを跨いで算出してよい）と決定 2（件数も存在も出さない）を、実供給元でどう守るか**
3. **同型の欠陥を二度作らないために、何を固定するか**

## 検討した選択肢

### 論点 A: 供給元

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A-1 | RetrievalService に「ABAC を跨ぐ類似度」の内部口を作り、Qdrant の埋め込みで引く（issue 本文の想定） | **不採用（今回）。** 埋め込み経路（#1215）に依存し、壊れていると再び 0 件。越境する口なのでサービス間限定の認可・新しい契約・Qdrant 前提のテストが要る。提案の品質は最も高い |
| **A-2** | **GraphService 内で、表題＋本文から語の出現数（Latin 語 ＋ CJK 2-gram）を持ち、IDF 重み付きコサインで引く** | **採用。** 決定的（同じ入力から同じ出力）。外部 LLM・埋め込み・他サービスに依存しない。本文は既に `DocumentUpdated` 購読でリンク抽出のために読んでおり、**読み取り経路を増やさない**。ADR-0051 決定 1 の「自システム内の演算」そのもの |
| A-3 | 表題だけの共起 | 品質が低い。**A-2 の縮退形として採り込む**（出現数の行が無い文書は表題から作る） |

### 論点 B: 出現数の作成契機

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **B-1** | **却下解除・リンク抽出と同じ「本文指紋の変化」**（ADR-0050 決定 3）。同じ 1 回の読み取りで作る | **採用。** storage への読み取りが増えない。本文が変わった文書は、次の生成で新しい出現数で候補計算される |
| B-2 | 生成のたびに全文書の本文を storage から読む | 不採用。生成 1 回が文書数ぶんの I/O になる |
| B-3 | 起動時に全文書を backfill する | 不可能。`graph_documents` は `MarkdownUri` を持たない（表題フォールバックが backfill の代わり） |

### 論点 C: 回帰対照の置き方

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C-1 | 生成器のテストに実供給元を使うテストを足す | 必要だが不十分。**Program.cs の登録を空へ戻しても落ちない** |
| **C-2** | **`TestWebApplicationFactory` は `ISimilarityCandidateSource` を差し替えず、本番 DI が解決する型と、実文書 2 件からの HTTP 生成で pending が 1 件以上生まれることを固定する** | **採用。** 欠陥そのもの（本番 DI が「常に空」）を直接測る |

## 決定

### 決定 1: 類似度の供給元は GraphService 内の語の共起を既定にする（A-2 ＋ A-3）

- `TermProfile`（Domain。純粋）: `Extract(title, body)` は CJK を `CjkBigramPayload.Encode` の 2-gram、それ以外を小文字化した
  2 文字以上の語に切り、表題の語を 3 倍に重み付けして**上位 128 語**を持つ（同数は語の順序＝決定的）。
  `Rank(origin, corpus, minScore, limit)` は `idf(t) = ln(1 + N / df(t))`、`w = (1 + ln tf) × idf`、コサインで、`minScore` 未満を落とし
  降順・同点は文書 ID 昇順で `limit` 件返す。**起点自身は返さない**
- `GraphDocumentTermProfile`（`graph_document_term_profiles`）: `document_id` PK・`terms jsonb`・`body_hash`・`updated_at`。
  **本文・表題・スニペットを持たない**（スコープを跨いで読まれる行である。`SimilarityCandidate` が本文を運ばないのと同じ理由）。
  `graph_documents` への FK は張らない（`edges` と同じ）
- `TermOverlapSimilarityCandidateSource`（Infrastructure/Persistence）: `graph_documents` を母集合に、出現数の行が無い文書は表題から作り、
  `Rank` で返す。**ログは起点の ID だけ**
- 構成 `AiSuggestions:Similarity:Source`（`term-overlap` 既定 ／ `none` = `Unconfigured…`）・`MinScore`（既定 0.1）。
  **未知の値は `ValidateOnStart` で起動を落とす**（既定へ倒すと本 issue の再演になる）。選択は解決時に行う
  （`builder.Configuration` を組み立て時に読まない —— テストホストの構成は Build 時に載るため）
- **ADR-0051 決定 1 の越境演算は RetrievalService ではなく GraphService 内で行う。** 計画は場所を定めていない。
  issue 受け入れ基準 1（RetrievalService に口を作る）は**形を変えて満たす** —— 越境する口が無いので、
  「サービス間呼び出しに限る」認可も要らない

### 決定 2: 出現数は本文指紋の変化を契機に、同じ読み取りから作り直す（B-1）

`GraphDocumentSyncConsumer` は指紋が変わったときに読んだ本文を `TermProfileSynchronizer.UpsertAsync` へも渡す。
本文が取れなければ表題だけで作る（辺と違い「消える」ものが無いので縮退してよい）。指紋が変わらなくても出現数の行が無い
文書には表題から作る（既存文書の初回）。`SaveChanges` は消費者が 1 回だけ呼ぶ（`LinkEdgeSynchronizer` と同じ規律）。
`DocumentDeleted` で行を消す。**表題だけの更新（指紋不変）では出現数を作り直さない**（本文の語を失うため。§結果）。

### 決定 3: 境界は変えない。実供給元で陰性対照を置く

供給元はスコープを受け取らず、**スコープ外の似た文書も返す**（ADR-0051 決定 1）。絞るのは従来どおり候補列挙の段
（`EnumerateAuthorizedCandidatesAsync`。IADR-0266 決定 2）であり、LLM より前である。
**実供給元がスコープ外を最上位で返しても LLM 送信本文に現れない**ことを `AiSuggestionGenerationTests` G-12 が、
**ログに件数・候補 ID が現れない**ことを `TermOverlapSimilarityCandidateSourceTests` T-46 が固定する。

### 決定 4: 「供給元が空」を本番 DI の回帰対照で赤にする（C-2）

`TestWebApplicationFactory` は `ISimilarityCandidateSource` を**差し替えない**。`SimilaritySourceWiringTests` が
①既定構成で解決される型が `Unconfigured…` ではないこと、②実文書 2 件を同期した状態で `POST /graph/suggestions/generate/{id}` が
`pending` の提案を 1 件以上返し一覧に出ること、③`Source=none` で `Unconfigured…` が解決されること（切り替えの陽性対照）、
④未知の値で起動が落ちることを固定する。**`Program.cs` の登録を空へ戻すと①②が落ちる**（変異試験で実走。作業仕様書 §T-53）。

### 決定 5: 重複・自己参照・既存辺・却下との噛み合わせは候補列挙の段の規則をそのまま使う

供給元は起点を返さず ID を重複させないが、**正は候補列挙**である（起点・却下済み・既存辺・既存提案を状態を問わず除外）。
却下の解除（本文指紋の変化で `pending` へ戻る）と出現数の更新は**同じ契機**なので、本文が変わった文書は
新しい出現数で候補計算され、戻った提案は「既存提案」として作り直されない（同じ行が再提示される）。

## 理由

- **決定 1（A-2）は「壊れにくさ」を「品質」より先に置いた。** #1244 の教訓は「供給元が無いと、その先の全部が守る対象を失う」である。
  埋め込み（A-1）は品質で勝るが、いま稼働環境で不安定な経路（#1215）に供給元を繋ぐと同じ形へ戻る。
  A-2 は品質で劣るが**必ず候補を返し**、提案の質は LLM（[5]）が表題を見て絞る。A-1 は A-2 の上に**追加の供給元**として
  後から重ねられる（ポートは 1 つのまま、実装を合成する）
- **IDF は省けない。** 日本語は「です」「ます」「こと」のような機能語の 2-gram をほぼ全文書が共有し、素の共起では
  どの文書も互いに似て見える。全件に共通する語ほど重みを落とすのが、無関係な文書を候補にしない唯一の仕掛けである
  （T-43 が変異で固定。IDF を 1 に固定すると定型句だけを共有する文書が 0.1 を超えて候補に入る）
- **決定 2 は ADR-0050 決定 3 の帰結である。** 本文を読む契機を増やすと、属性・タグだけの更新のたびに storage 読み取りが走る
- **決定 4 は欠陥の形に合わせた。** 欠陥は「本番 DI の登録」に在った。そこを直接測らないテストは、同じ欠陥を二度と検出しない

## 結果

- **良い影響**: FR-18 の提案が実際に生まれる。供給元は決定的で、外部の状態（LLM・埋め込み・他サービス）に依らず
  テストが再現可能。生成経路の結合テスト（HTTP → pending）が本番 DI で走る
- **悪い影響 / トレードオフ**:
  - **提案の網羅性は埋め込みに劣る。** 語彙が違う同義の文書（「認可」と「アクセス制御」）は結び付かない。
    A-1 を重ねる条件: #1215 が閉じ、埋め込み経路の安定が稼働で実測できたとき
  - **1 回の生成で全文書の出現数を読む**（実データ 2,368 件 × ≤128 語）。生成は利用者の明示操作で LLM 呼び出しを伴う
    経路であり許容する。転置索引（`graph_document_terms(document_id, term, weight)` ＋ SQL の内積）へ移す条件:
    文書数が 1 万件を超えるか、生成の応答時間のうち候補計算が LLM 呼び出しを上回ったとき
  - **既存文書は本文が次に更新されるまで表題だけの候補である**（backfill 不能）。品質は段階的に上がる
  - **表題だけの更新では出現数が古いままになる**（本文の語を保持するため作り直さない）。表題の変更は稀で、
    本文が変わればどのみち作り直される
  - **`MinScore` は実データで調整していない。** 既定 0.1 は T-43 の合成データで決めた値であり、構成で変えられる
- **稼働での実測が露見させた配備の欠陥**（作業仕様書 §7-2）: `values.yaml` の `graph.extraEnv` に `Services__LlmGateway` が無く、
  コード既定 `http://llm-gateway:5010` は k8s に無い名前だった。**供給元が空だったため誰も LLM の段に到達せず、露見しなかった。**
  helm / compose の宣言を本 PR で直した。**「常に空」は下流の欠陥を隠す** —— fail-closed の既定はその先の配線が検証されない
  ことと引き換えである
- **フォローアップ**:
  1. 利用者が生成を起動する導線（SC-03 のボタン／文書更新時の自動起動／定期）は計画に無い。planning へ裁定依頼を出す
     （作業仕様書 §8。`05_screens` §SC-21 の未確定「提案の生成頻度と滞留時の扱い」と同件）
  2. 稼働で `MinScore` と候補の質を実測し、必要なら既定を改める。**`pending` 行が実際に作られるところまでの稼働実測は、
     外部 LLM の API キーが構成された環境で行う**（本 PR 時点のクラスタは上流が認証で拒む）
  3. #1215 が閉じたら A-1 を**追加の供給元**として重ねるかを判断する（ポートは変えない）
