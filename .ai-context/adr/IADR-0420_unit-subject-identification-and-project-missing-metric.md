# IADR-0420: ユニットの主体はトークンが名乗る形だけで識別し、`project` 欠落は書き手の側のカウンタで数える

- 状態: Accepted
- 日付: 2026-09-09
- 決定者: claude（実装セッション。#1233 残作業 1・3）

## コンテキストと課題

`ADR-0085` 決定 4 は、残る穴（ユニットの保存経路を通らない書き込み）に対して
**基盤側の観測手段**を置くと定めた。

> **ユニットの主体が保存した文書のうち `project` を持たない件数** ——
> `POST /documents` の呼び出し主体が**ユニットのサービスアカウント**であり、かつ保存後の属性に
> `project` が無い文書の件数。**規定違反の検出。0 が正常である**

**定義はここまでである。「ユニットの主体をどう識別するか」は決めていない。** 実測でも
`src/**` に該当する計器は 1 件も無く（`grep -rn "unit_project\|project_missing"` → 0 件。
陽性対照 `ingest_unknown_tag_total` は 3 ファイルで返る）、
可観測性仕様書は 7 指標のままだった。**本 IADR はその 2 つを埋める。**

### 🔴 実測 —— 使える識別材料と、使えない識別材料

| 材料 | 使えるか | 実測 |
| --- | --- | --- |
| `platform-service` ロール | ❌ **使えない** | east-west の s2s 専用ポリシー（`ServiceCaller`）のためのロールであり、realm の `ai-stock-trading-kb-writer`（AST が KB へ書くクライアント）は **`platform-operator` しか持たない**（`deploy/keycloak/microservices-platform-realm.json`）。ロールで判定すると**当の書き手が母集合から落ちる** |
| 構成（appsettings）のサービスアカウント一覧 | ❌ **採らない** | 一覧から外すだけで計上を免れられる。`IADR-0373` 決定 4 が制限値の集合について同じ形を退けている |
| MCP のクライアント登録簿（`McpSubjectResolver`） | ❌ **使えない** | 登録簿は MCP のクライアントだけを持ち、`ai-stock-trading-kb-writer` は MCP クライアントではない（`IADR-0373` 決定 6 の実測） |
| JWT の `preferred_username` / `azp` | ✅ **使う** | Keycloak は client credentials の主体へ `preferred_username = service-account-<clientId>` を発行する（`SyntheticTraffic` の注記が同じ規約を述べている）。`profile` を持たない機械クライアントは利用者名を発行しない（`TestAuthHandler.NoNameHeader` の注記が実測として記録している） |

🔴 **ただし `azp` 単独は識別材料にならない。人間のトークンにも必ず付く**（SPA の clientId）。
**「クライアント識別クレームを持つか」だけで書いた判定は、全利用者を無人主体にする。**

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| (a) `platform-service` ロールで判定 | 「サービスアカウント＝ロールを持つ主体」 | **採らない。** 実測のとおり当の書き手が持っていない。**母集合が空になり、指標は永久に 0 を返す**（しかもそれは「正常」と読める） |
| (b) 構成の許可リスト | `appsettings` にサービスアカウント名を並べる | **採らない。統制の抜け道**（`IADR-0373` 決定 4 と同じ理由）。**「計器だから抜け道でもよい」ではない** —— 抜け道の形は同じである |
| (c) **トークンが名乗る形で判定**（採用） | `service-account-` 接頭辞、または利用者名なし ＋ クライアント識別 | **採用。** 構成に依存せず、realm の規約だけに閉じる。偽装には別のクライアント資格情報が要る |
| (d) `Gauge`（現在値）で表す | 「いま `project` を持たない文書は何件か」 | **採らない。** `ADR-0085` 決定 4 が明示的に退けた数え方である —— **母数がほぼ全件で張り付き、付与漏れの変化を映さない**。**測るのは書き手の側**であり、それは事象の積算（Counter）でしか表せない |
| (e) `SyntheticTraffic` を拡張して兼ねる | 既に claim を読む唯一の場所 | **採らない**（決定 2） |

## 決定

### 決定 1 — 「無人主体か」の判定を `MachinePrincipal` に 1 つ置き、2 つの腕で書く

`Platform.Shared.Infrastructure.Foundation.Observability.MachinePrincipal`。

- **腕 A**: 利用者名が `service-account-` で始まる（Keycloak の service account 規約）
- **腕 B**: 利用者名が**無く**、クライアント識別のクレーム（`azp` / `client_id`）がある
  （`profile` スコープを持たない機械クライアント）

🔴 **腕 B の「利用者名が無く」を落としてはならない。** 落とすと `azp` を持つ全利用者が
無人主体になり、**指標が母集合ごと壊れる**（案 (d) と同じ、張り付いて動かない数字になる）。

🔴 **迷ったら「無人ではない」へ倒す。** 人間の保存を 1 件でも数えると指標が常時非ゼロになり、
**0 が正常という読み方そのものが失われる**。取りこぼし（機械を人と読む）は 0 のままになるが、
それは**次の書き手が指標を信じ続けられる**方向の誤りである。**倒す向きを逆にしない。**

### 決定 2 — 🔴 `SyntheticTraffic` と合流させない。**目的が違う**

| | `SyntheticTraffic.IsSyntheticPrincipal` | `MachinePrincipal.IsMachine` |
| --- | --- | --- |
| 問い | **この特定の主体は合成監視か** | **主体は人か機械か**（種別） |
| 判定 | 構成の**許可集合との照合**（fail-closed。空なら 0 件） | **集合なし**。トークンが名乗る形だけ |
| 倒す向き | 空なら「合成でない」（費用計上を守る） | 迷えば「無人でない」（指標を守る） |

**合流させると、どちらかの規律が壊れる** —— 許可集合を「全機械」へ広げれば合成監視の
fail-closed が壊れ、種別判定を許可集合で塞げば本指標が構成依存（＝抜け道あり）になる。
**同じフォルダに並べるだけにして、`SyntheticTraffic` は 1 バイトも変えない。**

### 決定 3 — 計器は 1 本のカウンタ。属性は 2 つだけで、載せるのは**書き手と操作**である

`documents.unit_project_missing.total`（Prometheus では `documents_unit_project_missing_total`）。
`Counter<long>`、単位 `{document}`、Meter は既存の `microservices-platform.document-service` に相乗り。

- 属性は `documents.client_id`（`azp` の生値。**realm の登録済み機密クライアント数に閉じる**。
  取り出せなければ `unknown` へ倒す＝基数 1）と `documents.operation`
  （`create` / `update` / `update_metadata`）の **2 つだけ**。
- 🔴 **文書 ID・題名・利用者識別子は載せない。** `ADR-0085` 決定 4 が同節の 3 条件
  （件数のみ・ロール限定・個人資料除外）を本指標にも適用すると定めており、
  **文書名へのドリルダウンを設けない**。`PrivateNoteNotificationMetrics` / `LlmUsageMetrics` と同じ規律。
- **計上は 3 経路（登録・編集・メタデータ更新）の `SaveChangesAsync` の後。**
  400 / 404 / 409 / 413 で戻った要求は**保存されていない文書**であり、母集合に入らない。
  数えると「保存した文書」ではなく「保存しようとした要求」を測ることになり、**弾いた要求で警報が鳴る**。
- **判定（誰が・何が欠けているか）は計器のメソッドに閉じる。** 3 経路へ散らすと、
  1 箇所だけ条件が変わって**指標の母集合が経路ごとに違うものになる**。
- **空白だけの `project` は「持たない」と読む。** 鍵の有無だけで見ると `project=""` で免れられる。

### 決定 4 — 🔴 `DashboardService` の集計語彙（`KnowledgeHealthIndicators.All`）へは足さない

計画の指標は 8 になったが、**受け口の語彙は 7 のままにする。**

- 本指標は**事象の積算**であり、可観測性仕様書が「**混ぜない**」と定めた 2 経路のうち
  **OTel カウンタ → Grafana** の側に属する。集計 API が運ぶのは**状態のスナップショット**である。
- 足すと**誰も送らない 8 件目が恒久的に 0 件で並ぶ。** 計画自身が
  「**生産者の無い指標を 0 件として並べてはならない**（その 0 は「問題なし」と読める）」と定めている。
- 🔴 **「計画が 8 指標だから語彙も 8」ではない。** 理由は語彙のコメントに残した
  （**次に「7 と 8 が食い違っている」と気付いた者が、足す前に読む場所**である）。

### 決定 5 — アラートは 4 経路へ同内容で 1 件。**`absent()` 系は使えない**

`increase(documents_unit_project_missing_total[1h]) > 0` / `for: 5m` / `severity: warning`。
群名 `knowledge-health-violations`（Prometheus 2 経路 ＋ Grafana 2 経路）。

- 🔴 **上の `knowledge-health-producers` 群とは向きが逆である。** あちらは**沈黙**（生産者の不在）を
  鳴らすが、こちらは**起きてはならない事象の発生**を鳴らす。
- 🔴 **したがって `absent()` は置けない。** 違反が 1 件も無ければカウンタの系列そのものが立たず、
  **平常時に鳴り続ける**。同じ理由で Grafana 側は `noDataState: OK` にする。
- 窓を 1 時間に採るのは、単発の違反を取りこぼさず、**再起動でカウンタが 0 へ戻っても検出が残る**ため。
  `for` は 5 分（窓が既に均しているので、ここは scrape の欠けだけを吸収する）。
- **SC-10 の画面には出さない**（`IADR-0119` の節ごと保留。`IngestTagMetrics` と同じ判断）。
  **裁定が求めたのは「0 でない値が検出になる」ことであり、Grafana で観測できれば成立する**——
  パネル 1 枚がその実体である。

## 結果

- **良い影響**
  - **`ADR-0085` 決定 4 の「実装の追加作業は指標 1 件だけ」が着地した。** 定義だけだった指標に
    生産者・パネル・アラートが付き、**0 でない値が検出として人に届く**ようになった。
  - **「ユニットの主体」の識別が 1 か所に閉じた。** 構成に許可リストを持たないため、
    **統制を無効化する抜け道が増えていない**（`IADR-0373` 決定 4 の姿勢をそのまま延ばした）。
  - **同型の計器がもう 1 本増えたことで、「0 が正常」の読み方が表として並んだ**
    （可観測性仕様書の計器表が 2 → 3 行）。
- **悪い影響 / トレードオフ**
  - 🔴 **穴は塞がっていない。これは統制ではなく計器である。** 計上されても保存は成功する。
    止めるには基盤側の必須化が要り、計画は決定 1 でそれを**しない**と決めた。
    **「0 である」を「穴が塞がっている」と読ませないこと**が、本 IADR の一番の負債である。
  - 🔴 **取りこぼす向きの誤りが残る。** 利用者名を持ち、かつ `service-account-` で始まらない
    機械クライアント（realm の設定次第で作れる）は**人間として扱われ、数えられない**。
    決定 1 のとおり意図した倒し方だが、**realm 側の命名規約に依存している**ことは事実である。
  - **同型の `ingest_unknown_tag_total` にアラートが無いという非対称が残った。** 本 PR の射程外
    （別 issue の候補として可観測性仕様書へ明記した）。**気付いていないのではない。**
  - **`Update` / `UpdateMetadata` の端点が `HttpContext` を取るようになった**（従来は取っていない）。
    計器のためだけの引数であり、**認可・応答の契約は 1 バイトも変わっていない**。
- **フォローアップ**
  1. **#1233 残作業 2（`project` を持つ文書の実件数）は測れない** —— 稼働 DB が無い。
     **利用者の手が要る**（仕様書 §やらないこと に数え方を書いた）。0 件に近ければ
     `ADR-0043` の候補 API が SC-01 / SC-08 で空になり、**別途の裁定が要る**。
  2. **配備時に `/api/v1/provisioning/alert-rules` が 13 件返すことを確かめる**（件数は導出値）。
  3. **`AST/ADR-0032` フォローアップ 4（他ユニットへの一般化）は planning 側で開いたまま**。

## 変異試験（実測）

| # | 変異 | 赤くなった試験 |
| --- | --- | --- |
| M-1 | `IsMachine` を「クライアント識別クレームを持つか」だけにする | **shared 1 件 ＋ DocumentService 3 件** —— `対話ログインの利用者はazpを持っていても無人主体と判定しない` / `対話ログインの人間がprojectなしで保存しても計上しない` / `登録で対話ログインの人間は計上しない` ほか。**陰性側はすべて緑のまま**であり、分けたのは陽性対照だけである |

| M-4 | 計上を `SaveChangesAsync` の前へ動かす | **1 件** —— `登録が400で落ちたら計上しない` |
