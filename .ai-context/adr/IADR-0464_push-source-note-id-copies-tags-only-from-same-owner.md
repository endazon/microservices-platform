# IADR-0464: push の `sourceNoteId` と、同じ所有者の資料からだけタグを写すこと

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-09-26
- 決定者: claude（#1521。planning#652 の裁定 1＝ADR-0105 フォローアップ 2 の 2026-09-26 訂正の実装）

## 起点・関連

- 関連する計画書 ID: FR-20・FR-19（タグ）・UC-11・SC-20 主要素 5（2026-09-26 追記: 別名コピーの定めはプラグインの「両方を残す」にも当てる）
- 関連する計画 ADR: **ADR-0105** 決定 1〜4（別名コピーはタグだけを引き継ぐ）・フォローアップ 2 の訂正、**ADR-0110**（planning#652 の裁定を記録した ADR。裁定 1 がこの経路）、ADR-0037 決定 7（競合はサーバで解決しない）
- 関連する実装 ADR: IADR-0444（競合の台帳と `both`。#1503 の追記）・IADR-0352（プラグインの 3 択）・IADR-0270（同期プロトコル。所有者スコープ外は 404）
- 関連する実装仕様書: `.ai-context/specs/20260926_1521_plugin-keep-both-source-note-tags.md`

## コンテキストと課題

プラグインの「両方を残す」（`conflictResolver.ts`）はローカル本文を `noteId: null` の新規 push で送る。サーバはこれを通常の新規作成と区別できず、`tags: []` で作っていた。
planning#652 の裁定 1 は「push の契約に『元のノートの ID』を任意項目として足し、**サーバが同じ所有者のノートからタグを写す**」と定めた。

計画が定めていないのは、**同じ所有者でない ID（他者の資料・存在しない資料・組織文書）が来たときに拒否するか、黙って写さないか**である。
この経路は同期トークン（Bearer）で呼ばれ、他者の資料 ID を送ることは利用者でもできる。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | **黙って写さない**（201・`sourceNoteId` 無しと同じ応答） | 他者の資料の有無が応答に現れない。写しの本文は必ず送られる |
| B | 404 で拒否する（同期プロトコルの所有者スコープ外と同じ） | 他者と不在を同じ 404 にすれば存在は漏れない。🔴 **しかし写しの push が失敗する** —— プラグインは既にローカルへ写しのファイルを書いた後であり、写しがサーバへ届かない。本文を失わせないための操作がタグのために止まる |
| C | 400 で拒否する（入力の誤りとして） | B と同じく写しが届かない。他者の資料と不在を区別すると存在が漏れ、区別しなければ 400 の意味が曖昧になる |
| D | 所有者を問わずタグを写す | 🔴 **他者の資料のタグ（組織の語彙のどれを付けたか）が写しを通じて見える。** タグ自体は秘密性を持たないが、「その資料にどの語彙が付いているか」は資料の属性であり、同期トークンから他者の資料には 1 バイトも届かない（FR-20 受け入れ基準）という性質を崩す |

## 決定

**A を採用する。**

1. push の要求に任意項目 `sourceNoteId`（uuid・null 可・既定 null）を足す（サーバ `PushNoteRequest`・プラグイン `types.ts`）。既定値があるので従前のプラグインはそのまま通る。
2. **新規作成（`noteId` が null）のときだけ読む。** 更新の push では読まない —— 既存の資料のタグを push で書き換える経路を作らない（タグの変更は画面の責務）。
3. **写す条件は「同期トークンの持ち主が所有する個人資料」**。判定は更新・pull・delete・move と同じ `ObsidianSyncEndpoints.FindOwnedAsync`（個人資料の台帳を ID で引き、所有者一致のときだけ返す）。組織文書は個人資料の台帳に行が無いので当たらない。**別の述語を作らない。**
4. 🔴 **当たらなければ黙って何も写さない。** 応答は `sourceNoteId` 無しと同じ 201・同じ本文の形。
5. **写すのは `Document.Tags` の識別子の集合そのもの**（別のリストにする）。辞書との突き合わせはしない（#1503・IADR-0444 の 2026-09-25 追記と同じ）。
6. **写すのはタグだけ。** 露出 3 トグル（`PrivateNoteDefaults` の明示の OFF）・共有先（台帳に行を足さない）・版（edits の数から）・機密区分（`restricted`）は新規作成の既定のまま（ADR-0105 決定 1〜4）。
7. **プラグインが `sourceNoteId` を送るのは「両方残す」（`resolveVersionConflict` の `both`）だけ。** 通常の新規 push と、サーバ側削除からの作り直し（`resolveServerDeleted` の `local`。元の資料と同じパスで作り直す。元の資料は削除済み）は送らない。

## 理由

- **A はタグの欠落を「機能の不足」に留める。** ADR-0105 決定 5 は「タグが無いことで漏れる向きの問題は生じない。機能の不足であり統制の不足ではない」と書いた。拒否（B・C）はその不足を**本文の同期の失敗**へ格上げしてしまう。
- **正当な利用者でも当たらない ID は起こり得る**（競合を提示した後、写しを送る前に元の資料が画面から完全削除された等）。そのたびに写しの送信が止まるのは向きが逆である。
- **D を採らないのは、同期トークンの射程を「自分の個人資料」に閉じる既存の性質（IADR-0270）を 1 経路でも崩さないためである。**

## 結果

- **良い影響**: サーバ側の解決（#1503）とプラグイン側の「両方残す」で、写しが引き継ぐものが揃う（計画 SC-20 主要素 5「経路によって引き継ぐものを変えない」）。
- **悪い影響・トレードオフ**:
  - 他者・不在の ID を送ったプラグインは、写しにタグが無いことを応答からは知れない（画面で見れば分かる）。**正規のプラグインは自分が追跡している資料の ID しか送らない**ので、通常は起きない。
  - 写しの分だけ各タグの使用件数が増え、写しがある間はそのタグを削除できない（ADR-0105 決定 3 が受け入れた副作用）。
- **フォローアップ**: Obsidian 実機での確認は #1235（実機目視）の場で行う。
