# IADR-0151: 権限内属性値は検索段の facet で数え、件数を捨ててから返す

- 状態: Accepted
- 日付: 2026-08-09
- 決定者: claude（実装）

## 起点・関連

- 関連する計画書 ID: **SC-01 / SC-08**（対象範囲フィルタ「権限内のタグ／部門／プロジェクトのみ選択可」）／
  **FR-04**（対象範囲の指定）／**FR-05**（ABAC）／**UC-02**
- **前提となる計画 ADR: ADR-0043（計画リポ）（`Accepted`）**
  —— 決定 1（到達できる文書に実際に付与された値だけ）・決定 2（**件数を返さない**）・
  決定 3（自由入力で代替しない）・決定 4（**読み取り口は 1 系統・スコープだけロール別**）。
  **同 ADR のフォローアップが「実装方式は実装リポジトリの IADR で確定する」と本 IADR を名指ししている。**
- 関連 ADR: [IADR-0014](./IADR-0014_qdrant-attribute-payload-key.md)（Qdrant ペイロードの表現。**属性はネスト構造体 `attributes -> {k: v}`**）／
  [IADR-0009](./IADR-0009_wiki-browsing-404-hides-existence.md)（存在秘匿）／[IADR-0036](./IADR-0036_sc11-config-viewer-visualization.md) 相当の動的束縛（キャッシュキーに主体を含める制約）
- 起点 issue: **#540**（後続 **#542** が同じ口へ管理者スコープを足す）

## コンテキストと課題

計画は「利用者が到達できる文書に**実際に付与されている値**の集合だけを返す」照会 API を求めている。
**返す範囲を誤ると存在秘匿（ADR-0004 の 404 原則）が実質的に破れる**——ADR-0043 が制限を 4 つ定めた理由である。

決めること:

1. 「到達できる文書に付与された値」を**どう数えるか**（実装方式）。
2. **件数**をどう扱うか（決定 2 は「返さない」だが、数える過程では出てくる）。
3. **キャッシュ**するか。
4. **口の形**——#542 が同じ口へ管理者スコープを足せるようにする。

## 検討した選択肢

### (1) 値集合の求め方

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **Qdrant の facet を ABAC フィルタ付きで呼ぶ**（採用） | ○ | **ADR-0043 が「検索段の ABAC フィルタと同じ経路を使うのが自然」と書いた形そのもの**である。フィルタの組み立ては `QdrantVectorStore.BuildAttributeFilter` を再利用でき、**検索結果に現れる集合と定義が一致する**（別経路で数えると「検索には出るが候補に無い値」が生まれ得る）。クライアント 1.18.1 が `FacetAsync` を持つことは実測で確認した |
| 全点を `ScrollAsync` して distinct を取る | × | **素朴に実装すると重い**（ADR-0043 §悪い影響・制約が名指しした落とし穴）。到達可能な全チャンクを読む |
| DocumentService を引いて distinct を取る | × | **ABAC 判定が 2 経路に分かれる。** 検索段のフィルタと文書側の判定がずれると「候補に出るのに検索に出ない値」が生まれる。[IADR-0014](./IADR-0014_qdrant-attribute-payload-key.md) が書き込み・フィルタ・復元を揃えた理由と同じ |
| 辞書（`AttributeDefinition.AllowedValues`）を返す | × | **ADR-0043 決定 1 が明示的に禁じている**（辞書を丸ごと返すと権限外の文書の存在が推測できる） |

### (2) 件数

**facet は値と件数の対で返る。件数はサービス内で捨て、応答に載せない。**

**「使えるから返す」を選ばない。** ADR-0043 決定 2 は「件数は値集合そのものより漏洩力が強い」と
理由まで書いている——「このタグは 12 件だが自分の検索では 8 件」＝**見えない文書が 4 件ある**。
**facet を使うこと自体は制限に触れない**（件数はサービスの外へ出ない）が、
**応答に件数が載っていないことをテストで固定する**（実装を書き換えたときに黙って載る型の事故である）。

### (3) キャッシュ

**キャッシュしない。**

ADR-0043 は「キャッシュする場合は**キャッシュキーに主体を必ず含める**」と条件を付けており、禁じてはいない。
だが本作業では採らない——**主体ごとに結果が変わるため共有できず**、効くのは同一利用者の連続呼び出しだけである。
**得られる効果に対し、「キーに主体を入れ忘れると他人の候補が漏れる」という新しい失敗の面を作る代償が大きい。**
必要になったら、**そのときに主体込みのキーで**入れる（本 IADR を改定する）。

### (4) 口の形

**#542 が同じ口へ管理者スコープを足せる形にする。** ADR-0043 決定 4 は「読み取り口を 3 種類作らない。
1 系統とし、スコープだけロールで変える」と定めており、**#540 と #542 は同じ口である**
（[IADR-0139](./IADR-0139_domain-bundled-contract-prs.md) 決定 5 の 2026-08-09 追記）。**#540 で一般利用者スコープを作り、#542 が管理者スコープを足す。**

- 応答は**値の配列だけ**を持つ形にする。#542 が件数を足すときは**管理者スコープ専用の別フィールド**として
  足せる（一般利用者の応答形は変えない）。
- **「口を分けない」ことが制限の掛け忘れを構造的に防ぐ**という決定 4 の趣旨を、実装の形で保つ。

## 決定

1. **権限内属性値は Qdrant の facet を ABAC フィルタ付きで呼んで求める。**
   フィルタの組み立ては検索段（`QdrantVectorStore.BuildAttributeFilter`）と**同じものを使う**——
   別経路で数えると「検索には出るが候補に無い値」「候補にあるのに検索に出ない値」が生まれる。
2. **件数はサービス内で捨て、応答に載せない**（ADR-0043 決定 2）。
   **応答に件数が無いことをテストで固定する。**
3. **キャッシュしない**（本作業では）。入れるときは**キャッシュキーに主体を含める**（ADR-0043 の制約）。
   本決定を改定せずにキャッシュを足さない。
4. **口は 1 系統とし、スコープだけロールで変える**（ADR-0043 決定 4）。
   #540 は一般利用者スコープを実装し、**#542 が同じ口へ管理者スコープ（件数・追加・改名・削除）を足す。**
   応答は値の配列だけを持ち、**一般利用者の応答形を変えずに拡張できる**ようにする。
5. **スコープが解決できない（deny-by-default）ときは空配列を返す。**
   404 にも 403 にもしない——**候補が無いことと権限が無いことを区別させない**（[IADR-0009](./IADR-0009_wiki-browsing-404-hides-existence.md) の存在秘匿と同じ向き）。
   ADR-0043 決定 3 が「権限が無いのか値が無いのか区別できないのは体験として悪い」と書いているのは
   **自由入力を採らない理由**であって、エラーで区別を与えよという意味ではない。

## 影響

- **一般利用者が呼べる読み取り口が 1 本増える**（従来は `/bff/admin/authz` の管理者限定しかなかった）。
- **候補列挙のたびに到達可能性の判定が走る**（ADR-0043 §悪い影響・制約）。facet はサーバ側集計なので
  全点走査より軽いが、**無料ではない**。呼び出し頻度が問題になったら決定 3 を改定してキャッシュを入れる。
- **#542 は同じ口へ足す**（別の口を作らない）。本決定 4 がその拡張点である。
- 件数を返さないため、**利用者は絞り込む前に結果数を知れない**（ADR-0043 が受け入れた代償）。

## フォローアップ

- **実 Qdrant での facet の動作と payload index の要否は未検証である**（#633 の AI レビュー指摘・🟡）。
  **測ったのは「クライアント 1.18.1 が `FacetAsync` を持つこと」と InMemory 実装の振る舞いまで**であり、
  `QdrantIngestionVectorStore.EnsureCollectionsAsync` は `tags` / `attributes.<key>` に
  **payload index を張っていない**（実測。`CreateCollectionAsync` を `VectorParams` だけで呼んでいる）。
  **本決定の回帰ではない**——**検索段の ABAC フィルタも同じキーを未索引で引いている**ので、
  索引の要否は照会 API 固有ではなく**フィルタ経路全体の性能判断**である。本 IADR では決めない。
  **上の「facet はサーバ側集計なので全点走査より軽い」は、Qdrant の設計上の性質であって本リポの実測ではない。**
  実 Qdrant を立てるテスト構成が無いため（`Knowledge.IntegrationTests` に Qdrant 系は存在しない）、
  **実測は稼働環境が用意できた時点で行う**。呼び出し頻度が問題になったときに、
  索引の付与とキャッシュ（決定 3）を**同じ場で**判断する。
- **#542**: タグ辞書の管理者スコープ（値集合・使用件数・追加・改名・削除）を同じ口へ足す。
  **(c) 改名の追随は保持方式の変更を伴う**ため、着手時に判断し必要なら計画へ裁定を仰ぐ
  （[IADR-0139](./IADR-0139_domain-bundled-contract-prs.md) 決定 5 の 2026-08-09 追記）。
- **#539**（SC-01 / SC-08 の対象範囲フィルタ）は本決定の口から候補値を得る。**着手順は #540 → #539 が自然**。
- 個人資料（`private-note`）に付与された値の扱いは ADR-0043 が「決めない」としており、
  **決定 1 に従えば所有者本人の候補には現れる**（動的束縛）。本 IADR も同じ扱いとし、別途決めない。
