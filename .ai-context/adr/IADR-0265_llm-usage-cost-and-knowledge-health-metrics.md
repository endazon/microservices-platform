# IADR-0265: 有効期間つき単価表による金額換算と、ナレッジ健全性指標の集計側除外

## コンテキストと課題

ADR-0044 は 2026-08-07 に確定したが、**実装に先行していた**。着手時点の実測では、
`src/` にも `deploy/` にも**単価に相当する設定・定数が 1 件も無く**、トークンは
[IADR-0212](./IADR-0212_llm-output-token-histogram.md) の**出力の分布**だけが存在した。
一方で計画側は、月次の手動確認という暫定統制を「費用の金額は 1 円も出せない」状態のまま置いていた。

論点は 3 つである。

1. **単価表をどこに置き、誰が金額へ換算するか。** ADR-0044 決定 3 は「設定に持ち、読む側で換算する」と
   定めるが、**有効期間の境界の扱い**（切替時刻ちょうどはどちらか）と、**該当が無いときの振る舞い**は
   実装に委ねられている。
2. **`#380` との境界。** 出力トークンは両方の issue に現れる。二重実装を避ける必要がある。
3. **ナレッジ健全性指標を誰が集計するか。** 計画は「個人資料を除外する」と定めるが、
   **除外を誰が行うか**を定めていない。指標の源は知識グラフ・文書カタログであり、
   DB-per-service（ADR-0002）のため集計主体からは直接数えられない。

## 決定

### 決定 1: 単価の有効期間は**半開区間 `[EffectiveFrom, EffectiveTo)`** とする

`EffectiveFrom` は含み、`EffectiveTo` は含まない。

**両端を含めてはならない。** 単価改定は「終了日 = 次の開始日」で書くのが自然であり、閉区間にすると
**切替時刻ちょうどに 2 区間が該当**して、どちらで換算したかが後から特定できなくなる。
逆に終了日を「前日 23:59:59」と書かせる運用にすると、**その 1 秒の隙間に落ちた呼び出しが単価なし**になる。
半開区間はこのどちらも起こさない。**境界（切替時刻ちょうど・前後 1 tick）は単体テストで固定した。**

### 決定 2: 該当する単価が無い呼び出しは、**金額を記録せず**警報として計上する

ADR-0044 決定 3 は「無音で 0 円として扱ってはならない」と定める。本実装は次の 3 つを同時に行う。

1. 警告ログ（モデル名と、期限切れ／未登録の別を出す）
2. カウンタ `llm.pricing.unpriced.total`（属性 `llm.pricing_status` = `out_of_period` / `no_entry`）
3. **金額メトリクスへは 1 件も積まない**

🔴 **3 が要点である。** 0 を積むと、**期限切れが「費用の減少」に化けて**増加の検知をすり抜ける。
「金額が過小である」ことは、金額そのものからは決して読めない —— 読めるのは 2 のカウンタだけである。
Grafana の費用ダッシュボードは、**このカウンタを最上段に置いて「0 でなければ下の金額は過小」と明示**する。

### 決定 3: 単価表の**区間の重なりは起動時に落とす**（`ValidateOnStart`）

重なりを実行時に先勝ちで解決すると、どちらの単価で換算したかを後から特定できず、費用の突合が
成り立たない。**誤った単価表は配備の失敗として表に出す**方が、誤った金額を出し続けるより安全である。

### 決定 4: `#380` とは「分布」と「累計」で分ける。**Histogram は変更しない**

- `llm.completion.output_tokens`（Histogram・IADR-0212）= **分布**。`max_tokens` の妥当性を上限付近の
  バケットの厚みで読む。**#380（稼働環境での実測と再調整）が使う面である。**
- `llm.tokens.total`（Counter・本 ADR）= **累計**。費用の分子であり、分布からは合算できない。
  入力トークンは**本 ADR で初めて計測点を持つ**（費用の入力側の分子であるため）。

**本 ADR は Histogram のバケットにも記録条件にも一切触っていない。** 二重実装ではない。

### 決定 5: ナレッジ健全性は**観測値**を受け取り、**除外は集計側で強制する**

生産者（知識グラフ・文書カタログ側）から**件数だけ**を受け取らない。個人資料を除外したかどうかを
受け手が確かめられず、**「除外し忘れた件数」と「除外済みの件数」が区別できない**ためである。
代わりに `(指標, 不透明な鍵, doc_scope)` の観測値を受け取り、**集計時に個人資料を落とす**。

- 報告は**指標ごとのスナップショット置換**とする。差分にすると「解消した観測値」を取り消す経路が別に要り、
  **取り消し漏れが件数を恒久的に膨らませる**。
- 🔴 **除外は集合帰属で判定する。「組織文書でない」で書いてはならない。** `doc_scope` は新設属性で
  実データが乏しく、否定で書くと**属性を持たない大多数が個人資料と見なされ、指標が一斉に 0 になる**
  （ADR-0054 決定 1・2 / ADR-0036 D-04 と同じ理由）。**2 つの実装は動作で見分けがつかない**ため、
  「スコープ属性を持たない観測値は集計に含まれる」という**陽性対照テスト**を置いた。
- 不透明な鍵は**応答に一切現れない**（計画「個々の文書名を出さず件数のみ」）。

### 決定 6: ナレッジ健全性の DTO は**サービス間契約に置かない**

`Knowledge.Contracts` ではなく `DashboardService.Api` 内に持つ。画面（SC-10 のナレッジ健全性節）の
実装は **#504 / #452** が引き受けるため、**使う側が居ない契約を先に固定しない**。
契約の形はスナップショット検査の対象であり、固定すると変更のたびに承認手続きが要る。
BFF へ載せる段で契約プロジェクトへ昇格させる。

## 理由

- 決定 1〜3 は、いずれも **ADR-0044 が挙げた失敗の形**（「反映を忘れると試算はエラーを出さずに過小になる」）
  から逆算した。**静かに間違うより、うるさく止まる方を選ぶ**という 1 つの方針の 3 つの適用である。
- 決定 4 は、同じ数字の定義を 2 か所に作らないという ADR-0044 決定 4 の考え方を、
  **issue 間の境界**へ適用したものである。
- 決定 5 は、統制を**強制できる場所**へ置くという判断である。計画は「3 条件のうち 1 つでも欠けると
  存在秘匿が崩れるため個別に緩めない」と明記しており、**確かめられない統制は統制ではない**。

## 結果

- **良い影響**
  - 用途別モデル振り分けの効果を**金額**で比較できる（従来は呼び出し回数という代理指標しか無かった）。
  - 単価改定は設定変更のみで反映でき、**反映漏れは警報として表に出る**。
  - ナレッジ健全性の 4 規則が、**それぞれ独立にテストで固定された**（403 の否定形・文書名の否定形を含む）。
- **悪い影響 / トレードオフ**
  - **時系列の系列数が増える**（ADR-0044 が予告したトレードオフ）。トークンは `llm.token_type` の分だけ
    さらに 2 倍になる。属性の値域はすべて閉じているため有界だが、モデルを大量に増やす場合は再検討が要る。
  - **単価表の保守は人手に残る。** 警報は反映漏れを検知するが、反映そのものは人手である。
  - **観測値の生産者側は未配線である。** 本 ADR は受け口と集計・統制までであり、
    知識グラフ・文書カタログ側から報告する実装は別作業に残る。**それまで指標は 0 のままである**
    —— これは「健全である」ことを意味しない。
  - **通貨は USD 固定**（円換算しない）。為替レートの取得という新しい外部依存を費用計算へ持ち込まないため。
- **フォローアップ**
  1. 観測値の生産者側の配線（知識グラフ・文書カタログ → `POST /dashboard/knowledge-health/observations`）。
  2. SC-10 のナレッジ健全性節の画面実装（引き受け先は **#504 / #452**）。
     **辺の型ごとの内訳**（型別の件数）は画面が要る粒度であり、そこで扱う。
  3. 月次予算の上限アラートの配線（Alertmanager 未配備・しきい値も計画側で未確定）。
  4. **`#380` の実測**（稼働環境）。本 ADR は計器を用意しただけである。
