# IADR-0347: パスワードリセットの存在秘匿は「応答を揃える」では閉じない —— 申請を送出経路の健全性に結び付け、宣言・稼働・運用の三層で強制する

- 状態: Accepted
- 日付: 2026-09-02
- 決定者: Claude（実装）
- 起点: issue **#1143**（`bug` / `priority:must`。#1102 から [IADR-0332](./IADR-0332_keycloak-smtp-externalsecret-wiring.md)
  決定 5 で分割）。直前に着地した [IADR-0344](./IADR-0344_dev-mail-capture-mta.md)（#1144）の上に積む。
- 関連する作業仕様書:
  [`.ai-context/specs/20260902_issue-1143_reset-existence-concealment.md`](../specs/20260902_issue-1143_reset-existence-concealment.md)

## コンテキストと課題

計画 `ADR-0026` は SC-15 の**存在秘匿**（登録の有無によらず常に同じ完了文言）を確定しており、
画面仕様書もそう書いていた。**稼働環境で測ると偽だった。**

送出に失敗すると **実在する利用者名のときだけ HTTP 500** が返り、実在しない利用者名は 200 を返す。
**この差だけで利用者名を 1 リクエストずつ列挙できる。** 🔴 これは「無言の縮退」ではない ——
**存在する利用者のときだけ大声で落ちる**という形の漏洩であり、未設定であることがそのまま
**利用者名の判定器**になっている。

### 稼働環境で測った 4 状態（陽性・陰性を対で）

| # | 状態 | 実在する利用者名 | 実在しない利用者名 | 区別できるか |
| --- | --- | --- | --- | --- |
| **A** | 送出経路が使える ＋ 申請が開いている | **200** | **200** | **できない**（正規化後の本文も一致） |
| **B** | `smtpServer` 未設定 ＋ 申請が開いている | **500** | **200** | 🔴 **できる** |
| **C** | 送出先へ接続できない ＋ 申請が開いている | **500** | **200** | 🔴 **できる** |
| **D** | 申請が閉じている（`resetPasswordAllowed=false`） | **400** | **400** | **できない**（本文はバイト一致・導線も消える） |

状態 D の本文比較（フローの識別子と、**申請者自身が送った利用者名の再表示**だけを伏せて正規化）:

```console
normalized equal = True | lens 3517 3517
```

🔴 **状態 B は「例外的な設定ミス」ではない。** 稼働クラスタで **Keycloak コンテナが再起動した直後は
必ず状態 B になる**ことを実測した（`RESTARTS 3`。H2 はコンテナ層にあり `kcadm` の実行時反映は消える。
realm 再インポートが `resetPasswordAllowed=true` を復元し、`smtpServer` は空のまま）。
**放っておくと定期的に脆弱な組へ戻る。**

## 検討した選択肢

### 決定 1: どこで塞ぐか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. テーマで失敗時も同じ画面を返す | `error.ftl` / メッセージを差し替える | **不採用（測って落とした）**。**テーマは HTTP ステータスを変えられない** —— 500 は認証器がエラーページとして組み立てており、テンプレートは本文しか差し替えられない。受け入れ基準 1 は**ステータスの一致**を要求する。加えて [IADR-0261](./IADR-0261_keycloak-theme-and-smtp-injection.md) 決定 1 が「テンプレート（.ftl）は上書きしない」と定めている（上書きすると本体のセキュリティ修正に追随できなくなる） |
| A'. 認証フローを組み替える | `reset-credential-email` を ALTERNATIVE / DISABLED にする | **不採用（測って落とした）**。稼働 realm の `authentication/flows/reset%20credentials/executions` を読むと **`configurable: false` かつ `requirementChoices: ["REQUIRED"]`** である。**設定で挙動を変える余地が無い** |
| C. BFF で申請端点を包む | 応答を BFF が同値化する | **不採用**。**SC-13〜15 の画面は Keycloak テーマ側である**（`ADR-0026`・`AuthBffEndpoints.cs` 冒頭の宣言）。ブラウザは Keycloak のオリジンへ直接 POST しており、BFF は経路上に居ない。前段へ入れるのは**計画側の決定を要する** |
| **B. fail-closed で同値にする** | **申請は送出経路が使える間だけ開く** | **採用**。issue 本文が「500 をテーマで隠せない場合は (b)」と示した道であり、**状態 D が実測で同値**であることを確かめた |

### 決定 2: 結合をどこで強制するか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. 宣言（realm JSON）だけ見る | 静的検査で足りるとする | **不採用**。**宣言が正しくても稼働状態は状態 B へ戻る**（再起動の実測）。「宣言が正しい」は「稼働が正しい」を意味しない |
| B. 稼働状態だけ見る | 実行時検査で足りるとする | **不採用**。脆弱な宣言をそのままマージできてしまう。**混入を止める場所と、戻りを捕まえる場所は別**である |
| **C. 宣言・稼働・運用の三層で持つ** | 静的検査 ＋ 実行時検査 ＋ runbook の手順 | **採用**。3 つは**別の事故**を捕まえる（混入 / 戻り / 人の操作順序） |

### 決定 3: 残る窓を自動で閉じるか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. Keycloak の SPI（Java）で認証器を差し替える | 根本。500 そのものを消せる | **不採用（射程外）**。本リポジトリに Java 成果物のビルド基盤が無い |
| B. 前段プロキシで応答を正規化する | エッジで 500 を 200 に書き換える | **不採用**。既定のエッジは応答ステータスの書き換えを持たない（もう一方のエッジ実装でしか書けない）ため、**既定の経路が守られない**。加えて**本物の障害も隠す** |
| C. realm を書き換える調停器を常駐させる | 送出先の到達性を監視して自動で開閉する | **不採用（本 issue の裁量を超える）**。realm の更新には広い管理権限が要り、[IADR-0329](./IADR-0329_identity-admin-keycloak-provider-and-realm-wiring.md) が「必要なクライアントロールは 3 つだけ」と守った**最小権限の後退**になる。**秘匿のために権限を広げるのは、別の穴を開けている** |
| **D. 検出と運用手順で塞ぎ、残余を記録して環流する** | 到達判定 ＋ 実行時の門 ＋ runbook | **採用**（下記§結果の「測っていて、直していないこと」） |

## 決定

- **決定 1: 案 B。** 不変条件は「**`resetPasswordAllowed = true` は、使える送出先（`host` と `from` の両方）と
  一対でしか成立しない**」。使えないなら**閉じる** —— 閉じた状態は実在／非実在のどちらにも
  **同じ 400 とバイト一致の本文**を返す（実測）。
- **決定 2: 案 C。** 三層で強制する。
  1. **宣言（静的）**: `scripts/check-realm-constraints.js` に門を足す。`from` だけ空でも落とす
     （**宛先だけ揃っていても Keycloak は送出前に拒否し、同じ 500 になる**）。変異試験 9 件つき。
  2. **稼働（実行時）**: `scripts/check-password-reset-mail.js` が **応答を測る前に** 稼働 realm の組を読み、
     脆弱な組なら**どの状態に居るかを名指しして落とす**。資格情報は Pod の env のまま使い、値は出力しない。
  3. **運用（手順）**: runbook に **§0「先に申請を閉じる」** と **§確認 3「送出の成立を確かめてから開き直す」**
     を置く。**順序を逆にしない**ことを明記する。
- **決定 3（`--fields` を使わない）**: 稼働 realm の読み出しに `kcadm get realms/<realm> --fields …` を使わない。
  **設定済みの realm に対しても `smtpServer: { }` を返す**（#1144 で陽性対照つきで実測）。
- **決定 4（射程の境界）**: **利用者向けの応答に送出失敗を出さないことと、送出失敗を運用が観測できることは
  両立させる。** realm は送出の成功／失敗の監査イベントを既に記録する設定である（実測）ので、
  本 PR はそれを**壊さない**ことだけを守る（`ADR-0045` 決定 8）。
- **決定 5（残余の扱い）: 案 D。** 送出経路が「開いたまま」落ちた瞬間から閉じるまでの窓は**残す**。
  自動で閉じる 3 つの手段（決定 3 の A / B / C）はいずれも本 issue の裁量を超える。
  **残余を消さずに記録し、計画へ環流する。**

## 理由

- **決定 1 の向き**: 「応答を揃える」方向は**測って行き止まりだった**。テーマはステータスを変えられず、
  フローは設定不能である。**残る自由度は「そもそも利用者ごとの分岐を起こさせない」ことだけ**であり、
  それが「申請を閉じる」である。**行き止まりを実測で確かめてから曲がった**ことを記録に残す ——
  そうしないと、後任が同じ壁に同じ順序でぶつかる。
- **決定 2 の「三層」**: #1144 で **realm 宣言が `smtpServer` を持つようになった**ため、
  **再インポートは状態 B ではなく状態 A へ戻る**。それでも稼働層を置くのは、
  **宣言の正しさが稼働の正しさを保証しないこと**を実測で知ったからである（再起動の件）。
  **「宣言を直したから大丈夫」で止めていたら、この issue はまた偽の完了報告になっていた。**
- **決定 3**: `--fields` の誤診は**runbook の確認手順に書かれていた**。**手順どおり打つと「入っていない」と
  読み違える**形であり、#1143 の起票時の測定もこの形で採られている。**器の癖を記録に残す。**
- **決定 5 の正直さ**: 窓を「無い」と書くほうが報告は綺麗になるが、**残っているものを消すと、
  次に誰かが「閉じたはずだ」と信じて測らなくなる**。#1143 自身が「画面仕様書が『する』と書いているのに
  偽だった」という事故であり、**同じ型を繰り返さない**。

## 結果

- **良い影響**
  - **脆弱な組が宣言としてマージできなくなった**（静的な門・変異試験 9 件）。
  - **稼働状態が脆弱な組へ戻ったことを、応答を漏らす前に検出できる**（実行時の門）。
    実測で、組を崩すと**応答を測る前に**失敗すること・戻すと緑になることを対で確かめた。
  - **画面仕様書が実測と一致した**（4 状態の表を根拠として持つ）。
  - **runbook が順序を持った** —— 「先に閉じる／成立を確かめてから開く」。
- **悪い影響 / トレードオフ**
  - **閉じている間はパスワードリセットが使えない。** 可用性を秘匿へ振っている（fail-closed）。
    `ADR-0045` 決定 9-b の代替手段（管理者による本人確認済みリセット）は**この状態でも機能する**
    （realm 設定だけで成立し SMTP を要さない）ので、復旧経路が同時に失われることはない。
  - **実行時の門が realm 管理者の資格情報を使う**（Pod の env のまま・値は出力しない）。
    検査器がこの権限で動くこと自体は増える面である。
- **測っていて、直していないこと（重要）**
  - 🔴 **送出経路が「開いたまま」落ちた瞬間から、運用が閉じるまでの窓は残る。**
    決定 3 のとおり、自動で閉じるには SPI・前段プロキシ・調停器のいずれかが要り、
    **いずれも本 issue の裁量を超える**。現状は**検出**（#1144 の到達判定 G8 と本 PR の実行時の門）と
    **運用手順**で塞いでいる。**開発環境では送出先がクラスタ内に閉じている**ため（#1144）、
    **外部リレーの停止ではこの窓は開かない** —— 開くのは「近接 MTA 自体の停止」だけである。
  - 🔴 **go-live の topology では窓が広い。** 計画 `ADR-0045` 決定 2-b は
    「Keycloak → `smtp.gmail.com:587`」を接続の書式として定めており、**その構成では上流の停止が
    そのまま利用者名の判定器になる**。実装側は決定 9 の捕捉用 MTA を dev で挟んで塞いだが、
    **go-live の topology は計画の領分**である。**環流する**（下記フォローアップ 1）。
- **フォローアップ**
  1. **計画へ環流する**: 「**Keycloak を外部リレーへ直結させない**（常時受け付ける近接 MTA を挟む）」を
     `ADR-0045` の決定 9 の production 版として検討してほしい、という issue を project-planning へ起票する。
     根拠は本 IADR の 4 状態の実測である。
  2. **残る窓の自動閉塞**（決定 3 の A / B / C）は、上の裁定が出てから選ぶ。
  3. `docs/tests/SC-15_password-reset.md` の **T-21（閉じた状態の同値性）は手動のまま**である
     （状態を作る操作を伴うため）。自動化するなら使い捨てのスタックで行う。
