# IADR-0232 PR の CI は並列化とキャッシュで速くし、検出力は落とさない。日次・週次の失敗は自動起票する

## 状況

PR の CI が遅く、開発の反復が止まっていた。**着手前に実 run を測った**（2026-08-21・
run `32487460689` ほか）。1 push で 8 ワークフロー・約 40 ジョブが起動し、
CodeQL 11分24秒 / CI 8分03秒 / Claude Code Review 3分38秒 が並ぶ。

測って初めて分かったことが 2 つある。

**1 つ目。「ジョブが多いから遅い」ではなかった。** `ci.yml` の 20 ジョブは `needs:` を
1 つも持たず全並列であり、17 個の軽量ジョブ（各 10〜17 秒）は待ち時間をほとんど作っていない。
遅いのは `build-and-test` **1 本**（7分42秒）で、その中身は
2 ユニットの直列ループと Testcontainers 統合テストの同居である。
**ジョブ数を減らす施策と、クリティカルパスを縮める施策は別の問題である。**

**2 つ目。同じ C# を 1 PR で 5 回コンパイルしていた。**
`ci.yml:build-and-test` / `ci.yml:lint`（`dotnet format` が MSBuild ワークスペースをロードする）/
`codeql.yml`（トレース付き Release ビルド）/ `security.yml:vulnerable-scan`（全 sln restore）/
`ci.yml:template-backend-build`。しかも `setup-dotnet` は本リポで 8 箇所使われて
**1 つも `cache:` を設定していなかった**（`actions/cache` も `NUGET_PACKAGES` も皆無）。

一方で、CI を速くする手段の多くは**検証の精度を落とす**。何をどこまで落としてよいかは
実装側だけでは決められないため、利用者へ裁定を求めた。

## 決定

### 決定 1: PR の精度は落としてよい。ただし落とした分は後段で必ず担保する

利用者裁定（2026-08-21）: **「毎プルリクの精度は下がってもいいが、develop ブランチ
マージ時か日次実行にするなどしてどこかで担保できるようにする。そのときに失敗したら
自動で issue を起票する」。**

> 🔴 **［2026-08-22 改定 3］この裁定は一度も取り消されていない。**
> 途中の「なるべく精度は落とさない方向で」を「PR から外す案は全部取り下げよ」と読んで
> 決定 3・4・5 をすべて差し戻したが（改定 2）、**これは読み違いだった**。
> 利用者の再指摘: 「**プルリク時の精度低下は、どこかで回収できるならある程度許容する**ので、
> AI コーディング→プルリク→CI→AI コーディング…の**ループ効率が上がるように**してください」。
>
> 「なるべく」は「**両立する手段を優先せよ**」の意であり、土台を取り消すものではなかった。
> **改定 3 で土台へ戻し、評価軸を「PR の待ち時間 ＝ ループ 1 周の長さ」に置き直す。**
>
> **判断基準（今後ぶれさせない）**:
> 速くなるが精度が落ちない手段 → **無条件で採る**。
> 速くなるが精度が落ちる手段 → **回収先を書けるなら採る。回収先が無いなら採らない。**

この裁定が本 IADR の他のすべての決定の性格を決める。以下の決定 3・4・5 は
「検証をやめる」のではなく**「検証を PR から後段へ移す」**である。両者は結果が違う。
**後段が黙って赤いまま放置されれば、移しただけで失っているのと同じになる。**
したがって**自動起票は付随的な便利機能ではなく、この設計の成立条件である。**

担保の場所と精度:

| PR で落とすもの | 担保する場所 | 後段の精度 |
| --- | --- | --- |
| Testcontainers 統合テスト | `integration.yml`（`push: develop` ＋ 日次） | **PR 前と同一** |
| CodeQL の生成コード解析 | `codeql.yml`（push ＋ 週次・`build-mode: manual`） | **現状と同一** |
| `vulnerable-scan` | `security.yml`（push ＋ 週次） | **現状と同一** |

### 決定 2: 必須 check 名は 1 つも変えない。matrix は集約ジョブで名前を保つ

ブランチ保護の必須 check 名はジョブ ID そのものであり、消えると PR が恒久的にマージ不能になる。
`build-and-test` を matrix 化すると `build-and-test (platform)` へ改名されてしまう。

そこで matrix は別ジョブ ID（`backend-build` / `backend-format`）へ切り出し、
`build-and-test` / `lint` は `needs:` ＋ `if: always()` で結果を判定するだけの
**集約ジョブ**として名前を維持する。

**これは新しい発明ではない。** `images.yml` が `changes` → `build`（16 並列 matrix）→
`image-build`（集約）で既に実装しており、同ファイルのコメントが理由まで書いている
（`IADR-0067`）。**リポ内の既存パターンの横展開であり、ブランチ保護の手動更新は発生しない。**

### 決定 3: 統合テストは PR から外し、`integration.yml` で全量回収する

**［2026-08-22 改定 1］**当初は AST の `IADR-0049` に倣って PR から外す設計だった。
**［2026-08-22 改定 2］**「なるべく精度は落とさない方向で」と読んで PR へ戻した。
**［2026-08-22 改定 3］読み違いを是正し、回収先つきで再び外す**（決定 1 の判断基準に従う）。

変更前は 1 ジョブが `for slnx in ...; do restore; build; test; done` と**直列**に回しており、
クリティカルパスは「全ユニットの合計」だった（実測 462 秒）。現在の形:

- `backend-build`（matrix: ユニット）— restore → build → test（**`--filter "Category!=Integration"`**）
- `build-and-test`（集約・必須 check 名）— 結果を判定し、カバレッジを**報告のみ**（後述）
- `integration.yml`（**回収先**）— push: develop ＋ 日次 ＋ 手動で**全量**を走らせ、**床を強制**する

**外した理由は実測である。** 改定 2 の形（PR で全量）でのクリティカルパスは
`backend-build (knowledge)` の **2 分 44 秒**であり、その大半が Testcontainers
（実 RabbitMQ / Postgres / MinIO）の起動だった。**ループ 1 周の待ち時間に最も効くのがここである。**

#### 🔴 回収先は `--filter` を付けず「全量」で回す（ここが設計の要）

`integration.yml` で `--filter "Category=Integration"` を**使わない**。これで 3 つの問題が同時に消える。

1. **カバレッジ床を置き直さずに済む。** 床 `line 39 / branch 27` は
   **統合テストを含む全量 43/43 の実測**から置かれている（`src/coverage-floor.json` の根拠欄）。
   全量で回すなら**床はそのまま使える**。
2. **二重集計が起きない。** 同じテストプロジェクトを 1 回しか実行しないため Cobertura は 15 件のまま。
3. **fail-closed の門が要らなくなる。** フィルタが無いので「Trait の付け忘れで 0 件実行のまま緑」が
   起こり得ない。🔴 **門を諦めたのではない** —— 門は「フィルタに依存するなら併設する」ものであり、
   **依存自体を無くしたということである。ここへ `--filter` を戻すなら門も必ず戻すこと。**

さらに、**両側でフィルタしない**ことで `[Trait]` の付け忘れが **fail-safe に倒れる** ——
付け忘れたテストは `ci.yml` 側の除外に掛からず**PR に残る**（少し遅くなるだけで検証は失われない）。
両側でフィルタしていると、同じ付け忘れが「**どこでも走らない**」に倒れる。

#### 🔴 カバレッジ床は PR で `--report-only`、回収先で強制

床は全量の実測から置かれているため、**統合テストの無い PR へ当てると必ず割れる**。
かといって PR 用に低い床を別に置くと、**床が 2 つ並んでどちらが本物か分からなくなる**。

- **PR**（`build-and-test`）: `check-coverage-floor.js --report-only` —— 数値はログに出るが落とさない。
- **`integration.yml`**（全量）: フラグ無しで**床 39 / 27 を強制**。失敗は自動起票。

**門は 1 つだけ置く。** 🔴 **PR 側の `--report-only` を外すと、床割れで PR が恒久的に赤くなる。**

#### 実測で 1 度踏んだ事故（改定 2 の実装）

改定 2 の実装は「ユニット並列 × 単体／統合の分離」で、**同じテストプロジェクトを 2 回実行**していた。
**coverlet はテスト実行ごとに Cobertura を出すため、0 件一致の実行でも「全クラス・被覆 0」の
レポートが出る。** `check-coverage-floor.js` はレポートを単純合算する（クラス単位の重複排除が無い）ため、
**行の分母だけが 2 倍**になった。

| | レポート | 行（被覆/全体） | line | branch |
| --- | --- | --- | --- | --- |
| 変更前（ベースライン） | 15 件 | 9958 / 24947 | 39.92% | 28.36% |
| 分離実装（run `32496937488`） | **30 件** | 10087 / **49894** | **20.22%** | **14.27%** → fail |
| 改定 2 の是正後（run `32499045863`） | 15 件 | 9960 / 24947 | 39.92% | 28.36% → OK |

🔴 **不変条件: 1 テストプロジェクト = 1 Cobertura レポート。**
**同じテストプロジェクトを 1 つの run の中で 2 回実行してはならない。**
**割れ方は fail なので気付けるが、「テストが減った」と取り違えやすい。**

#### Trait の欠落（着手前の走査で見つけた 1 件）

`Storage/ObjectStorageRoundTripTests.cs` は `MinioBuilder().WithImage(...)` で MinIO の
Testcontainer を起動するのに `[Trait("Category", ...)]` を持っていなかった。
**改定 3 の形でもこの是正は要る** —— `ci.yml` の `--filter "Category!=Integration"` に掛からず
PR に残り続けるためである（落ちはしないが、外したはずのコンテナ起動が PR に残る）。
同プロジェクトの他 11 クラスと同じ形に揃えた。

この経験は一般化できる: **「フィルタで振り分ける」変更は、フィルタの母集合を
走査してからでないと振り分けたことにならない。** 件数を実測するまで「分けた」と言わない。

### 決定 4: CodeQL は PR だけ `build-mode: none`。全量解析は push / 週次で回収する

**［2026-08-22 改定 2］**「PR だけ `none`」を一度取り下げた。
**［2026-08-22 改定 3］利用者裁定（ループ効率優先）により再び採る。**

```yaml
build-mode: ${{ github.event_name == 'pull_request' && 'none' || 'manual' }}
```

着手前の実測（2026-08-21）で本ワークフローは **11 分 24 秒**掛かり、PR で最も長かった。

- **PR**: `none`。**生成コード（EF Migrations・source generator 出力。カバレッジログの実測で
  270 クラス / 8990 行）が解析対象外になる。これが落とす精度である。**
  トレースビルドに要る 3 ステップ（submodule 取得・`setup-dotnet`・キャッシュ・明示ビルド）も
  `if: github.event_name != 'pull_request'` で止める。
- **push（develop / main）／週次 schedule**: `manual` ＋ トレースビルドで**全量解析**。
  **PR で落とした精度はここで回収する。** 失敗は `report-failure` が自動起票する。

🔴 **同じ check 名で PR と後段の精度が違う。読み手が最も誤解しやすい点である**ため、
ワークフローのコメントにも明記した。本ワークフローは**必須チェックではない**ので、
PR で軽くしてもマージ判定は変わらない。

### 決定 5: `vulnerable-scan` は PR から外し、push / 週次で回収する

**［2026-08-22 改定 2］**一度 PR へ戻した。
**［2026-08-22 改定 3］利用者裁定（ループ効率優先）により再び外す。**

本ジョブが見るのは「**既存の**推移依存 × **後から公開された** advisory」であり、
PR の差分とは元来無関係である。全ソリューションの restore を伴うため PR ごとの費用が大きい。

**PR で見えなくなるもの**: その PR が新しく持ち込んだ依存に既知の advisory がある場合。
**ただしこれは `dependency-review` が PR で捕まえる**（同じ `security.yml` の別ジョブ）。
本ジョブ固有の価値（既存依存への新規 advisory）は時間の経過で現れるため、
**push ＋ 週次 schedule で間に合う。** 失敗は `report-failure` が自動起票する。

### 決定 6: Node 検査ジョブは束ねるが、検査は 1 本も減らさない

17 ジョブを `static-checks` / `static-checks-units` の 2 つへ束ねる。
`commit-messages`（必須）・`scripts-tests`（45+ の子プロセスを回す実質ヘビージョブ）・
`template-backend-build`（dotnet 必要）は単独のまま残す。

🔴 **束ねる際、失敗の可読性を落としてはならない。** 単純に連続ステップへ並べると
**最初の失敗以降の検査が走らず**、1 回の CI で 1 件しか分からなくなって往復が増える。
1 ステップ内で全検査を回し、失敗を蓄積してから落とす形にする。

🔴 **既存ジョブのコメントを 1 行も捨てない。** このリポジトリのワークフローのコメントは
ADR 番号・事故の経緯・「これを外すと検査が空回りする」という設計要点を持つ資産である
（例: `deploy-manifests` の「overlay 名をここへ書かないこと。書くと次に overlay が
増えたとき静かに検査対象から外れる」）。統合先の各ステップ直前へ移設する。

## 却下した案

### 却下 A: 統合テストをプロジェクトごと nightly へ回す

`Deployment` / `EndpointRouting` の 6 クラスまで巻き添えになる。これらは Docker 不要で
速く、PR 時点で manifest 配線の退行を捕まえている。**遅いから外すのであって、
同じディレクトリに居るから外すのではない。**

### 却下 B: CodeQL を PR から丸ごと外す

PR 時点で SAST の指摘が一切出なくなる。**`paths:` を持つため PR で起動しない回もあり、
「指摘が無い」と「起動していない」が読み分けられない。**

**［2026-08-22 改定 3］同節にあった「PR だけ `build-mode: none`」は却下から外し、決定 4 として採った。**
生成コード（実測 270 クラス / 8990 行）が解析対象外になる点は変わらないが、
**push / 週次で回収でき、回収先の失敗は自動起票される**ため、
利用者裁定（ループ効率優先）の下では許容できる精度低下である。**「丸ごと外す」だけが却下として残る。**

### 却下 F:（撤回）統合テストを PR から外して日次へ回す

**［2026-08-22 改定 3］本項は却下ではなくなった。決定 3 として採用している。**
改定 2 で一度却下したのは「なるべく精度は落とさない方向で」の読み違いによるものであり、
**回収先（`integration.yml` の push / 日次）と自動起票を備える以上、裁定の土台に沿う。**
実測でクリティカルパスの大半（`backend-build (knowledge)` 2 分 44 秒）がここだった。

### 却下 C: 自動起票を後追いの別 PR にする

「PR から外す変更」と「後段で担保する仕組み」を別 PR に割ると、
**その間だけ担保が無い窓ができる**。決定 1 の趣旨に反するため同じ PR に入れる。

### 却下 E: frontend の `e2e` を `build-test` へ依存させて二重ビルドを解消する

`frontend.yml` の 2 ジョブは `pnpm install` と `pnpm run build` を二重に行っており、
ランナー時間の無駄は実在する。しかし依存させると **e2e が build-test の完走
（storybook ビルドを含む）を待つ**ことになり、並列だった今より wall-clock が伸びうる。
**本 IADR の目的はランナー時間の節約ではなく PR の待ち時間の短縮**であり、目的に対して逆向きになる。
重複の解消は「依存させずに `dist` を共有する」形が要るため別 issue へ切り出す。

### 却下 D: ワークフローレベルの `paths:` で PR の実行を絞る

`paths:` を持つワークフローは対象外の PR で **report されず恒久 pending** になるため、
必須チェックに指定できない（`docs/ai-workflow.md` の既存ルール）。
出し分けが要る場合は上流ジョブの出力による**ジョブ条件 `if:`** で実装する
（`if` でスキップされたジョブは success として必須チェックを満たす）。

## 影響

- **PR の待ち時間が大きく縮む。** 統合テストと全量 CodeQL を回収先へ移したため、
  `build-and-test` のクリティカルパスは restore / build ＋ 単体テストだけになる
  （改定 2 の実測 3 分 09 秒 → 目標 約 1 分 30 秒）。CodeQL も PR では約 1 分になる。
- 🔴 **PR で走る検証の集合は変更前と同一ではない。** 統合テスト・生成コードの SAST・
  `vulnerable-scan` は PR から見えない。**回収先（`integration.yml` / `codeql.yml` の push・週次 /
  `security.yml` の push・週次）が唯一の門であり、その失敗は自動起票される。**
  **回収先が赤いまま放置されれば「外した」は「やめた」と同義になる。**
- **カバレッジ床の門は `integration.yml` に 1 つだけ。** PR 側は `--report-only` で報告のみ。
- **`develop` / `main` への push は `cancel-in-progress` の対象にしない**
  （全量解析・定期走査の結果が「その時点で走った」記録として残る経路であるため）。
- **必須チェックの最長は `claude-review`（3〜4 分）になる。**
  **ループ 1 周の下限がここで決まる。**（次項）
- 新しい依存として `actions/cache` / `actions/github-script` / `actions/download-artifact` が
  加わる。`scripts/action-versions.json` の `expected` へ同時に追加する
  （片方だけ直すと `check-action-versions.js` が CI で落ちる）。

### 決定 7: `claude-review` は必須のまま残す（裁定 2026-08-22）

本改定後、必須チェックの最長は `claude-review` になる。**ここは削らない。**
人手レビューなしで AI 実装を回す以上、**AI レビューが事実上唯一のレビュー層**であり、
実際に本作業でも `IADR-0049` の誤参照と fail-closed の門の欠落をこれが検出している。
**待ち時間と引き換えに残す価値がある**という判断である。
これ以上ループを縮めるには**本裁定を覆す新しい判断が要る。**

## 残余リスク

- 🔴 **自動起票は「動かないことに誰も気付かない」種類の仕組みである。**
  失敗したときにしか走らないため、平時は常に skip で緑になる。
  **改定 3 では回収先が 3 本（`integration.yml` / `codeql.yml` / `security.yml`）に増え、
  この仕組みへの依存が改定 2 より強くなった。**
  `workflow_dispatch` の `force_failure` 入力で**実際に 2 回走らせて**
  ① issue が立つ ② 2 本目が立たずコメントが足される を実測すること。
  実測しないまま「起票を入れた」と言わない。
- 🔴 **カバレッジ床は「1 テストプロジェクト = 1 レポート」に依存している。**
  `integration.yml` が**フィルタ無しで全量を 1 回**走らせるので、レポートは 15 件・
  床 39 / 27 がそのまま使える。**同じテストプロジェクトを 2 回実行する形へ戻すと
