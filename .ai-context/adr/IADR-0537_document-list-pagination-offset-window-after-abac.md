# IADR-0537: 文書管理の一覧をページで返し、総件数は ABAC で絞った後の数だけを返す

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

## コンテキストと課題

SC-05 の一覧は `GET /bff/documents` を 1 回呼び、台帳の全件（稼働で約 3.9 万件）を並べていた。BFF は gRPC `ListDocuments` で
全件を 1 応答で受け、`IsManageable`（ABAC のスコープ ∧ 個人資料でない）で絞る。応答は約 17 MB になり、grpc-dotnet の既定の
受信上限 4 MB を超えて空一覧に化けた（#1897）。#1899 は D-1 のチャネルの受信上限を 64 MiB に上げて凌いだ。

ページングを足すにあたり、決めることは 3 つある。

1. **どこで切るか。** 後段（文書サービス）は、内容の ABAC の門が閉じている間、組織文書の ABAC を持たない。
   ABAC で絞るのは BFF である。後段で切った窓を BFF が絞ると、ページが短くなり、総件数も境界も絞る前の数になる。
2. **総件数をどう出すか。** オーナーは総件数の表示を求めている。権限外の文書の存在を、総件数・ページの境界・続きの印から
   漏らしてはならない（IADR-0009）。
3. **送り方（cursor か offset）とページの大きさ。**

## 検討した選択肢

### どこで切り、総件数をどう数えるか

1. **後段はキーセットのページで返し、BFF が後段のページを辿りながら ABAC で絞り、絞った後の並びで窓を切って数える（採用）。**
   総件数は絞った後の正確な数になる。権限外の文書は窓にも数にも入らない。1 要求で台帳を 1 周する（O(N)）。
2. **ABAC の条件を後段へ渡し、後段が SQL で絞って数える（棄却）。** 総件数を SQL の `COUNT` で出せるので速い。
   しかし ABAC の実施点を BFF から後段へ動かすことになる（IADR-0041 / IADR-0045。`DocumentBffEndpoints` の注記「移行で判定の位置を
   動かさない」）。属性は jsonb で、分岐（選言）の評価を SQL へ訳す作業も大きい。内容の ABAC の門（#1615）が開く段で扱う。
3. **後段で切って BFF が絞り、総件数は後段の数を返す（棄却）。** 総件数が絞る前の数になり、権限外の文書の存在を数で漏らす。
4. **総件数を返さない（棄却）。** 漏れは無いが、オーナーの要求（総件数の表示）を満たさない。選択肢 1 で正確な数を出せる。

### 送り方

1. **BFF の口はオフセット（`offset` / `limit`）、後段の rpc はキーセット（採用）。**
   - BFF は総件数のために 1 要求で台帳を 1 周する。1 周する以上、BFF の口に続きの印を持たせても読む量は減らない。
     オフセットならページ番号へ跳べる（画面の要求）。
   - 後段の rpc は 1 応答を有界にするための切り方であり、BFF がそれを終端まで辿る。キーセットは途中の文書の削除・追加で
     位置がずれない（`GET /documents/page` と同じ理由。IADR-0475）。
2. **BFF の口もキーセット（棄却）。** ページ番号へ跳べない。総件数を出す限り読む量は同じで、得るものが無い。
3. **後段の rpc もオフセット（棄却）。** 1 回の走査の途中で文書が消えると、後続のページが 1 件ずれて読み飛ばす。

## 決定

**決定 1: gRPC `ListDocuments` をページで返す（proto はフィールドの追加だけ）。**

- `ListDocumentsRequest.page_size = 2`・`page_token = 3`、`ListDocumentsResponse.next_page_token = 2` を足す。番号の追加だけで後方互換である
  （`check-proto-contracts` の baseline を更新）。
- `page_size`: 0（省略）は既定 **500**、上限 **1000** を超えた値は 1000 に丸める。負は `INVALID_ARGUMENT`。
  1 件は約 450 バイトなので、1 応答は約 450 KB で、既定の受信上限 4 MB に収まる。
- 並び: **更新日時の降順・同時刻は ID の降順**（全順序）。REST `GET /documents` の並びも同じ全順序へ揃えた（従前はタイブレークが無かった）。
- 続きの印: キーセット（前ページの末尾の `UpdatedAt` と `Id`）。線上は不透明な base64url（`u1:<ticks>:<Id N 形式>`）。
  壊れた値・`GET /documents/page` の印（`v1:`）は `INVALID_ARGUMENT`。
- 🔴 **読めない文書は切り出す前に除く**（台帳を SQL のキーセットで塊ごとに読み、塊の中で `DocumentReadAccess` を当てる。
  `GET /documents/page` の塊読みと同じ形）。🔴 **続きの印は返した最後の文書から作る**（読めない文書の ID・時刻を載せない）。
- 索引 `(UpdatedAt, Id)` を足す（移行 `AddDocumentUpdatedAtIdIndex`）。降順は索引を後ろから辿る。
- **総件数は gRPC に足さない。** この面が数えられるのは「この面が読める件数」で、BFF の ABAC で絞る前の数である。
- REST `GET /documents` と MCP の `document.list_documents` は全件のまま変えない（呼び出し元の母集合は作業仕様書）。

**決定 2: `GET /bff/documents` はオフセットの窓を返し、総件数は ABAC で絞った後の数だけを返す。**

- クエリ: `offset`（既定 0。負・数でない値は 400）・`limit`（既定 **50**。1〜**100** に丸める。数でない値は 400）。
- 応答: `DocumentListPageDto { items, total, offset, limit }`（`offset` / `limit` は丸めた後の値）。従前の `DocumentDto[]` を置き換える
  （呼び出し元は SC-05 の 1 画面だけ。実測）。
- BFF は後段のページ（1000 件ずつ）を終端まで辿り、`IsManageable` が真の文書だけを数え、その順番が窓に入る文書だけを保持する
  （`DocumentListWindow`）。🔴 **権限外の文書は窓の位置を進めず、総件数にも入らない。** 権限外の文書の有無で、総件数・ページの中身・
  境界は 1 ビットも変わらない（試験 `BffDocumentListPagingTests` が、権限外の文書を混ぜた台帳と混ぜない台帳の応答の一致で固定する）。
- 🔴 **後段の続きの印は BFF の外へ出さない。** 画面に出るのは `offset` / `limit` / `total` だけである。
- 🔴 **後段から一覧を引き切れなかったら（途中のページを含む）502（ProblemDetails）を返し、WARN を 1 行出す。**
  空のページ（`total` 0）へも、そこまでの部分の窓・数へも畳まない —— 空へ畳むと画面は「文書はまだありません。」と出し、
  本当の 0 件と区別できない（#1897 の本質の再発）。502 は運用画面の一覧（`/bff/datasources`・`/bff/conversion/jobs`）と同じ向きである。
  本文は中立の文言だけで、文書の有無も件数も載せない（存在秘匿は崩れない）。画面はエラー表示（再試行つき）にする。
  許可ポリシーが無い（見える文書が無い）ときの空のページ（deny-by-default）は従前どおりである。

**決定 3: 画面（SC-05）は件数の選択（25 / 50 / 100、既定 50）・前後・ページ番号・総件数と表示範囲を出す。**

- ページ番号は先頭・末尾・現在の前後 1 つを出し、間を省略する。件数を変えたら先頭のページへ戻す。
- ページを替える間は前のページを出したままにする（`keepPreviousData`）。
- 削除などで総件数が減り、現在のページが末尾を越えたら、末尾のページへ戻す。
- 一覧の無効化は従前のキー `['/bff/documents']` のままで、全ページのキー（`['/bff/documents', { offset, limit }]`）に前方一致で届く。

## 理由

- 総件数を正確に、かつ漏らさずに出す方法は、ABAC の実施点（BFF）で絞った後に数えることだけである。実施点を動かさない以上、
  BFF が台帳を 1 周する費用を受け入れる。費用は従前（全件を 1 応答で受けて絞る）と同じ桁で、1 応答の大きさだけが有界になる。
- 段 2（絞り込み・並べ替え）は、BFF のクエリ引数を足し、窓へ入れる前の述語を足す形で入る（`DocumentListWindow.Collect` の `visible`）。
  更新日時以外の並べ替えは、後段の rpc に並べ替えの引数を番号の追加で足す。

## 結果

- #1897 の受け入れ基準「`ListDocuments` の 1 応答の大きさが台帳の件数に比例しない」を満たす（上限 1000 件）。
- 画面は 1 ページ 50 件を描く。BFF の応答も 1 ページ分になる（約 3.9 万件を描いていた）。
- 試験: 後段は `DocumentListPagingTests`（境界・安定順序・読めない文書と印・改ざん・丸め）と `GrpcDocumentReadTests`（REST と同値・
  `INVALID_ARGUMENT`）と `DocumentListKeysetPostgresTests`（実 PostgreSQL の順序・丸め・索引）、BFF は `BffDocumentListPagingTests`（窓と総件数・存在秘匿・後段のページを辿る・丸めと検証・縮退）、
  画面は `DocumentManagementPage.test.tsx`（ページ送り・件数の選択・末尾を越えたときの戻り）と `pageNumbers.test.ts`。
- 配備の順序: 新しい BFF と旧い document-service の組では、後段が全件を 1 応答で返し続ける（印が空なので BFF は 1 回で終える）。
  旧い BFF と新しい document-service の組では、旧い BFF は先頭の 500 件しか受け取らない。両者は同じリリースで配備する。
  旧い画面と新しい BFF の組では、画面が配列を期待して一覧が空に見える（画面と BFF も同じリリースで配備する）。

## 残余リスク

- **1 要求ごとに台帳を 1 周する（O(N)）。段 1 では受容する。**
  - 数値: 稼働の台帳は少なくとも 38,703 件（#1895 の実測）。後段のページは 1000 件なので、1 回の一覧表示で後段への往復は **39 回**、
    受け取る量は 1 件約 450 バイトで **約 17 MB**（従前の 1 応答と同じ量を 39 回に分けて受ける）。ページ送り・件数の変更・更新後の
    無効化のたびに同じ費用がかかる（TanStack Query の既定 `staleTime` 30 秒の間は同じページを引き直さない）。
    後段は塊ごとに `(UpdatedAt, Id)` の索引を位置から引くので、1 往復の SQL は台帳の件数に比例しない。BFF が保持するのは窓の 100 件以下である。
  - **段 2 以降でサーバ側の絞り込み（後段で絞って SQL で数える形）へ移す条件**（いずれか 1 つで移す）:
    (a) PoC の実測で、1 回の一覧表示（BFF の応答時間）の p95 が **2 秒**を超える。
    (b) 台帳が **10 万件**（往復 100 回・約 45 MB）を超える。
    (c) 段 2 の絞り込み（データソース・状態・保存日・表題の部分一致）を足す —— 絞り込みを BFF の窓の述語に置くと全周の費用は変わらず、
        条件に一致する件数が少ないほど無駄が大きい。絞り込みは後段の rpc に番号の追加で渡し、後段が SQL で絞る。
    (d) 内容の ABAC の門（#1615）が開き、後段が組織文書の ABAC を `DocumentReadAccess` で実施するようになる。
  - 移すときも、**総件数は ABAC で絞った後の数だけ**という線（決定 2）は変えない。ABAC を SQL へ訳せない間は、後段の絞り込みで
    母集合を小さくしてから BFF（または後段）が ABAC で絞って数える。
- **走査の途中で更新された文書は、その走査で読み飛ばされ得る**（更新日時の降順なので先頭へ移る）。重複はしない。
  1 要求の中の走査なので、影響は「その 1 回の総件数とページが 1 件ずれる」に留まる。
- **オフセットのページ送りは、ページの間に文書が増減すると行がずれる**（次のページで同じ行が出る・1 行を見逃す）。
  管理画面の閲覧であり、走査（取り込み・再発行）には使わない。
- **#1899 の受信上限 64 MiB は戻さない。** 戻す条件は、(a) 全環境の document-service がページングの版になったこと、
  (b) 稼働で `ListDocuments` の 1 応答が 1000 件以下であることを計器かログで確かめたこと、の両方である。
  戻すときは構成キー `Services__DocumentServiceGrpcMaxReceiveMessageSize` の既定を 4 MB へ戻し、同キーで上書きできることは残す。
- 計画は送り方を定めていない。本決定を計画へ環流するかは計画側の判断に委ねる（下書きは作成済み・未起票）。
