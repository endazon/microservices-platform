## コンテキストと課題

ADR-0033 は辺のデータモデルを確定したが、**リンクの解決規則を未決のまま残した** ——
「相対パス → 文書 ID・外部 URL の扱い・タイトル一致による解決の可否」の 3 点である。
決定 8 は Obsidian 記法から既定型への写像（3 意味層）を定めているが、**リンク先の文字列から
どの文書に行き着くか**は書いていない。#912 はこれを実装側で決めて IADR に残すよう指示している。

加えて実装に着手して 3 つの穴が見えた。

1. **差分の母集合を `SourceDocumentId` で絞れない。** ADR-0033 決定 6 は「当該文書を**起点とする**
   自動抽出の辺を作り直す」と定めるが、対称型（`related`）は書き込み時に (min, max) へ正規化される
   （IADR-0242 決定 9）ため、`SourceDocumentId` は「小さい方の文書 ID」であって抽出の起点ではない。
2. **本文が取れないときの倒し方が決まっていない。** WikiService の `StorageMarkdownReader` は
   プレースホルダー本文へ縮退するが、同じことをリンク抽出でやると本文にリンクが 1 本も無いため、
   差分更新が「全リンクが消えた」と解釈して当該文書起点の辺を全部消す。
3. **フォールバック件数の保持先。** ADR-0033 決定 3 は「フォールバックの発生件数は SC-10 で
   観測できるように」と定めるが、SC-10 の「ナレッジ健全性」節は [IADR-0119](IADR-0119_fr17-21-hold-until-adr-fixed.md)
   により節ごと着手保留である。

## 検討した選択肢

### 論点 1: リンク先の解決手段

| | A. タイトル一致（採用） | B. パス（相対パス）で解決 | C. 解決せずプレースホルダーのノードを作る |
| --- | --- | --- | --- |
| Obsidian 記法との相性 | **良い**（`[[note]]` はノート名そのもの） | 悪い（`[[note]]` にパスが無い） | — |
| 相対パスの起点 | 不要 | **無い**（正規化 Markdown は本文だけを持ち、原本の置き場を運ばない） | 不要 |
| 誤結合のリスク | 同名文書で曖昧（**解決しないことで回避**） | 低い（起点があれば） | 高い（実在しないノードが増える） |
| ADR-0033 との整合 | 決定 2（属性が無いノードは不可視）と両立 | — | **決定 2 に反する**（属性の無いノードを量産する） |

### 論点 2: 差分の母集合の絞り方

| | A. `ExtractedFrom` 列を足す（採用） | B. `SourceDocumentId` で絞る | C. 当該文書を端点に含む auto 辺をすべて置換 |
| --- | --- | --- | --- |
| 決定 6「当該文書を起点とする」の実装 | **正しい** | **誤り**（対称型で起点が入れ替わる） | 誤り |
| 他文書起点の related 辺 | 保存される | **巻き込んで消える** | **巻き込んで消える** |
| 費用 | migration 1 本（NULL 可の列 ＋ 索引） | 0 | 0 |

### 論点 3: 本文が取得できないときの挙動

| | A. 抽出をスキップし辺を触らない（採用） | B. プレースホルダー本文で抽出する | C. 例外を投げてリトライさせる |
| --- | --- | --- | --- |
| 既存の辺 | 保たれる | **全消しになる** | 保たれる |
| ストレージ未配備の dev/test | 静かに機能しない（警告ログ） | 壊す | **起動のたびに DLQ が育つ** |

## 決定

### 決定 1 — リンク先は**タイトルの一致**で解決し、解決できなければ辺を作らない

- 照合先は `graph_documents.Title`（ABAC 属性と同じ**複製**。ADR-0033 決定 2）である。
  **正本（DocumentService）へ同期照会しない** —— ホップごと判定と同じ鮮度契約に従う。
- 順序は **① ordinal 完全一致 → ② 大文字小文字を無視した一致**。②で複数件に当たったら解決しない。
- **0 件（不在）・複数件（曖昧）・自己参照は辺を作らない**（#912 の既定。宙ぶらりんのノードを作らない）。
- **パス指定は最終セグメントで解決する**（`[[folder/note]]` / `[docs/note.md](docs/note.md)` は
  いずれも `note`）。相対パスの起点となる情報が正規化 Markdown に無いためである。
  拡張子 `.md` は落とし、URL エンコードは復号する。
- **外部 URL（スキーム付き絶対 URI）は辺にしない。** グラフのノードは本システムの文書であり、
  外部 URL に対応するノードが無い。文書内アンカーのみの参照（`[x](#見出し)`）・画像も同じ。

### 決定 2 — 構文 → 既定型は 3 層で解き、未定義型は `related` へ丸めて**警告とカウンタ**を残す

ADR-0033 決定 8 の表をそのまま写像する。`EdgeTypeResolver`（純粋関数）が持つ。

| 層 | 入力 | 既定型 | アンカー |
| --- | --- | --- | --- |
| ① 明示 | フロントマターのキー（`supersedes: [[x]]` 等） | **キー名** | — |
| ② 文脈 | `[[note#見出し]]`（`#^block` 含む） | `cites` | 見出しを `to_anchor` へ |
| ② 文脈 | `![[note]]` / `![[note#見出し]]` | `embeds` | 見出しがあれば `to_anchor` へ |
| ③ 既定 | `[[note]]` / `[[note\|alias]]` / `[text](uri)` | `related` | 使わない |

- **辞書は実行時に変わる**（決定 3。SC-09 から追加・改名する）。解決器は「今の辞書に在るか」だけを
  引数で受け取り、型 ID を知らない。**①②の名前が辞書に無ければ `related` へ丸め、フォールバックの
  印を返す。**
- **`related` 自体が辞書に無ければ辺を作らない**（seed 前の起動）。存在しない型 ID の辺は後から
  作れないためで、`AiSuggestionGenerator.PersistAsync` と同じ倒し方である。
- **カウンタは抽出側の OTel カウンタに置く** —— `graph.edge_type_fallback.total`
  （Meter `microservices-platform.graph-service`。`IngestTagMetrics` と同型）。
  **SC-10 の画面へは出さない**（「ナレッジ健全性」節は IADR-0119 により節ごと保留であり、
  1 指標だけ差し込むと保留の線引きが壊れる。**裁定が求めたのは観測できることであり、Grafana で
  観測できれば成立する**）。画面の行は保留が解けて同節を作るときに一緒に置く。
- **タグは層（`explicit` / `contextual`）だけにし、型名はログへ回す。** 未定義の型名は書き手が
  自由に書けるフロントマターのキー名で基数が無界であり、時系列の系列数が爆発する。
- **数えるのは発生した回数である**（種類ではない）。ADR-0033 決定 3 の「フォールバックの**発生件数**」を
  字義どおり採る。`IngestTagMetrics`（種類を数える）と違うのは、あちらが「辞書に無いタグの**集合**」を
  1 文書ごとに測るのに対し、こちらは 1 リンクごとに独立した事象だからである。

### 決定 3 — 差分の母集合は `Provenance == auto` **かつ** `ExtractedFrom == 当該文書`

`edges` に **`ExtractedFrom`（`Guid?`・NULL 可）** を足し、自動抽出の起点文書を記録する
（migration `AddEdgeExtractedFrom` ＋ 索引 `ix_edges_extracted_from`）。

- **対称型の正規化で入れ替えない。** 起点は端点の並びと独立である。
- **一意索引 `ux_edges` には参加させない。** 参加させると NULL 同士が相異なる扱い（PostgreSQL 既定）に
  なって重複防止が壊れる。参加させないので、同じ関係を別の文書が起点として二重に持つことはない。
- **遡及移行は不要。** `EdgeProvenance.Auto` の辺は本実装が唯一の生成者である
  （`User` は `GraphEndpoints`、`AiApproved` は `AiSuggestionEndpoints` のみ）。既存の auto 辺は
  テストのフィクスチャにしか存在しない。
- 追加するのは「**どの出所の**既存辺とも一致しないもの」に限る —— 利用者が既に張った同じ関係へ
  auto を重ねると `ux_edges` で衝突し、かつ人の辺を機械の辺で覆うことになる。

### 決定 4 — 抽出の契機は**本文指紋の変化のみ**、本文が取れなければ**辺を触らない**

- 契機は `DocumentUpdated.ContentFingerprint` の変化（ADR-0050 決定 3）。**却下解除と同じ判定材料**で
  あり、同じ `if` に相乗りする。指紋 `null`（発行側が指紋化できなかった＝不明）では抽出しない。
- 本文取得ポート `IGraphContentReader` は**取得不能で `null` を返す**（URI 未指定・ストレージ未配備・
  未知のスキーム）。呼び出し側は警告を残して**辺を一切触らずに抜ける**。
- **実取得の失敗（storage / HTTP の例外）は握り潰さず送出する** —— Wolverine のリトライ・
  デッドレターへ委ねる。`null` は「配備・指定が無い」の側だけを表す。

### 決定 5 — 純粋部分は `GraphService.Domain`、差分同期は当面 `GraphService.Api`

IADR-0280 決定 2 の写像に従い、`ObsidianLink` / `ObsidianLinkParser` / `EdgeTypeResolver` を
**`GraphService.Domain`（本プロジェクト初の実コード）** へ、ポートを `GraphService.Application`、
storage アダプタを `GraphService.Infrastructure` へ置く。

**`LinkEdgeSynchronizer` は `GraphService.Api` に置く。** 写像では調整サービスは Application だが、
本クラスが触る `GraphDbContext` / `Edge` / `EdgeType` は IADR-0280 決定 1 の**段 2 が未着手**で
まだ Api 側にある。**依存の向きに従い、依存先と同じ層へ置く**（段 2 で一緒に移す）。

## 理由

- **決定 1**: Obsidian のリンクは**ノート名**であり、パスを持たない。正規化 Markdown（pandoc の変換物）は
  本文しか運ばず、相対パスの起点が復元できない。したがってタイトル一致以外に解ける手段が無い。
  曖昧なときに解決しないのは、**誤った文書へ辺を張るより張らない方が回復可能**だからである
  （辺は本文からの派生であり、全再構築で復旧できる —— ADR-0033 決定 6）。
- **決定 2**: ADR-0033 決定 3 が「拒否すると取り込み全体が落ち、破棄すると辺そのものが失われる」と
  書いており、丸めて警告する以外の選択肢は既に落ちている。カウンタを画面ではなく OTel に置くのは、
  **保留中の節へ 1 指標だけ差し込むと「どこまでが保留か」が読めなくなる**ためで、
  `IngestTagMetrics`（#637 / planning#304）で同じ線引きが既に採られている。
- **決定 3**: 列を足さない案は**決定 6 の条文をそのまま実装できない**。実装できないまま出荷すると、
  2 文書が互いに `[[...]]` を張ったときに「片方の再取り込みで、もう片方の本文由来の辺が消える」
  という**静かなデータ喪失**になる。migration 1 本（NULL 可の列と索引）はこれに見合う。
- **決定 4**: 指紋を使わないと、タグ改名による全該当文書への再発行のたびに storage 読み取りが走り、
  辺は 1 本も変わらない（ADR-0050 の起点となった実測がこれである）。縮退本文で抽出しない理由は
  上表のとおりで、**「機能が正しく動いたまま静かに消す」形を作らない**という ADR-0033 §結果 の
  警戒と同じ向きである。

## 結果

- 良い影響:
  - ADR-0033 §未決事項の 1 件（リンク解決規則）が閉じ、決定 8 の 3 意味層が実際に辺の型へ届く。
  - 自動抽出・利用者付与・AI 承認済みの 3 出所が差分更新で正しく分離される（決定 4・6 の実効化）。
  - 純粋パーサと型解決が Domain に閉じ、DB もイベントも要らずに単体で試験できる。
- 悪い影響・トレードオフ:
  - **同名の文書が複数あるとリンクが解決しない。** 曖昧さは警告ログにしか出ず、利用者からは
    「辺が張られない」としか見えない。タイトルの一意性を運用で保つ前提が要る。
  - **受容する残余（相互 related の片側喪失窓）**: 2 文書が相互に `[[...]]` を張る場合、行は 1 本に
    正規化されるため**先に抽出した側が起点として記録される**。その起点側がリンクを外すと、他方が
    まだリンクしていても辺は消え、他方の次回本文変更まで復元されない。全再構築（ADR-0033 決定 6 の
    復旧手段）で収束する。**多起点（起点の集合）を持つスキーマは複雑化に見合わない。**
  - **本サービスがオブジェクトストレージへ依存する。** compose / helm の設定が要り、未設定の環境では
    抽出が静かに行われない（警告ログのみ）。
  - `LinkEdgeSynchronizer` の配置が写像どおりでない（段 2 まで Api に居る）。
- フォローアップ:
  1. IADR-0280 段 2（GraphService の移送）で `LinkEdgeSynchronizer` / `GraphDbContext` / `Edge` を
     Application / Infrastructure / Domain へ移す。
  2. SC-10「ナレッジ健全性」節の保留（IADR-0119）が解けた時点で、
     `graph.edge_type_fallback.total` の行を `IngestTagMetrics` と一緒に画面へ置く。
  3. 同名文書によるリンク未解決の実データでの発生率は、取り込み経路が本番データで動いてから測る
     （現時点で測る材料が無い）。
