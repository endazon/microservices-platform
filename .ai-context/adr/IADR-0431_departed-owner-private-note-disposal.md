# IADR-0431: 退職の窓の判定は認可サービスが解き、個人資料の定期処理は述語 1 つで完全削除する

- 状態: Accepted
- 日付: 2026-09-11
- 決定者: 実装（worker。#1409 / 親 #438）

## 起点・関連

- 関連する計画書 ID: FR-19（個人資料）・FR-22（通知。**本経路では送らない**）・UC-11・
  SC-19（固定文言「退職日から 30 日間」）・SC-17（無効化＝起点の発生源）・SC-10（削除の事実の観測）・
  ADR-0096 決定 1〜3（本 IADR の直接の起点）・ADR-0036 D-09 ／ §未確定事項 2・
  ADR-0057 決定 1（削除の射程）／決定 2（残余を置かない）・ADR-0037 決定 5（90 日の器）・ADR-0082 決定 5
- 関連する実装仕様書: `.ai-context/specs/20260911_issue-1409_private-note-disposal-after-window.md`
- 前提として扱う実装ADR: IADR-0428（起点と 3 値判定。**決定 5 を本 IADR が解消する**）/
  IADR-0296（完全削除がオブジェクトストレージの本文へ及ぶ実装）/ IADR-0401（利用者名簿の狭い読み口）/
  IADR-0385（属性の線上表現）/ IADR-0379 決定 4（east-west に利用者トークンを載せない）

## コンテキストと課題

IADR-0428（#1392 / PR #1401）は退職の保持起点と 3 値判定（`Elapsed` / `WithinWindow` /
`NotEvaluable`）を置いたが、**決定 5 で「窓が閉じた後の動作は実装しない」と自ら明記して止めた** ——
ADR-0036 §未解決事項 2 が未決だったためである。

ADR-0096（2026-09-11 裁定・選択肢 A）がこれを確定した。決定 1「30 日が過ぎた個人資料は完全削除する」・
決定 2「削除はシステムの定期処理が行う（既存 `PrivateNoteMaintenanceService` に述語を 1 つ足す形）」・
決定 3「窓の間の管理者の権能は閲覧に限る」。

🔴 **配線前の状態は「退職者の資料が無期限に残る」であり、これは ADR-0096 が退けた案 B と同じである。**

決めるべきは 3 点である。

1. **30 日の窓を誰が解くか**（消費側の knowledge ユニットか、起点を持つ認可サービスか）
2. **無効化の事実をどう運ぶか**（既存の狭い読み口は「有効状態を返さない」と決めていた）
3. **述語を周期のどこへ置き、失敗と通知をどう扱うか**

## 検討した選択肢

### 1. 窓を解く場所

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | **認可サービスが解き、3 値の答えだけを線に載せる** | **採用**。起点の解決・ISO-8601 の固定書式・**30 日**・fail-safe の向きは `RetentionAnchorPolicy`（IADR-0428 決定 2・3）が単一情報源のまま保たれる |
| B | 属性（`account_disabled_at` の生値）を運び、knowledge 側で判定する | 不採用。🔴 **knowledge ユニットは `AuthorizationService.Domain` を参照できない**（ユニット外参照は `src/platform/backend/Shared/` の 3 プロジェクトのみ）。判定を複写すると **30 日が 2 か所に生まれる** —— `PrivateNote.RetentionDays = 90` と混同した実例が既にある（IADR-0428 のコンテキスト）。加えて**どの属性キーが起点かは構成（`RetentionAnchor:Source`）が決める**ので、消費側が構成まで知ることになる |
| C | `RetentionAnchorPolicy` を `Platform.Shared.Kernel` へ移す | 不採用。**起点を書く側（SC-17 の無効化端点）と読む側が同じ場所に居る**のが IADR-0428 決定 1 の形であり、判定だけを共有基盤へ引き上げると「どこが正か」が分かれる。読み手が 1 つ増えただけで共有面を広げない |

### 2. 無効化の事実を運ぶ面

| 案 | 内容 | 評価 |
| --- | --- | --- |
| ア | **既存の `GetUserAttributes` の応答へ `enabled` と判定を足す** | **採用**。面（proto service / rpc / クライアントクラス）を 1 つも増やさない |
| イ | `UserDirectory` へ新しい rpc（`GetRetentionStatus`）を足す | 不採用。呼び出し元は 1 人の利用者を名指しで引くだけであり、**同じ引数・同じ後段（`FindByUsernameAsync`）の rpc が 2 本並ぶ**。往復も増える |
| ウ | 新しい proto service を立てる | 不採用。east-west の面を 1 つ増やす対価に見合わない（IADR-0401 が狭い読み口へ寄せた方針に逆行する） |

🔴 **`GetUserAttributes` は「ロール・**有効状態**・内部 ID は返さない」と書いていた。** その理由は
**「呼び出し元が使わないものを面へ出さない」**であり、ADR-0096 決定 1 が**使う呼び出し元を作った**。
**理由が消えたので制限も外す。ロールと内部 ID は依然として出さない**（使う呼び出し元が無い）。

### 3. 述語の置き場と順序

| 案 | 内容 | 評価 |
| --- | --- | --- |
| a | `RunAsync` の**先頭**へ置く | **採用**（下記 決定 3） |
| b | 90 日の物理削除（`PurgeExpiredAsync`）の後ろへ置く | 不採用。退職者の**論理削除済み**の資料が先に 90 日側で拾われ、**FR-22 ①-c の事後通知が無効化済みの宛先へ飛ぶ**（ADR-0096 決定 1 が「届かない通知を送る設計にしない」と明記した状態になる） |
| c | 独立した定期処理（別 HostedService）を起こす | 不採用。ADR-0096 決定 2 が「述語を 1 つ足す形であり、**新しい定期処理を起こさない**」と明記する |

## 決定

### 決定 1: 判定は認可サービスが解き、線に載せるのは 3 値の答えである

- `platform.authz.v1.UserDirectory/GetUserAttributes` の応答へ `enabled`（bool）と
  `retention_eligibility`（enum）を足す。**rpc もサービスも増やさない。**
- 認可サービス側は `RetentionAnchorPolicy.Resolve` → `Evaluate` をそのまま呼ぶ。
  🔴 **30 日も書式も構成キーも面に出さない** —— 出すと ADR-0082 決定 5 が禁じた
  「配備が計画の決定を弱める」形へ戻る。
- 消費側（knowledge）は `IOwnerRetentionDirectory` という自分のポートで受け、
  契約の enum を自分の enum へ写す。**契約型を定期処理の中まで運ばない。**

### 決定 2: 🔴 proto3 の既定値 `0` は `UNSPECIFIED` であり、消費側は `NotEvaluable` へ倒す

- `RETENTION_ELIGIBILITY_UNSPECIFIED = 0`。`ELAPSED` を 0 に置かない。
- 消費側の写像は `_ => NotEvaluable` である（未知の値も含む）。
- **これは 2 段の fail-safe である** —— 本項目を知らない古い配備が応答すると 0 が返るが、
  0 が「削除してよい」を意味しないので**何も起きない**。逆向き（既定が `ELAPSED`）にすると、
  **配備の順序を間違えただけで全退職者の資料が消える。**

### 決定 3: 述語は `RunAsync` の先頭に 1 つだけ置く

- 述語は `Found && !Enabled && Eligibility == Elapsed`（`OwnerRetentionStatus.IsPurgeable`。**1 か所**）。
- 🔴 **それ以外はすべて残す** —— 名簿に居ない・有効・`WithinWindow`・`NotEvaluable`・
  **引けなかった（`null`）**。ADR-0057 決定 2 により残余を置かないので**誤削除は取り返せない**
  （ADR-0096 §結果）。曖昧さは常に「消さない」へ倒す。
- 🔴 **論理削除の有無を見ない。** 窓が閉じた時点で ADR-0096 決定 1 の対象であり、生きている資料も消える。
  これが 90 日の器（`PurgeAt <= now`）と違う唯一の点である。
- **順序は 90 日の器より先**（上記 選択肢 3-b の通知の漏れを構造で防ぐ）。
- 削除の射程は ADR-0057 決定 1 と同じ —— `DocumentObjectPurger.PurgeIsolatedAsync` で本文の実体、
  `Documents` / `PrivateNotes` の行、`DocumentDeleted` の発行で索引。**新しい削除の意味論を作らない。**
- **失敗は行を残す**（`PurgeIsolatedAsync` が文書ごとに隔離する。IADR-0296 決定 3）。
  所有者の状態が変わらない限り次周期で再入する。

### 決定 4: 監査は「いつ・誰の・何件」だけ。通知は 1 件も送らない

- `audit.Record("private-note.purge.departed", ownerId, "granted", $"count={n}")`。
  🔴 **タイトル・本文・資料 ID を載せない** —— 残余を置かないという ADR-0057 決定 2 を、
  ログ経由で破らない。時刻は監査ログの行そのものが持つ。
- FR-22 ① の通知を送らず、`PrivateNoteUsage.RecordUsageAndWarnAsync` も呼ばない
  （容量警告が同じ宛先へ飛ぶ）。**宛先は無効化済みである。**

### 決定 5: 口が構成されていない配備では 1 件も削除しない

- `Services:AuthorizationServiceGrpc` が未宣言なら `UnavailableOwnerRetentionDirectory`
  （常に `null` を返す）を登録する。🔴 **口の不在を「窓が閉じた」へ倒さない。**
- 例外を投げる縮退にしない —— 定期処理の他の 5 段（90 日の物理削除・版の刈り取り・3 段通知）まで
  巻き添えで止まる。

## 理由

- **判定を認可サービスへ寄せたのは、複写を避けるためである。** 30 日は計画の決定であり
  （ADR-0082 決定 5「期間は変えない。変えるのは起点だけ」）、2 か所に置いた瞬間に片方が腐る。
  **ユニット境界が参照を許さない以上、複写か「答えを運ぶ」かの二択であった。**
- **面を増やさなかったのは、呼び出し元が実際に要る問いが既にある rpc の延長だからである。**
  IADR-0401 決定 2 が面を狭めた理由は「呼び出し元が使わないものを出さない」であり、
  **使う呼び出し元ができた項目を出すことはその理由と矛盾しない。**
- **既定値を `UNSPECIFIED` にしたのは、配備の順序を間違えたときの向きを決めるためである。**
  認可サービスと DocumentService は別々に配備される。**古い認可サービス × 新しい DocumentService**
  の組み合わせは必ず一度は起きる。そのとき 0 が `ELAPSED` を意味すると、**起点を持たない利用者まで
  含めて全件が削除対象になる。**
- **陰性対照を 5 本別々に置いたのは、束ねると変異が通り抜けるからである**（実測。§結果）。

## 結果

- 良い影響: ADR-0096 決定 1・2 が配線され、IADR-0428 決定 5 の保留が解ける。
  ADR-0036 §未確定事項 2 が実装の側でも閉じる。**誰も消せない資料が生まれない**
  （NFR-27 の枠も自然に空く）。
- 悪い影響・トレードオフ:
  - 🔴 **所有者 1 人につき 1 往復である**（日次粒度）。個人資料を持つ所有者の数だけ認可サービスを呼ぶ。
    一括照会の口は s2s の面に無く（IADR-0401 決定 2 が列挙を出さないと決めた）、
    **面を広げるより往復を受ける。** 所有者が数万人規模になったら測り直す。
  - 🔴 **誤削除の救済手段は無い**（ADR-0096 §結果）。起点が誤っていた場合、
    IADR-0428 決定 4 の再有効化（起点を消す）が 30 日以内に行われた場合にしか救えない。
  - **実 Keycloak・実クラスタでの疎通は測っていない。** 単体・結合テストが緑であることは、
    実 IdP の予約属性が読めることを意味しない（IADR-0428 §結果 と同じ注記）。
  - **共有されていた資料の共有先へは何も通知されない**（ADR-0096 §残るもの。計画側の裁定待ち）。
- **変異による裏取り**（宣言ではなく実測。`OwnerRetentionStatus.IsPurgeable` を 1 か所書き換えて計測）:

  | 変異 | 結果 |
  | --- | --- |
  | `!Enabled` → `Enabled`（述語の反転） | 10 件中 **6 件が赤**（在籍中の陰性対照を含む） |
  | `== Elapsed` → `!= WithinWindow`（`NotEvaluable` の門を外す） | **1 件が赤**（`起点が未供給または読めない所有者の資料は消えない`） |
  | `Elapsed` → `WithinWindow` | 10 件中 **6 件が赤** |

- フォローアップ:
  1. ADR-0096 フォローアップ 2（**無効化時に同期トークンが確実に失効するか**）を実測して
     計画へ環流する。🔴 失効しないなら、決定 3（窓の間の権能は閲覧に限る）は管理者側だけを縛っており
     **本人側の egress が開いている**。
  2. 稼働クラスタで予約属性の読み出しと本経路の発火を実測する（IADR-0428 フォローアップ 3 と同じ機会）。
  3. 効果測定（ADR-0096 フォローアップ 5）「起点を持つが削除されていない利用者の件数」を数える器は
     本 PR では置いていない。監査ログ（`private-note.purge.departed`）と SC-10 が観測点である。
