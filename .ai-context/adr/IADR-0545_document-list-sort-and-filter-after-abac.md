# IADR-0545: 文書管理の一覧の並べ替えは後段のキーセットで行い、絞り込みは BFF が ABAC の後に当てる

## コンテキストと課題

段 1（IADR-0537）で、`GET /bff/documents` はオフセットの窓と ABAC で絞った後の総件数を返すようになった。BFF は後段の
`ListDocuments`（更新日時の降順のキーセット）を終端まで辿り、`IsManageable` で絞りながら数える（1 要求で台帳を 1 周する）。
オーナーは段 2 として、並べ替え（更新日時・表題など）・表題の部分一致・状態などの絞り込み・件数の要約（全体と絞り込み後・状態別）を求めている。

決めることは 3 つある。

1. **並べ替えをどこで行うか。** BFF は窓の 100 件しか保持しない。並べ替えは後段の並びそのものを変える必要がある。
2. **絞り込みをどこで当てるか。** IADR-0537 (c) は後段の rpc へ渡すと定めた。しかし画面は「全体 n 件」も出す。
3. **索引でまかなえない並べ替えをどう扱うか**（台帳は約 4〜5 万件）。

## 検討した選択肢

### 並べ替え

1. **後段の rpc に並べ替えの enum を足し、キーごとのキーセット（続きの印が並べ替えを持つ）で辿る（採用）。**
   どのキーも複合索引 `(キー, Id)` の開始位置から引ける。BFF は並びを変えずに窓を切る。
2. **BFF が全件を受けて並べ替える（棄却）。** 窓の外も保持することになり、BFF のメモリが台帳の件数に比例する（IADR-0537 の「保持は窓だけ」を崩す）。
3. **後段がオフセットで並べ替えて返す（棄却）。** 1 回の走査の途中の増減で行を読み飛ばす（IADR-0537 の送り方の棄却理由と同じ）。

### 絞り込み

1. **BFF が ABAC の後に窓の述語として当てる（採用）。** 1 周の中で「ABAC 後の全体」「状態別」「絞り込み後（窓の母数）」を同時に数えられる。
   費用は段 1 の 1 周と同じで増えない。
2. **後段の rpc へ渡し、後段が SQL で絞る（IADR-0537 (c)。棄却）。** 絞り込み後の窓は安く引けるが、画面が出す「全体 n 件」と状態別の件数は
   ABAC で絞った後の数でなければならず、ABAC の実施点は BFF にある（後段は組織文書の ABAC を持たない）。全体の数のために
   絞らない 1 周がもう 1 回要る —— 合計の費用は採用案と同じかそれ以上になる。
3. **後段で絞り、全体の数は出さない（棄却）。** オーナーの要求（全体と絞り込み後の件数の要約・状態別の件数）を満たさない。

### 索引でまかなえない並べ替え

- 並べ替えのキーは **更新日時・作成日時・表題の 3 つ（各昇降）に限る**。更新日時 `(UpdatedAt, Id)` と作成日時 `(CreatedAt, Id)` の索引は在る
  （IADR-0537 / IADR-0509）。表題は `(Title, Id)` の索引を足す（表題は最大 500 文字で、btree の 1 項目の上限に収まる）。
- **データソースの並べ替えは入れない。** 一覧の契約（`DocumentDto`）にデータソースが無く、台帳の `DataSourceName` には索引も無い。
  入れるなら契約へ足す段で、索引と併せて判断する。
- 表題の部分一致（`%q%`）は索引で引けないが、絞り込みは BFF の述語なので後段の SQL の形を変えない（1 周の費用のまま）。

## 決定

**決定 1: gRPC `ListDocuments` に並べ替えを足す（proto はフィールドと enum の追加だけ）。**

- `ListDocumentsRequest.sort = 4`（enum `DocumentListSort`）。`UNSPECIFIED`（0）は従前の更新日時の降順。ほかに更新日時の昇順・作成日時の降順・昇順・表題の昇順・降順。
  **未定義の値は `INVALID_ARGUMENT`**（既定へ畳むと別の並びのページが黙って返る）。
- 並びは常に全順序: キーが同値なら ID。**ID の向きはキーと揃える**（降順のキーは ID も降順）—— 1 本の複合索引を前からも後ろからも辿れる。
- 続きの印は並べ替えを持つ。既定の並び（更新日時の降順）は従前の `u1:<ticks>:<id>` のまま（配備の途中で新旧の document-service が混ざっても読める）。
  ほかは `s1:<キー>:<値>:<id>`（表題は UTF-8 の base64url で包む）。🔴 **要求の並べ替えと印の並べ替えが違えば `INVALID_ARGUMENT`**。
- 比べ方は SQL に任せる（IADR-0509）。表題は `string.Compare` で書き、SQL の `<` / `>` に訳される（ORDER BY と同じ照合順序で比べる）。
  先頭の「キー <= c」（昇順は「>= c」）を索引の開始位置に使う（実 PostgreSQL の EXPLAIN で固定）。
- 索引 `(Title, Id)` を足す（移行 `AddDocumentTitleIdIndex`）。
- 🔴 **読めない文書は切り出す前に除き、印は返した文書からしか作らない**（IADR-0537 決定 1 のまま。表題も読める文書の表題しか印に載らない）。
- **総件数・絞り込みは rpc に足さない**（決定 2）。

**決定 2: `GET /bff/documents` は並べ替え・表題の部分一致・状態の絞り込みを受け、絞り込みは ABAC の後に窓の述語で当てる（IADR-0537 (c) を改める）。**

- クエリ: `sort`（`updated-desc` 既定 / `updated-asc` / `created-desc` / `created-asc` / `title-asc` / `title-desc`）・
  `q`（表題の部分一致。大文字小文字を区別しない序数比較。前後の空白を除き、空は無指定。最大 200 文字）・
  `status`（`draft` / `normalized` / `published` / `archived`）。**未知の値・長すぎる `q` は 400**（後段を呼ばない）。
- 応答 `DocumentListPageDto` に `unfilteredTotal`（ABAC 後・絞り込み前の件数）と `statusCounts`（同じ集合の状態別の件数）を足す。
  `total` は窓の母数（ABAC ∧ 絞り込み）。
- 1 周の中の順序は **ABAC → 全体・状態別の数 → 絞り込み → 窓** である。🔴 ABAC で落ちた文書はどの数にも入らない
  （試験 `BffDocumentListFilterTests` が、権限外の文書を混ぜた台帳と混ぜない台帳の応答の一致で固定する）。
- 後段への要求は、1 回の走査の中で同じ並べ替えを渡し続ける（印が並べ替えを持つため）。

**決定 3: 画面（SC-05）は一覧の上に操作の帯（表題で検索・状態・並べ替え・条件を解除）を置き、件数の要約と本文・更新日時の列を出す。**

- 表題の検索は入力が止まってから 300 ms 後に引く（1 打鍵ごとに台帳を 1 周させない）。条件を変えたら先頭のページへ戻す。
- 状態の選択肢に状態別の件数を添える。要約は「全 n 件中 a–b 件」／絞り込み時は「絞り込み m 件（全 n 件）中 a–b 件」。
- 全体が 0 件の「文書はまだありません。」と、絞り込みの結果の 0 件（「条件に一致する文書はありません。」と条件の解除）を分ける。
- **「索引の状態」の列は出さない**（台帳に無く、索引は取り込み側が持つ）。台帳で出せる「本文」（本文あり／本文なし〔原本を参照〕／本文未設定）を出す。
  見出しも「本文」とし、索引の状態と読み違えさせない。
- 長い表題は 1 行で省略し、全文はホバー（`title`）で出す。リンクの名前（読み上げ）は全文のまま。操作は 1 行に並べ、溢れたら表が横にスクロールする。

## 理由

- 総件数（全体・絞り込み後・状態別）を正確に、かつ漏らさずに出す方法は、ABAC の実施点（BFF）で絞った後に数えることだけである（IADR-0537）。
  全体の数を出す以上 1 周は避けられず、その 1 周に絞り込みの述語を載せれば費用は増えない。後段で絞る形は全体の数のための 1 周を別に要する。
- 並べ替えは窓の外の文書の位置を変えるので、BFF の窓では行えない。後段のキーセットに載せれば、1 応答も BFF の保持も有界のままである。
- 3 つのキーを索引で引けるので、1 往復の SQL は台帳の件数に比例しない（IADR-0537 の性質を保つ）。

## 結果

- 試験: 後段 `DocumentListPagingTests`（6 通りの全順序・読めない文書・印の往復と改ざん・不一致・未定義）・`GrpcDocumentReadTests`（別の並べ替えの印は
  `INVALID_ARGUMENT`）・`DocumentListKeysetPostgresTests`（実 PostgreSQL で同じキーの群を辿る・`(Title, Id)` の索引を印の位置から引く）、
  BFF `BffDocumentListFilterTests`、画面 `DocumentManagementPage.test.tsx`・`documentBody.test.ts`、e2e の SC-05 スモークと a11y。
- 配備の順序: 新しい BFF と旧い document-service の組では、`sort` が無視され常に更新日時の降順が返る（並べ替えが効かないだけで、件数は正しい）。
  旧い BFF と新しい document-service の組は従前どおり動く（既定の並びの印は従前の形）。画面と BFF は同じリリースで配備する
  （旧い BFF は `unfilteredTotal` / `statusCounts` を返さない。画面は無い項目を「絞り込みなし」として読むので壊れはしない）。
- 移行 `AddDocumentTitleIdIndex`（索引の追加だけ）。

## 残余リスク

- **1 要求ごとに台帳を 1 周する費用は変わらない**（IADR-0537）。絞り込み・並べ替え・表題の検索を変えるたびに 1 周する。
  表題の検索は入力の 300 ms 待ちと問い合わせの `staleTime`（30 秒）で抑える。
  **サーバ側の絞り込み（後段で絞って SQL で数える形）へ移す条件は IADR-0537 の (a)(b)(d) を据え置く**（(c) は本決定で改めた）。
  移すときは、全体の件数・状態別の件数を出し続けるか（出すなら 2 周目が要る）を併せて決める。
- 表題の並びは台帳のデータベースの照合順序に従う（日本語の読みの順ではない）。画面は「表題の昇順・降順」とだけ示す。
- 「索引の状態」（索引済み・埋め込み待ち・未索引）は出せていない。取り込み側から文書ごとの状態を引く口が要る（#1908 の側の作業）。
- データソース・機密区分・保存日・タグ・プロジェクトの絞り込み、本文のプレビュー、元の URL へのリンク、機械取り込みの見分けは次の段（#1923）。
- 計画は絞り込み・並べ替えを定めていない。画面要素として計画へ載せるかは planning#796 の提案 4 と同じく計画側の判断に委ねる。
