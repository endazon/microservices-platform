# IADR-0522: 知識グラフの辺は明示リンクと共有タグで結ぶ（#1396）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-10-09
- 決定者: claude（#1396 の利用者裁定 2026-10-09 を実装する）

## 起点・関連

- 起点 issue: **#1396**（稼働 PoC で文書 20,290 件・辺 0 本・クラスタ 6,107 件がすべて単独。クラスタ数のオーダーが測れない）
- 利用者裁定（#1396 コメント 2026-10-09）: **辺は「文書内の明示リンク（Wiki・Obsidian のリンク）」と「同じタグを持つ文書」で結ぶ。同じフォルダでは結ばない。埋め込みの類似度でも結ばない。**
- 計画: ADR-0033 決定 3（自動抽出の既定型 `related`）・決定 4（出所 3 値）・決定 6（最新版のみ・差分更新・再取り込みで全再構築）・決定 8（リンク構文）、
  ADR-0034（ホップごと判定）、ADR-0035 決定 1（ハブ文書の次数上限は実装が実データで決める）・決定 3・決定 8、ADR-0083 フォローアップ 2。
- 先例: [IADR-0281](./IADR-0281_obsidian-link-extraction-and-resolution.md)（リンク抽出）・[IADR-0389](./IADR-0389_knowledge-health-producers-and-observation-dimension.md)（リンク先の名前の保存）・
  [IADR-0503](./IADR-0503_republish-document-updated-admin-endpoint-and-driver.md)（再発行）・IADR-0242 決定 9（対称型の正規化）
- 作業仕様書: [`20261009_1396_graph-edges-links-tags.md`](../specs/20261009_1396_graph-edges-links-tags.md)（§調べたこと f-1〜f-6）

## コンテキストと課題

辺が 0 本だった直接の原因は 2 つである（作業仕様書 f-1・f-3）。

1. 稼働の文書（AST のニュース・報告書と検索用 seed）は本文にリンクを持たない。リンク抽出は走っており、抽出数が 0 だった。
2. **タグから辺を作る経路が無かった。** `DocumentUpdated.Tags` は届いているが、GraphService は保持もしていない。

あわせて、明示リンクの側に 2 つの取りこぼしがあった（f-4・f-5）。

3. **Wiki のリンクが解決できない。** Wiki.js の文書ページの正準パスは `doc/<DocumentId>` だが、パーサは最終セグメント（GUID）を題名として解決しに行く。
   さらに Unix の実行環境では先頭がスラッシュのパス（`/doc/<ID>`・`/en/page`）が `file:///…` の絶対 URI として外部 URL 扱いになり、黙って捨てられていた。
4. **後から届いた相手へのリンクが恒久的に辺にならない。** 名前の解決は起点の本文が変わったときにしか走らない。Obsidian の初回同期のように順不同で届くと、相手が未着のリンクは残り続ける。

決めること: 共有タグの辺の形（何本・どの型・どの出所）、二乗の膨張の抑え方、他の出所の辺との関係、Wiki のリンクと後着の解決、既存文書への反映の手段。

## 検討した選択肢

### 共有タグの辺の表し方

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A. 文書どうしの組を直接結ぶ（組あたり 1 本）＋ 文書数の上限** | 2 文書がハブでないタグを 1 つ以上共有すれば `related` を 1 本 | **採用**。計画のノードは文書だけで、既存の探索・ABAC・クラスタ検出がそのまま効く |
| B. タグをノードにする（文書 → タグ → 文書） | 辺は O(N) | 却下。計画のグラフのノードは文書であり（ADR-0033）、タグノードは ABAC の判定対象・SC-18 の描画・クラスタ検出の入力のいずれにも定義が無い。**計画に無いノード種を足すことになる** |
| C. 上限なしで全組を結ぶ | 裁定の字義どおり | 却下。N 文書のタグは N(N−1)/2 本。AST のニュースのように数千件が同じタグを持つと、1 タグで数百万行になる |
| D. タグごとに鎖・星で結ぶ（O(N)） | 連結性だけ保つ | 却下。どの 2 文書を結ぶかが任意（並び順）で、「なぜこの 2 つが結ばれたか」を説明できない。裁定が類似度を退けた理由（説明しにくい）と同じ欠点を持つ |
| E. 組ごとにタグの数だけ辺を張る | 重みが共有タグ数に比例 | 却下。一意索引 `ux_edges` の粒度（同じ関係は 1 本）と探索の辺の上限（ADR-0035 決定 1 の 500 本）を食う。近傍に同じ組が何本も並ぶ |

### 出所の値

| 案 | 評価 |
| --- | --- |
| **自動抽出（`auto`）のまま、内訳列 `AutoSource`（`link` / `tag`）を足す** | **採用**。出所の値集合は計画が 3 値で固定している（ADR-0033 決定 4）。内訳は差分の母集合を分けるためだけに持つ |
| 出所に `tag` を足す | 却下。計画の値集合を実装が勝手に増やすことになる |
| `ExtractedFrom` が null の自動抽出を共有タグとみなす | 却下。暗黙の符号化は後から割れる（null の自動抽出が他の理由で生まれた瞬間に混ざる） |

## 決定

### 決定 1: 共有タグの辺は「ハブでないタグを 1 つ以上共有する文書の組」に 1 本、既定型 `related`・出所 `auto`・内訳 `tag`

- タグの複製を `graph_document_tags(DocumentId, Tag)` に持つ。`Tag` は前後の空白を落として不変カルチャで小文字化し、空は捨て、200 字で切る。
  **受信のたびに全量で置き換える**（本文の指紋に依らない。本文を読まないので ADR-0050 決定 3 の契機を増やさない）。
- 型は名前で `related` を引く（本文のリンクと同じ。辞書に無ければ辺を触らずタグの複製だけ進める）。

### 決定 2: 文書数が `TagEdges:MaxDocumentsPerTag`（既定 **50**）を超えるタグからは辺を作らない

- 既定値は探索のハブ次数上限 `GraphTraversal.MaxHubDegree`（50。ADR-0035 決定 1 を実装が具体化した値）と同じにする。
  **51 文書以上のタグの所属文書は、そのタグだけで次数が 50 を超え、探索の中継点として使われない** —— 行数だけが二乗で増え、探索に効かない。
- 構成で 2〜1000 に変えられる。範囲外は既定へ倒し、起動は落とさない（購読ごと止めない）。
- **上限を跨いだとき**（受信した文書が入ってハブになった・抜けてハブでなくなった）は、そのタグの所属文書の組も作り直す。跨がない限り、受信した文書を含まない組は変わらない。

### 決定 3: 他の出所の辺とは行を重ねず、互いを消さない

- 同じ 5 つ組（`ux_edges`）の辺が既にあれば共有タグの辺を足さない（本文のリンク・利用者付与・AI 承認のどれでも）。
- 本文のリンクが同じ関係を表明したら、**共有タグの行を引き取って**本文のリンクの辺へ書き換える。リンクが消えた後に組がタグを共有していれば、**同じ保存で削除予定の行を**共有タグの辺へ戻す。
  **消して入れ直さない** —— 同じ保存の中で同じ一意キーの行を削除と挿入にすると、PostgreSQL では文の順序次第で一意索引に当たる。
- 利用者付与（`POST /graph/edges`）・AI 承認が共有タグの行と同じ関係を張るときは、その行を引き取る（409 にしない）。**以後はタグを外しても消えない**（ADR-0033 決定 6）。
  本文のリンクの辺に対する従前の扱い（重複は 409・承認は重ねない）は変えない。
- 1 通の処理（ノードの更新・本文のリンクの差分・後着の張り直し・共有タグの差分）は **1 回の保存**に収める。後段は変更追跡の項目（未保存の追加・削除）まで見る（`TrackedEdges`）。

### 決定 4: Wiki の文書ページへのリンクは文書 ID で解決する

- 標準 Markdown リンクの宛先のパスの最後の 2 セグメントが `doc/<GUID>` なら（先頭スラッシュ・ロケール接頭辞・`http(s)` の URL を許す。クエリ・断片は落とす）、名前を `doc/<GUID 小文字>` とする。
- 解決規則（`LinkTargetMatcher`）の先頭で、この形は**文書 ID の一致で**解決し、無ければ不在に数える。題名とは突き合わせない。辺を張る側と未解決リンク数の側は同じ規則を通る（IADR-0389 決定 3）。
- 先頭がスラッシュのパスは絶対 URI として扱わない（Unix で `file:///` に化けていた）。

### 決定 5: 後から届いた相手へは、保存済みのリンクから張り直す

- `document_link_targets` を 1 リンク 1 行にし、名前に加えて構文の別・明示型・アンカーを保存する（未解決リンク数は従前どおり (起点, 名前) で重複を落として数える）。
- 文書の**新規・改名・撤収・削除**のとき、新旧の題名（大小文字を無視）か `doc/<ID>` を指す行を持つ起点と、当該文書に本文のリンクの辺を持つ起点について、
  **起点の本文を読まずに**保存済みの行から辺を作り直す。解決の候補は当該文書の未保存の題名で上書きする（撤収・削除は候補から外す）。
- **構文の別が null の行（本移行より前に保存した行）を持つ起点は作り直さない。** 型が分からない行から作ると `cites` / `embeds` を `related` へ落とし、
  行の無いリンクの辺を「本文から消えた」と読んで消す。次に起点の本文が変わったときの再取り込みで埋まる。

### 決定 6: 既存文書への反映は `DocumentUpdated` の再発行（IADR-0503）で行う。グラフだけを選んで流す口は作らない

- GraphService は文書台帳の全件を読む口を持たない（DB per Service）。タグを含む全項目を運ぶのは `DocumentUpdated` だけであり、再発行の口はそれを通常の門で出す。
- IADR-0503 決定 1 が「射影ごとに選んで出す口は作らない」としており、それに従う。**再発行は取り込みにも届き、埋め込みの費用がもう一度かかる**（§残余リスク）。
- 再発行の通では本文の指紋が変わらないので本文のリンクは作り直さない（既存の抽出結果がそのまま正しい）。タグはこの通で複製され、共有タグの辺ができる。

## 結果

- 裁定の 2 つの出所で辺ができる。辺は既存の `edges` 表に入り、探索・近傍・MCP・クラスタ検出・健全性の指標は**読み取り経路を変えずに**それを見る。
- **ABAC**: 新しい読み取り経路を作らない。共有タグの辺も両端の可視性の連言（IADR-0242 の型ゲート）を通り、権限外の相手は近傍にも件数にも現れない（`TagEdgeAbacTests`）。
  個人資料は従前どおりクラスタ検出の入力から外れる（ADR-0035 決定 8）。
- 健全性の指標への波及（裁定の帰結として受容）: **孤立文書数**は共有タグの辺で減る。**型別の使用件数**の `related` が増える。
  **AI のリンク提案**は既に辺がある組を候補から外すので、共有タグの組は提案されない。
- マイグレーション `AddGraphDocumentTagsAndEdgeAutoSource`: `graph_document_tags` を作り、`edges.AutoSource` を足して既存の自動抽出の辺を `link` で埋め、`document_link_targets` に 3 列を足す（既存行は NULL）。

## 残余リスク（受け入れたもの）

- **ハブの上限で、裁定の「同じタグを持つ文書」の一部を結ばない。** 51 文書以上のタグ（AST のニュースのように件数の多いタグ）は辺を作らない。
  稼働 PoC のタグの分布次第では、上限を超えるタグばかりで辺がほとんどできない。運用仕様書の手順 1（タグの分布）で流す前に確かめる。**上限の値は計画へ環流する**（§フォローアップ）。
- **上限の判定は権限外の文書も数える。** 閲覧者が見える 2 文書が同じタグを持つのに辺が無いとき、そのタグを権限外の文書を含めて 51 件以上が持つことが推せる
  （どの文書かは分からない。件数の下限だけ）。上限を閲覧者ごとに変えることはできない（辺は全員で共有する）。
- **共有タグの辺は「どのタグで結ばれたか」を持たない。** 近傍・MCP の links/backlinks では本文のリンク由来の `related` と見分けられない（応答の契約は出所までしか出さない）。
  SC-18 で辺の根拠を表示するなら契約の追加が要る。
- **同名の題名が多い名前の改名・新規は、その名前を指す起点の数だけ作り直す**（1 通の処理の中で起点ごとに読み込む）。`document_link_targets` の名前は小文字化の式索引を持たないので、
  新規・改名のたびに表を走査する。現状の行数（PoC は 0）では問題にならない。
- **再発行は埋め込みの費用を重ねる**（決定 6）。グラフだけの反映のために全文書を再埋め込みすることになる。
- 移行前に抽出したリンクの起点は後着の張り直しから外れる（決定 5）。PoC の `document_link_targets` は 0 行なので実害は無い。

## フォローアップ

1. **実装 → 計画（環流）**: 共有タグの辺は FR-17 の「リンクは正規化 Markdown からの自動抽出と利用者による明示的な付与」に無い第 3 の出所であり、
   ADR-0033 の出所（決定 4）・自動抽出の定義・ハブの上限（決定 2 の 50）を計画へ記録してもらう必要がある（利用者裁定は #1396 のコメントにしか無い）。
2. **実装 → 計画（環流）**: 稼働 PoC で再発行 → 検出 1 周期の後にクラスタ数のオーダーと大きさの分布を測り、ADR-0083 フォローアップ 2 として環流する（#1396 の残り）。
3. 辺の根拠（共有したタグ）を SC-18 で見せるなら、近傍の応答に内訳を足す契約の改定を起票する。
