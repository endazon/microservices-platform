# IADR-0611: 緊急アクセスの BFF の中継と、SC-03 の閲覧の後段判定の素通し（#2046 の 2 本目）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-10-24
- 決定者: claude（#2046。裁定は planning#841）

## 起点・関連

- 関連する計画書 ID: FR-19（受け入れ基準「緊急アクセス」）、UC-11、SC-19（発動の導線）、SC-03（管理者の閲覧の導線）。
  計画 ADR-0036 D-08（統制の表）、ADR-0034 決定 9（機械の主体は個人資料を読まない）、ADR-0029（east-west gRPC）。
- 前提とする実装 ADR: [IADR-0610](IADR-0610_break-glass-consented-admin-view.md)（後段の判定点 `BreakGlassViewGate`・端点・監査ログ）。
  [IADR-0447](IADR-0447_current-groups-binding-and-shared-with-branch-wiring.md) 決定 4（BFF の読み取りの判定 `IsReadable` は裁量の分岐だけで個人資料を通す）。
  [IADR-0272](IADR-0272_graph-write-action-authorization.md)（書き込みの `write` スコープ。個人資料の BFF の書き込みもこれに従う）。
- 作業仕様書: [20261024_2046_break-glass-bff-relay](../specs/20261024_2046_break-glass-bff-relay.md)。

## コンテキストと課題

1 本目（IADR-0610）で文書サービスに発動記録と閲覧の判定を置いた。2 本目は BFF に口を開ける。課題は 3 つあった。

1. **SC-03 の BFF の詳細・本文が、後段の許可を必ず 404 にする。** BFF の読み取りの判定 `IsReadable`（IADR-0447 決定 4）は、
   許可の根拠が裁量の分岐（`owner` / `shared_with`）であることを要求する。管理者の ABAC は静的属性の分岐しか持たないので、
   後段が緊急アクセスとして許した個人資料を BFF が「スコープ外」として落とす。裁定の受益者が 1 人も読めない。
2. **BFF は後段の許可が緊急アクセスによるものかを知れない。** gRPC の `GetDocument` は「読めた」しか返さない。
   個人資料・所有者でない・共有先の写しが空、といった外形から推すと、共有先として読めた相手と区別がつかず、判定を 2 本目に書くことになる。
3. **BFF は閲覧でない前段でも gRPC の `GetDocument` を呼ぶ**（版の一覧・特定版・書き込みのスコープ確認）。1 本目の形では
   `GetDocument` が常に緊急アクセスを含むので、指名された管理者が版の口や書き込みの口を叩くと、閲覧が返らないのに閲覧の監査ログが 1 行増える。
   本人の確認（下の決定 2）を同じ rpc で行うと同じことが起きる。

## 決定

### 決定 1: 緊急アクセスを判定に含めるかは、呼び出し元が gRPC の要求ごとに明示する（既定は含めない）

- `GetDocumentRequest.allow_break_glass`・`GetDocumentContentRequest.allow_break_glass`（`bool`、番号 3）を足す。**既定（false）は
  緊急アクセスを含めない** —— `DocumentReadUseCase.GetAsync` と同じ判定であり、閲覧の監査ログを作らない。
- BFF が true で呼ぶのは **SC-03 の詳細（`GET /bff/documents/{id}`）とその本文（`/content`）の前段だけ**。本文の rpc に true を立てるのは、
  前段の詳細が緊急アクセスで読めたときだけである（通常の判定で読めた本文に緊急アクセスを問わない）。
- 版の一覧・特定版・書き込みの前段・本人の確認（決定 2）は false のまま呼ぶ。
- REST の `GET /documents/{id}`（文書サービス）は IADR-0610 のまま緊急アクセスを含める（BFF は REST の読み取りを使わない。口を狭める理由が本件に無い）。
- 配備の順序に依らず閉じる向き: 新しい文書サービス × 古い BFF は旗を立てないので開かない。古い文書サービス × 新しい BFF は
  応答の印（決定 3）が立たないので BFF の `IsReadable` が従来どおり落とす。

### 決定 2: 発動・終了・状態は、BFF でも本人の個人資料かを確かめてから中継する（二重の守り）

- BFF の `/bff/private-notes/{id}/break-glass`（発動・状態）・`…/end`（終了）は、中継の前に
  ①人の主体である（機械・名前の無い主体は 404）②文書サービスの読み取りの rpc（**緊急アクセスを含めない**）で 1 件を引き、
  `doc_scope=private-note` かつ `owner` がセッションの利用者名と一致する、を確かめる。満たさなければ後段へ送らず 404（存在秘匿）。
  後段に届かなければ 502（本人の資料が「無い」に化けない）。
- 後段も台帳（`PrivateNote.OwnerId`）と文書の `owner` で本人かを判定する（IADR-0610 決定 4）。どちらか一方が壊れても他人の資料に届かない。
- 既存の個人資料の口（`PrivateNoteBffEndpoints`。IADR-0285）は「本人性の判定は後段が持ち BFF は複製しない」としている。本件だけ確かめる理由は、
  発動が**第三者に閲覧を開く操作**であり、計画 D-08 が「第三者の発動経路を設けない」を統制の中心に置くからである（他の口の判断は変えない）。
  比較は後段の `DocumentBodyIntake.IsOwnedBy` と同じ（大小を区別する完全一致）。判定の軸は `owner` 属性 1 つで、台帳の照合は後段に任せる。
- **発動だけ** ABAC の `write` スコープで前段を絞る（共有の追加と同じ作法。IADR-0272）。**終了と状態には置かない** —— 終了は露出を縮める
  向きであり、ポリシーの有無で止めると指名された管理者の閲覧が 15 分まで続く（端末の個別失効に前段を置かない理由と同じ）。
- 監査ログ（`/bff/break-glass/audit`）は人の主体だけ（機械は 403）。**誰の行まで読めるかは後段が決める**（BFF に管理者の判定を複製しない）。
  `documentId` / `limit` は型で受けて組み立て直し、知らないクエリを後段へ渡さない。

### 決定 3: SC-03 の詳細・本文は、文書サービスが緊急アクセスとして許したことを応答の印で受け、BFF の ABAC を重ねずに通す

- `GetDocumentResponse.granted_by_break_glass`（`bool`、番号 3）を足す。文書サービスは、通常の判定で読めず緊急アクセスの判定
  （IADR-0610 決定 2 の AND の 7 条件。閲覧の監査ログの保存を含む）で許したときだけ true にする。
- BFF の `FetchForViewAsync`（詳細・本文の前段）は、印が立っていればそのまま返す。立っていなければ従来どおり BFF の ABAC（`IsReadable`）を
  AND で重ねる。**緊急アクセスの可否を BFF は決めない（許可も拒否も足さない）** —— 可否はサーバ側の発動記録で要求ごとに決まる（D-08）。
  ABAC の解決に失敗しても（スコープ無し）、後段が許した閲覧は落とさない。
- 応答の共有先の写しは後段が落としている（IADR-0610 決定 2）。BFF で重ねて落とさない。

## 検討した代替案

- **BFF の `IsReadable` に「個人資料なら後段の判定に任せる」枝を足す**: 所有者・共有先の経路でも BFF の ABAC の層が消え、多層防御（IADR-0044）が
  1 枚になる。緊急アクセスだけを通すには許可の理由を後段から受けるしかない。
- **外形（個人資料・所有者でない・共有先が空）から緊急アクセスと推す**: 共有先として読めた相手と区別できず、判定を BFF に 2 本目として書くことになる。
- **応答の印だけを足し、要求の旗は足さない**: 版・書き込みの前段・本人の確認のたびに閲覧の監査ログが増える（課題 3）。監査ログを
  「閲覧 1 件ずつ」とした裁定 5 の意味が崩れる。
- **本人の確認を個人資料の一覧（`GET /private-notes/`）で行う**: 台帳の照合になるが、一覧は資料の数に比例し、容量の行の作成という副作用を持つ。
  状態の照会（残り時間の表示で繰り返し呼ばれ得る）の前段に置くには重い。
- **本人の確認を置かず後段に任せる**（既存の個人資料の口と同じ）: 依頼の要件（BFF でも確かめる二重の守り）を満たさない。

## 結果

- 良い: 裁定の受益者（指名された管理者）が SC-03 の既存の口で読める。BFF は可否を決めず、後段の発動記録だけが決める。閲覧でない前段は閲覧の記録を作らない。
  第三者の発動・終了・状態は BFF と後段の両方で止まる。
- 悪い・受容: 本文の閲覧は前段の詳細の 1 行（属性）と本文の 1 行の 2 行が残る（BFF は本文の前に属性を引くため）。画面が詳細と本文を開くと 3 行になる。
  いずれも本当に読んだ（応答を受けた）ものであり、少なく記録する向きではないので受容する。
- 悪い・受容: ABAC の解決ができない（スコープ無し）利用者の詳細・本文でも、緊急アクセスの判定のために後段を 1 回呼ぶようになった（従前は呼ばずに 404）。
- 配備: 文書サービスと BFF の両方を入れ替える。どちらの順でも閉じる向き（決定 1）。DB の変更は無い。
