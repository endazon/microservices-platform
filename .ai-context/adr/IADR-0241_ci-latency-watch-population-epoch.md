# IADR-0240 逆転監視の母集合は「現在の CI 構成で測られた PR」に限る

## 状況

逆転監視（[IADR-0232](IADR-0232_ci-pr-latency-reduction.md) 決定 8。`ci-latency-watch.yml` /
`scripts/check-ci-latency.js`）は「`build-and-test` の**中央値** > `claude-review` の**最小値**」で判定する。

**中央値は「直近 N 本のマージ済み PR が同じ CI 構成で走った」と仮定している。**
CI 構成を変えると窓の多数派がしばらく旧構成のままになり、**中央値は旧構成の値を現在の値として報告する**。

同決定の**定常性の門**（中央値 ≧ 最小 × 2 なら判定しない）はこれを止めきれない。
門は「構成が変わったほど大きな段差」を検出する仕掛けであり、**段差が 2 倍未満だとくぐる**。

### ai-stock-trading で実際に起きた（本決定はその追随である）

同じファイルを複写して使っている ai-stock-trading で、CI 高速化の直後に発現した。
`build-and-test` は 223 → 125 秒（**1.8 倍**）になったが、窓の backend PR 7 本のうち
最適化後は 2 本しかなく、**監視は数週間「逆転している」と言い続ける状態**になった。

🔴 **監視は嘘をついていない。** 中央値は窓の多数派を映すのだから、多数派が旧構成なら旧構成の値を返す。
🔴 **問題は「窓が入れ替わるまで毎週同じ文言で鳴り続ける」ことである** ——
その間、**本物の再逆転が起きても同じ文言に埋もれて見分けられない**。
「判定しない」とは別の形で、監視が意味を失う。

### 本リポジトリの現状（着手前に実測。2026-08-22）

```
マージ済み PR 10 本を走査: build-and-test 10 件 / claude-review 10 件
build-and-test の中央値 121 秒  vs  claude-review の最小 151 秒（余裕 30 秒）
OK: 逆転していない。
```

🔴 **本リポジトリの監視はいま「判定していて緑」である。** 本決定は**予防**であり、
**最優先の制約は「判定している監視を、判定しない監視に変えないこと」**であった。

## 決定

**しきい値では直らない。** 倍率を動かしても段差の大きさ次第でまた漏れる。**母集合を正す。**

1. **epoch（CI 構成が最後に変わった時刻）を GitHub API から導出する。**
   `GET /commits?path=.github/workflows/ci.yml&per_page=1&sha=<統合ブランチ>` の
   `commit.committer.date`。
   - 🔴 **日付を焼き込まない。** 固定値は必ず腐る —— 同監視が「しきい値を固定値で持たない（自己校正）」と
     決めたのと同じ理由である。
   - 🔴 **`git log` で求めてはならない。** `actions/checkout` は既定で shallow であり、出力が
     **履歴の打ち切り位置**を指し得る。**形式としては正しい日付が返るので気付けない**
     （`.claude/rules/traceability.repo.md` の ★ が同じ罠を警告している）。
   - 🔴 **統合ブランチも焼き込まない。** `sha` を省略すると**リポジトリの既定ブランチ**になり、
     GitHub の設定に依存する。**母集合の PR 自身の `base.ref` の最頻値**を採る ——
     「その計測がどのブランチ向けに行われたか」そのものであり、設定より確かである。
     本ファイルは複数リポジトリへ複写して使うため、ブランチ名の決め打ちは複写先で静かに誤る。
2. **「この計測は現在の CI 構成を表すか」で母集合を絞る。**
   - 🔴 **計測時刻（check 群の開始）で見る。マージ時刻ではない。**
     「CI が走ったのは構成変更の前、マージはその後」という PR は普通に起こる
     （PR を放置している間に統合ブランチ側で `ci.yml` が変わり、リベースせずマージされた場合）。
     その 1 本は旧構成の値なのに母集合へ残り、**本決定が塞ごうとした穴を epoch 自身が再現する**。
   - 🔴 **ただし構成変更を持ち込んだ PR 自身は残す。** その run は**新しい `ci.yml` で走っている**
     （`pull_request` の run は base を取り込んだ merge ref で動く）のに、epoch＝統合ブランチへ載った
     時刻はその run より**後**になる。落ちるのは「**新しい構成での最初の 1 本**」＝最も知りたいサンプルである。
     ai-stock-trading では実際にこれで**母集合が 0 本になった**。
   - **外した本数と、どのブランチのどのファイルで測った epoch かを必ず出力する**（黙って母集合を狭めない）。
3. **最小本数 3 本。** 満たなければ epoch と本数を添えて判定しない。
   **本数の門は null 判定より前**に置く —— **0 本のときこそ epoch を理由に添えねばならない**。
4. **0 本のときの「check 名の設定ミスを疑え」は、epoch で外したのが原因なら出さない。**
   原因が分かっているのに**読み手を誤った方向へ差し向ける**のは、監視が黙って壊れるのと同じくらい害になる。
5. **定常性の門（[IADR-0232](IADR-0232_ci-pr-latency-reduction.md) 決定 8）は残す。**
   epoch は**既知の構成変更**を、門は **`ci.yml` を触らない原因**（依存更新でテストが重くなる等）で
   段差が出た場合を扱う。**役割が違うので片方に寄せない。**
6. **fail-open の向きを 1 箇所だけ逆にしている（意図的）。**
   変更ファイル一覧が引けなかったとき `changedConfig` は false 扱いになり、計測が epoch より前なら
   その PR は落ちる。

   | 誤り方 | 起きること |
   | --- | --- |
   | 落とす | 母集合が 1 本小さくなるだけ。**本数は出力される**（黙っていない） |
   | 残す | **旧構成の値が中央値へ混ざる**＝本決定が塞いだ誤報そのものが戻る |

   「判断材料が欠けたら狭めない」の原則は**黙って狭めないこと**を言っており、数えて出しているここには
   当たらない。**向きを揃えると誤報の側へ倒れる。** 次に読む人が「不整合」として直さないよう、
   コードにも同じ理由を残した。

## 採らなかったもの

| 案 | 理由 |
| --- | --- |
| 定常性の門の倍率を下げる（2 → 1.5 等） | **段差の大きさ次第でまた漏れる。** しきい値の調整では構造が直らない |
| 窓を短くする（10 → 5 本） | 入れ替わりは速くなるが、**外れ値 1 本で中央値が動く**。誤報を減らす目的に反する |
| epoch を日付定数で持つ | **必ず腐る。**「しきい値を固定値で持たない」と決めた理由がそのまま当てはまる |
| `git log` で epoch を求める | checkout は既定で shallow で、**出力が履歴の打ち切り位置を指し得るのに形式は正しい** |
| **backend を skip した PR を母集合から外す**（ai-stock-trading の対応する決定） | 本リポジトリに「backend 非変更 PR で backend ジョブを skip する」機構が**無い**。母集合は二峰性にならず、入れても**恒久的に不活性なコード**になる。🔴 **入れる条件: 本リポジトリが同種の skip を導入したとき。そのとき同時に入れる**（条件を書かない除外は恒久化する） |
| docs のジョブ名参照の検査器（同じく ai-stock-trading 側の決定） | 向こうの `docs/ai-workflow.md` の**表の書式に密結合**している。本リポジトリの同型の乖離は `scripts/README.md` にあり書式が違う。**必要になったら別途** |

## 影響

- `scripts/check-ci-latency.js` のみ。**`.github/workflows/` は触らず、必須チェック名も変えない。**
- **権限の追加は不要**（`contents: read` / `pull-requests: read` / `checks: read` を既に持つ）。
- 自己試験 39 → **65 件**。

### 実測（両方向 ＋ 0 本の場合）

| 条件 | 結果 |
| --- | --- |
| **変更後（本番の設定）** | 母集合 5 本（epoch 以降 4 本 ＋ 構成変更を持ち込んだ 1 本を救済）。**中央値 121 秒 vs 下限 151 秒で判定し「逆転していない」。exit 0** |
| epoch を過去へ（`2026-08-01`） | 母集合 10 本。中央値 121 秒（絞り込みだけが効いていることの対照） |
| epoch を未来へ（`2026-12-01`） | 母集合 0 本。epoch と本数を添えて判定せず、**誤った原因（check 名の設定ミス）は指さない**。exit 0 |

🔴 **最優先の制約（判定している監視を壊さない）を満たしていることを、変更前後の実測で確認した。**

🔴 **ただし「判定する状態」は恒久的には保証できない。実測で確認した。**
本決定を入れた 1 時間後、`#907` が `ci.yml` を **1 行だけ**（カバレッジ床の値）変更したため
epoch が前進し、直近 10 本のうち 8 本が母集合から外れて **2 本**になり、**監視は判定しなくなった**。
カバレッジ床は `build-and-test` の所要と無関係だが、**「挙動に影響するか」は機械では判定できない**
（上記「残余リスク」がその日のうちに現実になった）。

**壊れ方の向きは正しい。** 「2 本しかないので判定しない」と**理由つきで明示**され（黙って緑を返さない）、
マージが数本進めば**自己修復する**。そして**「旧構成の値を現在の値として報告する」ことは無くなった** ——
これが本決定の目的である。

🔴 **フォールバック（本数が足りなければ絞り込みを外して判定する）は採らない。**
それは epoch を入れる前の状態そのもので、ai-stock-trading で数週間の誤報を生んだ経路である
（段差 1.8 倍は定常性の門をくぐる）。**判定しないほうが、誤って判定するより良い。**

### 変異試験（7 種すべて当たることを実測）

緑と件数は証拠にならないので、1 箇所ずつ壊して落ちることを確かめた。

| 変異 | 落ちた試験 |
| --- | --- |
| epoch の絞り込みを無効化 | 3 件 |
| 境界（同時刻）を `>` にする | 1 件 |
| 構成変更 PR の救済を外す | 1 件 |
| 最小本数の門を外す | 3 件 |
| `sha` を載せない（既定ブランチ依存へ戻す） | 1 件 |
| 統合ブランチを最頻値ではなく先頭で採る | 1 件 |
| ページネーションを 1 ページ目で打ち切る | 3 件 |

## 残余リスク

- 🔴 **`ci.yml` へのトリビアルな編集**（コメント追記など `build-and-test` の挙動に影響しない変更）でも
  epoch は前進し、「判定できない」期間が延びる。**意図したトレードオフである** ——
  構成変更を機械的に検出する以上、「挙動に影響するか」は機械では判定できない。
  頻度が問題になるようなら、そのとき初めて手を入れる（**同型の事故 2 回**を待つ）。
- **自己試験は配線を見ない。** 母集合の絞り込みが `collect()` へ実際につながっているかは
  自己試験では確かめられず、**実データでの前後比較でしか見えない**（本決定でも実データで確認した）。
- **ai-stock-trading 側の対応する決定と本決定は、今後も別々に動く。** 同じファイルを複写して
  使っているが、片方に入れた変更がもう片方へ自動で入ることはない。
