# IADR-0272: グラフの書き込みは read と write の 2 スコープで判定し、解決アクションを既定値の無い必須引数にする

- 状態: Proposed
- 日付: 2026-08-23
- 決定者: claude（#993 / 親 #450）

## 起点・関連

- 関連する計画書 ID: FR-05 / FR-17 / FR-18 / FR-21 / UC-10 / SC-03 / SC-21 /
  ADR-0036（D-01・D-07）/ ADR-0034（決定 2・8）/ ADR-0033（決定 7）/ ADR-0051（決定 1〜4）/ ADR-0004
- 関連する実装仕様書: `.ai-context/specs/20260823_issue-993_graph-write-action-authorization.md`
- 前提となる既存決定: [[IADR-0253]] 決定 5（`AccessScopeRequest` へ `Action` を足す。#989 で実装着地）、
  [[IADR-0242]] 決定 2（`AuthorizedNode` の型ゲート）・決定 5（存在秘匿は 404 に一本化）・決定 9（対称型の正規化）

## コンテキストと課題

GraphService の書き込み経路（`POST /graph/edges` / 提案の `approve` / `reject`）が、
**読み取りの認可スコープで判定していた**。`/authz/scope` が `read` をハードコードしていた時代の名残であり、
「**読めるなら書ける**」形になっている。

[[IADR-0253]] 決定 5 が契約へ `Action`（既定 `read`）を足し、#989 が実装を着地させた。
**しかし既定値による後方互換は「呼び出し側の無改修を許す」という意味であり、無改修なら挙動も変わらない。**
契約が直っても、呼び出し側が `Action` を渡さなければ既定の `read` のままである。

決めるべきは 4 つある。

1. **どのアクションを割り当てるか**（`manage` か `write` か）
2. **到達可能性の検証（ADR-0034 決定 8）まで write へ移すのか**
3. **解決したスコープをどこまで使うか**（`Granted` だけか、文書条件まで見るか）
4. **同じ事故が同じ形で再発しないようにするには、何を構造で塞ぐか**

## 検討した選択肢

| 論点 | 案 | 評価 |
| --- | --- | --- |
| 1 | `manage` を渡す | **不採用。** 計画に `manage` の判定規則が無い。計画配下で `manage` が現れるのは §選言 の表と変更履歴の 2 か所だけで、いずれも「実装の `PolicyAction` が 3 値である」という**実測の引用**であり、計画が意味を与えた記述ではない |
| 1 | **`write` を渡す** | **採用。** 計画 `07_abac-attribute-model` §動的束縛 が「`write` 許可: `doc.owner ∈ { ${current_user} }`」を、ADR-0036 **D-07** が同じ規則を定める。値域へ `write` を足した裁定（planning#466・2026-08-22）がこの読み替えを求めている |
| 2 | 書き込み経路の解決を `read` → `write` へ**置き換える**（1 回だけ解決する） | **不採用。** ADR-0034 決定 8 の具体化は「リンク作成時に、リンク先文書に対する作成者の**閲覧権限**を検証する」と書いている。置き換えると閲覧権限の検証が消え、決定 8 と矛盾する |
| 2 | **read と write を別々に解決する** | **採用。** 書き込み経路は「両端は見えているか（read）」と「書いてよいか（write）」という**別の問い**を持つ |
| 3 | `writeScope.Granted` だけを見る | **不採用。** write ポリシーの文書条件を捨てることになり、`confidentiality ∈ {public}` に限った write 権限で `restricted` の文書へ辺を張れる。**#993 と同型の欠陥**（スコープを取得しておいて使わない） |
| 3 | **`AuthorizedNode.Authorize(起点, writeScope)` を通す** | **採用。** 述語を直接呼ばず型ゲートを経由する（[[IADR-0242]] 決定 2 の作法） |
| 4 | `ResolveAsync` の `action` に既定値 `read` を置く | **不採用。** 既定値が黙って read を意味していたことが本欠陥そのものである。残せば同じ形で再発する |
| 4 | **`action` を既定値の無い必須引数にする** | **採用。** 全呼び出しがアクションを明示する。既定値の不在をリフレクションで固定する |

## 決定

### 決定 1: 解決アクションは `write` である（`manage` ではない）

**計画の原文が規則を与えているのは `read` と `write` の 2 つだけである。** `analyze` と `manage` は
値域に列挙されるだけで判定規則を持たない。**規則のあるほうを採る。**

### 決定 2: 書き込み経路は read スコープと write スコープの**両方**を解決する

| 問い | アクション | 根拠 |
| --- | --- | --- |
| 「両端は、この主体に**見えて**いるか」 | `read` | ADR-0034 決定 8 の具体化（**閲覧**権限を検証する） |
| 「この主体は**書いて**よいか」 | `write` | ADR-0036 D-07 |

**既存の read 判定は 1 つも消さない。** write ゲートは**変更の直前**に足す。
片方へ寄せると、決定 8 か #993 のどちらかを壊す。

### 決定 3: write は**起点（source）**に要求する。終点（target）には要求しない

ADR-0034 決定 8 の具体化は、**リンク先に課す条件を「閲覧権限」と明示**している。
target へ write を課すと「自分の個人資料から会社文書へリンクを張る」という、
**同決定が明らかに想定している操作**が成立しなくなる。**計画に無い制約を足さない。**

🔴 **対称型（`related`）では緩い側に残る。** [[IADR-0242]] 決定 9 により対称型は `(min, max)` へ
正規化されるため、A→B と B→A は同じ行になる ⇒ 実質「**どちらかの端点に write があれば張れる**」。
**計画は対称型の書き込み側の端点を定めていない。** ここは裁定待ちの残件として記録する
（本 IADR は成立を主張しない）。

### 決定 4: `IGraphAccessResolver.ResolveAsync` の `action` は**既定値を持たない必須引数**にする

🔴 **これが本 issue の構造的な再発防止である。** 既定値つきの引数は「書かなければ read」を意味し、
**書き忘れが認可の緩みとして現れる**。既定値を外せば、新しい経路を足すたびに**アクションの選択が
コンパイラによって強制される**。既定値の不在は `GraphTypeGateArchitectureTests` がリフレクションで固定する。

**値域は `GraphAccessAction`（`Foundation/Ports/`）の定数として持つ。** 正本は `AuthorizationService` の
`PolicyAction` だが、knowledge → platform のサービス参照は禁止であり、契約 DTO は本作業の担当外である。
**綴りがずれれば `/authz/scope` が 400 を返し、`GraphAccessResolver` が `Granted=false` へ縮退する**
（deny 側に倒れる＝緩む向きの失敗ではない）。

### 決定 5: 拒否は **404** に揃える（403 を足さない）

write 拒否は主体側の性質なので 403 でも文書の存在は漏れない。**それでも 404 に揃える。**
`GraphEndpoints` / `AiSuggestionEndpoints` は「不可視・不存在はすべて 404」を明文の不変条件として持ち
（[[IADR-0242]] 決定 5）、`GraphEndpointsSecrecyTests` が固定している。
**新しい状態コードを足すと、秘匿の 1 本道が 2 本になる。** 診断性は落ちるが、一本道を優先する。

### 決定 6: 提案の**生成**（`POST /graph/suggestions/generate/{id}`）は本 IADR の射程外に置く

生成は `db.AiSuggestions` へ行を足す**書き込みではある**が、次の 2 点により本決定を適用しない。

- **正しいアクションは `analyze` である可能性が高く、計画は `analyze` の判定規則を定めていない。**
  推測で `write` を当てると生成が全件遮断され、#915 が壊れる。
- ADR-0051 は本経路の制約を**要求元の read スコープ**だけで書いている（決定 4「各実行が 1 利用者の
  スコープに閉じていること」）。現状が計画に反しているとは読めない。

**「触れなかった」ではなく「範囲の外に置いた」として記録する。** 裁定が要る事項である。

## 理由

- **契約が直っても呼び出し側が直らなければ何も変わらない。** 既定値による後方互換は無改修を許す仕組みで
  あって、是正ではない。**是正は呼び出し側にしか書けない。**
- **read と write を 1 つのスコープで兼ねる形は、そもそも表現できない。** 決定 8 は閲覧権限を、
  D-07 は書き込み権限を求めており、**同じ 1 回の解決で両方の答えは出ない。**
- **「スコープを取得して使わない」形を繰り返さない。** #993 の欠陥は「間違った問いを投げた」ことだが、
  `Granted` だけを見る実装は「正しい問いを投げて答えを捨てる」形であり、**同じ family** である。
- **既定値は事故の温床である。** #993 の起点は `AccessScopeRequest` の `Action` 不在だったが、
  **その修復に既定値を使ったことで、今度は呼び出し側の書き忘れが同じ欠陥を生む形になった。**
  GraphService の port では既定値を置かない。

## 結果

- 良い影響:
  - 「読めるなら書ける」が閉じる。行為別ポリシーが運用され始めても権限の逆転が起きない。
  - 新しい書き込み経路を足すとき、**アクションの選択が型として強制される**（書き忘れが起きない）。
  - write スコープの**文書条件が効く**ため、write 権限の範囲がそのまま辺の作成範囲になる。
- 悪い影響・トレードオフ:
  - 🔴 **write ポリシーが 1 件も登録されていない環境では、辺の作成・提案の承認／却下が全件 404 になる**
    （deny-by-default の正しい帰結）。**配備時に write ポリシーの登録が前提になる。**
    404 に揃えた（決定 5）ため、**利用者からは原因が読めない。**
  - 書き込み 1 要求あたり `/authz/scope` の往復が **1 回 → 2 回**になる。write の解決は read の検証を
    通過した後に置き、**拒否される要求では 2 回目を発行しない。**
  - 対称型では「どちらかの端点に write があれば張れる」形が残る（決定 3）。
- フォローアップ:
  1. **`analyze` の判定規則を計画へ問う**（RAG・提案生成が `read` のままでよいか。決定 6）。
  2. **対称型の書き込み側の端点を計画へ問う**（決定 3）。
  3. **`BffScopeResolver`（`Platform.Shared.Infrastructure`）が同じ形を持つか確かめる** ——
     BFF の文書書き込み経路が read スコープで判定していないか。担当範囲外のため統括へ返す。
  4. **write ポリシーの配備手順**（計画の write 規則 `doc.owner ∈ { ${current_user} }` をどのポリシーとして
     登録するか）。SC-09 の画面が `write` を選べるようにする追随も要る（#989 が報告済み）。
