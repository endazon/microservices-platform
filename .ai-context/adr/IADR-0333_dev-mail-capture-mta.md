# IADR-0333: 開発環境の捕捉用 MTA を dev 既定で置き、送出先の既定を「外向き」から「内向き」へ反転させる

- 状態: Accepted
- 日付: 2026-09-02
- 決定者: Claude（実装）
- 起点: issue #1144（#1102 から [IADR-0332](./IADR-0332_keycloak-smtp-externalsecret-wiring.md) 決定 5 で分割）。
  先行する実装 ADR: [IADR-0261](./IADR-0261_keycloak-theme-and-smtp-injection.md)（供給方式）/
  IADR-0332（起動器への配線）
- 関連する作業仕様書:
  [`.ai-context/specs/20260902_issue-1144_dev-mail-capture-mta.md`](../specs/20260902_issue-1144_dev-mail-capture-mta.md)

## コンテキストと課題

計画 `ADR-0045` 決定 9（`Accepted`）は「**開発環境では実送信しない。k3s 上に捕捉用 MTA（Mailpit 等）を
置き、送信内容を画面で確認できるようにする。本番のメールテナントを開発環境から指さない**」と
**無条件で**定めている。**その実体がリポジトリに 1 つも無かった**（`deploy/` 配下 0 件。同じ走査器・
同じ範囲で `qdrant` は 16 件＝走査は効いている）。

結果として、開発環境は次の 2 つを同時に抱えていた。

1. **送出先が外を向いたままだった。** `bootstrap.sh` の `SMTP_HOST` 既定は `smtp.gmail.com:587` で、
   **`from` に実値が入った瞬間に外部の本番リレーへ実送信する**側へ倒れる。#1102 が配線を通したので、
   **配線が通ったぶんだけ倒れやすくなっていた**。
2. **`docs/tests/SC-15_password-reset.md` の T-10 / T-16 が「手動（実環境）」で止まっていた。**
   仕様が難しかったからではなく、**メールの届く先がどこにも無かった**からである。

決めるべきことは 5 つ。**①どこに、どのゲートで置くか ②dev 既定をどこで付け替えるか
③ADR-0045 決定 5（STARTTLS 必須）とどう折り合うか ④閲覧 UI をどこへ出すか
⑤「外へ出ない」を機械にどう持たせるか。**

## 検討した選択肢

### 決定 1: ゲート

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A. `deploy/local/infra`（base）へ置き、ゲートを持たせない** | `up` で常に立つ | **採用**。決定 9 は無条件である |
| B. `MAILCAPTURE=1` の opt-in にする | 既存の可観測性・Vault と同じ形 | **不採用**。**ゲートを立てない人の既定が外を向いたまま**になり、決定 9 の弱い版（守る人だけが守る）にしかならない。opt-in の先例（OBSERVABILITY / VAULT / HEADLAMP）は**あってもなくても既定の安全性が変わらない**ものであり、本件は性質が違う |
| C. 永続化オーバーレイにも PVC を足す | 受信箱を再起動で失わない | **不採用**。捕捉したメールは**使い捨て**であり、`up` のたびに空から始まるほうが検査の前提が単純になる（増分で測れる） |

### 決定 2: dev 既定の付け替え先

dev 既定は **2 箇所**にある。**片方だけ直しても、もう片方から外へ出る。**

| 供給源 | 採否 | 増える秘匿値 |
| --- | --- | --- |
| `deploy/keycloak/microservices-platform-realm.json` の `smtpServer`（新規） | **採用**。`--import-realm` した開発環境が**最初から**捕捉用 MTA を指す | **0 個**（`noreply@platform.localhost` はクラスタ外で意味を持たない合成値） |
| `deploy/local/vault/eso/bootstrap.sh` の `SMTP_HOST` / `SMTP_PORT` / `SMTP_STARTTLS` 既定 | **採用**（issue の受け入れ基準 2） | 0 個（`from`/`user`/`password` は**空のまま**） |

**`from`/`user`/`password` を Vault 側で空のまま残した**のは、IADR-0332 決定 4 と runbook §2 の
「長さが 0 なら `kcadm` を打つな」を壊さないためである。**ESO 経路は実リレーの値を入れるための経路**で
あって、dev 既定の経路ではない。

> **`realm.json` へ書いてよいか。** runbook §なぜ realm.json に直接書かないか が禁じているのは
> `from`/`user`/`password` の**実環境の値**であって、**クラスタ内でしか意味を持たない合成値ではない**。
> 同節が「将来 `host`/`port`/`starttls` だけを静的に投入する余地はある」と述べていた枠を、dev 既定として行使した。
> 副作用として **realm を再インポートすると dev 既定へ戻る** —— これは事故ではなく fail-safe である
> （再インポート後にうっかり実送信する状態にならない。IADR-0261 が残した「再インポートで `smtpServer` が消える」
> という限界の**向きが変わった**）。

### 決定 3: ADR-0045 決定 5（STARTTLS 必須・平文フォールバックを許さない）との折り合い

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. 捕捉用 MTA にも STARTTLS を張る | 決定 5 を字面どおり守る | **不採用**。自己署名証明書を Keycloak に信頼させる配線が増えるだけで**守るものが無い** —— 捕捉用 MTA は**読ませるために置く装置**であり、経路はクラスタ内の Pod ネットワークに閉じて外へ 1 通も出ない |
| **B. 捕捉用 MTA 宛に限り平文とし、既定の STARTTLS は「宛先から導出」する** | 捕捉用 MTA なら 1025/平文、**それ以外なら 587/STARTTLS** | **採用** |
| C. `SMTP_STARTTLS` の既定を素朴に `false` にする | 実装が最も短い | **不採用・危険**。実リレーへ向けるために `SMTP_HOST`/`SMTP_FROM`/… だけを渡した運用者が、**STARTTLS 無しで外部へ繋ぐ**（決定 5 の破れ。しかも成功するので気付かない） |

### 決定 4: 閲覧 UI の出し方

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. `mailpit.localhost:50000` のエッジ Ingress（`qdrant` と同型） | ブラウザで開くだけ | **不採用**。Mailpit の UI は**認証を持たず**、中身は**パスワードリセットリンク＝認証資格**である（決定 5 の理由がそう述べている）。qdrant の先例が公開しているのは埋め込みであって資格情報ではない。**認証の無い資格情報ストアをエッジへ出すのは、本 issue の射程外の新しい統制判断**になる |
| **B. Service の HTTP ポート ＋ 運用者が明示的に開く `kubectl port-forward`** | 決定 9 の「画面で確認できる」を満たす | **採用**。`headlamp` の port-forward 手順と同型 |

### 決定 5: 「外へ出ない」の機械化をどこへ置くか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. `check-stack-ready.js` で realm の**実行時** `smtpServer.host` を見る | 稼働環境の実態を直接測る | **不採用**。決定 9 の但し書き（疎通と文面の検証が要る段階に限り実リレーを用いてよい）で運用者が**正当に**実リレーへ向けている状態と区別できず、**正しい状態を赤にする** |
| **B. `check-realm-constraints.js` に静的な門を足す**（realm の静的既定 ＋ Vault seed の既定） | リポジトリの**変更**を捕まえる | **採用**。受け入れ基準 5 が言う「実リレーへ向ける**変更を入れると**落ちる」はそもそも静的な性質である。同検査器は既に realm を計画 ADR と突き合わせており、`--self-test` に**変異させると必ず落ちる**ことを書ける器を持つ |
| C. 新しい検査器を足す | 独立させる | **不採用**。realm を読む器を 2 つ持つ理由が無い |

## 決定

- **決定 1: 案 A。** `deploy/local/infra/mailpit.yaml`（Deployment ＋ Service。SMTP 1025 / HTTP 8025）を
  **base の kustomization** へ入れ、`k8s-local-up.sh [4/7]` で `rollout status` を待つ。**ゲートを持たせない。**
  永続化オーバーレイには加えない。
- **決定 2: 両方の dev 既定を付け替える。** realm の `smtpServer`（新規・秘匿値 0 個）と
  `bootstrap.sh` の `SMTP_HOST`。**実リレーへ向くのは `SMTP_HOST` を明示したときだけ**である。
- **決定 3: 案 B。** 捕捉用 MTA 宛に限り平文（`auth=false` / `starttls=false`）とし、**ADR-0045 決定 5 の
  明示的な適用外**として記録する。**`SMTP_PORT` / `SMTP_STARTTLS` の既定は宛先から導出**し、
  捕捉用 MTA 以外の宛先では決定 2-b の確定値（`587` / STARTTLS 有効）へ**自動的に戻る**。
- **決定 4: 案 B。** エッジへは出さない。`kubectl port-forward svc/mailpit 8025:8025` を
  `k8s-local-up.sh` の最終案内・`deploy/local/README.md`・runbook へ書く。
- **決定 5: 案 B。** `check-realm-constraints.js` に ADR-0045 決定 9 の門を足す。**期待値の単一情報源は
  `deploy/local/infra/mailpit.yaml` の Service** であり、検査器は**宛先の名前を 1 つも持たない**
  （走査して組み立てる）。0 件走査は fail-closed。
- **決定 6（到達判定）**: `check-stack-ready.js` に **G8**（捕捉用 MTA が居る ＋ API がループバックで
  読める）を足す。🔴 **G7 と違い「無ければ飛ばす」をしない** —— 飛ばせるのは opt-in の構成だけであり、
  本件は base の dev 既定だからである。
- **決定 7（T-10 / T-16 の自動化）**: `scripts/check-password-reset-mail.js` を新設し、
  **申請 → 送出 → 受信 → 本文**を通しで測る。`integration-stack.yml` の 3 つめの門にする。
  **TLS の検証は切らない**（クラスタのローカル CA を使う）。
- **決定 8（射程の境界）**: **SC-15 の存在秘匿の破れは本 PR では直さない。** 本 PR が固定したのは
  **送出経路が生きているとき**の同値性（T-10）だけである。**送出が死んでいるときの同値性は #1143**
  が、本 PR が置いた比較器（`normalizeConcealmentBody` / `evaluateConcealment`）を使って足す。
- **決定 9（対象外）**: docker-compose 経路には捕捉用 MTA を置かない（決定 9 は「**k3s 上に**」と明示している）。
  NotificationService（FR-22）の SMTP 送出も対象外（実トランスポート自体が未実装で、**dev 既定が外を
  向いている箇所が無い**）。

## 理由

- **決定 1 の「ゲートを持たせない」**: 本件の欠陥は「既定が外を向いている」ことであり、
  **opt-in にすると同じ欠陥の弱い版が残る**（IADR-0332 決定 1 と同じ形の判断である）。
- **決定 3 の「導出」**: ここが本 PR で最も壊れやすい所である。**素朴に既定を `false` へ書き換えると、
  実リレーへ向ける運用者が平文で外部へ繋ぐ** —— しかも**成功するので誰も気付かない**。
  「捕捉用 MTA 宛のときだけ緩める」は、**緩める条件を宛先に結び付けた**という一点で安全側にある。
- **決定 5 の向き**: 受け入れ基準 5 は「**変更を入れると**落ちる」と書かれている。**変更はリポジトリで
  起きる**のだから、門も静的でなければならない。実行時を見る門にすると、正当な運用（決定 9 の但し書き）を
  赤にするか、赤を避けるために抜け道を作るかの二択になる。
- **決定 8 の分割**: 存在秘匿の破れは**送出が失敗したときの挙動**であり、本 PR が作ったのは
  **送出を成功させる台**である。同じ PR で両方をやると、**どちらの実測がどちらを支えているのかが
  読めなくなる**（IADR-0332 決定 5 と同じ理由）。

## 結果

- **良い影響**
  - **ADR-0045 決定 9 が既定で成立する。** 開発環境からメールは 1 通も外へ出ず、
    それでいて**送出は成立する**（これまでは「出ない」と「成立しない」が同じことだった）。
  - **T-10 / T-16 が「手動（実環境）」から自動になった。** T-17（送出の成立）/ T-18（dev 既定の宛先）/
    T-19（変異が必ず落ちること）を新設した。
  - **runbook の誤診を 1 つ潰した**（下記）。
- **悪い影響 / トレードオフ**
  - **開発環境の Pod が 1 つ増える**（requests 25m / 64Mi）。決定 9 が明示的に求めた構成要素である
    （計画 ADR §結果 も「構成要素が 1 つ増える」と織り込んでいる）。
  - **捕捉用 MTA の UI は認証を持たない。** エッジへ出さないことで閉じたが、port-forward を開けている間は
    同じ端末から誰でも読める。dev 専用の割り切りである。
  - **`realm.json` に dev 既定の `smtpServer` が入った。** 秘匿値は 0 個だが、
    「realm.json に SMTP 設定は書かない」という**言い方**は今後使えない（正確には
    「**実環境の値**は書かない」である）。runbook を言い直した。
- **測っていて、直していないこと（重要）**
  - 🔴 **SC-15 の存在秘匿は、送出経路が死んでいるときにまだ破れている。** 本 PR の作業中に
    **陽性対照として意図的に再現した**（送出先を届かない宛先へ向けると、実在する利用者名だけ 500 に戻る）。
    決定 8 のとおり **#1143** の射程である。
  - 🔴 **`kcadm.sh get realms/<realm> --fields smtpServer` は、設定済みの realm に対しても
    `"smtpServer" : { }` を返す**（2026-09-02 実測。**設定済みであることを全体取得で確認したうえでの
    陽性対照つき**）。`--fields` の絞り込みが入れ子のマップを描かない。
    **この誤診は runbook §確認 に手順として書かれており、#1143 の起票時の測定 2 もこの形で採られている。**
    runbook を直した（`--fields` を使わず全体を取って `grep` する）。**機械検査は置いていない**
    （kcadm の出力仕様であり、こちらのコードではないため。同型がもう一度起きたら考える —— 1 回目の記録）。
  - **`keycloak.localhost` は Windows の `getaddrinfo` では解決できない**（`ENOTFOUND`。curl は解決するので
    気付きにくい）。RFC 6761 §6.3 は `.localhost` で終わる名前をループバックへ解決することを求めているが、
    Windows はサブドメインでこれを守らない。`check-password-reset-mail.js` は**RFC の要求どおりに落とす**
    フォールバックを持つ（他の名前は OS の解決に委ねる）。
- **フォローアップ**
  1. **捕捉用 MTA の UI をエッジへ出すかは未決**（決定 4）。出すなら SSO か閉域の統制が要る。
  2. **docker-compose 経路には捕捉用 MTA が無い**（決定 9）。compose で runbook を実行すると
     その時点から外部へ実送信される。runbook に警告を書いたが、**構造では止めていない**。
  3. **NotificationService（FR-22）の実 SMTP トランスポート**が入るとき、dev の送出先は
     そのまま捕捉用 MTA を使える（#600）。
  4. **T-11 / T-12 / T-14 / T-15 は依然として手動**である（30 分の待機・全セッション失効・
     一時パスワード発行・新パスワード設定画面の表示）。捕捉用 MTA では自動化できない。
