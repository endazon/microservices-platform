# IADR-0268: ドリフトの「検証不能」を原因で分け、突合の基準が空のまま起動しない

- 状態: Accepted
- 日付: 2026-08-23
- 起票: #444（FR-14 / FR-15 の再実装）

## コンテキストと課題

FR-15 は「宣言（Git）と実行時の実効構成の不一致を検出・警告できる」ことを求め、IADR-0029 が
判定粒度を 5 分類・2 値深刻度で確定した。実装は完成しているが、**検出が静かに効かなくなる経路が 2 つ**残っていた。

1. **`Unverifiable` が 2 つの異なる原因を 1 つの深刻度で表していた。**
   `DriftDetector` は宣言の段の担当サービスが到達できないとき `Unverifiable` / `Info` へ縮退する
   （誤検知抑制。IADR-0029）。ところが **`Introspection:Services` にその service が最初から登録されていない
   場合も同じ経路へ落ちる。** 前者は再起動やロールアウトで解消する一過性の状態であり、後者は
   **解消することが無い構成の誤り**である。両方が `Info` で出るため、「宣言はあるのに突合だけが永久に
   行われない段」が一過性の雑音に紛れる。宣言が在ることと、宣言が検証されていることは別である。

2. **突合の基準そのものが空でも起動できた。**
   `AddPlatformPipelineConfig` は `Pipeline:ConfigPath` が指すファイルが無ければ黙って何もせずに返る
   （段ホストがローカルで既定配線へ縮退できるようにするための仕様）。構成情報 API 側でこれが起きると
   **宣言 0 件が突合の基準になり、実効の購読すべてが `UndeclaredSubscription` として偽陽性で並ぶ** ——
   #146 / #118 監査で実際に起きた回帰である。当時の是正は compose / Helm のマウント配線を静的に検査する
   ものであり、**読む側（起動時）には防壁が無かった**。

## 決定

### 決定 1: `Unverifiable` を原因で 2 つの深刻度へ分ける

宣言で有効な段の担当サービスが、

- **自己申告の収集対象に登録されていない**（`ReachableServices ∪ UnreachableServices` のいずれにも無い）
  → `Unverifiable` / **`Warning`**
- **登録済みだが応答しない** → `Unverifiable` / `Info`（従来どおり。誤検知抑制を壊さない）

**種別・深刻度の値域は変えない。** SC-11 が確定した「種別 5 分類・深刻度 2 値・対象は常に段名」に閉じ、
変えるのは同じ値域の中での**割り当て**だけである。したがって契約（`DriftFindingDto`）・OpenAPI・
フロントの写像（`driftView.ts` の 5 値 / 2 値）に追随は要らない。

**宣言で無効な段には適用しない。** 無効な段は検証の必要が無く、未設定の警告を広げると恒常的な雑音になる。

### 決定 2: 構成情報 API は、宣言を要求しておきながら受け取れていないなら起動しない

`AddPlatformConfigInspection` は、`Pipeline:ConfigPath` が設定されているのに束縛結果の段が 0 件なら
`InvalidOperationException` で起動を止める。ConfigPath 未設定（ローカル・単体試験）は従来どおり素通りする
——「宣言なし」は正当な構成だが、「宣言を指定したのに読めていない」は構成の誤りである。

**適用先は構成情報 API の合成経路だけ**であり、**段ホストが通る `AddPlatformPipelineConfig` の振る舞いは
1 バイトも変えない**（全サービスが依存する共有経路であり、既定配線への縮退はローカル実行の前提である）。
`AddPlatformConfigInspection` の呼び出し元は BFF の 1 箇所だけであることを実測して確認した。

## 理由

- 決定 1 は「検出できていない」ことを検出可能にする。恒久的に突合されない段は、**ドリフトそのものより
  検出の欠落として重い**（気づく手段が無くなる）。深刻度で分けるのは、値域を広げずに区別できる唯一の軸である。
- 決定 2 は既に一度起きた回帰（#146）の**再発の形を変えた版**を塞ぐ。当時の是正はマウント配線の静的検査
  であり、「マウントはされているが中身が空・形式違い」は素通りする。読む側に防壁を置けば形を問わず止まる。
- いずれも新しい検査器・新しい値域・新しい抽象を導入しない。

## 結果

- 良い影響: 収集対象の設定漏れが運用アラート（`IDriftAlertSink`）へ Warning として上がる。
  宣言が届いていない構成情報 API は起動段階で落ち、偽陽性のドリフト報告を運用へ出さない。
- 悪い影響 / トレードオフ: 収集対象を意図的に絞った環境（一部サービスだけを立てる検証環境など）では
  Warning が出る。宣言側で当該段を `enabled:false` にするか、収集対象へ登録することで解消する。
  また、宣言のマウントを失敗させた BFF は起動しなくなる（従来は起動して誤報していた）。
- **積み残し**: 画面（SC-11）の `Unverifiable` の表示文言は「担当サービスへ到達できない」に固定されており、
  未設定の場合にやや不正確である。深刻度と `Detail` で区別は付くが、文言の是正は別 issue とする
  （フロントは #444 の担当領域外）。
- **積み残し**: ポート実装の自己申告（`IntrospectionBuilder.AddPort`）が**手書きのリテラル**であり、
  構成でポート実装を差し替えても自己申告は追随しない。実効構成の「ポート選択」だけが実態とずれ得る。
  呼び出し元が担当領域外のサービスにあるため本 issue では是正せず、記録に留める。
