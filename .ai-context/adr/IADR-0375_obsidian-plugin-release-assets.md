# IADR-0375: プラグインの配布 —— タグ運用・版番号・資産の形・起動条件

- 状態: Proposed
- 日付: 2026-09-05
- 決定者: claude（実装判断）／起点 issue #1213（#1098 / #1153 / #1154 / #1176 の残射程）

## 起点・関連

- 関連する計画書 ID: FR-20（前提 FR-19）/ UC-11 / SC-20 / `ADR-0037` 決定 1（転送方式 ＝ 自作
  Obsidian プラグインの**社内配布**）/ `ADR-0021`（エッジ）/ 08_data-egress-policy（成果物に
  外部 CDN・Web フォント・analytics を含めない）
- 関連する実装仕様書: `.ai-context/specs/20260905_issue-1213_obsidian-plugin-release-assets.md`
- 前提 IADR（覆さない）: `IADR-0338`（決定 3 が配布のリリース資産化を**フォローアップ 3** へ切った。
  本 IADR がそれを閉じる）/ `IADR-0348`（エッジ経路）/ `IADR-0352`・`IADR-0360`（プラグインの機能）

## コンテキストと課題

プラグインは CI で build され egress 走査も通っているのに、**利用者へ渡す経路が 1 つも無い**。
手順書は `dist/` を手でコピーする前提で、導入にリポジトリのクローンと pnpm のビルドを要求していた。

実測（2026-09-05・陽性対照つき）:

| 測ったこと | 結果 |
| --- | --- |
| `gh release list` | **0 件** |
| `git tag` | **0 件** |
| 資産を出すワークフロー | **無い**（陽性対照: `grep -ril "release" .github/workflows/` は 4 件を返す＝走査は効いている） |

決めるべき論点は 4 つある —— ①タグの形と版番号の対応 ②資産の形 ③版の食い違いをどこで止めるか
④起動条件（既存の必須チェックを増やさないこと）。

## 検討した選択肢と決定

### 決定 1: タグは **`obsidian-plugin-v<version>`**。裸の `v<version>` は使わない

| 案 | 評価 |
| --- | --- |
| A. 裸の `v0.2.0`（Obsidian の慣習） | 🔴 **不採用**。このリポジトリはモノレポで、`v*` は既に `changelog.yml` が**リポジトリ全体の**リリースノート生成に使っている。プラグインの版でこの名前空間を奪うと、リポジトリ全体の版とプラグインの版が同じ数直線に乗る（サービスイメージや SPA を配るときに衝突する） |
| **B. 前置つき `obsidian-plugin-v0.2.0`（採用）** | 成果物ごとに名前空間が分かれる。`v*` に一致しないので `changelog.yml` と互いに起動しない（実測で確かめ、`scripts.repo.test.js` が両者の起動条件を突合して固定する） |
| C. 日付タグ（`obsidian-plugin-20260905`） | 利用者に見える版（`manifest.json` の `version`）と対応が取れない。「入れ替えたのに版が変わらない」を判別できなくなる |

- **公開レジストリ（Obsidian community plugins）に登録するなら、この形は要件と食い違う**
  （公開登録は裸の版タグと `versions.json` を要求する）。`ADR-0037` 決定 1 は**社内配布**であり、
  公開登録は計画に無いので**射程外**とした。やるならタグの形の改定を伴う別 issue になる。

### 決定 2: 版の正は **`manifest.json` の `version`**。`package.json` とタグは**それに揃える**

- **Obsidian が読むのは `manifest.json` だけ**である。利用者の「コミュニティプラグイン」画面に出る版も、
  プラグインの更新判定も、この 1 つで決まる。
- `package.json` の `version` は pnpm workspace メンバとしての版で、誰も参照しないが**在る**。
  片方だけ動かせる形を残すと、いつか動く。
- タグは「どのコミットを配ったか」の記録である。**版を上げてからタグを打つ**（タグで版を上げない）。

### 決定 3: 食い違いは **1 つの検査器**（`scripts/check-plugin-release-version.js`）で、**2 箇所から**止める

| 掛ける場所 | 何を見るか | なぜそこか |
| --- | --- | --- |
| `frontend.yml` の `build` ジョブ（プラグインのビルドの**直前**） | `package.json` ⇔ `manifest.json` | **PR で毎回**見る。タグはこの文脈に無いので `--tag` は渡さない |
| リリースワークフロー（資産を作る**前**） | ＋ タグ ⇔ `manifest.json` | 揃っていない資産を**作らせない**。作ってから気付いても、ずれは残る |

- 🔴 **なぜ機械で止めるか**: 版の食い違いは**ビルドもテストも通る**。タグだけ上げれば利用者の画面で
  版が変わらず「入れ替えたのに古いまま」に見え、`manifest.json` だけ上げればどのコミットの成果物かが
  タグから辿れない。どちらも**静かに壊れる**。
- 「検査器の追加は同型の事故が 2 回起きたら」という規律とは**衝突しない**と判断した ——
  これは新しい**規約**の検査ではなく、**本 PR が新設した配布経路それ自体の前提条件**である
  （タグと版の対応が無ければ、この配布は定義できない）。既存の必須チェックへは 1 件も足さない。
- 判定は純関数（`evaluate`）に閉じ、`scripts.repo.test.js` が**変異試験**（版の突合を外すと
  食い違いが素通りすることの確認）まで含めて 12 件で固定する。

### 決定 4: 資産は **`main.js` と `manifest.json` の生ファイル 2 つ**。zip にしない・`cli.mjs` を配らない

| 案 | 評価 |
| --- | --- |
| **A. 生ファイル 2 つ（採用）** | Obsidian の慣習そのもの（プラグインフォルダに置くファイルがそのまま資産になる）。**追加の依存が 1 つも要らない** —— zip を作るには外部コマンド（`zip`）か自前の ZIP 書き出しが要り、前者は環境依存、後者は配布のために圧縮器を書くことになる |
| B. zip 1 つ | 導入が「展開して置く」の 1 手になるが、置くファイルは**もともと 2 つしかない**。得られる簡便さに対して、作る側の複雑さと環境依存が釣り合わない |
| C. 生ファイル ＋ zip の両方 | 資産が 3 つになり、「どれを落とすのか」が増える。同じものを 2 通りで配る |

- `styles.css` は**存在しない**（`IADR-0338` 決定 3。独自の見た目を持たない）。無い物を資産に書かない。
- `cli.mjs` は**実測・検証用のハーネスであって配布物ではない**（同決定 6）。ビルドすると `dist/` に
  できるが、資産には含めない —— 利用者の Vault に置く物ではなく、置けば「使ってよい」と読まれる。
- **資産は egress 走査を通ったものだけを出す**。`frontend.yml` と同じ検査を**配る直前にも**置いた
  （配るものを配る前に見る）。走査対象が無ければ `--require` が落とすので、「走査 0 件で緑」にならない。

### 決定 5: 起動は **タグ push と手動だけ**。`pull_request` を持たない

- 必須チェック（develop の 8 件）は `docs/ai-workflow.md` の表が正で、**そこへ 1 件も足さない**。
  `pull_request` を持たないワークフローは PR で 1 度も起動しないため、必須指定の候補にすら上がらない
  （逆に、起動しないものを必須にすると恒久 pending になる —— 同文書が `codeql.yml` で実測している）。
- 🔴 **代償**: PR で走らないので「壊れても気付けない」。よって**中身の不変条件は
  `scripts.repo.test.js`（必須チェック `scripts-tests`）が静的に固定する** —— `pull_request` を
  持たないこと・タグ前置が検査器の定数と同じこと・資産が 2 つであること・版の突合 → ビルド →
  egress 走査 → 公開の順であること。
- `workflow_dispatch` を持たせたのは、**タグを消して打ち直すより既存タグに対して回し直す方が安全**
  だからである（タグの打ち直しは、既に落とした利用者の手元と齟齬を生む）。
- submodule は取らない。プラグインは可変ユニットを 1 行も参照しないので、その取得失敗が配布を止めない。

## 理由

- **決定 1・2** は「利用者に見える版はどれか」を 1 つに決めることに尽きる。Obsidian が見るのは
  `manifest.json` だけなので、そこを正にしないと他のどれを揃えても利用者側の症状は直らない。
- **決定 3** は `IADR-0183`（偽の緑を作らない）と同じ形 —— 静かに壊れる経路には、機械の門を置く。
- **決定 4** は「配るために新しい道具を持ち込まない」。置くファイルが 2 つしかないのに圧縮器を足すのは、
  配布の複雑さを利用者側ではなく**こちら側**に増やすだけである。
- **決定 5** は必須チェックの表を動かさないため。表を動かすのは運用の形を変える行為で、
  `docs/ai-workflow.md` は利用者の同意を要件にしている。

## 結果

- 良い影響:
  - 利用者が**リポジトリを取得せずに**プラグインを入れられる（`ADR-0037` 決定 1 の「社内配布」が
    手順として成立した）。`IADR-0338` フォローアップ 3 を閉じる
  - 版の食い違いという**静かに壊れる**経路に門ができた（PR とリリースの 2 箇所）
  - 配る成果物が、配る直前に egress 走査を通る
- 悪い影響・トレードオフ:
  - 🔴 **リリースワークフローは PR で 1 度も走らない。** 実際に回るのは最初のタグを打つときで、
    それまでは静的な不変条件（`scripts-tests`）でしか確かめられていない。**本 PR ではタグを打たない**
    （タグ運用の開始は配布の意思決定であり、実装 PR が勝手に始めることではない）
  - 版を**上げ忘れた**ことは検出しない（3 つ揃って古いのは正しい状態である）。配布のたびに上げる
    規律は人が持つ
  - タグの形が公開レジストリの要件と食い違う（決定 1）。公開登録するなら改定が要る
  - 検査器が 1 本増えた（49 → 50。母集合のラチェットが設計どおり発火した）
- フォローアップ:
  1. **Obsidian 実機での目視**（競合の 3 択ダイアログ・Vault のイベント配線・設定タブ）。
     実機が検証環境にも CI にも無く、`dist/cli.mjs` の実 HTTP は**画面の目視を代替しない**。
     **本 PR では実施していない**（別 issue）
  2. 署名と公開レジストリへの登録（やるなら決定 1 の改定を伴う）
  3. `IADR-0338` フォローアップ 4（`coverage.include` への算入と床の再計測）・5（en ロケール）は
     そのまま残る
