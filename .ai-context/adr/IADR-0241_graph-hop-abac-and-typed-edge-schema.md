# IADR-0241: グラフ探索のホップごと ABAC を型で強制し、辺の型はサロゲートキーの行データで持つ

> **番号は暫定である。** マージ直前に develop の最大＋1 へ付け直し、`.ai-context/adr/README.md` の索引も更新する（`check-adr-numbering.js` は昇順・欠番なしを fail で見る）。

- 状態: Proposed
- 日付: 2026-08-22
- 決定者: claude（#908 / 親 #450）

## 起点・関連

- 関連する計画書 ID: FR-17 / UC-10 / ADR-0033（決定 1〜10）/ ADR-0034（決定 1〜9）/ ADR-0004 / ADR-0036
- 関連する実装仕様書: `.ai-context/specs/20260822_issue-908_graphservice-foundation.md`
- 前例として参照した既存実装: `AbacPageFilter` / `WikiAccessResolver`（WikiService）、`TagDictionaryEndpoints` / `Tag`（DocumentService。[[IADR-0152]] / [[IADR-0153]]）

## コンテキストと課題

ADR-0034 決定 1 は「**ホップごとに ABAC 判定を行う。終端でまとめてフィルタしない**」を定め、決定 2 は「見えない辺は件数・匿名ノードを含め完全に隠す」を定めている。

ところが本リポジトリの認可判定 API は `POST /authz/scope` **1 本のみ**であり、返るのは**フィルタ集合**（`AccessScopeResponse`）であって資源ごとの可否ではない。実測:

- `AccessScopeRequest(string UserId, Dictionary<string,string> UserAttributes)` に **Action フィールドが無い**（`Platform.Shared.Contracts/Dtos/AccessScopeDto.cs`）。エンドポイント側で `PolicyAction.Read` がハードコードされている
- **バッチ判定 API は存在しない。キャッシュも存在しない**
- リポジトリ共通の作法は「スコープを 1 回解決 → 資源ごとにローカル述語」であり、`AbacPageFilter` は明示的に**取得後のメモリ内フィルタ**である

**これを素朴に使うと、まさに決定 1 が禁じる形になる。** 決めるべきは 2 つ:

1. フィルタ集合方式で決定 1 を満たせるのか。満たせるとして、「探索してから濾す」実装が**書けてしまう**ことをどう防ぐか
2. 辺の型を、後から種類が増えてもマイグレーションを要さない形でどう持つか（ADR-0033 決定 3 は「型の値集合は SC-09 で管理しコード定義にしない」、決定 9 は「参照があれば削除拒否・改名は許し既存辺は追随」を要求する）

## 検討した選択肢

### 論点 A: ホップごと ABAC の強制方法

| 案 | 機構 | 強さ | 費用 |
| --- | --- | --- | --- |
| **A-1 コンパイラ型ゲート（採用）** | フロンティアの要素型を `AuthorizedNode`（private ctor・構築経路は述語のみ）にし、接続辺ロードはそれしか受け取らない。加えて応答 DTO は `Seal(UnfilteredSubgraph, scope)` からしか作れない | **ビルド時・回避不能**（リフレクションを除く） | ほぼゼロ（型 2 つ＋ファクトリ 1 つ） |
| A-2 アーキテクチャテストのみ | ハンドラ戻り値型・型の露出をリフレクションで検査 | テスト時。実装の書き方は縛れない | 小 |
| A-3 検査スクリプト新設 | `check-unit-dependencies.js` 同型の Node 検査で `Endpoints` が探索型を直接 using しないことを文字列検査 | CI 時・文字列ベースで粗い | 中。**運用規約に反する**（検査器の追加は同型事故 2 回が条件で、現在 0 回） |
| A-4 規約とコメントのみ | 仕様書に書く | 無し | ゼロ |

**出力ゲートだけでは不十分**である点が判断の分かれ目になった。`Seal` 経由でしか応答を作れないという制約は「未フィルタが外に出ない」ことは保証するが、「濾したのが**ホップごと**である」ことは保証しない —— 全ホップを権限無視で展開してから `Seal` に渡す実装が書けてしまい、それが**まさに禁じられた形**である。したがって「展開の入口」を塞ぐ型が要る。

### 論点 B: 辺の型の持ち方

| 案 | 新型追加 | 改名 | 削除ガード |
| --- | --- | --- | --- |
| **B-1 サロゲートキーの行データ（採用）** | `edge_types` へ INSERT のみ＝**マイグレーション不要** | `Name` 列の 1 行 UPDATE。既存辺は 0 行触らず追随 | `ON DELETE RESTRICT` ＋ サービス層 409 |
| B-2 C# enum / DB enum 型 | **型追加のたびにマイグレーション**（ADR-0033 決定 3 違反。SC-09 での管理も不可） | 不可 | 表現できない |
| B-3 `edges` に型名を直接持つ（自然キー） | INSERT 不要（自由文字列） | **該当辺の質量 UPDATE**。書きかけ失敗で混在状態 | 参照数の集計は可能だが FK が張れない |
| B-4 型ごとにテーブル/列を分ける | 型追加のたびにスキーマ変更 | 不可 | — |

### 論点 C: デノーマライズ属性の置き場所

ノード表のみ（採用）／辺にも複製／両方。

## 決定

### 決定 1: フィルタ集合方式の prune-before-expand は ADR-0034 決定 1 に忠実である

「スコープを 1 回解決し、フロンティア拡張のたびに述語を評価し、**拡張前に刈る**」を決定 1 の忠実な実装として採る。

判別性質は「**非許可ノードが橋になれるか**」である。prune-before-expand では非許可ノード X はフロンティアに一度も入らないため X の接続辺は展開されず、`A→X→B` で B が浮上する経路が存在しない。したがって資源ごとのオラクルを各ホップで呼ぶ実装と**観測上区別できない**。

「ホップごと判定」とは *HTTP 呼び出しの回数*の話ではなく、***探索のどの時点で判定を適用するか***の話である。

### 決定 2: 2 段の型ゲートで「探索してから濾す」を表現不能にする（論点 A → A-1）

- **ゲート 1（展開の入口）**: `AuthorizedNode` は private ctor を持ち、構築経路は `AbacNodeFilter.Authorize(node, scope)` ただ 1 つ。接続辺のロードは `IReadOnlyList<AuthorizedNode>` しか受け取らない → **非許可ノードからの展開が型として書けない**
- **ゲート 2（出力）**: 探索・永続化層は `internal` な `UnfilteredSubgraph` しか返さず、応答 DTO は `AuthorizedGraphView.Seal(UnfilteredSubgraph, AccessScopeResponse)` からしか構築できない → **未フィルタ結果はコンパイルが通らない**

**検査スクリプトは作らない**（A-3 を棄却）。運用規約が「検査器の追加は同型の事故が 2 回起きたら」を条件としており現在 0 回であること、および型ゲートの方が回避不能で安いことによる。代わりにアーキテクチャテストで構築経路の単一性を固定する（A-2 を補助として併用）。

### 決定 3: 述語は既存 `AbacPageFilter` と意味論一致とし、一致をテストで固定する

deny-by-default ／ フィルタ間 AND・値集合内 OR ／ **属性キー欠落は不一致（fail-closed）** ／ `AllowedFilters` が空かつ `Granted=true` は全許可 ／ 比較は `OrdinalIgnoreCase`。

### 決定 4: 上限は述語通過後にのみ計数する

ノード 200 / 辺 500 の計数は述語を通過した品目に対してのみ行う。これにより「上限や件数が権限外の存在を漏らす」（ADR-0034 決定 4 の禁止）が**構造的に不可能**になる。打ち切り順序は決定的（`created_at`, `id`）とする —— 非決定だとテストが flake し、利用者から見て「見えたり見えなかったり」する。

### 決定 5: 存在秘匿は 404 に一本化する

非許可・属性レコード欠落・文書不存在を**すべて同一の 404** にする。403 と 404 を打ち分けると存在が漏れる。ADR-0034 は「リンク切れと権限不足を区別できないこと」を受け入れ済みの副作用として明記しており、その線に従う。

### 決定 6: 辺は両端点が許可されたときのみ可視とし、辺自身には機密属性を持たせない（論点 C の一部）

辺の機微性は「両端文書の存在と関係を明かすこと」に由来し、端点判定の連言で完全に覆われる。辺に独自の ACL 軸を足すのは計画に無い抽象化であり、CLAUDE.md 禁止事項「計画外の過剰な抽象化」に当たる。出所（provenance）は認可軸ではなくメタデータである。

### 決定 7: 辺の型はサロゲートキーの行データで持つ（論点 B → B-1）

`edge_types(id uuid PK, name, layer, is_symmetric, is_seed, ...)` とし、`edges.edge_type_id` が FK で参照する（`ON DELETE RESTRICT`）。

- **改名追随はサロゲートキーの帰結である**。`Name` は可変列にすぎないため改名は 1 行 UPDATE で、既存辺は 0 行触らずに追随する
- **削除ガードは 2 層**。DB 層の `ON DELETE RESTRICT`（最後の防壁）＋ サービス層の事前カウント 409（使用件数を添える）。RESTRICT 例外を素の 500 で漏らさない
- **新しい型の追加は INSERT のみ＝マイグレーション不要**

**これは既存のタグ辞書実装と同型である**（`DocumentService` の `Tag` / `TagDictionaryEndpoints`。[[IADR-0152]] / [[IADR-0153]]、#634 / #635）。ADR-0033 決定 9 が「同じ規則をタグ辞書にも適用する」と言っている当のものが既に実装されており、車輪を再発明しない。

### 決定 8: 辺の型辞書は GraphService が所有する

[[IADR-0152]] 決定 1 がタグ辞書を DocumentService に置いた理由は「使用件数が文書の局所クエリになるため。サービスを跨ぐと削除拒否の判定のたびに同期呼び出しが要り、数え落としが『消してはいけないタグを消せる』事故になる」である。**同じ論法で辺の使用件数は GraphService の局所クエリである**から、辺の型辞書は GraphService が所有する。SC-09 の UI が 2 サービスの 2 辞書を編集する形になるが、これは齟齬ではなく一貫である。

### 決定 9: 辺は常に 1 行とし、対称型は正規化する

方向型（`cites` / `supersedes` / `derived-from` / `embeds` ほか）は行の source→target が意味方向そのもの。対称型（`related`）は書き込み時に `(min(uuid), max(uuid))` へ正規化して重複を防ぎ、読み取り時に `is_symmetric` を見て無向として提示する。

**バックリンクは行を増やさず** `ix_edges_target` の逆引きで実現する。探索は最初から双方向（source がフロンティア OR target がフロンティア）を引く。

### 決定 10: デノーマライズ属性はノード表のみに置く（論点 C）

理由は探索アルゴリズムの形状にある。述語評価の対象は常に「フロンティアの隣接**ノード**」であり、ノード一括ロード時に属性が同じ行に載っていれば追加 I/O ゼロで判定できる。辺へ複製すると (a) 属性変更 1 件が接続辺全行の書き換えに増幅し（ADR-0033 決定 2 の「即座に更新」が高価になる）、(b) ノード側と食い違う瞬間が生まれて鮮度契約が二重になる。辺の可視性は端点判定の連言で導出されるため、辺側に判定材料は要らない。

### 決定 11: ストアは当面 PostgreSQL 隣接リストとし、`IGraphStore` 越しに交換可能に保つ

ADR-0033 の未決事項「ストア製品」は実測待ちのままである。待つとすべてがブロックされるため、プラットフォーム標準（EF Core + Npgsql + 起動時 `MigrateAsync` + DB-per-service）にそのまま乗る形で進める。hops≤3・上限 200/500 の下では BFS はホップ毎 2 クエリ・計 6 クエリ程度であり、専用グラフ DB の優位が出る領域（可変長パス・大深度）に到達しない。

**再訪トリガ**: ①実データ規模での探索 p95 が対話的利用に耐えない実測が出たとき、②計画側で hops>3 や全グラフ解析（中心性等）の要求が確定したとき。そのときの実測値を planning へ環流する。

### 決定 12: デノーマライズ属性の鮮度契約

1. 判定は常に「最後に受信・適用した属性」に対して行う。同期照会による補正はしない
2. **失敗方向は非対称である。** 属性の緩和の遅延は「まだ見えない」＝安全側。**厳格化の遅延は「まだ見える」＝ stale-allow の漏えい窓**。これは WikiService の ABAC 同期が既に持つのと同型の受容であり、GraphService が新たに悪化させるものではない。**この一文を仕様書に明記し、黙って出荷しない**
3. **属性レコードが無いノードは不可視**（fail-closed）
4. upsert はイベントの更新時刻をガードに使い、保持中より古いイベントは適用しない。冪等

## 理由

- 決定 2 が本 IADR の核心である。「規約とコメント」（A-4）や「テストのみ」（A-2）では、**将来の実装者が善意で「まず全部集めてから濾す」と書ける**。それは動作としては正しく見え、レビューでも通りやすく、しかし ADR-0034 決定 1 が名指しで禁じた情報漏れの形である。**型で書けなくするのが唯一、意図に依存しない防ぎ方**である
- 決定 7 は「後から辺の種類が増えたときの migration 地獄」を避けるという要求に直接答える。サロゲートキーにするだけで、改名追随（決定 9 の要求）と削除ガード（同）と型追加のマイグレーション不要が**同時に**得られる
- 決定 8 と決定 7 は既存実装の前例に乗っており、新しい判断をほとんど加えていない

## 結果

- 良い影響:
  - 「探索してから濾す」形がコンパイルできないため、ホップごと判定が**実装者の注意力に依存しない**
  - 辺の型の追加・改名がマイグレーションを伴わず、SC-09 からの実行時管理と噛み合う
  - 既存のタグ辞書実装と同型のため、レビュー時に読み替えの負担が小さい
- 悪い影響・トレードオフ:
  - `AuthorizedNode` のラップにより、探索コード内で `.Node` を経由する記述が増える（可読性の軽微な低下と引き換えに、回避不能性を得る）
  - 型辞書がサロゲートキーであるため、表示には JOIN（または型辞書の 1 回ロード）が要り、書き込み時に名前 → id の解決が要る
  - `edges` の anchor 2 列は当面デッド列である（ADR-0033 決定 5 が予約を要求しているため受容する）
  - 述語をメモリ内評価するため、フロンティアが大きい場合に取得量が増える。SQL（jsonb）へ押し込む最適化は意味論一致の検証が難しくなるため初期実装では採らない
- フォローアップ:
  - 実データ規模での探索 p95 を計測し、決定 11 の再訪トリガに照らす（#909 着地後）
  - **ADR-0034 決定 6・8・9（個人資料の境界）は現時点で強制できない。** `owner` が実データ 0% 充足、3 分岐 OR が `AccessScopeResponse` に表現構造を持たない、`/authz/scope` が Read 固定、の 3 点による（#516 系）。**未強制であることを固定するテストを置き**、ギャップ解消時に赤くなって気付ける形にする
  - `/authz/scope` への Action パラメータ追加の要否は、write 系の規則（辺の削除を作成者に限る等）が必要になった時点で planning へ環流する
