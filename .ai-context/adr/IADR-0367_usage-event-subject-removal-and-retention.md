# IADR-0367: 利用イベントの主体と保持期間の実装形

- 状態: Accepted
- 日付: 2026-09-04
- 決定者: 実装（#1198）

## 起点・関連

- 関連する計画書 ID: FR-10 / UC-05 / SC-10 / ADR-0072（決定 1・3）
- 関連する実装仕様書: `.ai-context/specs/20260904_issue-1198_usage-event-subject-and-retention.md`
- 先行: `IADR-0343`（利用イベントの発火側。**決定 6 の 2 が本件を受容せず環流した**。その受け皿が本作業）／
  `IADR-0357`（検索傾向のしきい値。**構成の fail-open と「報告する値は倒した後の値」の作法**）／
  `IADR-0353`（陳腐化文書数のしきい値運搬。同じ作法の先例）

## コンテキストと課題

`ADR-0072`（Accepted・2026-09-03）が確定させたのは「**読んでいないものを持たない**」と
「**画面から読めない行を残さない**」の 2 点である。計画が決めたのは**何をするか**までであり、
実装には次の 3 つが残った。

| # | 残った問い | なぜ計画では決まらないか |
| --- | --- | --- |
| A | 「主体解決を維持する」を**どう書くか** | 列へ書かないなら、解決した値の行き先が無い |
| B | 保持日数を**構成キーにするか** | 計画は「90 日」とだけ定め、可変性を述べていない |
| C | 削除を**どの API で行うか** | `ExecuteDelete` はテストの実行環境で動かない |

## 決定

### 決定 1 — 主体解決の「維持」は認証の維持であり、未使用の変数を残すことではない

受け口 `POST /dashboard/events` の **`RequireAuthorization()` を維持する**。認証パイプライン
（`AddPlatformAuth`）が JWT から主体を解決し、**解決できなければ 401 になる**という筋は変えない。
**変えたのは終端が `HttpContext` を受け取らなくなったこと**である。

🔴 **`var userId = http.User.Identity?.Name;` を「維持の証」として残さない。** 使われない値は
コンパイラ警告になり、読み手には「まだ使う気がある」と読める。**維持したのは統制であって
コード片ではない。** 統制が残っていることは**未認証で 401 / 認証済みの一般利用者で 201** の
2 本（T-71 / T-72）で機械が押さえる —— `RequireAuthorization()` を消せば前者が落ち、
管理者限定にすれば後者が落ちる。

### 決定 2 — 保持日数は構成キーを持たない。集計の上限と同じ 1 つの定数である

`ADR-0072` §残るもの 末尾は「**集計の上限を変えるときは保持期間も同時に見直す（片方だけ動かすと、
照会できるのに行が無い期間が生じる）**」と定めている。

🔴 **保持日数を独立の構成キーにすると、その事故を運用時に起こせる形をわざわざ作ることになる。**
`UsageRetention:RetentionDays=30` と書けてしまう構成は、**画面が 90 日を選べるのに 31 日目以降が
空になる**配備を 1 行で作れる。「同時に見直す」という規律を、機械が破れる形にして人へ預けるのは
本末転倒である。

したがって:

```csharp
public const int RetentionDays = DashboardEndpoints.MaxDays;   // 定数を 2 つ置かない
internal static DateTimeOffset CutoffUtc()
    => DashboardEndpoints.SinceUtc(RetentionDays);             // 式も 1 つしか置かない
```

**同じ定数・同じ式**である。**削除の述語は集計の否定**（集計 `OccurredAt >= 起点` ／
削除 `OccurredAt < 起点`）であり、境界は 1 点しか無い。

**構成で変更できるのは掃除の有無（`UsageRetention:Enabled`）と間隔（`IntervalMinutes`）だけ**である。
不正値（0 以下）は既定へ倒し、**起動時のログに出す値も倒した後の値**にする
（`IADR-0357` 決定 4 / `IADR-0353` 決定 3 と同じ作法。倒したのに構成値を出すと、
ログの周期と実際の周期が食い違う）。`ValidateOnStart` は付けない ——
**掃除の間隔の打ち間違いで、利用イベントの記録と集計まで巻き添えに止める価値は無い。**

> **★ これは本作業の指示（保持日数も構成で変更可）からの意図的な逸脱である。** 指示は
> `IADR-0357` / `IADR-0353` の作法をなぞることを求めていたが、その作法の対象は
> **しきい値のような「運用で調整する値」**であり、保持日数は**別の値と同時にしか動かせない値**である。
> 計画 ADR の §残るもの と衝突するため、計画側を採った。**逸脱の記録として本項を残す。**

### 決定 3 — 削除は `RemoveRange` で、1 周を 500 行で区切る

`ExecuteDeleteAsync` は使わない。**テストは InMemory プロバイダで走り、InMemory は同 API を
実装していない** —— 使うと、保持期間の統制だけが**テストで触れない領域**に落ちる。
同じサービス内の前例（`Features/KnowledgeHealth/Report`）も `RemoveRange` である。

代わりに**読み込みを `BatchSize`（500）で区切る**。初回適用時（90 日より古い行が溜まった DB）に
全件をメモリへ載せると、**保持期間の掃除が原因でサービスが落ちる**。上限に達した周は
**同じ周でそのまま続ける**（次の周期まで放置すると、初回に何日も消え切らない）。

### 決定 4 — 常駐処理は起動直後に 1 周し、1 周の失敗では止まらない

形は `NotificationMaintenanceHostedService`（platform 側の前例）をなぞる ——
`BackgroundService` ＋ `PeriodicTimer` ＋ `IServiceScopeFactory`。

- **初回は起動直後**（`do { } while (WaitForNextTickAsync)`）。1 周期後にすると、
  再起動の多い環境では**一度も回らないまま次の再起動を迎える**。
- **1 周の失敗で常駐処理を止めない。** 止めると保持期間の統制が静かに効かなくなり、
  **画面も応答も何も変わらないまま行だけが溜まる**（気付く手掛かりが無い）。
- **削除した周だけログを出す**（0 件の周は出さない）。毎周の「0 件削除」は運用ログを埋め、
  本当に消えた周が読めなくなる。

### 決定 5 — 移送マイグレーションは列だけを落とす

`20260904100741_DropUsageEventUserId`。`Up` は `DropColumn`、`Down` は `AddColumn`（既定値 `""`）。

🔴 **既存行の値は失われ、復元できない**（`Down` で戻るのは列だけである）。それが決定の目的だが、
「誰が投入したか」を後から辿る手段は無くなる。**行そのものは消えず、件数は前後で変わらない** ——
消えるのは列だけである。`ADR-0072` §残るもの が受け入れ済みのトレードオフとして明記している。

## 検討した選択肢

| 論点 | 案 | 評価 |
| --- | --- | --- |
| A 主体解決 | 未使用のローカル変数を残す | ❌ 警告になり、読み手に誤解を与える。**統制はテストで押さえる方が強い** |
| A 主体解決 | **終端から `HttpContext` を外す（採用）** | `RequireAuthorization()` は残り、401 / 201 の 2 本で固定される |
| B 保持日数 | 構成キーにする（作業指示） | ❌ **集計の上限と別々に動かせる形**は ADR-0072 §残るもの が禁じた事故を作る |
| B 保持日数 | **集計の上限の定数を直接使う（採用）** | 定数も式も 1 つしか無い。片方だけは動かせない |
| B 保持日数 | 集計の上限そのものを構成化し 1 キーで両方動かす | ❌ 射程外（BFF 側にも同じクランプがあり、計画は上限の可変性を求めていない） |
| C 削除 API | `ExecuteDeleteAsync` | ❌ InMemory で動かず、**統制がテストの外へ落ちる** |
| C 削除 API | **`RemoveRange` ＋ 500 行の区切り（採用）** | 同サービス内の前例に一致。初回適用でメモリを飛ばさない |

## 結果

- `DashboardService` に**常駐処理が 1 つ増えた**（このサービスで初めての `BackgroundService`）。
- **BFF の発火側は変更していない**（もともと `(EventType, Query)` の 2 項目しか送っていない。実測）。
- **応答契約は変わらない**（`UsageEventRequest` に利用者の欄は無い。`docs/api/openapi.yaml` の差分 0）。
- **画面の表示は変わらない** —— 消える行は最初から画面に出ていなかった行である。
- 運用仕様書に §データ保持期間（利用イベント）を新設した（**失敗時の見え方**を含む。`ADR-0072` §結果）。

## 残るもの

- 🔴 **`Query`（検索語）は 90 日残る。** `ADR-0071` のしきい値は画面の統制であって保管の統制ではなく、
  **DB へ直接到達できる者にはしきい値未満の語も読める**（`ADR-0072` §残るもの のとおり）。
  本 IADR が縮めたのは**期間**であり、**保管中の可読性ではない**。
- **掃除が回っていることを機械が常時見張ってはいない。** 見えるのはログだけであり、
  **計器（メトリクス）は置いていない** —— 置くなら「最後に削除した時刻」であって件数ではないが、
  現時点で監視の受け皿（Alertmanager）が未配線であり、**出しても誰も見ない**。
  監視配線の作業で併せて判断する。
- **1 周の上限（500 行）は実測に基づく値ではない。** 初回適用時の行数が大きい配備で
  周回数が増えたら見直す（**上限そのものは構成キーにしていない** —— 動かす理由が実測で出るまでは
  定数のままにする）。
- **合成トラフィックの除外（`ADR-0076` 決定 4）は本作業の射程外**である。標識をどこで落とすかは
  同 ADR の追随作業が決める。
