# IADR-0527: ループバックのリダイレクト URI の port 必須を外す（#1859 後段）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-10-09
- 決定者: **利用者（製品の判断）**。裁定 2026-10-09「外す」。外し方（何を残すか・門の形）は claude。

> 🔴 **番号について**: 起草時の `origin/develop`（`24a8bee8`）の最大は IADR-0524 である。0525（PR #1866）と 0526（PR #1865）が未マージで番号を
> 予約しているため、本 IADR は 0527 を採った。両 PR のマージまで `check-adr-numbering.js` の欠番が赤になり得る。

## 起点・関連

- 起点 issue: **#1859** の後段（「ループバックの redirect URI で port を必須にする規則を外すか」）。前段（Keycloak 26.7.4 への更新）は PR #1869・[IADR-0524](./IADR-0524_keycloak-26-upgrade.md)。
- 計画: ADR-0134 決定 1（ループバックは `http://127.0.0.1` / `http://[::1]`。RFC 8252 §7.3）。計画は port の有無を定めていない（port の扱いは実装へ委ねた細目。IADR-0516 の #1844 追記）。計画への環流は要らない。
- 前提: [IADR-0516](./IADR-0516_sc12-keycloak-service-account-provisioning.md) の PR #1854 追記（port 必須の導入。決定 4「緩める条件: 25.0.6 以上へ上げ、門 M9 で横取りの形が 400 になることを確かめてから」）と #1859 追記（証拠の表と推奨）。
  [IADR-0524](./IADR-0524_keycloak-26-upgrade.md) 決定 4（門 M9 の port なしの対）・残余 2。[IADR-0514](./IADR-0514_infra-image-digest-pinning-and-checker.md)（digest 固定）。
- 作業仕様書: [20261009_1859_loopback-port-optional](../specs/20261009_1859_loopback-port-optional.md)（母集合の走査・変異の結果）。

## コンテキストと課題

PR #1854 は、配備の Keycloak 24.0.5 の CVE-2024-8883（port なしで登録したループバックに `http://127.0.0.1:<任意>@evil.example/cb` が一致し、認可コードが外へ渡る）を、
入口の規則「ループバックは port の明示が必須」で塞いだ。代わりに RFC 8252 §7.3 の「port なしで登録し、実行時に空いている任意の port で戻す」を失った。
有人の MCP クライアント（ネイティブアプリ・CLI）は起動のたびに変わる port で待ち受けるのが普通で、固定の port は塞がっていればログインできない（複数の port を登録する回避は上限 10 件で尽きる）。

PR #1869 で認証基盤は 26.7.4 へ上がり、port なしの登録でも横取りの 4 形 × 2 ホストは 400 になった（手元の実測。門 M9 の対が稼働で測る）。24.0.5 では同じ対の 5 段が赤になる。

## 決定

### 決定 1 — 外すのは「ループバックは port の明示が必須」の 1 点だけ

- `RedirectUriRules.Violation`（後段。呼び出し元は登録の検証器 `RegisterMcpClientValidator` だけで、認証基盤の表現の読み戻しはリダイレクト URI を入力どおりかで比べ、この規則を呼ばない）は、綴りで `http://127.0.0.1` / `http://[::1]` に続くのが
  `/`・`?`・末尾なら（port なし）通す。`:` が続くときは従来どおり 1〜5 桁の数字の後が `/`・`?`・末尾で、値が 1〜65535 のときだけ通し、
  外れれば「ループバックのリダイレクト URI '…' の port が不正です（1〜65535 の数字で書くか、port を書かずに登録してください）」で 400。
- **残すもの（変えない）**: `https` 以外の非ループバック・`localhost`・別の綴り（`127.1`・`127.0.0.2`・`127.0.0.1.evil.example`）・ワイルドカード・フラグメント・
  利用者情報（`user@`）・相対・他のスキーム・前後の空白・空・重複・11 件以上。判定の順も変えない。
- 横取りの形（`127.0.0.1:<任意>@evil.example/cb` ほか port なしの登録に当てる 4 形 × 2 ホスト）を `redirectUris` に**登録すること**は、入口の 3 つの判定
  （利用者情報・綴りと解析後の host の突き合わせ・port の形）がそれぞれ止める（変異で確かめた。作業仕様書）。
- 画面の写し（`isAllowedRedirectUri`）も同じ形に揃える。理由の識別子 `redirect-uri-loopback-port-required` は撤去する（出す場面が無い）。
  `:` だけ・`:0` は `redirect-uri-invalid`。入力欄の説明・例は「port を省くと実行時の任意の port で戻る」へ改める。

### 決定 2 — 門 M9 の port なしの対を常設し、SC-12 の実際の登録経路で作ったクライアントへ当てる

- IADR-0524 決定 4 の対（master の管理者で Keycloak に直接作った port なしのクライアント）を、**SC-12 で登録した port なしのクライアント**（201・有人のテンプレートどおり・入口の印）へ当て替える。
  陽性対照（登録どおり・任意の port でログイン画面へ進む）・横取り 4 形 × 2 ホストが 400・path 違いが 400・`localhost` が 400 は変えない。
  入口を迂回して作ると、入口の規則が緩みすぎた・テンプレートが崩れた退行を対が見ないためである。
- 入口の否定形を足す: port の形が不正（`http://127.0.0.1:/cb`）と、利用者情報ですり替える形（`http://127.0.0.1:49152@evil.example/cb`・`http://[::1]:@evil.example/cb`）の登録が 400 で Keycloak に何も作らない。
- 旧い否定形「port なしの登録は 400 で何も作らない」は外す（規則が変わった）。port つきの既存の対（完全一致・横取りの形）は残す。
- 自己試験が、対を SC-12 の登録へ当てていること・Keycloak に直接作っていないこと・横取りの形と陽性対照があることを源の形で固定する。

### 決定 3 — 説明と生成物を同じ PR で改める

`docs/api/openapi.yaml`（登録の口・`RegisterMcpClientRequest.redirectUris` の説明。「Keycloak 24 の CVE で port 必須」を外す）と生成物（orval の `bff.schemas.ts`・`mcp-clients.ts`。`pnpm run codegen`）、
カタログ（Lingui。`pnpm run i18n`）、通信・試験・画面の仕様書、セキュリティ仕様書の「版に依存する統制」の行を改める。

## 統制と現在の実現手段

| 統制 | 現在の実現手段 | 配備までの暫定手段 |
| --- | --- | --- |
| port なしで登録したループバックに、横取りの形（利用者情報で宛先をすり替える 4 形）を一致させない（CVE-2024-8883） | **認証基盤の照合だけ**（26.7.4。index の digest で固定され、`check-image-digests` が黙った差し替えを止める）。入口の port 必須は外した | — |
| 認証基盤の照合の退行を見つける | integration-stack の門 M9（日次）が SC-12 で作った port なしのクライアントへ横取りの 4 形 × 2 ホストを当てる（陽性対照つき）。版を 24 系へ戻すと 5 段が赤になる（IADR-0524 の実測） | — |
| 横取りの形そのものを登録させない | 入口の利用者情報・host の綴り・port の形の判定（後段と画面の写しの両方） | — |

## 結果

- 良い: RFC 8252 §7.3 の使い方（port なしで登録し、実行時の任意の port で戻す）が戻る。ネイティブの MCP クライアントは固定の port を要らない。
- 悪い（受け入れたトレードオフ）: **防御は 2 段から 1 段になる。** 入口の規則は認証基盤の照合の不具合を覆わなくなる。照合が退行しても、門 M9 が赤になるまでの**窓は最長 1 日**残る。
  緩和は「digest の固定（版は黙って下がらない。上げるときは PR と門を通る）」と「門 M9 の日次の実行」である。

## 残余

1. **稼働での初回の確かめ**は本 PR のマージ後の integration-stack（M9 の SC-12 経由の port なしの対）である。手元の実測（IADR-0524 の #1859 追記の表）は master の管理者で直接作ったクライアントのもので、
   テンプレートは同じ（公開・認可コードだけ・PKCE S256）だが、入口の印・audience の写像・既定のスコープの差は照合に効かないと読んでいる（未実測）。
2. 窓（最長 1 日）を縮める仕掛け（版の更新の PR での M9 の必須化など）は置いていない。版の更新は integration-stack の dispatch を経るのが運用の慣行で、それに頼る。
3. 既存の port つきの登録は変えない（そのまま完全一致で照合される）。port なしへ移るなら登録し直す（SC-12 に URI の差し替えの操作は無い）。
