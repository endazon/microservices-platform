# IADR-0297: SC-12（MCP クライアント登録管理）の境界・配備・画面の決定

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: claude（実装担当）

## 起点・関連

- 関連する計画書 ID: FR-16 / UC-09 / SC-12 / ADR-0024（§決定・§5）/ ADR-0034 決定 9 / ADR-0021
- 関連する実装仕様書: `.ai-context/specs/20260828_issue-452_sc12-mcp-client-management.md`
- 先行: IADR-0269（MCP ツールの公開経路を 1 本に閉じる）/ IADR-0292（自己申告は候補 → 選別の 1 経路）/
  IADR-0089（BFF downstream の上流ポート）/ IADR-0288（サービス名と配備の欠落）

## コンテキストと課題

後段の管理 API（`/mcp-clients*` の 6 端点・永続化・テスト 8 件）は #445 で着地している。
**しかしそこから先が全部欠けていた** —— 契約に `mcp` の語が 1 件も無く、BFF の口が無く、画面が無く、
`McpServer` は Dockerfile すら無いため compose にも chart にも載っていなかった。
「後段はあるが誰も到達できない」状態であり、SC-12 は成立していない。

実装へ委任された範囲で決めるべきことが 5 つある。

- (a) BFF の口をどこに置き、後段の応答をどう扱うか
- (b) 配備上のサービス名（chart のキー / compose のサービス名 / コード既定のホスト名）
- (c) 公開ツールの変更をどこで受けるか
- (d) 属性割当の値域をどこから引くか
- (e) 「呼び出し監査ログへの導線」の遷移先

## 検討した選択肢

### (a) BFF の口と応答の扱い

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A-1 | BFF で応答を整形し、404 を 403 へ寄せる（管理面なので「拒否」で統一する） | **却下。** 後段の 404 は「登録が無い」であり、403 は「権限が無い」である。**BFF が言い換えると、存在秘匿の設計が BFF 層で破れるか、逆に不在を拒否と誤読させる。** どちらも管理者の判断材料を壊す |
| A-2 | **`/bff/admin/mcp-clients` に AdminOnly の透過中継を置く**（`/bff/admin/authz` と同型） | **採用。** 状態コード・Content-Type・本文をそのまま返す。後段が返す 400（禁止された属性割当の理由）・404（不在）・409（重複）は画面が必要とする情報そのものである。後段不達だけは 502 へ縮退させる（管理 API であり存在秘匿は不要） |

**資格情報は後段へ伝播する。** 後段も `AdminOnly` を強制する二重ゲートであり、伝播を落とすと
すべて 401 になる。`BffMcpClientEndpointTests` が**陽性対照つきで**固定する。

### (b) 配備上のサービス名

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B-1 | chart のキーを `mcp-server` にする（プロジェクト名に揃える） | **却下。** `deployment.yaml` / `service.yaml` が `{{ $name }}-service` を組むため、Service 名が **`mcp-server-service`** になる。BFF のコード既定と一致させるには `services.bff.extraEnv` へ上書きが要り、**上書き漏れが不達（#342 の 21 秒タイムアウト）を再演する** |
| B-2 | **chart のキーを `mcp`、Service 名・compose のサービス名を `mcp-service`、コード既定を `http://mcp-service:8080` にする** | **採用。** 3 つが文字列一致し、manifest 側の上書きが 1 つも要らない。後発サービスはコード既定を 8080 にする規約（IADR-0089 の系）にも合う。イメージ名は `microservices-platform/mcp-service`（`check-image-mapping.js` が compose のサービス名との一致を要求する） |

**Dockerfile が無かった**（`find src -name Dockerfile` の 15 件に含まれない）。**イメージが焼かれない
サービスは配備に出ない** —— IADR-0288 が通知サービスで踏んだのと同型の欠落なので、同じ 4 点
（Dockerfile / compose / chart values / `MAPPING`）を同じ PR で埋める。DB（`mcp_svc`）は
**compose と k8s の init 2 本の両方**へ入れる（片方だけだと片方の環境が起動時にクラッシュループする）。

### (c) 公開ツールの変更

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C-1 | 画面に公開・非公開のトグルを置く（モックの一覧に「（無効）」の表示がある） | **却下。** 計画 §SC-12 のアクションが「公開ツールの変更は本画面から直接行わず、Git 経由の公開構成変更へ誘導する（許可リスト方式・GitOps）」と明示している。**編集口を作った時点で許可リストの単一情報源が 2 つになる** |
| C-2 | **読み取り専用の一覧＋変更経路を示す固定文言だけを置く。BFF にも書き込みの口を作らない** | **採用。** 「置かなかった」ことは**陽性対照つきの否定形テスト**で固定する（何も描かない実装でも緑になる形にしない）。BFF 側は `Composition_maps_exactly_the_expected_bff_route_groups` が群の一覧を、契約は `x-roles` が実効ロールを固定する |

### (d) 属性割当の値域

| 案 | 内容 | 評価 |
| --- | --- | --- |
| D-1 | 機密区分・タグの値集合を画面へ持つ（モックが「社内限」「週報」と描いている） | **却下。** 辞書を増やしても選べず、辞書から消えた値を選べてしまう。**値域の正は属性辞書側**である |
| D-2 | **属性辞書（`/bff/admin/authz/attributes`）から引き、利用者スコープの項目だけを出す** | **採用。** 文書スコープの属性を主体へ割り当てると意味が反転するため落とす。**禁止された割当（無人アカウントへ個人資料）は画面で判定しない** —— 判定は後段の 1 つの検証関数に閉じており、写すと 2 つ目の判定が生まれて片方だけが緩む（IADR-0269 決定 2 と同じ論法） |

### (e) 呼び出し監査ログへの導線

| 案 | 内容 | 評価 |
| --- | --- | --- |
| E-1 | アプリ内に監査ログ画面を作る | **却下。** 計画のルートパス表に監査ログ画面は無い。**計画に無い画面を実装側で作らない** |
| E-2 | 運用ダッシュボードへ送る | **却下。** あちらは利用状況の画面であり、ツール呼び出しの監査ログを持たない。**「送った先に無い」導線は誤誘導である** |
| E-3 | **実行時設定のログ基盤 URL へ外部リンクし、未設定なら導線を出さず所在を文言で示す** | **採用。** 監査は後段が構造化ログへ落としており、実体はログ基盤にある。接続先をビルドへ焼かない作法は SC-10 の外部ツール導線と同じである。**存在しないリンクを描かない** |

## 決定

1. **`/bff/admin/mcp-clients` に管理者限定の透過中継を置く。状態コード・本文・Content-Type を作り替えない。**
   後段不達のみ 502。資格情報は後段へ伝播する。
2. **配備名は `mcp` / `mcp-service` / `microservices-platform/mcp-service` で統一し、manifest の上書きを作らない。**
   Dockerfile・compose・chart values・イメージ対応表・DB init 2 本を同じ変更で揃える。
3. **公開ツールの編集口を画面にも BFF にも作らない。** 変更経路（Git 上の公開構成）を固定文言で示す。
4. **属性割当の値域は属性辞書から引く。** 禁止された割当の判定は後段に置いたままにする。
5. **監査ログの導線はログ基盤への外部リンクとし、未設定時は導線を出さない。**

## 結果

- 良い: 画面 → BFF → 後段の 3 層が揃い、SC-12 が到達可能になった。許可リストの単一情報源が保たれる。
- 良い: 配備の 3 点（イメージ・Service・DB）が同時に揃うため、「実装はあるが動かせない」状態が残らない。
- 悪い（受容）: **「有人アカウントの上限を超えない」は実装していない。** 身元の契約が登録者の属性上限を
  返さず、後段にもこの検証が無い。画面側だけで近似すると「通ったのに実際は超えている」形になり、
  **信頼できない検証は無いより悪い**（計画自身が別画面で同じ判断をしている）。画面仕様書に
  「一部する」として記録し、契約に上限が載った時点で後段と画面の両方へ入れる。
- 悪い（受容）: **登録は認可サーバーのクライアント作成を伴わない。** 後段にその口が無く、
  管理用の資格情報とクライアント種別ごとのテンプレートという別の決定が要る。繰り延べる。
- 悪い（受容）: **管理操作（登録・無効化・属性割当）の監査記録は入れていない。** 記録の実体は
  監査記録基盤側の決定である。**ツールの呼び出し**の監査は既に後段が行っている。
- 悪い（受容）: **外部 AI エージェントの入口（Ingress の `/mcp`）は公開していない。** ADR-0021 の射程で、
  公開には認証・レート制御・越境の統制を同時に決める必要がある。SC-12（管理画面）とは別の作業である。
