## コンテキストと課題

17 画面が取得の 3 相を**それぞれの流儀**で描いていた。実測された不揃いは 3 種類ある。

1. **分岐の書き方**: 三項連鎖 ／ `&&` 並置 ／ early return の 3 流儀が混在。
2. **文言**: 「読み込み中です。」「読み込み中…」「検索中…」。
3. **役割**: `role="status"` / `role="alert"` を付ける画面と付けない画面がある
   （HEAD 直前の実測: `role="status"` の直書きが 25 ファイル 41 行）。

さらに**判定の順序**が画面ごとに違い、**失敗したときに「該当するものはありません」と描く**画面があった。
これは単なる不揃いではなく**意味の誤り**である——利用者は「本当に無い」と読む。

決めるべきは 3 点。(a) フックか部品か、(b) どこの層に置くか、(c) 再試行の可否を誰が決めるか。

## 決定

### 決定 1: 判定順を **`isError` → `isPending` → `isEmpty` → 本体** に固定し、部品に閉じ込める

- **失敗を先に見るのは、0 件と失敗を混同しないため。**
- **`isEmpty` は成功したデータに対してだけ評価する**（失敗時のデータの有無は問わない）。
- **陰性対照テストを必須とする** —— 「失敗しているときに空状態を出さない」を明示的に測る。
  正常系だけを測ると、順序を入れ替えても全部緑のまま通る。
- `role="status"` / `role="alert"` は三部品（IADR-0436）が持ち、**ここで重ねて付けない**。
  二重に付けると同じ本文が 2 回読み上げられる。

### 決定 2: 置き場所は foundation（`@foundation/ui/QueryState`）である

既定の待ち文言・空文言・失敗の見出し・再試行ラベルを**この 1 か所**で `msg` マクロに載せる。
共有 UI（`@platform/ui`）は文言を持たないので置けない（IADR-0125 決定 1）。
knowledge / AST から foundation の内部を引くことはできないので、**AST は共有 UI の
`ErrorState` と `refetch` を自前の薄い部品で繋ぐ**（AST 側の判断。本リポジトリの射程外）。

### 決定 3: 再試行の可否は部品が判断せず、`canRetry` prop で画面から受ける（既定 true）

🔴 **利用者が押す再試行と、取得ライブラリの自動再試行は別物である**（計画の横断規約が明記）。
自動再試行の判定（4xx は再試行せず 408 / 429 のみ例外。`lib/api/queryClient.ts`）は
**存在秘匿により 404 が日常的に返る**ことに由来しており、本部品はそれに触れない。

`canRetry={false}` を渡すのは、**押しても状況が変わらないと分かっている**ときに限る。実例:

| 画面 | なぜ再試行を出さないか |
| --- | --- |
| 運用ダッシュボード（403 / 404 の中立化） | 権限が無い／存在しない、のいずれかである。押しても同じ結果が返り、**存在秘匿を探る往復**を誘う |

### 決定 4: 存在秘匿にかかる 404 は、`QueryState` の**手前**で空状態として描く

文書詳細・Wiki 閲覧・ナレッジグラフは、**404 を失敗として扱わない**（IADR-0009 / 計画の存在秘匿）。
これらは `QueryState` へ入る前に `EmptyState` を返す。理由は 2 つある。

1. **再試行ボタンを押させない。** 「権限が無い」と「存在しない」が同じ応答である以上、
   再試行は必ず同じ結果を返す。
2. **失敗の器（`role="alert"`）で描かない。** 不在は障害ではない。

**5xx・ネットワーク断は区別する**（IADR-0129 決定 3 と同じ線引き）。区別しないと運用者が
「権限が無い」と誤読して障害を見逃す。

### 決定 5: `errorDescription` を明示できるようにし、中立文言の割れを塞ぐ

既定では `ApiError` が持つ中立メッセージを出す。画面固有の説明（「運用ダッシュボードは
利用できません。」等）は `errorTitle` / `errorDescription` で渡す。
🔴 **秘匿が破れるのは「同じ画面の中で」権限の有無によって文言が変わるときだけ**であり、
**画面をまたいで同一文言にする必要は無い**（IADR-0129 決定 3）。明示の口を用意したのは、
既定へ落ちたときに画面ごとの説明が消えて文言が割れるのを防ぐためである。

### 決定 6: `query` の型は `UseQueryResult<T, unknown>` にする

orval 生成フックの `TError` は `unknown` である。`Error` に固定すると**生成フックをそのまま渡せず**、
呼び出し側が型を合わせるためのラップを書くことになる（それは不揃いの再生産である）。
`query.error instanceof ApiError` で絞るので、`unknown` のままで安全に扱える。

### 決定 7: `useMutation` の結果には使わない

AI 分析ダッシュボードの結果表示は `useMutation` であり、**再試行は「もう一度送信する」を意味する**。
意図しない送信・課金を誘うので、三部品を直接使い、再試行ボタンは置かない。
**`QueryState` を `useMutation` に対応させて分岐を増やさない**——分岐が増えるほど部品の意味が薄れる。

## 理由

- フックではなく部品にしたのは、**描画を画面から取り上げないと不揃いが再発する**からである。
- 判定順を部品へ閉じ込めたのは、順序が**意味の正しさ**に直結するためである。規約文として書いても
  17 画面が守る保証は無いが、部品に閉じ込めれば構造で守られる。
- `canRetry` を prop にしたのは、**「押しても変わらない」を知っているのは画面だけ**だからである。
  部品がエラー種別から推測すると、存在秘匿の判断がエラーコードの解釈へ移ってしまう。

## 結果

- 良い影響:
  - 実測（HEAD）: 20 ファイル・36 か所が `QueryState` を使っている（着手前は 0）。
    手書きの三状態は 17 画面から撤去された。
  - `role="status"` の直書きは 25 ファイル 41 行 → 21 ファイル 25 行へ減った
    （残るのは三部品以外の用途——ストリーミング中の通知・検証結果の告知など）。
  - 待ち・空・失敗の文言が 1 か所に集まり、翻訳カタログの重複が消えた。
- 悪い影響・トレードオフ:
  - **render prop は 1 段ネストが増える。** 深い分岐のある画面では読みにくくなる。
  - **`QueryState` の外で描く例外が 2 つある**（決定 4 の存在秘匿、決定 7 の `useMutation`）。
    例外を知らないと「なぜここだけ違うのか」が読めないので、各画面の冒頭コメントに理由を書いた。
- フォローアップ:
  - AST 側の薄い部品（共有 UI の `ErrorState` ＋ `refetch`）と本部品は**別実装**である。
    共通化は AST が foundation を引けるようになるまで行わない。
