# IADR-0360: 同期契約のリネーム —— 独立した `move` の口・版を進めない・楽観ロックと存在秘匿は push と同形

- 状態: Proposed
- 日付: 2026-09-03
- 決定者: claude（実装判断）／起点 issue #1176（#1153 第 2 段の積み残し）

## 起点・関連

- 関連する計画書 ID: FR-20（前提 FR-19）/ UC-11 / SC-19（`vaultPath` の表示）/ SC-20 /
  `ADR-0037` 決定 2（双方向）・7（競合をサーバで自動解決しない）・9（監査は「誰が・いつ・何件」）・
  14（KB が唯一の正）
- 関連する実装仕様書: `.ai-context/specs/20260903_issue-1176_obsidian-sync-rename-contract.md`
- 前提 IADR: `IADR-0270`（サーバ側中核。決定 3・7）/ `IADR-0338`（プラグイン第 1 段）/
  `IADR-0352`（プラグイン第 2 段）

## コンテキストと課題

`IADR-0352` 決定 5 は、リネームを次の 2 方向に分けた。

- サーバ → ローカル: manifest の `vaultPath` の変化を検知してローカルのファイルを**移動**する（実装済み）
- ローカル → サーバ: 追跡の紐付けだけ更新し、**サーバへは伝播しない**

後者は「契約に口が無い」ことの帰結であり、#1153 の宣言ファイル領域が
`Features/ObsidianSync/**` を対象外にしていたため、その PR では直せなかった。結果として、
Obsidian 側でファイル名を変えてもナレッジベース側の名前（`vaultPath`。SC-19 の表示と manifest の
突き合わせキー）は旧名のままになる。利用者には「ナレッジベース側の名前は変わりません」と
通知しており、**双方向同期（決定 2）が名前について片方向**である。

本 IADR は `IADR-0352` 決定 5 の**後半（ローカル → サーバ）だけ**を改定する。前半（サーバ →
ローカルの移動）・決定 1〜4・6 は覆さない。

## 検討した選択肢と決定

### 決定 1: 契約は**独立した `POST /private-notes/sync/notes/{id}/move`** で足す（更新 push を拡張しない）

| 案 | 評価 |
| --- | --- |
| A. 更新 push（`noteId` あり）で `vaultPath` が変わっていれば台帳も更新する | 🔴 **既存クライアントの意味論を静かに変える。** 現行のプラグインは更新 push の `vaultPath` に**追跡中のローカルパス**を毎回載せている（`pushPlanner` の `update`）。サーバがそれを採り始めると、**サーバ側リネームをまだ pull していない端末の push が、サーバ側の新しい名前を旧名へ巻き戻す**。「本文を送る」と「名前を変える」が 1 つの要求に混ざり、片方だけ拒否できない（パス重複で 409 にすると本文まで落ちる） |
| **B. 独立した `move` の口（採用）** | 名前の変更だけを運ぶ。既存 push の形・意味論は 1 バイトも変わらない（非破壊）。パス重複で 409 になっても本文の送信は独立して成功する。プラグインは「移してから中身を送る」順で送れる |
| C. `PATCH /private-notes/sync/notes/{id}` に汎用のメタデータ更新を作る | いま変えたい項目は 1 つだけで、汎用の口は「何を書き換えてよいか」の境界を曖昧にする。フェイルセーフ既定（所有者・機密区分）を書き換える経路を同期トークンへ与えかねない |

- 要求は `{ "vaultPath": "…", "version": N }`、応答は `{ noteId, vaultPath, version, updatedAt }`。
- **BFF には載せない** —— 同期プロトコル群は資格情報が別系統でSPA は呼ばない（既存の群分けのまま）。
  エッジ公開は #1154 の射程であり、本 IADR は経路を増やさない。

### 決定 2: リネームで**版を進めない**。楽観ロックは掛けるが、掛ける相手は `Document.Version` である

| 案 | 評価 |
| --- | --- |
| A. リネームで版を 1 進める | 本文が変わっていないのに版が増える。版履歴（決定 16 の直近 50 版）を名前の変更で使い切る。「10 編集 → 10 版」（決定 8）の数え方も濁る |
| **B. 進めない（採用）** | `VaultPath` は台帳（`PrivateNote`）の項目であり `Document` の版ではない。名前の変更は履歴を汚さない。プラグインの状態に持つ版もそのまま使い続けられる |

- それでも `version` は**必須**にする。クライアントが最後に見た版と現在版が違えば 409
  `version_conflict` を返す —— **古い認識のまま名前を動かすのを止める**ため（決定 7 と同じ向き。
  サーバは自動解決しない）。応答の形は push の 409 と同形にし、クライアントの解析を 1 本に保つ。
- 版が進まないので、成功後にクライアントが版を積み直す必要は無い（`state.version` は不変）。

### 決定 3: 存在秘匿・パス一意性・監査は**既存と同じ実体**を通す（規則を 2 つ持たない）

- 所有者スコープ外・不在の ID は **404**（`ObsidianSyncEndpoints.FindOwnedAsync`）。403 を返さない。
- 移動先のパス重複は `PrivateNoteEndpoints.ActivePathExistsAsync` → `PathConflictProblem`
  （409 `vault_path_conflict`）。**新規作成の重複判定と同じ関数**であり、数え方を 2 つにしない。
  現在のパスと同じ値への move は**冪等な 200**（自分自身と衝突させない）。
- 論理削除済みの資料への move は 409 `deleted`（push と同じ。復元してから同期する）。
- 監査は `private-note.sync.move` で「誰が・いつ・何件」。🔴 **`vaultPath` を記録しない** ——
  個人資料の `vaultPath` はファイル名であり、実質的に題名である。決定 9 が禁じているのは
  「タイトル・内容」であって、パスはその抜け道になる。テストで対に固定する。

### 決定 4: プラグインは push の一巡の中で、**中身より先に**名前を送る。409 は再送しない

- `pushPlanner` の `rename-local` に、新しいサーバパス（`vaultPath`）と `baseVersion` を載せる。
  `pushSync` はその順（rename-local → update）で送るので、**名前を移してから本文を送る**。
  逆順にすると、本文の push が旧名で成功したあとに名前だけ失敗する組み合わせが増える。
- **ローカルの紐付けの更新（`state.localPath`）は、move の成否によらず行う** ——
  ファイルは既にローカルで移動しており、紐付けを戻すとその資料が `missing-local` になって
  「追跡中だが見当たらない」と報告され続ける。サーバの `vaultPath`（`state.vaultPath`）だけを
  成功時に進める。次の pull は `state.vaultPath === manifest.vaultPath` を見るので、失敗した
  リネームでローカルのファイルが旧名へ引き戻されることはない。
- 409 は `IADR-0352` 決定 3 と同じ扱い —— **再送しない**。`version_conflict` は既存の
  `cause: 'version'`、`vault_path_conflict` は既存の `cause: 'path-taken'` の競合として報告し、
  利用者が名前を選び直す（自動で連番を付けない。勝手に名前を作らない）。
- 実測用の非対話ハーネスとして CLI に `move <from> <to>` を足す（ローカルのリネーム記録 → push）。

## 理由

- **決定 1** は「既存の形を変えない」という後方互換の要請と、「名前と中身を別々に拒否できる」という
  運用上の要請の両方を満たす唯一の案である。A 案の巻き戻し事故は、旧クライアントが 1 台残るだけで起きる。
- **決定 2** は `VaultPath` の置き場所（台帳であって `Document` ではない）の素直な帰結であり、
  決定 8・16 の数え方を守る。
- **決定 3** は `IADR-0141` の「同じ判断を 2 か所に持たない」。パス一意性の規則が 2 つになれば、
  片方だけが直る。
- **決定 4** の「紐付けは常に進める / サーバ値は成功時だけ進める」は、`IADR-0352` 決定 2 の
  「判らないときは消す向きの操作をしない」と同じ安全側の非対称である。

## 結果

- 良い影響:
  - `ADR-0037` 決定 2（双方向）が**名前についても双方向**になった。`IADR-0352` の
    フォローアップ 1 を閉じる
  - 既存 push・delete・manifest・pull の契約は無変更（`check-contract-schema` 非破壊）
  - 名前の重複・版ずれ・存在秘匿・監査の規則を、新しい口でも**既存の実体で**満たしている
- 悪い影響・トレードオフ:
  - 同期プロトコルの口が 4 → 5 に増える。プラグインの一巡の HTTP 往復も、リネームがあった
    資料の分だけ増える（無ければ 0 往復）
  - リネームは版を進めないため、**「いつ名前が変わったか」は `UpdatedAt` にしか残らない**
    （版履歴を辿っても出てこない）。名前の変更履歴が要るなら別の記録が要る
  - 移動先が埋まっているとき、プラグインは名前を自動で付け替えない（利用者が直すまで
    ローカルとサーバで名前が食い違う）
- フォローアップ:
  1. エッジ公開（#1154）—— 本 IADR は経路を増やさないが、公開する口は 5 つになる
  2. 名前の変更履歴（要求が出たら）
  3. `IADR-0352` フォローアップ 2・3 はそのまま
