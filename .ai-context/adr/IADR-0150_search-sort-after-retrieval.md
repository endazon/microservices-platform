# IADR-0150: 並び順は取得後に適用し、関連度を候補の門番として残す

- 状態: Accepted
- 日付: 2026-08-09
- 決定者: claude（実装）

## 起点・関連

- 関連する計画書 ID: **SC-02**（検索結果一覧。§主要素「並び順（関連度〔既定〕｜更新日時の新しい順）」）／
  **FR-03**（ハイブリッド検索）／**UC-01**（横断検索）
- 裁定: **Q5**（2026-08-05・planning#197）「**並び順は「関連度（既定）／更新日時の新しい順」の 2 値に確定する**。
  更新日時順は**「規程が改訂されたはずだが最新版はどれか」という基本動作**に要る。
  タイトル順・作成者順は採らない」
- 関連 ADR: [IADR-0149](./IADR-0149_search-result-updated-at-indexing.md)（更新日時の索引表現。**本決定はその値を使う側**）／
  [IADR-0131](./IADR-0131_openapi-as-bff-contract-source.md) 決定 5（値集合を `enum` にしない）
- 起点 issue: **#532**（先行 **#536** が索引項目を載せた。先例 **#531** が検索モードで同じ形を採った）

## コンテキストと課題

`SearchRequest` に並び順の指定軸が無く、応答は常に関連度（`Score`）降順である（実測）。
[IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) 決定 3 は「**日時を知らないチャンクを新しい順のどこに置くかは #532 が自分で決める**」と
明示的に本決定へ送っている（`null` は最小でも最大でもない）。

決めること:

1. 並び替えを**どこで**行うか（ストア側か、取得後か）。
2. 日時順のとき、**候補集合をどう取るか**。
3. **日時を持たないチャンク**（未再索引）をどこへ置くか。
4. [IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) フォローアップが挙げた**ペイロードインデックス**を作るか。

## 検討した選択肢

### (1) 並び替えの場所

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **取得後に並べ替える**（採用） | ○ | **関連度が候補を決め、日時が表示順を決める。** 計画が挙げた動機は「**規程が改訂されたはずだが最新版はどれか**」であり、これは「**関連する結果の中で**最新はどれか」を意味する。検索語は候補の選抜に効き続ける |
| Qdrant の `order_by` でストア側に並べさせる | × | **`order_by` はスコアリングを置き換える**（クライアント 1.18.1 が `OrderBy` を持つことは実測で確認したが、使うと**クエリ語が順位に一切効かなくなる**）。返るのは「アクセスできる中で新しい文書」であり、**検索ボックスに打った語が無視される**。計画は検索の並び替えを求めており、全文書の日付一覧を求めてはいない |
| 両立させる（ハイブリッドのスコアへ日時を重み付ける） | × | 計画は**2 値の切替**を定めており、連続的な重み付けは求めていない。重みは調整の根拠を持たないパラメータを 1 つ増やす（[IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) が索引の表現で避けたのと同じ「決める根拠が無い値」） |

### (2) 日時順のときの候補集合

**関連度で `candidateK` 件取り、日時で並べ替えて `topK` 件返す。**
`candidateK` は融合（RRF）が既に使っている `max(topK * 4, topK)` を再利用する。

**限界を明示する** —— **候補（`candidateK`）の外にある「もっと新しい関連文書」は出てこない。**
関連度 81 位の最新版は `topK=20` / `candidateK=80` では拾えない。
**これは取得後に並べ替える方式の構造的な帰結であり、隠さない**（§影響）。
候補を広げるほど緩和するが、`candidateK` を上げると往復と後段の負荷が増えるので、
**融合と同じ値に揃える**（同じ検索で 2 つの候補幅を持たない）。

**単系統（`keyword` / `semantic`）でも同じ幅にする。** 現行は単系統のとき候補を広げていないが、
それは「融合しないので広げる意味が無い」からである。**並び替えるなら広げる意味が生まれる。**

### (3) 日時を持たないチャンク（未再索引）

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **末尾へ置く**（採用） | ○ | 「新しい順」の**先頭が日時不明で埋まらない**。しかも[IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) 決定 4 のとおり**再索引で解消する一時状態**であり、一時状態を先頭に出す理由が無い |
| 先頭へ置く | × | 「最新版はどれか」を見に来た利用者の目に、**日時が分からないものが最初に入る** |
| `MinValue` として扱う | × | 結果は末尾で同じだが、**比較子が嘘を持つ**。[IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) 決定 3 が `null` を保った意味が消え、後で「本当に古い文書」と区別できなくなる。**null-last は比較子で明示する** |
| 結果から落とす | × | [IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) 決定 3 と同じ理由で不可（再索引が終わるまで既存文書が消える） |

### (4) ペイロードインデックス

**作らない。** [IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) のフォローアップは「`updated_at` のペイロードインデックス作成は #532 の射程」と
書いたが、**それは (1) でストア側に並べさせる前提だった。** 決定 1 で取得後に並べる以上、
Qdrant は `updated_at` で絞りも並べもしないので**インデックスは要らない**。
**前提が変わったので作らない**——使われないインデックスは索引の書き込みコストと運用の説明責任だけを増やす。

## 決定

1. **並び替えは取得後に適用する。** Qdrant の `order_by` は使わない。
   **関連度は候補の門番として残り、並び順は表示順だけを決める。**
2. **`SearchRequest` へ `SortBy` を既定値つきで足す**（`string? SortBy = null`）。
   値集合は `SearchSorts`（`relevance`〔既定〕/ `updated`）を **`const` 文字列 ＋ `Normalize`** で持つ
   ——`enum` にしない（[IADR-0131](./IADR-0131_openapi-as-bff-contract-source.md) 決定 5）。**未知値・未指定は既定（`relevance`）へ縮退する**
   ＝旧クライアントは従来どおり動く（#531 が検索モードで採ったのと同じ形）。
3. **`updated` のときは `candidateK` 件を取得してから並べ替え、`topK` 件を返す。**
   `candidateK` は融合と同じ `max(topK * 4, topK)`。**単系統（`keyword` / `semantic`）でも同じ幅にする。**
4. **日時を持たないチャンクは末尾へ置く**（null-last を比較子で明示する。`MinValue` へ倒さない）。
   **同着（同じ日時・日時なし同士）は関連度の順を保つ**——安定ソートで元の順序を壊さない。
5. **`updated_at` のペイロードインデックスは作らない**（決定 1 の帰結。[IADR-0149](./IADR-0149_search-result-updated-at-indexing.md) フォローアップを本決定が上書きする）。

## 影響

- `Knowledge.Contracts` の `SearchRequest` に `SortBy` が増える（**非破壊**。既定値つき）。
- **候補の外にある「もっと新しい関連文書」は出てこない**（決定 3 の限界）。
  利用者から見ると「関連度上位 `candidateK` 件を新しい順に並べた一覧」である。
  **計画の動機（改訂版の特定）には足りる**——同じ規程の版は同じ語で強く当たるため候補に入る。
  足りなくなったら `candidateK` を上げるのではなく**ページング**（SC-02 §未決事項 2・計画が送り方を
  定めていない）で解くべき論点になる。
- **画面（切替 UI）は本決定の射程外である。** #531 が検索モードで契約と配線までを射程としたのと同じで、
  SC-02 の「並び: 関連度 ▾」は**契約が揃った後の画面実装**として残る（SC-02 §実装しない要素 (a)）。

## フォローアップ

- SC-02 の**切替 UI**（並び順・検索モードの 2 つ）。モックでは同じツールバー行に並ぶため、
  **まとめて 1 つの画面実装として扱うのが自然**である。
- 候補幅（`candidateK`）を利用者から見える形で調整する必要が出たら、**ページング**（§未決事項 2）と
  合わせて計画へ問う。単独で定数を上げない。
