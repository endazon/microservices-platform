# IADR-0237: 実ブローカ結合テストの器は「届いた」ではなく「ローカルへ落ちなかった」を証拠にする

## 文脈

計画 `ADR-0027` の移行チェックリスト **手順 8** は、実ブローカ結合テストを移行の完了条件に含めると定める。
この器が塞ぐべき最大のリスクは、デュアルスタック期間（1 プロセスに MassTransit バスと Wolverine
ホストが同居する期間）に **publish が黙ってプロセス内へ閉じ、外部購読者へ 1 通も出て行かない**形である。
起動もビルドも封じ込め検査もトポロジ検査も通り、実行時に無音で壊れる。

したがって器の設計は「メッセージが届いたことを見る」だけでは不足である。
**ローカル配送になった形を確実に落とす**ことが要件になる。

## 決定

### 決定 1: 新規テストプロジェクトを作らず `Knowledge.IntegrationTests` へ相乗りする

coverage 床（`line 38 / branch 27`）の余裕は **0.49pt** しかなく、テストプロジェクトを 1 つ増やすと
レポート跨ぎの二重計上で割れる（#899 の実記録）。置き直しには `integration.yml` の実測が要り、
`workflow_dispatch` の API 起動が 403 のため**人間による Web UI からの手動実行**を消費する。

🔴 **［2026-08-22 追記］本 PR の作業中に #900（IADR-0236）が着地し、集計はレポートを跨いで
重複排除するようになった。** 上の「割れる」機構は塞がれたため、根拠としては弱くなっている。
それでも相乗りを採るのは、16 件 ratchet を動かさずに済み、レポートが増えないため床の
再測定自体が不要で、#900 と衝突しないからである。新しい余裕は測っていない（床の置き直しは
#900 の射程であり、本 PR は床に触れない）。

相乗りが床を動かさないことは実測で確かめた。coverlet は**テストアセンブリ自身を計装しない**
（`IncludeTestAssembly` は runsettings の opt-in であり、本リポジトリに `.runsettings` は存在しない）。
裏付けは `coverage-floor.json` にある #897 の CI 差分 —— テストコード実数 227 行を足したときの
分子増加は **+9** であった。計装されていれば約 100 行増える。

⚠️ **条件が 1 つある。`Knowledge.IntegrationTests.csproj` へ新しい `<ProjectReference>` を足さないこと。**
足すとそのプロジェクトの行がこのレポートの分母へ複製され、#899 と同じ機構で床が動く。
本器は素の Wolverine ホストだけを立てるため、新規のプロジェクト参照を必要としない。

### 決定 2: 手順 4 の破れは「明示ルーティングを持たないホスト」でしか観測できない

🔴 **これは実測で判明した。当初の設計は誤っていた。**

当初、器は「exchange への明示ルーティングを持つ発行ホストから `UsePlatformMessagingDefaults()` を
外せば、配送がローカルへ落ちて外部購読者が飢える」と想定していた。**変異試験で外しても落ちなかった。**

`opts.PublishMessage<T>().ToRabbitExchange(...)` を設定した時点で経路は確定し、
**明示ルーティングは規約ローカルルーティングより優先される**。よってその構成では手順 4 の有無が
挙動に一切現れない。当初の器は、W3 が塞ぐべきリスクを 1 ミリも塞いでいなかった。

したがって手順 4 の被験体は、**このイベント型を外へ出す経路を 1 つも設定しないホスト**とする
（`StartLocalRoutingProbeAsync`）。この形でのみ「発行元に同じ型のハンドラがあると publish が
プロセス内へ閉じる」が観測できる。

### 決定 3: 検出器が生きていることを示す陽性対照を必ず対で置く

「囮ハンドラが 1 通も受信しなかった」は、**囮が発火し得る**ことを別に示さなければ何も証明しない。
囮が壊れて二度と発火しなくなっても「受信 0 件」で緑になるからである。

よってプローブは必ず 2 本 1 組で置く。

| 構成 | 期待 | 意味 |
| --- | --- | --- |
| `applyPlatformDefaults: false` | 囮が**受信する** | ローカル配送が実在し、囮が生きている（陽性対照） |
| `applyPlatformDefaults: true` | 囮は**受信しない** | 手順 4 が効いている（本体） |

**陽性対照を落とす変異が無い器は、検出力を主張できない。**

### 決定 4: 器の状態は実行ごとに隔離する（exchange・キュー名に実行 ID を入れる）

🔴 **これも実測で判明した。** キュー名を固定にしていたとき、**同一コード・変異なしで**
「フィルタ実行では緑・全体実行では 60 秒タイムアウトで赤」という再現性のある食い違いが出た。
RabbitMQ の束縛とキューは永続するため、前回の実行が残した状態が今回の結果を左右していた。

さらに悪いことに、固定名は**変異を隠した**。fan-out の前置を潰す変異（手順 3 の破れ）が、
「前回の実行で作られた正しい束縛がまだ残っている」せいで検出できなかった。

よって exchange 名とキューのサービス名に実行ごとの一意な ID を混ぜる。前置の形
（`<service>.<event>`）は変えないので手順 3 の証明力は保たれる。

**器の緑がブローカの履歴に依存する形は、それ自体が無音の穴である。**

### 決定 5: 束縛とリスニングは同じ 1 つの名前から導く

キュー名を束縛側とリスニング側で別々に書くと、片方だけ誤った状態が「ブローカに前回の束縛が
残っているせいで通る」形で見逃される（決定 4 の実測はこの経路で起きた）。
`ListenToPlatformQueue` はキュー名を内部で組み立てるため、束縛側も同じ引数から導く。

### 決定 6: ブローカの供給経路を 2 つ持ち、いずれも fail-closed にする

| 経路 | 供給元 | 使う場面 |
| --- | --- | --- |
| Testcontainers | `RabbitMqBuilder` | CI（`integration.yml`） |
| 外部エンドポイント | 環境変数 `PLATFORM_TEST_RABBITMQ` | Docker Engine API を持たない環境 |

2 が要るのは、containerd バックエンド（Rancher Desktop 等）では Testcontainers が起動できず、
**実ブローカ結合テストが全件 skip されたまま緑になる**ためである。変数が設定されているのに
接続できない場合は skip せず**失敗させる**。「設定したのに黙って skip」は本器が塞ぐ穴そのものである。

skip 判定は既存の `DockerFactAttribute` を緩めず、**器専用の `BrokerFactAttribute`** を新設して行う。
`DockerFact` は Postgres / MinIO も要求するテスト群が使っており、緩めるとそれらが skip されずに落ちる。

## 帰結

- 後続の全辺 PR（E1〜E3b）は `WolverineBrokerEdge` を使う。fan-out（2 購読先の同時受信）は
  E3b（`DocumentUpdated`）の要件であり、器はその形を表現できる。
- 変異試験は器の付属物ではなく**完了条件**である。決定 2 と決定 4 はいずれも、変異が当たらないことで
  設計の誤りが露見して初めて分かった。**器を書いたら変異で殴る**まで、検出力は未知である。
