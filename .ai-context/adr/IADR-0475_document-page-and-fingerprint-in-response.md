# IADR-0475: 文書の応答へ本文指紋を載せ、組織文書の絞り込みとページングは別の口に置く

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-09-26
- 決定者: claude（#1575。AST#1028 の実装〔AST#1038・AST/IADR-0436〕が挙げた基盤の文書 API の不足 4 点）

## 起点・関連

- 関連する計画書 ID: FR-06（文書の CRUD・メタデータ管理）、NFR-08（文書 数万〜数十万件）、UC-03、SC-05（管理系の破壊的操作は管理者限定）
- 関連する計画 ADR: **ADR-0050** 決定 1（本文の内容のみに依存する不透明な値）・フォローアップ 3（算出方法は実装側が決めて IADR に残す）、
  **ADR-0036** D-07（所有者ベースの書き込みは個人資料の投入経路）・D-08（平時は管理者も個人資料を見ない）・§未確定事項 6、
  ADR-0034 決定 9（機械の主体は個人資料を対象にしない）、ADR-0054（`doc_scope`）、ADR-0091（文書の同一性は文書 ID）
- 関連する実装 ADR: IADR-0012 / IADR-0041 / IADR-0045（読み取りの ABAC の実施点は BFF ただ 1 つ）、IADR-0075（AST の KB 用クライアントは `platform-operator` のみ）、
  IADR-0122（契約スナップショット）、IADR-0379 / IADR-0402（文書読み取りの gRPC 面は REST と同値）、IADR-0401 決定 2（呼び出し元の居ない口を面へ出さない）
- 関連する実装仕様書: `.ai-context/specs/20260926_issue-1575_document-page-and-fingerprint.md`

## コンテキストと課題

AST は確定報告書を KB へ入れ直す操作で、基盤の文書 API の不足を迂回している（KB の全件を 1 回引き、属性
`project` + `periodKey` + `kind` で既存の写しを探す）。不足は次の 4 点である。

1. 外部 ID での引き当て・upsert が無い
2. `GET /documents` に属性の絞り込みとページングが無い（収集記事を含む全件を引くしかない）
3. 返す文書に本文の指紋が無い（保存済みの本文が最新か判定できない）
4. サービスアカウントが自分の所有する文書のメタデータ更新・削除をできない（管理者限定）

## 検討した選択肢

### 項目ごとの採否（計画との照合）

| # | 計画 | 採否 |
| --- | --- | --- |
| 1 | 同一性は文書 ID ただ 1 つ。`外部 ID` / `external_id` / `自然キー` / `冪等キー` / `upsert` の記述は計画に 0 件 | **採らない**（新しい同一性の概念を実装が作ることになる。環流） |
| 2 | 一覧の形に沈黙。FR-06 の読み取りの詳細化 | **採る**（見える集合を広げない形に限る） |
| 3 | ADR-0050 が性質を定め、算出方法を実装へ委ねた。台帳は既に値を持つ | **採る** |
| 4 | SC-05 は編集・削除を管理者限定とする。機械クライアントへの射程は環流 `20260809_document-write-machine-client` が裁定待ち（status open）。ADR-0036 D-07 の所有者ベースの書き込みは個人資料の投入経路の規定 | **採らない**（認可モデルの変更であり計画の裁定が要る。環流） |

### 項目 2 の置き場所

| 案 | 評価 |
| --- | --- |
| A: 既存の `GET /documents` に `attr.*` / `limit` / `cursor` を足す | 却下。ページングには次の位置が要り、応答を配列のまま保つと位置をヘッダで運ぶことになる。応答の形を要求で変えると 1 つの口が 2 つの形を持つ。さらに BFF の一覧（全件を ABAC で絞る）と gRPC `ListDocuments`（REST と同値）が現行の形を前提にしている |
| **B: 別の口 `GET /documents/page`（応答は `{ items, nextCursor }`）** | **採用**。既存の口・BFF・gRPC の同値は 1 つも動かない |

### 項目 2 の並びとページング

| 案 | 評価 |
| --- | --- |
| オフセット（`skip` / `take`。FeedbackService の先例） | 却下。前のページの文書が消えると後続がずれ、未読の文書を読み飛ばす |
| 更新時刻の降順 ＋ キーセット | 却下。走査の途中で他者が更新した未読の文書が先頭へ移り、読み飛ばされる |
| **作成時刻の昇順 ＋ キーセット（`CreatedAt`, `Id`）** | **採用**。作成時刻は台帳の初期化子でしか決まらない不変の値で、**走査の間ずっと在った文書はちょうど 1 回ずつ返る**。途中で作られた文書は末尾に現れ、削除はカーソルの位置を動かさない |

## 決定

**決定 1 — 応答へ本文指紋を載せる。** `DocumentDto.ContentFingerprint`（`string?`・末尾追加・既定 null）に台帳の
`Document.ContentFingerprint` を写す。gRPC `DocumentSummary` へも `optional string content_fingerprint = 11` を足し、
REST と同じ形を保つ（presence で運び、null を空文字へ化けさせない）。

- **算出方法（ADR-0050 フォローアップ 3 の記録）**: 全経路（本文つきの作成・`PUT /documents/{id}/body`・正規化の取り込み・
  Obsidian 同期）が `DocumentBodyIntake.Fingerprint` を通り、**格納した本文の UTF-8 バイト列の SHA-256 小文字 hex** を作る。
  正規化（改行・末尾空白）はしない。**本文を投入した呼び出し側は、送った本文から同じ値を計算して突き合わせられる**。
  この性質を契約として扱う（変えるなら呼び出し側との約束の変更であり、新しい IADR を起こす）。
- 本文を持たない文書・指紋化できなかった文書は null。
- 🔴 **原本が本文を持たない文書（`HasBody=false`。テキスト層の無い PDF 等）も応答では null に倒す**（#1603 の監査の指摘）。
  取り込み（`DocumentNormalizedConsumer`）は空の `document.md` を読んで指紋を計算するため、台帳には**空文字列の SHA-256** が入っている。
  そのまま返すと呼び出し側（AST の KB 入れ直し）が「本文がある」と読み違える。倒すのは `DocumentEndpoints.ToDto` の 1 か所で、
  生成マッパには同名で写させない（`[MapperIgnoreTarget]`）。**台帳とイベント（`DocumentUpdated`）の値は変えない** ——
  却下解除・再取り込みの判定は本文の変化だけを見ればよく、空の本文の指紋でも ADR-0050 決定 1 の性質を満たす。
  応答の契約は「**値があれば本文がある**」である。
- BFF はそのまま中継する。**本文を読める主体に本文の指紋を見せても新しい情報は漏れない**（個人資料の `contentHash` と同じ扱い）。
  AI 提案の「却下時点の指紋を公開面に出さない」は提案の内部状態の話で、本決定と別物である。

**決定 2 — 組織文書の絞り込み・ページングは `GET /documents/page` に置く。**

- 絞り込み: `attr.<キー>=<値>`（0 個以上・AND・キーと値とも大文字小文字を区別する完全一致）。同じキーの重複・空のキー・空の値は 400。
- ページング: `limit`（既定 100・1〜500 に丸める）、`cursor`（不透明。壊れていれば 400）。並びは `CreatedAt` 昇順・同時刻は `Id` 昇順。
- **認証を要する**（ロールは問わない）。既存の `GET /documents` は認証を要らないが、新しい口は狭い側で開ける。
- gRPC 面には足さない（呼び出し元が居ない。IADR-0401 決定 2 と同じ作法）。

**決定 3 — 見える集合を広げない。**

- DocumentService の読み取りは ABAC の判定を持たない（実施点は BFF の `BffScopeResolver` ＋ `IsManageable`）。
  直接の呼び出し元に見えている集合は `GET /documents` の全件であり、新しい口はそこから
  「**組織文書**」「**全絞り込みに一致**」で削るだけである。**構成上その部分集合にしかならない。**
- **個人資料（`doc_scope=private-note`）は、絞り込みの値にも呼び出し元にも依らず返さない**
  （ADR-0036 D-08・ADR-0034 決定 9 の線。BFF の管理一覧が `IsManageable` で個人資料を外すのと同じ）。
  判定は `DocumentScopes.IsPrivateNote` ただ 1 つで、集合帰属で書く（キー欠落は組織文書）。
  **ABAC の判定器を DocumentService に 2 つ目として足すものではない** —— 属性 1 つの構造的な除外である。
- 🔴 **機械の呼び出し元は、この口で機密区分の高い組織文書（`confidential` / `restricted` を含む）を ABAC を経ずに読める。**
  これは既存の `GET /documents`（認証すら要らない）と同じ露出であり、本決定が広げたものではない（部分集合であることは上のとおり）。
  **ロールの門は置かない。** 誰を通すか（例: 管理者・運用者に限る、サービスアカウントの属性で絞る）は読み取りの統制の射程の問いであり、
  計画の判断を待つ（planning#680 へ追加された論点）。裁定が出たら、既存の一覧と新しい口の両方へ同じ門を置く新しい IADR で扱う。

**決定 4 — 絞り込みは台帳を読んだ後にメモリ上で行う。** 属性は jsonb へ値変換で写しており、LINQ から SQL へ訳せない。
既存の `GET /documents` も全件をメモリへ読むので DB の負荷は増えない（減るのは応答の量）。

**決定 5 — 項目 1（外部 ID）と項目 4（機械の主体の所有文書の更新・削除）は実装しない。** 計画の裁定を待つ。
環流の下書きは PR 本文に置く（起票は利用者・コーディネータ）。既存の管理者限定（`Write_OperatorRole_Returns403` ほか）は変えない。

## 理由

- 項目 3 は計画が性質を定め、台帳が既に値を持っている。**呼び出し側が判定に使えるのは、算出方法が固定されているときだけ**であり、
  それを記録するのが ADR-0050 フォローアップ 3 の求めることである。
- 項目 2 の要点は「読み飛ばさない」ことにある。AST の入れ直しは一覧で見つからない写しを新しく作るので、
  **読み飛ばしはそのまま重複の作成になる**。不変のキーとキーセットの組だけがこれを構造的に防ぐ。
- 項目 1・4 は、前者が同一性の概念、後者が認可モデル（SC-05 の統制の射程）に触れる。
  どちらも実装側で決めると計画が知らない統制・概念が本番に入る。

## 結果

- 良い影響: 呼び出し側は自分の属性で絞った集合だけを、読み飛ばしなく辿れる。保存済みの本文が最新かを 1 回の比較で判定できる。
- 悪い影響 / トレードオフ:
  - 新しい口は全件を読んでからメモリで絞るため、1 ページごとに台帳全体を読む（既存の一覧と同じ費用がページ数だけかかる）。
  - 新しい口と既存の一覧で並びが違う（作成順 / 更新の新しい順）。
  - 項目 1・4 が入るまで、AST は「一覧で探す」迂回を続け、古い本文なしの写しを自分では消せない。
- フォローアップ:
  1. 項目 1・4 の環流（計画の裁定）。裁定が出たら新しい IADR で実装する。
  2. 台帳の規模が問題になったら、jsonb の包含演算子による SQL 側の絞り込みへ移す（属性の写し方の変更を伴う）。
- 再検討の条件: 呼び出し側が指紋の算出方法に依存できなくなる変更（正規化の追加・関数の差し替え）が要るとき。
