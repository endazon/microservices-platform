# IADR-0252 ABAC 正常系の観測

## 状況

`BFF → AuthorizationService` の ABAC スコープ解決について、**「実際に許可が出た」ことを確かめた記録が
リポジトリのどこにも無かった**。確かめてきたのは否定形（deny になること）と、
壊れていることを示す個別の実測だけである。

同じ経路で今日 2 つの欠陥が見つかった。**どちらも正常系の観測では見つかっていない。**

| | 欠陥 | 見つかった経緯 |
| --- | --- | --- |
| `#948` / PR `#966` | BFF が `/feedback/stats` へ資格情報を渡さず 401 を中継（2 箇所） | 稼働クラスタで 401 を踏んだ |
| `#958` / PR `#971` | WikiService / AiAnalysisService が `AuthorizationService` を不達ポートで呼ぶ（3 箇所） | 検査器の母集合を広げたら出てきた |

### 🔴 穴はコード上で確定している

```csharp
var scope = await BffScopeResolver.ResolveAsync(httpFactory, http, ct);
if (scope is null)
    return Results.Ok(new List<DocumentDto>());   // 200 ＋ 空リスト
```

**「認可が壊れている」と「文書が 1 件も無い」が、応答上まったく同じ**である。
`verify-oidc-edge-flow.sh` の段 7 は状態コードしか見ないので、**どちらも PASS する。**

## 決定

### 決定 1: 判定は正の対照と負の対照を**対で**置く

| # | 主体 | 操作 | 期待 |
| --- | --- | --- | --- |
| 11 | `developer` | `POST /bff/documents` | **2xx**（deny なら 403） |
| 12 | `developer` | `GET /bff/documents` | **非空**・作成した文書を含む |
| 13 | `poc-operator` | `GET /bff/documents` | **0 件** |

🔴 **負の対照に `poc-operator` を選ぶ理由がある。** この利用者は `platform-operator` を持つので
**一覧端点の RBAC は通り、ABAC 属性が空**なのでどのポリシーにもマッチしない。
**RBAC と ABAC を切り分けられる**唯一の主体である。

🔴 **負の対照に `POST` を使わない。** `POST` は `AdminOnly` なので、`poc-operator` では
**ABAC 以前に RBAC で 403** になる。対照に使うと何が効いたのか分からなくなる。

### 決定 2: 非空を観測するために**書き込みを 1 件だけ行う**（opt-in・既定オフ）

新規スタックには文書が 1 件も無い（初期投入経路は ABAC ポリシーだけで、文書は入らない）。
**したがって非空は書き込みなしに観測できない。**

`ABAC_POSITIVE=1` のときだけ有効にし、**既定は読み取り専用のまま**据え置く。
使い捨てのスタック専用であることをスクリプトのヘッダへ明記する。

### 決定 3: nightly に置く。PR ゲートには載せない

`IADR-0248` 決定 3 が上限を定義している ——「全 PR で起動するジョブは `ci.yml` の
`build-and-test` の **2 倍**を超えてはならない」。本ジョブは 8〜10 分で明確に超える。

### 決定 4: ポリシー投入の成否を握り潰さない

`k8s-local-up.sh` の `ABACSEED` は best-effort（失敗しても WARN で通す）。
投入器は冪等なので、**readiness の後に明示ステップとして再実行し、終了コードを見る。**
ここが緑なら、次の門の「空」はポリシー起因ではないと言える。

## 実測（`Integration Stack` run `32566511817` ほか）

[12/13] PASS  GET /bff/documents（許可あり）→ 200・1 件・作成した文書を含む
[13/13] PASS  GET /bff/documents（poc-operator）→ 200・0 件（deny-by-default が効いている）

## 🔴 実測による訂正 —— `#958` の症状の特徴づけを直す

`#958` / `#972` で私は「不達 → deny-by-default へ縮退 → **静かに空になる**」と書いた。
**M1 の実測はそうならなかった。**

```
[7/13]  FAIL  /bff/documents → 000
[11/13] FAIL  POST /bff/documents → 000
```

`000` は curl が応答を得られなかった（タイムアウト）ことを表す。
**k8s では ClusterIP に無いポートへ繋ぐと RST が返らずハングする**ため、
`BffScopeResolver` が例外を捕まえて deny へ縮退するより先に、**呼び出し側が待たされる。**
`#342`（`:5002` のまま live へ出て **21 秒タイムアウト → 502**）と同じ形である。

**環境で症状が変わる。**

| 環境 | 不達ポートへの接続 | 見える症状 |
| --- | --- | --- |
| docker-compose | 待ち受けが無ければ **connection refused**（即座） | 例外 → deny → **静かに空** |
| **k8s（ClusterIP）** | ポートが無いと**落とされる**（RST なし） | **ハング → タイムアウト** |

🔴 **「静かに空になる」は compose の挙動であり、k8s ではそうならない。**
`#958` の PR 本文と `#972` の起票文は compose の挙動を一般化していた。**訂正する。**
どちらにせよ欠陥であり修正の要否は変わらないが、**症状の予測が違えば探し方が変わる。**

検査器はこの形を名指しできるようにした（`000` を「上流の宛先が不達の疑い」と報告する）。

## 🔴 途中で見つかった 2 件（どちらも「走っていない検査は正しさを保証しない」の実例）

### 1. ABAC 投入器が今日から壊れていた

投入器は管理者パスワードを直書きしており、`#933` が realm のパスワードを一斉に変えたときに
追随しなかった。**統合スタックで明示実行して初めて 401 で落ちた。**
`ABACSEED` が best-effort なので、それまでは WARN が出るだけだった ——
**ポリシー 0 件 → deny → 画面が空**になるが、それは仕様どおりの deny と区別が付かない。
`#933` のレビューは同じ変更の追随漏れとして**文書 4 件**を挙げていたが、**この実行コードは挙がっていない。**

realm ファイル（単一情報源）から引く形へ直し、**realm の全平文パスワードがスクリプトへ
直書きされていないこと**を回帰テストで固定した。

### 2. スクリプト自身の想定が 12 日間陳腐化していた

段 8 は「読み取り系は匿名を許容する現行設計」を前提に**無トークンの 200 を PASS** としていたが、
**`#659`（2026-08-10）が無認証で到達できた BFF 9 端点を塞いでいた**。実測は 401 で FAIL になった。
**本スクリプトは自動実行されていなかったため、12 日間気づかれなかった。**

## 検出しないこと

- 🔴 **`#958` の実際の 3 箇所（WikiService / AiAnalysisService → AuthorizationService）は検出できない。**
  - **WikiService を通す BFF 端点が存在しない**
  - **`/bff/analysis/*` は LLM を必要とする**ため CI（鍵なし）では正の側が別の理由で落ちる
  - **M1 は BFF 自身のクライアントへ当てている。故障の形は同じだが、当てている経路は違う。**
    ここを混同しない
- **「直す前に届かなかったこと」は確かめられない。** `#958` は既に直っており、置いたのは**回帰の門**である
- 一覧の**件数の絶対値**は固定しない（投入データに依存する）
- **段 7 の他の 2 端点（`/bff/datasources` など）は状態コードのみ**である。
  非空の判定を入れたのは `/bff/documents` だけで、**残りは同じ穴を持ったままである**
