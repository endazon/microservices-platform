# IADR-0343: 利用状況イベントの生産者

- 状態: Accepted
- 日付: 2026-09-02
- 決定者: 実装（#1103）

## 起点・関連

- 関連する計画書 ID: FR-03 / FR-04 / FR-07 / FR-10 / UC-01 / UC-02 / UC-05 / SC-01 / SC-10 / ADR-0002 / ADR-0006 / ADR-0027 / ADR-0029 / ADR-0030 / ADR-0044
- 関連する実装仕様書: `.ai-context/specs/20260902_issue-1103_usage-event-producer.md`
- 先行: `IADR-0299`（ナレッジ健全性の生産者。**同型の穴として `POST /dashboard/events` の発火側が 1 本も無いことを記録したが、起票されていなかった**）

## コンテキストと課題

`POST /dashboard/events`（受け口）・`UsageEvent`（永続化）・`GET /dashboard/{usage,trends,summary}`（集計）・
`/bff/dashboard/summary`（BFF）・SC-10（画面）はすべて実装済みだが、**投入する製品コードが 1 本も無かった**。
実測（2026-08-30・`a2c7e5b1`、および 2026-09-02・`2211ee77` で再確認）では、当該パスを叩くのは
**テストとコメントだけ**である。したがって `totalSearches` / `totalAnswers` / 検索傾向は恒久的に 0 であり、
**画面はそれを「0 件」として描く** —— 「利用が無かった」と「一度も測っていない」が区別できない。

決めるべきことは 4 つある。

1. **誰が発火するか。** `IADR-0299` の解（`/internal/...` ＋ 無認可）は**持ち込めない** ——
   健全性指標の生産者はユーザー文脈を持たない定期処理だが、**利用状況イベントは利用者主体が要る**
   （受け口は `HttpContext.User.Identity.Name` から利用者を取る）。
2. **同期か非同期か。** 検索の応答時間（NFR 検索 p95 1.5s）に計測の往復を載せてよいか。
3. **失敗の扱い。** 計測の失敗で検索を落とさない（fail-open）。ただし黙って捨てると
   **#1103 が直そうとしている「0 件が正常に見える」形を作り直す**。
4. **`private-note` の扱い。** 健全性指標の「個人資料は集計から除外」と同じ規則が要るか。
   検索語を `query` に残す設計なので、**個人資料を狙った検索語が運用者から読める**形になっていないか。

## 検討した選択肢

### 発火点（論点 1）

| 案 | 評価 |
| --- | --- |
| **(b) BFF が応答時に送る（採用）** | 利用者の `Authorization` が**その場に在る**。BFF は既に検索・回答の双方で同ヘッダを後段へ伝播しており、**同じ値を受け口へ運べば主体が乗る**。発火点が 4 経路に閉じ、数えるべきものと数えてはならないものを 1 か所で判定できる |
| (a) RetrievalService / AiAnalysisService が送る | ❌ **二重計上を避けられない。** `RagOrchestrator` は回答の生成中に `POST /search` を呼ぶので、RetrievalService に置くと**質問 1 回が `answer` 1 件 ＋ `search` 1 件**になる。後段は呼び出し元が RAG か利用者かを知らない。加えて非同期化するなら主体を運ぶ必要があり、運べば自己申告になる |
| (c) SPA が送る | ❌ #1103 が明示的に却下（利用者が計測を止められ数が信頼できない） |

### 送出の経路（論点 2 の一部）

| 案 | 評価 |
| --- | --- |
| **HTTP（名前付き `HttpClient`。採用）** | 受け口は `POST /dashboard/events` の HTTP であり、**認証済みの主体をヘッダで運べる唯一の形**である。BFF から後段への呼び出しは全部この形で、`DashboardService` クライアントはホストに既に在る |
| Wolverine のメッセージ（ADR-0027 / ADR-0030） | ❌ 3 つ重なる。①**受け手が自己申告の userId を信じることになる**（メッセージに `HttpContext` は無い）——認証済みの主体が自己申告へ後退する。②**BFF も DashboardService も Wolverine ホストではない**（`Program.cs` に `UseWolverine` を持つのは 7 サービス。BFF と DashboardService は含まれない）。③受け口を 2 系統（HTTP ＋ メッセージ）にすると、**利用状況の唯一の入口という性質**が失われる |
| Refit | ❌ BFF 層では 1 本も使われていない（`Refit.HttpClientFactory` の参照はあるが、後段呼び出しは全部 `IHttpClientFactory` の名前付きクライアント）。既存の形に揃える |

### 同期性（論点 2）

| 案 | 評価 |
| --- | --- |
| **有界の列 ＋ 常駐ドレイン（採用）** | 発火は `TryWrite` の 1 回（O(1)・例外を投げない）。**検索の応答時間に往復が乗らない**。溢れは数えて捨てられる |
| 応答の前に await する | ❌ 検索 1 回ごとに受け口への往復が加算される。受け口が不調なとき**検索そのものが遅くなる**（計測が本処理の可用性を下げる） |
| `Response.OnCompleted` で送る | ❌ 応答は返っているが、**要求は callback が終わるまで完了しない** —— 受け口が固まると keep-alive の接続が最大 5 秒ずつ塞がる |
| 素の `_ = Task.Run(...)` | ❌ 同時実行に上限が無い。受け口が固まると検索のたびに滞留し、**溢れたことも数えられない** |

### `private-note` の扱い（論点 4）

| 案 | 評価 |
| --- | --- |
| **同じ除外規則は適用できないと結論し、最小フィールドで送る（採用）** | 健全性指標の除外は**文書**の集計についての規則で、判定材料は `doc_scope` である。**検索語は文書ではなく `doc_scope` を持たない** —— 判定材料が存在しない |
| 検索語を送らない | ❌ FR-10 の「検索傾向」が成立しない（`SearchTrendDto` の入力が消える） |
| 最小件数のしきい値で秘匿する | ❌ **集計側（`AggregateTrendsAsync`）の設計変更**であり、「何件以上を出すか」は指標の意味そのもの。実装が独断で決めてよいものではない → 計画へ環流する |

## 決定

### 決定 1 — 発火点は BFF の 4 経路とし、後段には置かない

`Knowledge.Bff.Endpoints` の次の 4 か所で、**本処理が成功したあと**に 1 回だけ発火する。

| 経路 | 種別 | 発火の条件 |
| --- | --- | --- |
| `POST /bff/search` | `search` | 後段 RetrievalService が 2xx を返したとき |
| `POST /bff/analysis/ask` | `answer` | 後段が 2xx を返し、回答を読めたとき |
| `POST /bff/analysis/ask/stream` | `answer` | 上流が 2xx（SSE のヘッダ）を返したとき |
| `POST /bff/analysis/analyze` | `answer` | 後段が 2xx を返し、回答を読めたとき |

🔴 **実行されていない検索を数えない。** 空クエリ・許可スコープ無し・後段の非 2xx・後段不達は
いずれも早期に空応答へ落ちる経路であり、**そこでは発火しない**（陰性対照をテストで固定した）。

🔴 **`POST /bff/analysis/analyze` も `answer` に数える。** 契約の `answer` は「AI 回答生成」であって
「SC-01 の質問」に限られていない —— 本経路も LLM が根拠つきの `AiAnswerDto` を生成する。
落とすと総回答数が実際の生成回数と食い違う。

**除外の全体（母集合 11 行と各行の理由）は作業仕様書 §母集合 が持つ。ここへ複写しない。**

### 決定 2 — 送出は HTTP。**メッセージングは選べない**

`IUsageEventReporter` ← `UsageEventReporter`、送出は `UsageEventDispatcher`（`BackgroundService`）が行う。
名前付きクライアントは `/bff/dashboard/summary` が使うものと同じ `DashboardService` を共有する。

🔴 **利用者の `Authorization` をそのまま受け口へ運ぶ。** これが「誰の利用か」を後段が解決する
唯一の材料であり、**発火点を BFF に置いた理由そのもの**である。伝播が落ちると受け口は 401 を返し、
fail-open のため**利用状況が静かに 0 のままになる**（テストで固定した）。

### 決定 3 — 発火は同期・O(1)・例外を投げない。送出は有界の列を介して非同期に行う

- `UsageEventQueue` = 容量 1024 の `Channel`。`FullMode` は `Wait` だが **`TryWrite` しか使わない** ——
  `DropWrite` にすると溢れても `TryWrite` が `true` を返し、**捨てたことを数えられなくなる**。
- ドレインは逐次 1 件ずつ。送出 1 回の上限は **5 秒**（`HttpPrivateNoteNotifier` /
  `HttpKnowledgeHealthReporter` と同値）。名前付きクライアント側の `Timeout` は変えない ——
  同じクライアントを `/bff/dashboard/summary` の集約が共有しているためである。
- **停止要求時に列へ残ったぶんは捨てる。** 利用状況の 1 件は再送に値せず、送り切るために停止を遅らせない。
- 🔴 **`HttpContext` を列へ載せない。** 送出は応答の後に別のスレッドで走るため、そのとき
  `HttpContext` は破棄され得る。種別・検索語・資格情報を**文字列として写し取ってから**載せる。

### 決定 4 — fail-open。ただし **4 つの結末をすべて計器に載せる**

`UsageEventMetrics`（`usage.event.dispatch.total`。Meter 名は BFF のサービス名と同じ）。
属性は `usage.event.type` と `usage.event.outcome` だけである。

| 結末 | 意味 |
| --- | --- |
| `sent` | 受け口が 2xx を返した（＝ `UsageEvents` に 1 行入った） |
| `rejected` | 受け口へ届いたが非 2xx（資格情報か配備の不整合） |
| `unreachable` | 受け口へ届かなかった（未配備・通信エラー・5 秒のタイムアウト・想定外の例外） |
| `dropped` | 送出待ちの列が溢れた（受け口の不調が続いたとき最初に現れる） |

`rejected` / `unreachable` / `dropped` はエラーログにも落とす。**握る範囲は「停止要求以外すべて」**である
（`IADR-0215` 決定 5-b と同じ理由 —— 例外型を列挙すると漏れたものが呼び出し元へ抜ける）。

🔴 **利用者識別子も検索語も、ログにも計器にも出さない。** 前者はカーディナリティが非有界で
個人の利用行動の記録に踏み込む（ADR-0044 決定 1 / 計画 §SC-10 Q27 理由 ②）。後者は本文そのものである
（ADR-0006 §結果「ログに本文・機密情報を出力しない」）。

### 決定 5 — 送るのは `eventType` と `query` の 2 つだけ。**`answer` では `query` を送らない**

受け口は種別が `answer` のとき検索語を保持しない。**捨てられる自由文（質問文）を
ネットワークと相手側のログに晒す理由が無い。** 利用者は送らない（受け口が JWT から解決する）。
文書 ID・出典・結果件数も送らない。

### 決定 6 — `private-note` の除外規則は利用状況イベントへ**適用できない**。残余リスクは記録して環流する

計画 §SC-10 の「個人資料（`private-note`）は集計から除外する」は**文書**の集計についての規則であり、
判定材料は `doc_scope` である。**検索語は文書ではなく `doc_scope` を持たない**ため、
機械的に適用する術が無い（否定で書けば全件が除外側へ倒れる）。

本決定で取れる統制は決定 5（最小フィールド）までである。**残る 2 つは計画の裁定事項として環流する。**

1. **検索傾向は検索語を素で運用者へ見せる。** 上位 N 件は件数降順であり、**語の種類が N 未満なら
   1 回しか検索されていない語も出る** —— 個人資料を狙った検索語が運用者に読める経路が残る。
   最小件数によるしきい値秘匿は `AggregateTrendsAsync` の設計変更であり、しきい値は指標の意味そのものである。
2. **`UsageEvent.UserId` を保存しているが、どの集計も読んでいない。** 計画 §SC-10 Q27 は
   一意利用者数を採らない理由として「一意集計には利用イベントへ利用者識別子を持たせる必要があり、
   『誰がいつ何回検索したか』の記録が残る。保持期間・目的外利用の禁止・開示請求への対応という統制が
   新たに要る一方、得られるのは数字 1 つであり見合わない」と述べている。**受け口はこの裁定より前に
   書かれており、列を持ったままである。** 発火側を入れた本作業により、**計画が避けると決めた記録が
   実際に溜まり始める。** 列の除去は移送を伴う受け口側の設計変更であり、保持の是非は計画の裁定事項である。

🔴 **本 IADR は 1・2 を「受容」しない。記録して環流するまでが本決定である。**

## 理由

- 発火点を BFF に置く決め手は**主体**である。受け口の認可（`RequireAuthorization()` ＋
  `HttpContext.User` からの利用者解決）を変えずに済む唯一の位置であり、`IADR-0299` が
  健全性指標で採った「受け口の認可を外す」解を**持ち込まなくてよい**。
- 二重計上（`RagOrchestrator` の内部 retrieval）は後段に置くと**構造的に**避けられない。
  BFF なら「利用者が始めた操作」だけを見ている。
- 有界の列は「fail-open にすると静かに落ちる」への答えでもある。`dropped` は
  **受け口の不調が続いていることが最初に現れる数**であり、これが無いと
  「利用状況が伸びない」の原因を切り分けられない。

## 結果

- 良い影響:
  - SC-10 の利用状況・検索傾向が**実データで動く**。「0 件」と「測っていない」が区別できるようになる。
  - 送出の 4 結末が計器に載るので、**届いていないことが表に出る**。
  - 検索・回答の応答時間に計測の往復が乗らない。
- 悪い影響・トレードオフ:
  - 送出は best-effort である。停止時に列へ残ったぶんと、溢れたぶんは失われる（数は載る）。
  - BFF がクラッシュすると列の内容は消える。**永続化しない**（利用状況の 1 件に見合わない）。
  - 資格情報（アクセストークン）が列に載っている間だけメモリに残る。列が滞留してトークンが
    期限切れになると `rejected` になる（数は載る）。
- フォローアップ:
  1. **決定 6 の 1・2 を計画へ環流する**（検索傾向のしきい値秘匿・`UsageEvent.UserId` の保持の是非）。
  2. MCP ツール `retrieval.search_documents` は**申告だけで実体が無い**（宣言先
     `/internal/mcp/search_documents` の実装が 0 件）。本作業の射程外だが、
     実装される段では利用状況の発火点として数え直す判断が要る。
