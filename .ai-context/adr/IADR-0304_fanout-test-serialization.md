# IADR-0304: fan-out の統合テスト 2 クラスは直列化する

- 状態: Accepted
- 日付: 2026-08-30
- 決定者: 実装（#1038 / #1059）

## 起点・関連

- 関連する計画書 ID: FR-02 / FR-06 / FR-13 / FR-14 / UC-04 / ADR-0018 / ADR-0027
- 関連する実装 ADR: IADR-0302（購読開始と実処理を分けた。**本 IADR はそれを覆さない**）／
  IADR-0232 決定 1（統合テストを PR から後段へ移した判断）／IADR-0245（Wolverine 移行）
- 対象: `Knowledge.IntegrationTests.Messaging.DocumentUpdatedFanOutTests` /
  `QueueOverrideFanOutTests`

## 背景

#1038 の 2 件は 5 ラウンドにわたり原因が特定できていない。潰れた仮説は
**購読開始の遅さ**（IADR-0302 の 2026-08-29 追記で実測により否定）・**キュー宣言の不一致**・
**exchange 束縛の欠落**・**ルーティングキーの不一致**であり、いずれも「なぜ落ちるか」を説明しない。

**#1059（CI 自動起票）は本件と同一原因である** —— run 33249756332 の失敗 2 件は #1038 の 2 件と
完全に一致し、**同一コミット `0784dd2` が失敗（33249756332）と成功（33273064354）の両方を出している**。

### 本ラウンドで新しく出た事実 —— 仮説ではなく run ログの実測

Integration の run 5 本（`gh run view <id> --log`）から、xUnit の相対時刻とテスト所要時間で
2 件の実行窓を復元した。

| run | 結果 | `DocumentUpdatedFanOut` | `QueueOverrideFanOut` | 2 件の重なり |
| --- | --- | --- | --- | --- |
| 33249756332 | **FAIL**（両方 wiki 側） | 35s（`01:01.96` に予算切れ） | 33s（`01:01.95` に予算切れ） | **ほぼ全域** |
| 33233171135 | **FAIL**（両方 ingestion 側） | 30s（`01:04.66`） | 30s（`01:28.40`） | **約 6 秒**（加えて一方の待ちの最中に他方がコンテナ 2 つ ＋ ホスト 3 つを起動） |
| 33273064354 | PASS | **2s** | **1s** | 無し（約 20 秒離れ） |
| 33226232176 | PASS | **3s** | **646ms** | 無し（約 33 秒） |
| 33195657772 | PASS | **341ms** | **2s** | 無し（約 51 秒） |

🔴 **分布が二峰である。** 緑は 341ms〜3 秒、赤は予算 30 秒を使い切る。**中間が 1 件も無い。**

## 決定

### 決定 1: **予算 30 秒を伸ばさない**（IADR-0302 決定の継続。実測で裏が付いた）

緑の実測が **341ms〜3 秒**である以上、30 秒は 10 倍以上の余裕である。
**分布に中間が無い以上、60 秒へ伸ばしても救われない。** #1038 が「測らずに待ち時間を延ばすだけ」を
禁じた判断は、本ラウンドの実測でも正しい。

### 決定 2: **2 つの fan-out クラスを同一コレクションへ入れ、`DisableParallelization` で直列化する**

`Messaging/FanOutTestCollection.cs` を置き、両クラスへ `[Collection(...)]` を付ける。

各クラスは **Testcontainers 2 つ（Postgres / RabbitMQ）と Wolverine ホスト 3 つ**を起こす。
2 クラスが重なる窓は 2 コアのランナー上で最も重い局面であり、**赤の 2 run はそこで落ち、
緑の 3 run では 20〜51 秒離れていた**。

🔴 **`IClassFixture` はコレクションに関係なくクラス単位のままである。**
コンテナは今までどおりクラスごとに別々であり、**ブローカを共有させてはいない**
（共有させればクラス跨ぎの競合コンシューマを自分で作り込むことになる ——
それは当のテストが検出しようとしている退行そのものである）。

### 決定 3: **予算切れの失敗へ「実際に購読しているキュー名」を載せる**

`ListenerReadiness.DescribeListeners` を足し、失敗メッセージへ
`rabbitmq` のリスナー Uri とその `Tracker` 状態を列挙する。

- キュー名が 2 本に分かれている → 前置は効いている。原因は配送／処理側
- キュー名が 1 本に潰れている → **競合コンシューマ化**（残る本命仮説）

**1 回の実走でこの 2 つが分かれる。** 現在の失敗メッセージは
「実処理側の遅さか受信そのものの欠落である」までしか言えず、**次に落ちても
同じ場所から仮説を建て直すことになる** —— 5 ラウンド繰り返した経路を閉じる。

診断は例外を投げない。採れなければ「採れなかった」と書いて返す ——
**診断が assert の失敗理由を覆い隠してはならない**し、黙って空にすると「購読ゼロ」と区別が付かない。

## 🔴 決定 2 の根拠には交絡がある。隠さずに書く

**落ちるテストは 30 秒居座るので、落ちれば重なりやすい**（逆向きの因果）。
本 IADR は**「重なりが原因である」とは主張しない。** 主張するのは次の 2 点である。

1. 重なりは**取り除ける**。副作用は実行時間だけで、**検査の強さは 1 ミリも落ちない** ——
   fan-out が本当に壊れていれば、直列化しても同じように落ちる（**症状を隠す変更ではない**）
2. 取り除いた後も落ちるなら、**「同時実行による混雑」を証拠つきで除外できる**

**どちらへ転んでも #1038 は前へ進む。** これが決定 2 を採る理由であり、
「たぶん直るから」ではない。

## 検討した代替案

| 案 | 採らない理由 |
| --- | --- |
| 予算を 60 秒へ伸ばす | 分布が二峰であり中間が無い。**伸ばしても救われない**（決定 1） |
| コンテナをアセンブリ共有（`AssemblyFixture`）にして混雑を根本から減らす | ブローカを共有させると **クラス跨ぎの競合コンシューマ**を作り込む。加えて 12 クラスの DB 分離前提が変わる。**Docker が無い環境では 1 件も実走できないまま入れる変更としては大きすぎる** |
| アセンブリ全体の `maxParallelThreads` を絞る | 効くかもしれないが、**全 77 件の実行時間へ一律に効く**。落ちている 2 クラスに限定した介入から始める |
| `TrackActivity()`（Wolverine の追跡セッション）へ載せ替える | 待ち合わせは決定的になるが、**本環境では 1 行も実走できない API へ丸ごと載せ替えることになる**。器の入れ替えは実測できる環境で行う |

## 結果

- 予算は 30 秒のまま。**PR の実行時間は変わらない**（統合テストは PR から外れている。IADR-0232）
- Integration の実行時間は、当該 2 クラスが他と重ならなくなる分だけ延びる（**見積 +40 秒程度**。
  ジョブ実測 7〜9 分 / `timeout-minutes: 30`）
- 🔴 **本 PR で #1038 は「直った」と言えない。** 本作業環境に Docker daemon が無く
  （Rancher Desktop の containerd。Testcontainers は Docker Engine API を要求する）、
  当該 2 件は `Skipped` になる（実測: `Knowledge.IntegrationTests` は 36 Passed / **41 Skipped** / 77）。
  **判定は `integration.yml` のマージ後の実走で行う**

## フォローアップ

- **同型で未発火のもの**（本 PR では触らない。走査済み）:
  `RawDocumentFetchedEdgeTests` / `WolverineBrokerEdgeTests` の `ReceiveTimeout = 60s`、
  `DocumentNormalizedSyncTests` の 500ms × 60 回。いずれも実測 5 run すべてで 2 秒前後の Passed であり、
  **発火していないものを予防的に触るのは「測らずに手を入れる」ことと同じである**
- 直列化しても落ちる場合、決定 3 の出力が競合コンシューマ化の有無を確定させる。
  そこで初めて `maxParallelThreads` かコンテナ共有かを選ぶ
