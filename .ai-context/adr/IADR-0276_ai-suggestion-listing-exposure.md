# IADR-0276: AI 提案は読み取り口だけを BFF へ出し、表示名はサーバ側で解決する（「すべて」はフィルタの解除として端点に持つ）

- 状態: Proposed
- 日付: 2026-08-23
- 決定者: claude（#918 / 親 #450）

## 起点・関連

- 関連する計画書 ID: FR-18（承認 UI は SC-03 主・SC-21 従／一括承認を提供しない／同一の一覧）・
  SC-21（主要素 6 件・入力/バリデーション・描いてはいけないもの）・SC-03（承認欄。**別 issue #452**）・
  UC-10 代替フロー（承認が確定するのは SC-03 経由のみ）・ADR-0033 決定 7・9・10・ADR-0034 決定 2
- 関連する実装仕様書: [`.ai-context/specs/20260823_issue-918_sc21-ai-suggestions.md`](../specs/20260823_issue-918_sc21-ai-suggestions.md)
- 先行する実装ADR: [IADR-0272](./IADR-0272_graph-write-action-authorization.md)（グラフの書き込みは read と write の 2 スコープ）／
  [IADR-0271](./IADR-0271_spa-stage4-client-foundations.md)（第 4 段の土台＝TanStack Table）／
  [IADR-0131](./IADR-0131_openapi-as-bff-contract-source.md)（OpenAPI が BFF 契約の単一情報源）／
  [IADR-0122](./IADR-0122_contract-schema-source-and-compat-gate.md)（契約の後方互換の判定）

## コンテキストと課題

#914 が AI 提案の永続と 3 状態遷移を、#915 が生成を実装した。しかし **BFF に提案の口が 1 本も無く**、
SPA からは提案を 1 件も見られない。SC-21（AI 提案一覧）を実装するにあたり、3 つの問いが立つ。

1. **BFF へ何を出すか。** GraphService には一覧・承認・却下・生成の 4 本がある。全部出すか、一覧だけか。
2. **一覧が描く「両端の文書名」をどこで解決するか。** 提案の DTO は ID しか持たない。
   SC-21 の列は「提案の内容（**両端の文書名**・辺の型、またはタグ名）」である。
3. **状態フィルタの「すべて」をどう表すか。** SC-21 の入力表は `pending`（既定）／`approved`／
   `rejected`／**すべて** の 4 値を要求するが、現行の一覧は 1 状態でしか絞れない。

## 検討した選択肢

### 問い 1（BFF へ出す範囲）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 一覧・承認・却下を BFF へ出す | SC-03 の承認欄（#452）が来たとき手戻りは無い。**しかし消費者の無い書き込み口が先に公開面へ出る** |
| **B（採用）** | **一覧（読み取り）だけを出す** | SC-21 は書き込みを一切しない画面である。承認の口は承認欄と同じ変更単位で開ける |
| C | 何も出さず、SC-03 の実装まで SC-21 を保留する | 一覧は棚卸しとして単独で価値があり、保留の理由にならない |

### 問い 2（表示名の解決）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | クライアントが行ごとに文書 1 件を照会する | 行数 ×（1〜2）往復。可視性判定も同数走る |
| **B（採用）** | **一覧の応答へ両端の文書名を載せる**（既定値つきの追加） | 一覧は可視性判定のため既に両端の複製を読んでいる。**照会が 1 件も増えない** |
| C | 文書名を出さず ID を描く | SC-21 主要素 1 を満たさない（識別子は棚卸しの判断材料にならない） |

**辺の型名だけは B を採らない。** ADR-0033 決定 9 が「表示名は辞書側で解決し、改名に追随させる」と
定めており、DTO へ焼き込むと改名後も一覧だけ古い名前を出し続ける。SC-18 が既にカタログで解決している。

### 問い 3（「すべて」の表し方）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | クライアントが 3 状態を 3 回引いて連結する | 並び順が状態ごとに分断される。可視性判定が 3 回走る。1 回だけ失敗した中途半端な状態が生まれる |
| **B（採用）** | **端点が `state=all` を「絞りの解除」として受ける** | 1 往復。並び順は 1 本のまま |
| C | `SuggestionState` の値集合へ `all` を足す | **永続層に `all` という状態を書ける形になる**。状態機械が壊れる |

## 決定

### 決定 1: BFF へ出すのは提案の**読み取り口 1 本だけ**とする

`GET /bff/graph/suggestions?state=&kind=` を足し、**承認・却下・生成の口は開けない。**

- SC-21 は「本画面では実行しない」と明記された**書き込みを一切しない画面**である。
- 承認の主導線は SC-03 であり、その承認欄は #452 の射程である。
  **消費者の無い書き込み口を先に開けると、IADR-0272 の write 認可の境界が測られないまま公開面へ出る。**
  「後段で効いているから BFF 経由でも効く」は測った証拠にならない（#952 → #962 の教訓）。
  境界のテストは承認欄と同じ変更単位に置くのが正しい。
- 🔴 **一括承認の口はどの層にも作らない**（FR-18・SC-21「描いてはいけないもの」）。
  不在は BFF のルート表走査（メソッドが GET だけであること）で機械的に固定する。

### 決定 2: 一覧の応答は**両端の文書名**を運び、**辺の型名は運ばない**

`AiSuggestionDto` へ `SourceDocumentTitle` / `TargetDocumentTitle` を**既定値つきで**足す
（既定値の無いメンバー追加は破壊的変更。IADR-0122 決定 2）。

- 名前を出すのは **`ResolveEndpointsAsync` の 1 か所だけ**とし、**不可視のときは名前を返さない**
  （空文字・null のまま）。可視性判定を通っていない名前を戻り値へ載せると、
  呼び出し側の書き間違い 1 つで文書名が漏れる形になる。
- タグ提案は終点を持たないので終点名は **null** である（空文字にしない。
  「名前の無い文書がある」と読めてしまう）。
- **辺の型名は入れない。** 辞書（`/bff/graph/edge-types`）でクライアントが解決する（ADR-0033 決定 9）。

### 決定 3: 「すべて」は**状態の値ではなくフィルタの解除**として端点が持つ

`AiSuggestionEndpoints.AnyState = "all"` を端点側の定数として置き、`SuggestionState.IsValid` には
入れない。`state=all` のときだけ状態の絞りを外す。

- **値域の検査は生かしたまま**である（未知の値は従来どおり 400）。
- 「`all` が永続化できる状態ではない」ことをテストで固定する
  （`SuggestionState.IsValid("all") == false`）。

### 決定 4: 絞り込みの単一情報源は URL とし、クライアント状態を持ち込まない

`/ai-suggestions?state=&kind=`。SC-18（IADR-0124・IADR-0126 決定 3）と同じ作法である。
`state` の既定は `pending`（URL に無くても pending）、`kind` の既定は `all`（URL から省く）。
未知の値は既定へ縮退させ、画面にエラー状態を持ち込まない（防壁はサーバの 400 に在る）。

**BFF は既定値を補わない。** 補うと既定値の情報源が BFF と GraphService の 2 か所に生まれる。

### 決定 5: 種類フィルタは**同じ一覧の絞り込み**であり、ルートを分けない

計画は「同じ一覧にタブまたはフィルタで同居させる」と択一を認めている。**選択（`<select>`）を採る** ——
計画の入力/バリデーション表が両フィルタとも「選択」と定めており、モックアップのタブ表現は
同じ意味を別の見た目で描いたものである。

🔴 **退行（種類ごとに画面を割る）は描画の検査では捕まらない**（別ルートは別テストになるだけである）。
**ルート表を走査して「`/ai-suggestions` ただ 1 本」であることを固定する。**

## 理由

- 決定 1 は「**公開面は消費者と同時に開ける**」という一般則の適用である。口だけ先に開けると、
  境界のテストが後追いになり、その間は誰も測っていない書き込み経路が残る。
- 決定 2 の「名前を出すのは 1 か所だけ」は、秘匿の破れを**構造で**塞ぐためである。
  可視性判定と名前の取得を別の場所に置くと、片方だけを呼ぶ経路がいずれ生まれる。
- 決定 3 は「**表示の都合を永続層の語彙へ持ち込まない**」ためである。`all` は利用者の意図
  （絞らない）であって、提案が取り得る状態ではない。

## 結果

- 良い影響:
  - SC-21 が単独で成立する（承認欄が来る前でも棚卸しの用途を満たす）。
  - 一覧の応答が 1 往復で描画に足りる形になり、行数に比例した照会が発生しない。
  - 「一括承認が無い」ことが**画面・公開 API の 2 層で機械的に固定**された。
- 悪い影響・トレードオフ:
  - 🔴 **導線の先（SC-03 の承認欄）がまだ無い。** 遷移はできるが承認はできない。
    画面の説明文と画面仕様書で明示するが、**説明を読まない利用者には不親切な状態が続く**。
    解消は #452 に依存する。
  - 承認の口を開ける #452 は BFF・OpenAPI・生成物へ再度触ることになる（決定 1 が選んだ代償）。
  - 契約スナップショットと OpenAPI の両方を更新する手間が増える（決定 2 の代償）。
- フォローアップ:
  1. 🔴 **タグ提案の値域強制が無い**（言語モデルが返した値をそのまま保存する）。辞書は文書サービス側で
     管理者・運用者限定のため、画面でも GraphService でも現状は引けない。**別 issue で扱う。**
     本 IADR では決めない —— サービス間依存と認可主体の決め方は生成側の判断であり、
     計画側の裁定を要する可能性がある。
  2. **再提示理由の発火が未配線**（#911 と ADR-0050 待ち）。表示側の契約だけが先に在る。
  3. **一覧の既定の並び順**が計画側で未確定である。確定したらサーバ側の並びを合わせる。
