# IADR-0278: `doc_scope` の不変性の実効化

- 状態: Proposed
- 日付: 2026-08-23
- 決定者: claude（planning#472 の裁定 = 計画 ADR-0058 への追随）

## 起点・関連

- 計画 `ADR-0058`（planning#472 の裁定。2026-08-23 Accepted）
  - **決定 1**: `doc_scope` は作成時に確定し、以後変更できない
  - **決定 2**: 更新経路は**既存値と異なる `doc_scope` を含む更新を拒否する**
  - **決定 3**: SC-05 の属性編集フォームで `doc_scope` を編集不可とする（サーバ側と併せた二層）
- 計画 `ADR-0054` 決定 5（既存文書へ遡及付与しない）・`IADR-0270` 決定 2（値域検証）

## コンテキスト

実装は作成経路（`POST /documents`）を「台帳を持たない個人資料ができると容量算入（FR-19）から
漏れる」という理由で塞いでいたが、**更新経路（`PUT /documents/{id}` と
`PATCH /documents/{id}/metadata`）は値域（2 値）しか見ておらず、同じ結果を作れた。**

## 決定

**決定 1: 判定は「既存値との一致」で行う。存在では弾かない。**

🔴 **「`doc_scope` を含む更新を拒否」と実装してはならない。** SC-05 の属性編集フォームは
既存属性をスプレッドして送る（`DocumentForm.tsx`）ため、**機密区分だけを変える通常の保存でも
`doc_scope` が同送される**。存在で弾くと SC-05 の保存が全部壊れる。

**決定 2: 属性は全置換であるため、次の 3 つをすべて「変更」に数える。**

| 形 | 起きること |
| --- | --- |
| 値を変える（`organization → private-note`） | 台帳・容量・ライフサイクルを持たない個人資料ができる |
| **既存値を削除する** | 集合帰属の判定（`== private-note`）で、個人資料が**組織文書へ化ける** |
| **後から新規付与する** | 「作成時に確定する」（計画 `ADR-0058` 決定 1）に反する |

**「既存値と一致しないものはすべて拒否する」という 1 本の規則で 3 つとも閉じる。**
`ScopeOrNull` で「未設定」を `null` に正規化し、`null` 同士の一致も許す
（`doc_scope` を持たない既存文書の更新は従来どおり通る —— 計画 `ADR-0054` 決定 5 と衝突させない）。

**決定 3: 判定は `DocumentAttributes` に置き、2 つの更新経路が同じ 1 つを呼ぶ。**
値域検証（`ValidateDocScope`）とは**別の関数**にする —— あちらは「知らない値か」を、
こちらは「作成時に確定した値から動いたか」を見るのであり、**必要とする入力が違う**
（後者は既存文書が要るため、取得の後に呼ぶ）。

**決定 4: 計画 `ADR-0058` 決定 3（SC-05 で編集不可）は、実測で既に満たされている。新しい UI を作らない。**
属性編集フォームは `doc_scope` の入力欄を持たず、既存値をスプレッドで素通しするだけである。
**回帰テストで固定するに留める**（入力欄を足すか、属性を落とすかのどちらでも赤くなる）。

## 理由

- **決定 1 を明示するのは、素朴な実装が SC-05 を壊すからである。** 「不変なのだから送ってくるな」は
  一見正しく見えるが、**送り手は全置換の契約に従って全属性を送っている**。壊れ方は
  「機密区分が変えられない」という無関係な形で現れ、原因にたどり着きにくい。
- **決定 2 の「削除」を含めるのは、集合帰属で判定しているからである。** `IsPrivateNote` は
  `== private-note` で判定する（否定形で書くと属性を持たない既存文書が一斉に該当するため）。
  この向きでは**キーを落とすことが値を変えることと同じ結果**になる。
- **決定 4 で UI を作らないのは、過剰実装だからである。** 「編集不可にする」は
  「編集できる状態を編集不可へ変える」ことではなく、「編集できる状態を作らない」ことで満たせる。

## 結果

- **良い影響**: 作成経路だけが塞がれていた非対称が閉じた。遷移の意味論を定めずに済む。
- **悪い影響 / トレードオフ**:
  - **誤った `doc_scope` で作成した文書を後から直せない。** 作り直しになる（計画 `ADR-0058` §結果 が
    明記したトレードオフであり、実装が増やしたものではない）。
  - **拒否の文言が「作り直せ」としか言えない。** 移行の導線は無い。
- **フォローアップ**:
  1. **既存データに「台帳を持たない `private-note` 文書」が無いかを確認する**（計画 `ADR-0058`
     §結果 フォローアップ 1）。**稼働 DB が要るため本 PR では実施できない。** issue で追跡する。

## 検証

- 追加: `DocScopeImmutabilityTests`（陰性 4 ＝ 値変更・メタデータ経路・削除・新規付与 /
  陽性対照 3 ＝ 同値の同送・未設定文書の更新・メタデータ経路の同送 / 値域検証の残存 1）
- 追加: `DocumentManagementPage.test.tsx` へ決定 4 の回帰（入力欄が無い ＋ 既存値を同じ値で送り返す）
- **変異試験**（1 変異ずつ独立に実施）:
  - **「存在すれば拒否」へ変える（＝決定 1 が禁じた実装）** → **陽性対照 3 件が赤**
  - `PATCH` 経路の検査だけを外す（元の欠陥の再現）→ **陰性 1 件が赤**
  - SC-05 のフォームから `doc_scope` だけを落とす → **追加した回帰 1 件が赤**（他は緑のまま）
