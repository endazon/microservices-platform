# IADR-0357: 検索傾向の出現件数しきい値の運び方

- 状態: Accepted
- 日付: 2026-09-03
- 決定者: 実装（#1197）

## 起点・関連

- 関連する計画書 ID: FR-10 / UC-05 / SC-10 / ADR-0006 / ADR-0031 / ADR-0068 / ADR-0071
- 関連する実装仕様書: `.ai-context/specs/20260903_issue-1197_search-trend-min-count.md`
- 先行: `IADR-0343`（利用イベントの発火側。**決定 6 の 1 が本件を受容せず環流した**）／
  `IADR-0353`（陳腐化文書数のしきい値運搬。**本 IADR はその形をなぞる**）

## コンテキストと課題

`ADR-0071`（Accepted・2026-09-03）が確定させたのは 4 点である —— **出現件数 3 件未満の語は出さず
落とす／画面に現在のしきい値を併記する／正規化は現状追認／ハッシュ化は採らない。**

裁定の決め手は指標の意味ではなく**射程の穴**にあった。計画の言葉では

> 計画には一貫した原則が既にある —— 「誰が・いつ・何件」までは残してよいが、
> 内容（タイトル・本文・**検索語**）は出さない。**本件は新しい原則を作る話ではなく、
> その原則の射程が画面に届いていなかった**話である。

実装に持ち帰ると、決めることが 3 つ残る。**(1) しきい値をどの器で運ぶか**、
**(2) `GET /dashboard/trends` は配列を返したままでよいか**、**(3) 画面もふるうべきか**である。

## 決定

### 決定 1: 集計は下限の述語を `Take(top)` の**前**に置く

`AggregateTrendsAsync` に `minCount` を足し、`GroupBy` → `Select` の直後に
`Where(t => t.Count >= minCount)` を置く。

🔴 **`Take(top)` の後に置いてはならない。** 後に置くと、上位 `top` 件に紛れ込んだ低件数語を
落とした結果として**返る件数が `top` より減る** —— 伏せた分だけ枠が空いたままになり、
本来出るはずだった語が押し出される。

**「その他 M 件」の集約行は作らない**（`ADR-0071` 決定 1）。M 自体が推測の材料であり、
とくに「その他 1 件」は「1 回だけ検索された語が 1 つある」と等価で、伏せた意味がほとんど残らない。

### 決定 2: しきい値は**封筒 DTO**（`DashboardUsageDto` / `DashboardSummaryDto`）が運ぶ

🔴 **`SearchTrendDto` の行に持たせない。** 行は**しきい値で伏せた結果として 0 件になり得る**。
0 件はしきい値の効果が最も強く出ている状態であり、**そこで併記が消えるのは本末転倒**である。
`IADR-0353` 決定 4 が観測値の行について書いたのと同じ理由が、ここでは一段強く効く
（あちらは「件数 0 のとき行が無い」、こちらは**しきい値そのものが行を消している**）。

**`GET /dashboard/trends` は配列を返したままにする。**

| 案 | 帰結 | 判断 |
| --- | --- | --- |
| **A. 配列のまま。しきい値は封筒だけが持つ** | 契約が**非破壊**。画面が読む経路（`/bff/dashboard/summary`）は完全に満たす | **採用** |
| B. `DashboardTrendsDto { minCount, terms[] }` へ包む | 応答の**形が変わる（破壊的）**。`contract-breaking-allowlist.json` の承認が要る（`IADR-0122` 決定 3） | 却下 |
| C. 各行に持たせる | 上記のとおり 0 件で消える | 却下 |

**A を採った根拠**: `ADR-0071` §結果 は契約追加先を「`DashboardSummaryDto` / `GET /dashboard/trends`」と
括弧書きするが、**受け入れ基準が同梱を求めているのは `/dashboard/summary` と
`/bff/dashboard/summary` の 2 段だけ**である。走査したところ **`/dashboard/trends` の呼び出し元は
テスト以外に 0 件**（BFF は `/dashboard/summary` だけを呼ぶ）で、**受け入れ基準が求めていない破壊を
承認で通すのは割に合わない**。**ふるい落とし自体は `/dashboard/trends` にも等しく効く。**

**残るもの**: `/dashboard/trends` を直接叩く運用者はしきい値を知れない。
`ADR-0071` 決定 2 の射程は画面であり、そこは満たしている。

### 決定 3: 契約の追加は**既定値つき**。既定 0 の向きが安全側である

`int SearchTermMinCount = 0` を両封筒の末尾へ足す。

- **既定値が要る**のは検査器の都合である ——「既定値の無いメンバーの追加」は
  `check-contract-schema.js` が**破壊的**に分類する（`IADR-0122` 決定 2）。実測でも
  破壊的 0 / 非破壊 2 として通った。
- 🔴 **0 という値の向きに意味がある。** 本項目を返さない旧 `DashboardService` が後段に居る
  ローリング更新の最中は、BFF の逆直列化が 0 を入れ、**画面のふるいは素通り**になる。
  既定を 3 にすると逆に、**しきい値を知らない応答から画面が勝手に語を消す**。
  「知らないものを消す」より「知らないものを通す」が安全側である —— 前者は
  **後段が古いという事実を、消えた語という形で隠す。**
- **BFF は既定値を補わない。** 補うと、後段が実際にふるった値と画面の表示が食い違い、
  **見えている語と併記された数字が矛盾する。**

🔴 **［2026-09-03 追記 / #1197］「既定 0 が安全側」は、項目が 0 として届くときにしか成り立たない。**

稼働 k3s で実測したところ、**しきい値を知らない旧 BFF は 0 を返さず、JSON から項目ごと落とした**
（`searchTermMinCount = undefined`）。生成型は `number` と言っているので TypeScript は何も言わない。
そして **`count >= undefined` は全件 false** である —— 素で使うと、
**取りこぼしを止めるはずの画面のふるいが一覧を丸ごと空にする。**
「知らないものを消す」向きであり、本決定がいちばん避けたかった側そのものである。

したがって画面は **`Number.isFinite(minCount)` でなければ 0 へ倒し**、ふるわず、
**下限も名乗らない**（「0 件以上の語のみを表示します」は何も言っていないうえ、
しきい値が効いているかのように読める）。**この穴は単体テストでは見つからなかった** ——
スタブが常に契約どおりの形を返していたためである。**実配備の 2 版混在が見せた。**

### 決定 4: 不正な構成は既定へ倒す。**報告する値も倒した後の値**

`SearchTrendOptions`（`SectionName = "SearchTrend"` / `DefaultMinimumCount = 3`）を新設し、
`SearchTrend:MinimumCount`（環境変数 `SearchTrend__MinimumCount`）で上書きする。
`appsettings.json` に既定を明記する。

- 🔴 **`ValidateOnStart` を付けない。** 秘匿パラメータの打ち間違いで、**利用イベントの記録
  （`POST /dashboard/events`）まで巻き添えに止める**のは割に合わない。`KnowledgeHealthOptions`
  （`IADR-0353` 決定 3）が fail-open を選んだのと同じ向きである。
- **0 以下は既定へ倒し、警告ログを残す。** そして 🔴 **応答へ添えるしきい値も倒した後の値にする** ——
  倒したのに構成値をそのまま返すと、**見える語（3 件以上）と表示された数字（0）が食い違う**。
  静かに壊れないための要点はここである。
- 境界は **「ちょうどは出す」**（`>=`）。`ADR-0071` 決定 1 は「3 件**未満**の語」を伏せると書いている。

**`Program.cs` で `Configure` するだけにし、`deploy/helm` へ `extraEnv` を足さない** ——
前例（`IADR-0353`）が置いておらず、既定は `appsettings.json` にある。必要になった配備で足す。

### 決定 5: 画面（SC-10）でも同じ下限でふるう

🔴 **後段が既にふるっているが、画面でも `count >= minCount` でふるう。**

`ADR-0071` §結果 が要求した検査は「**しきい値未満の語を含むサマリを返すスタブ**を渡して、
その語が表にも棒グラフにも現れない」ことである。**画面が素通しなら、この検査は書けない。**
そして書けないということは、**後段の取りこぼしがそのまま運用者へ出る**ということでもある。
`IADR-0044` の多層防御（BFF と後段の双方でロールを要求する）と同じ向きで、
**片側だけの統制は「迂回で通る」か「画面だけが壊れる」のどちらかを生む。**

- ふるいは**表と棒グラフの手前 1 箇所**（`SearchTrendTable` の入口）で行う。
  2 箇所に置くと片方が腐り、**表と図で見えるものが食い違う**。
- **併記は一覧が空でも消さない。** 0 件は下限の効果が最も強く出た状態であり、
  そこで数字が消えると「なぜ空なのか」が読めなくなる。
- **画面は自前の既定を持たない。** 併記する値は契約が運んだものだけである
  （テストは契約に 7 を返させて、7 と出ることで焼き込みを排除する）。

### 決定 6: 図の検査は `echartsLoader` をモックして **option そのもの**を見る

「棒グラフにも出ない」を器のテキストで確かめてはならない。**jsdom には canvas も実 SVG 描画も無く、
`EChart` の器は常に空**である —— 何を渡しても緑になり、**検査になっていない**。
`echartsLoader` にモックを当て、`setOption` へ渡った option を JSON 化して見る
（`EChart.test.tsx` / `GraphCanvas.test.tsx` と同じ構図）。

## 実測（変異試験）

**集計側** —— `AggregateTrendsAsync` から `.Where(t => t.Count >= minCount)` を外すと
**5 本が落ちた**（`Trends_BelowMinimumCount_AreOmitted` /
`Trends_OmittedTerms_AreNotAggregatedIntoAnOtherRow` / `Trends_MinimumCount_IsConfigurable` /
`Summary_InvalidMinimumCount_FallsBackToDefault` の 2 パラメータ）。
🔴 **境界の陽性テスト（`Trends_AtMinimumCount_AreIncluded`）は緑のまま通った** ——
陰性を対で置かなければ検査にならないことの実測である。述語を戻して 45/45 緑、`MUTATION` 残渣 0。

**画面側** —— `terms.filter(...)` を `terms` にすると
`omits terms below the threshold from both the table and the chart` と
`says there is no trend yet when every term is below the threshold` の **2 本が落ちた**。
戻して 24/24 緑、残渣 0。

## 実測（稼働 k3s。2026-09-03）

`dashboard-service` のイメージだけを差し替えた（`issue1186` → `issue1197`）。
🔴 **`bff-service` は差し替えていない** —— 当時 `bff:issue1199` が別セッションによって
**1 分前に焼かれており**、差し替えるとその実測を壊す。**壊さずに測れる**と判断した:
`topSearchTerms` のふるい落としは `DashboardService` が行い、BFF は素通しするため、
**陰性・陽性は旧 BFF のままでも観測できる**（下の 1）。

**1. 既定 3。陰性と陽性**（`GET /bff/dashboard/summary?top=50`。3 回の語と 2 回の語を投入）

```
searchTermMinCount = undefined      ← 旧 BFF は項目を落とす（決定 3 の追記の出所）
本 run の語: [{"term":"msp1197-pos-run1","count":3}]
その他 / その他 M 件 に相当する行: []
返った語の総数: 1 / 件数の最小値: 3
```

**2 回の語（`msp1197-neg-run1`）は 1 度も現れない。**「その他」の行も無い。
同じ時点の `GET /dashboard/summary?top=50` は `searchTermMinCount = 3` を返した。

**2. 配備時の構成で変わる**（`kubectl set env SearchTrend__MinimumCount=5`。4 回の語と 5 回の語を投入）

```
searchTermMinCount = 5
本 run の語: [{"term":"msp1197-five-cfg5","count":5}]
前回 run（3 回の語）が残っていないか: []
返った語の総数: 1 / 件数の最小値: 5
```

🔴 **4 回の語が落ちただけでなく、しきい値 3 のときは見えていた `msp1197-pos-run1`（3 回）も消えた。**
構成が実際に判定を動かしている（「たまたま出なかった」ではない）ことの対照である。

**3. 不正な構成（`SearchTrend__MinimumCount=0`）**

```
searchTermMinCount = 3
返った語: [{"five-cfg5":5},{"four-cfg5":4},{"pos-run1":3}]
```

```
warn: DashboardService.Features.Dashboard.Summary.DashboardSummaryEndpoint[0]
      検索傾向の最小件数の構成が不正である（0 件）。既定の 3 件へ倒した。構成キーは SearchTrend:MinimumCount である。
```

**起動は落ちず、既定 3 へ倒し、応答へ添えた値も 3 で、実際に 3 でふるっている**
（2 回の語は依然として出ない）。**構成値 0 をそのまま返していたら画面が嘘をつく**という
決定 4 の要点が、そのまま観測できた。

**4. 総件数はしきい値の影響を受けない**（規定どおり）

既定へ戻した後の応答は `"totalSearches":16` に対して `topSearchTerms` は 3 語（5+4+3 = 12）である。
**差の 2 は伏せた語の分**であり、**伏せているのは語であって件数ではない**ことが数で確かめられる。

## やらなかったこと

- **ハッシュ化**（`ADR-0071` 決定 4）。読めない語は「検索傾向」として成立しない。
- **全角半角・かなの正規化**（決定 3 が「本 ADR では定めない」とした）。
- **`RecordEvent/Endpoint.cs` の `Normalize` の変更。** 決定 3 は**現状の追認**であり、
  環流 planning#514 が推奨した「小文字化まで畳まない」は**採らないと確定した** ——
  畳まないと同じ語が分散して**伏せられる語が増える**だけで、秘匿は強くならない。
- **「その他 M 件」の集約行**（決定 1 が名指しで禁じた）。

## 残るもの

- 🔴 **下限は「何人が探したか」を保証しない**（`ADR-0071` 実測 4）。数えているのはイベント件数であり、
  1 人が 3 回検索すれば通過する。**受け入れたトレードオフ**である —— 一意性で引くには利用者識別子が要り、
  それは #1198（`ADR-0072`）が落とす方向のものである。
- **既定値 3 の妥当性は運用開始後に見直す余地がある。** 利用者数が少ない期間は、
  3 件でも同一人物の反復である可能性が高い。
- **`/dashboard/trends` はしきい値を運ばない**（決定 2）。直接叩く運用者は下限を知れない。
