## コンテキストと課題

計画 ADR-0128 は、LLM ゲートウェイを自前で維持し、次のいずれかが成立したら OSS ゲートウェイとの併用を再評価すると定めた。

1. 有効な生成プロバイダが 4 つ以上になる、または Claude 以外を常用するようになる。
2. 運用者向けの UI が計画に入る。
3. ゲートウェイの共有範囲が変わる。

同 ADR 決定 3 は、条件の成立を確かめる手段を「無い」とし、暫定手段（計画側が新しい送信先・UI・共有範囲を計画へ足すときに照らす）を置いた。そのうえで、実装側の棚卸し（`backlog-audit.yml` / `scripts/backlog-audit.js`）で確かめるかを実装に委ねた。

実測（`c63351de`）:

| # | 事実 |
| --- | --- |
| 1 | 棚卸しの 7 節（Proposed の IADR・動いていない作業仕様書・動いていない文書・写像後回しのテスト・blocked issue・ci-failure issue・古い PR）は、**どれも「止まっているもの」の列挙**である。設定の状態を判断条件と照らす節は無い |
| 2 | 生成の有効エンドポイントは `claude-managed` の 1 つ（`copilot-managed`・`selfhosted-oss` は `Enabled=false`）。deploy 配下に `Llm__Routing__*` の上書きは 0 件 |

## 決定

### 決定 1: 3 条件はいずれも棚卸しで機械的に確かめない。報告だけの行も足さない

- **条件 1** は、リポジトリから数えられるのが既定値だけで、実環境の有効化（環境変数・Secret）と「常用」は判らない。報告行は「条件は成立していない」を週次で出し続け、確かめていないことを確かめたように見せる。
- **条件 2・3** は計画の文書側の事象であり、本リポジトリから機械で確かめる手段が無い。
- 棚卸しは「止まっているもの」の列挙に保つ（実測 1）。判断条件の照合を混ぜない。
- 同型の事故（条件が成立していたのに再評価されなかった）は 0 件である（実測 4）。CLAUDE.md の規則に従い、検査器も報告行も足さない。

### 決定 2: 代わりの手当て

1. **計画側**: ADR-0128 決定 3 の暫定手段（新しい送信先・運用 UI・共有範囲の変更を計画へ足すときに ADR-0128 と照らす）。
2. **実装側**: 生成エンドポイントの定義を説明する機能仕様書（`docs/functional/FR-11_llm-egress-routing.md` §エンドポイント定義）に、「生成のエンドポイントを足す・有効にする、または新しい種類のアダプタを足すときは、OSS ゲートウェイ併用の見直し条件（計画）と照らし、成立するなら計画へ再評価を依頼する」を書く。条件 1 が動くのはこの節が説明する設定かアダプタを変える PR だけであり（実測 2・3）、変更点の文書が照合の場所になる。表示テキストに計画 ID は書かず、trace ブロックへ入れる。

### 決定 3: 機械化へ倒す条件

次のいずれかで、棚卸しへの報告行（または検査器）を改めて検討する。

- 見直し条件の成立を見落とした事故が **2 回**起きる（CLAUDE.md の規則）。
- 生成エンドポイントの有効化が、リポジトリの外（環境変数・Secret）ではなく設定ファイルで管理されるようになり、リポジトリから数えた値が実環境を表すようになる。

## 結果

- 良い影響: 棚卸しの性格（滞留の列挙）と、事故ベースで検査器を足す規則を保つ。週次で誤った安心を出さない。
- 悪い影響: 条件の成立は人（計画側の起案者と、実装側で設定・アダプタを変える PR の書き手）の照合に依る。ADR-0128 決定 3 の「現在の実現手段: 無い」は、実装側でも機械の手段としては無いままである。
- フォローアップ: なし（決定 3 の条件が成立したら起票する）。
