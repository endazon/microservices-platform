# IADR-0296: 削除はオブジェクトストレージの実体まで及ぶ

- 状態: Accepted
- 日付: 2026-08-28
- 決定者: 実装（#451）

## 起点・関連

- 関連する計画書 ID: FR-06 / FR-12 / FR-19 / FR-21 / UC-03 / UC-11 / SC-19 / ADR-0014 / ADR-0015 / ADR-0054 / ADR-0057
- 関連する実装仕様書: `.ai-context/specs/20260828_issue-451_deletion-propagation-to-object-storage.md`
- 先行: `.ai-context/specs/20260828_issue-1016_delete-propagation.md`（ADR-0057 の②索引・グラフ分）

## コンテキストと課題

計画 ADR-0057 決定 1 は完全削除の伝播範囲を「①オブジェクトストレージの本文・資産
②ベクトルストア ③監査・法務目的の残余を置かない」へ格上げした。②は先行 PR が実装済みで、
**①だけが残っていた。** 着手前の実測で、①が満たせない理由は 4 つあった。

1. **`IObjectStorageClient` に削除の口が無い**（6 メンバ。保存・取得・解決可否・署名 URL のみ）。
2. **削除の入口 3 つ**（FR-06 文書削除 / FR-19 完全削除 / 90 日自動物理削除）は
   いずれも DB 行を消してイベントを出すだけである。
3. 🔴 **`ObjectStorageOptions.EnableVersioning` の既定が `true`** で、起動時に
   `VersionStatus.Enabled` を掛ける。**素の `DeleteObject` は delete marker を書くだけ**であり、
   仮に削除の口を足しても過去の全版が残る。**これは本作業まで未記録の欠陥だった。**
4. 🔴 **`DocumentNormalized.AssetUris` が DocumentService に永続化されていない。**
   イベントは資産 URI を運んでいたが、`DocumentNormalizedConsumer` が
   `Document.CreateNormalized` / `ApplyNormalized` へ渡しておらず、`Document` に欄も無かった。
   **図表資産は台帳から辿れず、削除が構造的に届かなかった。**

加えて、オブジェクトキーの体系が経路ごとに違う（`documents/{id:D}/body.md` ／
`{id:N}/document.md` ／ `{id:N}/assets/{figureId}{ext}` ／ `{sourceId}/{fetchId}/raw{ext}`）ため、
**前方一致の一括削除で「この文書のオブジェクト」を表せない。**

## 検討した選択肢

| 論点 | 案 A | 案 B | 採否 |
| --- | --- | --- | --- |
| 削除の口 | `DeleteAsync(uri)`（全版削除を契約に書く） | `DeleteAsync(uri, allVersions: bool)` | **A**。呼び出し側に「残してよい版」という選択肢を与えない —— ADR-0057 の基準は「残っていない」であり、真偽の分かれる引数は誤用の口になる |
| 消し方 | 版を列挙して 1 つずつ | `DeleteObjects`（一括） | **A**。一括 API は 1000 件上限とページングの都合が版列挙と二重になり、MinIO 実装差の影響も受けやすい。1 オブジェクトの版数は高々数十で、性能上の理由が無い |
| 資産の在り処 | `Document.AssetUris`（jsonb） | `DocumentVersion` にも版ごとに持つ | **A**。IADR-0290 が版応答から本文参照を落とした直後であり、「その版の資産」と読まれる欄を版スナップショットへ足さない |
| 対象範囲 | 本文＋版スナップショット＋資産 | ＋ `OriginalUri` | **A**。§決定 2 |
| 順序 | オブジェクト → DB 行 | DB 行 → オブジェクト | **A**。§決定 3 |
| 失敗時 | fail-closed（対話）／文書ごとに隔離（定期） | 一律 fail-open | **A**。§決定 3 |

## 決定

### 決定 1: `IObjectStorageClient.DeleteAsync` は**全バージョンを消す**契約とする

`S3ObjectStorageClient` は `ListVersionsAsync` で版を列挙し、各 `VersionId` を
`DeleteObjectRequest` で消す。SDK API は **AWSSDK.S3 4.0.100.2 をリフレクションで実測**して確定した。

- **delete marker も版として消す。** .NET SDK は marker を別リストにせず
  `ListVersionsResponse.Versions` へ混ぜて返す（`S3ObjectVersion.IsDeleteMarker` で区別。
  同応答に `DeleteMarkers` プロパティは**存在しない**ことを実測で確認）。marker を残せば
  オブジェクトは「削除済みの版」として残り続ける。
- **`Prefix` は前方一致なので `Key` の厳密一致で絞る**（`body.md` の削除で `body.md.bak` を巻き込まない）。
- **`IsTruncated` の間は marker で辿る**（1 応答は既定 1000 件まで）。
- **列挙が 0 件でも versionId 無しの削除を 1 回撃つ**（バージョニング無効のバケット・
  未バージョン化オブジェクトの取りこぼしを塞ぐ。冪等なので害が無い）。

🔴 **`NullObjectStorageClient` は `Put*` と同じ作法（警告して成功）にする。** 例外にすると、
ストレージ未構成の dev/test で完全削除が 500 になる。**未構成環境では本文がそもそも
永続化されていない**（`Put*` は URI を返すだけ）ので、削除としては成功が正しい。
`Get*` が例外なのは「無い本文を返せない」からであり、向きが逆である。

### 決定 2: 台帳から逆引きする。`OriginalUri` は対象に含めない

`DocumentObjectPurger` が集めるのは 3 つ ——
①`Document.MarkdownUri` ②`Document.AssetUris` ③**全 `DocumentVersion.MarkdownUri`**。

③が要るのは、本文のキーが経路の切り替え（取り込み `{id:N}/document.md` → 本文直接受け入れ
`documents/{id:D}/body.md`）で**変わり得る**ためである。現行行だけを見ると、過去に指していた
本文を取りこぼす。`storage://` でない値（外部 URL 等）は選別して除く。

**参照カウントは持たない。** 実測の根拠は「1 文書 1 オブジェクト」ではなく
**削除対象の鍵空間が文書 ID で分割されていること**である —— 上の 3 経路のキーはいずれも
文書 ID を含み、2 つの文書が同じオブジェクトを指すことが構造上起こらない。

🔴 **唯一、共有が起こり得るのは `Document.OriginalUri` である。** これは API 要求
（`req.OriginalUri`）からしか入らず（取り込み経路 `CreateNormalized` は設定しない）、
`storage://` を指す場合その実体は DataSourceService が `{sourceId}/{fetchId}/raw{ext}` で書いた
**別サービス所有の原本**であり得る。本サービスの台帳は原本の参照数を知らないため、消すと
DB per Service の境界を越えて他サービスのデータを壊す。**この除外が、参照カウントを
持たずに済ませる条件そのものである。**

### 決定 3: **オブジェクトを先に消す。** 失敗時は fail-closed（対話）／文書ごとに隔離（定期）

2 つの壊れ方を比べた。

| 壊れ方 | 何が起きるか | 検知可能性 | 回復可能性 |
| --- | --- | --- | --- |
| **DB 行が先・オブジェクト削除が失敗** | 台帳が消え実体だけが残る。**その実体を指す値がもうどこにも無い** | 🔴 不能（棚卸しでも見つからない） | 🔴 不能（永久の不可視な残留） |
| **オブジェクトが先・DB コミットが失敗** | 文書行は残り本文が引けない | ✅ 画面が縮退表示になる | ✅ 再削除で解消（削除は冪等） |

**「消したのに残っている」ほうが悪い。** SC-19 は「いかなる方法でも復元できません」と
言い切る画面であり、不可視な残留はその宣言を**嘘にしたうえで、嘘であることを誰にも
観測させない**。よって **オブジェクト削除 → DB 行削除 → イベント発行** に固定する。

- **対話操作**（FR-06 削除・FR-19 完全削除）は**例外をそのまま通す**。`SaveChangesAsync` の
  手前で落ちるので DB 行は残り、利用者は 5xx を受ける。**「成功した」と告げないことが要点**である。
- **定期処理**（90 日自動物理削除）は**文書ごとに隔離**する。1 件の失敗で周期全体を止めると
  無関係な資料の期限超過が積み上がる。失敗した文書は行を残すため `PurgeAt <= now` を
  満たしたままであり、**次周期で自然に再入する**。

### 決定 4: 🔴 資産 URI は**遡及付与しない**（受け入れ基準①は既存文書の資産には及ばない）

`Document.AssetUris` は本作業以降に取り込まれた（＝`DocumentNormalized` を受けた）文書にのみ入る。
マイグレーションは全既存行へ `'[]'::jsonb` を入れるだけで、過去の資産 URI を復元しない
（イベントは再送されず、資産キーを文書 ID から再構成する術も無い —— `figureId` と拡張子が要る）。

**したがって、本作業より前に取り込まれた文書の図表資産はオブジェクトストレージに残る。**
`doc_scope` が実データ 0 件・遡及付与しない方針（計画 ADR-0054 §結果）と同型の受容である。
**「全部消える」と書かない。** 本文（`MarkdownUri`）は既存文書でも消える。

### 決定 5: SC-19 の但し書き（ADR-0057 決定 4）は**据え置く。ただし根拠を差し替える**

計画 ADR-0057 決定 4 は、決定 1 が未実装である間の暫定手段として「①の文言を出さない」か
「但し書きを添える」の 2 択を実装へ委ね、実装は但し書き
（「（削除の反映には時間がかかる場合があります。）」）を選んでいた。

- **当初の根拠は消えた。** 「本文の実体を消す経路がまだ無い」は本作業で解消した。
  SC-19 が扱う**個人資料は変換経路を通らないため資産を持たない**（`AssetUris` を書くのは
  `DocumentNormalizedConsumer` だけで、個人資料は `Document.Create` ＋ Obsidian 同期で作られる）。
  よって**決定 4 の限界は SC-19 の射程には掛からない。**
- **別の根拠が残っている。** ②索引・グラフの掃除は `DocumentDeleted` を介した**非同期**であり、
  応答を返した時点では検索・グラフ側に短時間残り得る。「削除の反映には時間がかかる場合が
  あります」は**この事実の記述としてなお真**である。
- したがって**文言そのものは変えない**（利用者に見える面を動かさない・i18n カタログを動かさない・
  計画の固定文言と衝突させない）。**変えるのは「なぜ置いているか」を説明している文書の側**である。

🔴 **「実装したから外す」と機械的に処理しないための決定である** —— 外す条件（①の未配備）は
消えたが、置いておく別の条件（②③の非同期性）が立っている。

## 理由

- 決定 1 は ADR-0057 の受け入れ基準が「引けなくなった」ではなく「**残っていない**」であることから
  直接導かれる。バージョニング既定 ON の下では、版を列挙しない実装は基準を満たさない。
- 決定 2・3 はいずれも「**観測できない壊れ方を作らない**」という同じ規準で選んでいる。
  不可視な残留（決定 3 の表の上段）と、他サービスのデータの破壊（決定 2 の `OriginalUri`）は、
  どちらも**壊れたことが誰にも分からない**種類の失敗である。
- 決定 4 は、満たせない範囲を**黙って出荷しない**ためにある。ADR-0054 が先例を作っている。

## 結果

- 良い影響:
  - ADR-0057 決定 1 の①が、本作業以降に取り込まれた文書について成立する。
  - `SC-19` の「復元できません」が、個人資料については**実体の裏付けを持つ主張**になった。
  - 配備ドリフト（compose の `document-service` に objectstorage-env が無い）を塞いだ。
    未構成は 500 にならず**静かに実体を残す**ため、配備側で塞ぐ以外に検知の口が無い。
- 悪い影響・トレードオフ:
  - **既存文書の図表資産は残る**（決定 4）。
  - 削除がオブジェクトストレージへの往復を含むようになり、削除要求の応答時間が伸びる。
    版数に比例した `DeleteObject` 呼び出しが要る（1 オブジェクトあたり版数 + 1 回）。
  - ストレージ障害中は完全削除ができなくなる（fail-closed の裏返し）。**意図した挙動**である。
- フォローアップ:
  1. **再正規化で参照から落ちた旧資産の掃除**（孤児）。`ApplyNormalized` は `AssetUris` を
     差し替えるため、落ちた資産は台帳から消えて実体が残る。ADR-0057 は**削除操作**の伝播範囲の
     裁定であり、再変換時の孤児掃除はその射程に無い。別 issue で扱う。
  2. `Document.AssetUris` を `DocumentDto` / openapi へ出すか（現状は出さない。契約を広げない）。
  3. 既存文書の資産を棚卸しする手段（オブジェクトストレージ側の全走査と台帳の突合）。
     決定 4 の限界を運用で埋める場合に要る。
