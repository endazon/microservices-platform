# IADR-0595: 取り込みの版の印と「書いてから消す」（#2101）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

## コンテキストと課題

`DocumentUpdatedConsumer` は、受け取った版の新旧を見ずに「全コレクションから消す → 本文を読む → 書く」を行っていた。

- `DocumentUpdated` は少なくとも 1 回届き、順序は保証されない（並行の発行・再配送・デッドレターからの再投入）。古い版が後から届くと新しい版を上書きし、
  判定軸（機密区分・共有先など）を厳しくした版の後では、緩い判定軸の索引が戻り得る。撤収（露出 OFF・アーカイブ）や削除で点を消した後の古い版も、点を書き戻す。
- 先に消すため、本文の取得・書き込みが失敗して再試行を使い切ると、文書は索引から消えたままになる。

## 検討した選択肢

1. **版の印を検索と別のコレクションに持ち、古い版を弾く。判定軸が同じ更新は書いてから消す（採用）**。
2. **既存の点の `updated_at` だけで判定する**（issue の推奨の最小形）。撤収・削除で点が全部消えた文書は判定の材料を失い、その後の古い版を弾けない。採らない（材料だけを点の外へ出したのが 1）。
3. **常に書いてから消す**。判定軸を厳しくする更新が途中で失敗すると、旧い（緩い）判定軸の点が残る。索引は判定軸を実体で運ぶので（消費側のフィルタだけで隠さない。IADR-0396 と同じ理由）、採らない。
4. **発行元（DocumentService）へ現状を問い合わせてから書く**。取り込みに同期の依存を 1 本足し、発行元の不調で取り込みが止まる。版の印で足りるので採らない。
5. **全順序の版番号を契約に足す**。`UpdatedAt` を進めない変更（露出トグル・共有・タグの改名・再発行）まで順序づけられるが、発行側と 4 つの受け手を揃えて変える契約変更である。本 IADR の射程の外（§結果・未決）。

## 決定

**決定 1（版の印と順序の門）**: 取り込みは文書ごとに**版の印**を持つ。置き場所はベクトルを持たない専用のコレクション `knowledge_document_index_versions`
（1 文書 1 点・点 ID ＝ 文書 ID）。検索のコレクションには混ぜない（検索側はこの名前を読まない）。値は `updated_at`（反映した `DocumentUpdated.UpdatedAt` の epoch ミリ秒）と
判定軸の指紋（決定 3）。最初の書き込みでコレクションを作る（起動時のブートストラップの呼び出し順は変えない。無ければ「印は無い」と読む）。
受け口は最初に印を読み、**印より厳密に古い更新は何もせず正常に終える**（ack。撤収・アーカイブの更新も含む。新しい版が正である）。等しい版（再配送・再発行）と印の無い文書は反映する。
比較はミリ秒で行う（保存の精度。ティックで比べると同じ版の再配送が等しく読めない）。撤収の門・本文所在なしの更新も印を進める（本文所在なしは点を書き換えないので指紋を引き継ぐ）。

**決定 2（書いてから消す）**: 判定軸が同じ更新は、旧版の点を消さずに新版を書き、**書き終えた後に旧版の点を消す**。旧版の点は
「文書の点 ∧ ¬(`updated_at` > この版) ∧ ¬(この取り込みで書いた点)」（`updated_at` を持たない移行前の点を含む）を全コレクション（モデル別 ＋ 語彙索引）から選ぶ。
書いた点はコレクションごとに分けて残す（同じチャンク ID の点が別のコレクション〔機密区分が変わる前・埋め込み待ち〕に残れば消す）。
本文の欠落（恒久的。IADR-0540）・索引テキストが空の文書は新版が点を持たないので、旧版をすべて消す（従前の「先に全消し」と同じ結果）。

**決定 3（判定軸が変わる・不明なら先に消す）**: 判定軸は**属性辞書 ＋ 共有先**（点が運び、検索の ABAC が引くもの）とし、その正準形（鍵と共有先を順序づけ・重複を除く）の SHA-256 を指紋として印に持つ。
到着した更新の指紋が印と違う、または印が無いときは、従前どおり**本文を読む前に全コレクションから消す**（fail-closed。途中で失敗しても旧い判定軸の点を残さない）。
**消してから印を書く**（印を先に書いて削除が落ちると、再試行は「判定軸は同じ」と読んで先の削除を飛ばす）。撤収した版の指紋は空文字列。
印が持つのは文書 ID・版・一方向の指紋だけで、題名・本文・タグ・属性の値は持たない。物理削除の後も残るが、本文の復元には使えない（ADR-0057 決定 2 が許す「削除の事実の記録」と同じ性質）。

**決定 4（追い越しを塞ぐ）**: 書き終えた後に印を読み直す。より新しい版が印を書いていたら、この取り込みは追い越されている —— **この版以下の点を（書いた点ごと）消し**、
完了イベントを出さずに終える。新しい版の点（版がより新しい）は残る。

**決定 5（時間の上限）**: 受け口の最悪の所要時間に、版の印の照会・記録・読み直し（Qdrant 3 回）と旧版の削除（コレクション数 × Qdrant）を足す。
既定（2 コレクション）で 20＋30＋20＋20＋300＋30＋10＝430 秒になるため、**受け口の実行期限の既定を 420 → 435 秒**へ上げる（`EnsureFits` は等しいと止める）。
再試行の連鎖は 4 × 435 ＋ 42 ＝ 1782 秒で、ブローカの consumer_timeout（既定 1800 秒）に収まる。

## 結果

- 良い: 到着順の逆転・デッドレターからの再投入・撤収や削除の後の古い版で、判定軸を厳しくした索引が緩まず、点が書き戻されない（GraphService と同じ規則が取り込みにも揃う）。
  判定軸が同じ更新の途中失敗で文書が索引から消えたままにならない。チャンク数の減少・置き場所の移動の旧版の点は書き終えた後に消える。
- 悪い（受容）:
  - **`UpdatedAt` を進めない変更の順序は判定できない**（露出トグル・共有の付与と取り消し・タグの改名・再発行）。等しい版として届き、後着が勝つ（従前と同じ）。全順序の版番号の契約追加が要る（選択肢 5。#2150）。
  - 版は発行側の時計である。レプリカ間の時計の差が更新の間隔を超えると、新しい更新を古いと判定し得る（GraphService と同じ前提）。
  - 印の読み書きは比較交換ではない。同じ文書の 2 版を並行に取り込むと印の後先が逆転する窓が残る。決定 4 で大半を塞ぐが、古い版が同じチャンク ID を上書きした後に消すと、
    新しい版の該当チャンクが次の更新まで欠ける（緩む側ではなく欠ける側へ倒れる）。既定の配備（1 レプリカ・Inline の受信）では並行は起きない。**ingestion を複数レプリカ・並行受信にする前に本項を解消する**（運用仕様書 §可用性・水平スケールに明記）。
  - 総枠の使い切り（デッドレターへ直行）で途中まで書いた版は、旧版の残りと混ざって次の更新まで残る（判定軸は同じ）。
  - Qdrant にコレクションが 1 本増える。受け口の実行期限の既定が 15 秒延びる（構成で上書きしていれば、その値が新しい式に収まるかを起動時に検査する）。
  - 配備時点で印を持つ文書は無く、最初の更新は「判定軸が不明」として従前どおり先に消す（移行の間の挙動は従前と同じ）。
- 境界: 発行側の原子性（DB の確定と発行。#2042）は扱わない。Outbox が入っても到着順の逆転・再配送は残るので、本決定は Outbox と独立に要る。Wiki・Catalog は #2102。
