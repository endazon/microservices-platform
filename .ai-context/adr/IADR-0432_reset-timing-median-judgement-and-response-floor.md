# IADR-0432: リセット申請の所要時間は反復した中央値を自己対照で判定し、床は経路に居る専用の器で掛ける

## コンテキストと課題

ADR-0094 は環流 planning#596 の実測（稼働 k3s・近接 MTA 配備済み）を受けて 4 つを決めた。
そのうち**実装が決めるべきことを 2 つ、計画が明示的に委譲している**。

| 委譲されたもの | 計画の書きぶり | 本 IADR が決めるところ |
| --- | --- | --- |
| `評価不能`（自己対照が広い）の**境界** | 「自己対照の側が広いとき（ノイズが大きいとき）は判定できない」。**広いの定義を書いていない** | 決定 2 |
| **床の値**と**床の置き場** | 「床の値は実装が実測から定める。**計画は値を発明しない**。導出規則を定める —— 床は実在側の所要時間分布の上側を覆う値とする」。置き場は書いていない | 決定 3・決定 1 |

差が構造由来であることは既に確定している。`IADR-0404` §着手前に自分で確かめたこと が上流ソースで
2 点を押さえた —— **Keycloak の送出は同期**（`DefaultEmailSenderProvider`）であり、
**非実在利用者は `forkWithSuccessMessage(EMAIL_SENT)` で即 200** を返す（`ResetCredentialEmail`）。
🔴 **非実在側はメールを作らず、送らない。** 近接 MTA を挟めば往復は localhost へ縮むが、
**往復そのものが消えない限り差は消えない。**

## 検討した選択肢

### 床の置き場（ADR-0094 が候補を挙げていない部分）

| 案 | 要求を握って床まで待てるか | 評価 |
| --- | --- | --- |
| 1. Istio の fault injection の `delay` | ❌ | **固定値を両側に同じだけ足すので比が変わらない**（ADR-0094 実測 5 が既に退けている）。154:49 に 100 ms を足せば 254:149 で比は縮むが 0 にはならない |
| 2. Istio の EnvoyFilter ＋ Lua | ❌ | 🔴 **Envoy の Lua フィルタが公開するストリームハンドル API に待機（sleep / timer）が無い。** 公開されているのは headers / body / bodyChunks / trailers / **httpCall** / respond / ログ / metadata / streamInfo / connection などであり、**待てるのは `httpCall` の応答待ちだけ**である。つまり Lua で床を作るには**待たせる相手を別に用意しなければならない** —— それなら案 4 と同じ器が要るうえ、ホップが 1 つ増える。加えて本リポジトリに EnvoyFilter の先例は **0 件**であり、**production の Keycloak マニフェストは本リポジトリに無い**（IADR-0404 決定 2）ため、ローカルエッジ限定の統制になる |
| 3. `reset-gate`（#1245 PR-C の器）を拡張する | ❌ | 🔴 **門は要求経路に居ない。** 近接 MTA へ能動 SMTP プローブを打ち、realm を PUT する**制御ループ**（Deployment の常駐ループ）であり、利用者の要求を握れない。プロキシへ作り替えれば器の性質が変わり、**門の判定（1 回の失敗で閉じ、連続 N 回の成功で戻す）と要求処理が同じプロセスで混ざる** |
| 4. **同じ配備単位に、経路に居る器を 1 つ足す** | ✅ | 逆プロキシとして Keycloak の手前に立ち、上流応答を受け切ってから床まで待つ。**部品が 1 つ増える**（ADR-0094 §結果 が既にトレードオフとして書いている） |

### `評価不能` の境界

| 案 | 評価 |
| --- | --- |
| 1. 境界を置かない（`cross ≤ self` なら常に合格） | ❌ 🔴 **ノイズが大きいほど緑になりやすい。** 自己対照は許容比そのものなので、環境が荒れるほど許容が広がる。ADR-0094 が「合格にしない」と明記した状態をまさに緑にする |
| 2. 構成で与える（未設定なら起動しない。`reset-gate` の作法） | ❌ この検査器は CI が引数なしで走らせる門であり、未設定＝常に `評価不能` になる。**`評価不能` の意味が「測れていない」から「設定していない」へすり替わる** |
| 3. **可検出性の下限**を実測から導いて定数で持つ | ✅ 決定 2 |

## 決定

### 決定 1: 床は `deploy/mail-relay/` に置く**専用の逆プロキシ**とし、Lua でも門でもない

`deploy/mail-relay/reset-floor.js`（Node 標準の `http` / `url` のみ・外部依存ゼロ）を、
近接 MTA・門と**同じ配備単位**に置く。ただし**門とは別の器**である（門は制御ループ、床は経路上の器）。

- **上流の応答を全部受け切ってから**床まで待ち、**ステータス・本文・ヘッダをそのまま**書き出す。
  🔴 **床が変えてよいのは返す時刻だけである。** ステータス・本文のバイト一致は近接 MTA と門が
  既に成立させており（ADR-0094 §統制と現在の実現手段の 1 行目）、**ここで触れば壊す。**
- **床を超えて返る応答は待たせない**（負の待ちを作らない）。ADR-0094 §残るもの が「床が分布を
  覆えなかった場合、上側の裾は残る」と明記しており、**裾を隠す仕掛けをここへ足さない**（未裁定である）。
- 🔴 **上流が落ちたときも床を守る。** 即座に 502 を返すと「速い 502」と「床で返る 200」が
  所要時間で区別でき、**床を入れたことで新しい窓を開けることになる。**
- **経路は POST だけを床へ向ける。** 差が出るのは申請の POST であり（送出が同期）、
  認可要求と申請画面の GET は**利用者名を知らない段階**で差が出ようがない。**差の無い経路まで遅くしない。**
- 🔴 **ログイン経路（`login-actions/authenticate`）には掛けない。** ADR-0094 決定 4 は同経路を
  判定の対象外とした（`failureFactor=5` のロックで標本を増やせず、反復を前提とする決定 1 が成立しない）。
  **裁定の無い経路へ統制を広げない。**

### 決定 2: `評価不能` の境界は「可検出性の下限」であり、実測の最小値から導く

**自己対照の比 `self` が 2 倍以上のとき、その反復は `評価不能` とする**（`cross ≤ self` であっても
合格にしない）。定数名は `SELF_CONTROL_WIDE_RATIO`。

**導出**: ADR-0094 §コンテキストと課題 が稼働 k3s で記録した本経路の比は **1.9〜3.1 倍**である。
🔴 **ノイズ帯がその最小値 1.9 倍以上に広い測定は、計画が既に見つけた最小の差すら再現できない。**
そのとき「比が自己対照を超えなかった」は「差が無い」ではなく「**ノイズに埋もれて見えない**」である。
1.9 を上へ丸めて **2 倍**とした（小数を書くと実測に無い精度を主張することになる）。

🔴 **これは許容比（閾値）ではない。** 許容比は依然として自己対照そのものであり、環境ごとに違ってよい
（ADR-0094 決定 1 が「環境自身に測らせる」と定めたとおり）。**ここが止めるのは
「測れていないのに緑」だけ**である。

### 決定 3: 床の値は 150 ms とし、導出は「判定に使う反復の実在側 max を覆う」である

| 段 | 値 | 出典 |
| --- | --- | --- |
| 実在側の max（反復 1・**暖機として捨てる**） | 202 ms | ADR-0094 §コンテキストと課題 の表 |
| 実在側の max（反復 2） | 108 ms | 同上 |
| 実在側の max（反復 3） | 126 ms | 同上 |
| **判定に使う反復の max の最大値** | **126 ms** | 上の 2・3 |
| **床** | **150 ms** | 126 ms を 50 ms 刻みで上へ丸めた |

🔴 **丸めの刻み（50 ms）だけが実装の選択であり、覆う対象は実測である。** 値そのものを発明していない。
🔴 **暖機の 202 ms を覆おうとしない。** 暖機は定常状態ではなく、そこへ床を合わせると
**全申請が定常の 1.6 倍遅くなる**（ADR-0094 実測 2 が「判定に使う状態を固定しなければ、
測るたびに結論が変わる」と書いたのと同じ理由が、床の値にも効く）。

**値はマニフェストが与え、コードは既定を持たない**（`RESET_FLOOR_MS` が無ければ器は起動しない）。
`reset-gate.yaml` / `probe.js` と同じ作法である。

### 決定 4: 床は opt-in にし、既定の描画をバイト等価に保つ

> 🔴 **［2026-09-26 追記 / #1500］本決定は計画 ADR-0097 決定 2（Accepted 2026-09-12）に覆された。床は既定 ON である。**
> 以下の本文は当時の判断として残す。現行の形は末尾の追記「床を既定 ON にする」を読むこと。

`deploy/mail-relay/kustomization.yaml` は床を**参照しない**。取り込むのは opt-in の overlay
`deploy/local/edge-istio-reset-floor/` だけで、そこが**器と経路を同時に**足す
（🔴 **片方だけでは効かない** —— 器だけなら誰も通らず、route だけなら 404 になる）。
`scripts/istio-edge-up.sh` は `RESET_FLOOR=1` のときだけそちらを当てる（既定 0）。

🔴 **近接 MTA（ADR-0078 決定 2）や門（同 決定 4）と違い、床は opt-in にしてよい。**
前二者は計画が**無条件**と定めた統制だが、**床は ADR-0094 の着手可否の注記が「覆り得る」と
名指しした決定**である —— 床を入れた構成で中央値の比が許容内に収まることを稼働クラスタで
実測するまで、「これで塞がる」と決めきれていない。**既定へ入れるのは実測の後**である。

### 決定 5: 検査器の測り方（ADR-0094 決定 1 の写像）

`scripts/check-password-reset-mail.js` の T-10 へ所要時間の軸を足す。

- **反復 3・片側 6 標本**。1 反復の中で実在／非実在を**交互に**打つ
  （🔴 まとめて打つと、反復内のドリフトが片側だけに乗り、それが「差」として出る）。
- **計るのは POST だけ**。認可要求と申請画面の GET を含めると、差の出ない 2 往復が分母に入って
  **比が薄まる** —— 「差が小さくなった」のか「測り方で薄めた」のかを区別できなくなる。
- **自己対照の 2 群は取得順の交互で分ける**（前半／後半では**ない**）。
  🔴 前半後半で分けると、反復内のドリフトを丸ごと「ノイズ」に数えて**自己対照を不当に広げる**
  ＝許容が緩くなる。交互なら両群が反復の全体にまたがる。
- **非実在名は実在名とバイト長を揃える**（`makeAbsentUsernameOfLength`）。
  🔴 申請した名前は応答へ反映されるため、長さが違えば本文長が必ず違う ——
  環流 planning#596 が 1 度目に踏んだ罠（「16 バイト違う」の 16 は名前の長さの差そのものだった）。
  realm 宣言と突き合わせて不在も確かめる。
- **走査件数と各反復の中央値を必ず併記**し、`評価不能` は `[T-10][評価不能]` の札で緑と別に出す。
- 🔴 **床が入るまで赤が続くことを受け入れる**（ADR-0094 決定 4）。**赤は「まだ塞いでいない」ことの
  正しい表示である。**

## 理由

- **床を専用の器にしたのは、Lua も門も要求を握れないからである。** Envoy の Lua は待てず、門は経路に
  居ない。🔴 **「既にある部品で済ませる」を優先すると、済ませられないものを済ませたことにしてしまう。**
- **`評価不能` の境界を実測から導いたのは、置かない案が「ノイズが大きいほど緑になる」からである。**
  自己対照は許容比そのものなので、境界が無ければ**荒れた環境ほど合格しやすい** ——
  ADR-0094 が「合格にしない」と名指しした状態をまさに緑にする。
- **床の値で暖機の 202 ms を覆わなかったのは、暖機が定常状態ではないからである。** 覆えば
  全申請が定常の 1.6 倍遅くなる。**測る側で捨てた状態を、塞ぐ側で拾い直さない。**
- **opt-in にしたのは、床が「覆り得る」決定だからである。** 実測が許容内に収まらなければ、
  ADR-0094 §着手可否の注記 のとおり**申請の受け口を製品側の端点へ移す案へ改める**ことになる。
  既定へ入れてから畳むより、**入れる前に測る**ほうが安い。
- **POST だけに掛けたのは、差の無い経路まで遅くしないためである。** ADR-0094 実測 6 のとおり
  床は性能要求と衝突しないが、**制約になるのは利用者の体感**であり、そこは節約できる。

## 結果

- **良い影響**: 所要時間が**判定できる形**になった（ADR-0078 決定 1 の保留が解けた）。
  許容比を環境に測らせるので、閾値の値をめぐる往復が起きない。床は**手元で実測した** ——
  上流 20 ms / 120 ms の 2 系統（**6.0 倍の差**）が床ごしに **1.000 倍**へ揃い、
  本文 81 バイト・`Set-Cookie` 2 本・`content-type` がいずれも不変で、
  **床（150 ms）を超える 400 ms の応答は 404 ms のまま出た**（裾を隠していない）。
- **悪い影響 / トレードオフ**: **部品が 1 つ増える**。**全申請が床まで遅くなる**。
  **検査器が床の配備まで赤で居続ける**（赤の意味を知らない者が「壊れている」と読む危険）。
  **反復 3 × 片側 6 標本 = 36 件の申請**を打つので、捕捉用 MTA に 18 通溜まる
  （T-16 / T-17 の「ちょうど 1 通」は本相より前に測り終えている。クラスタは CI の次の段で破棄される）。

### 残るもの

- 🔴 **床は稼働クラスタで打っていない**（#1410 の作業機にクラスタが無い）。**「動くはず」を実測として
  書かない。** 上の実測は**手元の Node で立てた上流に対するもの**であり、Istio のルーティング・
  Keycloak の実応答・k3s の資源の下で同じかは測っていない。再実測は `integration-stack.yml` を
  `RESET_FLOOR=1` で回して行う（ADR-0094 フォローアップ 3）。
- 🔴 **`check-password-reset-mail.js` は現在 develop で動いていない。** `#1402`
  （`platform-spa` の public client を realm から撤去）以後、realm に `publicClient: true` の
  クライアントが **1 つも無く**、`pickPublicClient` が null を返す ——
  `--self-test` の「宣言から対象を選べる（実データ・ラチェット）」と実行の両方が落ちる。
  **本 PR より前から落ちており、本 PR は `pickPublicClient` を 1 行も触っていない。**
  🔴 **したがって本 PR が足した所要時間の軸は、その前提が直るまで稼働クラスタでは走らない。**
  直し方は ADR-0032 / IADR-0429 / IADR-0273 との整合を要するため別 issue とする。
- **床が実在側の分布を覆えなかった場合の裾の扱い**は計画が未裁定である（ADR-0094 §残るもの）。
- **リセット申請の回数制限**を置くかは計画が未裁定（同上）。本 IADR は触れない。
- **ログイン経路の所要時間**は判定されないまま（ADR-0094 決定 4 の対象外・`IADR-0427` のとおり観測のみ）。

## ［2026-09-25 追記 / #1470］判定を 2 段にする —— 計画 ADR-0103 が決定 5（ADR-0094 決定 1 の写像）の判定式を部分改定した

**契機**: 床（150 ms）を入れた integration-stack で T-10 の所要時間判定が断続的に不合格になった（#1470・#1435）。
実在 153.0 / 非実在 152.0 ms・比 1.01 倍・自己対照 1.00 倍、のように**床の内側 0.5〜1 ms の揺れで赤になり、
遅い側が反復ごとに入れ替わった**。環流 planning#633 を経て、計画 ADR-0103（Accepted 2026-09-15）が
ADR-0094 決定 1 の判定式を部分改定した。原因は**比較の構造**である —— 自己対照は各群 3 標本（奇数）の
中央値なので刻み 1 ms、比は 6 標本（偶数）の中央値なので刻み 0.5 ms であり、**自己対照が 1.00 に落ちると
上限として機能しない**（0 より大きい差はすべて上限を超える）。

**決定（追加）**: `evaluateTimingConsistency` の判定を 2 段にする。

| 段 | 条件 | 判定 |
| --- | --- | --- |
| 1 | 実在・非実在の中央値の差 ≦ **自己対照の刻み** | **合格**（比と自己対照を比べない）。ただし自己対照 ≧ `SELF_CONTROL_WIDE_RATIO` なら `評価不能` |
| 2 | 差 ＞ 刻み | 従前どおり（`cross > self` で不合格、広ければ `評価不能`、それ以外は合格） |

- **判定順は段 1 を `cross > self` より前に置く**（ADR-0103 フォローアップ 1）。
- **刻みの導出（ADR-0103 決定 1 が「導出は実装へ残す」と委ねたもの）**: 標本の分解能は
  `TIMING_SAMPLE_RESOLUTION_MS = 1`（`submitReset` が `Date.now()` の差で測るため整数 ms）。
  群の中央値の刻みは、標本数が**奇数なら分解能**（観測値そのもの）、**偶数なら分解能 / 2**（中央 2 値の平均）。
  **自己対照の刻み＝ 2 群の刻みのうち細かい方**（2 つの中央値の差が表せる最小の間隔）。関数
  `selfControlStepMs` が計算し、**値を定数で書かない**（標本数を変えれば刻みも変わるため）。
  現行の片側 6 標本 → 各群 3 標本では **1 ms** であり、計画の「整数 ms の標本では 1 ms」と一致する。
- 🔴 **決定 1 と 2 の交点（実装の解釈）**: 段 1 を無条件に合格にすると、自己対照が 2 倍以上に広い反復でも
  中央値が偶然 1 ms 以内に並べば合格になり、**ADR-0103 決定 2 が「緩めない」とした広すぎる側を緩める**。
  よって段 1 は潰れた側にだけ効かせ、**広い反復は段 1 に当たっても `評価不能`** とした
  （同 決定 2「潰れた側に別の扱いを与えるだけであり、広すぎる側を緩めない」の字面どおり）。
- **本 IADR 決定 2（`評価不能` の境界 2 倍）・反復数・標本数は変えない**（ADR-0103 決定 2。案 3「標本数を増やす」は
  採られていない）。
- 🔴 **受け入れたリスク**: 刻み（1 ms）未満の系統差は検出しない（ADR-0103 決定 3）。より細かい時計で測れば
  見える可能性は否定されていない。判別できる測定器が現れたら見直す（同 フォローアップ 2）。

**床は引き直さない（ADR-0103 決定 4 / ADR-0097 決定 3）**: ADR-0097 決定 3 の契機「検査器の赤（T-10 が落ちたとき）」は
**発火した**。調べた結果は**床超過ではない** —— 中央値 152.0〜153.0 ms に対し床は 150 ms、決定 3 の導出元である
実在側 max は 126 ms であり、床は実在側を覆っている。**決定 3 の導出（判定に使う反復の実在側 max を 50 ms 刻みで
上へ丸める）は引き直していない**（床を上げても比較の刻みは変わらず、同じ揺れが同じように境界を跨ぐ）。
発火と調査結果の記録は計画 ADR-0097 決定 3 の注記（2026-09-15）が持つ。

**検証**: 自己試験に 7 件を足した（50 件）。#1470 の実測の形（自己対照 1.00・差 1 ms / 0.5 ms）は合格、
🔴 **境界の外側（自己対照 1.00・差 1.5 ms）は段 2 で不合格**、差 2 ms・自己対照 1.00 も段 2 で不合格、
差 2 ms でも比が自己対照の内側なら段 2 で合格、広い自己対照は差が刻み以下でも `評価不能`。
変異 7 種（段 1 の無効化・段 1 の広い側の除去・刻みを常に半分・刻みを粗い方で取る・`<=` を `<` へ・
**段 1 を `diff <= step + 0.5` へ緩める・`diff < 2 * step` へ緩める**）はいずれも自己試験が落とす。
🔴 **緩い側の 2 種は、差 1.5 ms の境界試験を足すまで生き残っていた**（監査の指摘）。刻みを超えた差を
段 1 が拾えば、刻みの 1.5 倍の系統差まで比較なしに合格する —— **守る側へ誤る変異を落とせない試験は、
存在秘匿の門として足りない。**🔴 **稼働クラスタ（integration-stack）での
再実測はしていない**（本作業の作業機にクラスタが無い）。

**残るもの**: MSP のテスト仕様書 `docs/tests/SC-15` は所要時間の項目を **T-25** と採番しているが、検査器の出力札は
**`[T-10][所要時間]`** である（本 IADR の決定 5 以来の不一致）。計画 ADR-0103 §実測 5 は「`T-25` は一度も
存在していない」とするが、根拠の走査は検査器ファイルに限られていた。本追記では ID を付け替えない。

## ［2026-09-26 追記 / #1500］床を既定 ON にする —— 計画 ADR-0097 決定 2 が決定 4（opt-in）を覆した

**契機**: #1491（#1470 の実装）の監査で、計画 ADR-0097 決定 2（Accepted 2026-09-12）が未実装のまま
`RESET_FLOOR` の既定が 0 であることが見つかった（#1500）。同決定は「**`RESET_FLOOR` の既定を 1 とし、
`deploy/mail-relay/kustomization.yaml` が床を参照する形へ改める**」と定め、**本 IADR 決定 4 を覆す**と明記している。

**覆された理由（計画の逐語の要点）**: 決定 4 の理由は「床は ADR-0094 の着手可否の注記が覆り得ると名指しした
決定だから」であった。ADR-0097 決定 1 がその注記を解除し（床を入れた integration-stack の実測で比 1.00 倍・
自己対照の内側。環流 planning#611）、**前提が消えた**。加えて計画は「床は失敗しても安全側である（効かなければ
遅くならないだけで、応答の内容は変わらない）」とする。逆に既定 OFF のままだと **go-live の経路で所要時間の統制が
1 つも効かない**。全申請が床（150 ms）まで遅くなるトレードオフは計画が引き受けた。

🔴 **実装の訂正（計画の「安全側」の射程）**: 「遅くならないだけ」が成り立つのは**経路が入っていない**ときだけである。
経路（VirtualService 先頭の POST route）は器だけを向き、Keycloak へ戻る予備の route は無い。**経路が入った後に
器が落ちる（ready な endpoint が 0）と、Envoy はリセット申請の POST をすべて 503 で返す**（監査 #1518 の指摘）。
これは存在秘匿を破らない（実在・非実在とも同じ 503）が、**申請そのものが失敗する**可用性の事象である。
対処は 2 つ: ①`k8s-local-up.sh` が器の rollout を待つ（経路を足す `istio-edge-up.sh` はその後に走る）、
②器の readiness は上流を映さない（映すと Keycloak が落ちた瞬間に床を待たない即座の 503 になり、決定 1 の
「上流が落ちたときも床を守る」が崩れる）。**予備の route は足さない** —— 足せば器が落ちたとき床の無い経路へ
黙って戻り、所要時間の窓が開く（監視の無い縮退を作らない）。この射程の違いは計画 ADR-0097 の記述に無い。

**決定（改定後の形）**:

| 部品 | 決定 4（旧） | 現行 |
| --- | --- | --- |
| 器（`deploy/mail-relay/reset-floor/`） | opt-in overlay だけが取り込む | **`deploy/mail-relay/kustomization.yaml` が取り込む**（近接 MTA・門と同じ配備単位。`deploy/local/infra` の描画に出る） |
| 器の本体（ConfigMap `reset-floor-script`） | `istio-edge-up.sh` が `RESET_FLOOR=1` のときだけ作る | **`k8s-local-up.sh` が infra の apply より前に作り**、rollout を待つ。`istio-edge-up.sh` も冪等に作る |
| 経路（`msp-keycloak-edge` 先頭の POST route） | `RESET_FLOOR=1` のときだけ `deploy/local/edge-istio-reset-floor` を当てる | **`RESET_FLOOR` の既定 1** で同じ overlay を当てる |
| 退路 | — | **`RESET_FLOOR=0`**（素の `edge-istio`。経路だけが外れ、器は誰も通らないまま居る） |
| 値（150 ms） | マニフェストが与え、コードは既定を持たない | **変えない**（決定 3 の形のまま。`RESET_FLOOR_MS` が無ければ器は起動しない） |

- **「既定 ON」とは overlay を既定で取り込むことであって、値をコードへ焼くことではない**（ADR-0097 決定 2 の逐語）。
- **`RESET_FLOOR` は 0 / 1 だけを受け付け、それ以外は入口に触る前に落とす。** 既定が 1 になったことで
  「`false` と書けば外れるつもり」の取り違えが起き得る。黙って入れても外しても誤りであり、Traefik を落とした
  後に気付くのが最悪である（`istio-edge-up.sh` 冒頭の前提確認と同じ理由）。**`k8s-local-up.sh` も冒頭で同じ検査をする**
  （空・0・1 のみ。長い起動の最後で落とさない。監査 #1518）。Istio のエッジが走らない起動（`ISTIO=1` ＋ `LOCALEDGE=1`
  でない）で `RESET_FLOOR` を与えたら、効かないことを WARN で告げる。
- **エッジの切り戻し（`istio-edge-down.sh`）は器を消さない。** 器は近接 MTA の配備単位の持ち物になった ——
  消すと infra の宣言から外れ、`check-stack-ready.js` の G11 が「宣言に在るのに稼働していない」で落とす。
  経路は VirtualService ごと消える。
- **integration-stack は `RESET_FLOOR` を job env で与えない。** 既定の経路そのものを測る（既定が 0 へ戻れば
  T-10 の所要時間が赤になって気付ける）。ADR-0097 決定 1 の解除条件「床を入れた構成の integration-stack で
  T-10 が継続して合格する」はこの既定の経路で満たす。
- overlay（`edge-istio-reset-floor`）は器も含んだままにする（器と経路の 2 つで 1 組を overlay 単独でも保つ。
  infra と同じ描画なので両方から apply して冪等）。

**計画の字面との差異**: ADR-0097 §フォローアップ 1 は「IADR-0432 決定 4 を部分改定する IADR を起こし、本 ADR を
根拠として引くこと」と書く。🔴 **本作業は新しい IADR を起こさず、本追記で記録した。** 先例は上の #1470 追記
（計画 ADR-0103 による決定 5 の部分改定を追記で持つ）であり、覆したのは計画であって実装の新しい判断ではない ——
実装が決めたのは上表の置き場と退路の形だけで、決定 4 の他の部分（器と経路を 2 つで 1 組にする）は変えていない。

**残るもの**:

- 🔴 **Traefik のエッジ（`ISTIO` 未設定のローカル経路）には床への経路が無い。** 経路は Istio の VirtualService の
  patch でしか書いておらず、器は立つが誰も通らない。ADR-0097 は `RESET_FLOOR` と `deploy/mail-relay/kustomization.yaml`
  だけを名指しており、Traefik 側の経路は計画外なので足していない。
- **go-live の経路**: 器は `deploy/mail-relay` の適用で入るが、**経路は go-live のエッジ側が与える必要がある**
  （production の Keycloak マニフェストは本リポジトリに無い。IADR-0404 決定 2）。
- **稼働クラスタでの実測はしていない**（ADR-0097 フォローアップ 2。本作業の作業機はクラスタへ触れない）。
- **検証**: `reset-floor.test.js` が既定 ON（器を取り込む resources 項目・`istio-edge-up.sh` を記録スタブの下で
  走らせた発行コマンド列・0 / 1 以外の拒否・切り戻しが器を消さないこと）を固定し、`k8s-local-up.test.js` が
  ConfigMap の作成順・rollout 待ち・冒頭の `RESET_FLOOR` 検査（不正値はコマンド発行前に落ちる・効かない起動で WARN）を固定する。変異 8 種（既定を 0 へ戻す・resources から器を外す・値の検査を
  消す・切り戻しで器を消す・up で ConfigMap を作らない・up で rollout を待たない・up 冒頭の値検査を外す・効かない起動の警告を外す）はいずれも落ちる。
