# IADR-0287 作業仕様書の status 据え置きに機械検査を置かない

## 起点・経緯

`.ai-context/specs/` の `status:` が実態から遅れる事故が 2 回続けて監査で出た。

- 波 2 監査 R1: 完了済みの仕様書 4 件が `status: draft` のまま
- 波 3 監査 T-推奨1: `20260828_issue-449_document-wiki-completion.md` が同じ形（**同型 2 回目**）

`CLAUDE.md`「検査器・規約の追加は**同型の事故が 2 回起きたら**」の条件が成立したため、
波 3 の監査記録（`20260828_wave3-audit-followup.md`）へ「**波 4 の掃き寄せで新設する**」と書いた。
**本 ADR はその予定を、実測に基づいて取り消す記録である。**

## なぜ実測してから決めたか

`scripts/check-doc-updated.js` の冒頭が定めた作法に従った ——
**「検査器は『思いついた式』ではなく手元の実例へ当てて誤検知を数えてから入れる」**
（同検査器は案 A・B を実測して落とし、案 C を採った。実測せずに入れていれば誤検知で
早々に無効化されていた、と記録されている）。#946 も同じ作法で「検査器を追加しない」と決めている。

## 実測

母集合は本 PR の範囲 `736f599..HEAD`（144 コミット・仕様書 40 件）。
各コミットを HEAD と見なして規則を当てる総当たりで数えた（`git ls-tree` + frontmatter 解析）。

| 案 | 判定式 | 実測 | 判定 |
| --- | --- | --- | --- |
| **A** | 仕様書のチェックボックスが全て `[x]` でないのに `done` / 逆に全て `[x]` なのに `draft` | **分離しない** —— `completed` の仕様書に未チェックが 28 件・6 件・4 件…と普通に残る（チェックボックスは網羅の記録ではなく作業メモとして使われている） | 棄却 |
| **B** | `draft` の仕様書より後に、その仕様書の `related_ids` と交差するスコープを持つ実装コミット（feat/fix/refactor/perf/test）がある | **144 コミット中 47 で発火（33%）**。しかもそれは正常な運用（起草 → 実装 → 確定）の途中状態そのものである。さらに**波 3 の事故（#449）を取り逃がす**（当該仕様書は最後の実装コミットより後に触られていたため） | 棄却 |
| **H** | `docs/` の trace ブロック（`specs:`）が引いている仕様書が `draft` | HEAD で 7 件。**うち `20260822_issue-439_bff-session-token-handler` は issue #439 が open**（＝ `draft` が正しい可能性がある）。かつ**波 2・波 3 の事故をどちらも取り逃がす**（当時それらは trace ブロックから引かれていなかった） | 棄却 |

**3 案とも、動機になった 2 件の事故を捕まえるか、正常状態を誤検知するかのどちらかである。**
案 B は 2 件のうち 1 件しか捕まえられず、その代償が 3 回に 1 回の誤検知である。
**赤の常態化は「赤を無視する学習」を生む**（`check-backend-libraries.js` の記録）ので、
この費用対効果では入れられない。

## 決定

### 決定 1: 機械検査を置かない。波 3 監査の「波 4 で新設する」を取り消す

上の実測が理由である。**取り消しは黙って行わず、本 ADR と波 3 監査記録の両方へ残す**
（予定だけが残ると、次の監査が「約束された検査器が無い」を新しい指摘として再発見する）。

### 決定 2: 事故の実体は「2 回」ではなく **46 件の系統的な滞留**である。issue へ回す

案 H の測定中に判明した。**HEAD 時点で `status: draft` の仕様書は 46 件あり、その大半は
完了済みの作業のものである**（例: `20260822_issue-908_graphservice-foundation` ——
issue #908 は PR #929 で closed / completed）。つまり監査が拾った 2 件は氷山の一角で、
`status:` は**運用として維持されていない**。

**本 PR では一括是正しない。** 理由:

- 46 件の frontmatter を一度に書き換える変更は**レビュー可能な単位ではない**
  （`IADR-0231` が 943 件の一括是正を棄却したのと同じ判断）。
- **1 件ずつ「本当に完了したか」を確かめる必要がある** —— #439 のように issue が open のまま
  正しく `draft` であるものが混ざる。確認せずに `done` へ倒すと、
  **滞留が「機械的に done と書かれた嘘」へ悪化する**（監査より劣化する）。
- 本 PR の射程は 72 issue の実装であり、過去 PR の帳簿整理はそこに含まれない。

**代わりに専用 issue（#1023）を起票し、母集合 46 件と確認手順（issue の state と突合）を渡した。**

### 決定 3: `status:` の凍結との関係を明示する

`.ai-context/specs/` は凍結記録だが、**frontmatter の状態欄は凍結の対象外**である
（`.claude/rules/traceability.repo.md` / #717 / `IADR-0191` 決定 2）。
したがって決定 2 の是正は「凍結記録の書き換え」に当たらない。**本文へ後付けの注記を足すのは別**で、
そちらは `［YYYY-MM-DD 追記 / #NNN］` 書式に限る。

## 結果・限界

- **この事故は機械では止まらないままである。** 止めるのは監査（フェーズ末のクロス監査）であり、
  実際に 2 回とも監査が拾っている。**「検査器を置いた」と書いて安心しないために、本 ADR を残す。**
- 案 H は棄却したが、**「live な `docs/` が `draft` の仕様書を根拠として引いている」という
  矛盾自体は実在する**（7 件）。母集合 46 件の是正の中で自然に解消するため、別建てにしない。
