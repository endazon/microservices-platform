# IADR-0373: MCP から外すプロジェクトは割当禁止だけでなくサービスアカウント実行経路の一律除外で守り、ABAC の判定軸は増やさない

- 状態: Accepted
- 日付: 2026-09-04
- 決定者: claude（実装セッション。#1190 が「どちらの設計を採るかを含めて基盤側の裁量に委ねる」と明示）

## 起点・関連

- 起点 issue: #1190（AST 起点 AST#662 / AST 実装 PR AST#665）
- 計画 ADR: `AST/ADR-0032` 決定 2・決定 3 ／ `ADR-0024`（2026-08-02 注記）／`ADR-0034` 決定 9 ／
  `ADR-0054`（`doc_scope` の前例）／`ADR-0062` 決定 2・3
- 関連 IADR: `IADR-0269` 決定 8（検証関数を構成検証と管理 API で共用する）
- 実装仕様書: `.ai-context/specs/20260904_issue-1190_mcp-project-attribute-ban.md`

## コンテキストと課題

`AST/ADR-0032` 決定 2 は、AST の文書を MCP から到達不能にする手段を `private-note` と同じ 3 点
（①文書属性 ②サービスアカウントへの割当禁止 ③CI 検証）と定めた。①は AST 側で実装済み（AST#665）。
#1190 は②③の受け皿である。

🔴 **ところが②③だけでは統制が 1 件も働かない。** 基盤の ABAC の具体判定規則
（`07_abac-attribute-model` §ポリシー評価モデル）に現れる属性は `confidentiality` /
`department` / `lifecycle` / `owner` / `shared_with` だけで、**`project` は無い**。したがって
サービスアカウントに `project=ai-stock-trading` が**付いていても付いていなくても、到達可否は
変わらない**。割当禁止は「設定ミスを防ぐ」だけである。#1190 も `AST/ADR-0032` 決定 3 も、この点を
明示したうえで**どう埋めるかを実装側の裁量に委ねた**。

`private-note` が実際に効いているのは ABAC ではなく **`ServiceAccountDocumentFilter`
（サービスアカウント実行経路での一律除外。`ADR-0034` 決定 9）** である。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| (a) 割当禁止（②③）だけ実装する | issue の「依頼したいこと」の字面どおり | **採らない。到達は 1 件も止まらない。** 「統制を定めた」と「統制が働いている」を取り違える形そのもの（`AST/ADR-0032` 決定 3 が名指しで戒めている） |
| (b) ②③ ＋ **`ServiceAccountDocumentFilter` へ `project` 判定を足す** | `private-note` と完全に同型 | **採用**（`AST/ADR-0032` 決定 3 の但し書きが「同じ形を採れば成立する」と指す先） |
| (c) ②③ ＋ **ABAC の判定軸へ `project` を加える** | 汎用の評価式で弾く | **採らない。** ポリシー契約（`/authz/scope` が `read` しか解決できない）・**選言が表現できない**という既存の制約（`07_abac-attribute-model` §選言）に波及し、暫定運用「多キーの文書条件を持つポリシーを運用しない」とも衝突する。**#1190 の射程を大きく超える** |
| (d) `doc_scope` に第 3 の値を足す | 属性を 1 つで済ませる | **計画が明示的に否定している**（`AST/ADR-0032` 決定 2「軸を 1 つの属性に重ねると、どちらの意味で判定しているのかが読めなくなる」） |

## 決定

### 決定 1 — 語彙は `RestrictedProject`（新規）に 1 つ持ち、集合帰属で判定する

`DocumentScope` と同じ形にする。**否定形（「制限値でない」）で書かない** —— `project` は任意属性で
あり、付いていない文書のほうが圧倒的に多い。否定で書くと**属性を持たない組織文書が一斉に落ちる**。
**2 つの書き方は「AST 文書を除外する」点では動作で見分けがつかず、分けられるのは陽性対照テスト
（`project` を持たない文書が残る／別の `project` 値の文書が残る）だけ**である。

### 決定 2 — 割当の検査は `projects`（複数）と `project`（単数）の**両綴り**を見る

計画は**文書側を単数 `project`、主体側を複数 `projects`** と定めている
（`07_abac-attribute-model` §基本属性／§利用者属性）。`AST/ADR-0032` 決定 2 (2) は `projects` と
書き、#1190 の本文は `attributes["project"]` と書く。**片方だけ塞ぐと綴りを変えるだけで抜ける**
ので両方を対象にする。多値の分解は `ServiceAccountAttributeSubset.Tokens` を再利用する
（分割規則を 2 つ持たない）。

### 決定 3 — 到達の統制は `ServiceAccountDocumentFilter` に置く。ABAC の判定軸は増やさない

選択肢 (b)。`private-note` と**同じ後段**・**ツール名で分岐しない**・**件数からも引く**
（`ADR-0034` 決定 2・4 の存在秘匿）・**有人実行では落とさない**
（`AST/ADR-0032` 決定 2「有人経路は従来どおり本人権限で読める」）。

🔴 **ABAC の判定軸への追加（選択肢 c）は本作業では採らない。** `AST/ADR-0032` フォローアップ 2 は
それも挙げているが、実現には**ポリシー契約と選言の制約**という別の課題を解く必要があり、
#1190 の射程を超える。**別 issue が要る**（§結果・フォローアップ）。

### 決定 4 — 制限値の集合を構成（appsettings）から読まない

読めるようにすると**統制を無効化する抜け道**になる（`check-stack-ready.js` G3「抜け道の環境変数を
置かない」と同じ理由）。他ユニットが同じ設計を必要としたら `RestrictedProject.Values` の 1 箇所へ
足す（`AST/ADR-0032` §結果「他ユニットが基盤 KB を使う場合も同じ設計が要る」）。

### 決定 5 — 違反はすべて返す（最初の 1 件で打ち切らない）

`ValidateServiceAccountAttributes` は `private-note` を見つけた時点で早期 return していた。
`project` の判定を足すにあたり**エラーを積む形へ改める**。打ち切ると、2 件目は 1 件目を直した
あとの実行でしか現れない（`ADR-0062` §結果「拒否理由は丸めない」と同じ理由）。

### 決定 6 — 「CI のスキーマ検証」に新しい機構を作らない

`private-note` について既に置かれているのは `dotnet test` が走らせる単体試験と起動時 fail-fast
である。**同じ 2 か所へ `project` の対を足す**（#1190 の「①②と同じ場所・同じ形」）。
🔴 **`scripts/check-realm-constraints.js` は置き場所ではない** —— realm に MCP クライアントは
1 つも無く、`project` / `projects` を持つ主体も 0 である（実測。仕様書 §走査 4）。realm に居る
`ai-stock-trading-kb-writer` は AST が文書サービスへ**書く**ための機密クライアントであって MCP
クライアントではなく、`AST/ADR-0032` 決定 2 (2) の対象ではない。

**ただし fail-fast 試験は 1 件足した** —— 検証関数が正しくても、**公開構成 JSON の
`service_account_attributes` が検証まで届いていなければ**構成は素通りする（デシリアライズの形と
検証の呼び出しは別の主張）。実際、実装中に JSON のプロパティ名が `serviceAccountAttributes` では
なく `service_account_attributes` であることをこの試験が示した。

## 理由

- **(a) を採ると、issue の字面は満たすが統制は 0 のままである。** #1190 自身が「どちらの設計を採るかを
  含めて基盤側の裁量に委ねる」と書いており、**選ばないことは選択肢ではない**。
- **(b) は前例と同型であり、次に読む人が覚える形が 1 つで済む。** `AST/ADR-0032` §理由 も
  「前例があることが決め手である」「同じ形を採れば、次に読む人は 1 つの形だけを覚えればよい」と
  同じことを言っている。
- **(c) を退けたのは実装コストではなく、既存の未解決課題（選言・`/authz/scope` の値域）へ波及する
  ことである。** そこは計画側にも未決が残っており、実装側だけで決めてよい範囲を超える。

## 結果

- 良い影響:
  - **統制が実際に働く。** サービスアカウント実行では制限プロジェクトの文書が応答にも件数にも
    現れない。変異試験 3 種（判定を常に false ／ `projects` を見ない ／ 否定形で書く）で
    それぞれ 5・7・14 件の赤を実測した。
  - **割当禁止が構成・管理 API の両方で効く**（関数共用を API 面のテストからも固定した）。
  - **他ユニットへの一般化が 1 行で済む**（`RestrictedProject.Values` へ値を足す）。
- 悪い影響・トレードオフ:
  - 🔴 **platform のドメインに可変ユニットの名前（`ai-stock-trading`）が 1 箇所入る。** ユニット外
    参照の禁止（`IADR-0120` / `src/README.md`）はプロジェクト参照の話であり本件は文字列定数だが、
    **platform が可変ユニットの語彙を知っている状態ではある**。構成から読む案は決定 4 のとおり
    退けた（抜け道になる）。
  - **除外は MCP のサービスアカウント経路だけである。** 有人 MCP クライアント・RAG・横断検索からは
    従来どおり見える（`AST/ADR-0012` が閉じるのは外部エージェント経路だけ、が計画の線）。
- フォローアップ:
  1. **文書保存時の `project` 必須化**（`AST/ADR-0032` フォローアップ 2 の別項目）。`DocumentAttributes`
     が静的に検証しているのは `confidentiality` 1 つだけであり、付与漏れは今も検出されない。
  2. **ABAC の判定軸へ `project` を加えるか**（選択肢 c）。選言・`/authz/scope` の制約と一緒に解く。
  3. **他ユニットへの一般化は計画側の判断**（`AST/ADR-0032` フォローアップ 4）。
