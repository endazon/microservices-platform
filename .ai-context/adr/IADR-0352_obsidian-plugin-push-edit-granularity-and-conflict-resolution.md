# IADR-0352: Obsidian プラグイン第 2 段 —「1 編集」の刻み・push の計画・409 の 3 択・サーバ側削除／リネームの伝播

- 状態: Proposed
- 日付: 2026-09-03
- 決定者: claude（実装判断）／起点 issue #1153（#1098 第 1 段の残射程）

## 起点・関連

- 関連する計画書 ID: FR-20（前提 FR-19）/ UC-11 / SC-20 / `ADR-0037` 決定 2・4・5・7・8・14・16、
  フォローアップ 5（「1 編集」の定義）・11（完全削除の Obsidian 側への伝播）/ `ADR-0046` /
  08_data-egress-policy §個人資料の同期に関する例外
- 関連する実装仕様書: `.ai-context/specs/20260903_issue-1153_obsidian-plugin-push-delete-conflict-stage2.md`
- 前提 IADR（覆さない）: `IADR-0338`（配置・ビルド・接続先・トークン保管・pull の差分規則）/
  `IADR-0270` 決定 3・7（同期トークン・push は `edits[]`・競合は 409 で自動解決しない）

## コンテキストと課題

第 1 段（`IADR-0338`）は設定 → manifest → pull の片方向だった。`ADR-0037` 決定 2 は**双方向**を求め、
決定 7 は競合を**利用者へ提示して選ばせる**（自動解決を既定にしない）と定め、決定 8 は**1 編集 = 1 版**と
定めるが、**「1 編集」をどの単位で刻むか**は計画が実装設計へ委ねている（フォローアップ 5）。また
サーバ側の削除・リネームがローカルへどう及ぶかも実装設計の論点である（フォローアップ 11 ②）。

サーバの契約（`Features/ObsidianSync/{Push,Delete}`）は #451 で確定しており**変えない**（#1153 の宣言
ファイル領域）。走査の結果、**契約には「リネーム」の口が無い**（`Push` の更新経路は `note.RecordBody` だけで
`VaultPath` を書き換えない。`PrivateNote` に setter も無い）。

## 検討した選択肢と決定

### 決定 1: 「1 編集」= 保存イベントを **30 秒の静穏窓**で畳み込んだ単位。`data.json` の journal に本文つきで積み、1 ファイル 50 件まで

| 案 | 評価 |
| --- | --- |
| A. 保存イベントごとに 1 版 | Obsidian は入力が止まるたび（約 2 秒）に保存する。1 段落を書く間に何十版も刻まれ、決定 16 の保持上限（直近 50 版）を数分で使い切る。「変更履歴を追跡できる」という決定 8 の目的に反して履歴がノイズになる |
| **B. 静穏窓（30 秒）で畳み込む（採用）** | 窓の中の連続保存は同じ編集（内容は最後の保存）、窓を超えて空いたら次の編集。「考えて書き、少し止まる」を 1 編集に写す。オフラインで 10 回（各 30 秒以上空けて）保存すれば 10 版になる（受け入れ基準） |
| C. 編集セッション（ファイルを閉じる／別ファイルへ移るまで） | Obsidian の「閉じる」はタブ運用に依存し、開きっぱなしのファイルは 1 日 1 版になる。版の粒度が利用者の操作習慣に左右され過ぎる |
| D. 同期 1 回 = 1 版 | 決定 8 が明示的に退けている |

- journal は `data.json`（`journal.edits[localPath][] = {at, content}`）に**本文つき**で持つ。本文を持たないと
  中間版を送れない。1 ファイル **50 件**で古いものから落とす（サーバも直近 50 版しか保持しない。決定 16）。
  トークンは引き続き持たない（`IADR-0338` 決定 5）。
- 同期中の自分の書き込み（pull）が発火させる保存イベントは拾わない（`syncing` で抑止）。遅れて届いた分は
  push 側が「最終同期時の内容と同じ先頭の編集」として落とす（`collectEdits`）。
- 窓の値（30 秒）は定数であり設定に出さない（設定項目を増やすほどの根拠が無い。CLI だけ環境変数
  `MSP_EDIT_QUIET_MS` で実測用に 0 にできる）。

### 決定 2: push の計画規則 —— 追跡状態・journal・同期フォルダの走査から決め、**削除と同期停止を区別**する

| ローカル（同期フォルダ配下の `.md`） | 追跡状態 | journal | 判定 |
| --- | --- | --- | --- |
| 在る | 未追跡 | 任意 | `create`（`noteId` 無し。edits = journal ＋ 最後と違えば現在の内容） |
| 在る | 追跡済み・内容が最終同期時と同じ | 編集なし | `unchanged` |
| 在る | 追跡済み | 編集あり or 内容が変わった | `update`（`baseVersion` = 状態の版＝楽観ロック） |
| 無い | 追跡済み | `deleted` | `delete`（論理削除を送る。決定 5） |
| 無い | 追跡済み | `movedOut` | `untrack`（同期停止。**削除は送らない**。決定 4） |
| 無い | 追跡済み | 記録なし | `missing-local`（報告のみ。**削除は送らない**＝安全側） |
| 在る（新パス） | 追跡済み（旧パス） | `renamed` | `rename-local`（紐付けだけ更新）→ 続けて内容で判定 |
| 任意 | `serverDeleted` | 任意 | `server-deleted`（競合として提示。ローカルが無ければ外すだけ） |
| — | 追跡済みだが同期フォルダの外 | — | `untrack`（設定変更で外れた。削除は送らない） |

- 「削除」と「同期停止」の区別は **Obsidian のイベントの種類**（`delete` か `rename` で外へ出たか）で付ける。
  イベントを見ていない間（プラグイン無効時）に消えたファイルは区別できないので**削除を送らない**
  （`missing-local`）。削除の伝播は取り返しが付きにくい向きなので、判らないときは送らない。

### 決定 3: 409 は**上書きせず**、利用者の 3 択（ローカル採用／サーバ採用／両方残す）を待つ。解決の実体は Obsidian 非依存

- `pushSync` は 409 `version_conflict` を受けたら状態も journal も進めず、競合として報告するだけ。
  🔴 **`serverVersion` を積み直して即再送する実装は後勝ちの自動解決であり、決定 7 に反する**。
  変異試験（`pushSync.ts` の 409 分岐を自動再送に書き換える）で `pushSync.test.ts` 1 件と
  `conflictResolver.test.ts` 4 件が落ちることを確認した（仕様書 §実測記録）。
- 3 択の意味（`conflictResolver.ts`）:
  - **ローカルを採用**: サーバの現在版を `pull` で読み、その版を `baseVersion` に積んでローカルの編集列を
    再 push する。サーバ側の編集はローカルの編集の前の版として履歴に残る（KB が正。決定 14）。
  - **サーバを採用**: サーバの本文でローカルを上書きし、未送信の編集列を捨てる。
  - **両方残す**: ローカルの内容を `<名前> (ローカル YYYYMMDD-HHmm).md` に写して新規 push し、元のパスは
    サーバの本文にする（`docs/api` の契約説明「別パスで新規 push」どおり）。
  - 解決の途中でサーバがまた進んだ／消えたら**実行せず `retry`** を返す（追いかけない）。
- 提示は Obsidian の `Modal`（`obsidian/conflictModal.ts`）。**「保留」で閉じれば何もしない**（次の同期で
  また提示される）。CLI ハーネスは `resolve <path> local|server|both` で非対話にし、実 HTTP の証跡を取れるようにした。
- 差分の 2 ペイン表示は置かない（版番号・未送信の編集数・更新時刻で選べる。必要になったら後続）。

### 決定 4: サーバ側削除（論理削除・完全削除）は**ローカルを消さず**、状態に印を残して push 側で提示する

| 案 | 評価 |
| --- | --- |
| A. ローカルも消す（ゴミ箱へ） | サーバの誤削除がそのまま端末へ伝播する。論理削除は 90 日復元できる（決定 5）のに、端末側は利用者が気付く前に消える |
| **B. 消さず、状態に `serverDeleted` を残して提示する（採用）** | 利用者が「ローカルを採用（新規として再作成）」「サーバを採用（ゴミ箱へ）」を選ぶ。両側で消えていれば黙って追跡を外す |
| C. 何もしない（第 1 段の件数通知のまま） | 追跡が残ったまま push すると 409 `deleted` になり続ける |

- manifest から**行が消えた**（完全削除）場合も区別できないので同じ扱い（フォローアップ 11 ②への回答:
  **サーバ側の完全削除はローカル Vault のファイルへ及ばない**。利用者が選ぶ）。
- 「ローカルを採用」は**新規として**再作成する（旧 ID は削除済みのまま。復元は画面 SC-19 の仕事）。

### 決定 5: リネーム —— サーバ → ローカルは**移動**で追随し、ローカル → サーバは**紐付けだけ更新して伝播しない**（契約に口が無い）

- 状態に**サーバの `vaultPath`** を持ち、manifest の `vaultPath` が変わったら新パスへ書き、旧パスが最終同期時の
  ままなら消す（ゴミ箱）。編集されていれば残して報告する（PR #1156 の AI レビューが指摘した旧ファイル残置への回答）。
- ローカルのリネーム（フォルダ内）は journal の `renamed[new] = 元パス` で追跡の紐付けを更新する。
  push の `vaultPath` には新パスを載せるが、**サーバは更新時に `VaultPath` を無視する**ので伝播しない。
  利用者には「ナレッジベース側の名前は変わりません」と通知する。契約へ `vaultPath` の更新を足すのは
  別 issue（宣言ファイル領域外）。
- 第 1 段の状態（`vaultPath` 無し）はそのまま読める。`vaultPath` が無ければサーバ値を正として扱い、
  `up-to-date` のときに第 2 段の形へ揃える（ファイルは触らない）。

### 決定 6: ポートの拡張と同期の契機

- `FileStore` に `list`（フォルダ配下の `.md`）/ `remove`（Obsidian は `trashLocal`＝復元できる）/ `rename` を足す。
  プラグインが**消す向き**の操作をするのは「サーバを採用」と「サーバ側リネームの旧パス」の 2 つだけで、
  どちらもゴミ箱経由。
- 同期の契機は**手動**（コマンド「同期する（取り込み → 送信）」／設定タブのボタン）。pull を先にするのは
  サーバ側の削除・リネームを先に取り込み、409 を減らすため。保存のたびの自動 push は計画に無く、後続。
- journal の書き込み（Vault イベント）は 1 秒のデバウンスで `data.json` へ保存する。

## 理由

- **決定 1** は決定 8 の「編集回数どおり」を、Obsidian の保存の実態（数秒ごと）と決定 16 の保持上限（50 版）の
  間で成り立たせるため。窓の値は「考えて書き、少し止まる」に寄せた実装値であり、計画の裁定は要しない
  （計画が実装設計へ委ねている）。
- **決定 2・4** は「消す向きの操作は判らなければ送らない」で一貫させるため（決定 4・5・7 の共通の意図
  ＝利用者の知らないうちに片方が消えない）。
- **決定 3** は決定 7 の直接の帰結。自動再送は最も書きやすい実装だが、まさにそれを禁じている。
- **決定 5** は契約を変えないという #1153 の制約の帰結。契約に口が無いことは走査で確かめた（仕様書 §母集合）。

## 結果

- 良い影響:
  - `ADR-0037` 決定 2（双方向）に到達した。編集・新規作成・削除がサーバへ届き、競合は 3 択で解ける
  - 実 HTTP で 10 版・409 → 上書きなし → 解決・論理削除・同期停止を 1 往復ずつ確かめた（仕様書 §実測記録）
  - プロトコル部は Obsidian 実体なしで 67 件のテストが固定し、楽観ロックを外す変異を検出する
- 悪い影響・トレードオフ:
  - 🔴 **ローカル → サーバのリネームは伝播しない**（契約に口が無い。別 issue）
  - journal は本文を `data.json` に持つ（最大 50 件 × 1 MB／ファイル）。Vault と一緒に複製される
    （業務資料の複製先が増えるわけではない——同じ Vault の中）
  - 自動同期が無い。同期し忘れれば競合は増える
  - 「サーバを採用」はゴミ箱経由とはいえローカルの未送信編集を捨てる（利用者が選んだ結果）
- フォローアップ:
  1. サーバ契約に `vaultPath` の更新（リネーム）を足す（#1176）
  2. 自動同期（保存のたび／一定間隔）—— 必要になったら
  3. `IADR-0338` フォローアップ 1（エッジ公開 #1154）・3〜5 はそのまま
