# IADR-0383: 木から導ける値は live 文書の本文に書かず正本を指す

- 状態: Accepted
- 日付: 2026-09-05
- 決定者: 実装（claude）。フェーズ末監査バッチ③（#1249 / #1250 / #1251）の是正として

## 起点・関連

- 関連する計画書 ID: `NFR`（文書統制のメタ作業。計画側の非機能要件表に当たる番号は無い）・
  `ADR-0065` / `ADR-0068`（サービス標準構成・Tests 鏡写し）・`ADR-0030` / `ADR-0041`（バックエンド標準ライブラリ）・
  `ADR-0031`（フロントエンドスタック）
- 関連する実装仕様書: `.ai-context/specs/20260905_issue-1249-1250-1251_rotten-derived-values.md`
- 関連 IADR: `IADR-0334`（鏡写し先の解決）・`IADR-0371`（参照実装 1 本）・`IADR-0361`（空枠の禁止と機械検査）

## コンテキストと課題

フェーズ末監査バッチ③が、live 文書（`docs/` と `src/**/README.md`）に残った **導出値の腐り** を 3 件起票した。
導出値とは「リポジトリの木か、計画側の状態から機械的に導ける値」である —— 件数・比率・列挙・状態語。

| # | 腐った記述 | 実測（2026-09-05） | どう腐ったか |
| --- | --- | --- | --- |
| #1249 | 「計画側条文の改定を**環流中**である」（`docs/tech/tech-requirements.md` 2 箇所・`src/README.md` 1 箇所） | `ADR-0065` は Accepted（2026-08-30）、計画側条文も同日改定済み、環流 planning#490 は closed | **計画側が動いたのに実装側の現況記述が置いていかれた。** #1146 は同じ主張を雛形 README でだけ直し、誤りの側の語（`環流中`）で母集合を引き直さなかった（規則 9 の破れ） |
| #1250 | 「knowledge features は `home, sc01..sc11`」（`src/platform/frontend/README.md` ＋ **`src/README.md`**） | `sc01`〜`sc12`・`sc17`〜`sc21` の **17 件**。`home` は無い | **木が動いたのに列挙が置いていかれた。** 2026-07 に書かれ、その後の画面追加に追随しないまま 2 つの PR がこのファイルを編集して通過した（規則 10 の破れ） |
| #1251 | 「実測 2026-09-04: FluentValidation `PackageReference` **0 件**・Riok.Mapperly **0 件**・`Platform.Shared.Kernel` の `ProjectReference` **0/14 サービス**」 | それぞれ **2 件 / 2 件 / 1 件（1/14）** | 🔴 **その文を書いた PR 自身が、同じコミットで 3 つとも偽にした**（`FeedbackService` へ 3 種すべてを同時投入した）。issue は `Kernel` だけを挙げていたが、走査したら**同じ文の 3 つ全部**が腐っていた |

同型の事故はこれで**少なくとも 3 回目**である（#1064 の issue 本文が「4/14」と書いて実測 0/14 だった →
#1232 が「0/14」と書いて自分で 1/14 にした → 本 3 件）。CLAUDE.md の「検査器の追加は同型の事故が
2 回起きたら」の条件は満たしている。**決めるべきことは 2 つ**である:

1. 腐った値を**書き直す**のか、**本文から外す**のか
2. 機械検査を足すのか

## 検討した選択肢

### 選択肢 A: 値を書き直し、時点（`実測 YYYY-MM-DD`）を添える

- 利: 現況が一目で分かる。既存の書き方（`実測 2026-08-21: …`）と揃う
- 欠: 🔴 **次に木が動いた瞬間にまた腐る。** #1251 は **同じコミットの中で**腐っており、時点を添えても
  「その時点では正しかった」以上の防御にならない。しかも `Kernel` の比率は #1230 / #1248 が
  残りのサービスへ展開するたびに動く —— **本作業のマージ待ちの間にも動きうる**

### 選択肢 B: 値を本文から外し、正本（実体・走査コマンド）を指す

- 利: **書かれていない値は腐らない。** 読み手は正本へ行くので、常に現在の値を得る
- 欠: 「今どうなっているか」を知るのに 1 手かかる。歴史的な経緯（何件から何件へ減らしたか）は表現できない

### 選択肢 C: 機械検査（`scripts/check-*.js`）を足して、腐った値を CI で落とす

- 利: 書き方を変えずに再発を止められる
- 欠: **述語が閉じない**（後述）

## 決定

1. **live 文書の本文には、木から導ける現況の値（件数・比率・列挙）を書かない**（選択肢 B）。
   代わりに **(a) 実体そのもの**（`knowledge/frontend/src/features/index.ts` 等）か
   **(b) 数え直すための走査コマンド**を書く。本作業では次のとおり置き換えた。

   | 直した箇所 | 置き換え先 |
   | --- | --- |
   | `docs/tech/tech-requirements.md` §浸透の状況 の「0 件 / 0 件 / 0/14」 | 「**着手前はいずれも参照が 1 つも無かった**」（着手前の事実）＋ 現況を数える `git grep` の一行 |
   | 同 「残り 13 サービスへの展開は別 issue が持つ」 | 「残りのサービスへの展開は別 issue が持つ」 |
   | 同 『Tests』の段落の「実装の現況は **14 サービス全件**が…旧名は **0 件**である」 | 「規約は全サービスへ適用済みで旧名は残っていない」＋数え直す `git ls-files` の 2 行。🔴 **この行は値としては正しかった**（実測 14/14・0 件）が、**本決定を立てる当の段落**にあり、残せば #1251 と同型の「自分の変更で自分の記述を置いていく」になる |
   | `src/platform/frontend/README.md` / `src/README.md` の「`home, sc01..sc11`」 | 「`sc<NN>-<name>`。一覧の正本は `features/index.ts`」 |
   | `src/platform/frontend/README.md` の「Zustand は 1 本だけで、その 4 つの参照元が…」 | 「`components/ai-chat/` に閉じている」＋ 数える走査コマンド |

2. **時点つきの歴史記述（「実測 2026-08-21: `.csproj` 14 → **0**」）は本決定の対象外**である。
   これは**過去に起きた出来事**の記録であり、木が動いても偽にならない。
   🔴 **区別の基準は「現在形で現況を述べているか」**である —— 「〜である」は腐り、「〜へ移した」は腐らない。

3. **状態語（`環流中` / `未達` / `改定待ち`）も導出値として扱う。** 相手の状態（計画 ADR の `status`・
   環流 issue の open/closed）から導ける値だからである。書くなら**時点を添える**か、
   **相手を指す**（`ADR-0065` の状態が正本、と書く）。

4. **機械検査は足さない**（選択肢 C を採らない）。理由は次節。

## 理由

### なぜ値を外すのか（A ではなく B）

**#1251 は「時点を添えれば防げる」という仮説の反証そのもの**である。あの文には
`実測 2026-09-04` と時点が添えてあった。それでも、**同じコミットが同じ日のうちに偽にした**。
時点は「いつの値か」を伝えるが、「もう違う」ことは伝えない。読み手は時点を読み飛ばして現況として受け取る。

一方、書かれていない値は腐りようがない。指し先（`features/index.ts`・`.csproj` の木）は
**その値の定義そのもの**なので、定義と記述が乖離する余地が構造的に無い。

### なぜ検査器を足さないのか（C を採らない）

条件（同型の事故 2 回）は満たしているが、**満たしていることは足す義務ではない**。3 つの形の
いずれについても述語が閉じないことを、実測で確かめた。

| 候補の述語 | なぜ閉じないか（実測） |
| --- | --- |
| `N/14` 型の比率を禁じる／木と突き合わせる | 分母 `14` 自体が導出値であり、サービスが増えれば検査器の期待値も動く。また `src/vitest.config.ts` の `6290/6498`（カバレッジ）のように**同じ形で無関係な値**が live に在る |
| `N サービス` を木と突き合わせる | live だけで **30 行以上**当たり、そのほぼ全部が正当である —— 「RabbitMQ を使う **7 サービス**」「申告を集める **3 サービス**」は全体数ではなく**特定の集合の濃度**を述べている。機械には区別できない |
| `scNN..scNN` の範囲短縮形を禁じる | これは閉じる。**しかし本作業で live の該当は 0 件になる**（残る 2 件は凍結記録で、検査対象から外れる）。**「もう本文に無い値」を見張る検査器**になり、`scripts/` へ 1 本足す対価に見合わない |

加えて、**機械化できる部分は既存の検査器が既に持っている**:

- 指し先の実在 —— `check-doc-links.js`（`docs/` と `.ai-context/` の相対リンク）と
  `gen-knowledge-graph.js --check`（trace ブロックのエッジ先）
- 木の側の不変条件 —— `check-scaffolding-frames.js`（空枠の残置。`IADR-0361`）

つまり **B を採ると、既存の検査器の射程が自動的に伸びる**（値を消して指し先に置き換えるほど、
「実在するか」という既に機械化された述語で守られる範囲が増える）。C は逆に、値を本文に残したまま
新しい述語を増やす方向であり、**必読規約と検査器の総量を増やして守りは弱い**。

🔴 **この判断は「今後も検査器を足さない」ではない。** 閉じた述語が見つかった時点で足せばよい。
本 IADR が固定するのは**書き方の側**（導出値を本文に置かない）であり、それは検査器の有無に関わらず効く。

## 結果

- 良い影響:
  - 是正した箇所の大半から**現況の数・列挙そのものが消えた**ため、木や計画側が動いても偽にならない（残したのは着手前の事実と、数え直すための走査コマンドである）
  - `#1230` / `#1248` が残りのサービスへ計画スタックを展開しても、`tech-requirements.md` を追随させる
    義務が発生しない（**並行作業の追随点が 1 つ減った**）
  - 「現在形で現況を述べているか」という、走査ではなく**読めば判る**判別基準が言語化された
- 悪い影響・トレードオフ:
  - 現況を知るのに走査が 1 手要る。特に `浸透の状況` は「どれだけ進んだか」を文書だけでは読めなくなった
    —— 進捗の正本は issue（`#1230` / `#1248`）であり、文書ではないと割り切る
  - 検査器を足さないので、**この規範を守っているかを見る機械は無い**。`traceability.md` の
    母集合規則と同じく、**作業仕様書のレビューで人が見る**前提で運用する
- フォローアップ:
  - 🔴 **`docs/tests/TEST_STRATEGY.md` の 2 箇所に同型の現在形の導出値（「14 サービス全件」）が残る。**
    本作業の 3 回目の引き直しで見つけた。**値は正しく腐ってはいない**が決定 1 の対象であり、
    本 PR の宣言ファイル領域の外なので**別 issue へ切り出す**（並列作業の直列化を避けるため）。
    **「本作業で live の該当を 0 件にした」とは書かない** —— それ自体が、この IADR が戒めている
    「引き直さずに 0 と断じる」記述になる
