# IADR-0636: 論理削除した個人資料を見つかる面から外し、復元で戻す（#2138）

## コンテキストと課題

論理削除（SC-19 の削除・Obsidian 側の削除）は台帳に印を付けるだけで、イベントを出さなかった。露出が ON の資料は 90 日間、所有者と共有先の
横断検索・グラフ・AI 入力・MCP のツール検索に残り、共有先は SC-03 と MCP の ID 指定の取得で開けた。削除中でも露出を ON にでき、ON にすると索引に載った。
計画 ADR-0142 が「削除で撤収し、復元で載せ直す」と裁定した。決めることは、(1) 撤収と載せ直しの形、(2) 削除中に他の経路が出す発行の扱い、
(3) 読み取りの判定への入れ方、(4) 露出の変更の拒み方、(5) 削除中の共有の変更（ADR-0142 フォローアップ 3。計画は未決）。

## 検討した選択肢

撤収の形:

1. **論理削除で `DocumentDeleted` を出す** —— 受け手（検索・グラフ）は完全削除と同じ片付けをする。グラフの削除は却下済み AI 提案とリンク先の名前まで消す
   （`GraphDocumentSyncConsumer.WithdrawAsync` の注記: それは削除イベントの担当で、撤収では残す）。**復元で却下した提案がよみがえる。** 採らない。
2. **契約に削除中の印を足す**（`DocumentUpdated` に項目、または状態の値） —— 受け手 3 つ（取り込み・グラフ・Wiki）すべてに門を足す変更になる。採らない（3 を上回る利点が無い）。
3. **露出 3 キーを `excluded` にした撤収の形の `DocumentUpdated` を出す（採用）** —— 受け手は既に ON → 全 OFF の撤収を持つ（ADR-0061 決定 4。取り込みは全索引から点を消し、
   グラフはノードと辺だけを消して却下済み提案を残す）。受け手の変更が無い。台帳の露出は変えない（ADR-0142 決定 1「露出 3 トグルの値は保つ」）。

削除中の他の経路（共有の付与・取り消し・タグの改名・再発行・管理者の属性の全置換）の扱い:

- a. 経路ごとに削除を確かめる —— 経路を足した人が忘れると、削除中の資料が載り直す。採らない。
- b. **唯一の発行点（`DocumentEndpoints.PublishUpdatedAsync`。`private`。IADR-0455 で全経路がここを通る）で台帳を引く（採用）** —— 削除中なら必ず撤収の形になる。

読み取りの判定:

- a. 一覧・個別の各呼び出し点で削除中を先に弾く —— 判定器が 2 つになる（`DocumentReadAccess` の「唯一の判定点」が崩れる）。採らない。
- b. `DocumentReadAccess` に DB を持たせる —— 一覧で文書ごとに問い合わせになる。採らない。
- c. **`CanReadAsync` が論理削除を必須の引数で受ける（採用）** —— 呼び出し点は共有先と同じく 1 クエリで引いて渡す。必須なので、渡し忘れはコンパイルで止まる。

## 決定

### 決定 1: 撤収と載せ直しは、唯一の発行点で台帳を引いて形を選ぶ

- `PublishUpdatedAsync` は、個人資料で台帳 `PrivateNote.DeletedAt` が埋まっていれば、属性の露出 3 キーを `excluded` に置き換えた写しで発行する
  （`DocumentExposure.WithAllExcluded`。台帳の `Document.Attributes` と `PrivateNote` の露出は変えない）。それ以外は従前どおり台帳の属性で発行する。
- 論理削除の 2 経路（SC-19・Obsidian）は、**削除の状態が変わったとき**に門（`SaveChangesAndPublishUpdatedIfIndexableAsync`）を通して確定と発行を 1 トランザクションで行う。
  露出が 3 つとも OFF の資料は門で止まり、何も出さない（索引に無いまま。ADR-0061 決定 2）。削除済みへの再削除は何も出さない。
- 復元も同じ門を通す。台帳はもう削除中でないので、台帳の露出のまま発行される（1 つでも ON なら載り直す。ADR-0142 決定 4）。
- 削除中に他の経路が門を通っても、発行は撤収の形になる（削除中に載り直さない）。

### 決定 2: 読み取りの判定は論理削除を必須の引数で受ける

- `DocumentReadAccess.CanReadAsync(principal, doc, sharedWith, privateNoteDeleted, ct)`。個人資料で `privateNoteDeleted` なら、門の開閉・主体に依らず偽。
  所有者にも共有先にも返さない（ADR-0142 決定 2 と 2026-10-24 の補完。SC-03・MCP の `get_document` / `list_documents` が同じ判定を通る）。
- 呼び出し点 5 か所は、共有先と同じく台帳から引いて渡す（一覧は 1 クエリ、個別は 1 件）。読めない文書は「文書が無い」と同じ扱い（404。ADR-0056）。
- SC-19 の削除済みタブ・Obsidian の同期（所有者の端末の経路。`IsDeleted` を運んで端末側で消させる）・緊急アクセス（IADR-0610 条件 ⑤ で既に拒む）は、この判定を通らない。変えない。

### 決定 3: 削除中の露出の変更は 409 で拒む

- `PUT /private-notes/{id}/exposure` は、削除中なら台帳を変えずに 409 `{ error: "deleted", purgeAt }` を返す（同期の push が削除済みへの更新を拒む形と同じ。ADR-0142 決定 3）。

### 決定 4: 削除中の共有の変更は許す（ADR-0142 フォローアップ 3 の選択）

- 共有の付与・取り消しは削除中も許す。共有の取り消しは ADR-0142 決定 6 の暫定手段として使えるべきであり、許しても見えるようにはならない
  （発行は決定 1 で撤収の形、読み取りは決定 2 で拒む）。この選択を計画へ環流した（planning#845）。

## 結果

- 良い影響: 削除した個人資料が、共有先を含む全員の横断検索・グラフ・AI 入力・MCP のツール検索から消え、SC-03 と MCP の取得でも開けなくなる。復元で露出の設定のまま戻る。
  受け手（取り込み・グラフ・Wiki）の変更は無い。
- 悪い影響 / トレードオフ:
  - 撤収の形のイベントは、露出の値について台帳と違う値を運ぶ（台帳は ON のまま）。運ぶのは「いま索引に載せてよいか」であって台帳の写しではない、と読む。
  - 個人資料の発行のたびに台帳を 1 件引く（共有先の解決と同じ桁）。
  - 🔴 **残余リスク（順序）**: 論理削除・復元はイベントの版（`Document.UpdatedAt`）を進めない（版を進めると版履歴と同期の並行トークンが動く。露出の変更と同じ扱い）。
    受け手は等しい版を反映するので、正しい順に届けば収束する。再試行で順序が入れ替わると（削除 → 復元〔埋め込みの一時失敗で再試行待ち〕→ 削除 → 復元の再試行が後着）、
    削除中の資料が載り直し得る。**同じ窓は露出の変更（ON → OFF → ON）に従前からある**（IADR-0595 は等しい版を反映すると決めた）。版を持たない状態変化の順序づけは #2251 で扱う。
- フォローアップ:
  - 削除中の共有の変更を許したこと（決定 4）を計画へ環流した（ADR-0142 フォローアップ 3 → planning#845）。
  - 版を持たない状態変化（露出・論理削除・復元）の順序づけ（上の残余リスク）→ #2251。
  - SC-19 の削除確認の文言（ADR-0142 フォローアップ 4。配備の後に足す 1 文）→ #2250。
  - 撤収の後の完全削除が実 Qdrant で失敗しないことの試験（ADR-0142 フォローアップ 1）は `Category=Integration`（Docker）であり、PR の CI では走らない。
    `integration.yml` の手動実行で確かめる。
