# IADR-0184: `check-feedback-dispatched.js` の取り込み方（#710）

- 状態: Accepted
- 日付: 2026-08-11
- 決定者: claude（実装）

## 起点・関連

- **NFR**（文書統制・運用保守。メタ作業なので無採番。[IADR-0179](./IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 1）
- 実装 issue: **#710**（出所: #707 の射程外宣言）
- 作業仕様書: [20260811_issue-710](../specs/20260811_issue-710_feedback-dispatched-checker.md)

## 文脈 —— **検査器を当てたら 1 件鳴った。そしてそれは偽陽性だった**

`feedback/` に記録は作ったが計画リポへ伝達していない、という滞留を警告する検査器が
キットに在り、**本リポだけ取り込んでいなかった**（キット `repo-template` **107 ファイル全数**で
突き合わせ、実質の未取り込みは**この 1 ファイルのみ**と確定した）。

**#707（PR #708）で実際に起きた事故 —— 3 件が最長 4 日据え置かれた —— は、これがあれば気づけた。**

キット原文を `feedback/` の **37 件**へ当てると **1 件**警告するが、**その 1 件は伝達済み**である。

| 手順（`feedback/README.md` は**両経路**を定める） | 当該記録 | 検査器が証拠と認めるか |
| --- | --- | --- |
| **記録ファイル経路**（`draft/feedback/` へコピー） | **完了**（PR planning#306） | **認めない** |
| GitHub Issue 経路 | 実施しない（一方で足りる） | 認める |

> **★ 偽陽性の原因は本リポの書き方ではなく、キット内部の不整合である。**
> **キット自身の `feedback/README.md` が両経路を定めているのに、キットの検査器は片方しか読まない。**

## ★★ 決定 1: **キット原文をそのまま置く。検査器を書き換えない**

[IADR-0115](./IADR-0115_impl-handoff-kit-as-single-source.md) 決定 2 が許す固有デルタは **4 種のみ**で、
**「検査器の判定ロジックを本リポ向けに調整する」はどれにも当たらない。**
**書き換えれば次の同期で消える**（同決定「これ以外の独自記述は同期時に削除する」）。

**同 決定 3 が「汎用的な改善はキットへ環流する」と定める。** 記録ファイル経路を証拠と認めるのは
**キット全体に効く汎用の改善**なので、**本リポで直さず環流する**（決定 4）。

**バイト一致であることを回帰テストで固定する** —— 分類 A は `diff` で機械判定できる、が IADR-0115 の前提である。

## ★★ 決定 2: **偽陽性を消すために、記録へ嘘を書かない**

**キットの 3 条件を、この記録が真として満たす方法は無い。**

| 条件 | 当てはめると |
| --- | --- |
| `planning_issue:` | **planning#306 は PR であって issue ではない**。issue 番号を名乗る鍵へ PR 番号を書けば誤りになる |
| 他リポの issue URL | **存在しない**（伝達は PR 経路） |
| 本文に「起票済み」 | **起票していない**（README が認める別経路を採った） |

**検査器を満たすためだけに別途 issue を立てるのも採らない** ——
記録自身が「いずれか一方で足りる」と書いた運用に反し、**検査器に合わせて事実の側を作りにいくこと**になる。

**したがって 1 件の警告は残す。** 警告であって失敗ではないので（**exit 0**）、**CI は緑のまま**である。
**既知の偽陽性であることと、環流先の issue 番号を記録に添える。**

> **★ #710 の受け入れ基準は「警告 0 件」と書いていた。** それは**キットが両経路を読める前提**での基準であり、
> **実測でその前提が成り立たないと分かった。基準の側を改める** —— 満たすために記述を歪めない。

## ★ 決定 3: **ステップはキットどおり。ただし独立ジョブにする（差異を明記する）**

キットの `ci.example.yml` と**同じ 2 ステップ**（`--self-test` → 本実行）を足す。
**厳格化の env はコメントのまま**にする —— **起票は人手の判断を伴い、ブロックにすると
「記録を作らない」という回避策を誘発する**（キットの設計意図。[IADR-0183](./IADR-0183_false-green-warning-on-worktree-state.md) 決定 1 と同じ理屈）。

**ただしジョブ構造はキットと変える。** キットは **`doc-links` ジョブへ追記**する形だが、
**本リポは独立ジョブ `feedback-dispatched` にする。**

| | キット | 本リポ | 理由 |
| --- | --- | --- | --- |
| ジョブ | `doc-links` に相乗り | **独立** | **必須チェックの context は「ジョブ名」**（[IADR-0182](./IADR-0182_required-check-contexts-and-blocked-record.md) 決定 1）。相乗りだと**単独では必須にできず**、`doc-links` の失敗に結果が埋もれる |
| コスト | checkout 1 回 | **checkout が 1 回増える**（実測 十数秒） | 上の利点に見合う |

**CI 配線は [IADR-0115](./IADR-0115_impl-handoff-kit-as-single-source.md) 決定 2 が許す固有デルタ（2. 技術スタックとその CI 配線）に当たる。**
**ただし「許される」と「記録されている」は別である** —— **明記しないと、次の同期で
「配線もキット原文どおりのはず」と照合されて気づかれない。**

> **★ 実装中にキット側の欠陥を見つけた。** キットの `# env:` は **`steps:` のリスト項目と同じ字下げ**にあり、
> **コメントを外すと YAML として不正になる**（リスト項目の並びに mapping キーが混じる）。
> **本リポは job 直下（4 字下げ）に置いたので、外せばそのまま効く。** 環流する（決定 4）。

## ★ 決定 4: **キットへ環流する（4 件）**

| # | 内容 |
| ---: | --- |
| 1 | **検査器が記録ファイル経路を証拠と認めない**（`README.md` は両経路を定める） |
| 2 | **`feedback/TEMPLATE.md` に `planning_issue:` が無い** —— **だから条件 a は 0 / 37 で誰も使っていない** |
| 3 | **本文の語の一致だけで発火する** —— **検査器について書いた記録が自己発火する**（本作業中に踏んだ） |
| 4 | **`ci.example.yml` のコメント `env:` が `steps:` のリスト項目と同じ字下げにある** —— **外すと不正 YAML になる** |

**2 件目は本リポでは直せない** —— `TEMPLATE.md` は**キットとバイト一致（分類 A）**である。

**4 件目は 3 箇所を全数で見て 2 件**である（`doc-links` / `ai-workflow-config`）。
**`scripts-tests` の 1 件は step 直下（8 字下げ）なので正しい** —— **字下げの深さだけが分かれ目であり、
「`# env:` がある」で数えると 3 件と誤る。**

## 決定 5: **本検査器は [IADR-0183](./IADR-0183_false-green-warning-on-worktree-state.md) のクラス C である**

`fs.readdirSync` で作業ツリーを読み、**git を一切呼ばない**。**順序で結果が変わらない**ので
順序警告を**足さない**（足せば嘘になる）。**#709 で新設した分類の回帰テストが機械的に確かめる**
（検査器の母集合が **32 → 33 本**になる）。

## 結果

- 良い影響
  - **#707 型の滞留（記録は作ったが伝達していない）に、初めて機械の目が付いた**
  - **キットとの差分が 0 になった** —— 実質の未取り込みはこの 1 ファイルだけだった
  - 分類 A のバイト一致を**回帰テストで固定**したので、うっかり手を入れると落ちる
- 悪い影響・トレードオフ
  - **既知の偽陽性が 1 件、環流が反映されるまで鳴り続ける**（決定 2）。**warn なので CI は緑**
  - **条件 a（`planning_issue:`）は当面 0 / 37 のまま** —— 雛形に無いので誰も書かない（決定 4 の 2 件目）
  - **`status` 語彙が未定義**なので、`open` が「未伝達」なのか「裁定待ち」なのかは検査器も読み分けられない（別 issue）
- フォローアップ
  - **環流 4 件は planning#319 として起票済み**（`docs/README.md` 運用ルール 5: **起票まで済んで初めて「環流した」と書ける**）。裁定待ち
