# IADR-0560: 文書管理の一覧のタブ（機械の収集と人の文書）と追加の絞り込みは BFF が ABAC の後に当て、データソースは BFF が文書ごとに 1 つの鍵に導く

## コンテキストと課題

段 1（IADR-0537）と段 2 の前半（IADR-0545）で、一覧はページ・並べ替え・表題の部分一致・状態の絞り込み・状態別の件数を持った。
残りの依頼は次の 4 つの判断を要する。

1. **データソースをどう定めるか。** 一覧の契約（`DocumentDto`）にデータソースが無い。台帳には取り込み元の表示名（`DataSourceName`）があるが、
   台帳の大半を占める AST の情報収集の文書は API（`POST /documents`）で書かれ、`DataSourceName` を持たない（出典名は属性 `source` にある）。
2. **絞り込みと件数をどこで当てるか**（データソース・機密区分・タグ・プロジェクト・保存日）。
3. **機械の収集と人の文書をどう見分けるか**（タブか既定の絞り込み）。
4. **元の URL と本文のプレビューをどの口から出すか。**

## 検討した選択肢

### データソース

1. **BFF が文書ごとに 1 つの鍵へ導く（採用）。** 順に `ds:<DataSourceName>`（コネクタの取り込み）→ `col:<属性 source>`（機械の収集）→
   `report`（属性 `kind` と `periodKey` を持つ確定報告書の写し）→ `manual`。材料に足りない `DataSourceName` だけを契約へ足す。
2. **台帳に「データソースの種類」の列を足し、後段が書く（棄却）。** 既存の約 4 万件へ遡及して書く移行が要り、API の書き手（AST）にも
   新しい項目を送らせる変更が要る。導出で足りる事実を台帳に二重に持つことになる。
3. **`DataSourceName` だけを使う（棄却）。** 台帳の大半（AST の収集）が「データソースなし」に潰れ、源ごとに分ける依頼を満たさない。

### 絞り込みと件数の位置

- **IADR-0545 決定 2 と同じく BFF が ABAC の後に窓の述語で当てる（採用）。** 全体の件数・データソース別・プロジェクト別の件数を
  同じ 1 周で数えられ、費用は増えない。後段へ渡す形の棄却理由（全体の数のために 2 周目が要る・ABAC の実施点が BFF）は IADR-0545 のとおり。
- 値は**序数の完全一致**（表題だけが部分一致）。画面は件数の鍵・タグ辞書・固定の語彙から選ぶので、表記揺れを吸収する必要が無い。
- 保存日は**作成日時**（台帳に保存された日時）とし、`createdFrom`（含む）・`createdBefore`（含まない）の ISO 8601 の瞬間で受ける。
  暦日と時刻帯の変換は画面が行う（利用者の時刻帯の 0 時。「まで」はその日を含むので翌日 0 時を送る）。BFF は時刻帯を知らない。

### 機械の収集と人の文書の見分け

1. **タブ（人の文書・報告書／機械の収集／すべて）で、既定は人の文書・報告書（採用）。** 依頼 8 の見出しは「既定の表示」であり、
   台帳の大半を占める機械の収集に人の文書を埋もれさせないことが目的である。タブに件数を添えるので、機械の収集は 1 押しで見える。
   タブはデータソースの鍵から導く（`col:` だけが機械の収集）ので、鍵と別の規則を持たない。
2. **既定を「すべて」にし、タブだけ置く（棄却）。** 従前の URL と表示は変わらないが、開いた時点の見にくさ（依頼の本旨）が残る。
3. **既定の絞り込みを帯の条件に入れる（棄却）。** 「条件を解除」で外れて全件に戻り、見分けの意図が操作のたびに消える。
   タブは見せ方として「条件を解除」の外に置く。

### 元の URL とプレビュー

- 元の URL は台帳の `OriginalUri`（API の書き手が渡す元の所在。AST の収集ではニュース・開示の URL）を**契約へ足す**。
  書き手の申告で検証していないので、画面は `http(s)` のときだけリンクにする（`noopener noreferrer`）。
- プレビューは**文書詳細と同じ本文の口**（`GET /bff/documents/{id}/content`。ABAC は BFF・本文は文書サービス〔IADR-0544〕）を使い、
  画面が先頭 1,000 文字を素の文字で出す。一覧の応答へ本文の先頭を載せる形は、1 周の間に全件の本文を読むことになるので採らない。

## 決定

**決定 1: 契約に `DataSourceName` と `OriginalUri` を足す（どちらも末尾追加・既定 null）。**
`DocumentDto`、gRPC `DocumentSummary`（`optional` の 13・14。presence で null と空文字を分ける）、REST の写像（同名の列）。
`DocumentDto` の「部分射影」から 2 つを外した（`OriginalPath`・種別・添付・版履歴は引き続き出さない）。

**決定 2: `GET /bff/documents` に `origin`・`source`・`confidentiality`・`tag`・`project`・`createdFrom`・`createdBefore` を足す（どれも省略可。省略は従前の応答）。**

- `origin` は `curated` / `collected`、`confidentiality` は 4 値。未知の値は 400。`source` は 300 文字、`tag` / `project` は 100 文字まで（超えたら 400）。
  `project=(none)` は属性 `project` を持たない文書。日時が壊れている・`createdFrom >= createdBefore` は 400。どの 400 も後段を呼ばない。
- データソースの鍵の導出は BFF の `DocumentListSources` の 1 か所。応答に `sourceCounts`（鍵ごと）と `projectCounts`（プロジェクトごと）を足す。
  集合は `statusCounts` と同じ（ABAC 後・絞り込み前）。
- 🔴 1 周の中の順序は IADR-0545 のまま **ABAC → 全体・状態別・データソース別・プロジェクト別の数 → 絞り込み → 窓**。権限外の文書・他人の個人資料は
  どの数にも入らない（`BffDocumentListFacetTests` が、混ぜた台帳と混ぜない台帳の応答の一致で固定する。陽性対照つき）。

**決定 3: 画面（SC-05）は表の上にタブ（既定は人の文書・報告書）を置き、帯に条件を足し、データソース・タグの列と出典・プレビューを出す。**

- タブの件数はデータソース別の件数から導く。タブは「条件を解除」で外さない。
- 列の表示のためにデータソースの鍵を画面でも導く（`types/documentSource.ts`）。🔴 規則の正は BFF であり、画面の写しは BFF の試験と同じ例で固定する。
- プレビューは横のペイン（運用者にも出す）。台帳が本文なし・本文未設定と言う文書は本文を引かない。
- タブだけで 0 件なら「このタブの文書はありません。」と「すべての文書を表示」を出す（「文書はまだありません。」は全体が 0 件のときだけ）。

## 理由

- 依頼の絞り込みはどれも、画面が出す件数（全体・状態別・データソース別）と同じ集合の上の述語である。ABAC の実施点で 1 周する以上、
  そこに述語と数を載せるのが最も安く、存在秘匿の論証も IADR-0545 と同じ 1 本で済む。
- データソースを導出にしたので、台帳の移行も書き手の変更も要らない。足した契約は台帳に既に在る 2 列の写しだけである。

## 結果

- 試験: BFF `BffDocumentListFacetTests`（導出・各絞り込み・件数・後方互換・存在秘匿 2 種・許可ポリシーなし・検証）、契約 `DocumentReadGrpcMappingTests`、
  後段 `DocumentMapperTests`、画面 `DocumentManagementPage.test.tsx`（タブ・帯・列・プレビュー・タブの空）・`documentSource.test.ts`、e2e の SC-05 スモーク。
  変異で確かめた: データソース別の数を ABAC の前に数えると BFF の試験が 16 件赤になる。
- 配備の順序: 新しい画面と旧い BFF の組では、新しいクエリが無視され件数の項目が無い（画面は無い項目を空として読み、タブの件数は出ない）。
  新しい BFF と旧い document-service の組では、`dataSourceName` / `originalUri` が来ないので、データソースの取り込みが「手入力」に見え、出典が出ない。
  **BFF・document-service・フロントは同じリリースで出す。** 移行（DB）は無い。
- 既定の要求が `origin=curated` を持つようになった（従前の URL は `?offset=&limit=` だった）。

## 残余リスク

- **索引の状態の列は出していない。** 索引の状態は取り込み側（IngestionService）が検索の索引の点として持ち、文書ごとに引く口が無い。
  出すには「文書 ID の集合 → 索引の状態」を返す口と BFF の結合が要る（別 issue で扱う。IADR-0545 は #1908 の側としたが、#1908 は閉じている）。
- **データソースでの並べ替えは入れていない。** 並べ替えは後段のキーセット（台帳の索引）で行う（IADR-0545 決定 1）が、データソースは BFF の導出値である。
- 確定報告書の見分けは属性の形（`kind` と `periodKey`）に依る。AST が写像を変えたら追随が要る（`AstStaleCopyRules` と同じ前提）。
- 機械の収集の見分けは属性 `source` の有無に依る。人が画面から `source` 属性を付けた文書は機械の収集に数えられる（画面の作成フォームは `source` を出さない）。
- 1 要求ごとに台帳を 1 周する費用（IADR-0537）は変わらない。条件を変えるたびに 1 周する。
- 計画は絞り込みの選択肢を実装に任せたので、本決定の値を計画へ写さない。
