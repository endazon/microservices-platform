# IADR-0555: Loki のログ書き出しを分け目に揃えた窓で取り、窓ごとに件数を検算する（#1969）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

- 状態: Accepted
- 日付: 2026-10-17
- 決定者: claude（オーナーの起票 #1969。突き合わせと取りこぼさないページ送りを求められた）

## 起点・関連

- 起点 issue: #1969（PoC 2026-10-16。8 時間の書き出しで 259 行・587 行が欠け、終了コード 0）。関連: #1938・#1965。
- 関連する計画書 ID: NFR-18（運用の口の統制。前段は変えない前提として引く）。
- 関連する計画 ADR: ADR-0006（観測スタック）・ADR-0133（Loki の前段。本件は前段も到達の制限も呼ぶ道も変えない）。
- 関連する実装 ADR: [IADR-0543](./IADR-0543_operator-loki-read-path.md)（書き出しの道具）・[IADR-0553](./IADR-0553_loki-grpc-msg-size-and-export-default-limit.md)（既定の 1 ページ 1000 行）。
- 採番: `origin/develop` の最大は IADR-0554。開いている PR に IADR を足すものは無い（2026-10-17 に確認）。本件は **0555**。

## コンテキストと課題

- 書き出し（`scripts/export-loki-logs.js`）は「前のページの最大時刻から含めて次を取る」ページ送りである。**応答が時刻順の先頭 limit 件であること**を前提にしている。
- 手元の Loki 3.0.0（compose と同じ設定）で再現した（仕様書に数値）。**1 要求が query-frontend の分け目（`split_queries_by_interval`＝既定 1h）を跨ぐと、ある stream の分け目の直後の行が抜け、代わりに他の stream のもっと後の行が limit 件に入る。** 分け目の両側を別々に引くとどちらも正しい。ページの最大時刻が先へ飛ぶので、ページ送りでは取り戻せず、終了コード 0 で欠ける。
- 件数（`count_over_time`）は Loki 3.0.0 では両端を含まない (T − r, T) を数え、評価の時刻と幅はミリ秒である（実測）。瞬時のクエリも 1h で分けられ、分け目ちょうどの行を数えない（長い範囲の 1 本の件数は目安にしかならない）。
- 決めること: (1) どう取りこぼさないか、(2) どう突き合わせるか（区間の端の扱い）、(3) 合わないときにどうするか、(4) Loki を版上げ・設定変更するか。

## 検討した選択肢

| 案 | 中身 | 評価 |
| --- | --- | --- |
| A | 範囲 1 本の件数と行数を最後に突き合わせるだけ | 欠けたことは分かるが、どこが欠けたか・どう取り直すかが分からない。1 本の件数自体が分け目で数え落とす（実測 −8）ので、一致の判定に使えない |
| B | Loki の `split_queries_by_interval` を外す・版を上げる | 配備の変更で、経路 B の Loki の他の読み手（Grafana）にも効く。3.0.0 の誤りがどの版で直ったかを確かめていない。道具が Loki の内部の誤りに依存しないほうが堅い。**採らない（射程外）** |
| **C（採用）** | 範囲を分け目に揃えた窓に区切り、窓の中だけでページを送る。窓ごとに件数を突き合わせる | 1 要求が分け目を跨がない（誤りの起きる形にならない）。件数の要求も窓の中に収まり分けられない。合わない窓を名指しできる |
| D | C に加えて、合わない窓を自動で狭めて取り直す | 取り込みの続く範囲（現在に近い）でも合わないことがあり、黙って取り直すと原因を誤らせる。書き出しの重複の扱いも複雑になる。**採らない** |

## 決定

1. **範囲を `--window` 分の窓に区切る。既定 10 分。1 時間の約数（1/2/3/4/5/6/10/12/15/20/30/60）だけを受け付け、窓の境目を UTC の 0 時からの倍数に揃える。** これで 1 要求（query_range・count の両方）が 1h の分け目を跨がない。10 分は PoC で件数が一致した回避策の幅である。
2. **窓ごとに検算する。** 期待値 = `sum(count_over_time(<query> [<窓の幅>ms]))` を窓の終わりの時刻で評価した値（両端を含まない区間）＋ 窓の始まりちょうどの行（`query_range` の 1 ns の幅、同じ時刻の取り直しと同じ形）。書き出した窓の行数・始まりちょうどの行数と比べる。
3. **1 窓でも合わなければ、全窓を書き終えてから合わない窓（最大 10）を名指しして失敗にする。** main は既存の扱いのまま、書きかけを `<out>.partial` へ改名して exit 1。少ない側（取りこぼし）も多い側（重複・取り込みの続き）も成功にしない。
4. **件数をミリ秒で数えるので、書き出しの `--from` / `--to` はミリ秒の単位までに限る**（`--summary` は問わない）。行の時刻はナノ秒のまま書く。
5. **合わない窓の自動の取り直しは入れない**（案 D を採らない理由）。手順書に「`--window 1` で別の出力先へ取り直す・現在に近い範囲は数分前までにする」を書く。
6. **呼ぶ道は変えない**（GET の `query_range` / `query` だけ。前段の読み取りの列挙の内側。ADR-0133）。要求は窓の数 × 2 だけ増える（8 時間・10 分で 96 回。手元の実測で全体 5 秒）。

## 結果・影響

- 正: 書き出しが自分で完全さを確かめ、欠けたら非 0 で終わる（監査が「行が無い＝処理が無い」と読む前に止まる）。
- 負: 要求が増える。`--from`/`--to` にマイクロ秒以下を与える運用はできなくなる（runbook の例はすべて秒まで）。
- 残余リスク: 窓の始まりちょうどの行は `count_over_time` では数えられず、1 ns の幅の `query_range` で数える。1 ns の要求は分け目を跨がないので本件の誤りの形にはならないが、件数と独立した経路ではない。Loki の件数の数え方（両端を含まない）が版で変わると、検算が合わずに失敗する（黙って通る向きには倒れない）。
