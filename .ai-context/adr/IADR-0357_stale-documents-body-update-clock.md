# IADR-0357: 陳腐化文書数（stale-documents）の生産

- 状態: Accepted
- 日付: 2026-09-03
- 決定者: 実装（#1186）

## 起点・関連

- 関連する計画書 ID: FR-10 / FR-17 / FR-19 / UC-05 / SC-10 / ADR-0006 / ADR-0050 / ADR-0054
- 関連する実装仕様書: `.ai-context/specs/20260903_issue-1186_stale-documents-indicator.md`
- 先行: `IADR-0299`（生産者の枠組み。**決定 1 が本指標を「しきい値未確定」として保留していた**）／
  `IADR-0265`（受け口・集計・統制）

## コンテキストと課題

planning#494 が 3 論点を確定させた（2026-08-29）。**しきい値 180 日（初期値）／起点は本文の更新のみ／
配備時の構成で変更でき、SC-10 には件数と現在のしきい値を併記する。**

裁定の決め手は指標の意味ではなく副作用の側にあった。計画の言葉では

> メタデータを含めると、**棚卸し作業そのもの（タグ整理）が指標を改善させる** ……
> **指標が自分の改善作業で消えるなら、それは測定ではない。**

問題は、**この裁定のもとでは既存の判定材料が使えない**ことである。

### 🔴 「判定材料は揃う」は成立していなかった

`KnowledgeHealthCollector` の冒頭は「判定材料（`UpdatedAt`）は揃うが、しきい値が計画側で未確定」と
書いていた。**2 つとも現況と食い違っていた。**

しきい値は確定した（2026-08-29）。そして材料の方も、走査すると次のようになる。

| 発行経路 | 本文 | `Document.UpdatedAt` | `ContentFingerprint` | `GraphDocument.UpdatedAt` |
| --- | --- | --- | --- | --- |
| `Documents/UpdateMetadata`（`UpdateMetadata` → `Touch()`） | 不変 | **進む** | 不変 | 🔴 **進む** |
| `Documents`（`Update` → `Touch()`。タイトル・属性・タグ） | 不変 | **進む** | 不変 | 🔴 **進む** |
| `Tags/Rename` | 不変 | 進まない | 不変 | 進まない |

**`UpdatedAt` で数えると、属性・タグだけの更新で件数が減る** —— 決定 2 が名指しで禁じた事故である。

⚠️ **起票（#1186）の理由づけは「タグ改名でも `UpdatedAt` が進む」と書いていたが、これは
現行実装では当たらない。** `Tags/Rename` は Tag 行だけを書き換え、文書の `UpdatedAt` は
そのまま再発行する（IADR-0153 決定 1・3「文書は 1 件も書き換えない」）。**結論は変わらない** ——
成立させているのは `UpdateMetadata` / `Update` の方であり、しかも改名は同じ再発行経路
（`DocumentEndpoints.PublishUpdatedAsync`）を通るため、将来 Tag 改名が文書を touch する実装に
変われば即座に当たる。**記録に残すのは実測の方である。**

揃っていたのは**材料**（`BodyHash` ＝ ADR-0050 の本文指紋）であって、値そのものではない。

## 決定

### 決定 1: 本文が変わったときだけ前進する時刻を `GraphDocument` に持つ

`GraphDocument.BodyUpdatedAt`（非 null）を新設し、**前進の判定をドメインに置く**。

- `Create`: 複製元イベントの `UpdatedAt` を写す（本文の時刻を別に知る手立てが無い）。
- `TryApply`: **`bodyHash` が非 null かつ保持中の `BodyHash` と異なるときだけ**前進させる。
  順序ガード（古いイベントは不適用）は従来どおり先に効く。
- `bodyHash` が null は「指紋化できなかった＝**不明**」であり変更と見なさない。
  `GraphDocumentSyncConsumer` が却下解除・リンク抽出で採っているのと同じ向きである
  （ADR-0050 決定 2・3）。

**消費側（Consumer）ではなくドメインに置く**のは、消費側が増えたときに規律が割れないためである。
現に指紋の変化判定は既に Consumer 側にも在り、**同じ規律が 2 箇所にある**状態を増やしたくない。

### 決定 2: 既存行は `UpdatedAt` を写して backfill する（NULL のまま残さない）

| 案 | 帰結 | 判断 |
| --- | --- | --- |
| **A. `UpdatedAt` を写す** | `UpdatedAt >= 実際の本文更新時刻` なので既存文書は**実際より新しく見える**。**偽陽性は出ない**。真に陳腐な文書も遅くとも移行から 1 しきい値（既定 180 日）以内には必ず数えられる | **採用** |
| B. NULL ＝不明として数えない | 既存文書（実データ 2,368 件）が**本文を編集されるまで恒久的に母集合から外れる**。指標はほぼ 0 を返し続ける | 却下 |

🔴 **B を却下した理由は planning#494 自身が書いている** ——「**生産者の無い指標を 0 件として
並べてはならない**（その 0 は『問題なし』と読める）」。数えられない母集合を抱えた指標は、
生産者が無いのと同じ読み方をされる。

**列の既定値では入れない。** `AddColumn(nullable: false, defaultValue: …)` は既存行へ定数
（`DateTimeOffset` の既定＝年 1）を書き、DEFAULT 制約も残す。それでは**全既存文書が翌周期で
一斉に陳腐化として報告される**。マイグレーションは 3 段（NULL 可で追加 → `UPDATE` で写す →
非 NULL 化）で入れる。

### 決定 3: しきい値は配備時の構成。**不正値で起動を落とさない**

- 既定 **180 日**をコードに置き、`KnowledgeHealth:StaleDocumentThresholdDays`
  （環境変数 `KnowledgeHealth__StaleDocumentThresholdDays`）で上書きする。
  `appsettings.json` に既定を明記する。Helm では `services.graph.extraEnv` へ置く。
- **SC-09 のタグ辞書運用には載せない**（planning#494 決定 3）。SC-09 はドメインの語彙を扱い、
  観測のしきい値は運用パラメータである。画面から変えられると、**指標の意味が利用者操作で動き、
  時系列の比較が成り立たなくなる**。
- 🔴 **`ValidateOnStart` を付けない。** 本サービスは `DocumentUpdated` / `DocumentDeleted` の
  購読ホストでもあり、**指標の構成ミスで購読ごと止める**のは割に合わない。既存の
  `HttpKnowledgeHealthReporter` が fail-open を選んだ理由（「指標の送出失敗で購読を止めない」）と
  同じ向きである。
- **不正値（0 以下）は既定へ倒し、警告ログを残す。** そして 🔴 **報告に添えるしきい値も
  倒した後の値にする** —— 倒したのに構成値をそのまま画面へ出すと、**件数と表示されたしきい値が
  食い違う**（画面が嘘をつく）。静かに壊れないための要点はここである。
- 境界は **「しきい値ちょうどは陳腐でない」**（`<` であって `<=`）。180 日ちょうどを含めると
  警告が 1 日早く出る。

### 決定 4: しきい値は**報告 1 通の属性**として運ぶ（観測値の行に持たせない）

planning#494 決定 3 は「SC-10 には件数と現在のしきい値を併記する」と定める。表示のためには、
受け口（DashboardService）まで値が届いていなければならない。

🔴 **観測値の行に持たせてはならない。** 観測値は指標 1 つ分の全量スナップショットであり、
**件数が 0 のときは 1 行も無い**。そこへ乗せると**しきい値も一緒に消え、0 件のときにだけ
併記できなくなる** —— 0 件は最も表示したい状態であり、そこで欠けるのは本末転倒である。

したがって:

- 送出口 `IKnowledgeHealthReporter.ReportAsync` に `int? thresholdDays` を足す。
  **null のときは JSON に項目を出さない**（しきい値を持たない指標の本文は 2 項目のまま）。
- 受け口は `KnowledgeHealthReportRequest.ThresholdDays`（省略可・**0 以下は 400**）で受け、
  指標ごとに 1 行の表 `knowledge_health_indicator_thresholds` へ置き換える。
  **添えられていなければ行を消す**（観測値と同じスナップショットの姿勢。残すと、生産者が
  しきい値の要らない指標へ変わった後も古い日数が出続ける）。
- 閲覧は `KnowledgeHealthIndicatorDto` に `ThresholdDays`（持たない指標では null）を足す。
  **全指標へ一律の既定値を埋めない** —— 意味の無いしきい値が画面へ出る。

### 決定 5: SC-10 の「ナレッジ健全性」節は**開かない**

planning#494 は「**節を開く条件は別の判断である**」と明記し、
「**実装側がこの理由で節を置かず否定テストを残したのは正しい**」とも書いている。
生産者の無い 3 指標（`unresolved-links` / `unsummarized-clusters` / `edge-type-usage`）が
0 件として並ぶ状態は変わっていない。

**`OperationsDashboardPage.test.tsx` の否定テストはそのまま残す。**
本作業で直すのは、その否定テストと画面のコメントに残る**古い理由づけ**（「しきい値の裁定待ち」）
だけである。

⚠️ 併せて実測した事実: **`/bff/dashboard/knowledge-health` は存在しない**（BFF が持つのは
`/summary` の 1 本だけ）。節を開くには BFF の口と契約（`Knowledge.Contracts` への昇格・
`check-contract-schema.js` の baseline・orval 再生成）が要る。**使う側が居ない契約を先に
固定しない**という既存の規律（`View/Query.cs` 冒頭）に従い、本作業では作らない。

## 結果

- **できるようになったこと**: 陳腐化文書数が実データで生産される。タグ・属性の整理では件数が減らない。
  0 件でも件数としきい値が受け口に載り、画面が読める形になった。
- **受け入れたこと**:
  - 既存文書は backfill により**実際より新しく見える**（移行から最大 1 しきい値ぶん、真の陳腐が
    遅れて現れる）。偽陽性は出ない側の受容である。
  - しきい値の変更には**再配備が要る**（実行時に変えられない）。planning#494 決定 3 が
    「配備時の構成で」と定めた範囲そのままである。
  - 指標の値は**生産者の時計**で決まる。レプリカ間の時刻差は 1 時間周期に対して無視できる。
- **フォローアップ**:
  1. **SC-10 の節を開くかの判断**（planning#494 が「別の判断」と明記）。開くには BFF の口が要る。
  2. しきい値 180 日は**初期値**である。運用開始後の実測で改めることが計画に明記されている
     ——「改めた」ことが読めるよう、SC-10 側に現在値を併記する形にした（決定 4）。
  3. **個人資料からの辺が孤立判定を変える問題**（IADR-0299 §結果 フォローアップ）は本作業の
     射程外であり、そのまま残る。
