# IADR-0538: AI レビューの検証の下限を Check review verdict で検査する

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。
> 計画リポジトリの ADR（`ADR-XXXX`）とは別系統（`IADR-XXXX`）とし、実装に閉じた決定を記録する。

- 状態: Accepted
- 日付: 2026-10-14
- 決定者: Claude（実装）／起点は #1924 の AI レビューの 2 回の下限違反（オーケストレーターの指示）

## 起点・関連

- 関連する計画書 ID: なし（CI の AI レビューの統制。メタ作業のため無採番の `NFR`）。
- 前提: [IADR-0198](./IADR-0198_kit-delta-fifth-kind-and-review-verdict.md)（`check-review-verdict.js` の採用。配線はレビュー用ワークフローに限る）、
  [IADR-0232](./IADR-0232_ci-pr-latency-reduction.md) 決定 7 の追記（#1911 / #1915。プロンプトに【検証の下限】を置いた）。
- 移植元: AST の `scripts/check-review-verdict.js`（AST#1337 で初版、AST#1346 で「N/N を申告しつつ精読していない自認」、
  AST#1347 で「計画書の除外を計画書だけの文に限る」）。AST 側の記録は AST の IADR-0190 決定 7 と、AST の作業仕様書
  `20261012_1315_review-depth-floor` / `20261013_1315_review-floor-check` / `20261014_1315_review-floor-not-read-declaration`。
- 作業仕様書: [20261014_review-floor-check](../specs/20261014_review-floor-check.md)（母集合の表・期待・frontend の判断）。

## コンテキストと課題

- #1915 でプロンプトに【検証の下限】（変更ファイルを全部読む・`deploy/helm/**` なら `helm lint` / `helm template`・
  `scripts/` か `.github/` なら `scripts.test.js` 全件 など）を置いた。下限はプロンプトの指示であり、守られたかは誰も見ていない。
- #1924 の AI レビューは 2 回続けて下限を満たさなかった。
  - 1 回目: 「変更 38 ファイル中、コード 15 ファイルと主要な文書を読んだ」「差分全体の精読までは行っていない」。
    `helm lint` / `helm template` / `scripts.test.js` を 🔍 の節で「走らせていない」と書いた。
  - 2 回目: 「変更 38 ファイル中、次の 8 ファイルは差分か全文を読んだ」。🔍 の節で「本文は精読していない」と書いた。
- 判定の見出し（🔴 / 🟡 / 🟢）は揃っているので、既存の `Check review verdict` は緑だった。IADR-0198 が止めた
  「緑だが検査されていない」と同じ形である。運用ガイドの「同型 2 回で検査器」に当たる。

## 検討した選択肢

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | プロンプトの文言を強めるだけ | #1915 の後に 2 回破られた。文言は守られたかを確かめない |
| B | AST の検査器をそのまま移植する | #1924 の 2 本は赤にできる。ただし #1921 の 2 回目（6/6 を申告し、🔍 の節に「全文を読めていない」）は緑で素通りする |
| C | B に本リポの文型の差を足す（🔍 の節の自認・生成物の語彙・他リポの除外） | 実文 79 本に当てて期待どおり（作業仕様書の表） |

## 決定

### 決定 1: AST の最終形（AST#1347 まで）を移植し、判定 (a)〜(c) で落とす

`scripts/check-review-verdict.js` は、判定の見出しを含む最後の候補（コメント投稿ツールの入力・assistant の text・result）を
レビュー本文とし、次の違反ごとに `::error` を出して exit 1 にする。判定の見出しの検査（IADR-0198）は変えない。

- (a) 冒頭（最初の判定の見出しより前）に「変更 N ファイル中 M ファイルを読んだ」の申告が無い、または M + K < N
  （K は「生成物 K ファイルを除外」の数）。M が数字で書かれていない申告（「コード 15 ファイルと主要な文書を読んだ」）は申告なし。
- (b) 同じ行に「下限」と「満たして(い)ない / 満たさない / 満たしていません」がある。あわせて、(a) を満たすとき（M + K ≥ N）に限り、
  読んだと申告したファイルを精読していない自認（全行／行単位／精読せず・精読していない／名前と範囲の確認／要点だけ／
  検査器の結果だけ／確認にとどまる／未読／読めていない／しか目視していない 等）がある。引用（インラインコード・「」・『』）と
  否定の否定は数えない。生成物だけの文は K>0 を申告しているときだけ数えない。計画書だけの文は数えない（計画書と他の対象を
  並べた文は数える）。
- (c) 変更ファイル（ステップが `git diff --name-only BASE...HEAD` で計算して `CHANGED_FILES` で渡す）に `deploy/helm/**` があるのに
  `helm lint` / `helm template` が、`scripts/` か `.github/` があるのに `scripts.test.js` が、「確認できたこと」の節に無い。
  🔍 の節に在るだけでは実行した記載とみなさない。`CHANGED_FILES` が空なら (c) だけを warn 付きで skip する（fail-open）。
- `ALLOW_MISSING_VERDICT=1` は判定の未投稿の緊急避難であり、下限には効かない。

### 決定 2: 本リポは「🔍 実行できなかったこと」の節の自認も数える（AST との差）

- 本リポのレビューは、精読していない自認を 🔍 の節に書く（下限の導入前の #1886・#1899・#1900・#1901・#1906・#1909・#1912、
  導入後の #1921 の 2 回目・#1924 の 2 回目）。AST の形（冒頭と確認できたことの節だけ）では #1921 の 2 回目が素通りする。
- ただし 🔍 の節では「読む」ことの自認の型（全行・行単位・精読・未読・差分を読まず・読めていない・流し読み）だけを数える。
  「…までしか確認できない」「要点だけ」「確認にとどまる」は数えない。この節には CI のジョブログ・他リポの pin のように、
  変更ファイルを読むこととは別の未検証が恒常的に書かれる（#1855・#1869・#1920 の実文で偽陽性になった）。

### 決定 3: 本リポの語彙に合わせる

- 生成物: orval の生成物（`src/<unit>/frontend/src/lib/api/generated/` 配下）・`pnpm-lock.yaml` を足し、`package-lock.json` を外した。
  EF の `*.Designer.cs` / `*ModelSnapshot.cs`・Lingui の `messages.ts` / `messages.po`・`CHANGELOG.md`・`openapi.yaml` は AST と同じ。
- 読む対象でない文: 計画書（「計画の ADR」の形を含む）に「他リポジトリ」を足した。
- プロンプトの【検証の下限】に、申告の書式（N・M・K を数字で）・「読んだ」の定義・検査器が読むこと・節の使い分けを書き、
  出力フォーマットに「✅ 確認できたこと」の節を足した。生成物の例は検査器の `GENERATED_TOKENS` と対であり、
  `scripts.repo.test.js` が固定する。

### 決定 4: frontend（`pnpm`）の実行は (c) に入れない

- 【検証の下限】に frontend の項目が無く、レビューのジョブは pnpm と依存を用意せず、`--allowedTools` にも `pnpm` が無い。
  検査器だけが求めると全 frontend PR が赤になる。frontend の検証は `frontend.yml` / `frontend-tests.yml` が CI で走らせている。
- 足すときは、ジョブの準備・許可・下限の項目を先に揃え、違反の実例が 2 回出てからにする。

## 理由

- 下限はプロンプトの指示であり、守られたかを確かめないと「緑だが検査されていない」が残る（IADR-0198 と同じ理由）。
- AST の検査器は AST#1337〜AST#1347 で実文に当てて偽陽性を潰した最終形であり、書式（見出し・申告）も本リポとほぼ同じである。
  一から作るより、移植して本リポの実文で差を測る方が確かである。
- 本リポの実文で測ると、AST の形のままでは #1921 の 2 回目を見逃す。差は決定 2 と 3 に限った。

## 結果

- 良い影響:
  - #1924 の 2 本と #1921 の 2 回目が赤になる。下限を満たした導入後のレビュー（#1915・#1918・#1920・#1921 の 1 回目）は緑のまま。
  - 下限を欠いたレビューで `claude-review`（必須 check）が赤になり、再実行かレビューの読み足しが要るようになる。
- 悪い影響・トレードオフ:
  - 書式に依存する。申告の書き方が揺れると偽陽性でジョブが落ちる。偽陰性より偽陽性へ倒す（IADR-0198 と同じ）。
  - 申告の N と実際の変更ファイル数は突き合わせない。少なく申告されると素通りする。
  - 「実行した記載」は節の中の語の有無で読むだけで、出力の真偽は見ない。自認を書かずに N/N と申告する嘘は捕まらない。
  - 🔍 の節の「読めていない」は、変更ファイル以外（他リポの issue 等）について書かれると偽陽性になり得る。
    「他リポジトリ」「計画書」と書いた文は数えない。
- フォローアップ:
  - backend の `dotnet build` / `dotnet test` / `dotnet format`、文書系の検査器の実行は見ていない。同型の違反が 2 回出たら足す。
  - frontend は決定 4 のとおり。
