# IADR-0482: SC-09 の編集器と検証器は、計画が動的束縛を置く 2 つの位置だけを許す（#1666）

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

> ［2026-09-28 追記 / #1676］**表題は決定 9・10 を含めて次のとおり読む**（`title:` と H1 は確定済みの記録として書き換えない。索引の行は読み替えた形に直した）:
> 「SC-09 のポリシーの編集器と認可サービスの検証器は、計画が動的束縛を置く **(action, key, 変数) の組**
> —— `read` の `owner` の `${current_user}`・`shared_with` の `${current_user}`/`${current_groups}` と、`write` の `owner` の `${current_user}` —— だけを許し、
> **束縛の位置の値は束縛だけで作る**（リテラルを混ぜない）」。表題の「2 つの位置」は `read` の 2 つを指し、`write` × `owner`（決定 9）と
> 値を束縛だけにすること（決定 10）が抜けていた。画面で選べるのは今も `read` の 2 つだけである（画面の対象アクションに `write` は無い）。

## コンテキストと課題

SC-09 の条件エディタは、対象属性を属性辞書から、値を辞書の許可値から選ばせる（IADR-0129 決定 2。計画の入力表「対象属性｜選択｜定義済み属性のみ」）。
`owner` と `shared_with` は計画 07 §文書属性に定義された属性だが、値が利用者名・グループ ID で列挙できないので辞書に載らない。
その結果、所有者の read ポリシーも共有先のポリシーも画面から作れなかった（ADR-0121 実測 7）。

一方、ポリシーの API は未定義のキーと任意の値を素通しで受け付けていた。**`${current_usr}` のような綴り違いも保存でき**、評価器はそれを
リテラルとして残す（`AbacEvaluator.BindPlaceholders`。既知の変数以外は置き換えない）。どの文書にも一致しない＝**誤りとして表に出ずに静かに効かない**。

決める必要があったのは次の 4 点である。

1. どの属性に、どの束縛を許すか
2. 辞書の外の属性をどう選ばせるか（「定義済み属性のみ」との関係・自由入力の禁止）
3. 表示の形（束縛であることを色だけでなく語で示す）
4. サーバー側の検証をどこまで入れるか（並行作業と重ならない最小）

## 検討した選択肢

| 論点 | 採用 | 退けた選択肢と理由 |
| --- | --- | --- |
| 1 | **計画が束縛を置く 2 か所だけ**: `owner` → `${current_user}`、`shared_with` → `${current_user}`・`${current_groups}`（文書の条件のみ） | どの文書属性にも 2 変数を許す —— 計画に無い位置（`owner ∈ {${current_groups}}`・`department ∈ {${current_groups}}`）を実装が先取りする。評価器が意味を与えても、計画が判定規則として定めていない。利用者の条件にも許す —— 評価器は利用者の条件を束縛しない（静かに効かない形を作るだけ） |
| 2 | **辞書の選択肢に「束縛の位置」を足す**（辞書の**文書スコープ**に同じキーが無ければ文書属性「所有者」「共有先」として足し、文書属性として辞書にあればその行の許可値の後ろへ束縛を足す）。値は常に選択肢の配列から選び、下書きも選択肢に無い値を積まない | 束縛専用の別フォームを作る —— 同じ「属性 × 値」の条件が 2 か所に分かれ、1 本のポリシーで組めなくなる。辞書へ `owner` を登録させる —— 値を列挙できない属性を辞書に入れる意味が無く（seed の注記）、辞書の許可値の検証が束縛を「辞書外」として落とす。自由入力欄 —— issue が禁じる |
| 3 | **「動的束縛: 操作する利用者本人（`${current_user}`）」の文**を値の選択肢・積んだ条件のチップ・一覧の要約の 3 か所に出す。チップと束縛を含む一覧の行は枠線の `Tag`（`outline`）にするが、意味は文言が担う | 記法（`${current_user}`）だけを出す —— 管理者が意味を読めない。説明だけを出す —— 運用手順書・API の本文と突き合わせられない。色（枠線）だけで区別する —— INDEX 決定 21 に反する。翻訳文に記法を入れる —— ICU の `{}` と衝突するので、記法は補間の値として渡す |
| 4 | **`AbacValidation.ValidatePolicy` に束縛の検証を足すだけ**: 値に `${` を含むものを束縛の形とみなし、①利用者の条件なら拒否、②文書の条件で表に無い (key, value) なら拒否。表の束縛は、辞書に同じキーが定義されていても「辞書外の値」として拒否しない | 評価器で未知の変数を拒む —— 判定の点を増やし、IADR-0253 決定 3（束縛は評価器の中だけ）と別の関心を混ぜる。保存済みのポリシーを検証し直す —— 既存の運用を止める。`${` を含まない綴り違い（`$current_user`）まで拾う —— 束縛の形の判定が推測になる |

## 決定

1. **束縛の位置の表は 2 か所に置き、同じ内容に保つ**: 画面 `abacVocabulary.ts` の `DYNAMIC_BINDINGS` と、認可サービス `AbacValidation.DynamicBindingPositions`。
   どちらも純関数の試験で値集合を完全一致で固定する（画面 P11・サーバ T-68/T-69）。**位置・変数を足すなら計画 ADR の側で定義してから両方に足す**
   （`AbacEvaluator` の束縛変数の注記と同じ趣旨）。
2. 画面の対象属性の選択肢は `policyAttributeOptions(辞書)` が作る（辞書 ＋ 束縛の位置）。下書き（`usePolicyDraft`）は選択肢に無い値を積まない。
3. 束縛の表示は上の文で統一する。束縛変数の説明（「操作する利用者本人」「操作する利用者の所属グループ」）は Lingui のカタログに置く。
4. 検証は保存と dry-run の同じ関数に入るので、両者の結果は一致する（`PolicyDryRunValidationTests` で固定）。dev seed の全ポリシーが検証を通ることも試験で固定する。
5. 評価器・契約（OpenAPI）・BFF は変えない。
6. ［2026-09-28 / レビュー］**選択肢の識別子はスコープとキーの組（`document:owner`）にする。** 束縛の位置の選択肢を足すかは
   **文書スコープに同名キーがあるかだけ**で決める。旧判定（どのスコープでも同名があれば足さない・`Select` の値はキーだけ）では、
   利用者スコープに `owner` 属性を 1 つ作るだけで所有者の read ポリシーを画面から作れなくなった。同じキーを両スコープに持つ辞書
   （利用者 `department` と文書 `department`）でも選び分けられなかった潜在の不具合も同時に閉じる。
7. ［2026-09-28 / レビュー］**認可サービスは利用者スコープの `owner`・`shared_with` の登録を拒否する**（`ValidateAttributeDefinition`。
   辞書のキーの同一性と同じく大小を区別しない）。束縛の位置と同名の利用者属性は、条件エディタで名前だけが同じ別物として並び、
   取り違えの元になる。dev seed の属性辞書・realm・既存の試験に利用者スコープの `owner`・`shared_with` は無く、何も壊さない（実測）。
   文書スコープの同名は拒まない（束縛の値と辞書の許可値を併せて持てる）。
8. ［2026-09-28 / レビュー］**束縛の位置のキーは大小を区別する（画面・サーバとも Ordinal）。** 評価の比較規則に揃えた ——
   評価器は束縛を値の完全一致で解決し（`BindPlaceholders`）、文書の属性の突き合わせもキーを大小区別で引く
   （`AttributeFilterMatch.MatchesAll` の `TryGetValue`・`DocumentAttributeEncoding.WithSharedWith` の Ordinal）。
   したがって `Owner ∈ {${current_user}}` は保存できても静かに効かない。サーバの表は当初 OrdinalIgnoreCase で `Owner` を通していた。
9. ［2026-09-28 / 監査］**表は (action, key, 変数) の組で持つ**（画面・サーバとも）。計画 07 §動的束縛 の判定規則のとおり、
   `read` は `owner` の `${current_user}` と `shared_with` の `${current_user}`・`${current_groups}`、`write` は `owner` の `${current_user}` だけ
   （「共有先には書き込み権限を与えない」。ADR-0036 D-07）、`analyze`・`manage` には束縛が無い。action の次元が無いと
   `write` × `shared_with:[${current_user}]` が通り、境界層の write スコープが共有先に書き込みを許していた（develop 以前からの API 経路の欠陥）。
   画面の対象アクションに `write` は無いので、画面で選べる束縛は `read` の 2 つだけであり、アクションを変えると許されない束縛の条件は下書きから外す。
10. ［2026-09-28 / 監査］**束縛とリテラルを同じ値の集合に混ぜない**（サーバは拒否し、画面は束縛の位置で値の選択肢を束縛だけにする）。
    `owner:[${current_user}, "bob"]` は、束縛と無関係に bob の文書を全員に許す。計画の所有者の位置は `{ ${current_user} }` だけである。

## 結果

- 所有者の read ポリシー（ADR-0121 決定 1 の形）と共有先のポリシーを、画面の操作だけで作れる（単体と E2E で送信本文を固定）。
  ADR-0121 決定 6 の暫定手段（API への直接投入）は、画面からの投入に置き換えられる状態になった。
- 綴り違いの束縛・利用者の条件の束縛・計画に無い位置の束縛は保存前に止まる（従前は保存でき、静かに効かなかった）。
