# IADR-0300: AI 提案の承認・却下は BFF を透過中継で開け、前段の write ゲートを置かず、SC-03 はタグ提案の承認だけを塞ぐ

- 状態: Accepted
- 日付: 2026-08-29
- 決定者: claude（#450）

## 起点・関連

- 関連する計画書 ID: FR-18（承認 UI は SC-03 が主・SC-21 が従／一括承認を提供しない）・
  SC-03「AI 提案の承認欄」（当該文書を両端のいずれかとする提案を本文の下部に表示し、その場で承認／却下できる／
  0 件なら欄自体を出さない／種類・相手・辺の型・根拠を示す／既定は `pending`／SC-21 への導線を置く）・
  UC-10 代替フロー（承認が確定するのは SC-03 経由のみ）・ADR-0033 決定 7・9・10・ADR-0034 決定 2・8
- 関連する実装仕様書: [`.ai-context/specs/20260829_issue-450_ai-suggestion-approval.md`](../specs/20260829_issue-450_ai-suggestion-approval.md)
- 先行する実装ADR: [IADR-0276](./IADR-0276_ai-suggestion-listing-exposure.md)（読み取り口だけを出す。
  **その決定 1 が「承認欄と同じ変更単位で開ける」と予告した、その変更単位が本 ADR である**）／
  [IADR-0272](./IADR-0272_graph-write-action-authorization.md)（グラフの書き込みは read と write の 2 スコープ）／
  [IADR-0044](./IADR-0044_backend-service-authorization-defense-in-depth.md)（多層防御）／
  [IADR-0135](./IADR-0135_generated-client-adoption-and-cache-keys.md)（生成フックが唯一の呼び出し口）

## コンテキストと課題

GraphService には承認・却下・生成が既にあるが、BFF に出ているのは一覧 1 本だけである。
SC-03 の承認欄を実装するにあたり、5 つの問いが立つ。

1. **BFF の口をどう作るか。** `ProxyAsync<T>` は GET 専用であり、本文を型で読み直して詰め替える。
2. **BFF に write の前段ゲートを置くか。** `PrivateNoteBffEndpoints` は置き、`DashboardBffEndpoints` も
   多層防御として両側に置いている。**前例が割れている。**
3. **却下の本文（両端の本文指紋）をどう扱うか。** SPA は指紋を持てない。
4. **タグ提案をどう描くか。** 後段はタグ提案を承認しても**文書のタグを 1 つも増やさない**
   （`AiSuggestionEndpoints` は `Kind == Link` のときだけ辺を作り、タグは「反映の経路は #918 で決める」と
   注記したまま、その #918 が一覧のみで着地した）。計画は「その場で承認／却下できる」と定めている。
5. **「一括承認をどの層にも作らない」の固定をどう保つか。** 現行の固定は「BFF のルートのメソッドが
   GET だけ」という形であり、承認・却下を開けた瞬間に**主張そのものが事実に反する**。

## 検討した選択肢

### 問い 1（BFF の口の作り）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | `ProxyAsync<T>` を POST 対応へ拡張する | 型引数つきで本文を読み直す形が残る。**409 / 400 の本文が失われる**（`Results.Ok(view)` へ詰め替わる） |
| **B（採用）** | **`ForwardAsync` ＋ `RelayAsync` を足す**（`PrivateNoteBffEndpoints` と同型） | 状態・Content-Type・本文をそのまま返す。`/{id}/restore` が本文なし POST の完全な同形で、先例に倣える |

### 問い 2（BFF の write ゲート）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | `ForwardIfWritableAsync` を真似て前段に write スコープの門を置く | **後段が既に同じ判定を含む。**加えて拒否が 403 になり、後段が 404 へ倒している存在秘匿と応答が割れる |
| **B（採用）** | **前段の門を置かず、後段の 4 段の門に委ねる** | 判断点が 1 つ。応答が 404 で一貫する。往復が増えない |

### 問い 3（却下の本文）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 指紋を DTO へ載せ、画面から送り返す | **内部状態を公開面へ出す**（IADR-0276 決定 2 が明示的に避けた）。文書を読めない利用者に本文の変化を判定させる副次経路になる |
| B | BFF が DocumentService から指紋を引いて詰める | BFF が持つ関心ではない。往復が増え、BFF に鮮度の判断が生まれる |
| **C（採用）** | **本文を送らない**（後段の任意本文を使わない） | 実測した帰結が小さい（下記 決定 3） |

### 問い 4（タグ提案の描き方）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | 承認も却下も押せるようにする（計画の逐語どおり） | **押せる承認ボタンが偽の作用を約束する。** 承認しても文書のタグは増えず、利用者は「反映が遅れている」と読む |
| B | タグ提案を承認欄に**出さない**（リンク提案だけ描く） | 計画が明記した「リンク候補・**タグ候補**を表示し」に反する。さらに **SC-21 の全行が持つ「文書詳細で確認」の導線が、タグ提案について行き止まりになる**（SC-21 主要素 4 は全行が SC-03 への導線を持つと定める）。**却下もできなくなる**——却下は完全に効く操作である |
| **C（採用）** | **表示する／承認だけを実行不可として理由を示す／却下は実行できる** | 表示は計画どおり。偽の作用を約束しない。効く操作は残る。**差異が画面上で読める** |

### 問い 5（一括承認の不在の固定）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A | ルート表の検査をやめ、画面側のテストだけに任せる | **API の側に一括の口を足しても落ちない。** FR-18 は画面と API の両方を禁じている |
| B | 「書き込みは approve / reject の 2 本だけ」と本数で固定する | 口が増えるたびに数を直すことになり、**数を直す作業が禁止の意味を薄れさせる** |
| **C（採用）** | **パターンで固定する**——「承認・却下に当たり、かつ 1 件の ID を取らないルートが無い」 | 一括の口は必ずこの形になる。単票を足しても落ちず、一括を足すと必ず落ちる |

## 決定

### 決定 1: BFF は承認・却下を**透過中継**で開ける（生成は開けない）

`POST /bff/graph/suggestions/{id}/approve` と `/reject` を足す。`ForwardAsync` ＋ `RelayAsync` で
**状態コード・Content-Type・本文をそのまま返す**。

- 🔴 **404 を作り替えない。** 後段は「権限外・不存在・書き込み権限なし」をすべて 404 に倒しており
  （ADR-0034 決定 2 / IADR-0272 決定 3）、403 や 200 へ変換すると**存在秘匿が BFF 層で破れる**。
- 409（`invalid_transition`）・400（`unknown_edge_type`）は**本文ごと**透過する。画面は理由で文言を
  出し分ける必要がある（「もう承認済み」と「辺の型が消えている」は別の指示になる）。
- 後段不達は 502 へ縮退する。**成功へ縮退しない** —— 承認できていないのに承認済みと見えるのが最悪である。
- **生成（`generate/{documentId}`）は開けない。** 計画は SC-03 にも SC-21 にも生成の導線を置いておらず、
  消費者の無い書き込み口を公開面へ出さないという IADR-0276 決定 1 の理由がそのまま残る。
  後段自身も「正しいアクションは `analyze` である可能性が高く裁定待ち」と注記している。
- **権限伝播は方式 A（Authorization ヘッダ）を維持する**（GraphBffEndpoints 冒頭の判断軸）。

### 決定 2: BFF に write の前段ゲートを**置かない**

`PrivateNoteBffEndpoints.ForwardIfWritableAsync` を真似ない。

- **あちらが置くのは、後段（DocumentService）が write スコープを見ないからである。**
  GraphService は自分で解決する（`IsSourceWritableAsync`。IADR-0272 決定 2・3）。
- **BFF に置ける門は後段の門の真部分集合にしかならない。** `BffScopeResolver` が返すのは
  「write を許すポリシーが 1 件以上あるか」＋文書属性フィルタであり、**提案 ID から起点文書を
  引けない BFF は文書条件を当てられない**（`ForwardIfWritableAsync` 自身が「スコープの中身は使わない」と
  書いている）。後段は起点文書を引いて `AuthorizedNode.Authorize` を通しており、**厳密に強い**。
- 置くと 3 つだけが増える: (1) 拒否が **403** になり 404 の存在秘匿と応答が割れる、
  (2) ABAC の判断点が 2 つになり片方が腐っても気付けない、(3) 承認ごとに `/authz/scope` の往復が 1 増える。
- **`DashboardBffEndpoints` の多層防御と割れて見えるが、あちらが両側に置いたのは静的な「ロール」である。**
  ロールは要求に依らない粗い条件で、二重化しても判断が割れない。ABAC は要求ごとに解決するので割れる。
- ⚠️ **反転条件を書き残す**: **後段が write スコープを見ない口を `/bff/graph` 群へ足すときは、
  この決定は反転する**（そのときは前段の門を置くこと）。

### 決定 3: 却下は**要求本文を持たない**（帰結を実測した）

後段の `RejectAiSuggestionRequest`（両端の本文指紋）は任意であり、BFF は本文を送らない。

**帰結を推測せず実測した。** 却下解除は `GraphDocumentSyncConsumer` が
**「その文書の本文指紋が実際に変化したとき」だけ** `ReinstateRejectedAsync` を呼ぶ形になっている
（外側の門）。`AiSuggestion.TryReinstate` が保存済み指紋と現在値を比べるのはその内側であり、
保存済みが `null` なら「変わった」と判定される。**したがって解除の発火条件は変わらない** ——
外側の門が既に ADR-0033 決定 10 の条件（両端いずれかの本文が変更された）そのものだからである。

**実際に劣化するのは `ReinstatedReason` の精度だけ**である（初回の解除で `source` / `target` ではなく
`both` になり得る）。画面はこの値を**真偽としてしか使っていない**（非 null なら固定文言を添える）ため、
利用者に見える差は無い。**指紋を後段が自分の複製から読む形にすれば消える差**であり、追随 issue へ回す。

### 決定 4: SC-03 は**タグ提案を表示し、承認だけを実行不可にする**（却下は実行できる）

**計画との差異であり、環流する。** 計画 §SC-03 は「リンク候補・タグ候補を…その場で承認／却下できる」と
定めるが、**タグ提案の承認は後段で実質 no-op** である（状態が `approved` になるだけで文書のタグは増えない）。

- **押せる承認ボタンは偽の作用を約束する。** 「承認したのにタグが付かない」を利用者が
  「反映が遅れている」と読むほうが、押せない理由が書いてあるより悪い。
- **隠す（案 B）を採らない決定的な理由**: SC-21 は**全行が SC-03 への導線を持つ**と定めており
  （主要素 4・「SC-03 への導線を持たない行」は描いてはいけないものに挙がる）、
  **SC-03 がタグ提案を隠すと、その導線がタグ提案について行き止まりになる。**
  加えて**却下は完全に効く**操作であり、隠すとタグ提案を承認欄からも一覧からも処理できなくなる。
- 押せない理由は `title` 属性だけでなく**画面上のテキストとしても出す**（無効なボタンだけを置くと
  理由が読めない。色・状態だけで意味を持たせない規則と同じ向き）。

### 決定 5: 一括承認の不在は**パターンで固定する**

`BffGraphSuggestionTests` の主張を「メソッドが GET だけ」から
**「承認・却下に当たり、かつ 1 件の ID をパスに取らないルートが 1 本も無い」**へ組み替える。
陽性対照を 2 段（提案のルートが取れる／**単票の承認・却下が在る**）で置き、
生成の口が無いことも同じテストで見る。

### 決定 6: SC-03 の文書での絞り込みは**当面クライアント側**に置く

> **［2026-08-31 追記 / #1104］本決定は撤回した。** 後段の一覧が `documentId` を受けるように
> なり、SC-03 は client 側の間引きをやめてサーバへ委ねた
> （[IADR-0323](./IADR-0323_ai-suggestion-document-filter.md)。**本決定 6 のみが Superseded であり、
> 決定 1〜5 は有効である**）。下の「当面」「追随 issue へ回す」という記述は、
> フォローアップ 2 が実行されたことで失効している。
> 🔴 **「秘匿の実施点ではない」という下の判断は変わっていない** —— 絞りをサーバへ移した後も、
> 秘匿を担うのは端点の文書属性による ABAC だけである。

後段の一覧は `state` と `kind` しか受けない。SC-03 は `state=pending` を引いて
`sourceDocumentId` / `targetDocumentId` で絞る。**サーバ側で絞るほうが正しい**が、
後段（GraphService）の変更を伴い本変更単位の外なので、追随 issue へ回す。
**権限による絞りはサーバ側で済んでいる**（権限外の提案は件数を含め届かない）ので、
ここでの間引きは表示対象の限定であって秘匿の実施点ではない。

## 理由

決定 2 が本 ADR の核心である。「多層防御だから両側に置く」は一見安全だが、
**BFF に置ける門が後段の門より弱い場合、増えるのは安全性ではなく食い違いの可能性だけ**である。
前例が割れて見えたのは、**割れている軸が「層」ではなく「判定の種類（静的なロール／要求ごとの ABAC）」
だった**ためであり、その軸で読み直すと 3 つの先例（PrivateNote / Dashboard / Graph）は矛盾しない。

決定 4 は「計画に従う」と「利用者を騙さない」が衝突した場面である。**表示（計画の要求）は満たし、
実行できない部分だけを、理由つきで実行不可にする**という分け方を採った。
差異を画面上で読める形にしておけば、環流の裁定が出たときに直す場所が 1 か所で済む。

## 結果

- 良い影響:
  - SC-03 が承認の主導線として機能し、SC-21 の「文書詳細で確認」が実際の判断へ到達する
  - 承認・却下の認可境界が**公開面で測られた**（IADR-0276 決定 1 が測られないまま出すことを避けた、その測定）
  - 一括承認の禁止が、口の増減に耐える形で固定された
- 悪い影響・トレードオフ:
  - **タグ提案は承認できない。** 計画の逐語を満たしていない（環流する）
  - SC-03 が `pending` の権限内全件を取得する。文書数・提案数が増えると無駄が大きい
  - 却下の `ReinstatedReason` が初回の解除で粗くなる（利用者に見える差は無い）
- フォローアップ:
  1. **計画へ環流**（裁定依頼）: タグ提案の承認に反映先が無い。承認欄はどう振る舞うべきか
  2. ~~**追随 issue**: 一覧へ `documentId` の絞り込みを足す（GraphService ＋ BFF ＋ 契約）~~
     **［2026-08-31 / #1104］完了**（[IADR-0323](./IADR-0323_ai-suggestion-document-filter.md)）
  3. **追随 issue**: 却下時の指紋を後段が自分の複製から読む（要求本文に依存しない）
  4. **追随 issue**: `docs/api/BFF_bff-surface.md` のエンドポイント一覧が `/bff/graph/*`・
     `/bff/private-notes*` を群ごと落としている（本作業より前からの欠落）
