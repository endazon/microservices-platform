# 作業仕様書: blocked 判定の再検証（#701）

## 起点

- **NFR**（運用保守。**メタ作業なので無採番**。[IADR-0179](../adr/IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 1）
- 起点 issue: **#701**（**#623 の子**・受け入れ基準 4）。実装 ADR: **[IADR-0180](../adr/IADR-0180_blocked-judgments-expire.md)**
- 正本: `planning/docs/ai-implementation-workflow-guide.md` §6 ／ 再発防止の対象: **#554 / #556 / #562 → #617**

> **★ 値の基準時点は develop `1063d0e`（2026-08-11 実測）である。**

## ★★ 母集合 —— 3 軸で引いた

### 軸 a: **「棚卸し・監査の観点」が本リポのどこにあるか**

**planning 側の `tools/doc-checks/stocktake.js` に相当するものは本リポに無い**（実測。`scripts/` に該当なし）。
**blocked 相当の判定が実際に置かれているのは引継資料の 2 箇所**である。

| 箇所 | 内容 | 性質 |
| --- | --- | --- |
| `docs/how-to/session-handoff.md` §2 の表 **行 H** | `稼働環境・ハードウェア依存（#271 #336 #388 #466 等）。AI だけでは閉じられない` | **スナップショット**（同節が「必ず古くなる」と自認） |
| 同 **§4.5** | **環境によって変わること —— 着手前に自分で実測する**（4 能力の測り方） | **手順書**（#617 で全面改稿） |

### 軸 b: **既存の規範が何を覆っているか** —— **「書くとき」は在り、「測り直すとき」が無い**

| 既存 | 覆う場面 |
| --- | --- |
| §4.5 冒頭 | **着手前**に測る（諦める前に自分で実測する） |
| §5 **型 8**（＋ #617 の追記「第 3 の形」） | **限界を書くとき**に「できない」と「環境でできない」を混ぜない |
| **（無い）** | **一度 H へ入れた判定を、後の棚卸しで測り直す** |

**#617 が是正したのは「書くとき」である。**
**本 issue が塞ぐのは「書いた後、据え置かれること」**である。

### 軸 c: **#617 の実測が根拠になる**

§4.5 の改稿理由がそのまま本件の根拠である ——
**#554 / #556 / #562 の 3 件は「AI だけでは完結しない」として保留され、フェーズ B 打ち切りの根拠にされたが、
3 件とも別の環境では実施でき、同日中に着地した。**

**判定は環境に依り、環境は変わる。したがって判定には賞味期限がある。**

## 判断

### ★★ 判断 1: **規範は §4.5（手順書）へ置き、§2（スナップショット）からは指す**

**§2 は自ら「この節だけは必ず古くなる」と書いており、規範の置き場所として不適である。**
**§4.5 は #617 が「能力の一覧ではなく実測の手順書」として書き直した節**であり、**再測定の規範はここに属する。**

### ★ 判断 2: **判定に「最後に測った時点」を持たせる**

**「AI だけでは閉じられない」とだけ書くと、いつの観測なのかが残らない。**
**測った時点が無い判定は、再検証すべきかどうかを判断できない。**

> **★ これは §2 が古くなること自体を直すものではない。**
> **古くなってよい**（GitHub が正）。**古いと分かる形にする**のが目的である。

### 判断 3: **個々の issue を再判定しない**（#701 の射程外）

**観点を足すのが本 issue** である。**#574 / #546 / #336 / #380 / #578 は現在も環境依存として据え置く。**

### 判断 4: **機械検査は置かない**

**「環境固有の観測か恒久制約か」は意味の理解が要り、文字列一致では判定できない**
（本リポが `AST` の近傍規則・認可の変更検知で既に採っている言い方と同じ）。
**同型の事故はまだ 1 回**（#617）であり、`CLAUDE.md`「同型の事故が 2 回起きたら」にも満たない。
**回帰テストで固定するのは「規範が消えないこと」だけ**である。
