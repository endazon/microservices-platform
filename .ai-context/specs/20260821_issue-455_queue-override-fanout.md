# 作業仕様書: queue 上書きの実挙動を宣言経由で試験する（#455 Phase 0 / U0e）

## 起点となる計画書（トレーサビリティ）

- 計画 ADR: `ADR-0027` 移行チェックリスト **手順 3** / `ADR-0018`（宣言的パイプライン構成）
- 機能要求: `FR-14` / ユースケース: `UC-04`
- 実装 issue: `#455` / `#441`

## 何が無いのか —— 3b と 3c の区別

`#892` で精密化したとおり、`queue` に関する主張は 2 つに分かれる。

| # | 主張 | 状態 |
| --- | --- | --- |
| 3b | 宣言値が `PipelineStepOptions.Queue` へ**束縛される** | ✅ `PipelineStepRegistrationTests`（`Pipeline:Steps:0:Queue`） |
| **3c** | 束縛した値が**受信エンドポイント名を実際に変える** | 🔴 **無い（本作業）** |

🔴 **3b が緑でも 3c は何も保証しない。** 束縛は `IConfiguration` → POCO の話であり、
`registration.Endpoint(e => e.Name = step.Queue)` が実際に MassTransit のトポロジを変えるかは別である。

**そして 3c こそが手順 3 のレバーである。** 手順 3 は「リスニングキュー名にサービス名を前置する」ことを
求めており、その手段が `queue` 宣言である。**宣言でキュー名を制御できることが確かめられていなければ、
手順 3 を「宣言で守る」という前提そのものが未検証である。**

## `#888`（U0c）との関係 —— 同じ退行の別経路

`#888` は**コード側**で競合状態を作った（`Program.cs` を書き換える変異試験）。
本作業は**宣言側**で同じ状態を作る。**同じ退行に 2 つの経路がある**:

| 経路 | 誰が誤るか | `#888` | 本作業 |
| --- | --- | --- | --- |
| コード | サービスの実装者が `Endpoint(e => e.Name = ...)` を誤る | ✅ 変異試験で実測 | — |
| **宣言** | **`pipeline.json` の `queue` を誤る（GitOps で配送される）** | — | 🔴 **本作業** |

🔴 **宣言側のほうが危険である。** `pipeline.json` は GitOps で配送される運用物であり、
**コードレビューを経ずに変わり得る**。コード側の誤りはレビューで止まる可能性があるが、
宣言側は「設定変更」として扱われやすい。

## 設計上の判断

### 1. フィクスチャは本番 `pipeline.json` から**実行時に派生**させる

規則 2 は登録される全段の宣言を要求するため、5 段すべてが要る。**手で書き写すと必ず腐る**
（U0d で確立した原則）。本番ファイルを読み、**`queue` フィールドだけを差し替えて**一時ファイルへ書く。

### 2. テスト A（本命）は**自己検証的**である

`ingest`（IngestionService）と `wiki-sync`（WikiService）に**同一の `queue` 名**を宣言する。

- **`queue` 上書きが効いている** → 2 購読者が同一キューを共有 → 競合コンシューマ →
  **片方だけが受信する**
- **`queue` 上書きが無視されている** → 既定のキュー名は**別々** → **両方が受信する** → **テスト A が落ちる**

🔴 **したがってテスト A は「上書きが効くこと」と「効いた結果 fan-out が壊れること」を同時に証明する。**
U0d のような別建ての「本当に読み込まれたか」テストは要らない（**テスト A 自身がそれを兼ねる**）。

### 3. どちらが受信するかは**非決定**である

RabbitMQ は共有キューの購読者のうち 1 つへ配送するが、**どちらかは決まらない**。
🔴 **「Ingestion が受信する」と書いてはならない**（半分の確率で落ちるテストになる）。
**「2 つのうち丁度 1 つ」**を assert する。

### 4. 否定の assert には猶予が要る

「もう片方が受信しなかった」は**待っても来ないこと**の確認である。受信を検出したあと
**追加の猶予時間**を置いてから、もう片方が発火していないことを確かめる。

**捨てるプローブで先に実測した**（できなければ設計を変える必要があった）:

```
Passed: 1 —— cfg["Pipeline:ConfigPath"] が派生側の値になることを確認
```

プローブは確認後に削除した（`git status` で残骸 0 を確認）。

| # | 基準 | 実測 |
| --- | --- | --- |

| 4 | 検査器一式 | 下記 |

### 変異試験

**変異**: `PipelineExtensions.cs` の `if (!string.IsNullOrWhiteSpace(step.Queue))` を
`if (false && ...)` にして **`queue` 上書きを無効化**した。

**変異が当たったことを先に確認**（生の diff）:

```
-        if (!string.IsNullOrWhiteSpace(step.Queue))
+        if (false && !string.IsNullOrWhiteSpace(step.Queue))
BUILD EXIT=0   ← 通ることが重要（通らなければ変異ではなく破壊）
```

**結果**:

```
変異あり: Failed 1, Passed 46, Total 47
変異なし: Failed 0, Passed 47, Total 47
```

**落ち方も期待どおり**:

```
Expected received to be 1 because 同一の queue 名を宣言した 2 購読者は競合コンシューマになり…
2 なら queue 上書きが効いておらず既定の別キューになっている, but found 2.
```

🔴 **`but found 2` が要点である。** 上書きを無効化すると既定のキュー名が別々になり、
**両方が受信する**。これは「テストが落ちた」だけでなく、**テストが本当に上書き経路を通っている**
ことの証拠である（通っていなければ変異しても結果は変わらない）。

**復旧確認**: 変異残骸 0・`git diff` に `src/platform/` の差分なし・復旧後 47/47 緑。

### 自己検証性が効いた

U0d では「宣言が実際に読み込まれたか」を別テストで assert する必要があった
（`AddPlatformPipelineConfig` が黙って return するため）。**本作業ではそれが要らない** ——
上書きが無視されれば既定キューが別々になり **received = 2 でテストが落ちる**ためである。
**同じ穴を、別建ての番人ではなくテスト自身の構造で塞いだ。**
