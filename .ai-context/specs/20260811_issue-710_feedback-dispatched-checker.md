# 作業仕様書: 環流の未送付を検出する検査器の取り込み（#710）

- **NFR**（文書統制・運用保守。**メタ作業なので無採番**。[IADR-0179](../adr/IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 1）

- 出所: #707（PR #708）の射程外宣言「**`scripts/check-feedback-dispatched.js` の取り込みは別 issue とする**」

付随する `scripts.test.js` のテストブロック（キット側 **50 行**）も本リポには無い。

## 判断

### ★★ 判断 1: **キット原文をそのまま置く。検査器を書き換えない**

[IADR-0115](../adr/IADR-0115_impl-handoff-kit-as-single-source.md) 決定 2 が許す固有デルタは **4 種のみ**で、
**「検査器の判定ロジックを本リポ向けに調整する」はどれにも当たらない。**
**書き換えれば次のキット同期で消える**（決定 2「これ以外の独自記述は同期時に削除する」）。

**同 決定 3 は「汎用的な改善は本リポに留めず、キットへ環流する」と定める。**
**記録ファイル経路を証拠として認めるのは、キット全体に効く汎用の改善である**（軸 c）。**環流する**（判断 5）。

### ★★ 判断 2: **偽陽性 1 件を「消す」ために、記録へ嘘を書かない**

**キットの 3 条件を、この記録が真として満たす方法は無い。**

| 条件 | この記録に当てはめると |
| --- | --- |
| a. `planning_issue:` | **planning#306 は PR であって issue ではない**。issue 番号を名乗る鍵へ PR 番号を書けば誤りになる |
| b. 他リポの issue URL | **存在しない**（伝達は PR 経路） |
| c. 本文に「起票済み」 | **起票していない**（README が認める別経路を採った） |

**検査器を満たすために別途 issue を立てるのは、記録自身が「いずれか一方で足りる」と書いた運用に反する**
——**検査器に合わせて事実の側を作りにいくことになる。**

**したがって 1 件の警告は残す。** 警告であって失敗ではなく（exit 0）、**CI は緑のまま**である。
**既知の偽陽性であることを本書と IADR に記録し、環流先の issue 番号を添える。**

> **★ #710 の受け入れ基準は「警告が 0 件」と書いていた。** それは**キットが両経路を読める前提での基準**であり、
> 実測でその前提が成り立たないと分かった。**基準の側を「既知の偽陽性 1 件・理由と環流先つき」へ改める**
> ——**満たすために記述を歪めない。**

### 判断 3: **「証拠なし 20 件」を一括是正しない**

**規約が無いものを 20 件へ一括適用しない**（#706 で `related_ids` について、#707 で `status` 語彙について
採ったのと同じ判断）。**19 件は検査器の条件にも掛からない。**

### ★ 判断 4: **ステップはキットどおり。ただし独立ジョブにする（差異を明記する）**

キットの `ci.example.yml` と**同じ 2 ステップ**（`--self-test` → 本実行）を `ci.yml` へ足す。
**厳格化の env はコメントのまま**にする —— **起票は人手の判断を伴い、ブロックにすると
「記録を作らない」という回避策を誘発する**（キットの設計意図。#683 判断 1 と同じ理屈）。

**ただしジョブ構造はキットと変える。** キットは **`doc-links` ジョブへ追記**する形だが、
**本リポは独立ジョブ `feedback-dispatched` にする。**

| | キット | 本リポ | 理由 |
| --- | --- | --- | --- |
| ジョブ | `doc-links` に相乗り | **独立** | **必須チェックの context は「ジョブ名」**（IADR-0182 決定 1）。相乗りだと**単独では必須にできず**、`doc-links` の失敗に結果が埋もれる |
| コスト | checkout 1 回 | **checkout が 1 回増える** | 上の利点に見合う |

**CI 配線は [IADR-0115](../adr/IADR-0115_impl-handoff-kit-as-single-source.md) 決定 2 が許す固有デルタ（2. 技術スタックとその CI 配線）に当たる。**
**ただし「許される」と「記録されている」は別である** —— **明記しないと、次の同期で
「配線もキット原文どおりのはず」と照合されて気づかれない**（レビュー 1 巡目の 🟢 が指摘した型）。

### ★ 判断 5: **キットへ環流する（4 件）**

| # | 対象 | 内容 |
| ---: | --- | --- |
| 1 | 検査器 | **記録ファイル経路を証拠と認めない**（README は両経路を定める） |
| 2 | `TEMPLATE.md` | **`planning_issue:` が無い** —— だから条件 a が **0 / 37** で誰も使っていない |
| 3 | 検査器 | **本文の語の一致だけで発火する**（判断 7。本作業中に踏んだ） |
| 4 | `ci.example.yml` | **コメント `env:` が `steps:` の項目と同じ字下げで、外すと不正 YAML になる** |

**いずれもキット由来であり、他の実装リポも同じ穴を踏む。**

> **★ 4 件目は「`# env:` がある」で数えると 3 件だが、実際に壊れるのは 2 件**である
> （`doc-links` / `ai-workflow-config`。`scripts-tests` の 1 件は **step 直下**なので正しい）。
> **分かれ目は字下げの深さだけ**で、目視の一次判定では誤った —— **構造で判定し直した。**

### 判断 6: **本検査器は #683 のクラス C である**

`fs.readdirSync` で**作業ツリーを読む**（git を一切呼ばない）。
**走らせる順序で結果が変わらない**ので、[IADR-0183](../adr/IADR-0183_false-green-warning-on-worktree-state.md) の
順序警告は**足さない**（足すと嘘になる）。**#709 で新設した分類の回帰テストが、これを機械的に確かめる。**

### ★★ 判断 7: **本記録自身が、検査器の 3 つ目の粗さを踏んだ**

**環流記録を書いた直後に警告が 1 → 2 件へ増えた。** 検査器は「本文に **未** ＋ **送付** の語がある」ことを
`status` を問わず警告する条件にしており、**検査器 *について* 書いた記録も語を含むだけで発火する。**

**見出しの語を「伝達漏れ」へ言い換えて回避した** —— **意味は変えていない**（自己申告ではなく検査器の説明である）。
**知見 3 として planning#319 へ追記した。**

> **★ 検査器を通すために事実を曲げたのではない。** 曲げれば判断 2 と矛盾する。
> **本記録は元から自己申告をしていない**ので、語の選び方を変えただけである。
