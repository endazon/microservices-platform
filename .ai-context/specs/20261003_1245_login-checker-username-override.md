# 作業仕様書 — ログインの検査器の利用者名の上書き と PR-D 手順書の未決の解消

## 起点

- issue: **#1245**（PR-D 待ち）。2026-10-03 の利用者裁定（issue コメント「§未決 8 点の振り分け」）:
  - **⑥ 足す**: `scripts/check-login-existence-disclosure.js` に利用者名の上書きを足す。試験専用の利用者を指定でき、
    **realm 宣言にある利用者名は拒否する**。
  - **④** C1 は上流が mailpit のときだけ測る。実テナントでは C1 を停止条件のまま測らない（送出経路の断は C2 / C2' / C3）。
  - **⑤** 実施後に `reset-gate.*` 属性を**消す**。記録は手順書の記録表に残す。
  - **②** 状態 D で申請へどう到達したかを、記録表の欄として足す。
  - **①③⑦⑧** は稼働環境の事実として PoC が実測する（未決ではなく実測項目）。
- 番号の対応（issue の丸数字 → 手順書 §未決事項の番号）: ①→1、②→2、③→3、④→4、⑤→5、⑥→6、⑦→9、⑧→10。
  手順書の 7（所要時間の判定式の実装）と 8（ロック中の応答）は裁定の 8 点に含まれない（下の「判断」）。

## 射程

### やること

1. 検査器に上書きの口を足す。
   - CLI `--username <名前>`（兄弟の `measure-cutover-inventory.js` の `--flag 値` 形）と環境変数 `LOGIN_PROBE_USERNAME`
     （`measure-search-ndcg.js` の `--k` / `NDCG_K` と同じく **CLI が環境変数に勝つ**）。
   - **指定が無ければ今と同じ**（realm 宣言の最初の対話利用者 ＝ `admin`）。CI（`integration-stack.yml` の `--live` /
     `--self-test`）は引数も環境変数も渡していないので挙動は変わらない。
   - realm 宣言の `users[].username` に一致する名前は**大小を無視して**拒否する（Keycloak は利用者名を小文字で保持するので、
     `Admin` は `admin` に当たる）。手順書の使い捨てスクリプトの拒否（完全一致）より厳しい側に揃え、
     使い捨てスクリプトは検査器の判定関数を借りる形へ改める（**拒否の正本を 1 つにする**）。
   - 🔴 **空の上書きは既定へ倒さない**。`LOGIN_PROBE_USERNAME=`（空・空白だけ）や値の無い `--username` は exit 2 で止める。
     既定へ倒すと「試験利用者を指定したつもりで `admin` に失敗を積む」—— 上書きを足した理由そのものを壊す。
   - 前後の空白・制御文字を含む名前も止める（作った利用者に一致しない名前で測ると、両側とも非実在の対になり**黙って緑**になる）。
   - 陰性対照（非実在名）を作るとき、上書きした名前も「取られている名前」に数える（生成した名前が試験利用者と衝突しないように）。
2. 試験（`scripts/scripts.repo.test.js`）: 上書きが効く／宣言済みの名前の拒否（大小違いを含む）／既定が変わらない／
   空・値なし・空白・制御文字・重複指定の扱い／陰性対照が上書き名と衝突しない／`main` の引数解析が `--username` を受ける。
3. 手順書 `docs/operations/password-reset-relay-state-measurement-runbook.md`:
   - §未決事項 を「裁定済み（②④⑤⑥）」「実測項目（①③⑦⑧ と、裁定の外の 8）」「残るもの（7）」へ組み替える。
   - §4: 試験利用者に対して**検査器を上書きつきで稼働モードにする手順**を足す（ロックの手前の 3 面を CI と同じ判定で測る）。
     ロック後の測定は検査器の射程外（ロックの手前で止まる設計）なので、使い捨てスクリプトを残し、拒否は検査器の関数を借りる。
     順序は **使い捨て（ロックさせる）→ 解除 → 検査器（失敗の計数がゼロからの 4 回）→ 削除**（逆順だと検査器の 4 回の失敗が
     計数に残り、使い捨ての 1 回目でロックして `afterLockThreshold` の境界がずれる）。
   - ⑤: 実施の最後に `reset-gate.*` 3 属性を消す手順（門の Pod から門自身の資格情報で、門と同じ read-modify-write の形で
     その 3 キーだけを落とす）。🔴 **開いた状態（`resetPasswordAllowed=true` かつ `state="open"`）でしか消さない** ——
     閉じた状態で標識を消すと、門は「人が手で閉じた」と読んで二度と開けない（`decide` の分岐）。
   - ④: S1・§2.2・§限界 を裁定どおりに。
   - ②: 表 1 に「申請への到達（導線が消えた後）」の欄。§2.6 に記録の指示。
   - 検査器の上書きを含む版であることを §前提 で確かめる。

### やらないこと

- 検査器の判定（T-09〜T-11）・標本数・所要時間の扱いは変えない。
- **上書きした利用者が稼働 realm に実在するかは検査器で確かめない**（管理 API の資格情報を持たない設計。下の残余リスク）。
- 手順書 §2.1 の所要時間の記述（順位和検定が未実装と書いている箇所）の更新。追跡 issue は CLOSED に変わっているが、
  §2.1 の書き換えは本裁定の射程外であり、§未決事項 7 に「本書の作成後に動いた」とだけ書く。
- `--self-test` の件数（25 件）は変えない（試験は companion 側へ足す）。README・テスト仕様書の件数表記が腐らない。

## 判断（IADR を起こさない理由）

上書きの形（CLI ＋ 環境変数、CLI 優先、空は止める、宣言済みは大小無視で拒否）は兄弟の検査器の作法と裁定の文言から
一意に決まり、代替案の比較を要する設計判断を含まない。IADR-0427 の判定・標本数の決定は 1 つも覆さない。

## 残余リスク

- 上書きした利用者が稼働 realm に**居ない**と、両側とも非実在の対になり T-09〜T-11 は一致して緑になる。
  検査器は管理 API の資格情報を持たないのでこれを見分けられない。手順書は「作った直後に管理コンソールで在ることを確かめる」
  「先にロックさせて User events にロックの行が出た利用者に対して走らせる」順序で塞ぐ。
- 手順書の削除手順（⑤）が前提にする「realm の PUT で `attributes` から落としたキーが消える」は稼働の Keycloak で未実測。
  消えなければその事実を記録して止める（手順書に分岐として書いた）。
