- 計画 ADR: **ADR-0113**（順位和検定・有意水準 1%。§結果「系統差が無くても約 100 回に 1 回は不合格になる」・フォローアップ 2「CI の実測を環流で届ける」）／
  **ADR-0097** 決定 3（検査器の赤を床の引き直しの契機にする）／ADR-0094（測り方・`評価不能`）
- 実装 IADR: **IADR-0470**（順位和検定の実装。本作業で追記）／IADR-0232（integration-stack を PR から後段へ移した理由）

## 切り分け（証跡）

`gh run view 36244009369` の手順一覧: `🔴 Gate — the stack is actually up` は緑、**`🔴 Gate — パスワードリセットの送出とメール本文（#1144）` が赤**、

順位和検定（両側・正確法）: … 実在側の順位和 W=713（期待値 588）・U=413 / p=0.0094（有意水準 0.01）

### 回帰ではない根拠

1. **緑と赤の間のコミットは #1590（`8f7b1e4d`）の 1 件だけ**で、変更は `scripts/check-realm-constraints.js`（静的検査）・`scripts/scripts.repo.test.js`・文書 4 件である。
   `integration-stack.yml` は `check-realm-constraints.js` を呼ばず、realm JSON・イメージ・chart も変わっていない。**クラスタへ入るものは緑の run と同一**。
2. 疑った候補のうち #1578 / #1587 / #1586 / #1576 / #1579 / #1584 / #1570 は**直前の緑 `2dad2d61` に含まれる**（`git merge-base --is-ancestor` で確認）。
   #1593 は赤の後（`8f32e373`）で、赤の run には入っていない。
3. **次の develop の run 36244939449（`8f32e373`）は緑**で、T-25 は W=563 / p=0.6165。
4. p=0.0094 は有意水準 0.01 をわずかに下回った**単発**であり、床の平均の外れ（床が外れれば実在 37 ms / 非実在 19 ms の形で p は 1e-9 未満。
   自己試験の陽性対照）とは桁が違う。中央値はすべて床 150 ms の内側 152 ms 台で、自己対照は 1.00 倍。
   integration-stack.yml の注記と検査器の文言が既に書いている見分け方（「偶然の赤は p が 0.01 をわずかに下回って単発に出る。床が外れていれば p はごく小さく、赤が続く」）にそのまま当たる。

### ADR-0113 フォローアップ 2 の CI 実測（本作業で集めた母集合）

- **母集合**: #1541 のマージ（`77898402`・run 36217595485）以降の integration-stack の run すべて（develop の push 23 件＋ dispatch 1 件＝ 24 件。
  2026-09-26T04:21Z〜13:22Z）。**検査器の段まで届いた run は 21 件**、届かなかった 3 件はいずれも `cancelled`（concurrency で後続に置き換えられた。
  36225372162 / 36236866295 / 36245515356）。実行中の 36245528408 は数えない。
- 抽出は各 run の `gh run view <id> --log` から `順位和検定（両側・正確法）` の行と `反復 N:` の行を読んだ。

| 項目 | 値 |
| --- | --- |
| 検査器の段まで届いた run 数 N ／届かなかった run 数 | 21 ／ 3（すべて cancelled） |
| `不合格` の回数（うち p < 0.001） | 1（run 36244009369・p=0.0094）（0） |
| `評価不能` の回数（自己対照の最大値） | 0（判定に使う反復の自己対照は 1.00〜1.01 倍） |
| p 値の分布 | p < 0.01: 1/21 ・ p < 0.05: 3/21 ・ p < 0.1: 3/21 ・ p < 0.5: 10/21 ／最小 0.0094・中央値 0.5062・最大 0.9593 |
| 一様分布との隔たり | Kolmogorov–Smirnov の D = 0.133（N = 21 の 5% 棄却点 ≈ 0.29 を大きく下回る） |
| p < 0.05 の 3 件の向き | 非実在が遅い 1 件（36234336402・p=0.0183）／実在が遅い 2 件（36239339535〔dispatch〕・p=0.0163 ／ 36244009369・p=0.0094）—— 向きが揃っていない |
| 反復ごとの中央値の範囲（暖機を含む） | 151.951〜153.487 ms（実在・非実在とも床 150 ms の内側） |
| 同順位ありの run 数 | 0 |
| 床の構成 | `RESET_FLOOR` を与えない既定（床あり）・Istio あり（`ISTIO=1`） |

読み方: 21 回で 1 回以上の偶然の赤が出る確率は 1 − 0.99^21 ≈ 19%。p < 0.05 が 3 件（期待 1.05 件）は多めだが、二項で P(≥3) ≈ 0.085 であり、
向きも揃っていない。**床の回帰（p が 0 付近へ偏る・赤が続く）を示す形ではない。** N がまだ小さいので、環流するなら N を積んだうえでよい。

## 根本原因

- **赤そのものの原因**: ADR-0113 が明示の値として受け入れた偶然の不合格（有意水準 1%）。コードの回帰ではない。
  🔴 **判定（p < 0.01 で `不合格`）は変えない。** 再測定で確かめてから落とす等の形は偶然の赤の率と検出力を変え、ADR-0113 決定 1・2 に反する（変えるには計画の裁定が要る）。
- **実装側の欠陥（本作業で直すもの）**: integration-stack の後段 4 ステップは GitHub の既定 `success()` で、前のどれかが落ちると走らない。
  そのため**計画が受け入れた 1% の偶然の赤で、独立した後段の門（ABAC・検索・ログイン経路の存在秘匿）が 1 本も評価されなかった**。
  同じ run に別の退行が入っていても見えず、しかも「T-25 だけの単発の赤か」を run 1 本で読めない。

## 🔴 着手前に確認した制約

- **ADR-0113 決定 1・2（有意水準 1%・片側 12・反復 3）と `check-password-reset-mail.js` の判定は変えない。** 検査器は 1 行も変えない。
- **ジョブの合否は変えない。** どれか 1 つでも落ちればジョブは赤で、#1597 のような起票も従来どおり起きる。`continue-on-error` は使わない。
- **起きていないスタックを後段で測らない。** 後段はスタックの門（`check-stack-ready.js`）が緑のときだけ走る。
- **ABAC と検索の門は 2 つの投入が緑のときだけ走る**（投入が落ちたまま測ると「認可の故障」と「投入漏れ」を区別できない。既存の注記の統制）。
- **ログイン経路の門は最後に置く**順序の統制（brute-force の計数を他の門へ波及させない）を変えない。
- 起動条件（schedule / push(develop) / dispatch）・必須チェック・`report-failure` は変えない。`permissions` も変えない。
- 稼働クラスタには触らない（LIVE 未設定・`--live` を手元で渡さない）。検証は integration-stack を本 PR のブランチで dispatch して行う。

## 母集合（[[IADR-0141]] 決定 1。着手時に自分で引いた）

### 「前の失敗で後段を飛ばす」形の門

`.github/workflows/integration-stack.yml` の `stack` ジョブの全ステップを読んだ（`grep -n "- name:"`）。

| ステップ | 扱い | 理由 |
| --- | --- | --- |
| 自己試験 3 本・k3d 導入・up・待ち | 変えない | スタックを起こす前段。落ちれば後段を測れない |
| `🔴 Gate — the stack is actually up` | `id: stack-ready` を付ける | 後段の前提（起きていないスタックを測らない） |
| `🔴 Gate — パスワードリセットの送出とメール本文` | 変えない（`if:` 無し＝スタックの門が緑のときだけ走る既定） | 偶然の赤を出し得る門そのもの |
| `ABAC ポリシーの投入を確定させる` / `検索検証用文書の投入を確定させる` | `if: !cancelled() && steps.stack-ready.outcome == 'success'` | T-25 の結果と独立 |
| `🔴 Gate — ABAC の正常系と検索の命中が観測できる` | `if: !cancelled() && 2 つの投入が success` | 投入の成否に依存（既存の統制） |
| `🔴 Gate — ログイン経路の存在秘匿` | `if: !cancelled() && steps.stack-ready.outcome == 'success'` | 他の門と独立。最後に置く順序は保つ |
| `Dump cluster state`（`if: failure()`）/ `Tear down`（`if: always()`） | 変えない | 既に失敗・常時で走る |

他のワークフローで偶然の赤を出す検査器を呼ぶものは無い（`grep -rn "check-password-reset-mail.js --live" .github/workflows` → integration-stack.yml の 1 件）。

## 変更内容

1. `.github/workflows/integration-stack.yml`: 上表のとおり `id` と `if:` を足し、パスワードリセットの門の注記に理由（run 36244009369）を足す。
2. `scripts/k8s-local-up.test.js`: 配線を固定する試験を 1 件足す（integration-stack.yml の配線試験が集まっている #1316 / #1304 の隣）。
   `if:` を文字列の部分一致ではなく**場面ごとに JS として評価する**（#1304 の真理値表と同じ理由）。`if:` の無いステップは既定の `success()` として評価するので、
   条件を外した形（＝是正前）は場面 1 で落ちる。場面: ① スタック緑・T-25 赤 → 後段 4 本が走る ② スタック赤 → 全部飛ばす
   ③ 投入の片方が赤 → ABAC と検索の門は飛ばし、ログイン経路の門は走る ④ 取り消し → 何も走らない ⑤ 全部緑 → 全部走る。
   あわせて `continue-on-error` が無いこと・パスワードリセットの門に `if:` が無いことを見る。
3. `.ai-context/adr/IADR-0470_reset-timing-rank-sum-exact-test.md`: 日付つき追記で、CI 実測の 1 回目（上表）と本配線を残す（新しい IADR は起こさない）。
