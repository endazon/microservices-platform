# 逆転監視の母集合を「現在の CI 構成で測られた PR」に限る

## 起点

計画 ID を持たない**メタ作業**（CI・開発ループの統制）である。`.claude/rules/traceability.md`
「起点 ID の種別」の無採番 `NFR` を許す 2 つ目の場合 —— 計画側の非機能要件表に当たる番号が無い
——に当たる（規約整備・検査器の追加が典型例として明記されている）。**環流はしない。**

**AST（ai-stock-trading）で先に実装し、実運用で確認した内容の追随である**（利用者裁定 2026-08-22
「AST を先に入れ、MSP は別 PR で追随」）。AST 側の記録は同リポジトリの `IADR-0208` 決定 13・15。

## 背景 —— AST で起きたこと

逆転監視（`ci-latency-watch.yml` / `scripts/check-ci-latency.js`）は
「`build-and-test` の**中央値** > `claude-review` の**最小値**」で判定する。
中央値は「直近 N 本のマージ済み PR が**同じ CI 構成**で走った」と仮定している。

AST では CI を高速化した直後、**窓の多数派が旧構成のまま**だったため、
監視が数週間にわたり「逆転している」と言い続ける状態になった。
**監視は嘘をついていない** —— 中央値は窓の多数派を映すのだから、多数派が旧構成なら旧構成の値を返す。

`IADR-0232` 決定 8 の**定常性の門**（中央値 ≧ 最小 × 2 なら判定しない）は
これを止められない。AST の段差は 223 → 125 秒＝**1.8 倍**で、2 倍の門をくぐった。

> **［2026-08-22 追記 / #927］この引用は当初「決定 9」と書いており、誤りだった**（AI レビューが指摘）。
> 🔴 **AST（ai-stock-trading）の番号をそのまま持ち込み、しかも本節へ「（本リポジトリでは同番号）」と
> 検証せずに断定していた。** 実物を引くと、逆転監視は
> **AST の `IADR-0208` では決定 9、本リポジトリの `IADR-0232` では決定 8** である
> （本リポジトリに決定 9 という見出しは無い）。
>
> **ずれの原因は AST にだけ「決定 8: テストのアセンブリ間並列化は試したが不採用」がある**ことで、
> そこから先が 1 つずれる。**同じ作業を 2 リポジトリへ移すとき、決定番号は一致しない。**
>
> 🔴 **移植で最も起こしやすい誤りである** —— 文章も設計も正しく移せているのに、
> **他リポジトリの記録を確かめずに同じ番号で引く**。読み手を存在しない見出しへ送るので、
> ポインタは是正した（本リポジトリ内 5 箇所 ＋ PR 本文）。**なぜ間違えたかを残すのがこの注記の目的である。**


🔴 **問題は「窓が入れ替わるまで毎週同じ文言で鳴り続ける」ことである。**
その間、**本物の再逆転が起きても同じ文言に埋もれて見分けられない**。

**しきい値では直らない**（倍率を動かしても段差の大きさ次第でまた漏れる）。**母集合を正す。**

## 本リポジトリの現状（実測 2026-08-22。着手前に確認した）

```
マージ済み PR 10 本を走査: build-and-test 10 件 / claude-review 10 件
build-and-test の中央値 121 秒  vs  claude-review の最小 151 秒（余裕 30 秒）
OK: 逆転していない。
```

🔴 **本リポジトリの監視はいま「判定していて緑」である。** したがって本作業は**予防**であり、
**最優先の制約は「判定している監視を、判定しない監視に変えないこと」**である。

epoch（`.github/workflows/ci.yml` の最終変更時刻）は **2026-08-21T20:40:15Z**（#902）。
直近 10 本のうち **epoch 以降に測られたのは 4 本**（#905 / #922 / #904 / #903）で、
さらに **#902 自身が「構成変更を持ち込んだ PR」として救済されて 5 本**になる。
**最小本数 3 本を満たすので、判定は継続する**（実測で確認済み。実装後に再確認する）。

## 変更内容

`scripts/check-ci-latency.js` のみ。**`.github/workflows/` は触らず、必須チェック名も変えない。**
**権限の追加も不要**（`contents: read` / `pull-requests: read` / `checks: read` を既に持つ）。

1. **epoch を GitHub API から導出する。**
   `GET /commits?path=.github/workflows/ci.yml&per_page=1&sha=<統合ブランチ>`。
   - 🔴 **日付を焼き込まない**（固定値は必ず腐る。本検査器が「しきい値を固定値で持たない」と決めたのと同じ理由）。
   - 🔴 **`git log` を使わない** —— `actions/checkout` は既定で shallow で、出力が**履歴の打ち切り位置**を
     指し得る。**形式は満たすので気付けない**（`traceability.repo.md` の ★ が同じ罠を警告している）。
   - 🔴 **統合ブランチは母集合の PR 自身の `base.ref` の最頻値から導く。**
     `sha` を省略すると**既定ブランチ**になり、GitHub の設定に依存する。**ブランチ名も焼き込まない。**
2. **`representsCurrentConfig()`: 「この計測は現在の CI 構成を表すか」を判定する。**
   - **計測時刻（check 群の開始 `t0`）で見る。マージ時刻ではない** ——
     「CI が走ったのは構成変更の前、マージはその後」という PR は普通に起こる。
   - ただし**構成変更を持ち込んだ PR 自身は残す** —— その run は新しい `ci.yml` で走っている
     （`pull_request` の run は base を取り込んだ merge ref で動く）のに、epoch はその run より後になる。
     **落ちるのは「新構成での最初の 1 本」＝最も知りたいサンプル**である。
   - **外した本数を必ず出力する**（黙って母集合を狭めない）。
3. **最小本数 `MIN_SAMPLES = 3`。** 満たなければ epoch と本数を添えて判定しない。
   **本数の門は null 判定より前**に置く（0 本のときこそ epoch を理由に添えねばならない）。
4. **0 本のときの「check 名の設定ミスを疑え」を、epoch で外したのが原因なら出さない。**
   原因が分かっているのに読み手を誤った方向へ差し向けない。
5. **定常性の門（決定 8）は残す。** epoch は**既知の構成変更**を、門は
   **`ci.yml` を触らない原因**（依存更新でテストが重くなる等）を扱う。役割が違うので片方に寄せない。
6. **`CI_LATENCY_EPOCH` / `CI_LATENCY_MIN_SAMPLES` / `CI_LATENCY_CONFIG_PATH` の環境変数上書き。**
   🔴 **実データに対して両方向を実測するために要る**（片方向では「常に skip する実装」と区別できない）。

### 採らないもの（AST にあって本リポジトリに入れないもの）

| AST の決定 | 採否 | 理由 |
| --- | --- | --- |
| 決定 13: **backend を skip した PR を母集合から外す** | **採らない** | 本リポジトリに「backend 非変更 PR で backend ジョブを skip する」機構（AST の決定 11・`detect-changed-areas.js`）が**無い**。母集合は二峰性にならず、入れても**恒久的に不活性なコード**になる。🔴 **入れる条件: 本リポジトリが同種の skip を導入したとき。同時に入れる**（条件を書かない除外は恒久化する） |
| 決定 14: `check-workflow-job-refs.js` | **採らない**（本 PR の範囲外） | AST の `docs/ai-workflow.md` の**表の書式に密結合**している。本リポジトリの同型の乖離は `scripts/README.md` にあり書式が違う。**必要になったら別途** |

**`fetchChangedFiles()`（全ページ取得）は採る** —— 決定 13 のためではなく、
上記 2 の「構成変更を持ち込んだ PR か」の判定に変更ファイル一覧が要るためである。
🔴 **1 ページ目だけ見ると誤る**のは AST で実測済み（変更 619 ファイルの PR が該当した）。

## 受け入れ基準

1. epoch より前に**測られた** PR が母集合から外れ、**外した本数が出力される**。
2. **構成変更を持ち込んだ PR 自身は残る**（`t0` が epoch より前でも）。
3. 対象が `MIN_SAMPLES` 未満なら、**epoch と本数を添えて**判定を skip する。
4. 対象が足りていれば**判定する**（skip しっぱなしでない）。
5. epoch が引けない／壊れている／計測時刻が取れないときは**絞り込まない**（fail-open）。
6. 🔴 **本リポジトリの監視が「判定する」状態を保つ**（実測で前後比較する）。
7. 自己試験・`scripts.test.js` / `scripts.repo.test.js`・全検査器が緑。必須チェック名は 1 つも変わらない。

## 母集合の取り方（規則 6・9: 引いた結果と除外の理由を残す）

- **コードの母集合**は `scripts/check-ci-latency.js` **1 ファイル**である。
  誤りの側（`merged_at` で母集合を切る記述・epoch を持たない記述）で走査した結果、他に該当は無い。
- **文書の母集合**: 新規 IADR ＋ `.ai-context/adr/README.md`（索引）＋ 本仕様書。
  🔴 **`IADR-0232` へは追記しない** —— **`#907` が同ファイルを触っており、ファイル領域が交差する**
  （運用ガイド「並列作業は宣言済みファイル領域の非重複で判定し、交差する issue は直列化する」）。
  新規 IADR から `IADR-0232` を**一方向**で参照する（`docs/README.md` 運用ルール 4 /
  [[IADR-0171]] のとおり、ADR 側に逆リンクを張る義務は無い）。
- **除外**: `.ai-context/specs/` の既存記録は point-in-time のため書き換えない。

🔴 **番号は予約できない。先にマージした側が保持する。** `check-adr-numbering.js` が昇順・**欠番なし**を
fail で見るため、**欠番を作る番号（飛ばし）を採ってはならない**。

- 着手時点の `origin/develop` の最大は **`IADR-0236`**。本作業は **`IADR-0237`**（＝最大 ＋1）を採る。
- **`#923` が同じ `0237` を要する見込みである**（同 PR は `IADR-0235` を使っているが、
  その番号は `#905` が develop で先に確保済みのため付け替えが要る）。
  **`#923` が先に着地したら、本作業は `origin/develop` の最大を読み直して `+1` へ付け替える。**
- **付け替えはマージ直前に行い、見込みで書かない。** 追随先はファイル名・frontmatter・H1・
  索引行（`README.md`）・本仕様書の `related_ids` ＋ 本節・PR 本文（**git の外なので手で直す**）。

> **［2026-08-22 追記 / #927］実際の結末。** 上の見込みは**半分外れた**。
> 分岐後に develop へ着地したのは 2 本で、**#924 が `IADR-0237` を、#923 が `IADR-0238` を確保**した
> （見込みは「#923 が 0237」だったが、#924 の存在を勘定に入れていなかった）。
> develop の最大が **0238** になったため、本作業は **`IADR-0239`** へ付け替えた。
>
> **外れたのは「どの PR がどの番号を取るか」だけで、「番号は予約できない・マージ直前に読み直す」
> という手順自体は正しかった。** 予見して本節を書いておいたので、**衝突は README.md の索引 1 行だけ**に
> 収まり、付け替えは走査で引いた 8 箇所（＋ git の外の PR タイトルと本文）を機械的に直すだけで済んだ。
>
> 🔴 **索引の衝突解消では、相手（#924・#923）の 2 行を落とさないことに注意した** ——
> 自分の行だけ残して解消するのが、この形で最も起きやすい事故である。

> **［2026-08-22 追記 2 / #927］同じことがもう一度起きた。** 上の付け替え（0237 → 0239）の直後、
> **#926 が `IADR-0239` を確保した**（`IADR-0239_wolverine-pipeline-step-registration.md`）。
> develop の最大が 0239 になったため、本作業は **`IADR-0240`** へ**2 度目の付け替え**をした。
> 衝突は今回も **`README.md` の索引 1 箇所だけ**だった。
>
> 🔴 **「番号は予約できない」を、2 回続けて実演したことになる。** 本節が「見込みで書かない・
> マージ直前に読み直す」と定めていたのは正しく、**1 回で終わる保証は無い**。
> レビュー往復のたびに develop は進むので、**付け替えは「最後にもう一度」ではなく
> 「マージの直前に毎回」引き直す**。
>
> **当時の記録（0237 → 0239）はそのまま残す。** 経過そのものが、この規約が要る理由の証拠である。
