# 作業仕様書 — E2E の flaky の集計と起票（E-73）

> 本仕様書は実装着手前に作成した（着手 2026-10-24）。親は #2013。基準書は `docs/tests/E2E_STANDARDS.md` §10・§12。

## 受け入れ基準（issue #2037）

- [ ] HTML レポートの flaky 件数を読み取り、閾値で警告・起票

（CI が緑になってから印を付ける。マージをもって完了とする。）

## 範囲の確定（オーケストレーターの指示）

- issue の題は「flaky 集計と**隔離規約**」で、触るファイル領域に「隔離 2 週間の規約」とある。**本 PR は隔離の仕組みも規約も作らない。**
  扱うのは集計・可視化・再発時の扱い（起票）だけである（オーケストレーターの指示。test を skip・quarantine して緑にする仕組み・規約は禁止）。
- 基準書 §10 の既存の記述（live は 2 nightly 連続で flaky なら `test.fixme` で隔離し 2 週間で解消）は、隔離の規約そのものなので
  「隔離で緑にしない」へ改めた（IADR-0623 決定 4）。

## 判断

1. **入力は html と同じ実行結果の JSON レポート**（`merge-reports --reporter html,github,json`、`PLAYWRIGHT_JSON_OUTPUT_FILE`）。
   html レポートは結果を圧縮して埋め込んでおり、解くと Playwright の内部形式に依存する。JSON レポートは同じ実行の同じ結果で、形が公開されている。
   受け入れ基準の「HTML レポートの flaky 件数」と同じ数を読む（手元の実測: html の Run Summary「1 flaky / 185 passed」と JSON の集計「flaky 1 / 186」が一致）。
2. **閾値**: 警告は flaky 1 件から（基準書 §10）。起票は同じ test が develop で 3 回連続（基準書 §10）。flaky で PR は落とさない。
3. **連続の数え方**: develop への push の Frontend CI の実行のうち、要約（成果物 `e2e-flaky-summary`、14 日）を残したものを新しい順に並べ、
   今回と直前 2 回のすべてで flaky だった test を「再発」とする。要約が無い実行は数えない（連続を作らない側へ倒す）。
   履歴が 2 件に満たなければ判定しない。`runNumber` で比べ、今回以後（再実行の自分自身を含む）は履歴に入れない。
   窓（規則 11）: 「増える側」= 3 回目の flaky で初めて起票されること、「減る側」= 間に 1 回 flaky でない実行が挟まれば起票しないこと、を自己試験の両方のプローブで見る。
   形は「窓の両端と中を全部見る（every）」で、片側（some）にすると減る側のプローブが赤になることを変異で確かめた。
4. **起票の置き場所**: 別ジョブ `e2e-flaky-issue`（`needs: e2e`、develop への push で e2e が success のときだけ）。
   `issues: write` を PR でも走る `e2e` ジョブに持たせない。履歴は `gh run list` / `gh run download` で読む（`actions: read`）。
   起票は test ごとに 1 issue（本文のマーカー＝識別子の sha256 の先頭 16 桁）。在ればコメントを足す。自動ではクローズしない。
   起票の型は `check-age-apkindex.js`（IADR-0568）に揃えた（ラベルの冪等な作成・マーカーで引く・token が無ければ exit 1）。
   `ci-failure-issue.yml` は「ワークフローの失敗」を 1 件の issue にする部品で、test ごとの issue と本文を持てないので使わない。
5. **fail-closed**: JSON を読めない・形が違う・test が 0 件・未知の status は exit 1。再発を検知したのに起票できないときも exit 1。
6. **検査器の新設の条件**: 「同型の事故が 2 回」ではなく、基準書 §10 と親 #2013 の分割案（E-73）の名指しに基づく新設である。
7. **AST（E-72・AST#1421）は同じ実装を各リポに置く**（issue の依存欄）。本 PR の `scripts/check-e2e-flaky.js` をそのまま写せる（MSP 固有の値は
   `renderIssue` の e2e の置き場所 `src/platform/frontend/e2e/` と、ワークフロー名 `frontend.yml` だけ）。

## 検証

```bash
cd src && pnpm install --frozen-lockfile && pnpm run build
# 一時の flaky spec（retry 0 で落ち、retry 1 で通る。describe の中）を足して 2 シャード → merge（json つき）→ 集計し、spec は消した
CI=1 npx playwright test --shard=1/2 / --shard=2/2      # 93 passed + 1 flaky / 92 passed
PLAYWRIGHT_JSON_OUTPUT_FILE=... npx playwright merge-reports --reporter html,github,json ./all-blob-reports
node scripts/check-e2e-flaky.js --report merged.json --out cur/e2e-flaky-summary.json
#   ::warning::E2E の flaky: smoke › zz-flaky.smoke.spec.ts › 一時の群 › 一時の flaky（…:4）／ flaky 1 件 / 186 件、exit 0
node scripts/check-e2e-flaky.js --self-test             # 13 件合格
REQUIRE_REPO_TESTS=1 node scripts/scripts.test.js       # 1184 passed
actionlint .github/workflows/frontend.yml
```

- 変異（入れて赤を確かめて戻した）: 連続の判定を every → some にすると「連続でない」の自己試験が赤。unexpected も flaky と数えると集計の自己試験が赤。
  `merge-reports` から json を外すと、`--report` の配線の試験が赤。`e2e-flaky-issue` の `if:` から develop への push の条件を外すと、起票の範囲の試験が赤。
- 実際の起票（GitHub の API）は develop への push の実行でしか走らない。自己試験は API を差し替えて、作成・追記・不要時に呼ばないこと・token 無しで赤を見る。
