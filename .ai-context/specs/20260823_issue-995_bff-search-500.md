# 作業仕様書: 統合スタックの `POST /bff/search` 500 を是正する（#995）

## 起点となる計画書（トレーサビリティ）

- 機能要求（FR）: FR-03（ハイブリッド検索）/ FR-02（取り込み・埋め込み）/ FR-05（ABAC）
- ユースケース（UC）: UC-01（検索・質問する）
- 画面（SC）: SC-01（検索・チャット）
- 関連 ADR: ADR-0016（埋め込みの越境判定・モデル別コレクション）・ADR-0023（メッシュとポート）
- 関連 IADR: IADR-0089（上流ポートのドリフト）・IADR-0249（上流ポート検査の母集合）・
  IADR-0255（エッジ導線スモークの段数 fail-closed）

## 起点

`integration-stack` が develop で 2 回連続して落ちている（#995）。
失敗は `scripts/verify-oidc-edge-flow.sh` の段 **[11/17]「認証ありで検索を叩く」** 1 点のみで、
残り 16 段は PASS である。

```
[11/17] 認証ありで検索を叩く（200 かつ SearchResponse の形であること）
  FAIL  POST /bff/search（認証あり）→ 500（200 を期待）

結果: PASS 21 / FAIL 1（段 17/17）
```
（run 32584777623 / job 97059924871。`info` に出力された応答本文は**空**である＝本文なしの 500）

段 10（無トークン → 401）は PASS しているので、**認証・ルーティング・BFF への到達は成立している**。
段 7 の `/bff/documents` も 200、段 13〜17 の ABAC 正常系も PASS なので、
**BFF・AuthorizationService・DocumentService は健全**である。壊れているのは検索の後段だけである。

## 🔴 根本原因 —— 2 つの欠陥が直列に並んでいる

`POST /bff/search` の経路は次のとおり。

```
edge → bff-service → (ABAC scope 解決: authorization-service) 200
                   → retrieval-service POST /search
                        → llm-gateway POST /embed        ← 欠陥 A
                        → qdrant  Search(vector, ...)    ← 欠陥 B
```

BFF は後段の非 2xx を**そのまま透過する**（`SearchBffEndpoints.cs`:
`if (!searchResp.IsSuccessStatusCode) return Results.StatusCode((int)searchResp.StatusCode);`）。
すなわち **500 は RetrievalService が返している**。RetrievalService の `/search` には
例外ハンドラが無い（`SearchEndpoints.cs`）ため、**未処理例外はそのまま本文なしの 500 になる**。

### 欠陥 A: RetrievalService → LlmGateway の**宛先ホストが k8s に存在しない**

`RetrievalService.Api/appsettings.json` は `"Services": { "LlmGateway": "http://llm-gateway:8080" }`。
しかし **chart が作る Service 名は `llmgateway-service`** である
（`templates/service.yaml` の `name: {{ $name }}-service` × values キー `llmgateway`）。
`llm-gateway` という Service も ExternalName エイリアスも**存在しない**
（`deploy/local/aliases/microservices-platform-externalnames.yaml` に無い）。

→ 名前解決に失敗し `HttpRequestException`。
`LlmGatewayEmbeddingService.EmbedAsync` は握らず、`SearchEndpoints` にも catch が無い → **500**。

**compose では起きない。** compose のサービス名は文字どおり `llm-gateway` であり、
`docker-compose.yml` も `Services__LlmGateway: http://llm-gateway:8080` を明示している。
**k8s だけが壊れている**ため、ローカルの compose 検証では一度も現れなかった。

`values.yaml` で `Services__LlmGateway` を上書きしているのは **aianalysis 1 件だけ**であり、
そこには「llm-gateway の Service 名は llmgateway-service である点に注意」というコメントまである。
**注意書きは書かれたが、同じ宛先を持つ他の 3 呼び出し元へは追随していなかった。**

**既存の検査器は原理的にこれを見ない。** `check-bff-downstreams.js` は
IADR-0249「検出しないこと」で **「ポート以外のドリフト（ホスト名の誤り・スキーム）。見るのはポートだけである」**
と明記している。ここはポートが 8080 で正しく、**ホスト名だけが誤っている**。

### 欠陥 B: ゲートウェイの fail-safe（空ベクトル）を、そのまま Qdrant へ渡している

欠陥 A を直しても段 11 は 500 のままである。

`/embed` は**必ず 200 を返す**設計である（`EmbeddingEndpoints.cs`）。送信拒否（fail-closed）・
次元不整合・呼び出し失敗のいずれも `Vector: [], Embedded: false` を 200 で返し、
**呼び出し側が `Embedded` を見てスキップする**という契約になっている
（`EmbedDto.cs` のコメント・IngestionService の `DocumentUpdatedConsumer` は実際にそうしている）。

**統合スタックでは埋め込みは必ず失敗する。** `Embedding__Voyage__ApiKey` を配線しているのは
`docker-compose.yml` だけで、**helm 側（`values.yaml` / `values-local.yaml`）はどこにも配線していない**
（実測: `grep -rn "Voyage" deploy scripts` のヒットは compose の 3 行のみ）。
キー未設定の `VoyageEmbeddingProvider` は `InvalidOperationException` を投げ、
`EmbeddingEndpoints` の catch が `Vector: [], Embedded: false, Retryable: true` の **200** へ縮退させる。

ところが RetrievalService 側の `LlmGatewayEmbeddingService` は **`Embedded` を読まず**
`result?.Vector ?? []` を返し、`HybridSearchService` はその**長さ 0 のベクトルを
`IVectorStore.SearchAsync` へ渡す**。実装は Qdrant であり、次元 1024 のコレクションへ
0 次元のクエリを投げるので gRPC が `RpcException` を返す。
`QdrantVectorStore.SearchAsync` は `KeywordSearchAsync` と違い **`RpcException` を捕まえていない** → **500**。

**テストが緑のまま本番だけ壊れる形**である（IADR-0014 と同型）。
`InMemoryVectorStore.SearchAsync` は `queryVector` を**まったく参照しない**ので、
0 次元だろうが 1536 次元だろうが同じ結果を返す。

## 母集合（自分で引いた結果と、除外したものとその理由）

規則 1（誤りの側から引く）・規則 2（あり得る形を列挙）・規則 3/4（拡張子・行フィルタで絞らない）・
規則 5（軸を 1 本で終わらせない）に従い、**4 軸**で引いた。

### 軸 A: 「k8s で解決できない宛先ホスト」を持つ実効値

引き方: コードの既定と appsettings をまとめて走査し、chart が作る Service 名の一覧と突き合わせた。

```
grep -rhno '"http://[a-z0-9.-]*:[0-9]*' src --include=Program.cs --include=appsettings*.json
```
（26 種のホスト:ポートが出た。うち `localhost:*` は開発既定なので対象外）

chart の Service 名（`values.yaml` の `services:` 直下キー ＋ `-service`、および
`wiki-js` / `minio` / infra エイリアス）と突き合わせた結果、**一致しないホストは `llm-gateway` ただ 1 つ**である。

| 呼び出し元 | 実効値（k8s） | 判定 |
| --- | --- | --- |
| **RetrievalService → LlmGateway** | `http://llm-gateway:8080` | 🔴 ホスト不達（本件の欠陥 A） |
| **IngestionService → LlmGateway** | `http://llm-gateway:8080` | 🔴 ホスト不達（同型・静かに壊れる） |
| **ConversionService → LlmGateway** | `http://llm-gateway:5007` | 🔴 ホスト不達 ＋ ポートも誤り |
| AiAnalysisService → LlmGateway | `http://llmgateway-service:8080`（values 上書き） | ✅ |
| その他 12 の downstream（document / datasource / retrieval / authorization / feedback / dashboard / graph / conversion / configuration / risk-management / market-monitor / wiki） | いずれも chart の Service 名と一致 | ✅ |
| infra（keycloak / qdrant / rabbitmq / redis / postgres / otel-collector / wiki-js / minio） | ExternalName エイリアスまたは実 Service が存在 | ✅ |

**3 件すべてを直す。** 本件に必要なのは Retrieval だけだが、**同じ軸で引いた同じ欠陥**であり、
片方だけ直すと母集合の規則 7（同じ値を持つ他の箇所が残る）を破る。
Ingestion の壊れ方は**静か**である —— 埋め込みに失敗しても消費側は再試行/DLQ へ回すだけで、
利用者からは「索引されない」としか見えない。

### 軸 B: 「後段が設計上の縮退（200 ＋ `Embedded=false`）で返した結果を、検証せず次の後段へ渡す箇所」

引き方: `grep -rn "EmbedAsync(" src --include=*.cs`（実装 6 / テスト 12 ヒット）と
`grep -rn "\.Vector\b\|Embedded" src --include=*.cs`。

| 呼び出し元 | `Embedded` を見るか | 判定 |
| --- | --- | --- |
| **RetrievalService `HybridSearchService`** | 🔴 見ない（`result?.Vector ?? []`） | 本件の欠陥 B |
| IngestionService `DocumentUpdatedConsumer` | ✅ 見る（`!embedding.Embedded` で分岐・`Retryable` で再試行） | 対象外 |
| AiAnalysisService `RagOrchestrator` | `/embed` を呼ばない（`/search` と `/complete` のみ） | 対象外 |

**`/embed` を呼ぶ実装は上の 2 つだけ**であり、無検証なのは RetrievalService 1 件である。

### 軸 C: 「Qdrant を呼ぶが `RpcException` を捕まえていない箇所」（RetrievalService）

| 箇所 | 現状 | 本作業の扱い |
| --- | --- | --- |
| `QdrantVectorStore.KeywordSearchAsync` | ✅ 捕まえて 0 件へ縮退（既存） | 変更しない |
| `QdrantVectorStore.SearchAsync` | 捕まえない | **変更しない**（決定 3。空ベクトルを渡さなくなるので本件の 500 は消える） |
| `QdrantVectorStore.ListAttributeValuesAsync`（`FacetAsync`） | 捕まえない | **対象外**（決定 3 と同じ理由。段 11 の経路ではない） |
| `QdrantVectorStore.UpsertAsync` / `DeleteByDocumentAsync` | 捕まえない | **対象外**（RetrievalService に本番呼び出し元が無い。書き込みは IngestionService 側） |

### 軸 D: 「BFF が後段の非 2xx をそのまま透過する経路」

`/bff/search` と `/bff/attribute-values` の 2 か所。**これは設計であって欠陥ではない**
（`SearchBffEndpoints.cs`「**後段が返した非 2xx は上で透過済みである —— 障害を 200 空応答で隠さない**」）。
**変更しない。** 透過をやめると、本件のような後段の故障が二度と CI で見えなくなる。

## 決定

### 決定 1: 宛先ホストを是正する（欠陥 A）

`deploy/helm/microservices-platform/values.yaml` の `services.retrieval` / `services.ingestion` /
`services.conversion` に `Services__LlmGateway: http://llmgateway-service:8080` を追加する。
compose は既に正しいので触らない。

### 決定 2: ゲートウェイの「埋め込めなかった」を、意味検索の系統の不在として読む（欠陥 B）

1. `LlmGatewayEmbeddingService`（Retrieval）は **`Embedded` を明示的に読み**、
   `false` なら空ベクトルを返す（契約の意図をコードに写す。`result?.Vector ?? []` の暗黙依存をやめる）。
2. `HybridSearchService` は**空ベクトルを後段へ渡さない**。
   - hybrid: ベクトル系統を呼ばず、**全文検索だけで続行**する（既存の「全文が使えなければベクトルのみ」の対称）。
   - semantic: 使える系統が無いので 0 件を返す（HTTP 200）。
   - いずれも `LogWarning` を出す。**静かに空にしない。**

### 決定 3: 🔴「設計上の縮退」は続行、「本当の故障」は 500 のまま上げる

**200 ＋ 空へ一律に潰さない。** 潰すと、後段が死んでいても検索は緑に見え、
`verify-oidc-edge-flow.sh` が段 11 のコメントで警戒している「直っていても壊れていても同じ緑」に
自らなってしまう（#972 / IADR-0252 が段 14〜15 で潰したのと同じ誤りである）。

- **続行するのは、後段が「使えない」と 200 で明示的に答えたときだけ**である
  （`/embed` の `Embedded=false`。これは ADR-0016 の fail-closed が正常に働いた状態であり、故障ではない）。
- **後段へ到達できない・後段が非 2xx やエラーを返す場合は 500 のまま**にする
  （ゲートウェイ不達の `HttpRequestException`、Qdrant の `RpcException`）。
  **CI が赤くなるのが正しい状態**である。決定 1 の是正が将来ドリフトで戻れば、また赤くなる。

### 決定 4: ホスト名軸の機械検査は**この PR では作らない**（記録に留める）

CLAUDE.md「検査器・規約の追加は**同型の事故が 2 回起きたら**を条件とする（1 回目は記録に留める）」。
ポート軸は #342 → #958 の 2 回で `check-bff-downstreams.js` を得たが、
**ホスト名軸は本件が 1 回目**である。加えて Retrieval / Ingestion / Conversion は
**typed client（`AddHttpClient<TInterface, TImpl>`）** で登録しており、既存パーサ
（`AddHttpClient("Name", c => ...)` しか読まない）と **appsettings.json を設定層として見ない**という
2 つの改造が要る。本件の射程を超えるため、IADR-0256 に**次に同型が起きたら何を作るか**を残す。

## 受け入れ基準

1. 埋め込みが得られない（`Embedded=false`）とき、`POST /search` は **200 ＋ `SearchResponse` の形**を返し、
   ベクトル検索を**呼ばない**（退行テストで観測する）
2. hybrid モードでは全文検索の結果が残る（「埋め込めない＝全滅」にしない）
3. semantic モードでは 0 件（200）を返す
4. 到達不能・`RpcException` は 500 のまま（**潰さない**ことをテストで固定する）
5. helm values の `retrieval` / `ingestion` / `conversion` の実効 `Services__LlmGateway` が
   `http://llmgateway-service:8080` になる
6. `dotnet build` / `dotnet test` / `dotnet format --verify-no-changes` が knowledge ユニットで通る

## テスト方針

- `HybridSearchServiceTests`: 空ベクトルを返す埋め込みスタブで
  (a) hybrid → ベクトル系統が **0 回**呼ばれ全文の結果が残る、(b) semantic → ベクトル系統 0 回・0 件、
  (c) 非空ベクトル → 従来どおり両系統が呼ばれる（退行させていないこと）
- `HybridSearchEndpointTests`: 空ベクトルの埋め込みスタブで `POST /search` が **200** かつ
  `SearchResponse` の形（段 11 が見ているのと同じ条件）を返す
- 例外の非隠蔽: 埋め込みが**例外を投げる**スタブで `SearchAsync` が例外を伝播する（決定 3 の固定）
