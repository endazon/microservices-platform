# 仕様書: タグの改名・再発行の読み直しとやり直し（#2150 段 1b）

## 起点となる計画書（トレーサビリティ）

- 要求: FR-02（文書の索引）、FR-06（再発行の口）、FR-09（タグ辞書の改名）。画面: SC-09（改名）。UC-04
- 計画 ADR: ADR-0027（少なくとも 1 回の配送）。順序の鍵を定める計画 ADR は無い（段 1a の作業仕様書と同じ）
- 実装 ADR: **IADR-0637 決定 6**（本書で追記）
- 前段: 段 1a（#2259。`EventSequence` を並行トークンにした）。追跡: #2258（段 1c）、#2260（R2 への移行の判断）

## コーディネーターの判断（2026-10-26）

- タグの改名は **R1**（1 トランザクションのまま）とする。
  - 競合したら全体を読み直して、上限 3 回までやり直す。
  - 超えたら何も確定せずに 409 `version_conflict` を返す。
- R2（バッチ化）は 1b では採らない。理由は次の 2 つである。
  - 契約・BFF・画面の変更が要る。
  - 「辞書は改名済みなのに射影が旧名のまま」という中間状態を生む。
- 前提: 改名は管理者のまれな操作である。行ロックは、利用者の編集を失敗させずに待たせるだけである。
- 再発行の 409 には、負けたページの先頭のカーソルを返す。
- 駆動スクリプトの再試行は、条件どおりに進めてよい。

## 設計

### 上限と再試行の形

- 上限は `DocumentVersionConflict.MaxBatchCommitAttempts = 3` で、初回を含む。改名と再発行で共有する。
- 負けたら `db.ChangeTracker.Clear()` で追跡を捨てて、読み直す。
  - 改名: タグ・同名の重複の検査・対象の文書。
  - 再発行: ページの文書・タグの表示名。
  - 読み直した後に、もう一度確定する。
- `CommitAsync` は、失敗した確定の発行を捨ててトランザクションを巻き戻す（IADR-0608 決定 2）。そのため、同じスコープでやり直せる。
- 上限を超えたときの応答は次のとおりである。
  - 改名: `409 { error: "version_conflict", message }`。
    - `message` は SC-09 がそのまま出す再送の促しである: 「他の変更と重なったため、改名しませんでした。もう一度改名してください。」
    - 改名も再発行も確定していない。未処理の範囲は要求の全体であり、同じ要求の再送で再開できる。
  - 再発行: `409 { error: "version_conflict", resumeCursor }`。
    - `resumeCursor` は負けたページの先頭（＝要求の `cursor`。先頭のページなら null）である。
    - 名前を `nextCursor` にしないのは、200 の `nextCursor` の null が「尽きた」を意味するからである。409 の null は「先頭から」を意味し、同じ名前で別の意味を持たせない。
- 冪等:
  - 改名済みの名前への再送は、同名の重複として拒まない（自分自身は除く。従前どおり）。辞書を変えずに再発行だけを行う。
  - 再発行の重複は、受け手の版の印が吸収する。

### 見積もり（条件 5）

| 項目 | 改名 | 再発行 |
| --- | --- | --- |
| 件数 | タグの使用件数 N（PoC で未計測。SC-09 の使用件数の列で分かる）。上限は全文書 22,564 件（#1762 の実測） | 1 ページ最大 500 件（`MaxLimit`。駆動スクリプトの既定のページは 50） |
| バッチ | 1 回（全体で 1 トランザクション） | 1 ページで 1 トランザクション |
| 1 件の費用 | 文書行の UPDATE（連番）と Outbox の INSERT。発行点が文書ごとに `SaveChangesAsync` を 1 回呼ぶので、約 1〜2 ms の往復が 1 件ごとに要る | 同じ |
| ロック時間（行ロックを確定まで持つ） | N = 1,000 → 約 1〜2 秒、N = 22,564 → 約 25〜45 秒 | 50 件 → 約 0.05〜0.1 秒、500 件 → 約 0.5〜1 秒 |
| 競合の確率 | N とロック時間に比例する。上限まで負ければ 409 で、管理者が再送する | 1 ページの範囲。上限まで負ければ 409 で、スクリプトが再試行する |

- 改名と再発行の所要時間と件数は、構造化ログ（Information）に残す。PoC で実測するためである。
  - `Tag rename republished {Affected} document(s) in {ElapsedMs} ms: tag {TagId}`
  - 表示名・表題は出さない。
- 上限まで負けたときは、Warning を残す。
- **保存を 1 回にまとめる案（#2259 の AI レビュー 🟡 1）**:
  - 発行点が文書ごとに保存するのをやめ、確定の最後に 1 回で保存する案である。Npgsql のバッチで、往復は N 回から N / バッチの大きさ回程度へ減る。
  - 見積もり:
    - N = 1,000 → 約 0.1〜0.3 秒
    - N = 22,564 → 約 3〜6 秒
  - 1b では**採らない**。唯一の発行点（19 経路が通る）の形を変えるからである。いまは保存の後に発行を積み、追跡外の実体では止めている。
  - PoC の実測で N が大きいと分かったときに、R2 と並べて判断する（#2260）。

### 駆動スクリプト

- 409 を特別扱いしない。いまでも 200 以外は失敗として数え、`state.cursor` を進めずに、同じカーソルで間を置いて（指数の後退）再試行する。
- そのため、負けたページの先頭から再開する形が、そのまま成り立つ。
- 連続失敗の上限（既定 3）で止まったら、`--resume` で続ける。
- 口が返す `resumeCursor` は `state.cursor` と同じ値なので、スクリプトは読まない。

## 受け入れ基準

- [x] 改名は 1 回負けても読み直して確定する。やり直した再発行は、勝った側の後の連番と新しい名前を運ぶ。
- [x] 改名は上限まで負けたら、409 と SC-09 が出す文言を返す。改名の再発行は 1 通も出ない。
- [ ] 実 PostgreSQL で、上限まで負けた改名は辞書の名前ごと巻き戻る。同じ要求の再送で確定する（`Knowledge.IntegrationTests` の `DocumentBatchCommitRetryTests`）。**根拠: Integration run 40210322433 待ち**（dispatch はコーディネーター）。
- [x] 改名済みの名前への再送は、辞書を変えずに再発行だけを行う（冪等）。
- [x] 再発行は 1 回負けても読み直して確定する。上限まで負けたら、負けたページの先頭のカーソルを返す。そこからの再開で、そのページを発行する（単体）。
- [ ] 同じことを実 PostgreSQL で確かめる（`DocumentBatchCommitRetryTests`）。**根拠: Integration run 40210322433 待ち**。
- [x] SC-09 は、改名の 409 の `message` を既存の経路で出す。
  - `apiClient` が本文の `message` を `details` に入れる。
  - 画面はそれを出し、使用件数の 409 と取り違えない。
  - フロントの試験は CI の frontend-tests で走る。手元は空き容量の都合で依存を入れず、Prettier だけを当てた。
- [x] 変異で赤になる。
  - 上限を 1 にする（やり直さない）→ 4 件が赤。
  - 改名の競合の catch を外す → 2 件が赤。
  - 再発行の `resumeCursor` を null にする → 1 件が赤。
- 試験の器: `DocumentRace` に、文書行を書く保存の直前に窓を開ける形（`AtSave`）を足した。
  - 改名は確定の関数の中で対象を読む。確定の口の手前で窓を開けても読み直しで追い付いてしまい、負けない（最初の版の試験はこれで空振りしていた。上限まで負ける試験が 1 回しか発火しないことで気付いた）。

## 残余

- 使用件数が大きいタグでは、ロック時間が N に比例する。PoC の SC-09 の使用件数で N が大きいと分かれば、R2（バッチ化）か保存の集約へ移す（#2260）。
- **改名の経路の HTTP の期限（#2261 の AI レビュー 🟡 2。実コードで引いた）**:

  | 区間 | 期限 | 根拠 |
  | --- | --- | --- |
  | SPA → BFF（`fetch`） | 無し | `src/platform/frontend/src/lib/api/apiClient.ts` の `fetch(...)` は signal を渡さない |
  | 入口（Traefik） | 応答の期限は無し | リポジトリの配備物（`deploy/local/edge/traefik-entrypoint.yaml`・`platform-frontend-ingress.yaml`）に期限の設定が無く、Traefik の既定に従う。既定はバックエンドの応答ヘッダーの待ちと書き込みが無制限（上流の既定で、ここでは確かめていない）。稼働のクラスタの値は見ていない（触らない） |
  | BFF → DocumentService（名前つきの `HttpClient` `DocumentService`） | **100 秒**（`HttpClient.Timeout` の既定） | `src/platform/backend/Bff/Platform.Bff/Program.cs:173` は `Timeout` を設定せず、BFF に resilience handler・`ConfigureHttpClientDefaults` も無い |
  | DocumentService の要求 | 無し | `AddRequestTimeouts` は無い |
  | DB の命令 | 1 命令ごとに 30 秒（Npgsql の既定） | 改名の命令は 1 件ごとの UPDATE・INSERT で短い。トランザクション全体の期限は無い |

  - 結論: **見積もり（N = 22,564 で約 25〜45 秒）は、いちばん短い期限（BFF → DocumentService の 100 秒）に当たらない**（余裕は約 2.2 倍）。
  - 見積もりは実測ではない。2.2 倍を超えて外れれば当たる。当たったときの振る舞い:
    - BFF の要求が取り消される。
    - DocumentService の要求の取り消し（`ct`）が確定を止め、トランザクションは巻き戻る。
    - 管理者には失敗が返り、何も確定していない。再送は同じ長さになる。
  - そのため、PoC で確かめる手当て（改名のログの `ElapsedMs` が 100 秒の半分を超えたら R2 へ移す）を #2260 に追記した。
- 1c の 8 経路（#2258）は、まだ 409 へ写していない。
- 受け手の連番の比較は段 2 である。
