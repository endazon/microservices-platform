## 実行主体とタイミング（決定 4 を実装側で決める）

**利用者リクエスト時に、その利用者のスコープで生成する。** 定期バッチは採らない。

- **不変条件「1 実行 = 1 利用者のスコープ」を、構造で満たせるのはこちらである** —— 要求の `HttpContext` から
  解決したスコープが、その実行の唯一のスコープになる。バッチだと「誰のスコープで走っているか」が
  実行時の変数になり、取り違えがテストに現れにくい
- **ADR-0051 決定 4 後段の「生成結果の失効条件」を新たに定める必要が無い** —— 提示は既存の一覧
  （`GET /graph/suggestions`）が**その時点のスコープで再判定**しており、属性変更後も決定 2 が破れない
- **ADR-0034 決定 9（MCP サービスアカウント）は支配規則にならない**（ADR-0051 §実行主体は既に決まっていた）。
  本口は認証済み利用者の要求としてのみ動く

## 🔴 スコープ述語をどの段で適用するか（本 issue の核心）

**候補列挙の段で適用する。LLM へ渡してから捨てる形にしない。**

```
[1] 起点文書        FindNode → AuthorizedNode.Authorize（不可なら 404。存在秘匿）
[2] 類似度          ISimilarityCandidateSource（★全文書横断でよい。ADR-0051 決定 1）
[3] 候補列挙 ★      IGraphStore.EnumerateAuthorizedCandidatesAsync(scope, …)
                      → 返り値は IReadOnlyList<AuthorizedNode> のみ
                      → 却下済み・既存辺・既存提案・自己をこの段で除外
[4] 送信物の封       SuggestionPrompt.Seal(origin, candidates, scope)  ← 述語を再適用（多層防御）
[5] LLM             ISuggestionLlmClient.ProposeAsync(SuggestionPrompt)
[6] 取り込み        許可済み候補集合に無い対象は捨てる（幻覚対策）→ pending で永続
```

**[3] と [5] の間に非許可ノードが入る経路を型で塞ぐ。** `SuggestionPrompt` は private コンストラクタを持ち、
構築経路は `Seal` ただ 1 つで、`Seal` は `AuthorizedNode` と `AccessScopeResponse` の両方を要求する。
`ISuggestionLlmClient` は `SuggestionPrompt` しか受け取らない。**結果として「生の GraphDocument を LLM へ渡す」
コードがコンパイルできない。** これは本サービスが既に採っている型ゲート（`AuthorizedNode` / `AuthorizedGraphView.Seal`。
IADR-0242 決定 2）と同じ手であり、新しい発明ではない。

### 🔴 SQL 述語ではないことを、ごまかさずに書く

**ABAC 述語は SQL へ押し込めない。** `graph_documents.attributes` は値変換（`jsonb` ↔ `Dictionary<string,string>`）で
持っており、`AbacNodeFilter.Matches` の「キー欠落は不一致・値集合内 OR・フィルタ間 AND」を EF が翻訳できない
（テストの InMemory プロバイダでも本番の Npgsql でも同じ制約である）。

**そこで「候補列挙の段」とは、次の 2 つを 1 つのメソッドの中で終わらせることを指す。**

1. **SQL で絞れるもの**（候補 ID 集合・自己・却下済みの組み合わせ・既存辺・既存提案）は `IQueryable` の
   `Where` に置き、**DB から出さない**
2. **ABAC 述語**は同じメソッドの中で、**返す前に**適用する。メソッドの返り値の型が `AuthorizedNode` なので、
   **非許可ノードが呼び出し側へ出る経路が無い**

**「LLM へ渡してから捨てる」形との差は、後段のフィルタの有無ではなく、非許可ノードを持つ値が
LLM 呼び出しの引数として存在し得るかどうかである。** 本設計では存在し得ない。

## 決定 2（件数も存在も漏らさない）を守るための具体

- 応答は**生成できた提案の配列のみ**。「スコープ外で N 件落とした」「候補が N 件あった」を**返さない**
- 落とした件数を**ログにも出さない**（ADR-0034 決定 1 の具体化「不許可ノードは辺・ノード・件数・**ログ**の
  いずれにも現れない」）
- 起点文書が見えない場合の応答は **404**（403 ではない。「権限が無いだけで存在はする」を漏らす）
- **目標件数に満たないぶんを追加で引き直さない。** ADR-0051 は応答時間の相関を禁じてはいないが、
  「範囲の外に置いた」と明記して実装側へ判断を残している。**追加照会を採らなければ、フィルタで落ちた件数と
  後段の処理量が相関しない。** 費用ゼロで側チャネルを 1 本閉じられるので採る（§7 の記録義務はこれで果たす）

### 変異試験（必須）— 実測した結果

**着手前の見込み（「候補列挙から述語を外せば G-01 が落ちる」）は外れた。** 実測して分かったことを書く。

| 変異 | 内容 | 落ちたテスト |
| --- | --- | --- |
| **A** | 候補列挙の述語を外す（`AuthorizeAll(rows, scope)` → 全許可スコープ） | G-01b・G-07（**2 件**）。**G-01 は落ちない** |
| **B** | 封（`SuggestionPrompt.Seal`）の再適用を外す | **0 件**（列挙の段が生きているため恒等） |
| **A ＋ B** | 両方 | G-01・G-01b・G-04・G-07（**4 件**） |

🔴 **単独の変異では G-01（送信ペイロードの否定形）が落ちない。** 2 段のゲート（列挙の段と封）が
**多層防御**になっているためであり、欠陥ではない。**しかし「G-01 があるから列挙の段が守られている」とは
言えない**ので、**列挙の段には対の否定形（G-01b）を別に置いた。** 2 つのゲートは別々の性質を担保している。

- **G-01b** … 絞りが **LLM 呼び出しより前（列挙の段）**にあること（ADR-0051 決定 3）
- **G-01** … 送信物にスコープ外が入らないこと（ADR-0034 決定 5）。**両方のゲートが同時に壊れたときに落ちる**

**変異はすべて元へ戻し、戻した状態で 154 件全緑を再確認した。**

もう 1 つ実測で分かったこと: **`System.Text.Json` は非 ASCII を `\uXXXX` へ逃がすため、生の送信本文に対する
「日本語の表題を含まない」という assert は、逃がされているというだけで無条件に通る。** 否定形テストが
空振りする典型なので、**表題の検査は復号後のプロンプト文字列に対して行い、空振り防止の陽性 assert を
同じテストの中へ置いた**（復号が効いていなければそちらが先に落ちる）。

- G-02 を対に置くことで「常に空を送る」実装が G-01 を通すのを防いでいる
