# 作業仕様書: AI レビュー観点への「記録と文書の追随」追加（#906）

## 起点

- `#906`。`#885` の裁定（trace ブロックの網羅性**検査器**は精度 2.6% で成立しないので足さない。
  `IADR-0235`）の**補助提案**として起票された。検査器ではなく **AI レビューの観点表**へ 1 項足す。
- `IADR-0235` 決定 2 は、この防護を「暗黙の挙動から**宣言された責務**へ格上げする」ことを定めた。

## 🔴 着手前の実測 —— 起票時の前提が 1 つ崩れた

`#906` と `IADR-0235` は **「再発防護は現に機能している —— 同型の追随漏れ 2 件はどちらも AI レビューが
捕捉した」** を前提にしている。**この前提は、母集合を引いて測ると成り立たない。**

### 母集合の引き方

`origin/develop` へ **2026-08-20 以降にマージされた PR 全 63 件**（squash 済み。日付で引いており
恣意的な抽出はしていない）。各 PR の `github-actions[bot]` コメントを全取得し、
**初回レビュー本文**の `🔴` / `🟡` / `🟢` 節の**先頭列の箇条書き**を指摘として数えた
（再レビューは同じ指摘の追跡なので二重計上しない。「（指摘なし）」で始まる行は除外）。

### 🔴 実測 2: 問題は精度ではなく**検出率**である

同じ 63 件について、**新観点が発火する条件**（新規 `.ai-context/` 記録の追加 ＋ `docs/**/*.md` の変更）を
git で数えた。

| 項目 | 実測 |
| --- | ---: |
| 新規記録を足した PR | 50 |
| `docs/**/*.md` を変更した PR | 30 |
| **両方（＝新観点の露出）** | **24 / 63（38%）** |
| 機械的な直積（記録 × 文書）の対数 | **191** |

**直積 191 のうち 116 対は `#872` 1 本**（記録 1 × docs 116）である。
**`#885` が「束ね PR の直積」を偽陽性の主因と特定したのは、この形を指している。**

さらに、**記録単位**に絞って（「その記録が、変更されたどの文書の trace ブロックにも無い」）
マージ後の状態を数えると:

| 項目 | 実測 |
| --- | ---: |
| 引っかかった PR | **13 / 24** |
| 引っかかった記録 | **21** |

**21 件のうち 18 件は diff を個別に開いて確認した**（残り 3 件＝`#929` の 2 件・`#883` の 1 件は推定）。
判定は「文書の**本文**がその記録の作業によって書き換わっているか」で行った。

| 判定 | 件数 | 例 |
| --- | ---: | --- |
| **本物の追随漏れ** | **16** | `#965`（`scopeFilter`→`scopeSelection` の改名を本文へ反映したが `specs:` は未更新）・`#902`（カバレッジ床の置き直しで `TEST_STRATEGY.md` 本文を改稿したが trace ブロックは 1 文字も変わっていない）・`#903` `#923` `#944` `#952` `#964` ほか |
| 無関係（追記不要） | 5 | `#878` の束ねた記録のうち `IADR-0230` / `deploy-manifest-ci` など、変更された 4 文書と関係が無いもの |

**記録単位で見た精度は 16/21 ≒ 76%** である。**`#885` が測った 2.6% は「記録 × 文書」の直積に対する値**であり、
**同じ窓を記録単位で数え直すと桁が違う。**

### 🔴 実測 3: 前提「2 回とも捕まえた」は生存者バイアスである

103 件の指摘のうち、**trace ブロックに触れたものは 4 件だけ**である。
このうち当該クラス（記録と文書の追随漏れ）を実際に捕まえたのは **`#884` の 1 件**にすぎない。

さらに **`#923` では、AI レビューが積極的に誤った**。

> `docs/tech/tech-requirements.md` の trace ブロック更新・…など、**周辺文書の追随は網羅されており抜けは見当たらなかった**

同じ PR で `20260822_issue-882_xunit1051-staged-adoption-harness` が `specs:` に**足されていない**。
**「見当たらなかった」という積極的な安全宣言が、実際には漏れている状態で出された。**

| 指標 | 値 |
| --- | ---: |
| 本物の追随漏れ（マージ後に残存） | **16** |
| うち AI レビューが指摘したもの | **1**（`#884`。指摘後に修正され、マージ後の状態には残っていない） |
| **検出率** | **約 6%** |

🔴 **`#906` / `IADR-0235` が引く「2 件とも捕まえた（n=2, 100%）」は、
「捕まえたから記録に残っている 2 件」を数えたものであり、母集合を引いていない。**
母集合を引くと、**同じ窓の 3 日間だけで 16 件が捕まらずにマージされている。**

## 決定

### 決定 1: 観点を足す —— ただし理由は起票時のものと逆である

**足す。** ただし `IADR-0235` 決定 2 が言う「**機能している防護を宣言へ格上げする**」ではなく、
**「機能していない防護を、機能させにいく」**のが実際の理由である。検出率は約 6% であり、
**現状は防護と呼べる水準にない。**

**足す判断の根拠は費用側にもある。** 増分は `prompt:` の **+3.29%**、実行はレビュー 1 回につき 1 度。
`#885` が検査器を退けた理由（偽陽性が CI を赤くし、赤の常態化を招く）は**ここには当たらない** ——
**レビューは判断であって門ではない。** 指摘が外れても CI は赤くならず、人が読んで捨てられる。

### 🔴 決定 2: これで塞がるとは主張しない。効果は事後に測る

**観点を足せば検出率が上がる、という根拠は無い。** 測ったのは「今の検出率が約 6% であること」までで、
**観点追加後の検出率は測っていない**（実装前に測れるものではない）。

したがって本 PR は**効果を主張しない**。`IADR-0250` に**再測定の手順と母集合の引き方を書き残す**
（同じスクリプトで引き直せる形にする）。**次に同種の判断をするときは、宣言ではなく実測を出すこと。**

### 🔴 決定 3: `#885` の裁定はこの PR で覆さない。別 issue にする

実測 2 は、**`#885` が退けたのは「記録 × 文書の直積」という形であって、
「記録単位」という形は測られていない**ことを示している。同じ窓で **76%** である。

**それでも本 PR では検査器に触れない。** 理由は 3 つ。

1. **射程が違う。** `#906` は観点表への 1 項追加であり、検査器の再設計は `#885` の射程である
2. **記録単位の規則は再現率を落とす。** 「どれか 1 つの文書に載っていれば良し」とするので、
   **5 文書中 3 文書に足すべきところを 1 文書だけ足すと素通りする。** 精度と引き換えに見逃す
3. **`#885` の裁定を、その issue の外で静かに覆さない**

**別 issue として起票した —— `#975`**（実測値・母集合の引き方・再現手順を渡してある）。

### 決定 4: 文面は 1 項に収め、経緯を書かない

`prompt:` は毎 PR 送信されて課金される（同ファイルの注記）。**実測値・経緯・issue 番号を書かない。**
判断に要る情報だけを置く。**機械的な直積で全対を要求しないことを明記する**
（`#885` の 191 対・`#872` の 116 対がその失敗形である）。

## 受け入れ基準

1. レビュー観点 **1.（トレーサビリティ）**の系列へ 1 項が入っている
2. `on:` の起動条件・ジョブ名・必須チェック名が**変わっていない**（差分で確認する）
3. 追加は `prompt:` ブロック内に収まっている。
   🔴 **当初ここへ「増分 500 バイト未満」と書いたが、確定した文面は 665 バイト（`prompt:` 比 +3.29%）で超えた。**
   500 は文面を書く前に置いた見込み値であり、実測ではない。**基準の方を実測へ直した。**
   超えた 1 文は「本文だけが書き換わり trace ブロックが手つかず」という兆候の記述で、
   **実測した 4 例すべてがこの形だった**（`#902` `#903` `#944` `#965`）ため残した。
4. `node scripts/check-reading-budget.js` が緑（本変更が必読予算に影響しないことの確認）
5. 文書検査（`check-doc-links` / `check-trace-blocks` / `check-adr-numbering` ほか）と
   `REQUIRE_REPO_TESTS=1 node scripts/scripts.test.js` が緑

## 検証しないこと（明示）

- 🔴 **観点追加によって検出率が上がることは検証しない。** 実装前には測れない。
  `IADR-0250` に再測定の手順を残すに留める
- **YAML の構文的な妥当性以上のこと**（レビューが実際にどう振る舞うか）は、
  この PR 自身のレビューが 1 サンプルを与えるだけであり、**n=1 を根拠にしない**

## 母集合の引き方（再測定用）

本仕様書の実測はすべて次の手順で再現できる。**次に測るときは同じ手順で引き直すこと。**

1. `gh pr list --state merged --base develop --limit 200 --json number,mergedAt` を
   `mergedAt >= <日付>` で絞る（**日付で引く。恣意的な抽出をしない**）
2. 各 PR の `issues/<n>/comments` から `github-actions[bot]` の本文を全取得する
3. **初回レビュー本文**の `🔴` / `🟡` / `🟢` 節の**先頭列の箇条書き**だけを指摘として数える
   （継続行・`[Fix this →]` 行・「（指摘なし）」で始まる行を除く）
4. 露出は git で数える —— `git show --name-status <squash>` で
   「`.ai-context/{specs,adr}/*.md` の新規追加」と「`docs/**/*.md` の変更」の同居を判定する
5. 追随漏れは**マージ後の状態**で数える（PR 中に直ったものは残らない。
   **直ったものを漏れに数えると防護の効果を過小評価する**）

🔴 **3 の「初回レビューのみ」は意図的である。** 再レビューは同じ指摘の追跡なので、
数えると 1 件の指摘が最大 9 回計上される（`#878` は再レビュー 9 回）。
