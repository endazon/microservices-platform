# 作業仕様書 — static-checks を build-and-test の律速から外す（#1910）

## 目的と射程

[[IADR-0505]] は `static-checks` を必須 check の集約 `build-and-test` の `needs` に入れた（2026-10-07）。根拠は
「所要 65〜80 秒で、直近 16 本のすべてで `build-and-test` の開始より前（最小 28 秒前）に終わる」だった。
10/9 以降は所要が 117〜149 秒に伸び、PR の律速になっている（下の実測）。本作業は**門の意味（`static-checks` の
赤で `build-and-test` が赤）を保ったまま**、`static-checks` を律速から外す（利用者裁定 2026-10-12）。

**射程外**（並行作業の領域）: `scripts/check-ci-latency.js`・`ci-latency-watch.yml`・[[IADR-0232]]・[[IADR-0241]]
（作業仕様書 `20261012_1910_ci-latency-self-floor`。#1912 で着地済み）。

## 受け入れ基準

1. `static-checks` の所要を、`build-and-test` の他の `needs`（ビルドの行列）の終了より前に収まる長さへ戻す。
2. 門の意味を変えない。`static-checks` は `build-and-test` の `needs` に残し、検査は 1 本も減らさない。
3. 必須 check 名・ジョブ ID を変えない（ブランチ保護に触れない）。
4. `docs/ai-workflow.md` の必須 check 表の `static-checks` 行と trace ブロック、IADR-0505（日付つき追記）、
   `ci.yml` の `build-and-test` のコメントを実態に合わせる。
5. PR の CI で `static-checks` の終了と `build-and-test` の開始を実測し、直近の PR と比べる。

### 原因

`k8s-local-up.test.js` の時間のほぼすべては、PATH のスタブの下で `bash scripts/k8s-local-up.sh` を走らせる回数である。
`spawnSync` を計測した（ローカル 4 コア・同時実行なし）:

| | `k8s-local-up.sh` の実行回数 | 試験数 | 全体に占める割合 |
| --- | --- | --- | --- |
| `6d97eaff`（10/8） | 175 | 263 | —（同時実行ありで計測したため割合は採らない） |
| `c4f511d3`（現行） | 251 | 316 | 97%（全体 186.5 秒のうち 181.7 秒。1 回平均 0.73 秒） |

10/8〜10/10（JST）に `k8s-local-up.test.js` / `k8s-local-up.sh` を触った 14 コミット（`git log -- <2 ファイル>`。#1803・#1826・#1827・#1833・#1836・#1852・#1856・#1860・#1864・#1865・#1866・#1869・#1884・#1893）の多くが、
それぞれ k8s-local-up.sh の新しい門とその試験（runUp の呼び出し）を足した。呼び出し箇所は 137 → 186、実行回数は 175 → 251（+43%）、
スクリプトは 1394 → 1646 行（1 回あたりの実行も約 1 割重い）。**特定の 1 コミットの退行ではなく、試験の正当な積み増し**である。
一方、試験は `ok()` の中の同期の `spawnSync` で 1 本ずつ回るため、ランナーの 4 vCPU のうち 1 つしか使っていなかった。

## 選択肢

| | (a) 段を別の並列ジョブへ出す | (b) 試験の中を並列化する（**採用**） | (c) 段を `static-checks` から外し門の外に置く |
| --- | --- | --- | --- |
| 効果 | 新ジョブ自体が 約 7 秒（checkout・setup-node）＋ 約 110 秒 ＝ 約 117 秒。`needs` に入れると最小 113 秒の他の needs をなお上回り得て、律速の持ち主が替わるだけ | 段が 約 110 秒 → 約 35 秒（ランナー 4 vCPU）。`static-checks` は 約 65 秒 | 律速から確実に外れる |
| 門の意味 | `needs` に入れれば保てる（効果は小さい）。入れなければ k8s-local-up の試験が門の外へ出る | そのまま（ジョブ・ステップ・コマンドは不変） | 門の外へ出る（IADR-0505 の穴を再び開ける） |
| 必須 check・ブランチ保護 | ジョブが増える。`needs`・判定ステップ・表・面 D の突合を足す | 変わらない | 変わらない |
| 将来の積み増し | 新ジョブで同じ伸びが再発する | コア数で割られる。ローカルの実行も速くなる | — |

(b) を採る。実行の 97% が互いに独立な `bash` の実行で（作業ディレクトリは毎回 `mkdtemp`、リポジトリへは書かない）、
並列化の効きが最も大きく、門・ジョブ・必須 check のどれにも触れない。(a) は単独では律速を解かない。(c) は IADR-0505 の目的に反する。

## 設計

- `node scripts/k8s-local-up.test.js` の起動は変えない。親プロセスは自分自身を `K8S_UP_TEST_SHARD=<i>/<n>` で n 本起動し、
  各子は `ok()` の通し番号が i（mod n）の試験だけを実行する。n は `os.availableParallelism()`（上限 8）。
  `K8S_UP_TEST_SHARDS=1` で従来の直列実行。
- 親は「全子 exit 0」かつ「各子の実行数の和 ＝ 試験の総数」を確かめ、崩れたら赤（取りこぼし・二重計上を黙って緑にしない）。
- 名前が「前提」で始まる試験は全子で実行する（計上は担当の子だけ）。ハーネスや実物の宣言が壊れたとき、
  無関係な試験より先にそこで落ちる、という既存の配置の意図を子ごとに保つ。
- トップレベルで `runUp` を呼んで複数の試験が共有する結果（`EDGE_FRESH` ほか 8 件）は、最初に読まれたときに作る（`lazyRunUp`）。
  担当の試験が無い子で余計な実行をしない。`DEFAULT` は前提の試験が読むので即時のまま。

## 検証

- `node scripts/k8s-local-up.test.js`（並列）と `K8S_UP_TEST_SHARDS=1`（直列）で、`ok` の行の集合が一致する（316 件）。
- 失敗の伝播: 失敗する試験を 1 件差し込んだ写しで、親が exit 1・失敗した子を名指しする。`K8S_UP_TEST_SHARD=4/4` は形の誤りで落ちる。
- node の検査一式（`scripts.test.js`・`scripts.repo.test.js`・`check-trace-blocks`・`check-commit-messages` ほか）。
- PR の CI の実測（下の「結果」）。
