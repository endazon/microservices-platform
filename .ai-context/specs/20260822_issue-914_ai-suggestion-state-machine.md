# 仕様書: AI 提案の永続と 3 状態遷移（#914 / 親 #450）

> 本書は**着手前**に作成した。

## 起点となる計画書（トレーサビリティ）

- 機能要求（FR）: **FR-18**（AI 提案。**一括承認の手段は提供しない**）
- 画面（SC）: **SC-21**（一覧・従）/ **SC-03**（承認の主導線）
- 関連 ADR: **ADR-0033 決定 7・9・10**

## 原文から拾った要求（planning を実測）

| # | 要求 | 出典 |
| --- | --- | --- |
| 1 | 状態は **pending / approved / rejected** の 3 値 | 決定 7 |
| 2 | `pending` は承認 UI にのみ現れ、**探索結果に含めない** | 決定 7 の具体化 |
| 3 | `approved` は**確定リンクとして探索結果に含める** | 同上 |
| 4 | `rejected` は探索結果に含めず、**再提示の抑止に用いる**（以後の提案生成で候補から除外） | 同上 |

| 7 | 🔴 **解除は削除ではなく「無効化」として記録する。**「いつ却下し、いつ何によって解除されたか」を追える | 決定 10 の具体化 |
| 8 | 🔴 **却下レコードに却下回数を保持する**（しきい値を後から入れられるように） | §結果 フォローアップ |
| 9 | 却下レコードは**本文を持たない**（両端 ID・却下日時・解除状態のみ） | §結果 トレードオフ |
| 10 | **一括承認の手段を提供しない** | FR-18 / SC-21「描いてはいけないもの」 |
| 11 | タグ提案は **SC-09 のタグ辞書に整合する値のみ** | SC-21 |
| 12 | リンク提案とタグ提案は**同一の一覧**（画面を分けない） | SC-21 |

## 🔴 いちばん重要な設計上の事実 — 却下解除は「発火」できない

### 不変条件 2・3・4 は**構造的に**満たされている（新しい仕組みが要らない）

`EdgeProvenance` は既に 3 値で、**`ai-approved` だけが辺になる**（#908 の時点でそう作ってある）。

```csharp
// AI 提案のうち人間が承認したもの（#914）。**未承認は辺にならない。**
public const string AiApproved = "ai-approved";
```

つまり **`pending` / `rejected` の提案は辺を持たない**ので、探索が provenance で絞る必要は無い。**絞る対象が存在しない**のが正しい形である。テストで固定する（S-05）。

### しかし要求 6（本文変更で却下解除）は、**発火する経路が存在しない**

| 実測 | 結果 |
| --- | --- |
| GraphService に消費者（`IConsumer` / handler） | 🔴 **0 件** |
| `GraphDocument.Create` / `TryApply` の本番からの呼び出し元 | 🔴 **0 件**（テストのみ） |
| #911（`DocumentUpdated` 購読） | **保留中**（Wolverine チェーン待ち） |

さらに、**仮に #911 が配線されても、イベントだけでは「本文が変更されたこと」を判定できない**。

```csharp
public record DocumentUpdated(
    Guid DocumentId, string Title, string Status, string? MarkdownUri,
    Dictionary<string, string> Attributes, List<string> Tags, DateTimeOffset UpdatedAt);
```

- **本文ハッシュを持たない**
- `UpdatedAt` は**タグ・属性・状態だけの更新でも動く**。これを使うと、決定 10 が「本文が変更されたこと**のみ**」と限定した条件より**広く**解除が起きる
- `MarkdownUri` が内容で変わるかは未確認（オブジェクトストレージのキー生成が本番経路で追えなかった）

**この不足は #911 と planning へ送る（下記 §未決事項）。本書では判定ロジックを「本文指紋（fingerprint）を受け取る」形で書き、指紋の供給元を #911 に委ねる。**

### 🔴 「未配線であること」を機械で固定する

**散文で「未配線」と書くだけでは足りない。書いた本人以外は読まない。**

そこで、**却下解除の判定メソッドに本番コードからの呼び出し元が存在しないことを assert するテスト**を置く。

- **#911 が配線した瞬間に落ちる。** 落ちたら実装者は「未配線という前提が変わった」ことを強制的に認識し、受け入れ基準を書き直すことになる
- 失敗メッセージに**次に何をすべきか**を書く（テストを消し、発火の受け入れ基準を #914 の本文から起こす）
- これは #920 の「**意図した不検出を、意図として固定する**」と同型である。欠陥と読まれることも、誰かが「ついでに」塞いで偽陽性を招くことも防ぐ

## 対象範囲

### 対象

- `ai_suggestions` テーブル（初回マイグレーションには含めず**ここで足す**。`Migrations/` はカバレッジ集計から除外＝IADR-0138 なので床は動かない）
- 3 状態遷移のドメインモデル（**不正な遷移を型・メソッドで拒む**）
- 承認 → `EdgeProvenance.AiApproved` の辺を生成（**#913 と同じ到達可能性の検証**を通す）
- 却下 → 却下回数を増やし、両端の指紋を保存
- **却下解除の判定ロジック**（指紋の比較 → `pending` へ戻し、解除理由を記録）
- **一括承認の口を作らない**ことをテストで固定
- 未配線であることの機械的固定

### 対象外

- **却下解除の発火**（#911）
- 提案の**生成**（#915。実行主体の裁定待ち）
- BFF 公開・SC-21 の画面（#918）
- タグ提案の値域検査の**実装**は入れるが、タグ辞書との突合は DocumentService 側の辞書を引く必要があるため、**本 issue では「辞書外の値を受け付けない」ことをサービス層の検証で固定するに留める**

## 受け入れ基準

- [ ] 3 状態（pending / approved / rejected）を持ち、**不正な遷移が拒まれる**
- [ ] 承認で `ai-approved` の辺が生成され、**両端が承認者のスコープで可視でなければ拒む**
- [ ] 却下で**却下回数が増え**、両端の指紋が保存される
- [ ] **解除は削除ではなく無効化として記録**され、「いつ却下し、いつ何によって解除されたか」が追える
- [ ] **本文指紋が変われば `pending` へ戻り、解除理由（どちらの端点が変わったか）が付く**（🔴 **呼び出し側は #911**。本 issue では発火しない）
- [ ] **一括承認のエンドポイントが存在しない**ことをテストで固定
- [ ] `pending` / `rejected` の提案が**探索応答の辺に一切現れない**
- [ ] 🔴 **却下解除の判定メソッドに本番からの呼び出し元が無いことを assert するテストがある**

## テスト方針

| ID | 内容 |
| --- | --- |
| S-01 | pending → approved / pending → rejected は通る |
| S-02 | approved → rejected など**不正な遷移は拒まれる** |
| S-03 | 承認で `ai-approved` の辺が 1 本できる |
| S-04 | 承認者から見えない端点があれば拒む（**#913 と同じ判定**。陽性対照つき） |
| S-05 | pending / rejected の提案は**辺を 1 本も作らない**（探索応答に現れない） |
| S-06 | 却下で却下回数が 1 → 2 と増える |
| S-07 | 指紋が変わると pending へ戻り、**解除理由に変わった側の端点**が入る |
| S-08 | 指紋が変わらなければ解除されない（**陽性対照 S-07 の対**） |
| S-09 | 解除後も**却下の履歴が残る**（削除されていない） |
| S-10 | 一括承認の口が**存在しない**（ルート表を走査） |
| S-11 | 🔴 却下解除の判定メソッドに**本番からの呼び出し元が 0 件** |

### 変異試験の設計

| 変異 | 落ちるべき | 🔴 注意 |
| --- | --- | --- |
| **M-1** 解除条件を「常に解除」にする | S-08 | **S-07 だけでは検出できない**（常に解除する実装は S-07 を通す） |
| **M-2** 解除を「レコード削除」にする | S-09 | 要求 7 |
| **M-3** 却下回数を増やさない | S-06 | 要求 8 |
| **M-4** 承認時に到達可能性の検証を外す | S-04 | #913 と同型 |
| **M-5** 承認の状態遷移ガードを外す（pending のまま辺を作る） | **S-03 / 再承認テスト** | 🔴 **当初 S-05 と書いたが誤りだった**（下記） |
| **M-7** **却下**でも辺を作る | **S-05** | S-05 の検出力はこちらで測る |
| **M-6** 判定メソッドを本番から呼ぶ（＝ #911 の配線を模す） | **S-11** | **落ちるのが正しい。** S-11 が落ちなければ、未配線の追跡は効いていない |

**M-6 は他と意味が逆である。** 他の変異は「実装を壊すと落ちる」ことを見るが、M-6 は「**前提が変わったら落ちる**」ことを見る。

### 🔴 M-5 の対応表を実測で訂正した

当初 **M-5 → S-05** と書いたが、**実測では S-05 は落ちなかった**（失敗 2 件はいずれも承認系）。
理由は単純で、**S-05 は approve を一度も呼ばない**からである。承認の口を壊しても、
承認を通らない経路だけを見る S-05 には届かない。

**「対応表に書いたから落ちるはず」で終わらせると、S-05 は検出力を測られないまま残る。**
そこで S-05 に届く変異 **M-7（却下でも辺を作る。「却下も関係の記録だ」という素朴な誤り）** を
別に当て、**S-05 が単独で落ちる**ことを実測した。

- 差異ではないが**不足**: `DocumentUpdated` が本文の変更を判定する手段を持たない（§未決事項 1）

## 🔴 明示的な限定 — 却下履歴は直近 1 周期しか追えない

**この形は設計判断であって、見落としではない。**

決定 10 の具体化は「解除は却下レコードの削除ではなく**無効化**として記録する。『**いつ却下し、いつ何によって解除されたか**』を追えるようにするため」と定める。本書の実装はこれを **1 行（`RejectedAt` / `ReinstatedAt` / `ReinstatedReason`）＋ 累積カウンタ（`RejectedCount`）** で満たす。

| 追えるもの | 追えないもの |
| --- | --- |
| **直近の周期**（いつ却下し、いつ、どちらの端点の変更によって解除されたか） | **過去の周期**（却下 → 解除 → 再却下 で上書きされる） |
| 却下の**累積回数**（何周期あったか） | 各周期の日時・解除理由 |

**そう読んだ根拠は 2 つある。**

1. ADR §結果 が「**1 レコード**は辺の両端 ID・却下日時・解除状態のみであり、本文を持たない」と**単数**で書いている
2. フォローアップが求める観測は「**同一の辺の組み合わせが 3 回以上却下された件数**」であり、**必要なのは回数であって全周期の履歴ではない**

**全周期を追う要求があるなら別表（`ai_suggestion_rejections`）が要る。** 本書の形からは自然に拡張できる（1 行の現在値はそのまま残し、周期ごとの行を足すだけ）。

**この限定は planning へ質問として送る**（SC-10 の観測項目の起票に相乗り）。後から SC-10 が全履歴を要求したときに、**設計判断だったのか見落としだったのかが分かる形**にしておくためである。
