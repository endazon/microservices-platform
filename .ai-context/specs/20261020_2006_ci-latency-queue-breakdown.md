# 仕様書: ci-latency の待ち時間を分解する（#2006）

> 本仕様書は実装着手前に作成した（着手 2026-10-20）。実装の基点は MSP `origin/develop` `7e5ea7ba`。判断は IADR-0232 決定 8 の 2026-10-20 追記（新しい IADR は起こさない。同じ監視の出力の改修であり、判定は変えないため）。

## 起点

- #2006（#1999 の調査コメント 6291108835 の提案）。計画 ID: NFR（メタ作業）。
- 関連 IADR: IADR-0232 決定 8（ci-latency の監視）・IADR-0241（epoch）。

## 要件

- 窓ごとに「実行の経路」と「キュー待ち」の中央値を並べる。
- 増えた分の大半がキュー側にあるときは「次の手」を「ランナーの混雑（同時間帯の run 数）を確認する」へ切り替える。構成の退行が主因なら従来の文言のまま。
- 閾値（R＝1.25）・判定は変えない。

## 方法

- `needs:` の木は構成ファイル（`CI_LATENCY_CONFIG_PATH`、既定 `.github/workflows/ci.yml`）から読む（`jobs:` 直下のジョブ ID・`name:`・`needs:` のスカラー／`[…]`／行の列）。
  check-run の名前はジョブの `name:`（`${{ … }}` を含めばその手前までの前方一致）か、`name:` が無ければジョブ ID。一致が 1 つでなければ引けない扱い。
- 1 PR の分解: 監視対象の check-run から、`needs:` に載るジョブの check-run のうち最後に完了したものを前段として遡る。
  キュー＝Σ（段の開始 − 前段の完了）＋（先頭の開始 − 群の開始）、実行＝Σ（段の所要）。和は待ち時間に等しい。
- 主因: 床の窓（`FLOOR_MIN_SAMPLES` 本以上の過去の窓のうち中央値が最小）と比べ、Δキュー > 0 かつ Δキュー > max(Δ実行, 0) ならキュー。Δ実行 > 0 なら実行。それ以外は決められない（従来の文言）。

## 範囲外・限界

- 過去の head の分解には現行の ci.yml の `needs:` を使う。構成が大きく違う head は引けず、分解できた本数に現れる。
- 混雑の原因（同時間帯の run 数）は自動では引かない（文言で案内するだけ）。
