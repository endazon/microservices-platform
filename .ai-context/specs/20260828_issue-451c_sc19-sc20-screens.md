## 設計

### 判断 1: ルートと URL（`IADR-0124` の作法）

| 画面 | ルート | 検索パラメータ（URL が単一情報源） |
| --- | --- | --- |
| 個人資料管理 | `/my/notes` | `tab`: `active`（既定）/ `trash`、`q`: タイトルの部分一致 |
| Obsidian 連携設定 | `/my/obsidian` | なし |

計画が `/my/notes?tab=trash` を明示しているので、**タブは URL に持つ**。未知の値は既定へ倒す
（選択肢しか無い UI に「エラー状態」を持ち込まない。SC-18 / SC-21 と同じ作法）。
左ナビのグループは **`personal`**（計画 §共通シェル。「個人」グループの最初の 2 項目）。

### 判断 2: 一覧は 1 本の問い合わせで、タブは絞りにすぎない

`GET /bff/private-notes` は**削除済みも含む全件と容量**を 1 応答で返す（契約のコメントが明記）。
したがって **タブごとに問い合わせを分けない**。削除済みの件数バッジも、容量の内訳
「うち削除済み」も、**同じ応答から画面が数える**（契約が「数え方を 2 つ持たない」と決めている）。

### 判断 3: 確認ダイアログは feature の外・`@platform/ui` の中でもない場所に置く

計画は SC-19 / SC-20 の両方に確認ダイアログを要求する。**`@platform/ui` に `Dialog` は無く**、
その移植は #452 の射程である（`src/packages/ui/README.md` §未了）。本作業でそこへ入れると、
**別の作業単位の射程を黙って動かす**ことになる。一方で 2 画面が同じ部品を要るので、
片方の feature に置いて他方から引くこともできない（feature の公開面は index のみ。`IADR-0262`）。

**よって `src/knowledge/frontend/src/components/ConfirmDialog.tsx` に置く**（既に `DataTable` /
`EChart` が居る、ユニット内の共有部品の置き場である）。**文言は持たない**（`IADR-0125` 決定 1 と
同じ規律）。`role="dialog"` ＋ `aria-modal` ＋ 見出しへの `aria-labelledby` を持ち、
**Escape で閉じる**。`@platform/ui` へ昇格するかは #452 が決める。

### 判断 4: 🔴 削除の文言に但し書きを添える（`ADR-0057` 決定 4 の選択）

計画は完全削除の確認に「この操作は元に戻せません。削除後はいかなる方法でも復元できません」を
求めるが、**2026-08-23 の追加で「この文言が事実になるのは、削除が本文の実体と索引まで及ぶように
なってから」**と条件が付いた。実測（本リポジトリの記録）では **①オブジェクトストレージの実体削除は
未実装**である（②索引・グラフの掃除は入った）。決定 4 は**実装側が選ぶ**として
「文言を出さない」か「但し書きを添える」の 2 択を与えている。

**但し書きを採る。** 文言を出さない側にすると、**利用者が「復元できる」と誤解する**危険が残り、
取り返しのつかない操作の手前で最も重要な警告が消える。**警告は残し、正確さを但し書きで補う**：

> この操作は元に戻せません。削除後はいかなる方法でも復元できません。
> （**削除の反映には時間がかかる場合があります。**）

**「配備後に消える」とだけ書いて現在の状態を伏せない**（計画 §統制の記述規則）。

### 判断 5: 容量の段階警告は「跨いだ段」を 1 つだけ出す

`percent` で 3 段（80 / 95 / 100）に分ける。**同時に 2 本出さない** ——
95% のときに 80% の予告も並べると、強い警告が弱い警告に埋もれる。

| 使用率 | 表示 | 新規作成 |
| --- | --- | --- |
| < 80% | 使用量のみ（`0.42 / 1.00 GB（うち削除済み 0.00 GB）`） | 可 |
| 80% 以上 95% 未満 | 予告（`info` の注記） | 可 |
| 95% 以上 100% 未満 | 警告色（`warning`） | 可 |
| 100% | 警告色（`danger`）＋ **計画の固定文言 2 段落** | **不可**（入力とボタンを無効化し、理由を示す） |

### 判断 6: 端末の状態は 4 値へ落とし、色だけに意味を持たせない

`SyncDeviceDto` は `revoked` / `expiresAt` / `active` を持つ。計画の 4 状態への写像は次とする。

| 条件 | 表示（`StatusBadge` の tone ＋ アイコン ＋ テキスト） | 行内の導線 |
| --- | --- | --- |
| `revoked` | `neutral`「失効済み」 | なし |
| 期限切れ（`expiresAt <= now`） | `danger`「期限切れ（同期は停止しています）」 | **再発行** |
| 残り 7 日以内 | `warning`「期限切れ間近（残り N 日）」 | 再発行 |
| それ以外 | `success`「有効（残り N 日）」 | 個別失効 |

**失効済みと期限切れを同じ見え方にしない**（計画が「同じ列で連続的に見せると停止に気づかない」と
明記）。個別失効は**期限切れ以外の全行**に置く（紛失時の唯一の防御線であるため、
状態を理由に隠さない）。

### 判断 7: 平文トークンは 1 回だけ・画面の状態にも残さない

`token` が載るのは発行／再発行の応答だけである。画面はそれを**その場の状態**として持ち、
**別の操作を始めた時点で捨てる**（一覧の再取得でも消える）。ダウンロード・コピー履歴・
`localStorage` へは一切書かない。「再表示できない（再発行のみ可）」旨を**同じ枠の中に**書く。

## テスト方針

- 置き場所は各 feature の `components/*.test.tsx`（既存の慣行）。**新規のテスト基盤は作らない。**
- ハーネスは `renderUnitRoute`（`@foundation/testing`）。**ロケールは ja 固定**（横断 setup）。
- モックは **`apiRequest`** に当てる（`IADR-0135` 決定 4。生成コードは `bffFetch` → `apiRequest`）。
- 🔴 **否定形（管理者導線が無い・本文編集欄が無い・平文が一覧に出ない・承認ステップが無い）は
  必ず陽性対照と対で置く。** 何も描かない実装でも否定形だけなら緑になる。
