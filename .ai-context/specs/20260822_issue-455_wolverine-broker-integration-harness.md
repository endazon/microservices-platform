## 🔴 本 PR が塞ぐリスク

デュアルスタック期間（E1〜E3b）は **1 プロセスに MassTransit バスと Wolverine ホストが同居する**。
このとき最も危険な失敗は「**publish が黙ってプロセス内へ閉じ、外部購読者へ出て行かない**」形である。
これは起動もビルドも封じ込め検査もトポロジ検査も通り、**実行時に無音で壊れる**。

したがって本 PR の器は「メッセージが届いた」を見るだけでは不足である。
**ブローカを経由せずローカル配送になった形を、確実に落とす**ことが要件である。

## 決定

### 決定 1: 新規テストプロジェクトを作らず `Knowledge.IntegrationTests` へ相乗りする

根拠は coverage 床である。床は `line 38 / branch 27` で**余裕 0.49pt**しかなく、
テストプロジェクトを 1 つ増やすとレポート跨ぎの二重計上で割れる（#899 の実記録）。
割れた床の置き直しには `integration.yml` の実測が要り、`workflow_dispatch` の API 起動は 403 のため
**人間による Web UI からの手動実行が 1 回**必要になる。この人手は #900 で既に 1 回使う予定であり、
増やさない。

🔴 **［2026-08-22 追記 / rebase 後の訂正］この根拠は作業中に弱くなった。**
本 PR の作業中に #900（[IADR-0236](../adr/IADR-0236_coverage-cross-report-line-dedup.md)）が
develop へ着地し、**カバレッジ集計はレポートを跨いで行を重複排除するようになった**。
上で「割れる」と述べた機構（共有ライブラリの行が参照プロジェクト数だけ分母へ多重計上される）は
**塞がれた**ため、新規テストプロジェクトが床を割るとは限らなくなった。

ただし相乗りの結論は変えない。理由が入れ替わっただけである。
- `scripts.repo.test.js` の 16 件 ratchet を動かさずに済む
- レポートが 1 件も増えないため、床の再測定そのものが不要である
- #900 と `src/coverage-floor.json` で衝突しない

**新しい余裕は測っていない。** 床の置き直しは #900 の射程であり、CI 実測を要する。
本 PR は床に 1 文字も触れないため、測る必要が無い。

**相乗りが床を動かさないことは実測で確かめた**（推論ではない）:

- coverlet は**テストアセンブリ自身を計装しない**。`IncludeTestAssembly` は runsettings の
  opt-in であり、本リポジトリに `.runsettings` は存在せず、`Directory.Build.props` にも
  coverlet の設定は 1 つも無い（走査済み・0 件）。
- 裏付けとなる実測は `coverage-floor.json` に既にある。#897 で `Platform.Shared.Infrastructure.Tests`
  （テストコード実数 227 行・ほぼ全行が実行される）を足したときの CI 差分は
  **分母 +949 行・分子 +9** であった。テストアセンブリが計装されていれば分子は約 100 行増える。
- レポート件数は「テストプロジェクト 1 つ ＝ レポート 1 つ」であり、既存プロジェクトへ
  ファイルを足しても 16 件のまま動かない。

⚠️ **ただし条件が 1 つある。`Knowledge.IntegrationTests.csproj` へ新しい `<ProjectReference>` を
足さないこと。** 足すとそのプロジェクトの行がこのレポートの分母へ複製され、#899 と同じ機構で
床が動く。本 PR の器は**素の Wolverine ホストだけ**を立てるため、新規のプロジェクト参照を必要としない。

### 決定 2: 試験を 2 系統に分ける（fan-out と、ローカル配送の検出）

🔴 **［2026-08-22 訂正］当初ここには「3 ホスト構成の囮 assert 1 つで M3 も落ちる」と書いていた。
実測すると落ちなかった。** 想定していた (a) ローカル優先・(b) 両方へ配る のどちらでもなく、
**(c) 明示ルーティングが規約ローカルルーティングより優先され、手順 4 の有無が挙動に出ない**
が正しかった。よって系統を 2 つに分ける（根拠は [IADR-0237](../adr/IADR-0237_broker-integration-harness-detection-power.md) 決定 2）。

**系統 1: fan-out（3 ホスト・exchange への明示ルーティング）** —— M1・M2・M4 を検出する。

| ホスト | ハンドラ | リスニング | 役割 |
| --- | --- | --- | --- |
| 発行側 | 囮（同一イベント型） | **無し** | 多重配送が起きたら気付く |
| 購読 A | `ingestion-service` 役 | `<service>-<runId>.<Event>` | fan-out の片側 |
| 購読 B | `wiki-service` 役 | `<service>-<runId>.<Event>` | fan-out のもう片側 |

**系統 2: ローカル配送の検出（1 ホスト・明示ルーティングを持たない）** —— M3 を検出する。
この形でのみ手順 4 の破れが観測できる。**必ず 2 本 1 組**で置く。

| 構成 | 期待 | 意味 |
| --- | --- | --- |
| 共通既定を当てない | 囮が**受信する** | ローカル配送が実在し囮が生きている（陽性対照） |
| 共通既定を当てる | 囮は**受信しない** | 手順 4 が効いている（本体） |

陽性対照が無いと、囮が壊れて発火しなくなっても「受信 0 件」で緑になる。

### 決定 3: ブローカの提供元を 2 経路にし、いずれも fail-closed にする

| 経路 | 供給元 | 使う場面 |
| --- | --- | --- |
| Testcontainers | `RabbitMqBuilder` | CI（`integration.yml`）。**本作業環境では 1 度も走らない** |
| 外部エンドポイント | 環境変数 `PLATFORM_TEST_RABBITMQ` | Docker API が無い環境（本作業環境） |

外部エンドポイントが設定されているのに接続できない場合は**例外にする（skip しない）**。
「設定したのに黙って skip」は、本 PR が塞ごうとしている無音の穴そのものである。

### 決定 4: skip 判定を器の側で分ける

既存の `DockerFactAttribute` は Postgres も要求するテスト群が使っており、判定を緩めると
それらが skip されずに落ちる。よって**器専用の属性を新設**し、
「Docker API が使える **または** 外部ブローカが設定されている」を条件にする。既存の属性は変えない。

### 決定 5: 器の状態を実行ごとに隔離する

🔴 **［2026-08-22 追記］固定キュー名は変異を隠した。** 前回の実行が残した束縛のせいで
M4 が検出できず、変異なしでも「フィルタ実行は緑・全体実行は 60 秒タイムアウト」という
再現性のある食い違いが出た。exchange 名とキューのサービス名へ実行ごとの一意 ID を入れる。
前置の形（`<service>.<event>`）は変えないため手順 3 の証明力は保たれる。
あわせて**束縛とリスニングを同じ 1 つの名前から導く**（IADR-0237 決定 4・5）。

## 変異試験の規律（#897 変異 E の罠を踏まない）

各変異について、**テスト結果を読む前に**次を確認する。

1. **当該箇所のみ**が変化していること。🔴 **未追跡ファイルでは `git diff` が空振りする**
   （実測。最初の M3 で気付かず素通りさせかけた）。pristine コピーとの `diff` で確認する
2. `dotnet build` が **`Build succeeded` / EXIT=0** であること
   （ビルドが落ちる変異は検出力を何も示さない）
3. そのうえで `失敗: N、合格: M` の**件数と名前**を読む（全件落ちたら器が壊れただけ）
4. 復旧後 `cmp` でバイト一致を確認し、`git status` に残骸が無いことを示す

**EXIT はリダイレクトして読む。パイプ先の終了コードを読まない。**

## 実測記録

### ブローカの供給（🔴 ローカルでは Testcontainers 経路を 1 度も走らせていない）

- `docker info` → **EXIT=1**、名前付きパイプ `docker_engine` → **PIPE_EXISTS=False**。
  よって `RabbitMqBuilder` は起動できず、**Testcontainers 経路はローカル未実走**である。
  この経路の検証は CI（`integration.yml`）に委ねる。
- 実走に使ったブローカは **nerdctl（containerd）で起こした `rabbitmq:3.13-alpine`**、
  `PLATFORM_TEST_RABBITMQ=amqp://guest:guest@localhost:5672`。
  Windows から `127.0.0.1:5672` へ到達可能であることを確認済み。
- **テスト本体（発行・購読・fan-out・ローカル配送の検出）は実ブローカ相手にローカルで実走した。**
  差があるのは「ブローカを誰が起こすか」だけである。

### 変異試験（全 4 件が検出された）

| 変異 | 内容 | `dotnet build` | テスト結果 | 落ちたテスト |
| --- | --- | --- | --- | --- |
| M1 | 発行を削る | `BUILD_EXIT=0` | 失敗 1 / 合格 4 | 実ブローカ経由で1回の発行が2購読先へ届き_発行元へは配送されない |
| M2 | 購読 B の登録を外す | `BUILD_EXIT=0` | 失敗 1 / 合格 4 | 同上 |
| M3 | **手順 4 の適用を外す** | `BUILD_EXIT=0` | 失敗 1 / 合格 4 | 共通既定を当てれば発行はプロセス内へ閉じない |
| M4 | 手順 3 の前置を潰す | `BUILD_EXIT=0` | 失敗 1 / 合格 4 | 実ブローカ経由で1回の発行が2購読先へ届き_発行元へは配送されない |

全件、変異箇所のみの差分を pristine との `diff` で確認し、復旧後に `cmp` でバイト一致を確認した。

### 🔴 途中で 2 度、器の誤りが変異試験によって露見した

**(1) 最初の M3 は当たらなかった。** 明示ルーティングを持つ発行ホストから共通既定を外しても、
テストは緑のままだった。**明示ルーティングは規約ローカルルーティングより優先される**ためで、
その構成では手順 4 の有無が挙動に出ない。当初の器は W3 が塞ぐべきリスクを 1 ミリも塞いで
いなかった。明示ルーティングを持たないプローブを足して初めて M3 が当たった。
あわせて**陽性対照**（共通既定を当てなければ囮が受信する）を対で置いた —— 発火し得ない囮の
「受信 0 件」は何も証明しないためである。

**(2) 最初の M4 も当たらなかった。** 原因は 2 つ。束縛とリスニングでキュー名を別々に導いて
いたため変異が束縛側にしか当たらず、さらに**前回の実行が残した束縛**が配送を成立させていた。
同じ問題は変異なしでも出ていた —— 固定キュー名のとき、同一コードで「フィルタ実行は緑・
全体実行は 60 秒タイムアウトで赤」という再現性のある食い違いを 2 回連続で観測した。
exchange とキューのサービス名に実行ごとの一意 ID を入れ、束縛とリスニングを同じ名前から導いた。
修正後は全体実行が **3 回連続で緑・所要 5 秒**（赤のときは 1 分 3 秒＝タイムアウト待ち）。

**器を書いただけでは検出力は未知である。** 両方とも変異で殴って初めて分かった。
