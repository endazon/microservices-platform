# 作業仕様書 — CI の k3d の導入（#2444）

> 本仕様書は実装着手前に作成した（着手 2026-11-06。develop `977ada5a`）。起点は NFR-18。

## 事象

次の 3 つのワークフローが、k3d を `curl -fsSL https://raw.githubusercontent.com/k3d-io/k3d/main/install.sh | TAG="${K3D_VERSION}" bash` で入れている。
- `.github/workflows/e2e-live.yml`（137 行）
- `.github/workflows/integration-stack.yml`（136 行）
- `.github/workflows/cutover-rehearsal.yml`（90 行）

入れる版は `K3D_VERSION` で固定されている。しかし、実行するインストールスクリプトは `main` の先頭から毎回取っており、内容が固定されていない。

## 方式

- k3d のリリースのバイナリ（`k3d-linux-amd64`）を、版の付いた URL（`https://github.com/k3d-io/k3d/releases/download/${K3D_VERSION}/k3d-linux-amd64`）から取る。
- `sha256sum -c` で照合し、合えば `/usr/local/bin/k3d` へ入れる。合わなければ step が赤で止まる（fail-closed）。
- sha256 は、各ワークフローの `env` の `K3D_SHA256` に `K3D_VERSION` と並べて持つ。
- 形は、`ci.yml` の kubeconform・promtool・amtool と同じにする（版・sha256 → `curl -o` → `sha256sum -c -` → `install`）。
- **共通化しない。** 3 か所に同じ手順を書き、版と sha256 が 3 つのワークフローで一致することを試験で固定する。
  - 理由: 各ワークフローは、取得が要る段（k3d）を他の段から独立して読めることを優先している。`ci.yml` の既存の 3 つの導入も、同じく step ごとに書いている。
  - composite action にすると、checkout の前に使えない・パスを揃える必要がある、という制約が増える。それに見合う利点が無い。
- IADR は作らない。IADR-0679（外部の成果物は版に加えて内容の sha256 で固定し、合わなければ止める）の方針を、CI の k3d へ当てるだけで、新しい判断が無いため。

## 版と sha256 の確かめ

- `v5.8.3` の `k3d-linux-amd64` を版の付いた URL から取り、手元で sha256 を計算した: `dbaa79a76ace7f4ca230a1ff41dc7d8a5036a8ad0309e9c54f9bf3836dbe853e`。
- 同じリリースの `checksums.txt`（`_dist/k3d-linux-amd64` の行）と一致した。

## 版の上げ方

1. 新しい版の `k3d-linux-amd64` を版の付いた URL から取り、`sha256sum` で計算する。同じリリースの `checksums.txt` の行と突き合わせる。
2. 3 つのワークフローの `K3D_VERSION` と `K3D_SHA256` を、同じ変更で対で改める。
3. 試験（`scripts.repo.test.js` の #2444 の節）が、3 つの版と sha256 が一致すること・形が崩れていないことを見る。

## 母集合（規則 9。ほかの「照合せずに取って実行する」形）

`.github/workflows/*.yml` の全体を、次の形で走査した。
- `curl|wget … | (sudo) (ba)sh`
- `bash <(curl …)`
- `| python|node|perl|ruby`
- `raw.githubusercontent.com`
- `install.sh`
- `curl -o` / `wget -O` の取得のすべて

| 場所 | 形 | 扱い |
| --- | --- | --- |
| e2e-live.yml・integration-stack.yml・cutover-rehearsal.yml の k3d | `main` の install.sh を照合せずに実行 | **直す**（本件） |
| ci.yml の kubeconform・promtool・amtool | 版つきの取得＋`sha256sum -c` | 既に照合あり |
| cutover-rehearsal.yml の `\| node -e '…'`（3 か所） | 手元の JSON をその場のスクリプトで読む | 対象外（取ったスクリプトを実行していない） |
| integration-stack.yml の `wget -q -T 10 -O /dev/null` | 到達の確かめ | 対象外（取った物を実行しない） |

ワークフローの外（参考。PR 本文に一覧として残す）:
- `scripts/setup.sh` が `https://dot.net/v1/dotnet-install.sh` を取り、照合せずに実行する。SessionStart hook の開発環境の準備で、ワークフローからは呼ばれない。本件の外とする。

## 受け入れ基準と試験

| # | 基準 | 試験 |
| --- | --- | --- |
| AC1 | 3 つのワークフローに、`main` から取ったスクリプトを照合せずに実行する形（`curl … \| bash` など・`raw.githubusercontent.com/…/main/`）が無い | `scripts.repo.test.js` の #2444 の節 |
| AC2 | 3 つのワークフローで、k3d を版の付いたリリースの URL から取り、`sha256sum -c` で照合してから入れる。`K3D_SHA256` は 64 桁の 16 進で、3 つの版と sha256 が一致する | 同上 |
| AC3 | 陰性対照: 現行の形（`main` の install.sh を bash へ流す）を入れる・照合を外す・sha256 を片側だけ変えると赤 | 同上 |
| AC4 | E2E Live と Integration Stack が緑で通る | PR の CI と、必要なら dispatch |
