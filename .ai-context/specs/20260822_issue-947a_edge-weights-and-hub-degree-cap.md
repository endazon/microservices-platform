# 仕様書: 辺の型の重みとハブ文書の次数上限（#947a / 親 #947・#450）

> 本書は**着手前**に作成した。

## 起点となる計画書（トレーサビリティ）

- 機能要求（FR）: **FR-04**（AI 回答と出典）/ **FR-17**（知識グラフ）
- ユースケース（UC）: **UC-10**
- 関連 ADR: **ADR-0035 決定 2**（探索パラメータ）/ ADR-0034 決定 4（表示上限）/ ADR-0033 決定 3

## 対象範囲

二段検索（#970）が使う 2 つの材料を、GraphService の中だけで用意する。**RetrievalService には触らない。**

### 対象

1. **辺の型ごとの重み**（`edge_types` に列を足す）
2. **ハブ文書の次数上限**（`GraphTraversal`。超える文書は**展開の中継点にしない**）

### 対象外

- 重みを**使う**再ランク（#970）
- `IVectorStore` の文書 ID 制約（#969）
- 重みの編集 UI / API（SC-09 の射程。planning が求めていない）

## 🔴 計画が実装へ委ねている領域である（委譲の根拠を明示する）

**「計画に書かれていないから実装で決めた」ではない。「計画が実装へ委ねているから実装で決めた」である。** その根拠を原文で示す。

### 次数上限

ADR-0035 §結果 フォローアップ:

> **ハブ文書の次数上限の具体値を実装側で決める（実データの次数分布を見て定める）。**

**明示的な委譲である。** 決定の場は実装側であり、planning へ送り返すのは誤りである。

### 重み

ADR-0035 決定 2:

> 辺の型による重み付け ｜ **型ごとに重みを持たせる。`supersedes` は最新版へ強く誘導し、`related` は弱く扱う**

**方向は計画が決め、具体値は決めていない。** ADR-0035 決定 4 が「選定の判断材料は…**実装リポジトリでしか測れない**」として実装側へ委ねているのと同じ構図である。

> ⚠️ **この判断を毎回明示する。** 今日の作業群では、**委譲済みのものを待たせかけた例**（実装で決めてよいのに裁定待ちにする）と、**実装が勝手に決めてはいけない例**（planning#446 の「全 N 件」表示）の両方が出ている。**どちらなのかを書かないと、次の人が読み分けられない。**

## 🔴 委譲された方法が実行できない

ADR-0035 は「**実データの次数分布を見て**定める」と方法まで指定している。**しかしその実データが存在しない。**

| 実測 | 結果 |
| --- | --- |
| GraphService の消費者（文書・辺の取り込み経路） | **0 件** |
| 辺の自動抽出（#912） | **未着手** |
| `DocumentUpdated` 購読（#911） | **保留中** |

**したがって次数分布は測れない。** 測れないことを「測った」と書かず、**暫定値であることと、いつ測り直すかを記録する。**

- 暫定値を置く（下記）
- **実データが入った時点で測り直す**フォローアップ issue を起こす
- 値は**定数 1 箇所**に置き、変えるのが 1 行で済む形にする

## 決める値

### 辺の型の重み（0.0〜1.0）

| 型 | 重み | 根拠 |
| --- | ---: | --- |
| `supersedes` | **1.0** | ADR が「**最新版へ強く誘導**」と名指し |
| `derived-from` | 0.8 | 系列辿り（日報→週報→月報）の主軸。SC-18 も系列を用途に挙げる |
| `cites` | 0.7 | 明示的な出典表記。書き手の意図が強い |
| `embeds` | 0.7 | 本文の一部として取り込む。結び付きは強い |
| 推奨追加 4 種 | 0.5 | 中庸。実データが無い段階で差を付ける根拠が無い |
| `related` | **0.3** | ADR が「**弱く扱う**」と名指し。種類が判別できない既定型でもある |

**新しく追加された型の既定は 0.5** とする（中庸）。**`related` より下げない** —— 未知の型を既定型より弱く扱う根拠が無い。

### ハブ文書の次数上限

**暫定 50。**

- ADR-0034 の表示上限（ノード 200）に対し、**1 つのノードが結果の 1/4 を占める**あたりが「ハブ」と呼ぶ境目である
- ADR-0035 が挙げる例（「全社共通規程」「用語集」）は**数百から参照される**想定であり、50 はそれらを確実に捕らえる
- **通常の文書が誤って中継点から外れない**こと（過剰な絞り込みにしない）を優先した

🔴 **これは実測ではない。** 実データが入ったら測り直す。

## 🔴 「中継点にしない」の意味を取り違えない

ADR-0035 決定 2:

> ハブ文書の次数上限を設け、**超える文書は展開の中継点にしない**

**「結果から除く」ではない。**

| | ハブ文書 |
| --- | --- |
| 探索結果のノードとして**現れる** | ✅ する |
| そこから**さらに展開する**（次のホップの起点になる） | ❌ しない |

除いてしまうと、**利用者から見えるはずの関係が消える**（「全社共通規程を参照している」という事実自体は正しい関係である）。狙いは「ハブ経由で無関係な文書が芋づる式に湧くこと」の抑制であり、ハブ自体の隠蔽ではない。

**この違いをテストで固定する**（T-05・T-06 の対）。

## 受け入れ基準

- [ ] `edge_types` に重み列があり、初期値集合が上表のとおりに入る
- [ ] 新規に追加された型の重みが既定値（0.5）で入る
- [ ] 次数が上限を超える文書が、**探索結果には現れるが、そこから展開されない**
- [ ] 上限以下の文書は従来どおり展開される（**陽性対照**）
- [ ] 既存の探索の挙動（ホップ数・200/500・ホップごと ABAC）が**変わらない**
- [ ] 重みは**まだ誰も使わない**（#970 が使う）。**未使用であることが分かる形で置く**

## テスト方針

| ID | 内容 |
| --- | --- |
| T-01 | 初期値集合の重みが仕様どおり（`supersedes` 1.0 / `related` 0.3 ほか） |
| T-02 | API で追加した型の重みが既定値 0.5 |
| T-03 | 重みは 0.0〜1.0 の範囲に収まる（値域） |
| T-04 | 改名しても重みが変わらない（識別子と同じく、改名で動かない） |
| T-05 | 🔴 次数が上限を超える文書は**結果に現れる**（除かれない） |
| T-06 | 🔴 その文書からは**展開されない**（向こう側の文書が結果に現れない） |
| T-07 | 上限以下の文書からは展開される（**陽性対照**。T-06 の対） |
| T-08 | 次数の計数は**権限判定と独立**（見えない辺も次数に数える。下記） |

### 🔴 T-08 について — 次数を ABAC で絞ると上限が利用者ごとに変わる

次数は「その文書が何本の辺を持つか」であり、**利用者から見える辺だけを数えると、同じ文書が人によってハブになったりならなかったりする。**

**数えるのは全辺である。** ハブ判定は「グラフの構造上の性質」であって、利用者の権限の関数ではない。

> ⚠️ **これは #962 で「使用件数を一般利用者へ返さない」と判断したのと矛盾しない。**
> あちらは**集計値を応答に載せる**話で、こちらは**内部の展開判断に使う**話である。
> **次数そのものは応答に現れない。**

### 🔴 M-5 が落ちなかった —— 期待値が自己参照だった

T-02 を当初こう書いていた。

```csharp
created.Weight.Should().Be(EdgeType.DefaultWeight);
created.Weight.Should().BeGreaterThanOrEqualTo(0.3);
```

**`EdgeType.DefaultWeight` と突き合わせるのはトートロジーである。** 定数を 0.5 → 0.3 に変えると
期待値も一緒に動くので、**何も検出しない**。2 行目も「以上」なので 0.3 を通す。

**リテラルで測り、比較を「より大きい」へ直した。**

```csharp
created.Weight.Should().Be(0.5, "新規追加の既定は中庸（0.5）である");
created.Weight.Should().BeGreaterThan(0.3, "既定を related と同じにすると…");
```

**直した後、M-5 は 2 件を落とした**（T-01・T-02）。

> **表に「M-5 → T-02」と書いた時点では仮説である。** 当ててみるまで対応は成立していない ——
> #914 で M-5 の対応表が誤っていたのと**同じ形**を、今回は自分の期待値の書き方で踏んだ。
