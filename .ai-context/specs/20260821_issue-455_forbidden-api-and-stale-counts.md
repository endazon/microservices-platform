### 訂正 1: 「手順 6 は未実装」は誤り —— 手順 6 は封じ込め検査である

従前、計画の 8 手順を**二次資料（自分の過去の計画メモ）から引いて**「手順 6 は
`DisableConventionalLocalRouting` / `PrefixIdentifiers` / `ServiceLocationPolicy` の実装であり、
リポジトリ全体で 0 件だから未実装」と書いた。**原典を読んで誤りと分かった。**

原典（planning `06_technical/12_backend-application-stack.md` §Wolverine 移行チェックリスト）:

| --- | --- |
| 3 | 共通ヘルパで**リスニングキュー名にサービス名を前置**する。**`PrefixIdentifiers` は使わない** |
| 4 | 共通ヘルパで **`DisableConventionalLocalRouting()`** を適用する |

**したがって U3 のうち「`PrefixIdentifiers` を 0 に保つ」部分は、Wolverine 配線を待たずに**
**今すぐ入れられる。** 移行の最中に誰かが書いた瞬間に落ちる仕掛けを、**書かれる前に**置くのが要点である

## 設計上の判断

### 新規スクリプトを作らず `check-backend-libraries.js` へ相乗りする

**理由 1: 概念が同じ。** 同検査器は既に「**不採用のものを新規混入させない**」を
`.csproj` / `props` / `targets` の `PackageReference` と `.cs` の `using` の双方で強制している。
**禁止 API シンボル**は同じ規律の別形であり、`.cs` を歩く仕組みは既にある。

**理由 2: 読み込み予算。** 毎セッション必読の規約は総量 50KB 予算で、**#623 で既に到達している**。
検査器を 1 本増やすと `scripts/README.md` の表も 1 行増える。**規律は増やさず、置き場を選ぶ。**

### ratchet は要らない（0 件から始まる）

既存規則 1 は MassTransit の残件があるため ratchet 方式だが、**`PrefixIdentifiers` は 0 件から
始まる**ので「新規混入 → fail」だけでよい。既存規則 3（共有カーネル）が
「既知違反ゼロで開始でき ratchet を要さない」としているのと同じ形である。

### 🔴 「同型の事故が 2 回起きたら検査器を足す」との関係

本リポジトリの規約は検査器の追加を「同型の事故が 2 回起きたら」に限る。
**`PrefixIdentifiers` の誤用は 0 回**である。それでも入れるのは、**この検査器が計画 ADR に
明示的に指示されたもの**だからである（手順 6「**個別サービスでの逸脱を静的検査で禁止する**」）。

**「2 回起きたら」は事故から規律を起こすときの歯止めであって、計画が要求した統制を
実施しない理由にはならない。** 両者を混同しないこと。

## 変異試験の設計

- **変異 A**: 任意の `.cs` に `cfg.PrefixIdentifiers();` を 1 行足す → **fail し、そのファイルを名指しする**

## 実測

### 🔴 実装中に自分で作った fail-open を 1 件検出し、塞いだ

自己試験 7 件を `selfTest()` の末尾へ足したところ **「78 件 OK」** と表示された。
件数が 71 → 78 へ増えたので、一見すると 7 件が通ったように見える。**通っていなかった。**

挿入先が **`for (const c of cases)`（pass/fail を数える評価ループ）より後ろ**だった。
`cases.length` はループの後で読まれるので**件数だけが増え**、**新しい 7 件の合否は一度も見られない**。

**実測で確かめた**（変異: assert を `=== 1` から `=== 999` へ変えて必ず偽にする）:

```
移動前: EXIT=0 / 「自己試験 78 件 OK。」      ← 🔴 偽の assert が緑を返す
移動後: EXIT=1 / 「FAIL PrefixIdentifiers の呼び出しを検出する」
```

**気づいた経路は「件数」ではなく「名前」である。** 78 という数字は正しく見えた。
`--self-test` の出力を grep して**自分が書いたテスト名が 1 つも現れない**ことに気づいた。

🔴 **これは PR #883 で作った `NaN` の fail-open と同型である** —— どちらも
**数字は動くのに門が開いている**。「検査器を足したら、その検査器が落ちることを確かめる」を
守らなければ、検査器の追加は**安心の錯覚を増やすだけ**になる。

## 本作業で確認された、機械検査を置けない失敗の型

本セッションで同じ根の事故が **4 度**起きた。**根は「手元に無い数字を、有る形で書く」**である。

| # | 形 | 気づいた経路 |
| --- | --- | --- |
| 1 | サブエージェントの数え（13 のうち 6）を検証せず転記 | AI レビューの指摘 |
| 2 | 未実行のコマンド出力を「実測しました」と記載 | 投稿後に自分で実行 |
| 3 | 表のセルを跨ぐ正規表現の対応づけを生の行で検算せず報告 | 行番号で引き直したとき |
| 4 | 自己試験の件数増加を「通った」と読んだ（実際は評価前に push） | **テスト名が出力に無い**ことに気づいた |

🔴 **1〜3 に機械検査は置けない**（コメントや報告が実行済みかを機械は知り得ない）。
**4 だけは置ける** —— 「`--self-test` の出力に、期待するテスト名が現れること」は検査可能である。
ただし**本作業では入れない**。規約は検査器の追加を「同型の事故が 2 回起きたら」に限り、
**4 の型（自己試験の fail-open）は #883 の `NaN` と本件で 2 回目**に当たるが、
`NaN` の件は**本体コードの門**であって**自己試験の評価順**ではない。同型と数えるのは早い。
**次に自己試験側で起きたら入れる**こととし、ここでは記録に留める。
