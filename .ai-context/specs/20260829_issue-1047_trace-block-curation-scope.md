# #1047: trace ブロックの完全性という前提を実測で棄却する

## 1. 背景

#1047 は**自分で起票した** issue である。PR #1046 のレビューが
`docs/how-to/session-handoff.md` の trace ブロックに `specs:` 2 件と `issues:` の `#1044` が
無いことを指摘し、そこから**「本文が引く記録は trace ブロックに列挙されるべきだ」という
完全性の義務**を一般化して、「specs 7 件・issues 43 件が未掲載」と数えて起票した。

**この一般化が誤りだったことを実測で確定させる**のが本作業である。

## 2. 母集合の引き方（規則 1・5・8）

**規則 1（誤りの側から引く）**: 「掲載されている」側ではなく「本文が引いていて掲載が無い」側を数える。

**規則 5（軸を 1 本で終わらせない）**: #1047 は `session-handoff.md` 1 文書しか見ていない。
**`docs/` 配下の全 Markdown（158 件）**へ同じ規則を当てる。さらに `issues:` だけでなく
**`specs:` の軸も引く**（キーごとに性質が違う可能性があるため）。

**規則 8（自分の記録が母集合を動かす）**: 走査対象から **trace ブロック自身を除外**する
（ブロック内の `#NNN` を「本文が引いている」と数えると自己参照で二重になる）。

**マスク**: `check-cross-repo-refs.js` の `maskCode`（フェンス・インラインコード）に加え、
**Markdown のリンク先 `](...)` を潰す**。#1047 が記録したとおり、潰さないと**目次のアンカー**
（`](#1-進め方…)`）を issue 参照として拾う。

**除外したものと理由**: `.ai-context/` 配下は trace ブロックの規約対象外（本文へ直接書く）。
`src/` 配下は Markdown 文書ではない。いずれも ADR-0048 決定 4 の適用範囲外である。

## 3. 実測

### 軸 1 — `issues:`（`docs/` 全 158 文書）

| 指標 | 実測 |
| --- | --- |
| trace ブロックを持つ文書 | 155 / 158 |
| 「本文が引くが `issues:` に無い」参照の総数 | **289** |
| それが 1 件以上ある文書 | **61** |
| `session-handoff.md` 単独 | 未掲載 44（マスク無しだと 81 → 73 で誤検出 8） |

### 軸 2 — `specs:`

| 指標 | 実測 |
| --- | --- |
| `.ai-context/specs/` の実在数 | **517** |
| `session-handoff.md` の `specs:` の掲載数 | **14** |
| うち実在しない（デッドリンク） | **0** |
| 2026-08-28 / 08-29 付だけで未掲載 | **39** |

## 4. 判定 —— 前提は成立しない

**規模そのものが反証である。** 61 文書が独立に同じ漂流を起こすことはない。**それらは別の規則で
書かれていた**と読むほうが自然であり、実際 `docs/traceability-appendix.md` の §trace ブロックは
そう書いている:

> 裸の `#NNN`（本リポジトリの issue 言及）は対象外で、地の文に書いてよい。

**裸の `#NNN` は地の文に書いてよい＝散文に残せる。** つまり `issues:` に載せなくても情報は
失われない。**完全性の義務はどこにも書かれていない。**

`specs:` はさらに明白である。517 件中 14 件しか載っていない。網羅索引という読み方を採ると
**引継資料は数百件の spec 名を抱えることになる**。そうなっていないのは、**trace ブロックが
「この文書が辿るべき記録」を取捨した集合**だからである。

### 4-1 それでも #1046 の修正は正しかった

PR #1046 が足した 2 件は、**その PR 自身が作った spec** であり、**同じ PR が変更した文書**の
trace である。「この文書が辿る記録」に当たるので取捨の結果として妥当である。
**誤りは修正そのものではなく、そこから完全性の義務を一般化したこと**である。

## 5. やること

**同じ誤読が 2 回起きている** —— #1047 の起票（自分）と、PR #1046 のレビューが完全性を前提に
指摘した書き方である。規約は「同型の事故が 2 回起きたら手を打つ」と定める。**検査器は足さない**
（測る対象が義務ではないため、足すと義務を新設することになる）。**正本の側へ 1 文を足して
読み違えを塞ぐ。**

- `docs/traceability-appendix.md` §trace ブロック へ、**取捨した集合であり網羅索引ではない**
  ことと、その根拠（裸の `#NNN` は地の文に残せる／`specs:` は網羅すると数百件になる）を書く。

**やらないこと**: 289 件・39 件の一括追記。**義務でないものを追記すると、以後それが既成事実と
して義務になる。** 数だけ #1047 へ残して閉じる。

## 7. 実測できないこと

- **本リポジトリは shallow clone である**（`git rev-parse --is-shallow-repository` → `true`）。
  そのため「どの spec がどの文書を生んだか」を `git log` / `git blame` から導けない。
  `specs:` の取捨が妥当かを履歴から機械的に裏づけることは**この環境では不可能**である。
  上の判定は**規模と正本の条文**に基づくものであり、履歴の突合ではない。
