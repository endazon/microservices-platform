# 作業仕様書: 宣言レンジを一次情報にする（#1369）

## 起点

- issue #1369。2026-09-10 の作業で**同じ場所で 2 回止まった**（人と AI が 1 回ずつ）。
- 実測: `feat(NFR-09,ADR-0005,ADR-0084): …` が
  `起点 ID "ADR-0084" が planning の 07_adr/ に実在しない（誤記・廃止の可能性）` で不合格。
  **宣言レンジは `ADR-0001..0093` であり `ADR-0084` は実在する。** CI では同じコミットが通る。

## 何が起きているか

`loadExistingPlanAdrIds()` は既定パス `<repo>/planning/projects` を `readdirSync` し、
**読めたらそれを実在集合にする**。読めなかったときだけ宣言レンジへ進む。

コード内のコメントは「**ファイルシステム走査は明示パス指定のときだけ意味を持つ。既定パスは
資料再編で実在しない**」と書いており、**既定パスが存在しないことを前提にしている**。

その前提が崩れる —— **`planning/` の複製を手元に置いている環境がある**（隣接クローンを
リポジトリ内へ置いた形）。複製は追跡されておらず、版も内容も揃わない。実測した複製は
**48 件・`ADR-0047` まで**しか無く、それが実在集合になっていた。

## なぜ実害か

1. **偽の不合格は本物の不合格より質が悪い。** 正しい ID を「誤記の可能性」と言われた側は、
   規約を疑うか検査器を疑うかの二択になる。どちらを選んでも時間を失う。
2. **ローカルと CI で判定が逆になる。** 複製の有無・版が人によって違うので**再現しない**。
3. **規約の記述と食い違う。** `traceability.repo.md` は
   「計画 ADR の実在性は本節の宣言レンジで検査する」「ファイル有無の突合は submodule 撤去により不可」
   と書いている。**走査が宣言より優先されるのは、この記述と反対である。**

## 設計

**既定パスのときは走査しない。宣言レンジへ直行する。**

明示パス指定（テスト・別構成）のときだけ従来どおり走査する —— そこは呼び出し側が
「このディレクトリを実在集合とみなす」と宣言している場合であり、意図が違う。

| 経路 | 変更前 | 変更後 |
| --- | --- | --- |
| 既定パス（引数なし） | 走査 → 読めなければ宣言レンジ | **宣言レンジのみ** |
| 明示パス（テスト等） | 走査 → 読めなければ null | 変更なし |

あわせて、**どちらの情報源で判定したかを出力へ出す**。食い違ったときに原因へ辿り着けるようにする。

### 採らなかった案

- **走査を残したまま、宣言レンジと突き合わせて「宣言に含まれるなら合格」にする。**
  2 つの情報源を持ち続けることになり、どちらが正かが曖昧なままになる。規約は宣言レンジが正だと
  書いているので、実装をそちらへ寄せるほうが単純である。
- **`planning/` を消す・`.gitignore` へ入れる。** 手元の資産に触る話であり、検査器の欠陥は残る。
  別の人が同じ場所へ複製を置けば再発する。

## 走査した母集合（規則 2・9）

「既定パスの走査に依存している箇所」を、**誤りの側**（走査してしまう経路）から引いた。

| 走査 | 結果 |
| --- | --- |
| `loadExistingPlanAdrIds` の呼び出し | `check-commit-messages.js` 2 箇所（`:564` `:625`）・`check-landed-subjects.js` 2 箇所（`:74` `:186`）。いずれも**引数なし＝既定パス** |
| `DEFAULT_PLAN_PROJECTS_DIR` の参照 | 同ファイル内のみ |
| 試験からの呼び出し | `scripts.test.js` に 5 箇所。うち**明示パスが 3 箇所**（`:974` `:1004` `:1011`）、引数なしが 2 箇所（`:620` ほか） |

**除外**: `check-trace-blocks.js` の `planAdrRange()` は宣言レンジ側の読み手であり、本件の対象ではない
（むしろ一次情報にする先）。
