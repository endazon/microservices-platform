## 調査 1: AST#1428 の opt-in を MSP が渡す経路はあるか

- 走査: `git grep -n -E "k8s-local-deploy|ai-stock-trading/scripts|ALLOW_DEV_CLIENT_SECRETS|allow-dev-client-secrets"`（submodule・specs・CHANGELOG を除く）。
- 結果: MSP の **CI（integration-stack・cutover-rehearsal ほか全ワークフロー）と `scripts/k8s-local-up.sh` は AST の起動器を呼ばない**。
  integration-stack は submodule を BFF・フロントのイメージのビルドにだけ使い、AST の chart を配備しない（待ちの対象の名前空間も
  `platform-infra` / `microservices-platform` だけ）。`k8s-local-up.sh` の言及は注釈 1 行（名前空間の冪等作成の説明）だけ。
- `ALLOW_DEV_CLIENT_SECRETS` は MSP 自身の判定（IADR-0517。kube context の許可集合つき）と**同名**だが、AST の判定は kube context を見ない別物。
  MSP の CI は MSP の判定に対して既に opt-in を渡していない（陽性対照として渡さないことを試験が固定）—— 変えない。
- よって CI への opt-in の追加は**不要**（MSP#2057 の `ALLOW_DEV_INFRA_CREDENTIALS=1` と違い、止まる起動器を CI が呼ばない）。
- 人が読む手順のうち AST の起動器を開発用の値で回すのは `docs/operations/local-sso-recovery-runbook.md` STEP 1（`*-dev-secret-change-me` を export する）。
  pin の前進でこの手順は `[0/5]` で止まるようになるため、**注記を足す**（本筋は開発用でない値、使い捨ての dev のクラスタだけ opt-in）。
