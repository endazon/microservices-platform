# 作業仕様書: 封じ込め検査器の不可視領域（#919 / #920）

## 起点

- `#919`（`dist/` 配下・UTF-16LE の `.cs` を検査器が見ていない）
- `#920`（値レベルの変異を検査器が見ていない）
- いずれも `#903` の U4 変異試験で実測された、**現存 0 件だが検査器としては素通り**する形
- 検査器: `scripts/check-backend-libraries.js`

## 🔴 着手前の実測 —— 「検査器を強くする」を自明の解にしない

`#885` が「候補 A は精度 1/38 ≈ 2.6% で成立しない、だから足さない」に至った先例がある。
**先例があるから同じ結論、ではなく、費用を測ってから決める。**

### 再現（対照つき）

| | 検査器 | 判定 |
| --- | --- | --- |
| `dist/` 配下に禁止シンボル（規則 4 の `PrefixIdentifiers`） | **EXIT=0** | 🔴 素通り（SX-1 再現） |
| **同じ内容を `dist/` の外へ置く** | **EXIT=1** | ✓ **検査器は生きている**（対照） |
| UTF-16LE の `.cs` に禁止シンボル | **EXIT=0** | 🔴 素通り（SX-2 再現） |

**対照を取ることが要る** —— 素通りが「検査器が壊れている」のか「その形を見ていない」のかを分けるため。

### #919 の強化費用（実測）

| 項目 | 実測 |
| --- | --- |
| 追跡下の `dist/` 配下ファイル | **0 件**（検査対象拡張子も 0 件） |
| 作業ツリーの `dist/` 配下 `.cs` / `.csproj`（未追跡込み） | **0 件** |
| `dist` を SKIP から外したときの走査時間 | **118ms → 128 / 131ms**（3000 ファイルの合成 dist を置いて計測。**skip したまま = 165ms より速く、計測ノイズの範囲**） |
| 非 UTF-8 の `.cs` | **0 件**（498 件を BOM で分類: UTF-16 BOM 0 / UTF-8 BOM 15 / BOM なし 483） |

🔴 **偽陽性は構造的に増えない**（新たに一致するファイルが 0 件）。
**`#885` の状況とは条件が逆である** —— あちらは偽陽性が支配的、こちらは偽陽性ゼロ。

### #920 の強化費用（実測）

3 変異すべて `BUILD EXIT=0` を確認したうえで測った（コンパイルエラーで落ちたのでは判定にならない）。

| 変異 | 検査器 | テスト |
| --- | --- | --- |
| A3 手順 5 の値のみ反転（`AlwaysAllowed` → `NotAllowed`） | **EXIT=0** | **1 件**落ちる |
| A5 手順 3 の前置を落とす | **EXIT=0** | **2 件**落ちる |
| A6 区切りを `-` へ | **EXIT=0** | **3 件**落ちる |

## 決定

### #919 → **塞ぐ**

1. `SKIP_DIRS` から `dist` を外す
2. `.cs` の読み込みで **UTF-16 の BOM を判定**して復号する

費用が実測でゼロだから塞ぐ。「不可視領域があること」自体が、検査器の緑を誤読させる。

### #920 → **塞がない**（実測に基づく裁定）

1. **テストが届かない範囲が無い。** 3 変異すべて既存テストで捕まり、A6 は 3 件が落ちる。
   強化しても**純粋な二重防護**にしかならない。
2. **偽陽性の費用が高い。** 値レベルの検証は C# ソース中のリテラルを判定することになり、
   `PlatformQueueName` の抽出・定数化・命名変更といった**正当なリファクタで落ちる**。
3. **CLAUDE.md の「検査器・規約の追加は『同型の事故が 2 回起きたら』を条件とする」** に対し
   **発生 0 回**である。

## 🔴 意図した不検出を、意図として固定する

強化後に **#920 の 3 変異が EXIT=0 のままであること**を変異試験で固定する。
これが無いと、後から見た人が「強化したのに値レベルが素通りする」を**欠陥として読む**。
**「証明力のない変異」と「検出漏れ」の区別を機械に埋め込む。**

### 🔴 実装中に踏んだ事故 —— 生の NUL バイトの混入（**通算 3 回目**）

**NUL の混入を説明するコメントに、実際の NUL バイトを書き込んだ。**
`git` / `grep` がファイルをバイナリ扱いし、**行番号も diff も出なくなる**（レビュー不能になる）。

| 回 | 場所 | 経緯 |
| --- | --- | --- |
| 1 | `#900` `scripts/check-coverage-floor.js` | 重複排除キーの区切りに NUL を使うつもりが、リテラルの NUL が入った |
| 2 | 本 PR `scripts/check-backend-libraries.js` | 「UTF-16 を utf8 で読むと NUL 混じりに化ける」を**説明する**コメントに実 NUL が 3 個 |
| 3 | 本 PR 本仕様書 | 上の回 2 を**記録する**文に実 NUL が 1 個 |

いずれも「`\u0000` と書いたつもりが実バイトになる」という同じ機序で、
**エスケープ表記を含む文を書くたびに再発している**。

🔴 **CLAUDE.md の「検査器・規約の追加は『同型の事故が 2 回起きたら』を条件とする」の条件を満たした。**
本 PR の射程（封じ込め検査器の不可視領域）とは別の関心事なので**本 PR では足さず、追随 issue を起票する**。
検出は「追跡下のテキスト系ファイルに生の NUL が無いこと」で足り、費用は小さい。

**この事故を「AI の編集操作の問題だから記録に留める」と片付けない。** 効果はリポジトリの成果物に出る
——バイナリ扱いされたファイルは diff もレビューもできず、**混入したまま気付かずマージされ得る**。
