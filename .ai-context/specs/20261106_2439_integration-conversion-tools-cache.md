# 作業仕様書 — 回収実行の変換ツールの導入（#2439）

> 本仕様書は実装着手前に作成した（着手 2026-11-06。develop `4b90c510`）。起点は NFR（CI の統制）。

## 事象

回収実行（`.github/workflows/integration.yml`。ジョブの `timeout-minutes: 30`）が上限に近づいた。
- develop の run 42086571941 は 29.2 分かかった。
- MSP#2415 の run 42087834357 は、試験の途中で 30 分に達して cancelled になった。

## 調べたこと（直近 58 回の run の step ごとの時間。GitHub の jobs API）

| step | 普段 | 伸びた回 |
| --- | --- | --- |
| `Install conversion tools (pandoc / poppler-utils)` | 8〜32 秒 | 461・576・763・810 秒（2026-11-05 16:29 以降の 4 回） |
| `All tests including real containers` | 744〜1227 秒（750〜900 秒と 1100 秒前後の 2 群） | 954・984 秒（普段の幅の内） |

- 伸びは、`apt-get update` / `apt-get install` の取得で止まっている時間である。遅い回のログでは、step の始まりから最初の出力（展開）まで 12.6 分、何も出ていない（`-qq`）。
- 速い回と遅い回で、ランナーのイメージ（ubuntu-26.04 / 20261101.186.1）と入ったパッケージの版は同じだった。
- 疑ったほかの要因は、どれも当たらなかった。
  - 新しい試験: 試験の step は普段の幅の内だった。
  - 並列度: 変えていない。
  - ランナーの負荷: 試験の時間の 2 群は前からあり、伸びと結びつかない。
  - コンテナの起動待ち: 試験の step の内にあり、普段の幅の内だった。
- 試験の最長 1227 秒（約 20.5 分）と準備（checkout・submodule・NuGet・dotnet・後処理で約 3 分）に、取得の止まり（最大 13.5 分）が重なると 30 分を超える。

## 方式

1. 変換ツールの `.deb` をキャッシュする。取り出し（`actions/cache/restore`）と保存（`actions/cache/save`）を分ける（どちらも ci.yml の `actions/cache` と同じ SHA に固定）。
   - 鍵は、ランナーのイメージの名前と版（`$ImageOS`・`$ImageVersion`）と、入れるパッケージの名前と、作り方の版（`-v<n>`。作り方を変えたら手で上げる）。イメージが替われば鍵も替わり、取り直す。
   - キャッシュに在れば、`dpkg -i` で入れる（取得なし）。失敗したら、取得の経路へ落ちる。
   - 保存は導入の直後に置き、キャッシュに無く、この回に `.deb` を置いた回だけ走らせる。試験の成否・cancelled に依らない（post で保存する `actions/cache` は、赤の回・cancelled の回に保存しない）。
2. キャッシュに無ければ、apt で取得する。
   - 時間切れと再試行を付ける（`Acquire::Retries=3`・`Acquire::http(s)::Timeout=30`）。
   - 取得は apt の既定の置き場（`/var/cache/apt/archives`。`_apt` の sandbox のまま）で行う。前に `apt-get clean` で空にし、この回に取得した `.deb` だけをキャッシュの置き場へ写す。
   - 取得した `.deb` が 0 個（イメージに入っていた）なら、写さず、保存もしない（`cp` の glob が展開されずに落ちるのを避ける。空の置き場を保存しない）。
3. 導入の step に上限（`timeout-minutes: 10`）を付ける。取得が止まっても、ジョブの上限を食い潰さず、導入の失敗として赤になる。
4. ジョブの上限（30 分）は変えない。
   - 根拠: 試験の最長 20.5 分と準備の約 3 分で 23.5 分。キャッシュに在る回の導入は数秒、キャッシュに無い回でも上限は 10 分。
   - 上限を上げるだけの直しは採らない。止まりの時間は上限を上げても縮まらず、次の止まりがまた上限に近づく。
5. #2128 の検査（導入が試験より前・失敗を握り潰さない・両ツールの確認）は、そのまま通す。
6. 導入の step の注記「版は本番イメージと同じ noble の apt に揃う」は、事実と違う。
   - ランナーは ubuntu-26.04 で、pandoc 3.7・poppler 26.01 が入る。本番イメージは noble で、pandoc 3.1.3・poppler 24.02 である。
   - 注記を事実に直す。版を揃えるかは本件の外（残すもの）。

［2026-11-06 追記 / #2440 のレビュー］
- 取り出し（`actions/cache/restore`）と保存（`actions/cache/save`）を分けた。`actions/cache` は post step で保存するので、試験が赤の回・上限で cancelled の回には保存されず、取得が止まりやすい時期ほど温まらない。
  - 保存は導入の直後に置き、キャッシュに無かった回だけ走らせる（`if: steps.<取り出し>.outputs.cache-hit != 'true'`）。
  - 導入が赤なら保存も走らない（空の置き場を保存しない）。試験の成否には依らない。
- 取得の置き場をホームの下へ向ける形（`Dir::Cache::Archives`）をやめた。1 回目の実走（run 42094791875）で「W: Download is performed unsandboxed as root」が出た（`_apt` がホームの下に書けない）。
  - apt の既定の置き場で sandbox のまま取得する。その前に `apt-get clean` で空にし、この回に取得した `.deb` だけをキャッシュの置き場へ写す。
- 置く物の作り方を変えたので、鍵の末尾を `-v2` に上げた（その後、0 個の `.deb` の扱いを足して `-v3`）（`-v<n>` は作り方を変えたら手で上げる、と step の注記に書いた）。

## 母集合（規則 9）

`git grep -n -E 'apt-get (update|install)' -- .github/workflows` で、ワークフローの apt の取得を引いた。
- ジョブの上限に達したのは integration.yml の変換ツールの step だけ。
- ほかの workflow の apt（ci.yml 等）は、上限に達した記録が無い。本件の外とする。

## 受け入れ基準と試験

| # | 基準 | 試験 |
| --- | --- | --- |
| AC1 | キャッシュの step が導入の step より前に在り、鍵がランナーのイメージの名前と版を含み、導入の step が同じ置き場から `dpkg -i` で入れる | `scripts.repo.test.js` の #2439 の節 |
| AC2 | キャッシュに無いときの取得に、時間切れと再試行が付き、取得した `.deb` を同じ置き場へ置く | 同上 |
| AC3 | 導入の step に上限（15 分以下）が在り、ジョブの上限は 30 分のまま | 同上 |
| AC4 | #2128 の検査が通る（導入が試験より前・握り潰さない・`pandoc --version`・`pdftotext -v`） | 既存の #2128 の節 |
| AC5 | 陰性対照: キャッシュの step を外す・鍵から版を外す・時間切れを外す・上限を外すと赤 | #2439 の節 |
| AC6 | 実走: CI の Integration で、キャッシュに無い回が置き、次の回がキャッシュから入れる | PR の CI（dispatch 2 回の step の時間とログ。結果は下の「実走の結果」） |

## 実走の結果（AC6。head 8cdee21b）

| run | キャッシュ | 取り出し | 導入の step | 保存 | ジョブ |
| --- | --- | --- | --- | --- | --- |
| 42099443811（1 回目） | 無し（`Cache not found for input keys: …-v3`） | 0 秒 | 9 秒（apt で取得。`unsandboxed` の警告は 0 件） | 2 秒（`Cache saved with key: …-v3`。試験の前） | 18.6 分・success |
| 42102809188（2 回目） | 在り（`Cache restored from key: …-v3`） | 4 秒 | 19 秒（「キャッシュの .deb から入れた（取得なし）」。apt の取得なし） | skipped（キャッシュに在った） | 17.7 分・success |

- 2 回目は取得を使わずに入れた。ネットワークの止まりに左右されない。
- 2 回目の導入（19 秒）が 1 回目（9 秒）より長いのは、dpkg の展開と後処理の時間である。取得の止まり（8〜13 分）と比べれば小さい。

## 受容すること

- キャッシュのある回で `dpkg -i` が失敗すると、取得の経路へ落ちる。その回は保存が走らない（キャッシュに在った回なので）。そのため、壊れた鍵が残る。
  - 鍵はランナーのイメージの版ごとで、イメージが替われば使われなくなる。その間は毎回取得の経路で入る（従前と同じ形）。受容する。
  - 直すには、鍵の末尾の `-v<n>` を手で上げる。

## 残すもの

- 回収実行の変換ツールの版（ランナーの apt）と本番イメージの版（noble）が違う。揃えるか（ランナーを noble に固定する・同じイメージの中で試験を走らせる）は別件。
