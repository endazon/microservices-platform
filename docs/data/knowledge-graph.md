# データ仕様書: 知識グラフ（GraphDocument / EdgeType / Edge）

> GraphService が所有する、文書間の関係（辺）とその型辞書、および認可判定に用いる文書属性の複製を扱う。専用 DB（`graph_svc`）に置く。

## 起点となる計画書（トレーサビリティ）

- **関連機能要求**: 文書間リンクの保持と探索（バックリンクを含む）、関係の種類と出所の区別、探索結果の権限スコープ制限
- **技術検討・裁定**: 知識グラフのデータモデルと格納先、グラフ探索時のアクセス制御強制方式、属性ベースアクセス制御の属性モデル、サービスごとの専用 DB
- **計画書リンク**: 計画リポジトリ `projects/microservices-platform/07_adr/` および `06_technical/`（GitHub 上を直接参照する）

## 概要

知識グラフは 3 つのエンティティで構成される。

| エンティティ | 役割 | 正本 |
| --- | --- | --- |
| `GraphDocument` | 探索の**ノード**。認可判定に用いる文書属性の**複製**を保持する | 文書管理サービス（複製元） |
| `EdgeType` | 辺の**型辞書**。実行時に管理され、コード定義を持たない | GraphService |
| `Edge` | 文書間の**辺**。型・出所・アンカーを持つ | GraphService |

**属性の複製は認可のために必要である。** 探索は各ホップで認可述語を評価するため、ノードの属性がグラフ側に無いと、ホップごとに別サービスへ同期照会することになり、探索が実用にならない。複製は文書更新イベントで追随する。

## エンティティ定義

### GraphDocument（テーブル `graph_documents`）

| 列 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| `document_id` | `uuid` | PK | 文書管理サービスの文書 ID と同一値 |
| `title` | `text` | NOT NULL DEFAULT `''` | 表示名 |
| `attributes` | `jsonb` | NOT NULL DEFAULT `'{}'` | 認可判定に用いる文書属性の複製 |
| `body_hash` | `text` | NULL 可 | 本文のハッシュ。提案の却下解除判定に用いる |
| `updated_at` | `timestamptz` | NOT NULL | 複製元イベントの更新時刻。順序ガードに用いる |

**`attributes` を `jsonb` にする理由**: 認可の属性軸は今後増減する（現在は実データ上ほぼ機密区分のみが有効で、部署・所有者・ライフサイクルの充足が課題として残っている）。属性ごとに列を切ると、軸が 1 つ増えるたびにマイグレーションが要る。`jsonb` なら**スキーマ無変更で追随**でき、アプリ側の属性辞書型（キーと値がいずれも文字列の辞書）とそのまま対応する。

**判定は取得後のメモリ内で行う。** SQL 側へ押し込むと、大文字小文字を区別しない比較を含む意味論の一致検証が難しくなる。フロンティアが大きい場合の最適化候補としては残すが、初期実装では採らない。

**属性レコードが無いノードは不可視とする**（欠落は安全側に倒す）。新規文書はイベントの初回同期まで、イベント欠損時は恒久的に、グラフ上に現れない。

### EdgeType（テーブル `edge_types`）

| 列 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| `id` | `uuid` | PK | **サロゲートキー。改名で変わらない** |
| `name` | `text` | NOT NULL / 正規化後一意 | 表示名。**改名で動くのはここだけ** |
| `layer` | `text` | NOT NULL | 意味の層（3 層構成） |
| `is_symmetric` | `boolean` | NOT NULL DEFAULT `false` | 対称関係か |
| `is_seed` | `boolean` | NOT NULL DEFAULT `false` | 初期値集合の目印（削除ガードとは独立） |
| `created_at` / `updated_at` | `timestamptz` | NOT NULL | |

一意索引: `ux_edge_types_name UNIQUE (name)`

**大文字小文字の違いはサービス層が弾く。** DB の一意索引は素の `name` に対するもので、`Related` と `related` を別物として通す。名前の重複判定はサービス層が正規化（前後の空白除去）＋大文字小文字を無視した比較で行い、先に 409 を返す。DB 側の一意索引は競合（検査と保存の間に別の要求が同名を入れる）を捕まえる最後の防壁として働く。

**コード定義（言語の列挙型）にも DB の列挙型にもしない。** 型の値集合は管理画面から実行時に管理すると計画側が定めており、列挙型にすると値の追加がそのままマイグレーションになる。**行データにすれば型の追加は INSERT のみで済む。**

**改名追随はサロゲートキーの帰結である。** 辺は `id` を参照するため、改名は `name` の 1 行 UPDATE で完了し、既存の辺は 1 行も書き換わらずに新しい名前へ追随する。表示名を辺側に複写する設計だと、改名が該当辺すべての UPDATE になり、書きかけの失敗で混在状態が生まれる。

これは文書管理サービスのタグ辞書が既に採っている形と同型である（タグ辞書も同じ「参照があれば削除拒否・改名は追随」の規則を持つ）。

### Edge（テーブル `edges`）

| 列 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| `id` | `uuid` | PK | |
| `source_doc_id` | `uuid` | NOT NULL | 始点。対称型では正規化順の小さい側 |
| `target_doc_id` | `uuid` | NOT NULL | 終点。対称型では正規化順の大きい側 |
| `edge_type_id` | `uuid` | NOT NULL / FK `edge_types(id)` **ON DELETE RESTRICT** | **削除ガードの最後の防壁** |
| `provenance` | `text` | NOT NULL / CHECK | 出所（自動抽出／利用者付与／提案の承認済み） |
| `source_anchor` | `varchar(200)` | NOT NULL DEFAULT `''` | **将来のチャンク粒度拡張のための予約列。当面は常に空文字** |
| `target_anchor` | `varchar(200)` | NOT NULL DEFAULT `''` | 同上 |
| `created_at` / `updated_at` | `timestamptz` | NOT NULL | |

制約・索引:

- `ux_edges UNIQUE (source_doc_id, target_doc_id, edge_type_id, source_anchor, target_anchor)`

**予約列を NULL 可にしない。** 一意制約に参加する列を NULL 可にすると、PostgreSQL の既定では NULL 同士が相異なるものとして扱われ、**同一の（始点・終点・型）を何行でも入れられてしまう** —— 予約列のせいで重複防止が壊れるのは本末転倒である。空文字を「文書単位」の表現に使えば素の一意制約がそのまま効き、モデルスナップショットとも齟齬が出ない。
- `ix_edges_source ON edges (source_doc_id)`
- `ix_edges_target ON edges (target_doc_id)` — **バックリンクの逆引き**
- `ix_edges_type ON edges (edge_type_id)` — 型別使用件数

**`graph_documents` への外部キーは張らない。** リンク抽出はノード同期より先に届き得るし、ノードレコードの欠落は「不可視」として認可側で吸収される。FK を張るとイベントの到着順に人工的な依存が生まれる。

**辺は常に 1 行である。** 方向型は行の始点→終点が意味方向そのもの。対称型は書き込み時に文書 ID の昇順へ正規化して重複を防ぐ（一意制約が効く）。読み取り時に `is_symmetric` を見て無向として提示する。**バックリンクは行を増やさず**逆引き索引で実現し、探索は最初から双方向を引く。

**辺自身は機密属性を持たない。** 辺の機微性は「両端文書の存在と関係を明かすこと」に由来し、両端点の認可判定の連言で完全に覆われる。辺に独自のアクセス制御軸を足すのは計画に無い抽象化である。出所は認可軸ではなくメタデータである。

**最新版のみ保持する。** 文書の版ごとに辺を持たず、差分更新する。

## 認可（探索との関係）

- 探索は**ホップごとに**認可述語を評価し、**非許可ノードはフロンティアに入れない**（拡張前に刈る）。したがって非許可ノードが「橋」となって権限外の隣接文書を浮上させる経路が構造的に存在しない
- **辺は両端点が許可されたときのみ可視**である
- 表示上限（ノード・辺の件数）は**述語を通過した品目に対してのみ計数**する。これにより件数が権限外の存在を漏らすことがない
- 非許可・レコード欠落・文書不存在は**すべて同一の 404** に倒す（リンク切れと権限不足を利用者が区別できないことは計画側で受け入れ済みの副作用である）

述語の意味論は既存の Wiki ページ用フィルタと一致させる: 許可ポリシー無しは全不可視、フィルタ間は AND・値集合内は OR、**属性キーを持たないノードは不一致**、フィルタが空で許可ありなら全許可。

## 複製の鮮度

1. 判定は常に「最後に受信・適用した属性」に対して行う。同期照会による補正はしない
2. **失敗方向は非対称である。** 属性の緩和の遅延は「まだ見えない」＝安全側。**厳格化の遅延は「まだ見える」＝漏えいの窓**である。これは Wiki 連携の属性同期が既に持つのと同型の受容であり、本サービスが新たに悪化させるものではない
3. 複製が無いノードは不可視
4. 更新時刻をガードに使い、保持中より古いイベントは適用しない（再配信・追い越しで厳格化後に緩和が復活する事故を塞ぐ）。冪等

## 設計上のトレードオフ

| 選択 | 得るもの | 払うもの | 棄却した代替 |
| --- | --- | --- | --- |
| 型辞書をサロゲートキーの行データにする | 改名が 1 行・削除ガードに外部キーが使える・実行時管理と噛み合う | 表示に結合（または辞書の 1 回ロード）が要る。書き込み時に名前 → id の解決が要る | 言語／DB の列挙型（値追加が即マイグレーション）。辺に表示名を直接持つ（改名が質量更新） |
| 型の追加を INSERT で済ませる | **マイグレーション不要** | 対称性・層を人が正しく入力する必要がある | 型ごとのテーブル／列 |
| 属性を `jsonb` で持つ | 認可の属性軸の増減にスキーマ無変更で追随 | SQL 側で型付け・外部キーが効かない。述語はメモリ内評価 | 属性ごとの列（軸追加のたびにマイグレーション） |
| 辺 1 行主義 | 重複維持が無い・差分更新が単純 | 探索とバックリンクが常に双方向クエリになる（どのみち要求されている） | 対称辺を 2 行複製（更新の原子性が負担） |
| アンカー 2 列を空文字既定で予約 | 将来のチャンク粒度拡張がスキーマ追加なしで着地。一意制約も既にアンカーを含み、素の制約がそのまま効く | 当面デッド列 2 本。「無い」を空文字で表す約束が要る | 予約しない（計画側の裁定に反する）。NULL 可で予約（一意制約が効かなくなる） |
| 属性の複製をノードのみに置く | 属性変更 1 件がノード 1 行の更新で済む。述語評価が追加 I/O ゼロ | 辺だけを見て可視性を判断できない（両端の参照が要る） | 辺にも複製（属性変更が接続辺全行へ増幅し、食い違う瞬間が生まれる） |

## ストアの選定

格納先の製品（リレーショナル DB の隣接リストか専用グラフ DB か）は計画側で**実測待ち**のままである。当面はプラットフォーム標準に沿って PostgreSQL の隣接リストで実装し、探索をポート越しに置いて交換可能に保つ。

**再訪の条件**: ①実データ規模での探索応答時間が対話的利用に耐えないという実測が出たとき、②計画側で深いホップや全グラフ解析の要求が確定したとき。そのときの実測値を計画側へ環流する。

## 既知の未強制（重要）

**所有者に基づく判定と個人資料の境界は、現時点では強制できない。** 実データ上、必須とされる文書属性のうち機密区分以外（部署・所有者・ライフサイクル）が充足しておらず、また「属性・所有者・共有先」の 3 分岐の論理和を表現する構造が権限スコープの契約に無い。したがって**実効的な認可軸は機密区分のみ**である。

「見かけ上強制されている」誤認を防ぐため、**現状の有効な認可軸を固定するテスト**を置き、この前提が解消された時点で赤くなって気付ける形にしてある。
