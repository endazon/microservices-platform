# 別紙: ID / issue 番号の修飾 —— 経緯と実測

> **★ これは「参照時にだけ読む別紙」である。** 毎セッション読む必要は無い。
> **規約の入口は [`.claude/rules/traceability.md`](../../.claude/rules/traceability.md)
> 「複数プロジェクトを跨ぐ場合の ID 修飾」節（キット配布物・一般規約）と companion [`traceability.repo.md`](../../.claude/rules/traceability.repo.md)
> 「複数プロジェクトを跨ぐ場合の ID 修飾（固有設定）」節（本リポの値。2026-08-16 / #755 に移した）**であり、**規範（`<PROJ>` の値・AST の採番レンジ・
> 短縮形の書式・列挙形の修飾・空白を入れない・`endazon` owner・誤例の書き方）はそちらに在る。**

> **本別紙が持つのは「なぜその規約があるのか」の経緯と実測だけ**である

## 衝突が実際に起きた経緯

  実際に AST の `FR-17`（当時 MSP は `FR-15` まで）と AST の `SC-01`（MSP の `SC-01`＝検索/チャットと衝突）で
  誤検出が発生した。

## 計画大改定で重なり方が変わった

  計画リポジトリの大改定で MSP のレンジが `FR-01..21` / `UC-01..11` / `SC-01..21` へ広がった結果、
  重なり方は次のとおり変化した。**修飾の欠落がどちらの誤りとして現れるかが変わる**ため区別する。
  - **`FR-16`〜`FR-20`**: 従来は AST にしか無く、裸で書けば「計画書に存在しない ID」＝**参照切れ**として目立った。
    MSP 側に同番号が生まれたことで**双方に存在し意味の異なる ID** へ変わり、修飾の欠落は**誤帰属**
    （別プロジェクトの要求へ静かに紐づく）として現れる。検査で捕まらないのはこの型である。
  - **`FR-01`〜`FR-15` / `UC-01`〜`UC-07` / `SC-01`〜`SC-03`**: 改定前から双方に存在する（従来どおり誤帰属）。
  - **`FR-22` / `UC-08`〜`UC-11` / `SC-04`〜`SC-21`**: MSP にしか無い（**`FR-22` は［2026-08-07 / #599］で追加**）。**`SC-18`〜`SC-21` は AST 側に対応 ID が
    存在しないため衝突しない**（将来 AST が採番を伸ばせば上の「誤帰属」型へ移る）。
  - **`FR-21`**: **［2026-08-17 訂正 / #455］従前この行は `FR-21` を「MSP にしか無い」側に置き、「AST の採番は `FR-01..20` なので衝突しない」と述べていた。
    その前提は失効している** —— **AST が `FR-21` を採番した**（AST 計画 `02_requirements/01_requirements.md`。［2026-08-07 裁定］で新設・［2026-08-08 改定］。走査基準 planning `767a9d48` で実測）。
    したがって `FR-21` は**双方に存在する**ようになり、**上の「誤帰属」型へ移った**。**この行が自ら予告した「将来 AST が採番を伸ばせば」がそのまま起きた事例である。**

## 入口から移した補足（2026-08-16 / #755）

- **`check-plan-id-qualification.js`が検出しないもの**: 「AST 文脈で裸の ID」（`AST リスク設定（SC-02）`）は近傍規則になり偽陽性が避けられないため検査しない —— 規約自身が「AST の `FR-17`」と誤帰属そのものを説明する地の文を持つ。列挙の後続 ID（`AST/SC-02/SC-03` の `SC-03`）も同様。**`check-cross-repo-refs.js` とは対象が違う** —— あちらは issue / PR 番号（`AST#24`）、こちらは計画 ID / ADR ID（`AST/FR-17`）。同じ `AST` で始まるので混同しないこと。
- **AST の採番レンジは pin `767a9d48` 時点の実測**である（**［2026-08-17 訂正 / #455］従前は `655e2ed` と書いていたが、
  同 sha は現在の `planning` のどの ref からも到達できず、走査基準として追試できない**）。AST の文書に他の `SC` 番号も現れるが、いずれも MSP 画面への参照であって AST の採番ではない —— `05_screens/01_screens.md` の `SC-13` / `SC-16`、`07_adr/ADR-0012_mcp-exposure-policy.md` の `SC-11`。
- **短縮形と長い表記**: `project-planning#NNN` / `ai-stock-trading#NNN`（リポジトリ名の裸書き）は短縮形でもフルパス形式でもない第 3 の表記であり使わない。Markdown の明示リンク（`[planning#197](https://github.com/endazon/project-planning/issues/197)`）は URL 側が自動リンクを担うのでテキストを短縮形にしても機能は落ちない（#507 の裁定）。空白が入ると（`AST #24` / `planning PR #144`）機械的突合に掛からず、自動リンクが効く面では番号が本リポジトリへ張り付く。
- **#590 の owner**: フルパス形式の owner を誤ると `.md` でも死んだリンクが描画される（型 1〜3 は `.md` では表記ゆれに留まる）。実測値は走査基準つきで 仕様書: フルパス形式の owner 誤りを検出する型 4 を追加する が正（数を条文へ埋めると自己試験へ正例を足しただけで黙って古くなる。#590 が実際にそれを踏んだ）。第三者リポジトリ（`anthropics/claude-code-action#723`）は owner が `endazon` でないのが正しい。
- **`〔〕` 注記**: 先頭の番号を裸にする形（`PR #244〔裁定依頼 planning#237〕`）は機械では検出できない —— 裸の `#244` は規約上「本リポジトリの PR」を意味する正しい表記であり、意味の取り違えは構文から判定できない。書き手が責任を持つ。

## 機械検査の射程

  - **機械検査**: `scripts/check-cross-repo-refs.js`（`--self-test` あり）が上記の各型
    （長い表記・列挙形の修飾漏れ・空白区切り・**フルパス形式の owner 誤り**）を検出する
    （**型の件数は書かない** —— 型を足したとき片方が黙って古くなるため。正は同スクリプト冒頭の列挙）。
    対象は追跡下の `*.md` と、
    `scripts/check-commit-messages.js` 経由の**コミット件名 / 本文 / PR タイトル**。
    規約に書くだけでは再発する（PR #561 は**本ファイルを編集する PR でありながら**同じ違反を犯し、
    書式しか見ない検査を green で通過した）。表記検査は表示テキストだけを見る、という実装判断による。

## どこで自動リンクが効くか

  - **どこで自動リンクが効くかを取り違えないこと**（実測。同実装判断の決定 1）。
    **`.md` では裸の `#NNN` も短縮形の修飾も自動リンクにならない**——`.md` でリンクになるのは
    フルパス形式だけである。したがって `.md` での違反は「表記ゆれ（機械的突合の不安定）」であり、
    **誤リンクという実害が出るのは issue / PR / コミットメッセージの本文**である。
