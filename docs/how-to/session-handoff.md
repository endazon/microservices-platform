### ［2026-08-23］オープン issue の一括消化（進行中）

**オープン 65 件を全件トリアージし、リポジトリ内で完結する 28 件を対象と判定して着手した。**
判定・除外理由の正は作業仕様書側にあり、**生きた状態は GitHub が正**である（この節は必ず古くなる）。

> 🔴 **この運用は §1 の「束ねない。1 issue = 1 PR」と正面から食い違っている。**
> **食い違いを解消する条文はまだ無い。** 作業ブランチがセッションの制約として 1 本に固定された
> ためだが、**「そうせざるを得なかった」は条文を改定しない。** 束ねの限定例外は 2 つあり、
> どちらも上限 4 件で、片方は `src/**`・`.github/**`・`CLAUDE.md`・`deploy/**` が
> **1 件でも入ったら束ねられない**と明記している —— 本作業はその全項目を踏んでいる。
>
> **必要なのは、第 3 の限定例外を定める新しい実装 ADR と、その根拠となる利用者裁定である**
> （既存の例外を足したときも、裁定と新 ADR の両方を要した）。**それが無い間は、この運用は
> 記録された例外ではなく、記録された逸脱である。** 次に同じことをする人は、まず裁定を取ること。
>
> 代わりに置いた歯止め: **1 コミット = 1 issue = 1 論理変更**を守り、件名を `種別(起点ID): 要約`
> に揃えて**コミット単位で issue を追える**ようにした。監査も「束ねても監査の対象数は減らない」に
> 従い、コミット範囲を母集合として渡している。

> 🔴 **対象外と判定した 37 件は、着手のたびに引き直すこと。** 実測で引き直したところ
> **7 件が ACTIONABLE へ変わっていた** —— 同じセッションの着地がそれらの待ち条件を解いていたためである。
> **「前に見たときは対象外だった」は根拠にならない。** 待ち先が閉じた瞬間に対象は増える。

この作業で新たに分かった、**次に引き継ぐ人が踏みやすい 3 点**:

- **並行するサブエージェントの未コミット変更が、検査の測定値へ混ざる。** 特に共有ファイル
  （ロックファイル・`.slnx`・`Directory.*.props`・各種 baseline）は、**staging の前に中身を見る**。
  数値を baseline へ焼くときは**コミット済み状態だけを展開したクリーンな worktree で測る** ——
  混ざった数字を床にすると、後から誰も再現できない。
- **その worktree は submodule を引き継がない。** フロントのビルドは submodule のワークスペースを
  解決できずに落ちるので、測る前に初期化する。**落ちたのを「壊れている」と読み違えないこと。**
- **`git checkout` はローカル変更があると abort する。** 検証用 worktree で
  「新しいコミットを測ったつもりが、abort されて古い方を測っていた」を 1 度踏んだ。
  **切り替えた後に `git log -1` で、測る対象を目で確かめる。**

### ［2026-08-23］計画側の裁定 6 件への追随（**環流を出した側が追随を負う**）

同セッション中に起票した環流 6 件へ、**すべて裁定が下りて計画へマージされた**。
新設された計画 ADR は 3 本（`ADR-0056` / `ADR-0057` / `ADR-0058`）である。

🔴 **裁定を受け取ったら、まず宣言レンジを引き直すこと。**
`.claude/rules/traceability.repo.md` の宣言レンジは `check-commit-messages.js` と
`check-trace-blocks.js` が**実在性を fail-closed で検査する一次情報**であり、遅れたままだと
**新しい ADR を引いた瞬間に CI が理由の分かりにくい形で落ちる**。
**環流を出した側は、裁定がレンジを動かすことを起票の時点で予測できる**（別紙の世代記録も参照）。
検査器が教えるのは「踏んだこと」だけで、「遅れていること」は教えない。

🔴 **裁定文が書いた「実装の現状」を、そのまま真として受け取らないこと。**
`ADR-0056` は「実装側に一律の書き換えは生じない」と結論していたが、**実測すると前提が
成立していなかった**（対象 4 経路は読み取り認可を一度も評価していなかった）。
**計画側は実装リポジトリを直接読めないため、現状認識は環流に書かれたことだけで作られる。**
誤りの半分は起票側にあった —— 打ち分けの形は正しく書いたが、
**「何が評価されていないか」を書いていなかった**。

> **環流は「何がどう書かれているか」だけでなく「何が評価されていないか」まで書く。**
> 前者だけだと、計画側は「確かめたうえでそう選んだ」と読む。

### ［2026-08-28］全 open issue（72 件）一括対応（進行中・波方式）

**利用者の依頼で open issue 全件を波方式で消化中である。** 束ねは、**波単位の積み上げ PR を
第 3 の限定例外として認める実装 ADR を新設し、利用者裁定を根拠として記録したうえで**行っている
—— 2026-08-23 節の 🔴（記録された逸脱）は**この形で条文化して解消した**。条文の正はその実装 ADR、
判定・波割り・除外理由の正は統括の作業仕様書（層 a 相当・`.ai-context/specs/` の 2026-08-27 付）、
**生きた状態は GitHub（積み上げ PR と各 issue）が正**である。ここへ転記しない。

この運用で新たに実測した、引き継ぐ人が踏みやすい 3 点:

- **バックエンドの実走は「SDK が無い」ではなく「PATH に無い」ことがある。** §4.5 のとおり
  諦める前に実測する（本環境では導入済み SDK を PATH へ通すだけで build / test / format が全部動いた）。
- **`scripts.repo.test.js` は companion であり、単体起動では 1 件も検査せず fail する。**
  §4 の表のとおり `scripts.test.js` 経由（`REQUIRE_REPO_TESTS=1`）で走らせる。
- **コンテナ再起動でサブエージェントの worktree が消えることがある。** 成果はブランチに
  コミットさせておけば cherry-pick で回収できる（実測 2 回）。**未コミットの成果は消える。**

もう 1 つ、**この波で 2 度目に踏んだ罠**（型 1 の派生）:

- **「不変にする」を「その項目を送ってきたら拒否」と実装すると、正常系が全部壊れる。**
  文書の属性編集フォームは**既存属性をスプレッドして送る**ため、機密区分だけを変える保存でも
  `doc_scope` が同送される。**判定は「既存値と一致するか」で行う。**
  壊れ方は「機密区分が変えられない」という無関係な形で出るので、原因にたどり着きにくい。
  **陽性対照（同値の同送が通る）が無いと、この実装は陰性だけで緑になる。**

## 4. 検査器と、それが実際に走る経路

## 4.5 ★ 環境によって変わること —— **着手前に自分で実測する**

> **［2026-08-08 全面改稿 / #617］本節は従前「この実行環境でできないこと（実測）」という表題で、
> 環境固有の観測を恒久的な制約として書いていた。それが実害を出した** ——
> §2 は #554 / #556 / #562 の 3 件を「**AI だけでは完結しない**」として保留し、
> フェーズ B を打ち切る根拠にしていたが、**3 件とも別の環境では実施できた**（同日中に 3 件とも着地）。
> **「できない」と書かれた項目は、引き継ぐ人が実測せずに諦める。**
> したがって本節は**能力の一覧ではなく、実測の手順書**として書く。

**下の 4 つは環境ごとに違う。作業を諦める前に必ず自分で実測すること。所要は合計 5 分程度である。**

| 能力 | 実測コマンド | 使える場合の出力 | 使えない場合 |
| --- | --- | --- | --- |
| **`gh` CLI** | `gh auth status` | `✓ Logged in to github.com` | コマンドが無い／未認証 → MCP ツール（`mcp__github__*`）を使う |
| **`.github/workflows/` の編集** | `gh` が在れば `gh auth status`（Token scopes の行）。**`gh` が無い環境では、捨てブランチでワークフローを 1 行変えて `git push` してみる**（下記） | scopes に **`workflow`** が在る ／ push が通る | 拒否される → 結線は人手へ渡す |
| **submodule の populate** | `git submodule update --init src/ai-stock-trading planning` | `Submodule path ...: checked out` | 認証エラー → フロントの `build` / E2E と計画 ADR の実在性検査が不可 |
| **フロントの `build` / E2E** | 上の populate 後に `pnpm run build` ／ `pnpm run test:e2e` | ビルド成功 ／ **全件 passed（failed 0）** | `@ai-stock-trading/features` が `error TS2307`（＝populate に失敗している） |

> **`gh` が無い環境での workflow スコープの測り方**（上表 2 行目）:
> 2 行目の実測は 1 行目の結果に依存するため、`gh` が無いと測れないままになる。その場合は
> **捨てブランチで実際に押してみるのが唯一の確実な判定**である（拒否は push の時点で起きる）。
> ```
> git switch -c probe/workflow-scope
> printf '\n' >> .github/workflows/frontend.yml && git commit -am "chore(NFR): probe" && git push -u origin probe/workflow-scope
> ```
> **通れば scope が在る**。確認後はリモートのブランチを消し、コミットは捨てる
> （`git switch -` で元へ戻る。**force push は使わない**）。

- **`pnpm` が PATH に無いことがある**（Volta の shim が壊れている等）。その場合は
  `npx --yes pnpm@<package.json の packageManager の版> …` で代用できる（実測）。
- **Playwright のブラウザは初回だけ取得が要る**:
  `pnpm --filter @platform/frontend exec playwright install --with-deps chromium`。

> **`build` と E2E が動くかどうかは「変異試験ができるか」を決める。**
> このリポジトリの issue は「**壊すと落ちることを実測せよ**」を頻繁に要求する（§5 型 4）ので、
> ここが動くかで**着手可否そのものが変わる**。だからこそ諦める前に測る。

**環境に依らない制約は §3 に書いてある。** 本節と混同しないこと ——
§3（履歴不変・`planning/` は pin のみ・`src/ai-stock-trading` を変更しない）は
**どの環境でも破らない**。本節は**測れば変わりうる**。

### ★★ 一度「できない」と書いた判定は、棚卸しのたびに測り直す

**判定は環境に依り、環境は変わる。したがって判定には賞味期限がある。**

  フェーズ C〜H の表は波の表へ差し替わり、**環境依存で保留していた issue は波 5 に入った**。

- **測り直して覆ったら、§2 の波を動かし、覆った事実を層 a へ残す**（消さない。**§5 型 8 の実例になる**）。

> **★ 根拠は #617 の実測である。** §2 は #554 / #556 / #562 の 3 件を

## 5. ★ このリポジトリで繰り返し起きる事故の型（9 型）

**新しい失敗はほとんど無い。同じ型が名前を変えて再発している。** 着手前にここを読むこと。

### 型 1: 母集合を引き直さない

**issue 本文の一覧・監査の一覧・前の PR の表は、いずれも母集合ではない。**
規則は `.claude/rules/traceability.md`「是正・追随の母集合の取り方」（キット・規則 1〜8）と `traceability.repo.md`（本リポ固有・規則 9・10）が正。
**破れた実例は、規則 1〜6 がクロス監査の実装 ADR の決定 1、規則 9・10（旧 7・8）が別紙 [`population-drawing-annex.md`](./population-drawing-annex.md)**（#730 で入口から外した。#755 で改番）。

**本セッションで新たに踏んだ形**:
- **`grep -l`（ファイル一覧）を母集合にした** —— #555 では 23 ファイルが該当するように見えたが、
  行まで見ると**是正対象は 0 件**（差はすべて経緯を述べたコメント）だった。
- **走査式の設計が結論を決めている** —— #609 は「`OK: 461 件` は 461 ファイルを見たと言っているが、
  **各ファイルのどのリンクを見たかは言っていない**」という形で 248 件が無検査だった。
  **「走査式が返さなかった」は「存在しない」を意味しない。**
- **［2026-08-23］検証を通した後に、自分でコードを足して検証を無効にした** —— 検査器一式を走らせて
  緑を確認し、**その後で入口チャンクへ数百バイト足し、予算の検査だけ引き直さなかった**。
  ビルドは通るので手元では気付かず、CI が落ちて初めて分かった。
  **母集合が動くのは他人の変更のときだけではない。自分の次の一手でも動く。**
  規則 7 の「数値を 1 つ直したら引き直す」は、**自分が動かした数値にも掛かる。**

### 型 2: 呼び出し口を 1 つだけ配線する（**本セッションで 3 度目**）

関数の引数を増やしたとき、**呼び出し口のうち 1 つにしか渡さない**。

| 回 | 何が起きたか |
| --- | --- |
| #507 | `crossRepoRefReasons` のラベル表に kind を 1 つ足し忘れ、CI が「未知の違反種別」を出した |
| #590 | **同じ表で同じ omission を再発**（型 4 を足したとき） |
| #612 | `validateIdExistence` の第 4 引数を `--title` 経路にだけ渡し、**CI の必須チェックが実行するレンジモードで無効**だった |

**対策**: **引数を増やしたら `grep -n '<関数名>(' ` で呼び出し口を全部出してから配線する。**
そして**経路ごとに実バイナリで当てる** —— #612 では `--title` の変異試験だけが通ったので
「検査が効いている」と誤って結論した。

### 型 3: 同じ数・同じ言明を 2 箇所に持つ

条文へ実測値を埋めると、**正例を 1 つ足しただけで黙って古くなる**。
**数は作業仕様書の §母集合 を正とし、条文・スクリプト・PR 本文へ書かない。**
（#590 が実際に踏み、その教訓を書いた `traceability.md` の行が**すでに古かった**）。

### 型 4: 変異試験をしていない検査を信用する

**「壊すと落ちる」を実測していない検査は、入れたのに効いていないことがある。**

本セッションの実例（いずれも自分で作って自分で踏んだ）:
- **`check-landed-subjects.js`**: baseline へ存在しないハッシュを**1 行足すだけで検査全体が緑**になった。
  「浅いクローン（skip）」と「履歴は完全なのに解決できない（fail）」を割って塞いだ。
- **`changelog-overrides.json`**: JSON の要素境界を誤り、**隣のエントリの説明文が別のコミット行に載った**。
  **構文が通ることは意味が通ることを保証しない。生成物を実際に作って目で見る。**

### 型 5: 開示を検査の代わりにする

**「この型は検出できないと書いた」は「検出できなくてよい」ではない。**
ただし**偽陽性は必ず塞ぐ**（検出漏れは開示してよいが、偽陽性は他人の PR を止める）。

**書けないことは書けないと明記する**のは正しい。実例は、着地件名の検査範囲を定めた実装 ADR の決定 3
（**PR タイトルからの ID 脱落は機械では判定できない** —— 落ちた後の件名は規約適合であり、
判定には PR タイトルとの突合が要るが、PR タイトルはリポジトリの中に無い）。

### 型 6: flat config / 設定ファイルの後勝ち置換

ESLint flat config は**同一ルールを後勝ちで置換する**。新しい禁止を足すつもりで
**既存の禁止を丸ごと無効化する**。`src/eslint.config.js` の冒頭が自ら警告している。
**新しいブロックを足す前に、既存ブロックへ 1 行足せないかを見る。**

### 型 7: **条文が片側しか書いていない**（そして書いた本人が逆側を踏む）

**フェーズ末クロス監査が出した 🔴 がこれである。**

#612 は「**スカッシュ件名から ID を落とすな**」という検査と条文を入れた PR だった。
**その同じ PR の着地件名が、実体を伴わない ID を足していた**
（`feat(NFR,FR-12,SC-07,IADR-0145)`。スコープに挙げた要求・画面の成果物は 1 つも触っていない）。

**条文は「落とすな」しか書いておらず、「足すな」が無かった。**
**穴を作った条文を書いた PR 自身が、その穴を踏んだ。**

しかも**先例は既にあった** —— #596 は同じ「remap で他コミットの記録を是正する」作業で、
対象の scope を継承せず自分の起点を名乗っている。**規約に無いだけで、作法は存在していた。**

- **禁止を書いたら、その逆向きも書けるか考える**（落とす／足す・広げる／狭める・消す／複製する）。
- **既存の似た作業を 1 つ探して、自分がその作法に従っているか確かめる。**
- **機械では捕まらない**——検査は「実在するか」しか見ないので、**落とした ID も足した ID も通る**。

### 型 8: 「できない」と「やると害の方が大きい」を混ぜる

着地件名の検査範囲を定めた実装 ADR の決定 3 へ「この事故は**機械では検出できない**」と 3 箇所書いたが、**実測すると過大だった**
（変更パス由来の ID 判定で着地件名 319 件中 26 件ヒットし、実際の事故を含む。**走査基準: develop `2cd8508` 時点**）。

正しくは「**PR タイトルとの突合はできない**」＋「**パス由来は可能だが偽陽性 25/26 で方向が合わない**」。
**後者の言い方は同じ規約が別の箇所で既に採っていた**（近傍規則の偽陽性）。

**「できない」は検証されると崩れる。「やると害の方が大きい」は実測で支えられる。**
**限界を書くときは、どちらなのかを確かめてから書く。**

> **［2026-08-08 追記 / #617］第 3 の形: 「この環境でできない」を「できない」と書く。**
>
> **型 9 として独立させず、ここへ畳む** —— 型 8 は「限界の言明を誤る」型そのものであり、
> 分けると**同じ教訓を 2 箇所に持つ**（型 3）ことになるためである。
>
> 旧 §4.5 は「**この実行環境でできないこと（実測）**」という表題で、
> `build` が通らない・`workflow` スコープが無いという**環境固有の観測**を書いていた。
> 観測自体は正しい。**誤りは、それを恒久的な制約の側（陳腐化しにくい節）へ置いたこと**である。
> §2 には「必ず古くなる」と但し書きがあったが、**§4.5 には無かった。**
>
> **実害**: #554 / #556 / #562 の 3 件が「**AI だけでは完結しない**」として保留され、
> フェーズ B が打ち切られた。**別環境では 3 件とも実施でき、同日中に着地した。**
>
> - **能力の言明には、必ず「どう実測するか」を添える**（旧 §4.5 には実測コマンドが無かった）。
> - **環境に依る制約と、リポジトリの制約を同じ表に混ぜない**（前者は §4.5・後者は §3）。
> - **「できない」と書かれているものを見たら、まず自分で実測する。**

### 型 9: **パターンの射程を、意図ではなく実際の一致で確かめない**

［2026-08-28 追記 / PR #1021］**書いたパターンが「自分が意図した範囲」より広く一致する。**
本セッションで 3 度踏んだ。いずれも**書いた本人には正しく見えていた**。

**① `src/*` は submodule に届く（最も危険だった）**

アーキ移送波の後片付けで、こう回した:

```
for s in <14 サービス名>; do rm -rf src/*/backend/Services/$s/src src/*/backend/Services/$s/tests; done
```

意図は「自分が持つ 2 ユニット（`src/knowledge` と `src/platform`）」だった。
実際の `src/*` は **`src/ai-stock-trading`（別プロジェクトの submodule）にも一致する**。
AST 自身の `NotificationService` は旧 8 要素配置のままなので `.../NotificationService/src` が実在し、
**67 ファイルを削除した。** gitlink は動いておらず、コミット前に気付いて復元したが、
**あと 1 コマンドでコミットしていた。**

- **気付けたのは stop hook が「未コミットの変更がある」と言い、それを commit せずに中身を見たから。**
  **警告に対して「じゃあコミットしよう」と反応していたら、他人のリポジトリの削除を push していた。**
- **教訓: 破壊的操作の対象は列挙する。** 「自分が持つ 2 つ」を意図しているなら
  `src/knowledge` と `src/platform` と書く。**`src/*` は「`src/` の下の全部」であり、
  その中には他人のリポジトリが在る。**

**② `\([^)]*\)` はコミットメッセージの括弧で早く閉じる**

cherry-pick の衝突マーカーを消す正規表現で `>>>>>>> <sha> \(<件名>\)` を書いたが、
本リポジトリの件名は `refactor(NFR,IADR-0282): …` と**括弧を含む**ため `[^)]*` が途中で止まり、
**置換が 0 件成功のまま「解決した」と表示された。** その状態で `git add` したので、
**衝突マーカーがコミットに入った**（次のコミットで気付いて amend）。

- **教訓: 「何件置換したか」を数えて、期待と突き合わせる。** 0 件なら失敗である。

**③ `git grep -l '\.Api\.'` は `.Worker.Composable` を拾わない**

移送で古くなった文字列を掃除するとき、検索語を `.Api.` に絞ったため
`IngestionService.Worker.Composable.Steps.…` が母集合から落ちた。
**型 1（母集合）と同じ病だが、こちらは「絞り込みの語が狭すぎた」形である。**

> **3 つに共通するのは「パターンを書いた時点の頭の中の範囲」と「実際に一致する範囲」の差**である。
> **書いたら、まず一致した集合そのものを見る**（`grep` なら結果を、`rm` なら `echo` に置き換えて、
> 置換なら件数を）。**実行してから確かめるのでは、破壊的操作には間に合わない。**
