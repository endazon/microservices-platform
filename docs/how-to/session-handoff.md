# 引継資料 — issue 消化フェーズ運用の現在地

> **この文書の位置づけ**: 全面再実装（#454）の issue 消化を引き継ぐ人／AI が、**最初に読む 1 枚**である。
> 規約の正は `CLAUDE.md` と `.claude/rules/traceability.md`、決定の正は `docs/adr/` にある。
> **ここへ規約や決定を転記しない** —— 転記すると正が動いたとき黙って腐る（[[IADR-0141]]「参照点を 1 つに畳む」）。
> 本書が持つのは**現在地と、繰り返し起きている事故の型**だけである。

## 1. 進め方（利用者裁定・2026-08-08）

| 事項 | 決まっていること |
| --- | --- |
| **フェーズ** | **複数の issue をまとめて処理する作業のまとまり**。1〜2 件に細かく割らない |
| **PR** | **束ねない。1 issue = 1 PR**（[[IADR-0116]] 規約 1。変更なし）。**例外は [[IADR-0139]] 決定 1 の 6 条件をすべて満たす同型の契約追加だけ**（資源単位。**上限の値はここに書かない** —— 正は下記の 2 つで、写すと片方が腐る。実際に腐った: #791 で 2 件 → 4 件へ改まったとき、本行だけが取り残された）——［2026-08-08 追記 / フェーズ末クロス監査］#624 が上流ガイドを写した際に条件を落として一般化し、本行と真逆に読める状態になったため、両側から同じ範囲を指すよう明示した。正は `CLAUDE.md` の該当行と [[IADR-0139]] |
| **クロス監査** | **フェーズ末に 1 回**（`adr-guardian` ＋ `traceability-auditor`）。**PR ごとには走らせない**。条文は [[IADR-0141]] 決定 4 の 2026-08-08 追記 |
| **フェーズ内** | **並行してよい**。ただし同じファイルを触る issue は直列にする（下記 §5） |
| **マージ** | **レビュー指摘がすべて対応済みだと確認できたら可**。承認待ちは不要 |

> **引き継ぐ人にとって価値があるのは §5 であって §2 ではない。**

## 3. 絶対に破らない制約

- **`force push` / `reset --hard` / `rm -rf` を使わない**（hooks が実際にブロックする）。
  履歴は不変。誤記の是正は `scripts/changelog-overrides.json` の `remap`（**生成物のみ**）。
- **`planning/` は pin 更新のみ**。計画書そのものを本リポから書き換えない。
- **`src/ai-stock-trading` を変更しない**（別プロジェクトの submodule）。
- **作業仕様書（`docs/specs/`）なしで実装へ着手しない。**
- **モデル ID をコミット・PR・コード・文書へ書かない。**
- **サブエージェントに push させない**（親が監査してから push する。**本セッションで 1 度破られた**）。
- **コミット前に `git status` の削除（`D`）を確認する。**

> **［2026-08-08 / #617］「`.github/workflows/` は編集できない」を本節から外し、§4.5 へ移した。**
> 従前ここには「**GitHub App 権限で編集できない**。新しい検査は既存の呼び出し口へ相乗りさせる」
> という項があったが、**それは認証に依る観測であって、どの環境でも破らない制約ではない**
> （`workflow` スコープを持つローカル認証では編集できる。**`CLAUDE.md` は #163 以来この形で書いている**
> —— 「GitHub App 権限では編集不可。ワークフロー変更はローカルの `workflow` スコープでコミット/プッシュする」。
> **断定を落として片側だけ写したのが本書だった。**）。
> **本節に置いたままだと、引き継ぐ人が実測せずに結線を諦める** —— #562 で実際にそうなった（§5 型 8）。
> 能力の判定は §4.5 の表 2 行目で実測する。**編集できない環境での回避策（既存の呼び出し口への相乗り）は
> [[IADR-0140]] 決定 2 のとおりで、既存の結線は §4 の表にある。**

## 4. 検査器と、それが実際に走る経路

**既存の検査は、`.github/workflows/` を編集できない環境で作られたため既存ジョブへ相乗りしている**
（[[IADR-0140]] 決定 2）。**この相乗りは既存の結線の由来であって、新しい検査への制約ではない** ——
編集できる環境なら新しいジョブを足してよい（#562 が実際に `frontend.yml` へ足した）。
まず §4.5 で実測すること。「検査器を作った」と「CI で走る」は別である。

| 検査器 | 走る経路 |
| --- | --- |
| `check-doc-links.js` | `ci.yml` の `doc-links` |
| `check-commit-messages.js` | `ci.yml` の `commit-messages`（**レンジモード**）／`pr-title.yml`（**`--title` モード**） |
| `check-cross-repo-refs.js` | 上記 `check-commit-messages.js` 経由 ＋ 単独 |
| `check-plan-id-qualification.js` / `check-adr-numbering.js` / `check-landed-subjects.js` / `check-i18n-catalogs.js` / `check-test-spec-coverage.js` | **`scripts/scripts.repo.test.js` 経由**で `ci.yml` の `scripts-tests`（`REQUIRE_REPO_TESTS=1 node scripts/scripts.test.js`） |
| ESLint（`src/eslint.config.js`） | `frontend.yml` の `lint` |

- **`scripts/scripts.test.js` は分類 A（変更禁止・キットとバイト一致）である。**
  **テストを足すときは必ず companion の `scripts.repo.test.js`** へ書く。
  この行は 2 度動いた —— #790 で「拡張点を埋めた配布先では原理的に通らない」試験があったため
  分類 B（X・期限つきの暫定）へ落ち、**#836 で環流 planning#380 が着地して A へ戻った**
  （[[IADR-0204]] 決定 4）。**次に赤くなったら、まず「キットが配布先の構成を断定していないか」を疑う。**
- **計画 ADR（`ADR-xxxx`）の実在性は CI で守られていない**（どの決定的ジョブも submodule を populate しない）。

## 4.5 ★ 環境によって変わること —— **着手前に自分で実測する**

> **［2026-08-08 全面改稿 / #617］本節は従前「この実行環境でできないこと（実測）」という表題で、
> 環境固有の観測を恒久的な制約として書いていた。それが実害を出した** ——
> §2 は #554 / #556 / #562 の 3 件を「**AI だけでは完結しない**」として保留し、
> フェーズ B を打ち切る根拠にしていたが、**3 件とも別の環境では実施できた**（同日中に 3 件とも着地）。
> **「できない」と書かれた項目は、引き継ぐ人が実測せずに諦める。**
> したがって本節は**能力の一覧ではなく、実測の手順書**として書く。

**下の 4 つは環境ごとに違う。作業を諦める前に必ず自分で実測すること。所要は合計 5 分程度である。**

| 能力 | 実測コマンド | 使える場合の出力 | 使えない場合 |
| --- | --- | --- | --- |
| **`gh` CLI** | `gh auth status` | `✓ Logged in to github.com` | コマンドが無い／未認証 → MCP ツール（`mcp__github__*`）を使う |
| **`.github/workflows/` の編集** | `gh` が在れば `gh auth status`（Token scopes の行）。**`gh` が無い環境では、捨てブランチでワークフローを 1 行変えて `git push` してみる**（下記） | scopes に **`workflow`** が在る ／ push が通る | 拒否される → 結線は人手へ渡す |
| **submodule の populate** | `git submodule update --init src/ai-stock-trading planning` | `Submodule path ...: checked out` | 認証エラー → フロントの `build` / E2E と計画 ADR の実在性検査が不可 |
| **フロントの `build` / E2E** | 上の populate 後に `pnpm run build` ／ `pnpm run test:e2e` | ビルド成功 ／ **全件 passed（failed 0）** | `@ai-stock-trading/features` が `error TS2307`（＝populate に失敗している） |

> **`gh` が無い環境での workflow スコープの測り方**（上表 2 行目）:
> 2 行目の実測は 1 行目の結果に依存するため、`gh` が無いと測れないままになる。その場合は
> **捨てブランチで実際に押してみるのが唯一の確実な判定**である（拒否は push の時点で起きる）。
> ```
> git switch -c probe/workflow-scope
> printf '\n' >> .github/workflows/frontend.yml && git commit -am "chore(NFR): probe" && git push -u origin probe/workflow-scope
> ```
> **通れば scope が在る**。確認後はリモートのブランチを消し、コミットは捨てる
> （`git switch -` で元へ戻る。**force push は使わない**）。

- **`pnpm` が PATH に無いことがある**（Volta の shim が壊れている等）。その場合は
  `npx --yes pnpm@<package.json の packageManager の版> …` で代用できる（実測）。
- **Playwright のブラウザは初回だけ取得が要る**:
  `pnpm --filter @platform/frontend exec playwright install --with-deps chromium`。

> **`build` と E2E が動くかどうかは「変異試験ができるか」を決める。**
> このリポジトリの issue は「**壊すと落ちることを実測せよ**」を頻繁に要求する（§5 型 4）ので、
> ここが動くかで**着手可否そのものが変わる**。だからこそ諦める前に測る。

**環境に依らない制約は §3 に書いてある。** 本節と混同しないこと ——
§3（履歴不変・`planning/` は pin のみ・`src/ai-stock-trading` を変更しない）は
**どの環境でも破らない**。本節は**測れば変わりうる**。

### ★★ 一度「できない」と書いた判定は、棚卸しのたびに測り直す（#701）

**判定は環境に依り、環境は変わる。したがって判定には賞味期限がある。**

- **棚卸し（引き継ぎ・フェーズ末監査）のたびに、§2 の波 5 に置かれている issue を上表の手順で測り直す。**
  **「前回できなかった」を根拠に据え置かない。**
  ［2026-08-16 追記 / #454］**従前ここは「§2 の行 H」と書いていた。** 行 H を含む
  フェーズ C〜H の表は波の表へ差し替わり、**環境依存で保留していた issue は波 5 に入った**。
- **判定には「最後に測った時点」を必ず添える**（日付 ＋ 起票 ID）。
  **時点の無い判定は、再検証すべきかどうかを判断できない。**
  **時点と根拠を書く先は §2 ではなく棚卸しの作業仕様書（層 a）である** —— §2 は順序しか持たない。
- **測り直して覆ったら、§2 の波を動かし、覆った事実を層 a へ残す**（消さない。**§5 型 8 の実例になる**）。

> **★ 根拠は #617 の実測である。** §2 は #554 / #556 / #562 の 3 件を
> 「**AI だけでは完結しない**」として保留し、**フェーズ B を打ち切る根拠にしていた**が、
> **3 件とも別の環境では実施でき、同日中に着地した。**
> **「書くとき」の誤りは §5 型 8 が覆う。本項が覆うのは「書いた後、据え置かれること」である。**

> **★ 機械検査は置いていない。** 「環境固有の観測か恒久制約か」は**意味の理解が要り、
> 文字列一致では判定できない**（本リポが `AST` の近傍規則で既に採っている言い方と同じ）。
> **人と AI が守る。**

## 5. ★ このリポジトリで繰り返し起きる事故の型（8 型）

**新しい失敗はほとんど無い。同じ型が名前を変えて再発している。** 着手前にここを読むこと。

### 型 1: 母集合を引き直さない

**issue 本文の一覧・監査の一覧・前の PR の表は、いずれも母集合ではない。**
規則は `.claude/rules/traceability.md`「是正・追随の母集合の取り方」（キット・規則 1〜8）と `traceability.repo.md`（本リポ固有・規則 9・10）が正。**破れた実例は規則 1〜6 が [[IADR-0141]] 決定 1、規則 9・10（旧 7・8）が別紙 [`population-drawing-annex.md`](./population-drawing-annex.md)**（#730 で入口から外した。#755 で改番）。

**本セッションで新たに踏んだ形**:
- **`grep -l`（ファイル一覧）を母集合にした** —— #555 では 23 ファイルが該当するように見えたが、
  行まで見ると**是正対象は 0 件**（差はすべて経緯を述べたコメント）だった。
- **走査式の設計が結論を決めている** —— #609 は「`OK: 461 件` は 461 ファイルを見たと言っているが、
  **各ファイルのどのリンクを見たかは言っていない**」という形で 248 件が無検査だった。
  **「走査式が返さなかった」は「存在しない」を意味しない。**

### 型 2: 呼び出し口を 1 つだけ配線する（**本セッションで 3 度目**）

関数の引数を増やしたとき、**呼び出し口のうち 1 つにしか渡さない**。

| 回 | 何が起きたか |
| --- | --- |
| #507 | `crossRepoRefReasons` のラベル表に kind を 1 つ足し忘れ、CI が「未知の違反種別」を出した |
| #590 | **同じ表で同じ omission を再発**（型 4 を足したとき） |
| #612 | `validateIdExistence` の第 4 引数を `--title` 経路にだけ渡し、**CI の必須チェックが実行するレンジモードで無効**だった |

**対策**: **引数を増やしたら `grep -n '<関数名>(' ` で呼び出し口を全部出してから配線する。**
そして**経路ごとに実バイナリで当てる** —— #612 では `--title` の変異試験だけが通ったので
「検査が効いている」と誤って結論した。

### 型 3: 同じ数・同じ言明を 2 箇所に持つ

条文へ実測値を埋めると、**正例を 1 つ足しただけで黙って古くなる**。
**数は作業仕様書の §母集合 を正とし、条文・スクリプト・PR 本文へ書かない。**
（#590 が実際に踏み、その教訓を書いた `traceability.md` の行が**すでに古かった**）。

### 型 4: 変異試験をしていない検査を信用する

**「壊すと落ちる」を実測していない検査は、入れたのに効いていないことがある。**

本セッションの実例（いずれも自分で作って自分で踏んだ）:
- **`check-landed-subjects.js`**: baseline へ存在しないハッシュを**1 行足すだけで検査全体が緑**になった。
  「浅いクローン（skip）」と「履歴は完全なのに解決できない（fail）」を割って塞いだ。
- **`changelog-overrides.json`**: JSON の要素境界を誤り、**隣のエントリの説明文が別のコミット行に載った**。
  **構文が通ることは意味が通ることを保証しない。生成物を実際に作って目で見る。**

### 型 5: 開示を検査の代わりにする

**「この型は検出できないと書いた」は「検出できなくてよい」ではない。**
ただし**偽陽性は必ず塞ぐ**（検出漏れは開示してよいが、偽陽性は他人の PR を止める）。

**書けないことは書けないと明記する**のは正しい。実例は [[IADR-0145]] 決定 3
（**PR タイトルからの ID 脱落は機械では判定できない** —— 落ちた後の件名は規約適合であり、
判定には PR タイトルとの突合が要るが、PR タイトルはリポジトリの中に無い）。

### 型 6: flat config / 設定ファイルの後勝ち置換

ESLint flat config は**同一ルールを後勝ちで置換する**。新しい禁止を足すつもりで
**既存の禁止を丸ごと無効化する**。`src/eslint.config.js` の冒頭が自ら警告している。
**新しいブロックを足す前に、既存ブロックへ 1 行足せないかを見る。**

### 型 7: **条文が片側しか書いていない**（そして書いた本人が逆側を踏む）

**フェーズ末クロス監査が出した 🔴 がこれである。**

#612 は「**スカッシュ件名から ID を落とすな**」という検査と条文を入れた PR だった。
**その同じ PR の着地件名が、実体を伴わない ID を足していた**
（`feat(NFR,FR-12,SC-07,IADR-0145)`。FR-12 / SC-07 の成果物は 1 つも触っていない）。

**条文は「落とすな」しか書いておらず、「足すな」が無かった。**
**穴を作った条文を書いた PR 自身が、その穴を踏んだ。**

しかも**先例は既にあった** —— #596 は同じ「remap で他コミットの記録を是正する」作業で、
対象の scope を継承せず自分の起点を名乗っている。**規約に無いだけで、作法は存在していた。**

- **禁止を書いたら、その逆向きも書けるか考える**（落とす／足す・広げる／狭める・消す／複製する）。
- **既存の似た作業を 1 つ探して、自分がその作法に従っているか確かめる。**
- **機械では捕まらない**——検査は「実在するか」しか見ないので、**落とした ID も足した ID も通る**。

### 型 8: 「できない」と「やると害の方が大きい」を混ぜる

[[IADR-0145]] 決定 3 へ「この事故は**機械では検出できない**」と 3 箇所書いたが、**実測すると過大だった**
（変更パス由来の ID 判定で着地件名 319 件中 26 件ヒットし、実際の事故を含む。**走査基準: develop `2cd8508` 時点**）。

正しくは「**PR タイトルとの突合はできない**」＋「**パス由来は可能だが偽陽性 25/26 で方向が合わない**」。
**後者の言い方は同じ規約が別の箇所で既に採っていた**（近傍規則の偽陽性）。

**「できない」は検証されると崩れる。「やると害の方が大きい」は実測で支えられる。**
**限界を書くときは、どちらなのかを確かめてから書く。**

> **［2026-08-08 追記 / #617］第 3 の形: 「この環境でできない」を「できない」と書く。**
>
> **型 9 として独立させず、ここへ畳む** —— 型 8 は「限界の言明を誤る」型そのものであり、
> 分けると**同じ教訓を 2 箇所に持つ**（型 3）ことになるためである。
>
> 旧 §4.5 は「**この実行環境でできないこと（実測）**」という表題で、
> `build` が通らない・`workflow` スコープが無いという**環境固有の観測**を書いていた。
> 観測自体は正しい。**誤りは、それを恒久的な制約の側（陳腐化しにくい節）へ置いたこと**である。
> §2 には「必ず古くなる」と但し書きがあったが、**§4.5 には無かった。**
>
> **実害**: #554 / #556 / #562 の 3 件が「**AI だけでは完結しない**」として保留され、
> フェーズ B が打ち切られた。**別環境では 3 件とも実施でき、同日中に着地した。**
>
> - **能力の言明には、必ず「どう実測するか」を添える**（旧 §4.5 には実測コマンドが無かった）。
> - **環境に依る制約と、リポジトリの制約を同じ表に混ぜない**（前者は §4.5・後者は §3）。
> - **「できない」と書かれているものを見たら、まず自分で実測する。**

## 7. 引き継いだ人が最初にやること

1. **§4.5 の 4 つを実測して、自分の環境の能力を確かめる**（5 分）。
   **ここを飛ばして「できない」と書かれた項目を鵜呑みにしないこと** —— それで
   フェーズ B が一度打ち切られた（§5 型 8 の第 3 の形）。
   `gh` が使えない環境なら GitHub 操作は MCP ツール（`mcp__github__*`）を使う。
2. **`develop` を貼り直して健全性を見る**（§4 の検査器を一通り走らせる）。
   `git checkout -B develop origin/develop` —— **クローンが shallow の場合**、
   `git merge --ff-only` が「refusing to merge unrelated histories」を出すことがあるが**異常ではない**
   （full clone なら通常どおり ff-merge できる。これも環境による）。
3. **フェーズ末クロス監査の指摘が残っていれば消化する。**
   **★ 実施済みかどうかは §2 ではなく `docs/specs/` の監査是正仕様書で確かめること**
   （フェーズ A = `20260808_phaseA-audit-followup.md`、フェーズ B = `20260808_phaseB-audit-followup.md`）。
   ［2026-08-08 追記 / フェーズ末クロス監査］**従前ここは「フェーズ A・B の監査は実施済み」と断定していたが、
   B は当時まだ未実施だった。** 完了宣言を「陳腐化しにくい」とされた本節に置いたのが誤りである
   —— **状態は §2 と同じく必ず古くなる。**
4. **§2 の波の並びに従い、未消化の最小の波から進む。**
   **どの波まで終わったかは GitHub と層 a で確かめる** —— **ここへ「次は波 N」と書かない**。
   旧版は手順 4 に「フェーズ C（#532 …）へ進む」と番号を書き、**その 7 件が全部閉じた後も残っていた**。
5. **波 5（XL 群）は、層 a の着手ゲート（3 条件）を自分で確かめてから。**
   **利用者の方針決定が先**であり、**子 issue は起票しない**（番号を増やしても消化は進まない）。
   ［2026-08-16 追記 / #778］**「起票しない」には層 a §8 が覆る条件を付している** ——
   **ゲートが開いて実際に着手する issue は、その時に分割してよい**（[[IADR-0116]] 規約 4）。
   #442 はこれに当たり、子 5 件へ分割した。**開いていない issue を先回りして割らないこと**が禁止の中身である。
