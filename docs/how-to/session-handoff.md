# 引継資料 — issue 消化フェーズ運用の現在地

> **この文書の位置づけ**: 全面再実装（#454）の issue 消化を引き継ぐ人／AI が、**最初に読む 1 枚**である。
> 規約の正は `CLAUDE.md` と `.claude/rules/traceability.md`、決定の正は `docs/adr/` にある。
> **ここへ規約や決定を転記しない** —— 転記すると正が動いたとき黙って腐る（[[IADR-0141]]「参照点を 1 つに畳む」）。
> 本書が持つのは**現在地と、繰り返し起きている事故の型**だけである。

## 1. 進め方（利用者裁定・2026-08-08）

| 事項 | 決まっていること |
| --- | --- |
| **フェーズ** | **複数の issue をまとめて処理する作業のまとまり**。1〜2 件に細かく割らない |
| **PR** | **束ねない。1 issue = 1 PR**（[[IADR-0116]] 規約 1。変更なし） |
| **クロス監査** | **フェーズ末に 1 回**（`adr-guardian` ＋ `traceability-auditor`）。**PR ごとには走らせない**。条文は [[IADR-0141]] 決定 4 の 2026-08-08 追記 |
| **フェーズ内** | **並行してよい**。ただし同じファイルを触る issue は直列にする（下記 §5） |
| **マージ** | **レビュー指摘がすべて対応済みだと確認できたら可**。承認待ちは不要 |

## 3. 絶対に破らない制約

- **`force push` / `reset --hard` / `rm -rf` を使わない**（hooks が実際にブロックする）。
  履歴は不変。誤記の是正は `scripts/changelog-overrides.json` の `remap`（**生成物のみ**）。
- **`planning/` は pin 更新のみ**。計画書そのものを本リポから書き換えない。
- **`src/ai-stock-trading` を変更しない**（別プロジェクトの submodule）。
- **`.github/workflows/` は GitHub App 権限で編集できない。** 新しい検査は
  **既存の呼び出し口へ相乗りさせる**（[[IADR-0140]] 決定 2）。経路は §4 の表。
- **作業仕様書（`docs/specs/`）なしで実装へ着手しない。**
- **モデル ID をコミット・PR・コード・文書へ書かない。**
- **サブエージェントに push させない**（親が監査してから push する。**本セッションで 1 度破られた**）。
- **コミット前に `git status` の削除（`D`）を確認する。**

## 4. 検査器と、それが実際に走る経路

**`.github/workflows/` を編集できないため、検査は既存ジョブへ相乗りしている。**
「検査器を作った」と「CI で走る」は別である。

| 検査器 | 走る経路 |
| --- | --- |
| `check-doc-links.js` | `ci.yml` の `doc-links` |
| `check-commit-messages.js` | `ci.yml` の `commit-messages`（**レンジモード**）／`pr-title.yml`（**`--title` モード**） |
| `check-cross-repo-refs.js` | 上記 `check-commit-messages.js` 経由 ＋ 単独 |
| `check-plan-id-qualification.js` / `check-adr-numbering.js` / `check-landed-subjects.js` / `check-i18n-catalogs.js` / `check-test-spec-coverage.js` | **`scripts/scripts.repo.test.js` 経由**で `ci.yml` の `scripts-tests`（`REQUIRE_REPO_TESTS=1 node scripts/scripts.test.js`） |
| ESLint（`src/eslint.config.js`） | `frontend.yml` の `lint` |

- **`scripts/scripts.test.js` は変更禁止**（[[IADR-0115]] 分類 A・キットとバイト一致）。
  テストを足すときは **companion の `scripts.repo.test.js`** へ書く。
- **計画 ADR（`ADR-xxxx`）の実在性は CI で守られていない**（どの決定的ジョブも submodule を populate しない）。

## 5. ★ このリポジトリで繰り返し起きる事故の型

**新しい失敗はほとんど無い。同じ型が名前を変えて再発している。** 着手前にここを読むこと。

### 型 1: 母集合を引き直さない

**issue 本文の一覧・監査の一覧・前の PR の表は、いずれも母集合ではない。**
規則と破れた実例は [[IADR-0141]] 決定 1 と `.claude/rules/traceability.md`「是正・追随の母集合の取り方」が正。

**本セッションで新たに踏んだ形**:
- **`grep -l`（ファイル一覧）を母集合にした** —— #555 では 23 ファイルが該当するように見えたが、
  行まで見ると**是正対象は 0 件**（差はすべて経緯を述べたコメント）だった。
- **走査式の設計が結論を決めている** —— #609 は「`OK: 461 件` は 461 ファイルを見たと言っているが、
  **各ファイルのどのリンクを見たかは言っていない**」という形で 248 件が無検査だった。
  **「走査式が返さなかった」は「存在しない」を意味しない。**

### 型 2: 呼び出し口を 1 つだけ配線する（**本セッションで 3 度目**）

関数の引数を増やしたとき、**呼び出し口のうち 1 つにしか渡さない**。

| 回 | 何が起きたか |
| --- | --- |
| #507 | `crossRepoRefReasons` のラベル表に kind を 1 つ足し忘れ、CI が「未知の違反種別」を出した |
| #590 | **同じ表で同じ omission を再発**（型 4 を足したとき） |
| #612 | `validateIdExistence` の第 4 引数を `--title` 経路にだけ渡し、**CI の必須チェックが実行するレンジモードで無効**だった |

**対策**: **引数を増やしたら `grep -n '<関数名>(' ` で呼び出し口を全部出してから配線する。**
そして**経路ごとに実バイナリで当てる** —— #612 では `--title` の変異試験だけが通ったので
「検査が効いている」と誤って結論した。

### 型 3: 同じ数・同じ言明を 2 箇所に持つ

条文へ実測値を埋めると、**正例を 1 つ足しただけで黙って古くなる**。
**数は作業仕様書の §母集合 を正とし、条文・スクリプト・PR 本文へ書かない。**
（#590 が実際に踏み、その教訓を書いた `traceability.md` の行が**すでに古かった**）。

### 型 4: 変異試験をしていない検査を信用する

**「壊すと落ちる」を実測していない検査は、入れたのに効いていないことがある。**

本セッションの実例（いずれも自分で作って自分で踏んだ）:
- **`check-landed-subjects.js`**: baseline へ存在しないハッシュを**1 行足すだけで検査全体が緑**になった。
  「浅いクローン（skip）」と「履歴は完全なのに解決できない（fail）」を割って塞いだ。
- **`changelog-overrides.json`**: JSON の要素境界を誤り、**隣のエントリの説明文が別のコミット行に載った**。
  **構文が通ることは意味が通ることを保証しない。生成物を実際に作って目で見る。**

### 型 5: 開示を検査の代わりにする

**「この型は検出できないと書いた」は「検出できなくてよい」ではない。**
ただし**偽陽性は必ず塞ぐ**（検出漏れは開示してよいが、偽陽性は他人の PR を止める）。

**書けないことは書けないと明記する**のは正しい。実例は [[IADR-0145]] 決定 3
（**PR タイトルからの ID 脱落は機械では判定できない** —— 落ちた後の件名は規約適合であり、
判定には PR タイトルとの突合が要るが、PR タイトルはリポジトリの中に無い）。

### 型 6: flat config / 設定ファイルの後勝ち置換

ESLint flat config は**同一ルールを後勝ちで置換する**。新しい禁止を足すつもりで
**既存の禁止を丸ごと無効化する**。`src/eslint.config.js` の冒頭が自ら警告している。
**新しいブロックを足す前に、既存ブロックへ 1 行足せないかを見る。**

## 7. 引き継いだ人が最初にやること

1. **`gh` は使えない。** GitHub 操作は MCP ツール（`mcp__github__*`）を使う。
2. **`develop` を貼り直して健全性を見る**（§2 の検査器を一通り走らせる）。
   `git checkout -B develop origin/develop` —— **このクローンは shallow** で、
   `git merge --ff-only` が「refusing to merge unrelated histories」を出すことがあるが**異常ではない**。
3. **フェーズ末クロス監査の指摘が残っていれば消化する**（フェーズ A の監査は実施済み）。
4. **フェーズ B の残り（#562 #556 #554）へ進む。** ただし **3 件とも AI だけでは完結しない**:
   - **#562 と #556 は `.github/workflows/` の編集が要る**（GitHub App 権限では閉じられない）。
     規約・スクリプト・変異試験までは AI が用意できるが、**結線だけは `workflow` スコープを持つ
     経路からの push が要る**。
   - **#554 は E2E の変異試験が要るが、この実行環境では実走できない**（§4.5）。
5. フェーズ C 以降は §2 の並びに従う。**フェーズ G は利用者の方針決定が先**。

> **着手前に必ず読む**: `CLAUDE.md` ／ `.claude/rules/traceability.md` ／ [[IADR-0141]]（母集合と監査巡数）。
> **そして §5 の 6 つの型。** 新しい失敗より、この 6 つの再発の方がはるかに多い。
