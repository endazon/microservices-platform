## 判断

### 判断 1: **値は厳密に 3 語へ固定し、修飾は備考へ移す**

`する` / `一部する` / `しない` の **3 語だけ**を「実装」列に置く。現在その列へ混ざっている
**由来（`#539` / `#535` / `［2026-08-09 / #640］`）・条件（`挙動として`）・生値の注記**は
**すべて備考列へ移す**。列の値で機械的に集計できる状態にすることが 3 値化の目的である。

### 判断 2: **`本画面では作らない`（10 行）は「しない」へ畳まず、第 4 の値として残さない**

**この 10 行は共通シェル**（パンくず・ブランド／アバター・左ナビ・右レール）であり、
**「この画面の作業ではない」＝ 引き受け先が別**という意味である。**「しない」と書くと
「作らないと決めた」と読め、「する」と書くと本画面の成果に数えてしまう。**

**採る形**: **`—`（対象外）** を置き、備考へ引き受け先（`foundation/ui/Layout` / #452 系）を書く。
**3 値は「本画面が実装する要素」に対する判定**であり、**そもそも本画面の射程外の行は
3 値の外に置く**。計画 Q21 が定めた 3 値の趣旨（**部分未実装を見えるようにする**）を損なわない。

> **なぜ「しない」に畳まないか**: 畳むと**「しない」の 36 行に、性質の違う 2 種
> （繰り延べ／射程外）が混ざる**（畳む前の「しない」は 36 行ある）。#552 が是正しようとしているのは
> **まさに「性質の違うものが同じ値に丸められる」こと**であり、同じ誤りを別の場所で作らない。

### 判断 3: **アクセス範囲の修飾（`管理者のみ` 4 行）は「一部する」ではない**

`する（管理者のみ）` / `する（管理者・運用者）` は **計画が定めたとおりのロールで実装した**という意味であり、
**満たしていない条件は無い**。**`する` へ畳み、ロールは備考へ書く。**
これを「一部」に数えると、**本当の部分未実装が薄まる。**

### 判断 4: **棚卸しは 85 行すべてを開く**（キーワードで絞らない）

`.claude/rules/traceability.md` 規則 4（**行フィルタで絞らない**）に従う。
「ただし」「のみ」「未実装」等で候補を出してから確認するのは、**その語を使わずに書かれた
部分未実装を落とす**。#552 自身が「**全行について確認すること（この棚卸しが本 issue の実質である）**」
と書いているのはこのためである。

### 判断 5: **凡例は各仕様書へ置く**（1 か所に集約しない）

#552 が「凡例を各仕様書に置く」と明示している。**共通ファイルへの参照 1 行で済ませない** ——
対応表は画面ごとに独立して読まれるため、凡例が別ファイルにあると 3 値の意味が伝わらない。

#### 新規発見 4 件が見つかった理由

- **SC-03 #5** —— **SC-05 は同じ論点（機密区分の表示名）を別行〔#7〕へ切り出して「しない」と判定している**のに、
  **SC-03 は 1 行へ畳んでいた**。**同型の画面を並べると、片方だけ粒度が粗いことが見える。**
- **SC-07 #3 / SC-09 #7** —— **同型が 2 画面にある**（モックが描く ID 採番が契約に無い）。
  片方だけ直すと非対称が残るので**両方を移した**。
- **SC-01 #8** —— **注記行は 6 画面にある**（SC-05 #13・SC-06 #11・SC-08 #10・SC-10 #15・SC-11 #17）。
  **5 つは `Alert` として描いており、SC-01 だけが描いていない。** 並べなければ気づけなかった。

### 3 値化で不要になった散文（**副次的な成果**）

**SC-09 / SC-10 / SC-11 の 3 枚は、対応表の直後に
「行数基準では捕まらない部分未実装が 1 件ある」という散文の補足を持っていた。**
**3 値化でこの補足は不要になった** —— 当該の行が**表の中に「一部する」として現れる**からである。
**補足が必要だったこと自体が二値判定の欠陥であり、それを是正するのが裁定 Q21 である。**
3 枚とも内訳の行数を数え直し、**何がどう変わったかを日付つきで残した**（削除はしていない）。
