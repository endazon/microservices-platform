## ★ 判断 0: **どこまでを「書き換えてよい」とするか**（#667 が決めよと言った線引き）

`.claude/rules/traceability.md` は「**確定済み（過去 PR の）作業仕様書は書いた時点の記録であり、
後から注記を足すのは記録の改竄にあたる**」と定める。**`status` はどちら側か。**

**決める。** **`status` はライフサイクルのメタ情報であって記録の本文ではない。ただし、
書き換えてよいのは「語彙の是正」に限る。**

| 種類 | 例 | 可否 |
| --- | --- | --- |
| **語彙の是正**（同じ状態を別の語で書いていた） | `fixed` → `done`、`implemented` → `completed` | **可** |
| **状態の進行**（当時と違う状態へ進める） | `draft` → `done`、`in-progress` → `completed` | **不可** |
| **本文への注記追加** | 「［2026-08-10 追記］…」 | **不可**（従前どおり） |

**理由**: 前者は**当時の判断を変えていない** —— 書き手は「完了した」と言うつもりで別の語を使った。
後者は**当時の記録の内容を変える**。**この線引きなら 250 件の一括置換にはならない**
（対象は語彙外の 37 件だけで、`draft` 58 件・`in-progress` 38 件には触れない）。

> **★ 自分に都合のよい線引きになっていないか確かめた。** 是正対象 37 件のうち **16 件は自分が
> 2026-08-09 以降に書いた `fixed`** である。**線引きを緩めれば自分の取りこぼしが消える。**
> だから**緩める方向ではなく狭める方向**で決めた —— **語の言い換えだけを許し、状態の進行は許さない。**
> `review` 8 件（すべて他者・2026-07）は**この線引きで触れない**（下記 判断 2）。

## 判断

### 判断 1: **規約は足さない。既にある規約へ実装を揃える**

`docs/README.md` 運用ルール 6 が値域を定義済みである。**新しい規約を書くと二重定義になる。**
足すのは **(a) 語彙外 22 件の是正**（残る 15 件は判断 2・3 で据え置き／対象外）、**(b) 値域を閉じる機械検査**、**(c) 規約が触れていない
種別への言及**（判断 3）の 3 点だけである。

### 判断 2: **`review` 8 件は触らない**（状態の進行にあたる）

`review` は**「実装の状態」ではなく「文書のレビュー状態」**であり、
**`done` / `completed` のどちらへ写像すべきかが文書から読み取れない。**

- 8 件すべて **2026-07** の作業仕様書で、**書いたのは自分ではない**
- 「レビュー中」だったのか「レビューを終えて完了した」のかは、**当時の判断であり推測できない**

**推測で `done` にすると、状態の進行を「語彙の是正」に見せかけることになる**（判断 0 で禁じた側）。
**したがって値域には `review` を含めず、この 8 件は検査の据え置き（baseline）として明示的に許す。**
**据え置きは件数を固定し、増えたら落ちる**（ラチェット。新規に `review` を書くことは止める）。

### 判断 3: **`how-to` / `runbook` / `design` は値域の対象外にする**

`docs/README.md:61` は **`how-to` は仕様ではなく作業手順の案内であり、起点 ID を持たないことがある**
と明記する。**運用ルール 6 の「その仕様書が記述する実装の状態」は手順ガイドに当てはまらない**
（手順に「実装中」は無い）。

**対象外の判定基準を 1 本にする**: **`docs/README.md` の種別表（必須 10 ＋ 任意 10）に載っている `type` か**。
載っていない `type` は「仕様書」ではないため、運用ルール 6 の定義が当てはまらない。

| 種別 | 件数 | 種別表 | 扱い |
| --- | ---: | --- | --- |
| `how-to` / `how-to-guide` | 3（`published` 2 / `active` 1） | 有り（任意） | **対象外**。README:61「仕様ではなく作業手順の案内」 |
| `runbook` | 2（`fixed` 1 / `active` 1） | 有り（任意） | **対象外**。README:60「状態の単一情報源は `operations.md`」 |
| `tech-note` | 1（`fixed`） | **無し** | **対象外**。`docs/tech/20260707_wikijs-poc-record.md` は PoC の実測記録であり要件書ではない |
| `design`（`docs/superpowers/`） | 1（`approved`） | **無し** | **対象外**。#59 / #72 由来の旧構造 |

**計 7 件。**

> **★ `tech-note` を後から対象外へ回した。** 最初は `docs/tech/` の `fixed` 3 件をまとめて
> `completed` にする表を書いたが、**1 件ずつ `type` を見たら 1 件だけ `tech-note` だった** ——
> **ディレクトリで束ねて種別を見落としていた。**（`.claude/rules/traceability.md` 規則 5「軸を 1 本で終わらせない」）

**「対象外」を書かずに検査から外すと、次に読む人が「検査漏れ」と読む。** README へ明記し、
**検査器は除外した件数をログに出す**（黙って飛ばさない）。

### 判断 6: **検査器を足す**（`CLAUDE.md` の「2 回」条件を数え直した）

`CLAUDE.md`「検査器・規約の追加は**同型の事故が 2 回起きたら**」。**数え方を先に決めた。**

| 数え方 | 件数 |
| --- | ---: |
| **実際に発火した事故**（レビュー・CI・成果物に出た） | **2 回**。① PR #666 の AI レビュー 🟢（「同日の他の仕様書は `fixed` なのに本 PR は `draft`」）②本 PR で判明した「規定を読まずに別リポの語彙を 15 件へ持ち込んだ」 |
| 潜在（乖離として存在するが発火していない） | 37 件 |

**「潜在」を事故に数えない**（PR #657 で実際にやって自己訂正した誤り）。
**発火した事故が 2 回あるので、検査器を足す条件を満たす。**

> **★ ②を事故に数えてよいか。** これは**本 PR の測定で判明したもの**であり、
> 「CI にも成果物にも出ていない」とも読める。**しかし ① と同じ型が 15 件へ広がった実体があり、
> ① の指摘は「個別の付け忘れ」として処理されて根本が残った**（#667 の起票文がその記録である）。
> **「1 回目は記録に留める」の 1 回目が ① であり、本 PR が 2 回目にあたる。**
