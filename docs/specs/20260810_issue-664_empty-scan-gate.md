# 作業仕様書: 0 件走査の門（#664）

- **NFR**（CI の検出力）。関連 IADR: **0163**（出所）・**0159**（再現した検査器）・**0130**（門の先例）
- 起点 issue: **#664**（**自分で起票した**。出所は #592 / PR #663）

## 母集合（自分で引き直した）

### 軸 1: issue 番号で引く

```console
$ git ls-files -z ':!planning' ':!src/ai-stock-trading' | xargs -0 grep -ln '#664'
（0 件）
```

### 軸 2: 検査器の本数

```console
$ ls scripts/check-*.js | wc -l

```

### ★ 軸 3: **grep の本数を転記せず、1 本ずつ実測した**

#664 は `grep` で「門を持たない **15 本**」と書きつつ、**「この 15 という数を欠陥数として扱ってはならない」**
と自ら釘を刺している（単一ファイル読み取り型は 0 が正常）。**転記せず、実際に走らせて確かめた。**

#### 実測の装置 —— **#592 の事故条件そのものを再現する**

**走査ルートが存在しない空リポジトリで 26 本を回す。**

```console
$ T=$(mktemp -d); cp -r scripts "$T/"; cp package.json "$T/"; (cd "$T" && git init -q && git commit -q --allow-empty -m init)
$ for f in scripts/check-*.js; do (cd "$T" && node "scripts/$(basename $f)"); echo "$?"; done
```

**#592 の事故は「`walk()` が絶対パスを渡されて `catch` が空配列を返した」＝ 走査ルートへ到達できない**形だった。
空リポジトリはこれを**一律に再現する**（各検査器のルートを個別に壊さずに済む）。

#### 実測の結果 —— **3 分類に分かれた**

| 分類 | 本数 | 意味 |
| --- | ---: | --- |
| **A: 0 件走査で「OK」と報告して緑** | **4** | **★ 欠陥。門を足す** |
| **B: 0 件だが「検査していない」と明示して緑** | 7 | **設計として正しい**（skip を可視化している）。触らない |
| **C: 落ちる** | 15 | 既に門があるか、例外で止まる。触らない |

**A（是正対象）**:

| 検査器 | 0 件のときの出力 |
| --- | --- |
| `check-cross-repo-refs` | `OK: 0 件の Markdown に他リポジトリ参照の表記違反はありません。` |
| `check-doc-links` | `OK: 0 件の Markdown に破損した相対リンクはありません。` |
| `check-plan-id-qualification` | `OK: 0 件に他プロジェクト ID の修飾違反はありません。` |
| **`check-unit-dependencies`** | `OK: ユニット依存方向の違反はありません。` —— **件数すら出さない**ので、0 件走査かどうかがログから読めない |

**B（触らない。理由を書く）**: `check-action-versions` / `check-ai-workflow-config` / `check-chunk-budget` /
`check-doc-updated` / `check-permission-denials` / `check-realm-constraints` / `check-static-egress`。
いずれも **「検査していない」「skip した」と明示して緑になる**。
`check-chunk-budget` と `check-static-egress` は**自ら「CI では `--require` で fail-closed にすること」**と書いており、
**設計として skip を選んでいる**。**これらを fail にすると、成果物を作らない文脈で CI が壊れる。**

### ★ 軸 4: **空リポジトリでは捕まらない経路がある** —— `check-openapi-dto-drift`

**この装置は「ルートが丸ごと無い」形しか再現しない。** `check-openapi-dto-drift` は空リポジトリでは
`OPENAPI` が読めず**例外で落ちる**ため、上の分類では C に入る。**しかし #664 が挙げた再現は別経路である。**
**自分で確かめた。**

```console
$ node -e "const d=require('./scripts/check-openapi-dto-drift.js');
  console.log(JSON.stringify(d.findDrift({Foo:{props:['a'],required:[]}}, {}, {entries:[]}, new Set())))"
[]
```

`main()` を読むと、**`DTO_ROOTS` が 1 件も拾えなくても** `records = {}` のまま
`findDrift` が `[]` を返し、**`OK: schemas 69 / C# record 0 のうち同名 0 件…` を出して `return 0`** になる。

> **★ 装置が万能でないことを記録する。** 空リポジトリ試験は
> **「ルートが無い」は捕まえるが「ルートはあるが対象を 1 件も拾えない」は捕まえない**。
> **`check-openapi-dto-drift` は後者であり、装置だけに頼っていたら見落としていた。**

**したがって是正対象は 4 ＋ 1 = **5 本**である。**

## 判断

### 判断 1: **門は「走査 0 件」で fail させる**（[[IADR-0130]] の作法へ揃える）

`check-test-spec-coverage.js` が #592 で確立した形をそのまま使う。

```
console.error('[<検査器>] … を 1 件も見つけられませんでした。');
console.error('  0 件検査は「検査しているつもりで何も見ていない」状態なので fail させています。');
process.exit(1);
```

### 判断 2: **分類 B の 7 本は触らない**

**「0 件で緑」だから欠陥、ではない。** 分類 B は**「検査していない」と明示している** ——
ログを読めば検出力ゼロだと分かる。**#592 の事故は「OK と報告した」ことが本質**であり、
**skip と明示するものは同じ型ではない。**

**むしろ fail にすると害がある**: `check-chunk-budget` / `check-static-egress` は
**ビルド成果物が前提**であり、成果物を作らない文脈（ドキュメントだけの PR 等）で CI が壊れる。
**両者は `--require` という fail-closed の入口を既に持っている。**

### 判断 3: **`check-unit-dependencies` は件数も出す**

0 件のとき**件数すら出さない**ため、ログからは検出力ゼロだと読めない。
門に加えて **OK メッセージへ走査件数を入れる**（他の 3 本は既に入っている）。

### 判断 4: **規約化はしない**（数え方を先に決めた）

`CLAUDE.md`「検査器・規約の追加は**同型の事故が 2 回起きたら**」。**数え直した。**

| 数え方 | 件数 |
| --- | ---: |
| **実際に発火した事故**（CI か成果物に出た） | **1 回**（#592 の初版。**コミット前に変異試験で捕まえたので CI には出ていない**） |
| **潜在**（再現はしたが発火していない） | **5 本**（本 PR が是正する） |

**「潜在」を事故に数えない。** 数えると**「いま残っている乖離」を「起きた事故」と取り違える**ことになり、
**PR #657 で実際にやって自己訂正した誤り**と同じである。**したがって本 PR は
「見つけた 5 本を直す」に留め、`CLAUDE.md` へ規約を足さない。**

> **★ ただし「2 回目」の判定材料は残す。** 次に同型が発火したら 2 回目である。
> **本仕様書の §軸 3 の装置（空リポジトリ試験）が、その判定を再現可能にする。**
