# 作業仕様書: 無採番 `NFR` の適用範囲の一般化（#724）

## 起点

- **NFR**（文書統制。**該当する `NFR-xx` が無いため無採番** —— **本 PR が一般化する当の規範を、本 PR 自身が使っている**）
- 起点 issue: **#724**。実装 ADR: **[IADR-0188](../adr/IADR-0188_unnumbered-nfr-applies-to-all-work.md)**
- 出所: **PR #723（#716）の AI レビュー 🟡**。[IADR-0186](../adr/IADR-0186_sshnet-transitive-pin.md) 決定 5 が暫定として記録した

> **★ 値の基準時点は develop `22ae1db`（2026-08-14 実測）である。**

## 事象

**[IADR-0179](../adr/IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 1 の見出しは「メタ作業」に限定されているが、
挙げている理由はメタ作業に固有ではない。**

> **★ 無理に付けるほうが悪い。** **実在しない対応づけを作る**ことになり、
> **トレーサビリティとしては無採番より劣化する**

**「当たる番号が無いなら無採番」という判断基準は、作業がメタか製品かに依らない。**
**#716（`SSH.NET` の脆弱性ピン）は製品の依存修正でありながら、根拠として決定 1 を引いた。**

## 判断

### ★★ 判断 1: **改定は「新 IADR ＋ 旧 ADR への日付つき追記」で行う**

**#724 は 2 案（新 IADR で Superseded / 日付つき追記ブロック）を挙げている。両方採る。**

| | 理由 |
| --- | --- |
| **新 IADR を起こす** | **射程の変更は、7 本の IADR が引用している live な規範の意味を変える。** 単独の記録が要る |
| **Superseded にはしない** | **決定 1 は覆っていない。** 「メタ作業は無採番」は一般化後も真である —— **広げただけ**である |
| **旧 ADR へ日付つき追記** | `.claude/rules/traceability.md`「決定を変える追記なら**日付つきの追記ブロック**」の形そのもの |

**IADR-0179 の原文は 1 文字も変えない。** **ファイル名（`..._unnumbered-nfr-for-meta-work.md`）も変えない**
——改番・改名は採番衝突のときの手順であり、**リンクを壊す代償に見合わない。**

### 判断 2: **一般化しても「番号は実装側で作らない」は動かさない**

**IADR-0179 決定 2 は採番を計画側の領分と定める。射程を広げると、**
**「当たる番号が無い」を口実に実装側が採番する誘惑が増える**ので、**決定 2 を明示的に維持する。**

### ★★ 判断 3: **予算は「入口の重複を削って」戻す。別紙へ新たに移すものは無い**

**入口の ID レンジ行（787B）が抱える `ADR-0023` の遷移の記述は、別紙 §2 に全文が既に在る。**
**同じ事実が 2 箇所にある状態であり、[IADR-0141](../adr/IADR-0141_audit-rounds-and-population-drawing.md) が禁じている形である**（片方が古くなる）。

**→ 入口には規範（走査基準の pin・4 種が動いていないこと・`Proposed` の件数）だけを残し、
内訳と遷移の理由は別紙へ委ねる。** **別紙への加筆は不要である** —— **移すのではなく、重複を消す。**

> **★ これは [IADR-0179](../adr/IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 4 の実行例である** ——
> **規範を足す機会に、同じ節の規範でない部分を出す。統制は増え、量は減る。**

### 判断 4: **予算に機械検査を置くかは本 PR では決めない**

**同型の事故は 1 回目である**（`CLAUDE.md`「検査器・規約の追加は同型の事故が 2 回起きたら」）。
**本 PR は記録に留め、[IADR-0188](../adr/IADR-0188_unnumbered-nfr-applies-to-all-work.md) 決定 4 に「検出できない」と明記する。**

### ★ 検証中に踏んだ 2 つの事実

1. **`develop` の planning pin は `cff0e7b` から `915981a` へ進んでいた**（#726 のマージ後）。
   手元のクローンが古いままだと `scripts.test.js` は**私の変更と無関係に落ちる** ——
   **clean な develop で再現することを確かめてから同期した**。
   **pin を合わせたうえで分類 A のバイト一致テストは通る** ので、**#721 型の追随漏れは新 pin では起きていない。**
2. **変異試験のハーネスが `set -o pipefail` ＋ `grep -q` で壊れていた** ——
   **`grep -q` が先に抜けると `printf` が SIGPIPE で死に、`pipefail` がそれを拾って「別の理由」と誤判定する。**
   **見逃しを「検出 OK」と誤報する向きではない**が、**判定を一時ファイル経由へ直してから 5 変異を測り直した。**
