### 起点 ID に無採番 `NFR` を使う理由

`.claude/rules/traceability.md` が無採番 `NFR` を許す 2 つの場合のうち、**2「ID 列はあるが、
その作業に当たる番号が無い場合」**に当たる。本作業は**規約（PR の変更単位）と文書統制の改定**であり、
同ルールが典型として挙げる**メタ作業**そのものである。計画側の非機能要件表（`NFR-01`〜`NFR-27`）は
**稼働する製品**の要件を並べたものであって、工程の規律を表す番号は持たない。

- **1（計画側が ID 列を持たない）ではない** —— ID 列は実在する（`NFR-01`〜`NFR-27`）。
- したがって**環流しない**。近い番号を無理に当てない（監査が「その NFR の実装」として数え、
  無採番より劣化するため）。

## 目的・背景

`CLAUDE.md` 自身が「**範囲を広げるには IADR-0116 / IADR-0139 の改定 IADR が要る**」と定めている。
**裁定が下りても、実装側 ADR を改めない限り規約としては 2 件のままである。** さらに `CLAUDE.md` の
拘束点の要約が「**束の上限は名目 3 件・実効 2 件**」と書いており、**裁定の時点から誤りになっている。**

### 裁定の内容（一次資料から引いた）

| 項目 | 裁定 |
| --- | --- |
| 束ねてよい対象 | **裁定済みの同型な契約追加**（変更なし） |
| **判定の単位** | **資源**（同じ API 資源または同じ DTO 群に閉じること）**のまま。ドメインへ広げない** |
| **実効上限** | **2 件 → 4 件** |

**理由は「レビューの読み筋を変えずに固定費だけ下げられる」ことである。** 束の性質（同一資源・同型）が
保たれる限り、件数が増えてもレビューは**同じ観点の反復**になる。

**不採用の案とその理由も裁定が明記した**（将来「やっぱりドメイン単位に」と言い出す人への回答になる）。

| 不採用 | 理由 |
| --- | --- |
| **案 C（ドメイン単位）** | 1 PR に**異なる DTO・異なる受け入れ基準**が混ざり、`IADR-0139` が資源単位を選んだ理由（**同型性の機械的な判定**）が失われる |
| **案 D（実測連動の可変上限）** | 理にかなうが**規則が状態を持つ**。「いまの上限は何件か」を追う仕組みが別途要る。**判定が機械化しにくい規則は守られない** |

> **巻き戻し単位が件数に比例して大きくなることは承知のうえで 4 件とした。**
> これは**トレードオフを飲む判断**であって、欠点が無いという判断ではない。

## 改定の形の判断（日付つき追記か、改定 IADR の新設か）

**採る形: `IADR-0139` 本文への日付つき追記ブロック（`［2026-08-16 追記 / #791］`）。旧記述は消さない。**
併せて `IADR-0116` の［2026-08-07 追記］ブロックにも、同じ日付つき追記で「その記述は当時のもの」と
明示する（**書き換えず、隣に置く**。`.claude/rules/traceability.repo.md` §Superseded / Deprecated な
ADR を引用するときの書式）。

### 根拠

1. **`IADR-0139` 自身が、この値を後で見直すと書いている。** 同 ADR「結果 / フォローアップ 5」は
   **「束を 1 本流したあと、実際の固定費削減と差し戻しの発生率を測り、上限 3 件と条件 F を見直す」**と
   置いた。**上限は、決定の中で改定が予定されていた変数である。** 予定された見直しを本文に書き足すのは
   同 ADR の設計どおりであり、新しい決定の追加ではない。
2. **対照的な先例が「新設せよ」と言っていたのは別の型である。** [IADR-0142](../adr/IADR-0142_fr19-20-scoped-release-by-overturn-range.md)
   が `IADR-0119` を部分改定したのは、同 IADR 決定 6 が**条件の置換を新 IADR で行うことを要求していた**
   ためである。`IADR-0139` にその要求は無い。[IADR-0117](../adr/IADR-0117_platform-shared-kernel-placement.md)・
   `IADR-0122` 決定 4 も**適用範囲そのものを動かす**改定であった。
3. **本件は範囲（対象・判定単位）を 1 ミリも動かさない。** 裁定は**対象＝裁定済みの同型な契約追加**、
   **判定単位＝資源**を**明示的に据え置いた**。動いたのは**件数の閾値ただ 1 つ**である。
   `CLAUDE.md` の「範囲を広げるには改定 IADR が要る」は、**実装側が読みだけで範囲を広げること**を
   止める規範であり、**上流の裁定が閾値を動かした場合まで新設を要求するものではない**
   （かつ本件は上流の運用ガイド §2 が射程を引き受けたことで、派生が範囲を決める余地自体が消えた）。
4. **決定の出所が実装側ではない。** 本件は上流の裁定の**反映**である。新しい IADR を立てると
   「同じ決定を持つ場所」が 2 つになり、**片方が古くなる**（[IADR-0141](../adr/IADR-0141_audit-rounds-and-population-drawing.md)・
   [IADR-0171](../adr/IADR-0171_backlink-obligation-one-way.md) が繰り返し避けている型）。
5. **機械的な副作用**（判断の主因ではないが実測した）: `docs/adr/README.md` の索引行は
   `scripts/adr-index-title-baseline.json` のラチェット下にあり、**`IADR-0139` は
   `title-too-long` として baseline に載っている**。新 IADR を立てると索引行が 1 行増え、
   **200 字以内で書けなければ baseline（`scripts/`）の更新が要る** —— `scripts/` は #790 の領域で
   本作業では触れない。追記方式ならこの交差が起きない。

### 併せて処理する実質的な論点（見落とすと上限が動かない）

**旧記述は「判定はファイル数・行数の目安が優先する」と書き、実効 2 件はその目安からの導出だった。**
2 → 4 と数字だけ書き換えると、**目安（概ね 50 ファイル / +2500 行）が優先する限り実効は 2 件のまま**に
なる（1 件 = 15〜25 ファイルの実測なので 4 件束は 60〜100 ファイル）。**裁定は、レビューが同じ観点の
反復になることを根拠に件数側を上限としたのだから、この導出は同型な契約追加の束については働かない。**
追記ブロックでその関係を明示する。

必読規約（Claude Code の母集合 = `CLAUDE.md` ＋ `.claude/rules/*.md`。**`AGENTS.md` は入らない**）は
**上限 51,200 バイト**で、`scripts/scripts.repo.test.js` が
**余白 `BUDGET - total >= 1000` をラチェットとして固定する**（IADR-0190 決定 4 を実読して確認した）。
着手時 50,193 バイト＝**余白 1,007 バイト。可処分は 7 バイト**である。

**正本が引き受けた分だけ、本リポの記述を減らせる**という関係である。

### 索引（`docs/adr/README.md`）の文字数 —— 2 コミット目で是正した

**結論: `IADR-0139` の索引セルを 3,547 字 → 157 字へ縮め、`scripts/adr-index-title-baseline.json`
の `rows` から `IADR-0139` の `title-too-long` を外した。上限 200 字を満たす。**

**★ 当初（1 コミット目）は「意図的に超過のまま」とした。その判断は誤りだった。**
理由は「200 字以内へ縮めると baseline が陳腐化して赤になり、その是正には `scripts/` の変更が要る。
`scripts/` は #790 の領域である」というものだったが、**#790 が実際に触るのは 6 ファイル
（`planning` / `check-commit-messages.js` / `check-cross-repo-refs.js` /
`contract-schema-baseline.json` / `kit-sync-classification.json` / `scripts.repo.test.js` /
`scripts.test.js`）であり、`adr-index-title-baseline.json` は含まれていなかった。**
**領域宣言を実測せず「`scripts/` 全体」と粗く読んだのが誤りである**（母集合を粗く取ったのと同じ型）。
なお**「縮めると落ちる」という機構の読み自体は正しかった** —— 是正は
**「縮める」＋「baseline から 1 行外す」の 2 手が対**であって、片方だけでは赤になる。

| | 前 | 後 |
| --- | ---: | ---: |
| 索引セルの文字数（`[...s].length`） | **3,547 字** | **157 字**（上限 200） |
| `baseline.rows['IADR-0139']` | `["title-too-long"]` | **削除**（他 ID には触れていない。行数 64 → 63） |

**`title-drift` の下限も満たす**（縮めた要約が本体と無関係な文へ化けていないことの検査）:
`minTitleOverlap` は **12**（JSON を実読）。本体 `title:` から ID 接頭辞を除いた文字列との
**文字単位 LCS は 45**、要求は `min(12, 本体 59 字, 要約 157 字) = 12` であり **45 ≥ 12** で通る。
**書く前に計算して確定した。**

**`title-addendum` を新たに立てていない**: 索引セルへ `［YYYY-MM-DD 追記］` の形を入れると
別の違反が立つ（検査式 `/［\d{4}-\d{2}-\d{2}\s*追記/`）。baseline から `IADR-0139` を外した後は
**どの違反も許容されない**ため、索引側は起票 ID だけを `#791` として書き、日付つき注記自体を置かない
形にした（改定の経緯は本体 ADR の［2026-08-16 追記］が持つ）。
