# 作業仕様書: `feedback/` の欠落節と `status` 語彙（#712）

## 起点

- **NFR**（文書統制。**メタ作業なので無採番**。[IADR-0179](../adr/IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 1）
- 起点 issue: **#712**。実装 ADR: **[IADR-0185](../adr/IADR-0185_feedback-status-vocabulary.md)**
- 出所: **#707 判断 3** と **#710 射程外**が「`status` 語彙の定義は別 issue」と分離した分

> **★ 値の基準時点は develop `a671a80` / planning pin `2cf0795`（2026-08-13 実測）である。**

## ★★ 母集合 —— 3 軸で引いた

### ★★ 軸 a: **`feedback/README.md` からキットの節が丸ごと欠けている**

**pin `2cf0795` のキット** `repo-template/feedback/README.md` と本リポのものを `diff` した。

| | 実測 |
| --- | --- |
| 差分の向き | **キットにあり本リポに無い（19 行）。逆向きの差分は 0** |
| 欠けている節 | **「【最重要】記録を作るだけでは計画へ届かない」** |
| `feedback/TEMPLATE.md` | **バイト一致**（分類 A。触らない） |

**#710（PR #711）で検査器そのものは取り込んだのに、それを説明するこの節を取り込んでいない。**

> **★ 比較先は pin `2cf0795` である。** 計画リポの HEAD（`690b0c7`）のキットは planning#319 の反映で

### ★★ 軸 b: **`status` の意味はどこにも書かれていない**

| 何が | どこに |
| --- | --- |
| **値域**（`open` / `triaged` / `accepted` / `rejected`） | **`scripts/scripts.repo.test.js` の検査（#700）だけ** |
| 既定値 `open` | `feedback/TEMPLATE.md` の frontmatter |
| **各値の意味・遷移・判断の主体** | **どこにも無い** |

**`feedback/README.md` は `status` という語を 1 度も使っていない**（実測: 出現 0 回）。

### ★★ 軸 c: **実務では `open` と `triaged` が同義に崩れていた**

**全数**で走査した（`README.md` / `TEMPLATE.md` を除く）。**「伝達の証拠」は検査器 `inspect()` の判定を
そのまま用いた**（`planning_issue:` 鍵 / 他リポ issue URL / 本文の「起票済み」のいずれか）。

| status | 件数 | 検査器が認める伝達の証拠 | `## 起票状況` 節 |
| --- | ---: | ---: | ---: |
| `accepted` | 26 | 10 | 4 |
| `triaged` | **7** | 6 | 6 |
| **`open`** | **3** | 2 | **3** |
| `rejected` | 2 | 0 | 0 |
| **合計** | **38** | 18 | 13 |

> **★★ #712 の本文と引き継ぎ資料はどちらも「37 件 / `triaged` 6 件」と書いているが、実測は
> 「38 件 / `triaged` 7 件」である**（`20260811_pr-size-400-vs-mandatory-specs.md` の 1 件が落ちていた）。
> **`.claude/rules/traceability.md` 規則 8 に言う「報告された件数は母集合ではない」の再演**であり、
> **受け入れ基準の「既存 37 件」は 38 件として読み替えて満たす。**

> **★ `open` の 3 件は、いずれも伝達済みである**（3 件とも `## 起票状況` 節を持ち、planning を参照する）。
> **つまり実務の `open` は「未伝達」ではなく「裁定待ち」を意味しており、`triaged` と区別が付いていない。**
>
> **一方 `scripts/check-feedback-dispatched.js` は `status: open` を「未伝達の疑い」と読む** ——
> **これが #710 で「既知の偽陽性」とした 1 件の正体である。**

## 判断

### 判断 1: **欠けている節を取り込む（デルタを減らす方向）**

[IADR-0115](../adr/IADR-0115_impl-handoff-kit-as-single-source.md) 決定 1 のとおり、キット本文を土台にする。**追随漏れを埋める。**

### ★ 判断 2: **CI ジョブ名だけは本リポの実態へ直す**

キットの節は検出を **`doc-links` ジョブ**が行うと書くが、**本リポは独立ジョブ `feedback-dispatched`**
（[IADR-0184](../adr/IADR-0184_feedback-dispatch-checker-verbatim.md) 決定 3）。**そのまま取り込むと嘘になる。**

**これは IADR-0115 決定 2 が許す固有デルタ（2. 技術スタックとその CI 配線）に当たる**ので、環流は要らない。

### ★★ 判断 3: **`open` は「未伝達」と定義する —— 機械の読みに合わせる**

**2 つの読みがありうる。**

| 案 | `open` の意味 | 結果 |
| --- | --- | --- |
| **A（採用）** | **未伝達**（伝達したら `triaged` へ） | **検査器の読みと一致**。現在の `open` 3 件は `triaged` へ直す |
| B | 裁定待ち | 実務の慣行には合うが、**検査器と恒久的に食い違う**。`triaged` と区別が付かない |

**A を採る。** **B は `open` と `triaged` を同義のまま固定してしまう**（軸 c の実測がまさにその状態である）。

| 値 | 意味 | 誰が遷移させるか |
| --- | --- | --- |
| `open` | 記録は作ったが**計画リポへまだ伝達していない**（TEMPLATE の既定値） | —— |
| `triaged` | **伝達済み**（issue 起票または `draft/feedback/` へのコピー）。**裁定待ち** | **実装側**（伝達した事実） |
| `accepted` | 計画側が**受け入れた**（計画書・ADR へ反映される／された） | **計画側の裁定**を実装側が転記 |
| `rejected` | **採らないと決まった** | 同上 |

### ★★ 判断 4: **#710 の「既知の偽陽性」は、これで真に解消する**

**`20260809_document-write-machine-client.md` を `open` → `triaged` へ直すと、警告は 1 → 0 件になる。**

**これは #710 の [IADR-0184](../adr/IADR-0184_feedback-dispatch-checker-verbatim.md) 決定 2「偽陽性を消すために記録へ嘘を書かない」と矛盾しない。**

| | #710 の時点 | #712 の時点 |
| --- | --- | --- |
| 語彙の定義 | **無い** | **ある**（判断 3） |
| `open` のまま置く理由 | **直す根拠が無かった**（`triaged` にする規約が無い） | —— |
| いま `triaged` にする根拠 | —— | **定義に照らして `open` は誤りだから**（伝達済みである） |

**#710 が退けたのは「`planning_issue:` へ PR 番号を書く」「満たすために別途 issue を立てる」という
事実を歪める手であって、`status` の付け替えではない。** **付け替えは、定義ができて初めて可能になった。**

> **★ 偽陽性の正体は検査器ではなく、語彙の不在だった。**
> **planning#319 の知見 1（経路を認めない件）は依然として有効**である —— **本作業は `status` 側だけを正す。**

### ★ 判断 5: **語彙の定義は暫定デルタとして置き、環流する**

**語彙の定義は IADR-0115 決定 2 の固有デルタ 4 種のどれにも当たらない。**
**同 決定 3 が「汎用的な改善はキットへ環流する」と定める** —— **どの実装リポでも同じ穴が空いている。**

**IADR-0115 が確立した「一時デルタ」の運用に従う** ——
**コメントで環流先の issue を必ず参照し、キット側へ反映されたら撤去する**（第 12〜13 ラウンドの先例）。

### 判断 6: **語彙の外にある既存記録を一括是正しない**

| 実測（検査器が認める伝達の証拠が無いもの） | 件数 | 扱い |
| --- | ---: | --- |
| `accepted` のうち証拠を持たないもの | **16** | **是正しない**（起票状況を書く運用より前の記録） |
| `rejected` のうち証拠を持たないもの | **2** | **是正しない**（実装側の取り下げと読める） |
| `triaged` のうち証拠を持たないもの | **1** | **是正しない**（同上） |

**規約が無かった時期の記録へ、後から規約を遡及適用しない**（#706 / #707 / #710 と同じ判断）。
**直すのは「定義に照らして明確に誤り」である `open` 3 件だけ**である。

> **★ これらは検査器を鳴らさない** —— `status` が `open` 以外だからである。**是正しないことで
> 警告が増えることはない**（判断 4 の「0 件」は保たれる）。

### ★★ レビューで見つかった欠陥と是正（PR #715 の AI レビュー 🔴）

**回帰テストのキット本文比較が、`planning` を populate した環境で必ずクラッシュしていた**
（`scripts.test.js` が **491 件中 107 件**で異常終了）。**再現して確かめたうえで直した。**

| | |
| --- | --- |
| 原因 | `strip()` が**行単位のフィルタ**で、`<!--` の行と `-->` の行にしか当たらず**3 行コメントの中間行が素通り**していた |
| **なぜ気づかなかったか** | 比較が **`fs.existsSync(KIT_README)` の内側**にあり、**手元も CI も `planning` を未 populate** —— **一度も実行されていなかった**。**10 件の変異試験もすべてこの分岐に入っていない** |
| 是正 | `strip()` を `/<!--[\s\S]*?-->/g` の**ブロック除去**へ変更。**キットを populate して 491 件全数 pass を再実測** |
| 併せて | 未 populate 時に **notice を出す**（黙って飛ばすと「検査した」と読めるため。[IADR-0183](../adr/IADR-0183_false-green-warning-on-worktree-state.md) と同型） |

> **★「変異試験を通した」は「変異試験が対象の分岐に入った」を意味しない。**
