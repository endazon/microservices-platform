## ★★ 判断 1: **伝達は GitHub Issue 経路を採る**

**`feedback/README.md` は 2 経路を等価と定めている**（記録ファイル経路 / GitHub Issue 経路。planning#319）。

**本作業では Issue 経路を採る。** 理由は**記録ファイル経路が使えないため**である ——
**本リポの運用制約により `planning/` は pin 更新のみで、計画書そのものを本リポから書き換えない。**
**`planning/draft/feedback/` へ写しを置くことができない。**

> **★ これは「手を抜いた」のではない。** **両経路は等価であり、Issue 経路でも検査器は緑になる**（planning#319 の裁定）。
> **証拠は `planning_issue:` に残す。**

## ★★ 判断 2: **11 件を 5 つの issue へまとめる。ドメインではなく「求める行動」で割る**

**`CLAUDE.md`「裁定依頼は小さく高頻度に流す」に従い、1 つの巨大な issue にしない。**
**一方で 11 件を 11 本にすると、同型のものが散って上流の処理を増やす。**

**割り方は「上流に何をしてほしいか」で決める** —— **取り込み / 是正 / 裁定は、上流での扱いが違う。**

| # | issue | 束ねる件 | 上流に求める行動 |
| --- | --- | --- | --- |
| A | **キット同期の分類表と突合検査を配る** | 9 | **取り込み**（★ 最優先） |
| B | **検査器・規約の汎用改善 5 件** | 1・2・3・4・10 | **取り込み** |
| C | **キット原文の誤り 2 件** | 5・6 | **是正** |
| D | **固有デルタ 4 種に不足がある** | 7・11 | **裁定** |
| E | **監査の巡数の目安に実測が無い** | 12 | **裁定** |

**D は 2 件を束ねる** —— **`AI_SETUP.md` も `commit-allowlist.json` も「キットが空欄・空配列で配り、各リポが埋める」型**であり、**同じ穴の 2 つの実例**だからである。**別々に出すと、上流が同じ判断を 2 回することになる。**
