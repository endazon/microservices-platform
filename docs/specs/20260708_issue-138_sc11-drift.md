# 仕様書: SC-11 ドリフト表示（Issue #138）

> Wave A 3 件目（SC-11 UI 群）の 2/3。#137（グラフ）に続き、#140（アクセス制御）に先行する。

## 起点となる計画書（トレーサビリティ）

- 機能要求（FR）: FR-15（宣言との不一致検出・警告）
- 画面（SC）: SC-11 構成ビューア
- 関連 ADR: [[IADR-0029]]（ドリフト分類）／ [[IADR-0036]]（可視化方式）
- Issue: #138（親 #122）

## 目的・背景

宣言（Git）と実効構成の差分（ドリフト）を一覧・強調表示する。判定は API 側（`DriftDetector`）が実施済で、
本画面は `/bff/admin/config/drift`（`DriftReportDto`・実装済）の結果を表示するのみ。種別は自由文字列
（IADR-0029 の 5 分類 MissingApply / UndeclaredSubscription / StaleStage / BindingMismatch / Unverifiable 等）
であり、UI は種別を固定せず **kind / severity をそのまま汎用描画**する（新分類追加に UI 改修が不要）。

## 対象範囲

- 対象:
  - `ConfigViewerPage` に `/admin/config/drift` の取得と `DriftView` セクションを追加。
  - 種別・深刻度・対象・説明の一覧表示。深刻度で強調色（既知値を小文字照合、未知は中立）。
  - 0 件（または `hasDrift=false`）時は「ドリフトなし（OK）」を確認時刻とともに明示。
  - ドリフト取得失敗はその領域のみ縮退（構成表示は維持）。
  - §(1) 実効構成側の強調表示: `finding.target` と一致する**パイプライン段**（`PipelineView`）に警告色を付与し、
    `DriftView`（`#drift-section`）へのリンクを表示する（IADR-0036・SC-11 §(1) 対応）。
  - テスト: Vitest（0件OK・findings 表示・領域縮退・パイプライン段の強調表示）。
- 対象外:
  - 履歴（#139）、アクセス制御テスト展開（#140）、BFF/バックエンド変更。
  - イベント接続（`EventBindingsView`）・ポート（`PortsView`）の強調表示: `DriftDetector`
    （`Shared.Infrastructure/Foundation/Introspection/DriftDetector.cs`）が返す `Target` は全分岐
    （`MissingApply`/`UndeclaredSubscription`/`StaleStage`/`BindingMismatch`/`Unverifiable`）で常に
    パイプライン段名であり、イベント名・ポート名になることは現行実装では無い。到達し得ない分岐への
    防御的実装を避ける方針（CLAUDE.md）に沿い、強調表示はパイプライン段のみに限定する。

## 設計

- `apiFetch<DriftReport>('/admin/config/drift')` を実効構成と独立に取得（疎結合）。
- `DriftReport = { hasDrift, checkedAt, findings: { kind, severity, target, detail }[] }`。
- ヘッダのバッジ: `OK` / `ドリフト N 件`。0 件は OK 明示（検出済みを日時で示す）。

## 受け入れ基準（Issue #138）

- [x] ドリフトが種別付きで一覧・強調表示される
- [x] ドリフト 0 件時に「OK」が明示される

## テスト方針

- 単体（Vitest）: パスで `/admin/config` と `/admin/config/drift` を振り分け、0件OK・findings（kind/severity/target）・領域縮退を検証。

## 計画書との差異

- 差異1（種別名）: あり（軽微）。SC-11 仕様書 (2) の種別表は例示（missing/stale 等）だが、実 API の `DriftFindingDto.kind` は
  IADR-0029 の分類名（StaleStage 等）を返す。UI は種別を固定せず汎用描画するため、種別が増えても追随不要。
- 差異2（明細の列構成）: あり（軽微）。SC-11 仕様書 (2) は各明細に「対象・種別・期待（宣言）・実際（実効）・検出時刻」の
  列を要求するが、実 API の `DriftFindingDto` は `Kind`/`Severity`/`Target`/`Detail` のみを持つ。期待（宣言）／実際（実効）は
  `detail` テキストへ統合され、検出時刻（`checkedAt`）は明細ごとではなくレポート全体に 1 つのため、明細行ではなくセクション
  全体で 1 回表示する。`DriftReportDto`/`DriftFindingDto`（IADR-0029 で確定）に起因する合理的な適応。
- 差異3（深刻度の値域）: 実 API の深刻度は `DriftDetector` の `Warning` / `Info` の 2 値（IADR-0029）。UI は大文字小文字を
  無視して既知値を照合し、未知値は中立色にフォールバックする（実在しない深刻度への分岐は持たない）。テストは実データ
  （Warning/Info）で着色を検証する。
- 差異4（§(1) 強調表示の対象範囲）: SC-11 仕様書 (2) は明細の「対象」を「段名/イベント/ポート」と記載するが、現行
  `DriftDetector` は `Target` に常にパイプライン段名のみを設定する。そのため §(1) の強調表示（警告色＋(2) へのリンク）は
  `PipelineView` のみに実装し、`EventBindingsView`/`PortsView` は対象外とした（到達し得ない分岐への防御的実装を避ける方針）。
  将来 `DriftDetector` がイベント/ポート粒度のドリフトを検出するようになった場合は、本差異を解消し対象を拡張する。
