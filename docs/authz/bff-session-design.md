# BFF セッション設計 実装ガイド

ブラウザと BFF の間のセッションを実装・運用するための入口である。**論拠は実装 ADR が持ち、本書は
運用手順と設定値の所在を持つ。**同じ値を両方へ書かない（複写した瞬間に、片方が古くなる）。

## 0. この設計が満たすもの

**アクセストークンをブラウザへ一切出さない。**ブラウザが持つのは HttpOnly Cookie のセッションキーだけで、
アクセストークンとリフレッシュトークンは BFF 側のセッションストアにのみ置く。

**利用者の無効化・退職時に全セッションを即時失効できる。**セッション実体をサーバ側に置くため、
ストアから削除した瞬間に失効する。

## 1. Cookie 属性

| 属性 | 値 | 備考 |
| --- | --- | --- |
| `HttpOnly` | 有効 | スクリプトから読めない |
| `Secure` | **常に有効** | フレームワーク既定は「リクエストと同じ」なので**明示して固定する** |
| `SameSite` | `Lax` | CSRF の 1 枚目の壁（§4） |
| `Path` | `/` | SPA と BFF は同一オリジンで、SPA 側のパスからも送出される必要がある |
| 名前 | `__Host-` 接頭辞を付ける | 接頭辞は `Secure` ＋ `Path=/` ＋ `Domain` 無しを**ブラウザ側で強制**する。上の 3 行と整合する |

**correlation / nonce Cookie も `Lax` にする。** 既定は `SameSite=None`（＋ `Secure` 必須）であり、
そのままだと平文 http のローカル開発でログインが壊れる。§3 の `query` 化とセットで `Lax` にできる。

## 2. 有効期間と「記憶」30 日

🔴 **数値を本書へ書き写さない。** 認可サーバ（Keycloak）の realm 定義が唯一の情報源である。

- 「記憶」を選んだセッションの寿命は realm の **remember-me 用のアイドル/最大寿命**に従う
- 選ばなかった場合は realm の通常値（未設定なら認可サーバの既定）に従う
- **フレームワーク既定の 14 日には根拠が無い。**必ず realm の値へ合わせる

**テストは realm 定義を読んで突き合わせる**（期待値をテストコードへ直書きしない）。
realm を変えたときにテストが追随せず緑のまま、という状態を作らない。

## 3. ログイン経路

**Authorization Code + PKCE を BFF が実施する。**ブラウザは認可サーバへ往復するだけで、
コードとトークンの交換は BFF が行う。

🔴 **コールバックは「クエリ」で受ける。**フレームワーク既定はフォーム POST で、その場合コールバックが
**クロスサイト POST** になり、correlation / nonce Cookie を `SameSite=None` にせざるを得なくなる
（＝ `Secure` 必須 ＝ 平文 http のローカル開発が壊れる）。クエリで受ければトップレベル GET になり、
すべて `Lax` で通る。

🔴 **OIDC の各パスはすべて `/bff/` 配下に置く。**エッジは `/bff` と `/bff/` しか BFF へ通さず、
それ以外は SPA へ委譲する。フレームワーク既定のパス（`/signin-oidc` 等）のままでは
**認可サーバからのコールバックが BFF に届かない。**

| 用途 | パス |
| --- | --- |
| ログイン開始 | `/bff/auth/login` |
| コールバック | `/bff/auth/callback` |
| ログアウト | `/bff/auth/logout` |
| ログアウトのコールバック | `/bff/auth/logout-callback` |
| バックチャネルログアウト受け口 | `/bff/auth/backchannel-logout` |
| 現在の身元 | `/bff/auth/me` |

## 4. CSRF 対策

**`SameSite=Lax` ＋ カスタムヘッダ検証**を用いる。壁は 2 枚ある。

| 攻撃 | 何が止めるか |
| --- | --- |
| 別サイトからの `fetch`（ヘッダ無し）・`<form>` 送信 | **`SameSite=Lax`** —— Cookie が付かない。到達しても未認証で 401 |
| 別サイトからの カスタムヘッダ付き `fetch` | **preflight** —— 非単純リクエストになり、**BFF に CORS 許可が無いのでブラウザが遮断** |

**SPA 側の実装は 1 箇所だけである。**生成クライアントの唯一の出口（`foundation/api` の mutator）で
全リクエストにヘッダを 1 つ付ける。個々の呼び出し側は何もしない。

> 🔴 **この方式は「SPA と BFF が同一オリジンで、BFF に CORS 許可が無い」ことの上に立っている。**
> **BFF に CORS 許可を入れる**か **SPA と BFF を別オリジンにする**決定が出たら、**壁が 1 枚に減るので
> トークン方式へ寄せ直すこと。**判断の根拠と条件は実装 ADR にある。

## 5. 失効

**セッション実体はサーバ側のストアに置く。**Cookie はセッションキーだけを運ぶ。

- **利用者単位の即時失効**: そのセッションをストアから削除する
- **認可サーバ側の操作に追随する**: バックチャネルログアウトの受け口で該当セッションを削除する

🔴 **やってはいけないこと（計画が明示的に禁じている）**

- **アクセストークンの有効期限を短くする方式（移行前の暫定措置）を引き継ぐこと。**
  サーバ側セッションになった以上、失効は即時に行える
- **後段サービスでリクエストごとに失効リストを問い合わせること。**
  毎リクエストの問い合わせはこの方式と同等のコストになる

## 6. 複数レプリカで動かすときの注意

🔴 **Cookie を保護する鍵を、レプリカ間で共有すること。**

共有していないと、**利用者のリクエストが別のレプリカへ振られた瞬間に Cookie を復号できず、
ログアウトしたように見える。**

**この欠陥は単体テストでは絶対に捕まらない。**テストは 1 プロセスで動くので鍵が 1 つしか無く、
**共有し忘れていても緑になる。**確かめるなら次のどちらかを置く。

1. **2 レプリカ以上を起こす統合テスト**
2. **鍵の永続化先が設定されていることを、構成の側から固定する検査**

**どちらも置かずに「テストが緑だから大丈夫」と読まないこと。**

## 7. 別系統であるもの

**MCP サーバの認証はブラウザセッションとは別系統である。**本書の対象は
ブラウザ ↔ BFF のセッションのみで、MCP の認可は別の仕組みに従う。混ぜないこと。
