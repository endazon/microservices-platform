# BFF セッション設計 実装ガイド

ブラウザと BFF の間のセッションを実装・運用するための入口である。**論拠は実装 ADR が持ち、本書は
運用手順と設定値の所在を持つ。**同じ値を両方へ書かない（複写した瞬間に、片方が古くなる）。

## 0. この設計が満たすもの

**アクセストークンをブラウザへ一切出さない。**ブラウザが持つのは HttpOnly Cookie のセッションキーだけで、
アクセストークンとリフレッシュトークンは BFF 側のセッションストアにのみ置く。

**利用者の無効化・退職時に全セッションを即時失効できる。**セッション実体をサーバ側に置くため、
ストアから削除した瞬間に失効する。

## 1. Cookie 属性

| 属性 | 値 | 備考 |
| --- | --- | --- |
| `HttpOnly` | 有効 | スクリプトから読めない |
| `Secure` | **常に有効** | フレームワーク既定は「リクエストと同じ」なので**明示して固定する** |
| `SameSite` | `Lax` | CSRF の 1 枚目の壁（§4） |
| `Path` | `/` | SPA と BFF は同一オリジンで、SPA 側のパスからも送出される必要がある |
| 名前 | `__Host-` 接頭辞を付ける | 接頭辞は `Secure` ＋ `Path=/` ＋ `Domain` 無しを**ブラウザ側で強制**する。上の 3 行と整合する |

**correlation / nonce Cookie も `Lax` にする。** 既定は `SameSite=None`（＋ `Secure` 必須）であり、
そのままだと平文 http のローカル開発でログインが壊れる。§3 の `query` 化とセットで `Lax` にできる。

## 2. 有効期間と「記憶」30 日

🔴 **数値を本書へ書き写さない。** 認可サーバ（Keycloak）の realm 定義が唯一の情報源である。

- 「記憶」を選んだセッションの寿命は realm の **remember-me 用のアイドル/最大寿命**に従う
- 選ばなかった場合は realm の通常値（未設定なら認可サーバの既定）に従う
- **フレームワーク既定の 14 日には根拠が無い。**必ず realm の値へ合わせる

**テストは realm 定義を読んで突き合わせる**（期待値をテストコードへ直書きしない）。
realm を変えたときにテストが追随せず緑のまま、という状態を作らない。

## 3. ログイン経路

**Authorization Code + PKCE を BFF が実施する。**ブラウザは認可サーバへ往復するだけで、
コードとトークンの交換は BFF が行う。

🔴 **コールバックは「クエリ」で受ける。**フレームワーク既定はフォーム POST で、その場合コールバックが
**クロスサイト POST** になり、correlation / nonce Cookie を `SameSite=None` にせざるを得なくなる
（＝ `Secure` 必須 ＝ 平文 http のローカル開発が壊れる）。クエリで受ければトップレベル GET になり、
すべて `Lax` で通る。

🔴 **OIDC の各パスはすべて `/bff/` 配下に置く。**エッジは `/bff` と `/bff/` しか BFF へ通さず、
それ以外は SPA へ委譲する。フレームワーク既定のパス（`/signin-oidc` 等）のままでは
**認可サーバからのコールバックが BFF に届かない。**

| 用途 | パス |
| --- | --- |
| ログイン開始 | `/bff/auth/login`（`returnUrl` は自サイト内のパスに限る） |
| コールバック | `/bff/auth/callback` |
| ログアウト | `/bff/auth/logout`（GET。**`sid` クエリ必須**・§4） |
| ログアウトのコールバック | `/bff/auth/logout-callback` |
| バックチャネルログアウト受け口 | `/bff/auth/backchannel-logout`（§5） |
| 現在の身元 | `/bff/auth/me`（`logoutUrl` を配る唯一の口） |

**SPA の側に認証ロジックは無い。** ログイン・ログアウトはトップレベル遷移で、身元は
`/bff/auth/me` を読むだけである。ロールも同端点の `roles` が一次情報である。

**アクセストークンの更新（refresh）は BFF が行う。** セッションの寿命はアクセストークンの寿命より
桁で長いため、毎認証時に期限を見て refresh_token グラントで更新する。🔴 **refresh を認可サーバに
拒まれたら、その場でセッションを破棄して 401 にする**（無効化・失効の第 2 の即時反映経路。
一過性の障害でもログアウト側へ倒す —— 可用性より失効の確実性を採る）。
**オフライン用の長命トークンは要求しない** —— 認可サーバ側のセッション終了後も生き残り、
「無効化 → 即時失効」と逆向きになるためである。

**下流サービスへの資格情報**は、セッションに保存済みのアクセストークンを **BFF が受信リクエストの
Authorization ヘッダへ昇格**して運ぶ（各端点の透過転送は無改修。応答には決して載らない）。

## 4. CSRF 対策

**`SameSite=Lax` ＋ カスタムヘッダ検証**を用いる。壁は 2 枚ある。

| 攻撃 | 何が止めるか |
| --- | --- |
| 別サイトからの `fetch`（ヘッダ無し）・`<form>` 送信 | **`SameSite=Lax`** —— Cookie が付かない。到達しても未認証で 401 |
| 別サイトからの カスタムヘッダ付き `fetch` | **preflight** —— 非単純リクエストになり、**BFF に CORS 許可が無いのでブラウザが遮断** |

**SPA 側の実装は 1 箇所だけである。**生成クライアントの唯一の出口（`foundation/api` の mutator）で
全リクエストにヘッダを 1 つ付ける。個々の呼び出し側は何もしない。

> 🔴 **この方式は「SPA と BFF が同一オリジンで、BFF に CORS 許可が無い」ことの上に立っている。**
> **BFF に CORS 許可を入れる**か **SPA と BFF を別オリジンにする**決定が出たら、**壁が 1 枚に減るので
> トークン方式へ寄せ直すこと。**判断の根拠と条件は実装 ADR にある。

**ログアウトだけは GET であり、上の 2 枚の壁の外にある。** 認可サーバへの往復はトップレベル
ナビゲーションでしか完結せず、そこにはカスタムヘッダを付けられないためである。代わりに
**セッションの `sid` と一致するクエリを要求する** —— `sid` は HttpOnly セッションの中にしか無く、
`/bff/auth/me` の `logoutUrl` だけが配る。攻撃者のページは知り得ないので、強制ログアウト CSRF は
成立しない。**`sid` を持たない・一致しない要求は拒否し、セッションは生き続ける。**

## 5. 失効

**セッション実体はサーバ側のストアに置く。**Cookie はセッションキーだけを運ぶ。

- **利用者単位の即時失効**: そのセッションをストアから削除する
- **認可サーバ側の操作に追随する**: バックチャネルログアウトの受け口が `logout_token` を検証し
  （署名・発行元・宛先・寿命・ログアウトイベントの存在・nonce の不在・sub の存在）、
  **その利用者の全セッション**をストアから削除する。失効の単位は利用者（subject）であり、
  個別セッションより広い —— **過剰失効側（安全側）へ倒す**
- **refresh の拒否も失効である**: バックチャネルが届かなくても、次の refresh（アクセストークンの
  期限、分単位）で認可サーバの拒否がセッションを殺す（§3）

### 5.1 受け口が解決するだけでは失効しない —— 「送り手の宛先」と「境界」

🔴 **バックチャネルログアウトは認可サーバが**サーバとして**BFF を叩く口である。** 認可サーバ側に
登録する宛先は、**ブラウザが開く URL 群とは別系統**であり、同じ値を書くと**一度も届かない**。
届かない失敗は静かで、認可サーバのログに 1 行残るだけ、管理者の画面には「ログアウトさせた」と映る。
そのとき実際に効いているのは refresh 拒否だけであり、**「即時失効」ではなく「アクセストークンの
寿命ぶん遅れる失効」に縮退している。**

宛先の選び方（実測でここまで絞られた）:

- **ブラウザ向けのエッジ host を書かない。** 裸の `localhost` は pod の `/etc/hosts` が
  必ず pod 自身へ向けるので、クラスタ DNS をどう設定しても宛先にならない。
- **`*.localhost` のエッジ host も書かない。** クラスタ DNS は正しく答えるが、
  **認可サーバのイメージ（UBI9 系 / glibc）の名前解決が `.localhost` を引かない**
  （同じ pod の netns に musl のコンテナを足すと同じ名前が解決する）。
- **クラスタ内の素のサービス名を書く**（`http://<bff の Service 名>:<port>/bff/auth/backchannel-logout`）。
  素の名前にしてあるのは、同じ realm ファイルをコンテナ合成の経路も読むためで、
  足りない側にはエイリアスを置く（k8s は ExternalName、コンテナ合成はネットワーク別名）。

🔴 **認可サーバがメッシュの外に居る配備では、宛先を直すだけでは届かない。** 相互 TLS が STRICT だと
Envoy が平文流入を落とす（接続は張れて即座に切られるので、ログの見た目だけが「接続拒否」から
「接続リセット」へ変わる）。開ける範囲は**最小にする** —— BFF の受信ポートだけを PERMISSIVE にし、
**principal を持たない（＝平文の）要求はバックチャネルの URI 以外へ通さない**拒否規則を併せて置く。
開けた口の安全性は署名済みの `logout_token` 検証が担う（この端点は本来インターネットに面する口であり、
平文で到達できること自体は資格ではない）。恒久像は認可サーバをメッシュへ入れることである。

🔴 **realm を差し替えても、既に立っている認可サーバには届かない。** インポートは同名 realm が在ると
**黙って飛ばす**ため、宛先の変更は冪等な後追い（管理 CLI）で当てる。ローカル起動スクリプトが
その後追いを呼ぶ。

🔴 **やってはいけないこと（計画が明示的に禁じている）**

- **アクセストークンの有効期限を短くする方式（移行前の暫定措置）を引き継ぐこと。**
  サーバ側セッションになった以上、失効は即時に行える
- **後段サービスでリクエストごとに失効リストを問い合わせること。**
  毎リクエストの問い合わせはこの方式と同等のコストになる

## 6. 複数レプリカで動かすときの注意

🔴 **Cookie を保護する鍵を、レプリカ間で共有すること。**

共有していないと、**利用者のリクエストが別のレプリカへ振られた瞬間に Cookie を復号できず、
ログアウトしたように見える。**

**この欠陥は単体テストでは絶対に捕まらない。**テストは 1 プロセスで動くので鍵が 1 つしか無く、
**共有し忘れていても緑になる。**確かめるなら次のどちらかを置く。

1. **2 レプリカ以上を起こす統合テスト**
2. **鍵の永続化先が設定されていることを、構成の側から固定する検査**

**どちらも置かずに「テストが緑だから大丈夫」と読まないこと。**

## 7. 構成の供給（配備）

🔴 **この設計はコードだけでは動かない。配備が構成を供給して初めて成立する。**
供給が無いと、ログイン開始が 500 になり、バックチャネル受け口はパスすら解決されない
（配線もテストも揃ったまま、稼働環境でだけ成立しない状態になる）。**実際に一度そうなった。**

**認可サーバのクライアント秘密は配備から注入する。**チャートにも compose にも実値を書かない。
供給経路は他の連携ツール（オブジェクトストレージ・可観測性・秘密管理）の秘密と**同じ形**にそろえる ——
秘密管理から同期して Secret を作り、Secret から環境変数として渡す。**同じ用途に 2 つ目の形を作らない。**

🔴 **realm 側に置かれた開発用の値と、注入する値は一致させること。**片方だけ変えると、
認可サーバは「クライアント認証に失敗」を返し、ログイン開始が 500 のままになる。

🔴 **秘密の参照は任意（optional）にしない。**任意にすると、注入漏れが「起動はする。ログインのときだけ
500」へ倒れ、ヘルスチェックは緑のままになる。**注入漏れは起動失敗にする。**

**エッジが TLS を終端する配備では、転送ヘッダを解釈させること。**解釈しないと、BFF は受け取った
リクエストの scheme（エッジから先は平文）でコールバック URL を組み、認可サーバに登録された
https のものと一致せず弾かれる。**秘密を入れただけでは往復は完了しない**（応答は「クライアント認証の
失敗」から「コールバック URL が不正」へ変わるだけで、同じ 500 に見える）。

**それ以外の設定値はコードの既定に委ねている。**寿命は認可サーバの realm が唯一の情報源であり
（§2）、Cookie 名は接頭辞の条件と結びついていて配備で差し替えられる値ではない。
**委ねる判断の根拠は実装 ADR にある。ここへ値を書き写さない。**

**注入漏れは機械で止める。**「秘密から注入する」と宣言した設定値が配備の両経路（チャートと compose）に
実在することを、検査器が突合する（[`scripts/README.md`](../../scripts/README.md)）。

## 8. 別系統であるもの

**MCP サーバの認証はブラウザセッションとは別系統である。**本書の対象は
ブラウザ ↔ BFF のセッションのみで、MCP の認可は別の仕組みに従う。混ぜないこと。
