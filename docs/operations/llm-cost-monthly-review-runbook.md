# Runbook: LLM 費用の月次確認

- **これは暫定の統制である。** Alertmanager が配備されたら本 Runbook は**終了する**（§終了条件）。
- 正は計画書 `06_technical/05_observability-ops.md` **§LLM 費用の上限アラートと暫定の統制**
  （2026-08-08 確定。決定 39〜41）。**計画が定めるのは「毎月 1 回確認する」までで、
  手順・担当・記録は本書が定める。**

## ⚠ 前提 —— **いま何が見えていて、何が見えていないか**

**この節を読まずに手順へ進まない。** 本 Runbook が与えるのは「気づく機会」であって「保証」ではない。

| 事実 | 状態 |
| --- | --- |
| **自動検知** | **無い。** Alertmanager が未配備で、`prometheus.yml` の `alertmanagers.targets` は空である。**超過してもアラートは飛ばない** |
| **費用そのもの（金額）** | **見えない。** トークン消費量・金額換算・単価表はいずれも**未実装**（[[IADR-0110]] §結果 フォローアップ 2 / #443） |
| **月次予算の金額（しきい値）** | **未確定。** 実測を待って確定する（計画 決定 41）。**本書は絶対額で判定しない** |
| **見えるもの** | **`llm_completion_total`＝補完の呼び出し回数**（用途別・モデル別・送信可否別）。**費用の代理指標**である |
| **検知の遅れ** | **最大 1 か月。** 月初に確認した直後から月末までに超過した場合、気づくのは翌月である（計画が受け入れた帰結） |

> **★ 呼び出し回数は費用ではない。** 1 回あたりのトークン数はプロンプトと応答の長さで大きく変わるため、
> **回数が横ばいでも費用は増えうる**。上位モデルの比率が上がった場合も同様である
> （だからモデル別のパネルを見る）。**この限界を承知したうえで運用する。**

## 担当と頻度

| 項目 | 定め |
| --- | --- |
| **担当** | **運用者ロール（`platform-operator`）を持つ者。** 月ごとに 1 名を決める（複数人で分担しない —— 「誰かがやっているはず」で抜ける） |
| **頻度** | **毎月 1 回。翌月の第 1 営業日**に前月分を確認する（月末締めの数値が出そろってから見る） |
| **所要** | 10 分程度 |

## 手順

1. **Grafana を開く。** SC-10（運用ダッシュボード）の **Grafana 導線カード**から入る
   （SC-10 に費用の KPI カードは無い。2026-08-05 裁定 Q26 により意図的に外してある）。
2. ダッシュボード **`LLM Usage (proxy for cost — NOT cost)`**（uid: `llm-usage`）を開く。
   実体は [`deploy/grafana/provisioning/dashboards/llm-usage.json`](../../deploy/grafana/provisioning/dashboards/llm-usage.json)。
3. **時間範囲を前月 1 か月に合わせる。** ダッシュボードの既定は直近 30 日であり、**前月とは一致しない**。
   累計系のパネル（用途別 / モデル別 / 送信可否）は**選択した範囲に追随する**ので、ここを合わせないと
   別の期間の数字を前月として記録することになる。**前月比のパネルだけは範囲に依らない**（固定 30 日 ＋ 30 日前との比）。
4. 次の 4 点を見る。**絶対額のしきい値は使わない**（決定 41）。

   | 見るもの | パネル | 注意して見る点 |
   | --- | --- | --- |
   | **前月比の増減** | 前月比（用途別）**※範囲に依らない** | **1.0 を大きく超える用途**が無いか。目安として **1.5 倍**を超えたら §増加を認めたとき へ |
   | **月内累計の推移** | 選択期間の累計（用途別 / モデル別） | 月の後半で**傾きが急に立っていない**か（月末に集中している用途は翌月に跳ねやすい） |
   | **モデル構成の変化** | 選択期間の累計（モデル別） | **上位モデルの比率が上がっていないか**。回数が同じでも費用は増える |
   | **無駄の増加** | 拒否率 / max_tokens 打ち切り率 | どちらも**費用は発生して成果が無い**分である。上昇していれば設定を見直す |

5. **記録する**（§記録）。**「異常なし」も記録する** —— 記録が無いと「確認しなかった」と区別が付かない。

## 増加を認めたとき

**本 Runbook は原因究明までは定めない。** 次のいずれかへ引き渡す。

| 兆候 | 引き渡し先 |
| --- | --- |
| 特定の用途が急増した | その用途の呼び出し元を調べる（`llm_purpose` の値と `appsettings` の `PurposeModels` が対応） |
| `llm_purpose="other"` が増えた | **定義していない purpose が来ている**＝ルーティングが既定へ落ちている（[[IADR-0110]]）。設定の追随漏れを疑う |
| 上位モデルの比率が上がった | 用途別モデル割当の見直し |
| 拒否率・打ち切り率が上がった | [`docs/observability/llm-completion-metrics.md`](../observability/llm-completion-metrics.md) §監視観点 |
| **費用の実額を知る必要がある** | **現状では出せない。** #443 / [[IADR-0110]] §結果 フォローアップ 2 の完了を待つ |

## 記録

- **置き場所**: 本書と同じディレクトリの `llm-cost-monthly-review-log.md` へ追記する
  （**本 PR では作らない** —— 1 回目の確認時に作る。空のログを置くと「運用している」ように見える）。
- **記録する項目**: 確認日 / 担当 / 対象月 / 前月比の最大値とその用途 / モデル構成の変化の有無 /
  拒否率・打ち切り率 / 所見（**異常なしの場合もそう書く**）。
- **保存期間**: しきい値が確定するまでの実測データとして使うため**削除しない**
  （計画 決定 41「月次予算の金額は実測後に確定する」の入力になる）。

## 終了条件

**Alertmanager が配備され、上限アラートが配線された時点で本 Runbook を終了する。**

- 終了時は本書を削除せず、**frontmatter の `status` を `superseded` にし、後継（上限アラート）を明記**する。
- **手動確認と上限アラートを併存させない**（計画 決定 39）。同じ統制を 2 か所で持つと、
  どちらが正かを決める根拠が無くなる —— 2026-08-05 の裁定 Q26 が避けた形と同じである。
- 配備時期は**実環境の判断**であり、**#546 で追跡が続いている**。
