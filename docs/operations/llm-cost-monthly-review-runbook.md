# Runbook: LLM 費用の月次確認

- **これは暫定の統制である。** 上限アラートに**月次予算の金額が設定された時点で**本 Runbook は**終了する**（§終了条件）。
- 正は計画書 `06_technical/05_observability-ops.md` **§LLM 費用の上限アラートと暫定の統制**
  （2026-08-08 確定。決定 39〜41）。**計画が定めるのは「毎月 1 回確認する」までで、
  手順・担当・記録は本書が定める。**
- 🔴 **［2026-09-26 / #1111］上限アラートの配線は入った。ただし金額が未設定なので働いていない。**
  **本 Runbook は引き続き唯一の統制である**（§上限アラートの現状）。

## ⚠ 前提 —— **いま何が見えていて、何が見えていないか**

**この節を読まずに手順へ進まない。** 本 Runbook が与えるのは「気づく機会」であって「保証」ではない。

| 事実 | 状態 |
| --- | --- |
| **自動検知** | **働いていない。** 🔴 **［2026-09-26 更新 / #1111］理由がもう一度変わった。** 用途別の上限アラート（`LlmMonthlyBudgetExceeded`）は compose・経路B の Prometheus と Grafana に**配線済み**であり、Alertmanager も配備済みである。それでも鳴らないのは、**月次予算の金額が設定されていない**からである。**金額が無いとアラートは評価対象を持たず、超過しても発火しない**（誤りではなく、金額を決めていない状態そのもの）。結論は同じ —— **超過してもアラートは飛ばない** |
| **費用そのもの（金額）** | **［2026-08-23 追記］見えるようになった。** トークン消費量・金額換算・有効期間つき単価表を実装した。金額はゲートウェイが単価表を読んで換算する（Grafana のクエリに単価は無い）。**ただし下の「単価の解決漏れ」が 0 のときに限る** |
| **単価の解決漏れ** | **ダッシュボード最上段のパネルで見る。** 0 でない間は**表示されている金額が過小**である（該当する単価が無い呼び出しは金額に計上されない）。原因は単価表の期限切れかモデルの登録漏れである |
| **月次予算の金額（しきい値）** | **未確定・未設定。** 実測を待って確定する（計画 決定 41）。**本書は絶対額で判定しない。** 設定の置き場は §金額を設定する手順（所有者） |
| **見えるもの** | **`llm_cost_total`＝金額**・**`llm_tokens_total`＝トークン消費量**（いずれも用途別・モデル別）と、**`llm_completion_total`＝補完の呼び出し回数**（用途別・モデル別・送信可否別） |
| **検知の遅れ** | **最大 1 か月。** 月初に確認した直後から月末までに超過した場合、気づくのは翌月である（計画が受け入れた帰結） |

> **★ 呼び出し回数は費用ではない。** 1 回あたりのトークン数はプロンプトと応答の長さで大きく変わるため、
> **回数が横ばいでも費用は増えうる**。上位モデルの比率が上がった場合も同様である
> （だからモデル別のパネルを見る）。**この限界を承知したうえで運用する。**
>
> **★［2026-08-23 追記］金額が出るようになっても、上の 3 つ（自動検知が無い・しきい値が未確定・
> 検知の遅れが最大 1 か月）は 1 つも変わっていない。** 変わったのは「何を見るか」だけであり、
> **本 Runbook が暫定の統制であることも、終了条件も変わらない。**
>
> **★［2026-08-30 追記 / #546］Alertmanager を配備しても、上の 3 つは 1 つも変わっていない。**
> 変わったのは**自動検知が無い理由**だけである（通知基盤の不在 → しきい値の未確定）。
>
> **★［2026-09-26 追記 / #1111］上限アラートを配線しても、上の 3 つは 1 つも変わっていない。**
> 変わったのは、**金額を決めたあとに要る作業が「配線」から「設定 1 か所」に縮んだ**ことだけである。
> 🔴 **「配線されたから本 Runbook を終了する」と読まないこと。** 金額が無いアラートは何も見ていない。
> **いま終了すると、費用の統制がゼロになる** —— それは本 Runbook が生まれた原因そのものである。

## 担当と頻度

| 項目 | 定め |
| --- | --- |
| **担当** | **運用者ロール（`platform-operator`）を持つ者。** 月ごとに 1 名を決める（複数人で分担しない —— 「誰かがやっているはず」で抜ける） |
| **頻度** | **毎月 1 回。翌月の第 1 営業日**に前月分を確認する（月末締めの数値が出そろってから見る） |
| **所要** | 10 分程度 |

## 手順

1. **Grafana を開く。** 運用ダッシュボードの **Grafana 導線カード**から入る
   （同ダッシュボードに費用の KPI カードは無い。2026-08-05 裁定 Q26 により意図的に外してある）。
2. ダッシュボード **`LLM Usage & Cost`**（uid: `llm-usage`。**uid は変わっていない**）を開く。
   実体は [`deploy/grafana/provisioning/dashboards/llm-usage.json`](../../deploy/grafana/provisioning/dashboards/llm-usage.json)。
3. **時間範囲を前月 1 か月に合わせる。** ダッシュボードの既定は直近 30 日であり、**前月とは一致しない**。
   累計系のパネル（用途別 / モデル別 / 送信可否）は**選択した範囲に追随する**ので、ここを合わせないと
   別の期間の数字を前月として記録することになる。**前月比のパネルだけは範囲に依らない**（固定 30 日 ＋ 30 日前との比）。
4. 次の 6 点を、**この順で**見る。**絶対額のしきい値は使わない**（決定 41。金額が出るようになっても
   しきい値は未確定であり、判定は前月比の推移で行う）。

   | 見るもの | パネル | 注意して見る点 |
   | --- | --- | --- |
   | **🔴 単価の解決漏れ**（**最初に見る**） | 単価を解決できなかった呼び出し | **0 でなければ、以下の金額はすべて過小である。** 単価表を直してから読み直す |
   | **金額の前月比** | 費用の前月比（用途別） | **1.0 を大きく超える用途**が無いか |
   | **金額の月内累計** | 費用（選択期間の累計・用途別 / モデル別） | どの用途・どのモデルが費用を出しているか |
   | **前月比の増減** | 前月比（用途別）**※範囲に依らない** | **1.0 を大きく超える用途**が無いか。目安として **1.5 倍**を超えたら §増加を認めたとき へ |
   | **月内累計の推移** | 選択期間の累計（用途別 / モデル別） | 月の後半で**傾きが急に立っていない**か（月末に集中している用途は翌月に跳ねやすい） |
   | **モデル構成の変化** | 選択期間の累計（モデル別） | **上位モデルの比率が上がっていないか**。回数が同じでも費用は増える |
   | **無駄の増加** | 拒否率 / max_tokens 打ち切り率 | どちらも**費用は発生して成果が無い**分である。上昇していれば設定を見直す |

5. **記録する**（§記録）。**「異常なし」も記録する** —— 記録が無いと「確認しなかった」と区別が付かない。

## 増加を認めたとき

**本 Runbook は原因究明までは定めない。** 次のいずれかへ引き渡す。

| 兆候 | 引き渡し先 |
| --- | --- |
| 特定の用途が急増した | その用途の呼び出し元を調べる（`llm_purpose` の値と `appsettings` の `PurposeModels` が対応） |
| `llm_purpose="other"` が増えた | **定義していない purpose が来ている**＝ルーティングが既定へ落ちている（補完メトリクスの設計を参照）。設定の追随漏れを疑う |
| 上位モデルの比率が上がった | 用途別モデル割当の見直し |
| 拒否率・打ち切り率が上がった | [`docs/observability/llm-completion-metrics.md`](../observability/llm-completion-metrics.md) §監視観点 |
| **費用の実額を知る必要がある** | **［2026-08-23］費用のパネルで読める。** ただし単価の解決漏れが 0 であることを先に確かめる |

## 記録

- **置き場所**: 本書と同じディレクトリの `llm-cost-monthly-review-log.md` へ追記する
  （**本 PR では作らない** —— 1 回目の確認時に作る。空のログを置くと「運用している」ように見える）。
- **記録する項目**: 確認日 / 担当 / 対象月 / **単価の解決漏れの件数** / **金額（用途別の合計）** /
  前月比の最大値とその用途 / モデル構成の変化の有無 / 拒否率・打ち切り率 /
  所見（**異常なしの場合もそう書く**）。
- **保存期間**: しきい値が確定するまでの実測データとして使うため**削除しない**
  （計画 決定 41「月次予算の金額は実測後に確定する」の入力になる）。
  **次の §金額を設定する手順 で金額を決めるときの根拠になるのは、この記録である。**

## 上限アラートの現状（［2026-09-26 / #1111］配線済み・金額未設定で不活性）

| 部品 | 状態 |
| --- | --- |
| ルール `LlmMonthlyBudgetExceeded` | **配線済み。** compose（`deploy/prometheus/alerts.yml`）・経路B の Prometheus inline・Grafana の provisioning（compose・経路B）の 4 か所に同じ式で入っている |
| 式 | 用途ごとに **直近 30 日の `llm_cost_total`** と **ゲージ `llm_budget_monthly_limit`** を比べる。**金額も単価も式に無い** |
| 上限のゲージ | LLM ゲートウェイが設定 `Llm:Budget:MonthlyLimits` を読んで出す。**設定された用途だけが系列を持つ** |
| **金額** | 🔴 **未設定（既定は無い）。** したがってゲージの系列は無く、**アラートは評価対象を持たず発火しない** |

**読み方の注意**:

- **上限は用途ごとである。総額 1 本の上限は無い。** 用途には利用側プロジェクトの用途（取引判断など）が
  含まれ、計画は基盤と利用側の費用を合算して 1 つの数値にすることを禁じている。**金額を置く用途だけが監視される。**
- **窓は暦月ではなく直近 30 日である。** 発火は「直近 30 日の費用 > 予算」で起き、解消（resolved）は月初ではなく
  **超過分が 30 日の窓から抜けたとき**に来る。月次確認（暦月）と数字がずれるのはそのためである。
- **単価の解決漏れが 0 でない間、アラートも過小に評価する**（金額に積まれない呼び出しがあるため）。
- **金額が無い間に「系列が無い」ことを鳴らすアラートは置かない。** 置けば恒常的に鳴り続け、
  本物の通知を握り潰す習慣を作る。

## 金額を設定する手順（所有者）

🔴 **金額を決めるのは所有者（利用者）である。実装側は数字を置かない。** 計画は「月次予算の金額は
実測を待って確定する」と定めており、確定の前提は**費用の実績が数か月分そろうこと**である（§記録 がその入力）。
以下は、金額を決めたあとの作業手順である。

### 1. 金額を置く（単一の置き場）

**置き場は 1 か所だけである**: `src/platform/backend/Services/LlmGateway/appsettings.json` の
`Llm:Budget:MonthlyLimits`（用途 → 金額）。

```json
"Budget": {
  "MonthlyLimits": {
    "rag-answer": <金額>,
    "trade-decision": <金額>
  }
}
```

- **キー**は `Llm:Routing:PurposeModels` のキー（同じファイル）か `default`。**それ以外は起動時に落ちる**
  （綴り違いを黙って読み飛ばすと、系列は出るのに費用と突き合わず「設定したのに鳴らない」になるため）。
- **金額**は正の値。**通貨は単価表の通貨**（同じファイルの `Llm:Pricing:Currency`。既定 USD）。
- **監視しない用途は書かない**（書いた用途だけが監視される）。
- 🔴 **deploy 側（helm の values・経路B の values・compose の environment）に
  `Llm__Budget__MonthlyLimits__<用途>` の環境変数として置かない。** 置き場が経路ごとに割れる。
  下の 3 の実演で一時的に使う上書きは**コミットしない**。
- 金額は**イメージに焼き込まれる**（`appsettings.json`）ので、再ビルドと再配備で反映される（単価表と同じ）。

### 2. 同じ変更で本 Runbook を終了させる（併存させない）

**金額を設定する PR の中で**、本書の frontmatter の `status` を `superseded` にし、冒頭に後継
（上限アラート `LlmMonthlyBudgetExceeded`）を明記する。あわせて運用仕様書 §監視・アラート / §未決事項 と
`llm-usage` ダッシュボードの説明の「自動検知はまだ働いていない」を書き換える。

🔴 **片方だけでは CI が落ちる。** `node scripts/scripts.test.js`（CI の scripts-tests ジョブ）が
「金額が設定されている」と「本 Runbook が `superseded`」の**食い違いを両向きとも**落とす
（金額を置いたのに Runbook が残る＝併存、Runbook を閉じたのに金額が無い＝統制ゼロ）。

### 3. 系列が出ることを確かめる（配備後）

前提: 経路B では**転送構成が有効**であること（既定の collector は debug だけの fail-safe で、
アプリのメトリクスは Prometheus へ届かない。`deploy/prometheus/alerts.yml` 冒頭の検証手順を参照）。

```bash
# compose（Prometheus は host の 9090）
curl -s 'http://localhost:9090/api/v1/query' \
  --data-urlencode 'query=count by (llm_purpose, llm_currency) (llm_budget_monthly_limit)'

# 経路B
kubectl -n platform-infra exec deploy/prometheus -- \
  wget -qO- 'http://localhost:9090/api/v1/query?query=count%20by%20(llm_purpose%2C%20llm_currency)%20(llm_budget_monthly_limit)'
```

- **設定した用途の数だけ系列が返ること**を確かめる。🔴 **0 件を「無い」と読む前に陽性対照を置く** ——
  同じ問い合わせ方で `count(llm_completion_total)` が非ゼロを返すことを見る（ゲートウェイの計器が
  そもそも届いていない可能性を先に潰す）。
- ルールが読まれていることは Prometheus の `/api/v1/rules` で `LlmMonthlyBudgetExceeded` を探して確かめる。

### 4. 意図的に発火させて届くことを確かめる（本番ではない環境で）

**配線したことは届くことの証明にならない。** 本番ではない環境で一度だけ実演する。

1. **前提**: 対象の用途に、直近 30 日の費用（`llm_cost_total`）が 0 より大きい系列があること
   （実 LLM 呼び出しの実績が要る。無ければ発火させようがない）。
2. その環境のゲートウェイにだけ、**ごく小さい金額**を一時的に与える（例: 経路B なら
   `Llm__Budget__MonthlyLimits__<用途>` を Deployment の環境変数へ一時的に足して再起動する）。
   **この上書きはコミットしない。**
3. `for: 5m` を待ってから Alertmanager を見る。

   ```bash
   # compose
   curl -s http://localhost:9093/api/v2/alerts
   # 経路B
   kubectl -n platform-infra exec deploy/alertmanager -- wget -qO- http://localhost:9093/api/v2/alerts
   ```

   `labels.alertname` が `LlmMonthlyBudgetExceeded`・`labels.llm_purpose` が対象の用途で、
   `status.state` が `active` の要素が現れることを確かめ、**出力を PR か issue に貼る**。
4. **一時的な上書きを外して元へ戻す**（再起動）。系列が設定どおりに戻ったことを 3 の問い合わせで確かめる。

## 終了条件

**上限アラートに月次予算の金額が設定された時点で本 Runbook を終了する。**

> **★［2026-08-30 追記 / #546］／［2026-09-26 更新 / #1111］3 条件のうち 2 つが満たされた。本 Runbook は終了しない。**
>
> | 条件 | 状態 |
> | --- | --- |
> | Alertmanager が配備されている | **満たした**（compose・経路B の両方。発火が届くことを実測） |
> | 上限アラートが配線されている | **満たした**（2026-09-26。4 か所に同じ式。金額はゲートウェイの設定から読む） |
> | **月次予算の金額が設定されている** | **満たしていない。** 計画側で未確定であり、実装側で数字を決めない（計画 決定 41）。設定は所有者が §金額を設定する手順 で行う |
>
> **条件を「かつ」で書いてある。配線だけで終了させないためである。**
> **本書を終了するのは、金額を設定するのと同じ変更である**（上の手順 2。CI が食い違いを落とす）。

- 終了時は本書を削除せず、**frontmatter の `status` を `superseded` にし、後継（上限アラート）を明記**する。
- **手動確認と上限アラートを併存させない**（計画 決定 39）。同じ統制を 2 か所で持つと、
  どちらが正かを決める根拠が無くなる —— 2026-08-05 の裁定 Q26 が避けた形と同じである。
- 🔴 **前月比の推移を読む作業そのものは終了後も有用である**が、それは統制ではなく分析である。
  終了後に続けるなら、本書ではなく別の分析手順として置く（併存を避けるため）。
