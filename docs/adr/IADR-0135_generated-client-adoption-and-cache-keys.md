## コンテキストと課題

[[IADR-0131]] 決定 1 は「**OpenAPI を変えると SPA の型検査が落ちる**」という保証を掲げ、#520 が
応答スキーマを `required` で必須化してその前提を整えた。**しかし画面は `apiFetch` ＋ 手書き型のままで、
保証が届いていたのは SC-08 の 1 画面だけだった**——#520 の変異試験 M6（`DriftFindingDto.detail` 削除）と
M7（`SearchResponse.totalHits` 削除）は、いずれも **`typecheck exit=0` で素通り**した。

本 ADR は 9 ファイル（`features/sc*/use*.ts` の 10 本から、載せ替え済みの SC-08 を除いた数）を
生成物へ載せ替えるにあたって必要になった判断を記録する。着手時の実測は作業仕様書 §着手時の実測 を正とする。

**#506 の申し送りと実測が食い違った点が 3 つある**（それぞれ設計に影響した）。

| # | #506 の申し送り | 実測 |
| --- | --- | --- |
| 1 | SC-02 は `useBffSearch` へ載せ替える | **`useBffSearch` は mutation である**（POST）。照会には使えない（論点 B） |
| 2 | 落とし穴は 5 点（封筒・エラー・キー・MSW・変異試験） | **6 点目がある**——**テストのモック層が `apiFetch` に当たっており、載せ替えると 13 ファイルが一斉に赤くなる**（論点 D） |
| 3 | （言及なし） | **生成フックの `TError` は OpenAPI のエラー応答から `void` になる**。`error instanceof ApiError` が**型エラーになる**（論点 E） |

## 検討した選択肢

### 論点 A: 応答封筒（`{ data, status, headers }`）をどこで剥がすか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A1 | **`select` で剥がす**（共有ヘルパ `okData`） | 画面が読む `query.data` の形が**載せ替え前と同じ**になり、画面側の読み出しコードを書き換えずに済む。TanStack の想定どおりの使い方 |
| A2 | 画面が `data.data` を読む（SC-08 と同じ形） | 追加の道具が要らない。**9 画面すべての読み出し箇所**を書き換えることになり、挙動を変えない作業に無関係な差分が増える |
| A3 | フックの戻り値を組み立て直す（`{ ...query, data: 本文 }`） | 画面は無改修。**スプレッドで tracked property の最適化が壊れ**、getter で作られた `queryKey` も落ちる |

### 論点 B: SC-02（検索）をどう載せるか

`/bff/search` は **POST** であり、orval は POST を `useMutation` として生成する。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B1 | **生成された操作関数 `bffSearch` を `useQuery` の `queryFn` に据える** | 型・URL・出口はすべて生成物由来。キャッシュ設計（[[IADR-0126]] 決定 3）が保たれる。**生成「フック」は使わない**という一点だけが例外になる |
| B2 | `useBffSearch`（mutation）へ載せ替える | 申し送りどおりだが**画面の挙動が変わる**——キャッシュに載らず、`?q=` での自動取得・戻る操作の即時表示が失われる |
| B3 | OpenAPI 側で `GET /bff/search` を足す | 契約が実装と食い違う（BFF は POST しか持たない）。**契約を画面の都合で曲げる** |
| B4 | 載せ替えない（`apiFetch` のまま） | 差分は最小。**受け入れ基準（M7 の再実行で落ちること）を満たせない**——`SearchResponse` を読むのは SC-02 だけである |

### 論点 C: キャッシュキーと無効化

生成キーは **URL 1 要素**（`['/bff/admin/config']`）である。TanStack Query の部分一致は**配列の要素単位**で
照合するため、`['/bff/admin/config']` は `['/bff/admin/config/drift']` に**当たらない**。
SC-11 が持っていた「1 回の無効化で 3 本」（階層キー `['bff','admin','config']` の前方一致）は成立しない。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C1 | **3 本を明示的に無効化する** | 挙動が保たれる（テストが「再取得で 3 本飛ぶ」を固定している）。**無効化の対象が 1 か所に列挙され読める** |
| C2 | 生成フックへ `queryKey` を渡して旧キー（階層キー）を維持する | 前方一致が復活する。**同じ URL に 2 つのキャッシュ実体ができる**——別の呼び出し箇所が生成キーのまま使うと、無効化が片方に効かない。**生成キーが正であるという単一情報源が壊れる** |
| C3 | `predicate` で URL の文字列前方一致を見る | 1 行で済む。**`/bff/admin/configuration` のような将来のパスまで巻き込む**（文字列前方一致はパス境界を知らない） |
| C4 | `invalidateQueries()`（引数なし＝全無効化） | 最短。**画面外のクエリまで再取得する** |

### 論点 D: 画面テストのモック層をどうするか

生成コードは mutator（`bffFetch`）→ **`apiRequest`** を通る。`apiFetch` を差し替えても効かない。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| D1 | **`apiRequest` を差し替える**（SC-08 の先例と同じ） | 差し替え点が 1 つ。**パス文字列が変わらない**ので既存の期待値がほぼそのまま使える。応答は `Response` 相当を作る必要がある |
| D2 | 生成された MSW モック（`*.msw.ts`）＋ `msw` のサーバへ移行する | fixture が契約由来になる。**13 ファイルの fixture を一斉に置き換える**ことになり、「挙動が変わっていない」ことの確認と混ざる。`setupServer` の導入も要る |
| D3 | `global.fetch` を差し替える | 実物に最も近い。**実行時 config・認証ヘッダまでテストの関心事になる**（`apiRequest` の責務を各テストが再実装する） |

### 論点 E: 生成フックの `TError` をどうするか

生成フックの `TError` の既定は OpenAPI のエラー応答から導かれ、**多くの面で `void`** になる。
`query.error` が `void | null` になるため、画面の `error instanceof ApiError` が
**`TS2358` で落ちる**（実測: SC-10）。

| 案 | 内容 | 評価 |
| --- | --- | --- |
| E1 | **`unknown` を明示する** | 実行時に何が飛ぶか（`ApiError` / `DOMException` / `SyntaxError`）を型で断定しない。画面は既に `instanceof` で絞っている |
| E2 | `ApiError` を明示する | 画面が絞り込み無しで `error.kind` を読める。**嘘になる**——`bffFetch` の `JSON.parse` は `SyntaxError` を投げ、中断は `DOMException` である |
| E3 | 既定（`void`）のまま画面側でキャストする | 生成物に忠実。**キャストが 9 画面へ散る**うえ、`void` は「エラーが無い」と読めて誤解を生む |

### 論点 F: SC-05 の状態遷移（1 本の分岐 → 3 本のフック）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| F1 | **3 本を束ねて公開し、画面が `DocumentCommand` で選ぶ** | 生成物をそのまま使う。[[IADR-0127]] 決定 7 の「列挙は戻り値から導く」がそのまま働く（`Object.values` が 5 本を見る） |
| F2 | 3 本を包む薄い `command` ミューテーションを自作する | 画面が無改修。**`useMutation` を手書きする**ことになり、`isPending` / `reset` / `error` を自前で合成する必要がある（[[IADR-0127]] 決定 7 が避けた「手書きの状態」そのもの） |

## 決定

**決定 1（論点 A）: A1 を採る。応答封筒は `select` で剥がし、道具は `foundation/api/orvalSelect.ts` の
`okData` 1 つに閉じる。** 型は生成物から導出する（`TResponse extends { status: 200; data: infer T }`）。

> **［実測で分かった制約］** TanStack Query の `UseQueryOptions` は `Omit<…>`（マップ型）を経由して
> 定義されているため、**`select` の戻り値から `TData` は推論されない**（既定＝封筒のままになる）。
> したがって呼び出し側は `useBffX<XDto, unknown>({ query: { … } })` と**本文型を明示する**。
> 明示した型と `okData` の戻り値は型検査で突き合わされるので、契約が変われば呼び出し側が落ちる。
> **同じ理由で `queryKey` も明示が要る**（`UseQueryOptions` は `queryKey` を必須にしている）
> ——結果として、各画面が**どの生成キーを使うか**がコード上に現れる（無効化の対象が読める）。

**決定 2（論点 B）: B1 を採る。SC-02 は生成された操作関数 `bffSearch` を `useQuery` に据える。**
「生成フックを使う」ことが目的ではなく、**契約と画面を型でつなぐ**ことが目的である。
POST で照会する面ではフックの形が合わないので、**関数だけを使い、キャッシュ設計は画面が持つ**。
手書き HTTP クライアントではない（`bffSearch` → `bffFetch` → `apiRequest` の一本道であり、
[[IADR-0121]] 決定 3 の出口の一本化は保たれる）。

**決定 3（論点 C）: C1 を採る。SC-11 は 3 本を明示的に無効化する。**
生成キーが唯一のキーであるという状態を崩さない（C2 を採ると同じ URL に 2 つのキャッシュ実体ができる）。
**SC-07 は逆に前方一致がそのまま働く**——絞り込み条件はキーの 2 要素目に載るため、
引数なしの `getBffConversionJobListQueryKey()` が全条件に当たる。**「前方一致が効くか」は
キーの構造で決まるのであって、パス文字列の見た目では決まらない。**

> **［2026-08-06 追記］本決定の射程が足りていなかった——非対称は SC-11 と SC-07 だけではなく、
> `SC-05 → SC-03` にも同じ破れがあった。**
>
> | | 一覧の無効化 | 詳細群 | 届くか |
> | --- | --- | --- | --- |
> | 載せ替え前 | `['bff','documents']` | `['bff','documents', id, …]` | **届く**（前方一致） |
> | 載せ替え後 | `['/bff/documents']` | `['/bff/documents/{id}']` / `.../content` / `.../versions` | **届かない** |
>
> 「前方一致が効くかはキーの構造で決まる」という上の一文は正しいが、**その分析を SC-11 と SC-07 に
> しか適用していなかった**。結果として、SC-05 で公開／アーカイブ／更新／削除した直後に SC-03 を
> 開くと `staleTime: 30_000`（`foundation/api/queryClient.ts`）の間だけ詳細・本文・版履歴が
> **古いまま表示される**という退行が入った（載せ替え前は届いていた）。
>
> **是正: SC-05 も C1（明示列挙）を採る。** 一覧に加えて、変更した文書の
> `getBffDocumentDetailQueryKey(id)` / `…Content…` / `…Versions…` を列挙する
> （`sc05-documents/useDocumentAdmin.ts` の `documentInvalidationKeys`）。
> 作成だけは対象 id が無く、まだキャッシュも存在しないので一覧のみで足りる。
>
> **C3（`predicate` でパス境界を見る）を採らなかった理由**: `queryKey[0]` が
> `'/bff/documents'` か `'/bff/documents/'` で始まるかを見れば `/bff/documentsX` を巻き込まずに
> 済むので、論点 C の C3 に挙げた欠点（パス境界を知らない）は消える。それでも採らないのは、
> **同じ画面（SC-11）で既に C1 を採っており、無効化の作法を 2 つに割りたくない**ためである。
> 明示列挙は「どのキーへ届くか」がコード上に列挙され読める（決定 1 の但し書きと同じ性質）。
> **載せ替え前より狭くなる点は自覚している**——階層キーは他の文書の詳細まで無効化していたが、
> 文書 X の変更で文書 Y の詳細が古くなることはない。
>
> **この退行は画面テストでは検出できない。** `foundation/testing/renderUnitRoute.tsx` の検査用
> QueryClient は `staleTime: 0` / `gcTime: 0` であり、無効化が届かなくても再マウントで必ず
> 再取得される。したがって守りは **QueryClient を直接使う単体テスト**
> （`sc05-documents/useDocumentAdmin.test.tsx`）に置いた——本番と同じ既定
> （`createAppQueryClient`）で `isInvalidated` を見る。**「一覧キー単独では届かない」という
> 非対称そのものも同ファイルが固定している**（前方一致が効くようになったら落ちる）。

**決定 4（論点 D）: D1 を採る。画面テストは `apiRequest` を差し替える。**
共通の道具（`jsonResponse` / `noContent`）を `foundation/testing/bffResponse.ts` へ置く。
**アサーションの意図は変えない**——変わるのは「要求の検証の書き方」だけである
（`('/x', { json })` → `('/x', objectContaining({ method }))` ＋ 本文の JSON 比較）。
**パス文字列は変わらない**（`bffFetch` が `/bff` 接頭辞を外して `apiRequest` へ渡す）。
D2（MSW）は**捨てていない**——fixture を契約由来にする価値は残るので、独立の作業として申し送る。

**決定 5（[[IADR-0131]] 決定 3 の改定）: 既存 2 本の `operationId` を規約へ揃える。**
`analysis-ask` → `bff-analysis-ask`、`analysis-analyze` → `bff-analysis-analyze`。
[[IADR-0131]] 決定 3 は「既存 2 本は改名しない——`useAnalysisAnalyze` の改名が SC-08 へ波及する」と
書いたが、**その波及先である SC-08 の 1 行を本作業で触るのが最も安い**（#506 §未決事項 4 が
本 issue へ送っている）。改定後、`operationId` は**例外なく** C# の `WithName` のケバブケースになる。

**決定 6（論点 F）: F1 を採る。SC-05 の状態遷移は 3 本の生成フックを束ねて公開し、
画面が `DocumentCommand`（`publish` / `archive` / `delete`）で選ぶ。**
[[IADR-0127]] 決定 7 の「ミューテーションの列挙は戻り値から導く」は**そのまま強くなる**
——束が 3 本から 5 本に増えても `Object.values` が全部を見る。

**決定 7（[[IADR-0132]] 決定 3 の引き継ぎ）: 既定値への縮退は消さない。**
生成型は #520 で必須化済みだが、**「契約上は必須」と「実行時に必ず来る」は別**である。
**本作業ではむしろ根拠が強まった**——`bffFetch` は本文が空のとき `{}` を返すため
（`orvalMutator.ts`）、配列を期待する面に配列でない値が入る経路が**型の外に実在する**。
新たに縮退を足すことはしない。

> **［2026-08-06 追記］本決定は結論こそ正しかったが、根拠として引いた経路の説明が事実と逆であり、
> そのために「守っているつもりで守れていない」コードを残した。**
>
> 当初この決定は「`?? []` を**そのまま**残す」と書き、その根拠に「`bffFetch` は本文が空なら
> `{}` を返す」を挙げていた。**`{} ?? []` は `{}` であり `??` は発火しない。**
> つまり**引用した経路こそが `??` で守れない経路**であった（`??` が守るのは `null` /
> `undefined` だけで、載せ替え前は `apiFetch` が空ボディに `undefined` を返していたから
> 効いていた）。実測すると、`/bff/admin/config/history` が 204 を返したとき
> **`TypeError: entries.map is not a function` で SC-11 のルートごとクラッシュ**した
> （develop では 4 見出しを描画していた）。SC-09 の属性・ポリシーも同じである。
>
> **是正: `??` ではなく `Array.isArray` で判定する。** 共有の `select` として
> `foundation/api/orvalSelect.ts` に `okArray` を置き、4 箇所（SC-03 版履歴 / SC-09 属性 /
> SC-09 ポリシー / SC-11 履歴）をこれへ寄せた。型の保証は `okData` と同じ
> （戻り値は `OkPayload<TResponse>` なので契約が変われば呼び出し側が落ちる）。
>
> **SC-02 で `?? EMPTY` を削除した判断は変わらない**（作業仕様書 §設計 5 の表）。
> 同じ前提から結論が分かれるのは**読み方の違い**による——SC-02 の画面は本文の
> **プロパティ**を読む（`search.data?.results ?? []`）ので、本文が `{}` でも
> `undefined` が出て `??` が効く。上の 4 箇所は**本文そのものが配列**なので `{}` が
> `.map` へ直接届く。**「`??` が効くかは、本文を丸ごと読むかプロパティを読むかで決まる」**
> ——当初はこの区別をせず、SC-02 では「削除」・他 4 箇所では「保持（根拠が強まった）」と
> 逆の結論を出していた。
>
> **SC-03 だけはクラッシュしていなかった**（実測）。`versions.data.length > 0` で節を
> 出し分けており `undefined > 0` が false になるためで、描画結果は develop と同じだった。
> それでも `okArray` へ寄せる——`VersionTable` を無条件に描く変更を入れた瞬間に同じ穴が開く。

## 理由

- **決定 1・2 に共通する軸は「何のために載せ替えるのか」である。** 目的は
  「生成フックを使うこと」ではなく「**契約が変わったら画面の型検査が落ちること**」——
  [[IADR-0131]] 決定 1 が掲げた保証を画面まで届かせることである。だから
  「フックの形が合わない面（POST の照会）では関数だけを使う」という判断が採れる。
- **決定 3 は「便利さ」ではなく「単一情報源」で決めた。** C2（旧キーの維持）は本 PR の差分を
  最小にするが、**キーの正が 2 つになる**。将来 `useBffConfigEffective` を別の場所から素直に呼んだ
  瞬間に、同じ URL の 2 つ目のキャッシュができて無効化が片方に効かない——**壊れ方が静かである**。
- **決定 4 は「テストが何を固定しているか」を守るために選んだ。** 既存テストが固定しているのは
  **画面の挙動**（DOM・文言・role・呼ばれたパスと回数）であり、モックの当て先ではない。
  当て先だけを移し、固定している内容を変えない。
- **決定 5 は ADR の改定である**（無断逸脱ではない）。[[IADR-0131]] 決定 3 の但し書き
  （「SC-08 へ波及する」）が、本作業でその波及先を触ることで消えるためである。

## 結果

- 良い影響:
  - **`features/sc*/use*.ts` の 10 本すべてが生成物に載った**（SSE を除く）。
    `apiFetch` を使う画面は **0** になり、`foundation/api` の直接利用は **SSE の `apiStream` だけ**になった。
  - **#520 の M6 / M7 が落ちるようになった**（載せ替え前は素通り）。
    契約のフィールドを消す／改名する変異が、画面の型検査で捕まる（作業仕様書 §変異試験）。
  - 手書き DTO 型（interface）が **8 ファイルぶん消えた**（SC-01 の `useAskStream.ts` は DTO 型を持って
    いなかったため、載せ替えた 9 ファイルのうち 8 つが該当する）。契約の写しが二重管理でなくなる。
  - `operationId` の規約の穴（既存 2 本の不統一）が閉じた（決定 5）。
- 悪い影響・トレードオフ（**検出しないこと**）:
  - **C# → OpenAPI の追随は人手のままである**（[[IADR-0131]] 決定 1 の但し書き）。
    本作業が届かせたのは「**OpenAPI を変えると落ちる**」までで、
    「**C# の DTO を変えると落ちる**」ではない。**C# を変えて OpenAPI を直し忘れると、
    画面は嘘の型を信じたまま緑になる。**
  - **テストの fixture は依然として型付けされていない**（`jsonResponse(body: unknown)` を経由する）。
    契約に無いフィールドを持つ fixture、必須フィールドを欠く fixture のどちらも検出されない。
    MSW（論点 D の D2）へ移せば解消するが、本作業では行っていない（フォローアップ 1）。
  - **`TError = unknown` は「どのエラーが飛ぶか」を型で語らない**（決定・論点 E）。
    画面は `instanceof` で絞る必要があり、絞り忘れても型検査は落ちない
    （`unknown` に対する読み出しは落ちるので、**握り潰しは起こらない**）。
  - **SC-02 だけがフックを使わない**（決定 2）。`/bff/search` が POST である限り残る非対称であり、
    「生成フックに載っているか」で機械的に検査することはできない。
  - **`?? 既定値` は型の上で到達しない枝として残る**（決定 7・[[IADR-0132]] 決定 3 と同じ）。

     #520 §未決事項 2 が挙げた穴はまだ空いている。
  2. **C# の非 null 性と OpenAPI の突合**（[[IADR-0131]] フォローアップ 2 ／ [[IADR-0132]] フォローアップ 1）。
     載せ替えが済んだいま、**残る穴はここだけ**である。
  3. **`orval-bff-only.cjs` に「`components.schemas` は素通りする」知見をコメントで置く**
