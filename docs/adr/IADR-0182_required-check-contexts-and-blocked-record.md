# IADR-0182: required status check の指定と、blocked:human の記録（#705）

- 状態: Accepted
- 日付: 2026-08-11
- 決定者: claude（実装）

## 起点・関連

- **NFR**（運用保守。メタ作業なので無採番。[IADR-0179](./IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 1）
- 実装 issue: **#705**（**#623 の子**・受け入れ基準 3）
- 作業仕様書: [20260811_issue-705](../specs/20260811_issue-705_required-checks-handbook.md)

## 文脈 —— **手順書は在った。そして、そのとおりにすると壊れる**

`#623` 基準 3 は「required status check にする（AI で完結しないなら手順を書き残す）」である。
**手順書を新設しようとして既存を探したところ、`docs/ai-workflow.md` §「必須チェックの有効化」が既に在った。**

**そして、そこに書かれた必須チェック名の一部は、check として存在しなかった。**

| 既存節が挙げるもの | 実在 |
| --- | --- |
| **`CI`** | **無い**（`ci.yml` の**ワークフロー名**） |
| **`Security`** | **無い**（`security.yml` の**ワークフロー名**） |
| `image-build` / `pr-title` / `CodeQL` | 在る |

PR #704 が report した **check 名 28 件を全数**で突き合わせて確認した（2026-08-11）。

> **★ 手順書どおりに設定すると develop が恒久的にマージ不能になる。**
> **同じ節が 12 行下で「`paths:` フィルタ付きを必須にすると永久 pending」と警告していた** ——
> **原因は違うが結果は同じ事故**であり、**警告文の側が原因を `paths:` に限定して書いていた。**
> **キット（`repo-template/docs/ai-workflow.md`）も同じ誤りを持つ。継承した欠陥である。**

## ★★ 決定 1: **必須にするのは「check の名前」。ワークフロー名は書かない**

GitHub Actions が report する status check の context は**ジョブ側の名前**である。
**ワークフロー名（`name:`）は context として存在しない。**

**手順書に実名の表を置く**（`build-and-test` / `lint` / `commit-messages` / `pr-title` /
`image-build` / `CodeQL` / `claude-review`）。**`CI` / `Security` / `Images` / `PR Title` は明示的に禁じる。**

## ★★ 決定 2: **「起動しないことがある」を `paths:` に限定して書かない**

既存の警告は原因を `paths:` フィルタに限定していた。**本 issue で 2 つ目の原因を実測した。**

| # | 原因 | 実測 |
| ---: | --- | --- |
| 1 | `paths:` フィルタ | 既存節が警告済み（**文書のみ**） |
| 2 | **`types:` に `reopened` が無い** | **`claude-code-review.yml` だけが該当**（他 8 ワークフローは持つ） |

**警告を「その PR で起動しないことがあるチェックを必須にしてはならない」へ一般化し、
既知の原因 2 つをその下に並べる。**

### 検査器を足す（`CLAUDE.md`「同型の事故が 2 回起きたら」の条件を満たした）

**`pull_request` で起動する全ワークフローが `types:` に `reopened` を含むことを回帰テストで固定する。**
実測で **8 / 9** が既に満たしており、**1 件直せば 9 / 9** になる。

> **★ `paths:` の側は検査器にしない。** `frontend.yml` などは**意図して** `paths:` を持ち、
> **必須にしないことで正しく運用されている**。**機械的に禁じると正当な設定を壊す。**
> **検査器にしてよいのは「例外が無いと言い切れる規則」だけ**である。

## ★ 決定 3: **`claude-review` は「必須にできる状態」にしてから候補に挙げる**

`claude-code-review.yml` の `types:` へ **`reopened` を足した**（1 行）。

**足さずに「必須にせよ」と書けば、手順どおりにした人が詰む。**
**決定 1 で見つけた誤りと同じ型の被害を、こちらは書く前に潰せる。**

## ★ 決定 4: **必須化で担保できるのは「完走」であって「指摘なし」ではない**

`claude-review` は **🔴 の指摘があっても success を返す**（採否の判断は人が行う）。
**必須にしても 🔴 のままのマージは止まらない。**

**`#623` の文言は「claude-review **完了**」であり、これと一致する。**
**「必須にすれば 🔴 が止まる」と読まれないよう手順書に明記する。**
あわせて、**AI 基盤の停止・トークン失効・レート超過で全 PR がマージ不能になる**副作用も書く。

## ★★ 決定 5: **設定できないことを、能力の不在と規則の禁止に分けて記録する**

**「できない」と書く前に実測した**（[IADR-0180](./IADR-0180_blocked-judgments-expire.md) 決定 1）。

| 経路 | 実測（**2026-08-11**） | 種別 |
| --- | --- | --- |
| MCP の GitHub ツール | branch protection / ruleset を扱うツールが**無い**（2 通りの語で全数確認） | **能力の不在** |
| `gh` / `hub` CLI | **どちらも入っていない** | **能力の不在** |
| GitHub API を直接叩く | **セッション指示が禁じている** | **規則による禁止** |

> **★ 3 つ目は能力ではない。**
> **能力の不在は環境が変われば消えるが、規則の禁止は指示が変わらない限り残る。**
> **混ぜて「できない」と書くと、環境が変わっても誰も測り直さない。**

**手順書に「最後に測った時点」と再測定の 3 手順を書く**（IADR-0180 決定 2）。

## ★ 決定 6: **手順書は新設せず、既存節を正す**

`docs/operations/` に Runbook を作らない。**作れば同じ内容が 2 箇所になる**
（[IADR-0141](./IADR-0141_audit-rounds-and-population-drawing.md) 単一情報源）。
**既に手順を持っている `docs/ai-workflow.md` の節を正す。**

## ★ 決定 7: **「推奨設定」と「現在の状態」を読み分けられるように書く**

既存節は「これにより……マージされない」と**断定**していたが、**ブランチ保護は配備されていない**
（実測: 本 PR までの全 PR が承認レビュー無しでマージできている）。

**推奨であることを冒頭に明示し、配備までの暫定手段を併記する** ——
計画側の裁定（2026-08-08 / planning#286）が定める書き方そのものである。

## 結果

- 良い影響
  - **手順書どおりに設定して壊れる状態が消えた。** `#623` 基準 3 を閉じられる
  - **`claude-review` を必須にできる状態になった**（`reopened` の追加）
  - 「起動しないことがある」型の事故に**検査器**が付いた（原因 2 のみ・例外の無い側だけ）
- 悪い影響・トレードオフ
  - **手順書が長くなった**（＋2,893B）。`docs/` は必読ではないので 50KB 予算には影響しない
  - **ブランチ保護は依然として未配備。** 本 PR が動かしたのは**手順の正しさ**であって**統制の有無**ではない
  - **`paths:` 側は機械検査が無いまま**である（決定 2 の但し書き）
- フォローアップ
  - **環流 2 件**: (a) キットの必須チェック名がワークフロー名になっている、
    (b) `claude-code-review.example.yml` の `types:` に `reopened` が無い
  - **設定の実施**は人の操作（決定 5）。**棚卸しのたびに測り直す**
