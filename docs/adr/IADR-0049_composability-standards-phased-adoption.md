# IADR-0049: コンポーザビリティ標準の段階適用と繰延条件

- 状態: Accepted
- 日付: 2026-07-10
- 決定者: claude（実装）

## 起点・関連

- 関連する計画書 ID: FR-14（コンポーザビリティ）／ADR-0018（固定/可変区分）
- 関連 ADR: [[IADR-0028]]（宣言的パイプライン構成＝JSON 単一宣言＋起動時 fail-fast）
- 関連仕様書: `docs/tech/composable-component-guide.md`（§1.1 エンベロープ・§2.1 ステートレス）、
  `feedback/20260709_composability-safety-net-gaps.md`
- Issue: #206（共通エンベロープ＋CI契約テスト）／#207（ステージング適用順序）

## コンテキストと課題

計画書 `06_technical/10_composability-design.md` は次を安全弁／標準として定める。

- **§3 イベント契約の標準化**: イベントは共通エンベロープ（文書ID・バージョン・ソースメタ・ABAC 属性ヒント・
  トレースID）＋ペイロードで標準化し、後方互換の追加のみ許可、**互換性は CI の契約テストで検証**する。
  ADR-0018 の固定/可変区分でも「イベント共通エンベロープの標準」は固定部。
- **§5 安全弁（誤構成対策）**: 適用は**ステージング → 本番**の順とし、本番適用前にステージングで
  パイプライン疎通（取り込み E2E）を確認する。

実装の現状は上記 3 点が未整備で、追跡 issue も一時消失していた（#102 残項目が #111 クローズ時に繰延された
まま。#206・#207 で追跡復活）。

| 上流の定め | 実装の現状（代替策） |
| --- | --- |
| 共通エンベロープ（§3・固定部） | 未実装。イベントは型ごとの個別 record（`Shared.Contracts/Events/`）。ABAC 属性は各イベントの `Attributes`、トレース相関は OTel/MassTransit ヘッダで実現 |
| CI の契約テスト（§3） | 未実装。CI は `pipeline-config`（宣言内整合 V1〜V6）のみ。互換性は「後方互換の追加のみ許可」の運用ルール＋PR レビューで担保 |
| ステージング→本番の適用順序（§5） | 未整備。単一環境（ArgoCD 単一 Application）。CI 検証＋起動時 fail-fast（[[IADR-0028]]）＋Git revert ロールバックで代替 |

計画側 triage（project-planning #16、2026-07-10）は**提案2「段階適用の注記」を accepted** とし、3 点を
**到達目標として維持**しつつ初期は現行の代替策を許容、**実装側は移行の繰延条件を IADR に明文化**すること、
エンベロープ項目確定時は `07_abac-attribute-model.md` と整合させることを依頼した。本 IADR はその繰延条件の
明文化である（FR-14／ADR-0018 は不変。到達目標として維持）。

## 決定

1. **§3 共通エンベロープ＋CI 契約テストを条件付きで繰延する。**
   - 初期は現行の代替策（イベントごとの個別 record ＋「後方互換の追加のみ許可」の運用ルール ＋ PR レビュー、
     トレース相関は OTel/MassTransit ヘッダ、ABAC 属性は各イベントの `Attributes`）を許容する。
   - **繰延解除の条件（＝実需要）**: 「段（パイプラインステップ）の挿抜」により、個別イベントの
     フィールド依存が問題化した時点。具体的には次のいずれかが顕在化したとき着手する。
     (a) 共通のバージョン項目・ソースメタが無いために後方互換性の判定を機械化できず障害・退行が生じた、
     (b) 新しい段の追加・差し替えで既存イベント型への横断的変更が繰り返し必要になった、
     (c) ABAC 属性ヒント／トレースID をイベント本体で標準搬送する要件（監査・相関）が確定した。
   - 着手時は作業仕様書＋IADR を作成し、**エンベロープ項目の確定は上流 `07_abac-attribute-model.md` と整合**
     させる。CI にイベントスキーマ後方互換性の契約テストを必須ジョブとして追加する。

2. **§5 ステージング→本番の適用順序を条件付きで繰延する。**
   - 初期は現行の代替策（単一環境＝ArgoCD 単一 Application ＋ CI 検証 ＋ 起動時 fail-fast（[[IADR-0028]]・
     宣言と実装の照合で不整合は起動拒否）＋ Git revert によるロールバック）を許容する。
   - **繰延解除の条件（＝環境分離の整備）**: ステージング環境が用意され、本番前の取り込み E2E 疎通を
     別環境で検証する運用が可能になった時点。具体的には (a) ステージング用の名前空間／クラスタと ArgoCD
     Application が分離配備された、(b) ステージング昇格ゲート（E2E 疎通確認）を CD に組み込む要件が確定した、
     のいずれか。着手時はデプロイ経路（環境昇格順序・ゲート）を運用仕様書／IADR に定義する。

3. **上流未定義の追加安全弁「起動時 fail-fast（[[IADR-0028]]）」を安全弁として維持する。**
   宣言（`pipeline-config`）と実装の起動時照合で不整合を検出し起動を拒否する仕組みは、計画 §5 に無い
   実装側の追加防御であり、ステージング整備までの主要な誤構成対策として位置づける（計画側にも
   plan-feedback で §5 への追記を提案済み・triage 反映済み）。

## 根拠 / 代替案

- **今すぐ実装しない**: 共通エンベロープの導入は既存イベント型の段階移行と ABAC 属性モデルの確定を伴い、
  影響が大きい割に「段の挿抜」という実需要が未到来。実需要が出た時点でエンベロープと契約テストをセットで
  再設計するのが妥当（[[IADR-0028]] の繰延判断と一貫）。契約テストのみ先行しても検証対象（エンベロープ）が
  無く空振りになる。
- **ステージングを今すぐ作らない**: 現状は単一環境で、CI＋fail-fast＋Git revert が誤構成の主要経路を塞ぐ。
  環境分離は運用コスト（クラスタ／名前空間／CD ゲート）が大きく、環境が用意でき次第の整備が費用対効果に
  見合う。fail-fast は起動時に不整合構成の本番反映を止めるため、単一環境でも安全弁として機能する。
- **到達目標は放棄しない**: FR-14／ADR-0018 は不変。本 IADR は繰延条件と代替策を明文化するもので、
  標準そのものの否定ではない。条件成立時は速やかに標準へ移行する。

- ドキュメント: 本 IADR の追加。`docs/tech/composable-component-guide.md`（§1.1・§2.1）は PR #208 で

- コード: 変更なし（繰延の意思決定記録）。
- CI: 変更なし（契約テストは繰延解除時に追加）。

- エンベロープ項目確定時の `07_abac-attribute-model.md` との整合（計画 triage の依頼事項）。
- ステージング整備時のデプロイ昇格順序・ゲートの運用仕様書化。
