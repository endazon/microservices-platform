## コンテキストと課題

[IADR-0138](IADR-0138_coverage-exclude-generated-code.md) は EF Core の生成コードを集計から落とし、
「マイグレーションを 1 本足しただけで床判定が動く」状態（PR #568 が現に踏んだ）を塞いだ。
しかし同 ADR は当初「EF 以外の生成物は develop の実レポートに 0 件」と書いており、**それは誤りだった**——
`git ls-files` で数えた結果であり、**source generator の出力は `obj/` 配下に出るため gitignore で見えなかった**。

**実レポートで数え直すと 0 件ではない。** 本作業の実測（develop `1d7edce`）では
**197 クラス / 4740 行 / 分岐 3970** が集計に残っており、**分岐分母の 40.1%** を占める。
被覆は行 11.2% / 分岐 6.3% にすぎない。

問題は量ではなく**動き方**である。`OpenApiXmlCommentSupport.generated.cs` は
**エンドポイントの XML doc コメントから生成される**。つまり:

> **API に `///` を 1 つ足すだけで生成コードが増え、床が動く。**

これは #571 が塞ごうとした事象（「設計上まったく無関係な操作で床が動く」）そのものであり、
**EF については塞げたが source generator については塞げていない**という状態だった。

決めるべきは (1) 何を source generator の出力とみなし、どう判定するか、(2) 除外量をどう数えるか、
(3) 定義が変わるため床をどう置き直すか、である。

### 着手時の実測（判定パターンを決めるための一次情報）

**形を仮定して書くと、フィルタが何にもマッチせず「除外したつもりで素通り」になる**（IADR-0123 /
IADR-0138 が繰り返し名指ししている失敗モードで、**IADR-0138 自身がそれを踏んだ**）。
よって実レポートの `<class filename>` を**全数**（重複除去後 1061 件）分類した。

| 分類 | 件数 | 中身 |
| --- | --- | --- |
| **`obj/` を区切り付きで含む** | **14** | `OpenApiXmlCommentSupport.generated.cs` **11** ／ `RegexGenerator.g.cs` **3** |
| `obj/` の外の `*.g.cs` / `*.generated.cs` | **0** | —— |
| `Migrations/` 配下・`*ModelSnapshot.cs`（既存の除外） | 117 | EF の生成物 |
| その他（手書き） | 930 | —— |

**`obj/` 配下は全数が source generator の出力であり、中間生成物（`Debug/net10.0/` 配下の `.dll` /
`.cache` 等）の巻き込みは 0 件だった。** issue #574 が懸念した点はここで解消している——
コンパイラが `<class filename>` へ書くのは**ソースとして食わせたファイル**だけだからである。

## 検討した選択肢

### 何を「source generator の出力」とみなすか

| | **A. `obj/` 配下（採用）** | B. `*.g.cs` ＋ `*.generated.cs` | C. 両方の OR |
| --- | --- | --- | --- |
| 本実測での取りこぼし | 無し | 無し（**A と完全に一致**） | 無し |
| 根拠の性質 | **構造的**——`obj/` は MSBuild の中間出力ディレクトリで gitignore 済み。人が書いたコードは定義上そこに無い | **規約的**——サフィックスは各 generator が選ぶ | 同左 |
| 新しい generator が別の名前で出したら | 当たる | **黙って素通りする** | B の弱点が残る |
| 出力先が変わったときの壊れ方 | 除外 0 件 → **notice で出る** | 無音 | **片方が当たると notice が出ないため、もう片方の劣化に気付けない** |
| 規則の本数 | 1 本 | 2 本 | 3 本 |

**C は「起こり得ないケースへの防御的実装」**（`CLAUDE.md` 禁止事項）であり、
実測で一致している以上、規則を 2 本持つ理由が無い。むしろ C は**壊れたことに気付けなくする**。

### 除外量の数え方

| | **A. 種別ごとに数える（採用）** | B. 既存の生成コード枠へ合算する |
| --- | --- | --- |
| 実装コスト | 小（カウンタを Map で持つ） | ゼロ |
| **IADR-0138 決定 3 の notice** | 種別ごとに出るため**片方の破損を検出できる** | **EF 側が壊れても source generator の 4740 行が数を埋め、notice が出ない** |
| CI ログの可読性 | 片方の増減が読める | 打ち消し合って読めない |

**B は既存の守りを黙って弱める。** 決定 3 の notice は「除外量 0 ＝ フィルタの素通り」を可視化する
仕組みであり、2 種を 1 つのカウンタへ合算するとその前提が崩れる。

### 床の置き直し

| | **A. 実測からの整数切り下げ（原則・採用）** | B. 据え置き（33 / 17 のまま） | C. 分岐だけ除外する |
| --- | --- | --- | --- |
| 意味の一貫性 | 新定義の実測から導いた床 | **旧定義の床を新定義へ流用**（緩みっぱなしになる） | **line と branch が別の母集合を測る** |
| [IADR-0123](IADR-0123_cobertura-class-attribution-and-line-dedup.md) 決定 4 の coverlet 突合 | 成立 | 成立 | **意味を失う**（`lines-valid` との一致検査が別母集合になる） |
| 歪みへの対処 | line / branch とも解消 | 未解消 | branch のみ解消。**非対称の代償のほうが大きい** |

## 決定

1. **source generator の出力は集計から落とす。** 対象は `<class filename>`（[IADR-0123](IADR-0123_cobertura-class-attribution-and-line-dedup.md)
   決定 2 が解決した経路）が **`obj/` を区切り付きの一区画として含む**クラスである。行・被覆行・分岐の
   すべてを落とす。**[IADR-0138](IADR-0138_coverage-exclude-generated-code.md) 決定 1 の 2 規則
   （`Migrations/` 配下・`*ModelSnapshot.cs`）は変えず、規則を 1 本足すだけである。**
   - **サフィックス（`*.g.cs` / `*.generated.cs`）では判定しない。** 実測では両者が完全に一致するが、
     採るのは**壊れたときに無音にならないほう**である（上表）。
   - 区切り付きで見るのは誤爆を避けるためである（`objects/` / `MyObj/` / `ObjectMapper.cs` は生成物ではない）。
   - **集計対象外ユニット（[IADR-0120](IADR-0120_excluded-units-from-gitmodules.md)）の除外を先に通す**
     ——IADR-0138 決定 1 と同じ順序であり、AST 由来の行を「生成コード」として二重計上させないためである。

2. **除外量は種別ごとに数え、種別ごとに診断と notice を出す。**
   [IADR-0138](IADR-0138_coverage-exclude-generated-code.md) 決定 2・3 の作法を保ったまま、
   カウンタを `ef` / `sourcegen` に分ける。**合算 1 本にしない**——片方のフィルタが壊れても
   もう片方が数を埋めて notice が出なくなり、**守っていたはずの穴が黙って開く**（上表）。

3. **床を置き直す: `line 33` → `39`。`branch 17` → `27`。**
   - **これは ratchet の引き上げではなく、測定基準の変更に伴う置き直しである**
     （[IADR-0123](IADR-0123_cobertura-class-attribution-and-line-dedup.md) 決定 7 ／
     [IADR-0138](IADR-0138_coverage-exclude-generated-code.md) 決定 4 と同じ性質）。
     **旧定義の床と新定義の床は分母・分子が違うため比較できない。**
   - **`branch` は切り下げの `28` を採らない。** [IADR-0118](IADR-0118_backend-coverage-floor.md) 決定 2 は
     「実測を整数へ切り下げる」と定めるが、**`28.01%` の切り下げ `28` は余裕が `0.01pt` しかなく、
     床として機能しない。** これは主観ではなく計算できる。

     | 床 | 赤にするのに必要な被覆の喪失 | 判定 |
     | --- | --- | --- |
     | `branch 28` | `1663 → 1662`（**被覆分岐 1 本**。`27.99%`） | **不可** |
     | **`branch 27`（採用）** | `1663 → 1603`（被覆分岐 60 本。余裕 `1.01pt`） | 可 |
     | **`line 39`（採用）** | `9486 → 9267`（被覆行 219 行。余裕 `0.92pt`） | 可 |

     [`src/coverage-floor.json`](../../src/coverage-floor.json) の `$comment` は既に
     **「計測ゆらぎで赤にならない幅を確認してから上げること」**と書いている。上表はその確認である。
     **切り下げが機能する床を与えないときは 1 つ下の整数を採る**——これを IADR-0118 決定 2 の例外として明示する。

     > **［2026-08-15 追記 / #574］この判断は仮定ではなく実証された。**
     > **本 PR の CI 実測は `branch 27.99%（1662/5938）`** —— ローカル実測（`1663`）より
     > **ちょうど被覆分岐 1 本少ない**。**切り下げの床 `28` を採っていたら CI は初回から赤だった。**
     > 上表の「被覆分岐 1 本の喪失で割れる」は、**まさにその 1 本の差が現実に出た**。
   - 値の正は [`src/coverage-floor.json`](../../src/coverage-floor.json) であり、導出は同ファイルの
     `$comment` に測定条件つきで記録した。

4. **床 39 / 27 は導出値ではなく実測値である。**
   [IADR-0138](IADR-0138_coverage-exclude-generated-code.md) 決定 5 は「CI の実測値を読む手段が無い」ため
   床 33 を**導出**したが、本作業では **CI と同じ手順をローカルで完走できた**ため、実測から直接置いた。

   | 項 | 値 |
   | --- | --- |
   | 測定条件 | develop `1d7edce` / .NET SDK `10.0.400` / Release 構成 / **レポート 14 件（CI と同数）** / **統合テスト 43/43 成功** / 2026-08-15 |
   | 実測（新定義） | `line 39.92%（9486/23762）` / `branch 28.01%（1663/5938）` |
   | 実測（旧定義＝EF のみ除外） | `line 35.14%（10016/28502）` / `branch 19.30%（1912/9908）` |
   | source generator 出力 | **197 クラス / 4740 行（被覆 530） / 分岐 3970（被覆 249）** |

   **ただし測定環境（SDK・`dockerd`）はセッション限りで消える。** よって
   **「常に測れる」ことを前提にした記述はしない**——値を疑うときは同じ手順で測り直す。

   > **［2026-08-15 追記 / #574］CI 実測で裏づけた**（PR #741 / run `31866326272` / job `build-and-test`）。
   >
   > | | ローカル実測 | **CI 実測** |
   > | --- | --- | --- |
   > | line | `39.92%（9486/23762）` | **`39.92%（9485/23762）`** |
   > | branch | `28.01%（1663/5938）` | **`27.99%（1662/5938）`** |
   >
   > **分母は完全に一致し**（`23762` / `5938`）、差は**被覆側の 行 1 / 分岐 1 だけ**である
   > （`ConversionService.Worker` の被覆行 674 → 673）。
   > **分母の一致は判定規則が CI でも同じ母集合を引いたことの直接の証拠**であり、
   > 除外量も種別内訳（EF 61 クラス / source generator 197 クラス・分岐 3970）まで完全に一致した。
   > 乖離はこの 2 本だけなので、下記フォローアップ 1 の「大きく乖離したら置き直す」には当たらない。

5. **[IADR-0138](IADR-0138_coverage-exclude-generated-code.md) 決定 4 の
   「branch は 17 のまま据え置く」の根拠は EF の生成コードに限られる。**
   同決定は「生成コードの分岐は 0/0」を理由に branch を据え置いたが、それは EF についての実測であり、
   **source generator の出力は分岐 3970 を持つ**。本決定は branch も置き直す。
   IADR-0138 側には日付つき追記でこの限定を明記した。

## 理由

- **「何を測っているか」を揃えるため**である。床の目的は手書きコードの試験の厚さを守ることであって、
  XML doc コメントの量を測ることではない。IADR-0138 が EF について採ったのと**同じ論拠**であり、
  同じ論拠が届く範囲に規則が及んでいなかっただけである。
- **床の値が上がるのは、source generator の出力が平均より薄く被覆されているからである**
  （行 11.2% / 分岐 6.3% に対し全体は行 35.14% / 分岐 19.30%）。EF のときは逆に**下がった**——
  統合テストが `MigrateAsync()` を通るため生成コードが厚く被覆されていた。
  **どちらも「分子・分母から同じものを抜いた」結果であり、品質の変化を意味しない。**
- **判定パターンを実レポートから決めた理由**は IADR-0123 / IADR-0138 と同じで、決め打ちが外れたときの
  壊れ方が「無音の素通り」だからである。**IADR-0138 は実際にそれを踏んだ**（`git ls-files` で数えて
  「0 件」と書いた）。今回は `<class filename>` を全数分類することで同じ轍を避けた。

### 変異試験（決定 1〜3 の根拠）

| # | 変異 | 期待 | 実測 | 判定 |
| --- | --- | --- | --- | --- |
| M1 | `obj/` の判定を無効化（`objDISABLED/` へ差し替え） | 旧定義の値へ戻り、床 39 / 27 に対して落ちる | `line 35.14%（10016/28502）` / `branch 19.3%` へ戻り **`exit=1`**。あわせて **source generator 側の notice が出た** | **落ちた（検出）** |
| M2 | **XML doc コメントを足した状態を再現**（`obj/…/OpenApiXmlCommentSupport.generated.cs` に 154 行・308 分岐・0 被覆を注入）・**除外あり** | 実測値が動かない | `line 39.92%（9486/23762）` / `branch 28.01%（1663/5938）`。**注入前と完全に同値**。一方「生成コードを戻すと」の値は `line 35.58% → 35.41%` / `branch 19.3% → 18.72%` と**動いた**（＝旧定義なら床が動いていた） | **意図どおり（不動）** |
| M3 | 床を `line 40` へ引き上げ | 落ちる | `実測 39.92% < 床 40%` で **`exit=1`** | **落ちた（検出）** |

**M2 が本 issue の核心である**——`branch` の動き（`19.3% → 18.72%`、**0.58pt**）は、
旧定義の床の余裕を優に超える。**XML doc コメントを 1 箇所足すだけで CI が赤になり得た。**

## 結果

- 良い影響:
  - **XML doc コメント・正規表現リテラルの増減が床判定を動かさなくなる。** 変異試験 M2 で確認済み。
  - **床が「手書きコードの試験の厚さ」を表す度合いが上がる。** `line 33 → 39` / `branch 17 → 27` は
    水準の引き上げではなく、**分母から測る対象でないものを抜いた結果**である。
  - 除外量が**種別ごとに** CI ログ・実行サマリで毎回読める。片方の破損が notice で出る。
- 悪い影響・トレードオフ:
  - **床の数値が大きく動く（`line +6` / `branch +10`）。** 表面上は強化に見えるが**強化ではない**。
    旧定義の床と比較できないことを、値を引用するすべての箇所に明記する必要がある。
  - **`branch 27` は切り下げの原則から 1 つ下げた値である。** [IADR-0118](IADR-0118_backend-coverage-floor.md)
    決定 2 の作法に例外を作った（決定 3）。**次に ratchet で上げるときは同じ確認を要する**——
    「実測を切り下げただけ」で上げると、また余裕 0.01pt の床が生まれ得る。
  - source generator のフィルタが壊れても **fail にはならない**（notice のみ）。
    IADR-0138 決定 3 を踏襲した意図的な設計だが、notice を読む運用が要る。
  - **検出しないこと**（明示する）:
    - **生成されたコードの正しさ**——OpenAPI の XML コメント連携が実際に効くかは別の責務であり、
      床は関与しない。除外後は生成コードの被覆率が「良く」も「悪く」も見えなくなる。
    - **`obj/` へ手書きコードを置いた場合**——黙って集計から落ちる。
      MSBuild の慣例上そこには生成物しか置かない（かつ gitignore 済みである）という前提に依存する。
    - **フロントのカバレッジ**（[IADR-0034](IADR-0034_frontend-coverage-gate.md) / `src/vitest.config.ts`）
      ——本決定はバックエンドの床にのみ効く。orval / Lingui 生成物の扱いは別の決定である。
    - **CI での実測値**——本作業の実測は**ローカル**である。CI と同じ手順・同じレポート件数
      （14 件）・統合テスト全通という条件を揃えたが、**CI 実測と一致することは保証しない**。
      余裕（line `0.92pt` / branch `1.01pt`）はこの不確かさを吸収するために残してある。
