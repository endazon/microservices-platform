# IADR-0129: SC-09〜11 の再実装 — 区画構成・条件エディタ・秘匿の中立化・閲覧ロールの据え置き

  [[IADR-0029]] / [[IADR-0030]]（構成情報 API の配置・`ConfigViewer` ポリシー）・[[IADR-0035]]（ロール別ナビ・存在秘匿）・

## コンテキストと課題

#504 は SC-09〜11 を新スタック（ADR-0031）で作り直す。3 画面に共通する関心事は
**権限による出し分けと存在秘匿**である。一方、3 画面は計画が求める要素のうち相当数が
**現在の API 契約に載らない**か、**[[IADR-0119]] が着手を保留した FR-17 / FR-18 に属する**。
どこまで作りどこで止めるかを画面ごとの場当たりで決めると、**同じ「無い」でも理由が混ざり、
後から「作り忘れ」と「意図的な保留」を区別できなくなる**。

## 決定

### 決定 1: SC-09 の区画は **2 つ**とし、残る 2 つは理由を分けて実装しない

計画 §SC-09 §主要素 は 4 区画（属性体系エディタ・タグ辞書・**辺の型辞書**・ポリシー定義）＋検証結果を挙げ、
hi-fi はこれを `seg` / `seg-opt` の切替として描く。本 issue が実装するのは **属性体系** と **ポリシー定義**（＋検証結果）である。

| 区画 | 実装 | 理由 |
| --- | --- | --- |
| 属性体系エディタ | **する** | `GET/POST/DELETE /bff/admin/authz/attributes` が実在する |
| ポリシー定義 ＋ 検証結果 | **する** | `GET/POST/PATCH/DELETE /bff/admin/authz/policies` が実在し、保存前検証の 400 が透過される（[[IADR-0040]]） |
| **辺の型辞書** | **しない（A: FR の着手保留）** | 計画自身が当該節を「**FR-17**・ADR-0033 決定3」と明示し、画面一覧の SC-09 行も `FR-05, FR-09, **FR-17**` と書く。ADR-0033 は `Proposed` であり [[IADR-0119]] 決定 2 の着手条件（`Accepted`）を満たさない |
| **タグ辞書** | **しない（B: 契約の不在）** | タグ辞書の値集合を返す口・**使用件数**・**改名の追随**のいずれも契約に無い。計画が確定した規則（参照 1 件以上は削除拒否・件数 N の提示・改名は既存文書が追随）は**そのすべてが契約側の機能**である |

**「辺の型」を値集合だけでも先に作る**案は採らない。値集合（中核 5 種・推奨追加 4 種・逆向きの表示語）
そのものが ADR-0033 決定3 の内容であり、`Proposed` な ADR を実装へ写すことになる。

**空のタブを置く**案も採らない（#502 が確立した「動かない UI を置かない」）。
利用者から見て「タブはあるが何もできない」状態は、保留であることを伝えず、むしろ壊れて見える。

### 決定 2: ポリシー条件は **構造化エディタ**（属性 × 許可値）とし、自由記述の条件式は実装しない

計画の入力表は「ポリシー条件｜必須｜**条件式**｜構文・矛盾検証に合格」「**対象属性**｜必須｜**選択**｜**定義済み属性のみ**」と
2 行を並べ、hi-fi は `user.dept == "開発" && doc.tags には "設計" を含む` という**自由記述の式**を描く。

**契約が表現できるのは属性キー → 許可値の集合所属だけ**である
（`AbacPolicyDto.UserConditions` / `DocumentConditions` はいずれも `Dictionary<string, List<string>>`）。
`<=`（機密区分の順序比較）も「含む」も**契約に存在しない**。

したがって画面は **属性 `Select`（属性辞書から）＋ 値 `Select`（その属性の `AllowedValues` から）＋ 追加**という
構造化エディタを提供する。これは計画の 2 行目（**対象属性は定義済み属性のみを選択**）を**満たす**一方、
1 行目の「条件式」の表現力を**部分的にしか満たさない**。

**旧実装（JSON テキストエリアに `{"key":["値"]}` を手書き）を踏襲しない**理由は、
それが計画の「定義済み属性のみ」をまったく強制せず、**属性辞書と条件が無関係に存在する**画面になっていたためである。

**これは対応表で「する」と判定される行に隠れる部分未実装**であり、
[作業仕様書](../specs/20260805_issue-504_sc09-11-admin-ops-screens.md) §3 と
[画面仕様書](../screens/SC-09_admin-abac-settings.md) の備考に明記し、環流の提案 3 として計画へ渡す
（#503 が SC-05 のタグ辞書整合で踏んだ穴——**二値判定の外側**——を同じ形で塞ぐ）。

### 決定 3: サーバ側の **403 と 404 は同一の中立文言**へ寄せる

[[IADR-0009]]（存在秘匿）は「権限外の資源は不在と同じ応答にする」と定める。
画面側でこれを崩さないため、**`forbidden` と `notFound` を区別した文言を出さない**。

- SC-10（BFF は AdminOnly ＝ 403 を返す）と SC-11（BFF は 404 で秘匿する）は、**同じ文言**を出す。
- 旧実装は「このダッシュボードを表示する権限がありません。」と「ダッシュボードは利用できません。」を
  出し分けており、**画面の文言から権限の有無が読めた**（秘匿の趣旨に反する）。

**5xx / ネットワーク断は区別する**（`role="alert"` の障害表示）。これは資源の存在ではなく系の状態であり、
秘匿の対象ではない。区別しないと運用者が「権限が無い」と誤読して障害を見逃す。

**この作法は主従を問わず、画面内のすべての問い合わせに適用する。** SC-11 は 3 本の問い合わせを
独立に縮退させる（決定 5）が、従の 2 本（ドリフト・履歴）だけを「種別によらず中立文言」にはしない
——「区別しないと障害を見逃す」という理由は従の問い合わせにも等しく当てはまり、
むしろ**画面の主要部（実効構成）が正常に見えている分だけ見逃しやすい**。
したがってドリフト・履歴も **`notFound` のみ中立文言、それ以外は `Alert`（`danger`・`role="alert"`）** とする。
射程を「主クエリだけ」に狭める案は採らない——狭める根拠が「従だから」しか無く、
決定の理由（障害の見逃し）と噛み合わないためである。

### 決定 4: SC-10 の閲覧ロールは **`platform-admin` 据え置き**とし、裁定を求める

計画 §SC-10 は「**運用者・管理者**ロール限定」と定めるが、実装は `platform-admin` のみである。
データ源 `/bff/dashboard/summary` は `AdminOnly`、**後段 `DashboardService` の集計も AdminOnly** であり、
BFF だけを広げても運用者には 403 が返る。

**画面だけを広げる**案は採らない——運用者に「開くと必ずエラーが出る画面」を見せることになり、
#503 が SC-07 で名指しした「**画面と API の権限がずれている**」形そのものである。

**BFF と後段を同時に広げる**案も本 issue では採らない。#504 は画面の再実装が射程であり、
**どちらが正か（計画の改訂か実装の是正か）は計画側の裁定を要する**——
planning#198 提案 8（SC-05/06/07 の閲覧ロール）と**同じ類型だが向きが逆**である
（#198 は「計画は管理者限定だが実装が広い」、本件は「**計画は運用者も許すが実装が狭い**」）。
環流記録の提案 7 として新たに問う。

**その帰結として、SC-10 から SC-11 への導線を権限で出し分けない。**
SC-10 に到達できるのは `platform-admin` だけであり、`platform-admin` は `ConfigViewer` の部分集合である
——`useHasAnyRole(Admin, Operator)` は**この画面では常に真**になる。旧実装はこの条件分岐を
「将来 SC-10 を運用者へ開放したときのための冗長性」として持っていたが、
`CLAUDE.md`「起こり得ないケースへの防御的実装を避ける」に反し、**到達しない分岐**として被覆率にも現れる。
SC-10 の閲覧ロールが広がる時点で、そのとき必要な出し分けを書く。

### 決定 5: SC-11 は **3 本の問い合わせを独立**に扱い、領域ごとに縮退する

実効構成・ドリフト・履歴は別のエンドポイントである。旧実装は 3 本を独立に取得し、
落ちた領域だけを縮退させていた（#138 / #139）。**この性質を新スタックでも保つ**
（TanStack Query の 3 本の `useQuery`）。

ただし**実効構成が取れない場合は他の 2 領域も出さない**——構成が無い状態でドリフトだけを見せても
「何に対する差分なのか」が読めないためである。

**履歴の件数は画面で切り詰めない。** [[IADR-0046]] と計画（2026-08-04 確定・planning#190）が
「正データ源は GitOps 層で、保持範囲は Git 無期限 ＋ ArgoCD の `revisionHistoryLimit` = 10 世代」と定めており、
**表示できる範囲はその規則から定まる**。画面が独自に上限を持つと、第二の規則が生まれる。

### 決定 6: 値集合と写像は **純関数ファイル**へ出し、純関数テストで固定する

#503 の変異試験 M31 は「値集合から 1 値落としても画面テストは 1 件も落ちない」ことを実測した。
本 issue が扱う値集合はいずれも**契約由来で、画面からは間接的にしか見えない**——

| ファイル | 固定する値集合・写像 |
| --- | --- |
| `sc09-admin-abac/abacVocabulary.ts` | アクション **3 値**（`read` / `analyze` / `manage`）・スコープ **2 値**（`document` / `user`）・条件リスト → `{userConditions, documentConditions}` の組み立て |
| `sc11-config/driftView.ts` | ドリフト種別 **5 値**・深刻度 **2 値** → `tone` ＋ 表示名。**未知の値は生値のまま**（丸めない） |
| `sc10-operations/opsTools.ts` | 外部ツール **3 件**（Grafana / Kiali / Jaeger・Tempo）と、未設定の実行時 config を落とす規則 |

### 決定 7: 新規 UI プリミティブを作らない

計画 [13_frontend-stack §shadcn/ui 派生の範囲](../../planning/projects/microservices-platform/06_technical/13_frontend-stack.md)
の 4 基準で判定した（[作業仕様書](../specs/20260805_issue-504_sc09-11-admin-ops-screens.md) §4 に判定表）。

- **SC-09 の区画切替**: 4 基準のうち 2 つ（複合キーボード操作・`aria-*` の動的同期）に該当するが、
  **#496 が移植済みの `Tabs`** がそれである。新規は作らない。
- **SC-11 の折りたたみ**: 4 基準のいずれにも該当しない。**ネイティブの `<details>` / `<summary>`** を使い、
  `@platform/ui` へは入れない（[[IADR-0125]] 決定 1 の「入れてよいものの範囲」にも合う）。

## 検討した選択肢（主要な分岐のみ）

| 論点 | 採用 | 棄却 | 棄却理由 |
| --- | --- | --- | --- |
| 辺の型区画 | 実装しない | 値集合だけ先に作る | `Proposed` な ADR-0033 の内容そのものを実装へ写すことになる（[[IADR-0119]] 決定 2） |
| 同上 | 実装しない | 空のタブを置く | 保留であることを伝えず、壊れて見える（#502 の「動かない UI を置かない」） |
| ポリシー条件 | 構造化エディタ | 自由記述の条件式 | 契約が集合所属しか表現しない。式を受け付けると**保存できない入力**を許すことになる |
| 同上 | 構造化エディタ | 旧実装の JSON テキストエリア | 計画の「定義済み属性のみ」を強制しない |
| 403 / 404 | 同一文言 | 出し分ける | 文言から権限の有無が読める（[[IADR-0009]] に反する） |
| 決定 3 の射程 | 主従を問わず全クエリ | 主クエリ（画面の可用性を決める 1 本）に限る | 「区別しないと障害を見逃す」は従クエリにも当てはまる。主要部が正常に見える分むしろ見逃しやすい |
| SC-10 の閲覧ロール | admin 据え置き ＋ 裁定 | 画面だけ operator へ開く | 開くと必ず 403 になる画面を見せる |
| 同上 | admin 据え置き ＋ 裁定 | BFF と後段を同時に広げる | 計画側の裁定を待たずに実装が答えを出す（#503 / [[IADR-0128]] 決定 2 と同じ作法） |
| SC-11 の縮退 | 領域ごと | 1 本でも落ちたら全体をエラー | 障害調査の最中に「ドリフトだけ見たい」が満たせない |
| SC-11 の折りたたみ | ネイティブ `<details>` | Radix の Accordion を移植 | 4 基準のいずれにも該当しない |

## 理由

- **「無い」の理由を 3 種類（A: FR の保留／B: 契約の不在／C: 他 issue）に分けて記録すると、
  後から読む者が「作り忘れ」と「意図的に止めた」を区別できる。** #502 が A / B を、#503 が C を確立した。
  本 issue は 3 種類すべてが同時に現れる初めての作業であり、分類の実効性がここで試される。
- **部分未実装を二値判定の外側に明記する**のは、#503 が実際に取りこぼした形だからである
  （「する」行の中に隠れた制約未達が集計に載らない）。
- **秘匿の中立化は画面側でしか守れない。** サーバが 403 と 404 のどちらを返すかは画面ごとに違う
  （SC-10 = 403 / SC-11 = 404）が、**利用者から見た文言が違えば秘匿は破れる**。

## 結果

- 良い影響:
  - 3 画面の秘匿の作法（`NotFound` の markup 一致・API 未呼出・403/404 の中立化）が揃う。
  - 保留対象（FR-17 / FR-18）が画面に一切現れず、解除時に何を足すかが対応表から読める。
  - 値集合が純関数テストで固定され、契約の値が増減したときに画面テストの外側で検出できる。
- 悪い影響・トレードオフ:
  - **SC-09 は計画の 4 区画のうち 2 区画しか無い**。管理者から見ると計画の姿より狭い。
  - **SC-10 は KPI カード 3 枚のうちモックと一致するものが無い**（SLO・コストは契約に無く、
    利用状況は件数であって人数ではない）。**モックの見た目に最も遠い画面**になる。
  - **SC-10 の閲覧ロールが計画と食い違ったまま残る**（裁定待ち）。
  - ポリシー条件の表現力が契約に縛られ、計画が描いた条件式は書けない。
- フォローアップ:
  1. 環流記録（`feedback/20260805_sc09-11-admin-ops-contract-gaps.md`）の起票と裁定。
  2. [[IADR-0119]] の保留解除時に、SC-09 の辺の型区画と SC-10 のナレッジ健全性節を実装する。
  3. `docs/api/openapi.yaml` への 3 群の追加（#506 の射程）。
