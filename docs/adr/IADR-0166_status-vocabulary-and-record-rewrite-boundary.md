# IADR-0166: 仕様書 `status` の値域と、過去の記録を書き換えてよい境界（#667）

- 状態: Accepted
- 日付: 2026-08-10
- 決定者: claude（実装）

## 起点・関連

- **NFR**（文書統制）。実装 issue: **#667**（**自分で起票した**。出所は PR #666 / #546 の AI レビュー 🟢）
- 作業仕様書: [20260810_issue-667](../specs/20260810_issue-667_spec-status-vocabulary.md)
- 規約の正本: **`docs/README.md` 運用ルール 6**（仕様書）／ [`docs/templates/adr_template.md`](../templates/adr_template.md)（IADR）
  ／ [`.claude/rules/traceability.md`](../../.claude/rules/traceability.md)

## 文脈 —— **起票の前提が誤っていた**

#667 は「**完了時の遷移先を定めた規定が無い**（`.claude/rules/` にも `docs/README.md` にも
`CLAUDE.md` にも見当たらない。実測）」と書いた。**誤りである。**
`docs/README.md` の運用ルール 6 が **5 値**（`draft` / `in-progress` / `completed` / `done` /
`superseded`）を定義し、**`done` は `docs/specs/` 用**と名指している。意味づけ
（「実装の状態」であって「計画としての確定度」ではない）と、計画側に追随しない理由まで書いてある。

**なぜ「無い」と書いたか。** 実測すると、**語彙外の `fixed` 16 件のうち 15 件が
2026-08-09 以降に自分が書いた作業仕様書**であった。**計画リポの語彙（`draft → review → fixed →
superseded`）を実装リポへ持ち込み、規定を読まないまま「規定が無い」と起票していた。**

> **★ これは「記憶で挙げた」型の誤りである**（`.claude/rules/traceability.md` 規則 7）。
> `grep -n status docs/README.md` の 1 行目に出る場所であった。

## 決定 1: **規約は足さない。既にある規約へ実装を揃える**

**新しい語彙を定義しない。** `docs/README.md` 運用ルール 6 が正本であり、
**別の場所に書くと二重定義になる**（そして片方が古くなる）。

足すのは 3 点だけである。

1. **語彙外 22 件の是正**（決定 3）
2. **値域を閉じる機械検査**（`scripts/check-doc-status-vocabulary.js`）
3. **規約が触れていなかった「対象外の種別」と「据え置き」の明記**（決定 2・4）

## ★ 決定 2: **過去の記録の `status` を書き換えてよいのは「語彙の是正」に限る**

`.claude/rules/traceability.md` は「**確定済み（過去 PR の）作業仕様書は書いた時点の記録であり、
後から注記を足すのは記録の改竄にあたる**」と定める。**`status` がその「記録」に含まれるかを、
#667 は「決めよ」と要求した。決めた。**

| 種類 | 例 | 可否 | 理由 |
| --- | --- | --- | --- |
| **語彙の是正** | `fixed` → `done` ／ `implemented` → `completed` | **可** | **当時の判断を変えていない。** 書き手は「完了した」と言うつもりで別の語を使った |
| **状態の進行** | `draft` → `done` ／ `in-progress` → `completed` | **不可** | **当時の記録の内容を変える。** 何を完了と見なしたかは当時の判断である |
| **本文への注記追加** | 「［2026-08-10 追記］…」 | **不可** | 従前どおり（`.claude/rules/traceability.md`） |

**この線引きなら一括置換にはならない。** 対象は語彙外の 22 件だけで、
**`draft` 58 件・`in-progress` 38 件・`done` 159 件には触れない。**

> **★ 自分に都合のよい線引きになっていないか確かめた。** 是正対象のうち **16 件は自分が
> 2026-08-09 以降に書いた `fixed`** である。**線引きを緩めれば自分の取りこぼしが消える。**
> だから**緩める方向ではなく狭める方向**で決めた —— 語の言い換えだけを許し、状態の進行は許さない。
> その結果、**`review` 8 件（すべて他者・2026-07）はこの線引きで触れないことになった**（決定 4）。
> **自分の分だけ直り、他人の分が残る線引きである。** それでも、
> **推測で他人の記録を進めるより、残すほうが誠実である。**

## 決定 3: **是正の写像は `type` で決める。ディレクトリで束ねない**

| 現在値 | 件数 | → |
| --- | ---: | --- |
| `fixed`（`docs/specs/`） | 16 | `done` |
| `fixed`（`docs/tech/`、`type: tech` の 2 件） | 2 | `completed` |
| `implemented`（`functional-spec` 2 / `test-spec` 1） | 3 | `completed` |
| `active`（`docs/specs/` 1 件） | 1 | `done` |
| **計** | **22** | |

> **★ ディレクトリで束ねて種別を見落とした。** 最初は `docs/tech/` の `fixed` **3 件**をまとめて
> `completed` にする表を書いたが、**1 件ずつ `type` を見たら 1 件だけ `tech-note`**（PoC の実測記録）
> だった。**要件書ではないので対象外**である（決定 4）。
> `.claude/rules/traceability.md` 規則 5「軸を 1 本で終わらせない」。

**`active` 1 件（`20260808_phaseB-audit-followup.md`）は推測で決めていない**:
対になる `20260808_phaseA-audit-followup.md` が `done` で**同じ体裁**であり、
本文に**未了・残件・保留の記述が 1 件も無い**。

## 決定 4: **対象外と据え置きを明示する。黙って飛ばさない**

**「検査していない」と「違反 0 件」を読み分けられるようにする**（#546 / #664 の型）。

### 対象外（値域の定義が当てはまらない）

判定基準を 1 本にする —— **`docs/README.md` の種別表に載っている `type` か**。

| 種別 | 件数 | 理由 |
| --- | ---: | --- |
| `how-to` / `how-to-guide` | 3 | README:61「仕様ではなく作業手順の案内」。**手順に「実装中」は無い** |
| `runbook` | 2 | README:60「状態の単一情報源は `operations.md`」 |
| `tech-note` / `design` | 2 | **種別表に無い**（PoC 記録 ／ #59・#72 由来の旧構造） |

**検査器は除外した件数をログに出す。**

### 据え置き（ラチェット。**増えたら落ちる**）

| 語 | 件数 | 理由 |
| --- | ---: | --- |
| `review` | 8 | **決定 2 の線引きで触れない。** 「レビュー中」だったのか「レビューを終えて完了した」のかが文書から読み取れず、**推測で `done` にすると状態の進行を語彙の是正に見せかけることになる** |
| `docs/specs/` の `completed` | 43 | **値域内の語である。** README 6 は `docs/specs/` を `done` と名指すが、`completed` も定義された語であり、**書き換えは是正ではなく好みの統一**になる |

**据え置きの上限は実データの件数と一致させる**（余裕を残さない）。**自動回帰テストで一致を検査する。**

## 決定 5: **`type` の割れは束ねない**（別 issue）

**`type` も 28 種類に割れている**（`spec` 195 / `work-spec` 63 / `work` 6 が同じものを指す。
`test` と `test-spec`、`functional` と `functional-spec`、`tech` / `tech-note` /
`tech-architecture` / `tech-requirements` も併存）。**同じ検査器で閉じられる。**

**それでも束ねない。**

1. **#667 は `status` だけを射程に書いている。** 射程を勝手に広げない
2. **是正の当て先が違う。** `status` の正本は `docs/README.md`、`type` の正本は
   `docs/templates/*.md`（17 枚が `<kind>-spec` / `spec` / `impl-adr` を書く）
3. **どこへ寄せるかが三つ巴である。** `spec_template.md` は `type: spec` を書き、
   `CLAUDE.md` の種別表は `work` と呼び、実データの多数派は `work-spec` である。
   **これは判断を要する問題であり、値域を閉じるだけでは決まらない**

**別 issue として起票した（#675）。**

## 決定 6: **検査器を足す条件（同型 2 回）を満たしている**

`CLAUDE.md`「検査器・規約の追加は**同型の事故が 2 回起きたら**」。**数え方を先に決めた。**

| 数え方 | 件数 |
| --- | ---: |
| **実際に発火した事故** | **2 回**。① PR #666 の AI レビュー 🟢（「同日の他の仕様書は `fixed` なのに本 PR は `draft`」）／② 本 PR で判明した「規定を読まずに別リポの語彙を 15 件へ広げた」 |
| 潜在（乖離として存在するが発火していない） | 37 件 |

**「潜在」を事故に数えない**（PR #657 で実際にやって自己訂正した誤り）。

> **★ ② を事故に数えてよいか。** 「CI にも成果物にも出ていない」とも読める。
> **しかし ① が同じ型の 1 回目であり、そのとき「個別の付け忘れ」として処理されて根本が残った** ——
> #667 の起票文そのものがその記録である。**「1 回目は記録に留める」の 1 回目が ①、本 PR が 2 回目**にあたる。

## 結果

- `docs/README.md` 運用ルール 6 へ**値域の検査・対象外・据え置き・書き換えの境界**を追記
- 語彙外 **22 件**を是正（`status` の 1 行のみ。**本文には触れていない**）
- `scripts/check-doc-status-vocabulary.js`（新規。自己試験 12 件）
- `scripts/scripts.repo.test.js`（8 件追加。**門 A（走査 0 件）と門 B（ラチェット）を別々に変異試験**）

### 門は 2 つあり、別々に変異試験する

**#665 の教訓 —— 1 つの変異で両方を確かめたつもりにならない。**

| 門 | 発火条件 |
| --- | --- |
| **A** | `docs/` を走査して frontmatter を 1 件も拾えない（[IADR-0130](./IADR-0130_test-spec-coverage-ratchet.md)） |
| **B** | 据え置きの件数が上限を超えた（ラチェット） |

> **★ 門 A の変異試験を最初に書き損ねた。** 一時ディレクトリへ `scripts/` を写しながら
> **写した側ではなく実リポジトリのスクリプトを叩いていた** —— 検査器は `__dirname/..` を
> REPO_ROOT にするため、**cwd を変えるだけでは変異が当たらない。**
> 門を消していないのにテストが「緑を返した」と落ちて気づいた。**#664 で同じ装置を書いたのに再発した。**

**変異試験は実データにも当てる**: 実ファイルの `status: done` を 1 件だけ語彙外へ変え、
その 1 件が違反として出ることを確かめる（フィクスチャだけだと「実ファイルの frontmatter が
想定の形でない」型の空振りを捕まえられない）。

### フォローアップ

1. **`type` の値域**（決定 5）—— **#675**
2. **`review` 8 件の実体判定** —— 決定 2 の線引きでは触れない。
   **当時の書き手に確認できる機会があれば**据え置きを解消する。
3. **`draft` 58 件・`in-progress` 38 件の棚卸し** —— **値域には収まっている。**
   「本当に着手前か」は `status` の語彙の問題ではなく、別の統制である。
