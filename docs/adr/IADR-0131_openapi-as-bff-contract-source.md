# IADR-0131: OpenAPI を BFF 契約の単一情報源とし、SSE を生成の入力から機械的に落とす

- 関連する計画書 ID: ADR-0031（Accepted）／FR-04・FR-06・FR-09・FR-12・FR-15／SC-01・SC-03・SC-05〜SC-11

## コンテキストと課題

`CLAUDE.md` と [[IADR-0121]] 決定 3 は SPA から BFF への到達経路を 2 つに限る——**orval 生成フック**
（入力は `docs/api/openapi.yaml` の `/bff/` 配下のみ）か `foundation/api` の `apiFetch` / `apiStream`。

着手時点の実測（母集合と数え方は作業仕様書 §着手時の実測）:

- `docs/api/openapi.yaml` に載る `/bff` パスは **8 本**。
- BFF の実装が持つルートグループは **9 接頭辞**（`MapGroup("/bff` の 10 行のうち 1 組は同一接頭辞の
  読み／書き分割）。**うち 4 群が丸ごと、1 群が一部、契約に載っていない。**
- `features/sc*/use*.ts` の **10 ファイル中 9 ファイルが `apiFetch` ＋ 手書き型**である
  （生成フックに載っているのは SC-08 の 1 ファイルだけ）。

規約違反ではない（`apiFetch` は許された経路である）。**問題は、契約に載っていない面では
「BFF の DTO が変わっても SPA の型検査が素通りする」ことである。**

さらに 2 つの食い違いが見つかった。

1. `AiAnswerDto.citations` の型が `SearchResultDto[]` と書かれているが、**実体は `CitationDto[]`** である。
   SC-08 は両者に共通するフィールドだけを使って回避していた（[[IADR-0127]] 決定 3）。
   **食い違ったまま生成フックへ載せると誤った型が生成される。**
2. `/bff/analysis/ask/stream`（SSE）が載っていない。**これは妥当な除外**だが、
   「載せ忘れ」と区別が付かない。

## 検討した選択肢

### 論点 A: 契約の正本をどこに置くか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A1 | **`docs/api/openapi.yaml` を手書きの正本とする**（現状の延長） | 追加コストゼロで即座に全面を覆える。**C# → OpenAPI の追随は人手**で、ずれは検出されない |
| A2 | C# から OpenAPI を生成する（`scripts/generate-openapi.sh` を整備し `MapOpenApi` の出力を採用） | ずれが構造的に起こらない。**BFF を起動できる CI が要る**／`Results.Content` で透過中継する面はメタデータを持たず**409・400 が生成物から丸ごと落ちる**（本 issue が「落とすな」と名指しした 4 件がすべて該当する） |
| A3 | 契約検査（[[IADR-0122]]）を OpenAPI へ拡張し、C# と突合する | ずれを検出できる。**A2 と同じ理由で、透過中継の応答は C# ソースから読めない** |

### 論点 B: SSE をどう扱うか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B1 | OpenAPI に載せない ＋ 文書で「意図的な対象外」と書く | 生成物は安全。**契約ファイルが不完全**（BFF の面の 1 本が契約に無い） |
| B2 | OpenAPI に載せる（そのまま orval へ渡す） | 契約は完全。**orval が “動きそうに見える” mutation フックを生成する**（実測） |
| B3 | **OpenAPI に載せる ＋ 生成の前処理（`orval-bff-only.cjs`）で落とす** | 契約は完全で生成物は安全。前処理に規則が 1 つ増える |

### 論点 C: 状態・種別の文字列を `enum` にするか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C1 | `enum` にする | SPA 側で網羅性検査が効く。**後段が値を増やすと SPA が既存の値を解釈できなくなる**。C# 側は `string` であり `enum` ではない（値集合は `const` 群） |
| C2 | **`type: string` ＋ description に値集合を書く** | 未知の値を受け取れる。網羅性は feature 側の純関数テストで担保する（既存の作法） |

## 決定

**決定 1（論点 A）: A1 を採る。`docs/api/openapi.yaml` を BFF 契約の単一情報源とし、手書きで維持する。**
ただし**その保証の上限を文書へ明記する**——得られるのは「**OpenAPI を変えると SPA の型検査が落ちる**」
であって「**C# の DTO を変えると型検査が落ちる**」ではない。A2 / A3 は**後段の応答を透過中継する面
（`Results.Content` / `Results.StatusCode`）を覆えない**ため、いま採ると 409・400 が契約から落ちる。

**射程の限定（[[IADR-0122]] 決定 1 との関係）**: [[IADR-0122]] 決定 1 が「正本にできない」と棄却したのは、
**イベント契約を含む C# `Shared.Contracts` 全体の後方互換ゲートの正本**としての OpenAPI である
（棄却理由は「イベント契約を 1 件も含まない」＋「手書き／雛形生成でコードとドリフトし得る」）。
**本決定の対象は BFF ↔ SPA の REST 面（SPA が読む型の生成入力）に限る。両者は排他ではない**
——C# 契約の正本は引き続き C# ソースであり（`scripts/check-contract-schema.js`）、
[[IADR-0122]] フォローアップ 3 自身が「フロントエンドの契約（orval 生成物と OpenAPI の整合）は
本件では扱わない」と射程外を宣言している。**「ドリフトし得る」という指摘を本決定は否定していない**
——それが上の但し書き（保証の上限）そのものであり、C# 側のゲートは [[IADR-0122]] が引き続き担う。

**決定 2: 定義は「BFF 実装 ＋ 後段サービス実装 ＋ 契約 DTO」の 3 つを開いて起こす。**
BFF のハンドラだけを読むと**透過中継されるステータスが落ちる**。本 issue が名指しした 4 件
（属性削除の 409・再変換の 409・文書更新の 409・`/bff/admin/config` の 404 のみ）は**すべてこの型**である。

**決定 3: `operationId` は C# の `WithName(...)` のケバブケースにする（新規分）。**
突合を機械的にするためである。**既存 2 本（`analysis-ask` / `analysis-analyze`）は改名しない**
——`useAnalysisAnalyze` の改名が SC-08 に波及し、「宣言の追加」という本作業の性質と混ざるためである。

> **［2026-08-05 追記］#519 が本決定の「（新規分）」を外し、既存 2 本も規約へ揃えた**
> （`bff-analysis-ask` / `bff-analysis-analyze`。改定は [[IADR-0135]] 決定 5）。
> 改名しない理由だった「SC-08 への波及」は、#519 が同ファイル（`useAnalysisTask.ts`）の
> import 1 行を触ることで消えた。**いま `operationId` は例外なく `WithName` のケバブケースである。**

**決定 4（論点 B）: B3 を採る。** `orval-bff-only.cjs` に
「**SSE の応答を持ち、JSON の応答を 1 つも持たない操作を落とす**」規則を足す。
**B2 が危険であることは実測で確かめた**——`/bff/analysis/ask/stream` を素直に載せると
`useBffAnalysisAskStream` が生成され、mutator（`bffFetch`）が本文を全部読んでから `JSON.parse` する
ため、**ストリーミングにならないうえ SSE 本文で例外になる**。orval は「扱えないから生成しない」と
いう振る舞いをしない。**規則は宣言ではなく成果物で固定される**——生成物はコミットされ CI が
再生成差分を検査するので、除外が壊れれば `useBffAnalysisAskStream` が現れて差分検査が落ちる。
専用の単体テストは置かない（トートロジーになる）。

**判定条件は応答の種別（2xx / エラー）を区別しない。** `isServerSentEventsOnly` は
`application/json` を持つ応答を 1 つでも見つけた時点で false を返すため、**SSE パスへ
`application/json` のエラー応答を足すと除外が外れる**。それでも判定を「2xx の応答に JSON があるか」へ
絞らないのは、(a) 現に `/bff/analysis/ask/stream` の応答は 200 の `text/event-stream` 1 つだけで
`application/json` を持たない（上流不達・非 2xx はヘッダ送出済みのため `event: error` で運ぶ）、
(b) 外れれば `useBffAnalysisAskStream` が生成物へ現れて再生成差分検査が落ちる、の 2 点による。
**絞るべきなのは、SSE パスが JSON のエラー応答を持つようになったときである**（そのとき判定を
「2xx の応答に JSON があるか」へ変える。前提が変わるまで規則を先回りして複雑にしない）。

**決定 5（論点 C）: C2 を採る。状態・種別の文字列を `enum` にしない。**
C# 側は `string` であり、値集合は `DocumentStatus` / `PolicyAction` / `AttributeScope` /
`ConversionJobStatus` などの `const` 群にすぎない。閉じた `enum` にすると後段の値追加で SPA が壊れる。
既存画面が「未知の値も受け取る」を明示的な仕様としている（`useConversionJobs.ts` ほか）ことと整合する。

**決定 6: 作業を 2 本に分割し、本 ADR の PR では「契約の追加と型の是正」だけを完了させる。**
**（分割そのものは [[IADR-0116]] 規約 4「1 PR が大きくなる場合は issue を分割する」の適用であり、
本 IADR の新規決定ではない。新たに判断したのは切り口——とくに下記 (c) の順序制約——だけである。）**
2 本目（画面の載せ替え）は独立に切り出す（**#519** として起票済み）。**理由は 3 つ**——(a) 1 本目だけで契約の単一情報源が揃う、
(b) 1 本目は宣言の追加に閉じて画面の挙動を一切変えないがレビュー単位として明確に違う、
(c) **順序が逆にできない**（`AiAnswerDto` の食い違いを直さずに載せ替えると誤った型が生成される）。

**決定 7: 書き込み要求の本文は既存の `CreateDocumentRequest` / `UpdateDocumentRequest` を再利用する。**
BFF の record（`DocumentCreateRequest` / `DocumentUpdateRequest`）は「DocumentService の要求と
**JSON 互換**」と実装が宣言しており、フィールドは 1 対 1 で一致する。同じ形の型を 2 つ生成させない。

## 理由

- **決定 1** は「いま覆えること」を優先した判断である。A2 / A3 は理想だが、本リポジトリの BFF は
  **応答を透過中継する設計**（[[IADR-0040]] の passthrough、`DocumentBffEndpoints.RelayAsync`）であり、
  C# のメタデータからは 409・400 が読めない。**理想の方式が、いま最も守りたいものを守れない。**
- **決定 4** の要点は「orval が SSE を扱えないこと」ではなく「**扱えないのに黙って諦めない**」こと
  である。人が気を付ける規約ではなく、**入力の段階で落として存在させない**——これは
  `orval-bff-only.cjs` が `/bff/` 以外に対してすでに採っている考え方（「そもそも関数が存在しない」）と
  同じであり、新しい作法を持ち込んでいない。
- **決定 5** は [[IADR-0122]] の思想（契約は形をスナップショットし、追加は非破壊）と整合する。
  `enum` を閉じると、後段での**非破壊な値追加が SPA では破壊的になる**という非対称が生まれる。

## 結果

- 良い影響:
  - `/bff/*` の**全 27 パス**（`grep -c '^  /bff' docs/api/openapi.yaml`）が契約に載り、
    **SSE 1 本を除く全操作に生成フック・型・MSW モックが存在する**ようになった。
  - `AiAnswerDto` の食い違いが解消し、[[IADR-0127]] 決定 3 の回避（共通フィールドだけを使う）が
    **不要になった**。SC-08 は `CitationDto` を直接使う。
  - 「載せ忘れ」と「意図的な対象外」が契約ファイルと通信仕様書の両方で区別できる。
- 悪い影響・トレードオフ:
  - **C# → OpenAPI の追随は人手のままである。** DTO を変えて OpenAPI を直し忘れると、
    SPA は古い型で通り続ける。**この穴は本 ADR では塞がない**（決定 1 の但し書き）。
  - **1 本目の時点で網が掛かるのは SC-08 だけである。** 残り 9 ファイルは 2 本目（**#519**）まで素通りする。
  - `orval-bff-only.cjs` の責務が 2 つになった（BFF 境界の絞り込み ＋ SSE の除外）。
    どちらも「生成の入力から落とす」であり、置き場所としては同じだが、名前は境界だけを表している。
- フォローアップ:
  1. **画面の載せ替え**（分割 2 本目 = **#519**）。手順は作業仕様書 §残りとして何をどうするか。
     **#519 の前に #520（既存の応答スキーマ 23 個へ `required` を入れる）を通す方が手戻りが少ない**
     ——両者は同じ生成型を触るため競合し、`required` の有無で生成される型の省略可否が変わるからである。

     > **［2026-08-05 追記］#520 で本項の前提（既存スキーマへの `required`）を消化した。
     > 項番 1 本体（画面の載せ替え = #519）は未消化である。** [[IADR-0132]] が方針を確定し、
     > **応答から到達する 36 スキーマのうち 31 個が `required` を持つ状態**になった
     > （残り 5 個は「入れない」判断を `description` に明記した除外）。
     > 生成型の省略可プロパティは **153 → 72**（`grep -c '?:' bff.schemas.ts`）。
     > **母集合は 25 個であり、上の「23 個」ではなかった**——23 は
     > 「`required` を持たない全 27 個 − #518 が意図的に持たせなかった 4 個」という数え方で、
     > **要求専用の 2 個（`AnalysisDataRange` / `UpdateMetadataRequest`）を含み、
     > 除外 4 個の再確認を範囲外に落としてしまう**。#520 は「27 − 要求専用 2」＝ 25 を採った。
     > 数え方と突合表は [作業仕様書 #520](../specs/20260805_issue-520_openapi-response-required.md)。
     > **#519 はこの状態を前提にしてよい**（載せ替え先の生成型はすでに必須化されている）。
     >
     > **［2026-08-05 追記］項番 1 の本体（画面の載せ替え）は #519 で消化した**（[[IADR-0135]]）。
     > **本 ADR 決定 1 の保証が画面まで届いたのはこの時点である**——#520 の変異試験で素通りしていた
     > M6 / M7 が落ちることを実測した。
  2. **C# → OpenAPI の追随を機械化する**（決定 1 の穴）。透過中継の応答を覆う方法が要る。
  3. 既存 2 本の `operationId` を決定 3 へ揃える（`analysis-ask` / `analysis-analyze`）。
     2 本目（**#519**）で `useAnalysisAnalyze` に触るなら、そのついでが最も安い。
     **［2026-08-05 追記］#519 で消化した**（[[IADR-0135]] 決定 5）。
  4. `/bff/feedback` 系の端点認可の裁定（通信仕様書 §未決事項 3 = **#521**。要裁定）。
     > **［2026-08-07 追記 / #586］裁定は下りた。** 計画 FR-08 が **無認証 401 / 権限外 403
     > （統計は運用者・管理者のみ）**を確定した（planning `3e58b97` = PR planning#244〔裁定依頼 planning#236〕）。
     > 本項に残るのは**実装**であり、**#521** が持つ。
