# IADR-0183: 検査器が「偽の緑」を返す条件の警告と、検証順序の置き場所（#683）

- 状態: Accepted
- 日付: 2026-08-11
- 決定者: claude（実装）

## 起点・関連

- **NFR**（文書統制・運用保守。メタ作業なので無採番。[IADR-0179](./IADR-0179_unnumbered-nfr-for-meta-work.md) 決定 1）
- 実装 issue: **#683**
- 作業仕様書: [20260811_issue-683](../specs/20260811_issue-683_checker-verification-order.md)

## 文脈 —— **手元で全部緑 → push → CI で赤**

**検査器に欠陥は無い。走らせた順序の問題である。**
`scripts/` の**検査器 32 本を全数**で分類したところ、**順序で結果が変わるものが 2 クラス・計 4 本**あった。

| クラス | 読むもの | **見えないもの** | 該当 | 件数 |
| --- | --- | --- | --- | ---: |
| **A** | `git show HEAD:` / `git diff …HEAD` | **未コミットの変更** | `check-doc-updated.js` / `check-landed-subjects.js` | **2** |
| **B** | **走査母集合を `git ls-files` から引く** | **untracked の新規ファイル** | `check-cross-repo-refs.js` / `check-plan-id-qualification.js` | **2** |
| C | 作業ツリー | （順序に依存しない） | 残り | **28** |

> **★ 上表は文字列 grep ではなく実挙動で引いた**（決定 8）。**初回の grep は 2 本を過大に拾っていた。**
>
> **★ #683 が挙げたのはクラス A の 1 本だけ**である（PR #682 の `check-doc-updated.js`）。
> **クラス B は本セッションが実際に踏んだ** —— PR #708 で、新規作成した作業仕様書に
> 「列挙形の修飾漏れ」が **3 箇所**あったにもかかわらず、`git add` 前に走らせた
> `check-cross-repo-refs.js` は**最後まで緑だった**。気づけたのは
> `check-commit-messages.js` がコミット本文の同じ形を検出したからである。
> **しかも本リポは、この型を planning#316 として同じ日に環流したばかりだった**
> （[IADR-0143](./IADR-0143_plan-id-qualification-checker-scope.md) 決定 4）。**環流した当人が踏んだ。**

## ★★ 決定 1: **失敗させない。警告に留める**

**未コミットで走らせること自体は正当な使い方**（書きかけの確認）であり、
**落とすと検査器が邪魔者になって外される**（#683 の但し書き）。

**終了コードを変えない。** 既存の `scripts/lib/ci-annotate.js` の `warn` を使う
（**18 本が既に使っている導線**。新しい仕組みを作らない）。

## ★ 決定 2: **クラスごとに「何が見えないか」を出し分ける**

**同じ文言にしない。読み手が採るべき行動が違う。**

| クラス | 警告の条件 | 促す行動 |
| --- | --- | --- |
| **A** | **未コミットの変更が 1 件以上** | **コミットしてから再実行** |
| **B** | **untracked が 1 件以上** | **`git add` してから再実行** |

**クラス C の 28 本には何も足さない** —— 作業ツリーを読むので順序で結果が変わらない。
**足せば嘘になる。**

## ★ 決定 3: **CI 用の環境分岐を書かない**

CI は**クリーンなチェックアウト**で走るので該当が 0 件になり、**自然に無音になる**。
`GITHUB_ACTIONS` を見る分岐を足すと、**条件と分岐が二重管理**になる。

> **★ レビュー環境では鳴りうる。** レビュー用の実行環境は `.claude/` と `CLAUDE.md` を
> develop へ復元するため、**未コミットの変更が常に存在する**。
> **鳴るのが正しい挙動**である —— その環境の結果が実 CI と一致しないのは事実だからである。

## ★ 決定 4: **走査範囲で絞り込まない（粗く鳴る側に倒す）**

クラス B の条件は「**untracked が 1 件でもあれば鳴る**」という粗いものにする。
**検査器ごとの走査範囲（`:!planning` / `:!src/ai-stock-trading` 等）と突き合わせない。**

**範囲の複製は必ず腐る** —— [IADR-0169](./IADR-0169_cross-repo-ref-scan-beyond-markdown.md) 決定 2 が
「名指しの除外リストは腐る」として退けたのと同じ理由である。
**粗くて鳴りすぎる方が、静かに見落とすより安い** —— **警告であって失敗ではない**ため実害が無い。

## ★ 決定 5: **境界の 3 本は対象にしない —— 理由はそれぞれ違う**

**git を使う ＝ 対象、ではない。** 実測（下記 決定 8）で git を呼ぶと分かった検査器のうち、
**3 本は「偽の緑」を作らない**。理由が違うので、まとめて「射程外」と書かない。

| 検査器 | 本リポに対する git の使い方 | 対象にしない理由 |
| --- | --- | --- |
| `check-action-versions.js` | `ls-files --error-unmatch <1 ファイル>` | **走査母集合ではない**（母集合は `readdirSync`）。しかも**追跡外なら専用の警告を自分で出す** —— 汎用の警告は覆いを増やさず雑音だけ増やす |
| `check-commit-messages.js` | `log origin/develop..HEAD` | **見落とす既存状態が無い**。コミット前に**件名は存在しない**（作業ツリーには「まだ書かれていない commit」は無い） |
| `check-planning-pin-freshness.js` | `ls-tree HEAD planning`（他は `-C planning`） | **偽の緑ではなく偽の赤**を作る。pin を未コミットで進めた状態では「遅れている」と出るだけで、**見落としの方向へは倒れない** |

## ★ 決定 6: **検証順序は `docs/DEFINITION_OF_DONE.md` にだけ書く**

`docs/ai-workflow.md` は「完了の定義 = `DEFINITION_OF_DONE.md` ＋ `/verify`」と**既に DoD を指している**。
**DoD が正本**であり、両方に書けば[IADR-0141](./IADR-0141_audit-rounds-and-population-drawing.md)（単一情報源）に反する。
**重複が無いことを回帰テストで固定する。**

## ★★ 決定 7: **注入したコードが到達可能であることを、静的判定ではなく実挙動で測る**

本作業の初回実装で、**当時の 6 本のうち 3 本の呼び出しが dead code だった** ——
`--self-test` ブロックが `return;` で終わっており、その**内側**へ挿していたためである。
**「到達可能か」を静的に見積もったヒューリスティックは、その 6 本すべて到達可能と誤答した。**

**是正**: **untracked のファイルを実際に作り、実行して警告が出るかを 1 本ずつ観測した**
（3 本が無音 → 挿入位置をブロックの外へ移動 → 再測定で全数が鳴る）。

> **★ この時点では規約にしなかった。** 「同型の事故が 2 回起きたら」の **1 回目**だったためである。
> **2 回目が決定 8 で起きたので、そこで検査器を足した。**

## ★★ 決定 8: **分類は文字列 grep ではなく実挙動で測る（同型 2 回目・検査器を足す）**

**初回の分類は文字列 grep で行い、`check-test-spec-coverage.js` を誤ってクラス B に入れた。**
当たったのは**エラーメッセージ中の `git ls-files`**（同ファイル 717 行）で、
**この検査器は `child_process` を一切 require しない。** AI レビューが指摘した。

**指摘は 1 本だったが、測り直したら過大は 2 本**だった（`check-action-versions.js` も外れる。決定 5）。

**是正の方法**: **PATH に `git` の shim を置き、32 本を実行して呼び出しを記録する。**
**推測ではなく実際の呼び出しが母集合になる。**

> **★ これは「静的な見積もりが誤答した」型の 2 回目**である（1 回目は決定 7 の到達可能性）。
> `CLAUDE.md`「**検査器・規約の追加は同型の事故が 2 回起きたら**」の条件を満たすので、
> **今回は検査器を足す** —— 回帰テストが同じ shim で分類を突き合わせる。

## ★ 決定 9: **分類の突合は 2 方向とも掛ける**

**宣言 → 実挙動**（宣言した検査器が実際にその git 使用を持つか）だけでは足りない。
**実挙動 → 宣言**（その git 使用を持つ検査器が宣言されているか）も要る。
**前者だけだと「宣言し忘れた新設の検査器」を素通りする。**

機械的な規則は 2 つで足りる（本リポを対象とする呼び出しに限る。`-C planning` は数えない）:

| # | 実挙動 | 要求 |
| ---: | --- | --- |
| 1 | `ls-files` を **`--error-unmatch` 無しで**呼ぶ | `MODE.TRACKED` を宣言していること |
| 2 | `show` / `diff` / `log` / `merge-base` / `rev-list` を呼ぶ | `MODE.HEAD` を宣言していること |

規則 2 の例外は **`check-commit-messages.js` の 1 件だけ**である（決定 5）。
**例外が 1 件であることも回帰テストで固定する** —— 名指しの除外リストは黙って伸びると腐る（IADR-0169 決定 2）。

## 結果

- 良い影響
  - **偽の緑を返しうる 4 本が、返しうる状況で自己申告する**ようになった
  - **検証順序が完了判定の正本（DoD）に載った** —— 手順の側にも根拠が残る
  - **クラス B が母集合に入った** —— #683 が挙げていなかった 2 本を含む
  - **クラス分けが手作業でなくなった**（決定 8・9）。**新しい検査器が git を使い始めたら、
    宣言し忘れを回帰テストが止める**
- 悪い影響・トレードオフ
  - **粗く鳴る**（決定 4）。走査範囲外の untracked でもクラス B の警告が出る
  - **レビュー環境では常時鳴る**（決定 3 の但し書き）
  - **分類の回帰テストは 32 本を実走する**（実測 **約 3.5 秒**）。静的検査より遅いが、
    **静的検査は 2 度誤答した**ので受け入れる
  - 規則 2 の**名指しの例外が 1 件ある**（`check-commit-messages.js`）。件数を固定して腐敗を防ぐ
- フォローアップ
  - **環流しない** —— キット側の検査器構成に依存する話ではなく、本リポ固有の分類である
