# IADR-0149: 検索結果の更新日時は索引ペイロードへ epoch ミリ秒で持ち、未再索引は null で縮退する

- 状態: Accepted
- 日付: 2026-08-09
- 決定者: claude（実装）

## 起点・関連

- 関連する計画書 ID: **SC-02**（検索結果一覧。§主要素「結果テーブル（文書／タグ／**更新日時**）」）／
  **FR-03**（ハイブリッド検索）／**FR-02**（取り込み）／**UC-01**
- 裁定: **Q6**（2026-08-05・planning#197）「**結果に更新日時を含める**。本項目のみ索引（Qdrant の
  ペイロード）へ日時を取り込むところから必要であり、**取り込み側の変更と既存文書の再索引を伴う**」
- 関連 ADR: [[IADR-0014]]（Qdrant ペイロードの表現。書き込み・フィルタ・復元を揃える）／
  [[IADR-0122]] 決定 2（既定値の無いメンバー追加は契約上の破壊的変更）
- 起点 issue: **#536**（後続 **#532** が本決定の索引項目をソートキーに使う）

## コンテキストと課題

`SearchResultDto` は日時を持たず、Qdrant のチャンクペイロードにも日時が無い（実測）。
計画は結果テーブルに更新日時を求めており、**索引へ取り込むところから**必要である。

決めること:

1. 索引ペイロードで日時を**どの型で**持つか。
2. 契約（`SearchResultDto`）へ**どう足す**か。
3. **既に索引されているチャンク**（日時を持たない）をどう扱うか。

3 は「あとで再索引すればよい」で済ませられない。**再索引は運用が実行する作業**であり、
本 PR が着地した瞬間から再索引完了までの間、索引は**日時を持つチャンクと持たないチャンクが混在**する。
この期間の振る舞いを決めないと、実装が暗黙の既定値（`default(DateTimeOffset)` = 0001-01-01）を返し、
**#532 の「更新日時の新しい順」で最古扱いになる**。

## 検討した選択肢

### (1) ペイロードの型

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **整数（Unix epoch ミリ秒）**（採用） | ○ | **表記に依らず順序が一意**。ISO-8601 は同じ時刻を `2026-08-09T12:00:00+09:00` とも `2026-08-09T03:00:00Z` とも書けるため、**文字列のまま並べると辞書順が実時刻順と一致しない**。整数なら比較が実時刻の比較そのものになる。Qdrant のペイロードインデックスにも数値としてそのまま載せられる（#532 が並び替えに使う） |
| 文字列（ISO-8601・UTC 正規化を強制） | × | 正規化を**書き込み側の規律**に頼る。書き込み経路は**2 つある**（取り込み側・検索側）ので、片方が正規化を忘れると静かに順序が壊れる。[[IADR-0014]] が同じ型の事故（表現の不一致）を実機で踏んでいる |
| Qdrant の datetime 型に委ねる | × | 表現の解釈をストア側の実装・バージョンに依存させる。**本リポジトリはテスト用のインメモリ実装も持つ**ため、ストア固有の型に寄せると 2 実装で意味が揃わない |

**オフセットは保持しない。** 値は「瞬間」であり、表示側のロケールで描く（画面は利用者のブラウザ設定に従う）。
元の文書がどのタイムゾーンで更新されたかは、計画が求めていない情報である。

### (2) 契約への足し方

**既定値つきの null 許容メンバーとして末尾へ足す**（`DateTimeOffset? UpdatedAt = null`）。
[[IADR-0122]] 決定 2 のとおり、既定値の無いメンバー追加は破壊的変更である。
`CitationDto` へ機密区分を足した #541 と同じ形を採る。

### (3) 未再索引チャンクの扱い

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **`null` を返す**（採用） | ○ | 「**日時を知らない**」を正しく表す唯一の値である。画面は `—` を描く |
| `DateTimeOffset.MinValue` で埋める | × | **嘘をつく。** 0001-01-01 の文書が実在するかのように振る舞い、#532 の「新しい順」で全部が末尾に固まる。「知らない」と「とても古い」は違う |
| 日時が無いチャンクを検索結果から落とす | × | **検索が壊れる。** 再索引が終わるまで既存文書がヒットしなくなる。計画が求めたのは列の追加であって、検索対象の縮小ではない |
| 本 PR で一括バックフィルを実装する | × | 再索引の仕組みは**既にある**（`DocumentUpdated` の再発行 → 全コレクションから削除して索引し直す。決定的チャンク ID により冪等）。新しい機構を足すと**同じことをする経路が 2 本**になる |

## 決定

1. **索引ペイロードのキーは `updated_at`、値は Unix epoch ミリ秒の整数**とする。
   **書き込みは 2 経路とも同じ表現で行う** —— 取り込み側（`QdrantIngestionVectorStore.BuildChunkPayload`）と
   検索側（`QdrantVectorStore.UpsertAsync`）。復元（`MapPayload`）も同じ表現から読む。
   [[IADR-0014]] が ABAC 属性で確立した「書き込み・フィルタ・復元を揃える」規律を、日時にも適用する。
2. **契約は `DateTimeOffset? UpdatedAt = null` を末尾へ足す**（既定値つき・[[IADR-0122]] 決定 2）。
3. **`updated_at` を持たないチャンクは `UpdatedAt = null` で返す。** 画面は `—` を描き、
   **「日時が無い」と「まだ再索引していない」を利用者へ区別して見せない**（索引の内部事情である）。
4. **本 PR は再索引を実行しない。** 手順は既存の運用（`DocumentUpdated` の再発行）に載せ、
   `docs/operations/operations.md` へ**本項目のための追記**をする。新しいバックフィル機構は作らない。
5. **時刻は取り込み側で作らない。** `DocumentUpdated.UpdatedAt`（既に契約にある）をそのまま運ぶ。
   取り込み時刻を書くと、**再索引のたびに全文書の「更新日時」が今になる** —— 計画が求めた
   「規程が改訂されたはずだが最新版はどれか」（Q5 の並び順の動機）が成立しなくなる。

## 影響

- `Knowledge.Contracts` の `SearchResultDto` に `UpdatedAt` が増える（**非破壊**。`check-contract-schema` の
  baseline は追加として承認する）。
- `IIngestionVectorStore.UpsertChunkAsync` / `ChunkPayload`（検索側のポート）の引数が増える。
  **どちらも内部ポートであり、サービス間契約ではない。**
- 再索引が完了するまで、既存文書の検索結果は `updatedAt` が `null` で返る（**縮退であって障害ではない**）。
- **#532（並び順の 2 値化）は本決定 1 の整数値をソートキーに使う。** 決定 3 により、
  #532 は「日時を知らないチャンクを新しい順のどこに置くか」を**自分で決める必要がある**
  （`null` は最小でも最大でもない。#532 側で判断し記録すること）。

## フォローアップ

- **#532**: 並び順 2 値（関連度〔既定〕／更新日時の新しい順）。本決定の索引項目を使う。

  （本 PR は値を載せるところまで）。
