# IADR-0148: 同期健全性はエンティティへ永続化する

> 実装リポジトリ内の意思決定記録（Implementation ADR）。1 ファイル = 1 意思決定。

## 背景

計画は 2026-08-05（利用者裁定・質問票 第12回 Q14・planning#198）で
**`DataSourceDto` へ同期健全性（連続失敗回数・再試行上限・直近エラー）を加える**と確定した。
根拠は次の一文である。

> データソースの同期は**「静かに壊れる」種類の機能**である。認証情報の期限切れ・共有名の変更・
> ネットワーク経路の変更で止まっても、誰も操作していないため気づかれない。
> **気づく手段が本画面の状態表示である。**

実装側には既に連続失敗の計数があった。**ただし singleton のインメモリ辞書**
（`SyncFailureTracker`。`ConcurrentDictionary<Guid,int>`）であり、
そのファイル自身が「本 PR ではインメモリ。DB 永続化は follow-up」と書いていた。

## 決定

### 決定 1: 健全性は `DataSource` エンティティの列として永続化する

`ConsecutiveFailureCount` / `LastSyncError` / `LastSyncErrorAt` をエンティティに持ち、
追加マイグレーション 1 本（すべて null 許容または既定値 0・**バックフィルなし**）で列を足す。

**棄却した代替案: インメモリの計数を読み口へ流用する（＝ 既存の `SyncFailureTracker` を endpoint から読む）。**

| 破れ方 | 何が起きるか |
| --- | --- |
| プロセス再起動 | 計数が 0 に戻る。**5 回連続で失敗していたソースが「正常」として表示される** |
| 複数レプリカ | 同期を実行したレプリカと、画面の GET を受けたレプリカが**別**になり得る。読んだ側の計数は 0 |
| 直近エラー | そもそもどこにも保持していない（計数しか持たない）。契約の 3 項目のうち 1 つが作れない |

**[[IADR-0083]] の単一書き手化は救いにならない。** アドバイザリロックが保証するのは
「**同時に同期を走らせるのは 1 レプリカだけ**」であって、「常に同じレプリカ」ではない。
読み取り（`GET /datasources`）はロックの外にあり、どのレプリカへ届くかは制御されていない。

**「静かに壊れる機能に気づく手段」として計画が位置づけた表示が、再起動やレプリカ配置で
静かに嘘をつくなら、要求を満たしていない。** したがって永続化する。

> **[[IADR-0136]]（`NextSyncAt` を持たない）と扱いが逆に見えるが、基準は同じである。**
> あちらは**ワーカーの位相から導出できる値**なので持たない（持つと実体とずれる）。
> こちらは**過去に起きた事実**であり、どこからも導出できない。**導出できるものは持たず、
> 導出できない事実は持つ** —— 判断基準は一貫している。

### 決定 2: 計数の置き場所は 1 つにする（`SyncFailureTracker` は削除する）

エンティティが計数を持つ以上、インメモリの計数を**併存させない**。併存させると
同じ数が 2 箇所に立ち、片方が黙って古くなる（本リポジトリが繰り返し踏んでいる型）。

`AlertOnFailure` はエンティティへ記録し、永続化は呼び出し側の `SaveChangesAsync` が行う
（手動 `/sync` と定期同期ワーカーの**両方**が既に呼んでいることを実測して確認した。
片方だけだと計数が保存されない経路が空く —— 「呼び出し口を 1 つだけ配線する」型）。

### 決定 3: しきい値は再試行上限そのものとし、定数を 1 つにする

計画は「**「継続失敗」のしきい値は再試行上限に達した時点とする**（hi-fi の「3/5」に倣えば
**5 回連続失敗**）。計画で決めないと実装が決めることになるため明示する」と書いている。

**現行実装は独自に `AlertThreshold = 3` を持っていた** ——
**計画が「実装が決めることになる」として明示的に排した状態そのもの**である。

`DataSourceSyncHealth.DefaultRetryLimit = 5`（契約側）を単一情報源とし、
`DataSourceSyncService.AlertThreshold` はそれを参照するだけにする。

> **hi-fi の「3/5」をしきい値 3 と読まない。** これは「**5 回中 3 回目**」という進捗表示である。
> 計画はその読み替えを明示している。**モックの数字を仕様として写さない。**

### 決定 4: 再試行上限は契約で返す（画面へ定数を複写させない）

`DataSourceDto.RetryLimit` を返す。画面は「3/5」の**分母を契約から得る**。

複写すると同じ数がサーバと画面の 2 箇所に立ち、サーバ側を変えたときに黙って割れる。
これは [[IADR-0127]] 決定 2 が禁じた「契約から導出できない表示」の裏返しである
——**表示できるようにするために契約へ載せる**のが同決定の趣旨だからである。

**`IsUnhealthy` のような導出フラグは契約に持たせない。** 判定
（`ConsecutiveFailureCount >= RetryLimit`）は画面側で行える。持たせると同じ判断が 2 箇所に立つ。

### 決定 5: 直近エラーは**保存の時点で**マスクする

例外メッセージは秘密を運ぶ（接続文字列の `Password=`・資格情報つき URI・`Bearer` トークン）。
`SyncErrorRedactor` を通してから保存する。

**表示の時点でマスクするのでは足りない。** DB に平文が残ると、バックアップ・ログ・
将来の別の読み口すべてが漏洩面になる。[[IADR-0053]] が応答の `Config` に与えた守りを、
**直近エラーという新しい経路にも同じ強さで**通す。

- **キー名は残し、値だけを伏せる** —— 原因の切り分けには「どの項目が悪いか」が要る。
- **URI の資格情報はユーザー名も伏せる** —— アカウント名自体が攻撃の手掛かりになる。
- **切り詰めはマスクの後に行う。** 順序が逆だと、上限より後ろの秘密が「切り詰めたから消えた」ように
  見え、上限を伸ばした瞬間に漏れる（テストで固定した）。

### 決定 6: マスク値（`***`）は保存しない —— **読んで書き戻す往復が秘密を壊さない**

> **［2026-08-08 追記 / PR #627 の AI レビュー 🟡］この決定は当初の実装に無く、レビュー指摘を
> 自分で再現してから足した。** 指摘は正しかった。

応答は秘密キーの値を `***` にマスクして返す（[[IADR-0053]]）。一方 **#534 が新設した `PUT` / `PATCH` は
`Config` を丸ごと差し替える**。したがって「**GET して一部を直して送り返す**」という API の最も普通の
使い方で、`apiToken` が文字列 `"***"` として永続化され、**本物の資格情報が破壊される**。

**実測**（当初実装で再現。`Update_WritingBackMaskedSecret_KeepsStoredValue` が `PUT` / `PATCH` の
両方で fail した）。

**決定**: 書き込み時、**秘密キーの値がマスクそのものなら保存しない**。

| 状況 | 挙動 |
| --- | --- |
| 秘密キー ＋ 値が `***` ＋ 既存値あり | **既存値を保つ**（往復が無害になる） |
| 秘密キー ＋ 値が `***` ＋ 既存値なし | **そのキーを落とす**（`"***"` という資格情報は存在しない。保存すると接続時に意味の分からない失敗になる） |
| **秘密キーでない** ＋ 値が `***` | **そのまま保存する**。マスクされて返らない値なので、利用者が意図して入れた文字列と区別できる。**過剰に守らない** |

**秘密キーの定義とマスク値は `SecretConfigMask` を単一情報源とする**（読みのマスクと書きの防御が
同じ知識を使う）。**2 箇所に持つと、マーカーを足したときに片方が黙って古くなる** ——
本リポジトリが繰り返し踏んでいる型である。従前は `DataSourceEndpoints` が自前のマーカー配列を
持っていたので、そこから移した。

> **「拒否（400）」ではなく「既存値を保つ」を選んだ理由**: 拒否すると、読んで書き戻すという
> 正常な使い方が**常に**失敗し、利用者はマスク済みキーを手で除く運用を強いられる。
> マスクが**可逆に往復する**ほうが、契約として素直である（パスワード欄が伏字で往復するのと同じ）。

## [[IADR-0127]] 決定 2 との関係 —— **予約の解除であって、覆しではない**

[[IADR-0127]] 決定 2 は「琥珀（警告色）は `DataSourceDto` が同期健全性を持つまで**どの状態にも
充てない**」と定め、`disabled` を中立に置いた。**本決定はその予約を解除する**（契約が健全性を
持ったため）。**同決定を `Superseded` にはしない。**

- **`disabled` を中立に置く判断は変わらない。** 計画も「実装が `disabled` を中立表示に改めて
  琥珀を空けたまま保留した判断は**妥当であり、そのまま活かす**」と明記している。
- 画面は**状態を健全性より先に見る**（無効なら中立）。無効化されたソースは同期が回らないので、
  残っている失敗回数を異常として出し続けると「管理者が意図して止めた正常な状態」に ⚠ が付く。

## 影響

- **契約**: `DataSourceDto` に 4 メンバー追加（すべて既定値つきの省略可能パラメータ＝
  [[IADR-0122]] 決定 2 の**非破壊**側。`check-contract-schema.js` が非破壊 7 件と判定した実測あり）。
- **DB**: `DataSources` に 3 列追加。バックフィルなし（既定 0 / null は実態と一致する ——
  過去の失敗回数はもともとどこにも記録されていない）。
- **表示**: SC-06 に琥珀の 2 状態（`再試行中（n/limit）` / `同期異常（n/limit）`）が出る。
  色だけで意味を持たせない（`StatusBadge` がアイコンとテキストを型で強制する。INDEX 決定 21）。
- **アラート発報そのものは変えていない** —— 構造化ログ（`Alert=true`）は [[IADR-0051]] 決定 3a の
  実装として既に在り、本決定が変えたのは**しきい値の値**だけである。
  Alertmanager への配線は未配備であり、本決定の射程外である（#546）。

## 検出しないこと（開示）

- **健全性のプロセス横断の合算はしない。** 永続化により再起動・レプリカ跨ぎで値は保たれるが、
  複数レプリカが同時に同じソースを同期する状況は [[IADR-0083]] が排しているため、
  合算そのものが要らない。**ロックが外れた場合に計数が競合し得ることは検出しない。**
- **直近エラーのマスクは網羅ではない。** 既知の型（キー=値・URI 資格情報・HTTP 認証スキーム）を
  塞ぐが、コネクタが独自形式で秘密を埋めた例外までは捕まえられない。
  **これは「できない」ではなく「網羅を主張しない」である**（[[IADR-0145]] 決定 3 の言い分けに従う）。
  新しい型が見つかったら `SyncErrorRedactor` へ規則を足し、`SyncErrorRedactorTests` へ正例を足す。
