## コンテキストと課題

[IADR-0116](IADR-0116_reimplementation-branching-and-pr-policy.md) 規約 1 は「1 issue = 1 branch = 1 PR」を
定める。これは #454 の「退行を発生させない」を最優先に、develop 基準の CI ゲート（ratchet・版数比較）を
生かしたまま、人がレビューできる変更単位を保つための決定である。

一方 #572 は、planning の裁定（2026-08-05 質問票 第12回）から一度に流入した **B 群 13 件**
（#532〜#544）が「DTO へ項目を足す ＋ OpenAPI ＋ contract baseline ＋ テスト ＋ 仕様書」という
**ほぼ同一の形**をしており、1 件ずつ PR にすると固定費が件数分そのまま掛かることを示した。
利用者裁定（2026-08-07）は「**ドメイン単位で束ねる（新 IADR を起票）**」を与えた。

決めるべきは 4 点である。(1) どういうときに束ねてよいか、(2) 束の 1 件だけを差し戻すときどうするか、
(3) 複数 issue を誰が閉じるか、(4) クロス監査を束ごとにするか issue ごとにするか。

## 検討した選択肢

| | A. ドメイン単位で束ねる（採用） | B. 現状維持（1 issue = 1 PR） | C. 全 B 群を 1 PR | D. issue を統合する | E. スタックド PR |
| --- | --- | --- | --- | --- | --- |
| PR 固定費 | 束の数だけ | **10 件分そのまま** | 1 回 | 統合後の件数分 | 件数分（積むだけ） |
| 1 PR の規模（実測換算） | 2〜3 件 = 37〜53 ファイル | 15〜25 ファイル | **150 ファイル超・8000 行超** | 大 | 小 |
| レビュー可能性（CLAUDE.md の目的） | 保てる | 最良 | **損なう** | 損なう | 保てる |
| issue 単位の追跡 | コミット＋`Closes`＋`refs/pull` | 自明 | 崩れる | **裁定 Q との 1:1 が切れる** | 保てる |
| develop 基準のゲート | 有効 | 有効 | 有効 | 有効 | **base が develop でない期間ができる** |
| マージ設定との整合 | 可（スカッシュ 1 回） | 可 | 可 | 可 | **rebase / merge commit が無効なため手作業のリベースが要る** |

- **B（現状維持）は裁定で否定された。** 実測の固定費（作業仕様書 288〜360 行・check runs 45 本
  ＝ 41.8 分・AI レビュー 3 本・監査 2 本・マージ 1 回）が 10 件分そのまま掛かる。
- **C（全 B 群を 1 PR）は採らない。** 1 件 15〜25 ファイル / +636〜943 行の実測から、10 件で
  150 ファイル超・8000 行超になる。[[IADR-0116]] 規約 4（PR が大きくなるなら issue を分割する）と
  正面から衝突し、共有 3 ファイルの巻き戻し単位も最大化する。
- **D（issue の統合）は採らない。** 各 issue は planning の裁定 Q 番号と 1:1 で対応する
  （本文末尾に「裁定: Q5」「環流元: planning#197」が入っている）。統合すると**裁定と実装の対応が切れ**、
  環流の追跡（`feedback/` → planning#NNN → issue → PR）が壊れる。#454 のチェックリストの粒度も変わる。
- **E（スタックド PR）は採らない。** 本リポジトリは `allow_rebase_merge = False` /
  `allow_merge_commit = False` で**スカッシュのみ**（実測）。親がスカッシュされると子の base を
  手で張り直す作業が毎回生じ、その間 base が develop でないため [[IADR-0116]] が案 B を退けた理由
  （develop 基準の ratchet・`--compare-with-ref origin/develop` が効かない）が小規模に再現する。

## 決定

### 決定 1: 次の **6 条件をすべて満たすとき**に限り、同一資源の契約追加を 1 PR に束ねてよい

> **裁定の言葉は「ドメイン単位で束ねる」だが、判定に使う単位は「資源」である**（条件 A）。
> ドメインを画面（SC）で読むと実効表が再現できないため、資源（同じ読み書き口 / 同じ DTO 群）で
> 判定する。理由は下記「条件 A を『同じ SC』ではなく『同じ資源』で判定する理由」に置いた。

| 条件 | 内容 | 満たさない実例（実測） |
| --- | --- | --- |
| **A. 同一資源** | **同じ API 資源（同じ読み書き口の系統）または同じ DTO 群に閉じること。同じ画面（SC）を共有するだけでは足りない**——1 画面は複数の資源を読むためである。資源が同一かどうかは、契約（DTO / エンドポイント）と、**それを「1 系統」と定めた計画 ADR の記述**で判定する | **#535 と #542**（**SC-09 を共有するが**資源が別。ポリシーの検証口 vs タグ辞書の読み取り口）／**#539 と #540**（**SC-01・SC-08 を共有するが**資源が別。後述のとおり ADR-0043 決定 4 は #539 側を照会口の**参照元**として挙げており、口そのものではない） |
| **B. 裁定が済んでいる** | 実装中に判断が要らない。issue 本文に**未解決の質問が無い** | **#546**（本文「本件は裁定の対象外です」＋「配備時期をお知らせください」。ラベルも `infrastructure` で B 群外） |
| **C. 非破壊側に収まる** | 契約追加が [[IADR-0122]] 決定 2 の非破壊側（既定値付きの追加・必須→省略可）に収まる | — |
| **D. 1 コミット = 1 issue** | 束の中で issue とコミットが 1:1 に対応する（決定 3 の担保とセット） | — |
| **E. 着手済みを含まない** | ブランチ・PR が既にある issue は単独で着地させる | #538 / #533 / #541 |
| **F. 契約の追加に閉じる** | 既存データの移行・**再索引**、取り込み側（インデクサ / ワーカー）の変更、外部システムの配備を伴わない。**エンドポイントの追加は「契約の追加」に含む**（#534 の PUT / PATCH、#540 の照会 API のように非破壊の追加であれば妨げない） | **#536**（本文「取り込み側の変更を伴う」「既存文書の再索引が要る」「契約の追加のみ の項目と**同じフェーズに束ねないこと**」）／**#546**（Alertmanager の配備そのもの） |

**条件 F は #575 の草案に無く、本決定で足した。** 根拠は #536 の issue 本文そのものである
（上記実測 (f) 2）。**草案 5 条件だけを機械的に当てると、issue が明示的に禁じている束ね方を
「条件を満たす」と判定してしまう。**

#### 条件 A を「同じ SC」ではなく「同じ資源」で判定する理由（クロス監査 🔴-1 の是正）

**当初の条件 A は「同じ DTO 群、同じ画面（SC）、または同じ API 資源」という選言だった。これは誤りである。**
そのまま当てると、SC-09 を共有する #535 と #542、SC-01・SC-08 を共有する #539 と #540 が束ねられ、
**決定 5 の実効表（2 束）が再現できない**。「4 束 → 2 束」を実際に導いた基準は資源の同一性であり、
それが本文に書かれていなかった。**次に条件を当てる人が同じ表を再現できないなら、条件として機能しない。**

資源の同一性を判定する一次根拠は、**issue 本文ではなく計画 ADR**である。#540 と #542 については
[ADR-0043](../../planning/projects/microservices-platform/07_adr/ADR-0043_scoped-attribute-value-lookup.md)
（`status: Accepted`。planning pin `e36b592` で本文を実読して確認した）**決定 4**が該当する。

> ### 決定 4: 読み取り口はロール別のスコープを持つ 1 系統とする
>
> 同じ「タグ辞書の値集合を読む」要求が 3 箇所にある。
>
> | 参照元 | 主体 | 必要な範囲 |
> | --- | --- | --- |
> | SC-01 / SC-08 の対象範囲フィルタ | 一般利用者 | 到達できる文書に付与された値のみ（決定 1・2） |
> | SC-05 のタグ入力（既定辞書に整合） | 管理者・運用者 | 辞書の値集合（読み取り専用） |
> | SC-09 のタグ辞書の管理 | システム管理者 | 値集合・使用件数・追加・改名・削除 |
>
> **読み取り口を 3 種類作らない。1 系統とし、スコープだけロールで変える。**

**この表が #540（一般利用者向けの照会）と #542（SC-09 のタグ辞書管理）を 1 つの資源として束ねている。**
当初 本 ADR は「#542 はタグ辞書＝別資源」と書いていたが、**計画 ADR の記述と衝突しており誤りだった**
（実装者の読みより計画 ADR が強い）。同表は **SC-01 / SC-08 の対象範囲フィルタ（＝#539 が触る面）を
「参照元」として挙げている**——照会口を**使う側**であって、口そのものではない。したがって
**#539 は #540 と同じ資源ではない**（決定 5 の判定はこの表から再現できる）。

#### 束の上限（クロス監査 🟡-1 の是正）

**名目上の上限は 3 件だが、実効上限は 2 件である。** 判定はファイル数・行数の目安が優先する。

| 目安 | 値 | 3 件束の実測 | 判定 |
| --- | --- | --- | --- |
| ファイル数 | 概ね **50** | **53**（#538 / #533 / #541 の union） | **超える** |
| 追加行 | 概ね **+2500** | +2413 | 収まる |

**実測の典型的な 3 件束はファイル数の目安を超えるため、当面は 2 件を上限として運用する。**
3 件を許すのは、両方の目安を下回ることが着手前に見積もれる場合に限る。根拠は実測
（1 件 = 15〜25 ファイル / +636〜943 行）であり、[[IADR-0116]] 規約 4
（**1 PR が大きくなる場合は issue を分割する**——PR を分割して 1 issue に複数 PR をぶら下げない）の
裏返しである。**規約 4 が大きい側に置いた歯止めは、束ねる側にも要る。**

### 決定 2: 差し戻しは「マージ前はコミット単位、マージ後は束単位」である

- **マージ前**（レビュー・監査で 1 件だけ通らない）: **その issue のコミットだけを落として束を進める**
  （`git rebase --onto` で外す、または `git revert` して差分を残す）。落とした issue は単独 PR へ戻す。
  束ごと閉じない。
  - 実測: 異なる DTO を触るコミット同士なら**衝突 0**で外せる。**同一 DTO を触る場合は衝突する**
    （束の典型はこちら）。衝突解決を誤った場合は**過剰・過小のどちらも
    `node scripts/check-contract-schema.js` が exit 1 で止める**（上記実測 (d)）。
  - **解決後は必ず `--update` なしで実行して baseline と突き合わせる。** `--update` を先に打つと
    「誤った解決結果を正として焼き直す」ことになり、網が消える。
- **マージ後**（develop へ入ってから問題が出た）: **develop には束が 1 コミットしか無い**
  （スカッシュのみ・実測 (b)）。`git revert <sha>` は**束全体を戻す**。部分差し戻しは新しい PR で
  手作業になる。
  - **これが束ねることの唯一かつ本質的な代償である。** だからこそ条件 B（裁定済み）・C（非破壊）・
    F（契約追加に閉じる）で「マージ後に差し戻す確率が低いもの」だけに例外を限る。
  - 束の PR は**全件の監査を終えてからマージする**（決定 4）。1 件でも保留があるなら、その 1 件を
    束から外してからマージする。

### 決定 3: サブ issue は **PR 本文の `Closes` を issue ごとに 1 行**書いて閉じる

- **キーワードは番号ごとに前置する**（`Closes #534` と `Closes #537` を別々の行に書く）。
  実測 (c) のとおり PR #422 でマージ 2 秒後に 2 件とも `state_reason=completed` で閉じている。
- **親 #454 のチェックリスト更新は併用するが、クローズ主体ではない。** チェックリストは進捗表示であり、
  issue の状態を変えない。両方やる。
- **スカッシュ後の develop 側の担保**は次の 3 段で行う（実測 (b) のとおりコミット境界は develop に残らない）。
  1. **PR タイトルに束の全 ID をカンマ併記**する（`種別(SC-06,UC-04): 要約`）。先例は `ef1978e`
     （9 個の SC を併記した件名が develop に載っている）。`check-commit-messages.js` / `pr-title.yml` は
     カンマ区切りの複数 ID を許容する。
  2. **スカッシュ本文に issue ごとの内訳**を書く（`#534: …` / `#537: …`）。
     既定は `squash_merge_commit_message = BLANK` なので**マージ時に手で入れる**。
  3. **1 コミット = 1 issue の実体は `refs/pull/<PR>/head` に残る**（`delete_branch_on_merge = True` でも
     参照は生きる。実測 (b)）。復元は `git fetch origin refs/pull/<PR>/head`。
- **`Closes` の書き忘れは何にも止められない**（テンプレートに欄が無く、機械検査も無い。実測 (c)）。
  現状は**人が手で閉じている**（B 群 3 件すべて。#538 はマージから 10 分 50 秒開いたままだった）。
  束の PR では**閉じ忘れ・閉じ遅れが件数分まとめて起きる**ため、レビュー時に
  「`Closes` の行数 = 束の件数」を目視で数える。

### 決定 4: クロス監査は **issue ごとに 1 回 ＋ 束ごとに 1 回**とする（軽くしない）

- **issue ごと（＝コミットごと）の監査を減らさない。** 根拠は実測 (e) であり、#541 / #538 / #533 の
  3 件すべてで監査が 🟡 指摘を出し、うち 2 件は**コードの是正**に至った。指摘はいずれも
  その issue 固有の中身（母集合の取り方・`null` の二義性・存在しないテストへの参照）で、
  束ねても消えない。
- **束ごとに 1 回を上乗せする。** 束にしか現れない面を見るためである。
  - 共有ファイル（`docs/api/openapi.yaml` / `scripts/contract-schema-baseline.json` /
    orval 生成物）の整合が**束の中で最後に勝った版**になっていないか
  - コミットの境界が issue と 1:1 か（決定 1-D）
  - 束内の順序依存が守られているか（例: 索引項目を作る側 → それを使う側）
- **#572 の施策 3（監査の重さを risk に比例させる）は「判断なし＝現状維持」である。**
  本決定は**監査を軽くしない**。減るのは PR 単位の固定費（作業仕様書 1 本・CI 1 周・AI レビュー 1 本・
  マージ 1 回）だけである。

  > **［2026-08-07 追記・前提の是正 / #594］この段落の前提は古い。** 施策 3 は同日中に
  > **利用者裁定（第 2 回）で「見直し」が確定**し、[IADR-0141](IADR-0141_audit-rounds-and-population-drawing.md)
  > として着地した。**ただし本決定 4 の実体は変えない**——2 つの決定は数えているものが違う。

  > | **[[IADR-0141]] 決定 2** | **1 対象あたりの巡数** | 各対象が全面 1 巡 ＋ 是正差分のみ |

  > 依然として有効**であり、限定されたのは巡数だけである（[[IADR-0141]] 決定 5）。

### 決定 6: 束ねた PR の作法

1. **ブランチ名**: [[IADR-0116]] 規約 3 の選び方をそのまま使い、**束の代表 ID**（同一資源なので
   通常は共通の SC / FR がある）を採る。例: `feat/SC-06-datasource-contract-bundle`。
2. **PR タイトル**: `種別(ID1,ID2): 要約`。束の全 ID を併記する（決定 3）。
3. **作業仕様書は束に 1 本**（CLAUDE.md の粒度「作業/PR 単位」どおり）。ただし **issue ごとの節**を必ず設け、
   受け入れ基準を issue 単位で書く。**機能 / 画面 / テスト仕様書の粒度は FR / SC 単位のまま変えない**
   （[[IADR-0130]] のテスト仕様書記載被覆はこの粒度で走る）。
4. **コミット**: 1 コミット = 1 issue。件名は `種別(起点ID): 要約`、**本文に `Refs #NNN`** を残す
   （スカッシュで develop からは消えるが、`refs/pull/<PR>/head` には残る）。
5. **束の中に順序依存があるなら、コミット順で表現する**（依存される側を先頭に）。
   ただし**依存の理由が「片方が索引・データを先に作る」ことなら、条件 F を疑う**
   ——#536 → #532 はこれに当たり、束から外れた。

## 理由

- **束ねてよい根拠は「同型であること」ではなく「マージ後に差し戻す確率が低いこと」である。**
  実測 (b) のとおり develop 側の巻き戻し単位は必ず束全体になる。したがって条件は
  「レビューで落ちにくい」＝裁定済み（B）・非破壊（C）・契約追加に閉じる（F）へ収束する。
  「DTO へ項目を足すだけだから軽い」という理由づけは、実測 (e) が示すとおり**成り立たない**
  （軽いはずの 3 件すべてで監査が実質的な指摘を出した）。
- **条件 F を足したのは、草案どおりだと issue の明示的な禁止（#536）を踏み越えるからである。**
  「同じ資源」と「同型」は別の性質であり、同じ検索資源の 2 件でも、片方が既存データの再索引を
  伴えば作業の形はまったく違う。**ドメインで束ねるという裁定は、作業の形が同じであることまでは
  保証しない。**
- **条件 A を資源基準にしたのは、条件が「表を再現できる」ことを要件とするからである。**
  当初の選言（DTO / SC / 資源のいずれか）は、決定 5 の実効表を導いた実際の基準（資源の一致）を
  本文に書けていなかった。**書かれた条件から表が再現できないなら、それは条件ではなく後付けの説明である。**
  資源の同一性の一次根拠を計画 ADR（[ADR-0043](../../planning/projects/microservices-platform/07_adr/ADR-0043_scoped-attribute-value-lookup.md) 決定 4）に置いたのは、
  **issue 本文は実装側の要約であって、口を 1 系統に保つと決めたのは計画側だから**である。
- **1 コミット = 1 issue でトレーサビリティを担保する**という #575 草案は、そのままではこのリポジトリで
  成立しない（スカッシュのみ・ブランチ削除）。決定 3 の 3 段（タイトルの全 ID・スカッシュ本文の内訳・
  `refs/pull`）で埋めた。**「コミットで担保する」と書いて終わりにすると、develop 上には何も残らない。**
- **監査を軽くしない**のは、#572 施策 3 に判断が出ておらず（＝現状維持）、かつ**軽くする根拠が実測に
  無い**からである。本決定は PR 単位の固定費だけを削る。ここを混ぜると、削減の効果と品質の劣化が
  同じ変更に載って切り分けられなくなる。
  > **［2026-08-07 追記・前提の是正 / #594］この段落も決定 4 と同じ古い前提に立っている。**
  > 施策 3 は同日中に利用者裁定（第 2 回）で見直しが確定し、
  > [IADR-0141](IADR-0141_audit-rounds-and-population-drawing.md) として着地した。
  > **ただし本段落の結論（本決定は監査を軽くしない）は変わらない**——限定されたのは
  > **1 対象あたりの巡数**であって、本決定が定める**監査の対象の数**ではない（決定 4 の追記と同じ区別）。
- **[[IADR-0116]] を `Superseded` にしないのは、原則が変わらないからである。** 例外は条件つきで
  最大 3 件の束に限られ、条件を満たさないものは規約 1 のままである。改定範囲を 1 点に限る先例は
  [[IADR-0117]]（IADR-0056 決定 3 の部分改定）と [[IADR-0122]] 決定 4（IADR-0049 決定 1 の部分繰延解除）。

## 結果

- 良い影響:
  - 残り 10 件の PR 数が **10 → 8** になる（2 束）。削減幅は #572 の見積（10 → 4）より小さいが、
    **根拠が issue と計画 ADR の実測にある**ぶん、束ねた結果が着手時に破綻しない。
  - 束ねてよい条件が**判定可能な形**（issue 本文・ラベル・IADR-0122 の分類）で残るため、
    以後の同種の流入（planning の裁定が一度に降りてくる形）にそのまま当てられる。
  - 差し戻しの手順とその限界が、実験の結果つきで書かれている。
- 悪い影響・トレードオフ:
  - **監査の回数はむしろ増える。** 束ねる 4 件（2 束）について、単独運用なら **4 回**だったクロス監査が、
    決定 4 により **issue ごと 4 回 ＋ 束ごと 2 回 = 6 回**になる。**減るのは PR 単位の固定費
    （作業仕様書・CI 1 周・AI レビュー・マージ）だけ**であり、監査コストは +2 回である。
  - **マージ後の差し戻しは束単位になる**（決定 2）。develop 上のコミットは 1 本しか無い。
  - **レビューの一度に読む量が増える**（2 件束で 37 ファイル前後）。**上限 3 件はファイル数・行数の
    実測から引いた目安であって、「何ファイルまでなら人が読めるか」を測った値ではない。**
  - **束の分だけ「1 件が遅れると全部遅れる」**。条件 E（着手済みを含まない）は、この結合を
    最小にするための条件でもある。
  - **`Closes` の書き忘れが件数分まとめて効く**（実測 (c)）。
  - **検出しないこと**（明示する）:
    - **束の 6 条件に機械検査は無い。** 本決定は規約であって検査器ではない。
      `check-commit-messages.js` は
      **「1 コミット = 1 issue」も「Closes の行数 = 束の件数」も検査していない**（実測。
      **同スクリプトが何を見るかは実測 (c) を正とする** —— ここへ列挙を写すと片方が腐る）。
      守られているかはレビューと監査でしか分からない。
    - **`Closes` の書き忘れ**——PR テンプレートに欄が無く、CI も見ない。マージは通り、issue は
      **人が気づいて手で閉じるまで開いたまま**である（#538 は 10 分 50 秒開いていた。実測 (c)）。
    - **決定 3 は「既定ブランチが `develop` であること」に依存する。** GitHub の `Closes` による
      自動クローズは**既定ブランチへのマージでしか働かない**。本リポジトリの既定ブランチは
      `develop`（`git ls-remote --symref origin HEAD` → `ref: refs/heads/develop` を実測）なので
      決定 3 は成立するが、**既定ブランチを `main` へ変えると束の issue が静かに閉じなくなる**。
      この依存を検査するものは無い。
    - **契約面以外の部分差し戻し**——実験で「誤った差し戻しが機械で止まる」ことを確かめたのは
      `Shared.Contracts` の面（[[IADR-0122]] のスナップショット）だけである。**EF マイグレーション・
      画面・orval 生成物・テストの巻き戻し漏れは、この網に載らない。**
    - **束ねたことによる退行**——カバレッジ床（[[IADR-0118]] / [[IADR-0138]]）も契約ゲートも
      PR 単位で判定するため、**束の中の 1 件が下げた被覆率を別の 1 件が埋めても通る**。
      issue 単位の品質は測っていない。
    - **issue 消化率そのもの**（#572 の起点）——本決定が減らすのは PR 数であって、issue の
      流入量にも消化速度の測定にも触れない。
    - **本決定の対象外の群**——A 群（裁定・実環境待ち）・C 群（大玉）・D 群（小〜中）には効かない。
      B 群と同じ「同型さ」が無いためである。
    - **決定 5 の実効表は 2026-08-07 時点のスナップショットである。** 判定の入力は issue 本文と
      ラベルであり、**それらが後から編集されれば判定は変わる**。本 ADR は自動では追随しない。
      束を組む直前に条件 A〜F を当て直すこと。
  - **未確認のまま残したこと**（推測で埋めない）:
    - **1 つのキーワードで複数番号を並べる形**（`Closes #534, #537`）は**本リポジトリに実例が無く、
      試していない**。決定 3 は実例のある「番号ごとに 1 行」だけを規定する。
    - **束ねた PR を実際にマージしたときの CI 実測**（check runs の本数・所要時間が束ねてどう変わるか）。
      本決定の固定費の数字は**単独 PR 3 本の実測**であり、束の実測ではない。
    - **監査の指摘件数（🟡 3 / 2 / 3 件）の出所は各 PR の修正コミットのメッセージ**であり、
      監査そのものの出力を読んだものではない。指摘が実在してコード・文書の是正に至ったことは
      差分で確認したが、**件数の網羅性は保証しない**。
- フォローアップ:
  1. **決定 5 の実効表を issue 側へ記録する**（束の所属をラベルまたは本文に残す）。本作業セッションは
     GitHub へ書き込めないため**親が行う**。#575 の受け入れ基準の 4 項目めはこれに当たる。
  2. **#572 コメントの表との差分（4 束 → 2 束）について利用者の確認を取る**（作業仕様書「未決事項」1）。
  3. **`.github/PULL_REQUEST_TEMPLATE.md` に「クローズする issue」欄を足すか**を別 issue で判断する。
     束ねる運用では書き忘れの損害が件数分になる（作業仕様書「未決事項」2）。
  4. **#537 の射程**（契約とアラート発報の境界）を着手前に確定する。できなければ束から外す（決定 5）。
  5. 束を 1 本流したあと、**実際の固定費削減と差し戻しの発生率**を測り、上限 3 件と条件 F を見直す。
