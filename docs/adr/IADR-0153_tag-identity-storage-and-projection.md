# IADR-0153: タグの正本は識別子、派生（索引・外部システム）は表示名。改名はイベント再発行で追随させる

- 状態: Accepted
- 日付: 2026-08-09
- 決定者: claude（実装）

## 起点・関連

- 関連する計画書 ID: **SC-09**（削除拒否・**改名は既存文書へ追随**・使用件数）／**SC-05**／**FR-06** / **FR-09**
- 関連 ADR: [[IADR-0152]]（タグ辞書の契約。**決定 6 が「保持方式は識別子参照」と定め、移行を #635 へ送った**）／
  [[IADR-0149]]（索引の追随を「再索引されるまで欠落を許す」で扱った先例）
- 起点 issue: **#635**（親 **#542**。前半は #634）

## コンテキストと課題

計画は保持方式を確定している（SC-09）:

> 辺は型の識別子を参照して保持し、表示名を辺へ複写しない（**複写すると改名時に既存の辺が古い名前のまま取り残される**）

> **辺の型と同じ規則をタグ辞書にも適用する**

**現状はその正反対である**——`Document.Tags` / `DocumentVersion.Tags` / `ConversionJob.Tags` / `WikiPage.Tags` と
Qdrant ペイロードの `tags` が**すべて表示名の複写**である（実測）。

**素直に読むと「タグを運ぶ 30 ファイルすべてを識別子へ変える」ことになる**が、それは正しくない。
**「複写するな」が禁じているのは、正本が古い名前を抱えて取り残されることである。**

決めること:

1. **どこまでを識別子にするか**（正本だけか、索引・外部システムまでか）。
2. **改名をどう追随させるか。**
3. **`DocumentVersion`（履歴）の過去版はどう見えるべきか。**
4. **取り込み時に辞書に無いタグが来たらどうするか。**

## 検討した選択肢

### (1) 識別子にする範囲

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **正本（`Document` / `DocumentVersion`）だけを識別子にし、派生は表示名のまま**（採用） | ○ | **下流が一切変わらない。** Qdrant ペイロード・Wiki.js・`SearchResultDto`・`/bff/attribute-values`・画面はすべて表示名を受け取り続ける。**変換点は `DocumentEndpoints.ToEvent` ただ 1 つ**である（実測。`DocumentUpdated` を組み立てる唯一の場所） |
| Qdrant ペイロードも識別子にする | × | **検索の hot path に辞書引きが増える。** facet が識別子を返すため、`/bff/attribute-values` も検索結果も**利用者へ見せる前に解決**が要る。RetrievalService は辞書を持たない（辞書は DocumentService。[[IADR-0152]] 決定 1）ので**検索のたびにサービスを跨ぐ**ことになる |
| Wiki.js も識別子にする | × | **外部システムであり、人が読む面である。** Wiki.js のタグに UUID が並ぶ |
| `ConversionJob` も識別子にする | × | **変換段はまだ文書ではない。** 取り込み元から来た自由文字列であり、辞書との突き合わせは**カタログ（正本）へ載せる時点**の仕事である |

**索引と外部システムは「正本から作り直せる射影」である。** 正本が識別子を持つ限り、
**射影が古い名前を抱えたまま取り残されることはない**——作り直せば正しくなる。
計画が禁じたのは**作り直せない複写**（＝正本側の複写）である。

### (2) 改名の追随

**改名したら、そのタグを使っている文書の `DocumentUpdated` を再発行する。**

**新しい仕掛けを足さない。** `DocumentUpdated` は既に

- **IngestionService** が購読して Qdrant を再索引し、
- **WikiService** が購読して Wiki.js へ push する

（実測）。**改名は「文書の表示名が変わった」ことに等しい**ので、既存の更新経路にそのまま乗る。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **`DocumentUpdated` の再発行**（採用） | ○ | 経路が 1 本で済む。Qdrant と Wiki.js の**両方**が同時に追随する。**取りこぼす面が構造的に生まれない** |
| 索引だけを直接書き換える | × | Wiki.js が取り残される。**面ごとに別の追随手段を持つと、面が増えたとき漏れる** |
| 追随しない（次回更新まで待つ） | × | 計画が「**改名は許して既存の文書が新しい名前へ追随する**」と確定している |

**版を増やさない。** 再発行は**射影を作り直すため**であり、文書の内容は変わっていない
（`Document.Snapshot` を呼ばない）。呼ぶと**改名のたびに全文書の版履歴が伸びる**。

### (3) `DocumentVersion`（履歴）の過去版

**過去版も新しい名前で表示される**（識別子を持つため自動的にそうなる）。

計画は改名を「**表示上の変更であり**…即時に反映される」と書いており、
**同一のタグの表示名が変わるだけ**である。「版 1 の時点ではこの名前だった」という記録は**求められていない**。

**むしろ、版履歴が古い名前を抱えるほうが計画に反する**——それこそが
「複写すると改名時に**古い名前のまま取り残される**」で禁じられた状態である。

### (4) 辞書に無いタグが取り込みで来たとき

**辞書へ自動登録し、その事実を記録する。**

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **自動登録する**（採用） | ○ | **落とすと文書のタグが黙って消える。** 拒否すると**取り込み全体が落ちる**。計画が辺の型で採った「**未定義型は `related` へフォールバックし、警告を記録して取り込む**」（拒否＝取り込みが落ちる／破棄＝辺が失われる、と理由まで書いてある）と**同じ形**である |
| 落とす | × | 取り込み元が持っていた情報が黙って失われる |
| 拒否する | × | 取り込み全体が落ちる |

**計画に明文が無い。** SC-05 の「既定タグ辞書に整合」は**画面からの手入力**についての規則であり、
取り込み経路は書かれていない。**上記は辺の型の規則からの類推であり、計画へ裁定を仰ぐ**（フォローアップ）。
**画面（SC-05）からの手入力は自動登録しない**——そちらは計画が「辞書に整合」と明示している。

## 決定

1. **正本（`Document.Tags` / `DocumentVersion.Tags`）はタグの識別子を持つ。表示名を複写しない。**
2. **派生（Qdrant ペイロード・Wiki.js・`SearchResultDto`・BFF・画面）は表示名のままとする。**
   **変換点は `DocumentEndpoints.ToEvent` と DTO 写像だけ**である。**下流のサービスは変更しない。**
3. **改名したら、そのタグを使っている文書の `DocumentUpdated` を再発行して射影を作り直す。**
   **版は増やさない**（内容は変わっていない）。
4. **`DocumentVersion`（履歴）の過去版も新しい名前で表示される。**
   改名は表示上の変更であり、同一のタグを指し続ける。
5. **取り込み経路（`DocumentNormalized`）で辞書に無いタグが来たら、辞書へ自動登録する。**
   **画面からの手入力は自動登録しない**（SC-05 が「辞書に整合」と定めている）。
   **計画に明文が無いため裁定を仰ぐ**（フォローアップ）。
6. **削除は使用件数が 0 件のときだけ許す**（[[IADR-0152]] 決定 2 の数え方に従う）。
   1 件以上なら**件数を添えて拒否する**（SC-09。件数を示さないと管理者は付け替えを判断できない）。

## 影響

- **移行が DocumentService に閉じる。** [[IADR-0152]] の時点では 30 ファイル規模と見積もっていたが、
  **決定 2 により下流が変わらない**ため、実際に触るのは正本・変換点・辞書エンドポイントとそのテストである。
- **改名は該当文書の数だけイベントを発行する。** 使用件数の多いタグの改名は重い。
  **件数は #634 で既に見えている**ので、管理者は事前に規模を把握できる。
- **改名の追随は非同期である**（イベント経由）。改名直後の一瞬、検索結果や Wiki.js に古い名前が残り得る。
  [[IADR-0149]] が #536 で採った「**再索引されるまで欠落を許す**」と同じ性質であり、同じ理由で受け入れる。
- **既存データの移行が要る**（表示名 → 識別子）。移行時に**辞書へ未登録の名前は辞書へ登録してから**紐づける。

## フォローアップ

- **計画へ裁定を仰ぐ（決定 5）**: 取り込み経路で辞書に無いタグが来たときの扱い。
  本 IADR は辺の型の規則（未定義型はフォールバックして警告を記録し取り込む）から類推したが、
  **計画に明文が無い**。`decision-needed` で流す。
- **辺の型（値集合）の辞書も同じ形で作れる。** 知識グラフ（FR-17）は [[IADR-0142]] が着手条件を別に定めており、
  本 IADR では触らない。
