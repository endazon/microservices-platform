# IADR-0152: タグ辞書は DocumentService が持ち、読み取りは権限内候補 API の 1 系統へ相乗りする

- 状態: Accepted
- 日付: 2026-08-09
- 決定者: claude（実装）

## 起点・関連

- 関連する計画書 ID: **SC-09**（タグ辞書の管理。削除拒否・改名の追随・使用件数）／
  **SC-05**（「既定タグ辞書に整合」。辞書は管理系ロールが引ける照会口から取得する）／
  **FR-06**（文書管理）／**FR-09**（管理機能）／**UC-03** / **UC-05**
- 前提となる計画 ADR: [ADR-0043](../../planning/projects/microservices-platform/07_adr/ADR-0043_scoped-attribute-value-lookup.md)（`Accepted`）
- 関連 ADR: [[IADR-0151]]（#540 で作った権限内候補 API。**決定 4 が本 IADR の拡張点である**）／
  [[IADR-0116]] 規約 4（PR ではなく issue を分割する）
- 起点 issue: **#542**（親）→ **#634**（(a) 値集合・(b) 使用件数）／**#635**（(c) 改名の追随・保持方式の移行）

**本 IADR は (a)(b)(c) の契約をまとめて定める。** 計画が「3 つとも契約で定める」「(a)(b)(c) は分割できない」と
書いた要求を、**契約の定義としては 1 箇所で満たす**ためである。実装は #634 → #635 の 2 PR へ分ける
（[[IADR-0116]] 規約 4。根拠は #634 本文の実測）。

## コンテキストと課題

計画は 2026-08-02 に規則を確定した——**参照が 1 件でもあるタグは削除を拒否し、改名は許して既存の文書が
新しい名前へ追随する。削除前に「このタグは N 件で使われている」と件数を示す。**
そして 2026-08-05 に「**そのすべてが契約側の機能**であり、画面だけでは 1 つも満たせなかった」と明記した。

**現状、タグ辞書というものが存在しない**（実測）。`AttributeDefinition.AllowedValues` は ABAC 属性の
許可値であって辞書ではない——**計画自身が同じことを書いている**。文書のタグは
`Document.Tags` / `DocumentVersion.Tags` / `ConversionJob.Tags` / `WikiPage.Tags` に
**表示名の `List<string>` として複写**されている。

決めること:

1. **辞書をどのサービスが持つか。**
2. **使用件数を何で数えるか**（版履歴は？ アーカイブ済みは？）。
3. **読み取り口の形**——[ADR-0043](../../planning/projects/microservices-platform/07_adr/ADR-0043_scoped-attribute-value-lookup.md) 決定 4 が「口を 3 種類作らない」と定めている。
4. **一般利用者の候補を辞書へ切り替えるか**（#540 は Qdrant の facet で求めている）。
5. **保持方式**（(c) の前提）。

## 検討した選択肢

### (1) 辞書の所有サービス

| 案 | 採否 | 理由 |
| --- | --- | --- |
| **DocumentService**（採用） | ○ | **使用件数が局所クエリになる**（文書を持っているのは DocumentService である）。サービスを跨ぐと、削除拒否の判定のたびに同期呼び出しが要り、**数え落としが権限の穴ではなく「消してはいけないタグを消せる」事故になる**。読み取り口も knowledge BFF なので経路が一直線になる |
| AuthorizationService（platform） | × | **タグは knowledge ドメインの概念**であり、platform（基盤）へ置くと `CLAUDE.md` の「platform → 可変ユニットは禁止」に照らして向きが逆になる。使用件数を数えるには DocumentService を呼ぶしかない。**計画も「`AllowedValues` はタグ辞書ではない」と切り分けている** |
| 新サービス | × | 計画に無く、[[IADR-0056]] のユニット構成に対して過剰である |

### (2) 使用件数の母数

**現行版の文書の件数を数える。版履歴は数えない。アーカイブ済みの文書は数える。**

| 母数の候補 | 採否 | 実測にもとづく理由 |
| --- | --- | --- |
| 現行版の `Document.Tags` | ○ | 管理者が**付け替えられる**単位である |
| `DocumentVersion.Tags`（版履歴） | × | **append-only で付け替えられない**（`Document.Snapshot` が `_versions.Add` するだけで、既存の版を書き換える経路が無い。実測）。数えると**一度でも使われたタグは永久に削除できず**、計画が定めた「使用件数 0 件のときに限り削除できる」が空文になる |
| アーカイブ済みを除く | × | **`UpdateMetadata` にアーカイブ済みの禁止が無い**（guard が掛かっているのは `Publish` だけである。実測）。つまり**アーカイブ済み文書のタグは付け替えられる**ので、数えても管理者は行動できる。除くと、削除した直後にアーカイブ済み文書が消えたタグを指したままになる |
| Qdrant の facet 件数 | × | **到達可能チャンクの件数**であって文書の件数ではない。主体ごとに変わるため管理者の判断材料にならない |

**版履歴を数えないことの代償は明示する**——タグを削除すると、**過去の版が指していた事実の表示は失われる**。
これは #635 が扱う（削除時の表示の決めは #635 の射程）。

### (3) 読み取り口の形

**[[IADR-0151]] 決定 4 が用意した拡張点に載せる。** すなわち `/bff/attribute-values` の 1 系統のまま、
**管理者スコープ専用の別フィールド**を足す。一般利用者の応答形（`values` の配列だけ）は変えない。

**件数は管理者スコープの応答にだけ載せる。**
[ADR-0043](../../planning/projects/microservices-platform/07_adr/ADR-0043_scoped-attribute-value-lookup.md) 決定 2（件数を返さない）は
**一般利用者に対する制限**である——理由が「このタグは 12 件だが自分の検索では 8 件」＝
**見えない文書が 4 件ある**ことの推測を封じることだからである。**辞書の全体を見てよい管理者には当たらない。**
[[IADR-0151]] 決定 2（件数を捨てる）も同じ射程であり、**一般利用者向けの facet 経路では引き続き捨てる**。

### (4) 一般利用者の候補を辞書へ切り替えるか

**切り替えない。facet のまま（#540）とする。**

[ADR-0043](../../planning/projects/microservices-platform/07_adr/ADR-0043_scoped-attribute-value-lookup.md) 決定 1 は
**「辞書を丸ごと返す」を明示的に禁じている**（権限外の文書に固有の値からその存在が推測できる）。
辞書ができたからといって一般利用者へ辞書を返してはならない。
**辞書は管理面、facet は利用者面**という 2 経路を**意図的に**保つ。

**口は 1 つでも、返す母集合はスコープで違う。** これは決定 4 の「スコープだけロール別」そのものである。

### (5) 保持方式

**文書はタグの識別子を参照し、表示名を複写しない**（計画が SC-09 で確定した形）。**#635 で移行する。**

**改名時の一括伝播で代替しない。** 計画は辺の型について
「複写すると改名時に既存の辺が古い名前のまま取り残される」と理由まで書いて複写を退けており、
**タグ辞書にも同じ規則を適用すると明記している**。

**#634 の時点では移行前なので、使用件数は表示名の一致で数える。**
これは**移行までの暫定**であり、#635 が識別子参照へ移した時点で識別子の一致へ置き換える。
**暫定であることをコードのコメントとテストに残す**（黙って残ると、移行後も表示名で数え続ける）。

## 決定

1. **タグ辞書は DocumentService（knowledge ユニット）が所有する。** 使用件数を局所クエリで数えられることを優先する。
2. **使用件数は現行版の文書の件数である。版履歴は数えず、アーカイブ済みの文書は数える。**
   版履歴を数えると削除が原理的に不可能になり、計画の「0 件のときに限り削除できる」が空文になる。
   アーカイブ済みを除かないのは、**アーカイブ済みでもタグを付け替えられる**（実測）ためである。
3. **読み取り口は `/bff/attribute-values` の 1 系統を保ち、管理者スコープは専用の別フィールドで足す。**
   一般利用者の応答形は #540 から変えない（[[IADR-0151]] 決定 4）。
   **件数は管理者スコープの応答にだけ載せる**——ADR-0043 決定 2 の制限は一般利用者に対するものである。
4. **一般利用者の候補は Qdrant の facet のままとし、辞書へ切り替えない**（ADR-0043 決定 1）。
   **辞書は管理面、facet は利用者面**の 2 経路を意図的に保つ。
5. **ロールは既存のポリシーへ写す。** 値集合の**読み取り**は `ConfigViewer`（管理者・運用者。SC-05 の Q18）、
   **追加・改名・削除**は `AdminOnly`（システム管理者。SC-09 のアクセス制御。`/bff/admin/authz` と同じ）。
   **新しいロールを作らない。**
6. **保持方式は識別子参照とする**（計画確定）。移行は **#635**。
   **#634 の使用件数は表示名の一致で数える暫定である**ことをコードとテストに明記する。

## 影響

- **DocumentService に辞書のテーブルが 1 つ増える**（マイグレーション 1 本）。
- **`/bff/attribute-values` の応答型に管理者スコープ専用のフィールドが増える**。
  一般利用者には `null` であり、**契約上は既定値ありのメンバー追加なので破壊的変更ではない**（[[IADR-0122]] 決定 2）。
- **管理面と利用者面で候補の集合が一致しない**——辞書に在るが誰の文書にも付いていないタグは、
  管理者には見えて一般利用者の候補には出ない。**これは意図した差**である（決定 4）。
- **#635 は本 IADR の決定 6 を実施する。** 併せて、削除（参照 1 件以上なら拒否）も #635 で入れる——
  識別子参照でない状態で削除規則だけ入れると、改名と削除で保持方式の前提が食い違う。
- **版履歴を数えないため、削除したタグを過去の版がどう表示するかという問題が残る**（#635 の射程）。

## フォローアップ

- **#635**: 保持方式の移行（識別子参照）・改名の追随・削除（参照 1 件以上なら拒否）・
  Qdrant ペイロードの扱い・Wiki.js への再 push。**`DocumentVersion`（履歴）の過去版の表示**は
  着手時に判断し、履歴の不変性と衝突するようなら計画へ裁定を仰ぐ。
- **辺の型（値集合）の辞書は本 IADR の射程外である。** 計画は「タグ辞書と同じ運用に載せる」と書いているが、
  知識グラフ（FR-17）は [[IADR-0142]] が着手条件を別に定めている。**同じ形で作れるように辞書の作りを揃えておく**
  に留め、本 IADR では決めない。
