## コンテキストと課題

計画は SC-07 の一覧に「デッドレター状態の表示」を求め、その内訳が見えないと運用者が
「再実行すれば直るもの」と「二度と直らないもの」を区別できず**直らないジョブに再実行を繰り返す**と
述べている（`05_screens:325`）。しかし契約 `ConversionJobDto` は `Attempts`（試行回数）しか持たず、
**上限が契約に無いため回数からも導けなかった**（同 `:324`）。

着手時の実測（詳細は作業仕様書 §着手時の実測）:

- 自動再試行は**実在する**。`ConversionService.Worker/Program.cs` の `cfg.UsePlatformRetry()` が
  `UseMessageRetry(r => r.Intervals(2s, 10s, 30s))` を設定し、使い切ると MassTransit が
  `<queue>_error` へ移す。**再試行 3 回＝ 1 回の配信で 4 試行**である。
- メッセージング基盤は **MassTransit 8.4.1**。ADR-0027 / ADR-0030 が定める Wolverine への移行は
  ConversionService では未実施で、`scripts/backend-library-baseline.json` に ratchet 済みで載っている。
  **既存の再試行機構に揃える**（無いものを有ることにしない）。
- `ConversionJob.Attempts` は `MarkProcessing` が受信・再試行の都度 +1 し、
  **手動再変換（`TryRequeue`）でリセットしない**。すなわち**手動再変換をまたいで累積する**。

## 検討した選択肢

### 論点 A: デッドレターを状態値にするか、独立した標識にするか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A1 | `ConversionJobStatus` に 5 つ目（`dead-lettered`）を足す | 一覧の状態列がそのまま使える。**計画が「4 値である」「`failed` の内訳として扱う」と明記**（`:308`）しており、`JOB_STATUSES` / `jobStatus.test.ts` が固定した 4 値も壊す。**裁定の範囲を超える** |
| A2 | **独立した真偽値 `DeadLettered`** | 4 値モデルを壊さない。状態と標識の 2 軸になり、表示側は組み合わせを解釈する必要がある |

### 論点 B: 標識を導出するか記録するか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| B1 | `Status == failed && Attempts >= MaxAttempts` で**導出**する（列を増やさない・マイグレーション不要） | 計画の文（「上限が契約に無いため回数からも導けなかった」）は導出を示唆して読める。**しかし成立しない**——`Attempts` は手動再変換をまたいで累積するため、2 回目以降の配信の途中で失敗した瞬間に「まだ `<queue>_error` へ送られていないのに標識が立つ」。契約が嘘をつく |
| B2 | **記録する**（列 `DeadLettered` を足し、コンシューマが立てる） | 「送られたか」という**事実**を持つ。コンシューマは自分が最後の試行かを `ConsumeContext.GetRetryAttempt()` で知れる。列 1 本とマイグレーション 1 本のコスト |
| B3 | `<queue>_error` を実際に読んで突合する | 最も正確。**運用ツール向けのキューを画面の情報源にする設計**であり [[IADR-0042]] が既に棄却している。射程も大きく超える |

### 論点 C: 試行上限の値をどこから採るか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| C1 | 契約に定数を置くだけ（`4` と書く） | 単純。**再試行の間隔を増減しても契約は 4 のまま**で、静かにずれる |
| C2 | **再試行設定（`UsePlatformRetry` の間隔配列）を単一情報源にし、契約側の `const` と一致することをテストで束ねる** | 間隔を足せばテストが落ちる。**定数が 2 か所に見える**（契約と基盤）ため、束ねているテストの存在を知らないと重複に見える |
| C3 | 契約プロジェクトから基盤プロジェクトの値を直接参照する | 定数は 1 か所。**契約（`Knowledge.Contracts`）が MassTransit 依存の基盤（`Platform.Shared.Infrastructure`）へ依存する**——契約は依存を持たないから契約でいられる。C# の既定引数は `const` を要求するため、そもそも参照先を `const` にすると今度は基盤側で間隔配列から導けない |

## 決定

**決定 1（論点 A）: A2 を採る。デッドレターは独立した真偽値 `DeadLettered` とし、状態値は 4 値のまま据え置く。**
計画が `:308` で「ジョブ状態モデルは 4 値である…デッドレターの表示は `failed` の内訳として扱う」と
明記しているためである。**これは実装の裁量ではなく計画の確定事項の写しである。**

**決定 2（論点 B）: B2 を採る。標識は導出せず記録する。**
B1 が成立しないのは `Attempts` の意味による——手動再変換をまたいで累積するため、
`Attempts >= MaxAttempts` は「上限に達した」ではなく「これまでに合計で上限回以上試した」を意味する。
**`Attempts` の意味を変える（配信ごとにリセットする）案は採らない**——既存契約の意味変更であり、
裁定（Q13）の範囲外である。

**判定はコンシューマで行う**: `context.GetRetryAttempt() + 1 >= MassTransitExtensions.MaxAttempts`。
`GetRetryAttempt()` は初回 0・再試行ごとに +1 を返す。
**前提は「本サービスの受信エンドポイントが `UsePlatformRetry()` で構成されていること」**であり、
`Program.cs` がそう構成している。**この前提は本 ADR の限界でもある**（§結果）。

**標識は `failed` のときだけ真とする。** `MarkProcessing`（再受信）と `TryRequeue`（手動再変換の受付）で
`false` へ戻す。戻さないと「`processing` / `queued` なのにデッドレター」という自己矛盾した行が一覧に出る。

**決定 3（論点 C）: C2 を採る。試行上限の単一情報源は再試行設定である。**
`MassTransitExtensions` の間隔配列を `private` にし、`MaxAttempts => RetryIntervals.Length + 1` を公開する。
**間隔を増減すれば上限も動く。**

**決定 4: 契約側は `ConversionJobRetryPolicy.MaxAttempts`（`const`）を持ち、決定 3 との一致をテストで束ねる。**
C# の record の既定引数には `const` が要り（決定 5）、契約プロジェクトから基盤プロジェクトを参照しない
（C3 の棄却理由）ため、**値の写しが 1 つだけ生じる**。それを
`MaxAttempts_contract_constant_matches_platform_retry_policy` が固定する。
**「2 か所に書かない」ではなく「2 か所がずれたら落ちる」で担保する。**

**決定 5: DTO への追加は末尾へ既定値つきで行う。**
`bool DeadLettered = false` / `int MaxAttempts = ConversionJobRetryPolicy.MaxAttempts`。
[[IADR-0122]] 決定 2 は**既定値の無いメンバー追加・位置の入れ替えを破壊的**に分類する。
OpenAPI では両方を `required` に入れる（[[IADR-0132]] 決定 1・決定 2。**既定値は引数の既定であって
シリアライズの省略ではない**ため、JSON には必ず出る）。**新しい値集合は作らない**ので
[[IADR-0131]] 決定 5（`enum` にしない）は該当しない。

**決定 6: 既存行は `false` として読む。** マイグレーションの列既定を `false` にする。
過去の失敗が本当に上限到達だったかは記録が無く**遡って復元できない**ため、
**偽陽性（直るものを「直らない」と示す）を出さない側へ倒す。**

## 理由

- **決定 2** の核心は「計画の文が導出を示唆して読めても、実装の事実がそれを許さない」ことである。
  `Attempts` の累積という**実測**が B1 を否定した。契約は画面が信じる情報であり、
  **一時的にでも嘘をつく契約は、嘘をつかない契約より悪い**（運用者は標識を見て再実行を止める）。
- **決定 3・4** は「数字が 2 か所にある」ことを認めたうえで、**ずれを検出できる形**にした判断である。
  依存の向き（契約 → 基盤）を汚さないことと、値の一致を保つことは両立できる——テストで束ねればよい。
- **決定 6** は縮退の向きの選択である。既存行を `true` に倒すと、単に古いだけの失敗ジョブが
  「もう直らない」と表示され、運用者は**直るものの再実行をやめる**。逆向きの誤りは
  「効かない再実行を 1 回試す」で済む。

## 結果

- 良い影響:
  - SC-07 の「デッドレター状態の表示」が**契約の上で実装可能になった**（[[IADR-0127]] 決定 2 の
    「導出できる値だけで表示する」に照らして、**いまや導出できる**）。
  - 試行上限が契約に載ったことで、**画面がしきい値を推測しなくてよい**（SC-06 の
    「継続失敗のしきい値＝再試行上限」と同じ考え方が SC-07 でも成立する）。
  - 契約変更は**非破壊**である（`check-contract-schema.js`: 破壊的 0 件 / 非破壊 3 件）。
- 悪い影響・トレードオフ:
  - **判定は「バスが `UsePlatformRetry` で構成されている」ことに依存する。** 別の再試行方針で
    バスを組むと標識と実挙動がずれる。判定側も設定側も `MassTransitExtensions` を通るため
    変える箇所は 1 つだが、**構成の自由度を暗黙に縛っている**ことは自覚しておく。
  - **標識はコンシューマの記録に依存する。** 記録の書き込み自体が落ちれば標識も落ちる
    （`<queue>_error` の実体との突合ではない。[[IADR-0043]] のフォローアップとして残る）。
  - **`Attempts` と `MaxAttempts` を「n / N」の形で並べて表示できない。** `Attempts` は累積であり、
    手動再変換を重ねた行では上限を超える。SC-06 の hi-fi「3/5」に相当する表示を SC-07 で採るなら、
    `Attempts` の意味を変える裁定が別途要る（作業仕様書 §未決事項 2）。
  - 定数の写しが 1 つ増えた（決定 4）。テストを消すと静かにずれる。
- フォローアップ:
  1. **SC-07 画面への表示**（`status == failed` かつ `deadLettered` を区別する）。別 issue の起票が要る。
  2. `<queue>_error` との突合（[[IADR-0043]] フォローアップと同じ項）。
  3. Wolverine 移行時（ADR-0027 / ADR-0030）に、`GetRetryAttempt()` 相当と
     `MaxAttempts` の出所を移行先の再試行機構へ読み替える。**移行の作業項目としてここに残す。**
