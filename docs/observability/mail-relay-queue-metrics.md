# 可観測性仕様書: 近接 MTA（メール中継）のキュー

## 起点

計画は**存在秘匿の統制**として、パスワードリセットの送出経路に**キューを持つ近接 MTA** を挟み、
あわせて**上流停止の観測点を近接 MTA のキューへ移す**ことを確定させた。

🔴 **移さなければ、統制を足したことで観測が失われる。** 近接 MTA が投函を受理した時点で
認証基盤から見た送出は成功であり、**その後の上流失敗は認証基盤に一切戻らない**。
認証基盤の監査ログだけを見ていると、**上流が止まっていることに誰も気付かない。**

**本書が答えるのは「キューの何が、どこで、どう見えるのか」である。**

## 🔴 いま測れているのは 3 つのうち 2 つである

計画が名指した観測対象は**キュー長・滞留時間・後送の失敗率**の 3 つである。

| 対象 | どこで見るか | 状態 |
| --- | --- | --- |
| キュー長 | **Grafana**（Platform Overview） | ✅ **測れている**。`postfix_queue_size` |
| 滞留時間 | **Grafana**（同上） | ✅ **測れている**。`postfix_queue_oldest_message_age_seconds` |
| 後送の失敗率 | — | ⚠️ **代理値しか無い。** 下記「後送の失敗率が直接は測れない理由」 |

> **運用ダッシュボードの画面には出していない。** 画面は専用ツールへの入口であり、
> 時系列は Grafana 側で見る（ナレッジ健全性の 2 指標と同じ扱いである）。

## 経路（🔴 Prometheus は直に取りに行かない）

```
mail-relay Pod
  ├ postfix        （近接 MTA 本体。spool へ書く）
  └ queue-exporter （サイドカー。spool を読み :9154/metrics へ出す）
         ↓  scrape（30 秒）
  otel-collector の prometheus receiver
         ↓  remote write
  Prometheus  →  アラート ／ Grafana
```

🔴 **Prometheus の scrape 対象を増やしていない。** 可観測性パイプラインの不変条件は
「**scrape 対象は可観測性コレクタ 1 つだけ**」であり（そこが落ちたことを `up` で判定している）、
直 scrape を足すとこの判定の意味が崩れる。**取り手をコレクタ側に置けば、既存の経路にそのまま乗る。**

🔴 **コレクタ設定は 3 つあり、うち 2 つ（k8s の既定と転送）に受け口を置いた。**
**compose 側には置いていない** —— compose スタックに近接 MTA が居らず、**宛先の無い scrape は
恒常的に失敗し続ける**からである。乖離は意図であり、compose 側の設定ファイルにも明記した。

## 計器

| 計器 | 種別 | 単位 | 属性 | 読み方 |
| --- | --- | --- | --- | --- |
| `postfix_up` | gauge | — | なし | **1 = 全キューを読めた。** 0 は「キューが空」ではなく**読めていない** |
| `postfix_queue_size` | gauge | メッセージ数 | `queue` | `deferred` が 0 でない間、**メールは届いていない** |
| `postfix_queue_oldest_message_age_seconds` | gauge | 秒 | `queue` | 最も古いメッセージの**到着からの**経過秒。空なら 0 |

`queue` の値は `incoming` / `active` / `deferred` / `hold` / `maildrop` である。
**`defer` と `bounce` は数えない** —— あれはメッセージではなく**理由のログ**である。

Prometheus 上では `job="mail-relay"` が付く（コレクタの受け口の名前に由来する）。

### 🔴 滞留時間をファイルの更新時刻から採っていない

Postfix のキュー管理は、メッセージを `deferred` へ落とすとき**キューファイルの更新時刻を
「次回の配送予定時刻」へ書き換える**。つまり **`deferred` の更新時刻は未来**であり、
そこから齢を採ると**負の値**になる。

代わりに**キューファイル名（キュー ID）に埋め込まれた到着時刻を復号している**。
長形式のキュー ID は `<秒><マイクロ秒>z<inode>` の形で、時刻部は 52 進の安全アルファベットである
（この形式は設定の既定であり、近接 MTA のイメージはこの設定を変更しない）。

🔴 **復号できない ID が 1 件でも混ざったら、そのキューの系列を出さない**（`postfix_up` も 0 になる）。
最古でないものを最古として出すより、**測らないほうがよい。**

### 🔴 「測っていない」を 0 で出さない

読めなかったキューの系列は**出さない**。0 を出すと画面上「滞留なし」に見え、
**沈黙が正常と読める** —— 本リポジトリが 2 度踏んだ形である
（存在しない計器名を見ていたアラートと、生産者の居ない健全性指標）。

したがって **`postfix_queue_size{queue="deferred"} == 0`（滞留なし）と、
系列そのものの不在（測っていない）は別物**である。後者は専用のアラートが拾う。

## アラート（3 つ。**しきい値は暫定である**）

| 名前 | 条件 | for | 深刻度 | 何を拾うか |
| --- | --- | --- | --- | --- |
| 後送の滞留 | `deferred` のキュー長 > 0 | 5 分 | warning | **上流の停止・認証失敗・宛先拒否。** 利用者にも監査ログにも現れない |
| キュー寿命への接近 | `deferred` の最古の齢 > 1200 秒 | 5 分 | critical | **破棄される直前**（寿命は 30 分）。破棄は事後に数えられない |
| 評価対象の不在 | `deferred` のキュー長の系列が無い | 5 分 | warning | **観測点そのものが消えた**（上の 2 つが空ベクタになり発火しない） |

🔴 **しきい値と `for` は実測が 1 つも無い暫定値である。**
計画は所要時間の閾値を「**実測してから定める**」とし、キューの容量設計も未了としている。
**確定は稼働クラスタでの実測を待つ**（下記「配備と実測は利用者の手が要る」）。
現在の値は**キュー寿命 30 分**（リセットリンクの有効期限に合わせた値）と
**再送の最小間隔 60 秒**から導いた初期値であり、「よく効く」ことを測ったものではない。

**3 系統に同内容で置く**（compose の Prometheus ルール／k8s の inline ／ Grafana の暫定アラート）。
一致は機械検査が守る。

### 後送の失敗率が直接は測れない理由

**キュー寿命（30 分）を超えたメッセージは、キューから消える。** バウンスも溜めない設定である。
したがって **spool を読むだけでは「何通が捨てられたか」を事後に数えられない**
（届いたものも捨てられたものも、同じく「消えている」）。

- 正しく数えるには **Postfix のログを読む**必要があるが、近接 MTA のイメージはログを
  ログ収集デーモン経由で標準出力へ出しており、**サイドカーから読めるログファイルが存在しない。**
- そこで本書は**捨てられる前に鳴らす**方式を採る（上の「キュー寿命への接近」）。
  **失敗率という数字は持たない。** 持っているのは「失敗し続けている状態」と「その齢」である。

**この差は繰り延べであり、解消していない。** 解消するならログ収集経路（ログ基盤側での抽出）が要る。

## 併存する観測（消していないもの）

**認証基盤 → 近接 MTA の投函失敗は、引き続き監査ログへ残る**（計画が明示している）。
近接 MTA 自身の障害の一次情報はそちらであり、**本書のキューの観測はその上流側だけを見る。**

- **門（リセット申請を機械で閉じる常駐プロセス）の不在は、まだ観測に載っていない。**
  門が落ちている間は存在秘匿の窓が開いたままになるが、**その不在を鳴らす計器は無い**（残件）。

## 相関・保持

- 保持は可観測性基盤の既定に従う（開発環境の時系列は 7 日）。
- **秘匿値は 1 つも出さない。** 宛先・差出人・件名は計器に載せない —— 属性はキュー名だけである。
  **メールアドレスは基数が無界であり、かつ個人情報である。**

## 配備と実測は利用者の手が要る

🔴 **本書の内容は稼働クラスタで 1 つも実測していない**（作業機にクラスタが無い）。次は利用者の手が要る。

1. 近接 MTA の Pod にサイドカーが立ち、`:9154/metrics` が上の 3 計器を返すこと。
2. 空の spool を被せてもメール中継が起動すること（イメージが起動時にキュー用のフォルダを作り直す
   ことは上流ソースで確認したが、**稼働では確かめていない**）。
3. 可観測性コレクタが 30 秒ごとに取り、Prometheus に `job="mail-relay"` の系列が立つこと。
4. 上流を止めたときに `deferred` が増え、復旧で 0 へ戻ること（**アラートのしきい値はここで決める**）。
5. アラートが 3 系統とも登録されること（Prometheus の規則一覧と Grafana の provisioning）。

## 未決事項

- **後送の失敗率（捨てられた通数）は測れていない。** 上記のとおりログ経路が要る。
- **しきい値と `for` は暫定。** 実測して計画へ返す。
- **門の不在を観測へ載せていない。** 門が落ちている間は存在秘匿の窓が開く。
- **キューの容量設計（寿命・永続化）は未了。** キューはコンテナと同じ寿命で、Pod の再作成で失われる。
