# ログ・可観測性仕様書: ハイブリッド検索の全文側の縮退

## 何を観測するのか

ハイブリッド検索は**ベクトル検索と全文検索**を並行実行して融合する。
**全文側だけが死んでも、応答は `200` で結果も返る。** 利用者にも試験にも正常に見える。

🔴 **もっとも危険な故障は例外を伴わない。** ベクトルDB のペイロードに全文インデックスが無いとき、
版によっては全文 `Match` が**部分文字列の全走査へ黙って落ちる**（語でない断片に当たり、
語順に依存し、全点を走査する）。**例外が出ないので、ログにも応答にも現れない。**

したがって観測は 2 段構えにする。

| 観測点 | 何を見るか | 例外の有無 |
| --- | --- | --- |
| **readiness** | **索引が在るかどうかそのもの** | 例外を伴わない故障を捕まえる唯一の手段 |
| **メトリクス** | 縮退した回数（理由つき） | 例外を伴う故障と、readiness が検出した欠落の両方を数える |

**応答（`SearchResponse`）へは何も足さない。** 「なぜ空か」を利用者に区別させないことが
検索端点の設計意図（存在秘匿）であり、そこは変えない。**観測は応答の外側に置く。**

## ログ

| ログ種別 | レベル | 出力項目（構造化フィールド） | 出力先 |
| --- | --- | --- | --- |
| 全文検索の要求が拒まれた（検索サービス） | `Warning` | 例外・`Collection`（検索が見ているコレクション名） | 標準出力 → ログ基盤 |
| 起動時に索引を張れなかった（取り込みサービス） | `Error` | 例外 | 同上 |

- 🔴 取り込み側を `Error` にしているのは、**索引の失敗が自分では現れない**からである。
  コレクションが無ければ次の書き込みが例外になるが、**索引が無くても検索は 200 を返し続ける**。
  ここが唯一の起動時の記録になる。
- 🔴 **クエリ文字列をログの検索キーにしない。** 利用者の入力であり、ログ基盤の索引を汚す。

## メトリクス

| メトリクス | 種別 | 単位 | 用途 |
| --- | --- | --- | --- |
| `search.keyword_degraded.total` | Counter | `{query}` | **0 が正常。** 全文側が使えず縮退した回数 |

| 属性 | 値域 | 意味 |
| --- | --- | --- |
| `search.keyword_degraded_reason` | `missing_index` | 索引そのものが無い（readiness が検出した。**この理由は例外を伴わない**） |
| | `backend_error` | ベクトルDB が全文検索の要求を拒んだ（接続断・旧版の索引未作成エラー等） |

- Prometheus 上の名前は OTLP の変換後（`.` → `_`）である。**コード側の計器名とは表記が違う。**
- 🔴 **クエリ文字列を属性にしない。** 利用者の入力は基数が無界で、時系列 DB の系列数が爆発する。
  **理由はタグへ、詳細はログへ**分ける（既存の可観測性仕様と同じ作法）。
- **0 でない値そのものが検出である。** しきい値は置かない。

## readiness（health check）

| チェック名 | 判定 | 状態 |
| --- | --- | --- |
| `qdrant-fulltext-index` | 検索が見ているコレクションの `payload_schema` に `text`（text 型）が在る | `Healthy` |
| | 在らない | **`Degraded`** |
| | 応答を読めない（ベクトルDB が答えない） | **`Degraded`**（到達性そのものは別のチェックが `Unhealthy` で受け持つ） |

🔴 **`Unhealthy` にしない。** ベクトル側は生きており検索は結果を返し続ける。
ここで pod を Ready から外すと、**キーワード側の欠落を理由に検索全体を落とす**ことになり、
計画の非機能要件（障害時の縮退運転: 検索は継続し、AI 回答のみ一時停止を許容）に反する。

`Degraded` は `/health/ready` を **200** のまま応答本文へ現す。
k8s の readinessProbe は落ちず、**運用（本文・ログ基盤・Grafana）からは見える** ——
「壊れているのに完全に正常に見える」状態だけを解消する。

## 運用手順（Degraded を見たとき）

1. 取り込みサービスの起動ログに索引生成の失敗（`Error`）が無いか見る。
2. ベクトルDB のコレクション定義を直接見る（`payload_schema.text` の有無と `tokenizer`）。
3. 取り込みサービスを再起動する。**索引は起動時に無条件・冪等に張り直される**ので、
   手作業での索引作成や移行スクリプトは要らない。
4. 直ったことは、全文だけで既知文書がヒットすることで確かめる（統合スタックの検証スクリプトと
   実機の全文インデックス検証スクリプトが、陽性対照と陰性対照を対で測る）。
