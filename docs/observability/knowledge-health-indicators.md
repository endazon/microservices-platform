# 可観測性仕様書: ナレッジ健全性の指標

## 起点

計画は知識グラフとタグ辞書の運用指標として **8 指標**を定め、あわせて集計・表示の 4 規則
（全体集計・ロール限定・個人資料除外・件数のみ）を確定させている。
**8 つ目は 2026-09-06 に加わった**（ユニットの主体が保存した文書のうち `project` を持たない件数）。

**本書が答えるのは「どの指標が、いまどこで見られるのか」である。** 定義そのものは計画が持つ。

## 🔴 いま測れているのは 8 指標すべてである（2026-09-11）

> ★［2026-09-11 更新］**本節は「5 件」で止まっていた。** その後 2 件（解決できないリンク数・
> 辺の型ごとの使用件数）が 2026-09-05 に、1 件（未要約クラスタ数）が 2026-09-11 に配線された。
> **測れているかどうかと、画面に節を開くかどうかは別の判断である**（後述の注記）。

| 指標 | どこで見るか | 状態 |
| --- | --- | --- |
| 孤立文書数 | 集計 API（運用者・管理者のみ） | ✅ **測れている**。知識グラフ側の定期処理が 1 時間周期で観測値を報告する |
| 未定義型のフォールバック警告件数 | **Grafana**（Platform Overview） | ✅ **測れている**。カウンタ `graph_edge_type_fallback_total` |
| 取り込み経路で辞書に無いタグが現れた件数 | **Grafana**（同上） | ✅ **測れている**。カウンタ `ingest_unknown_tag_total`。**0 が正常である** |
| ユニットの主体が保存した文書のうち `project` を持たない件数 | **Grafana**（同上） | ✅ **測れている**（2026-09-09〜）。カウンタ `documents_unit_project_missing_total`。**0 が正常である** |
| 陳腐化文書数 | 集計 API（運用者・管理者のみ） | ✅ **測れている**（2026-09-03〜）。**本文が変わったときだけ前進する時刻**で数え、既定 **180 日**。件数と現在のしきい値を対で返す |
| 解決できないリンク数 | 集計 API（運用者・管理者のみ） | ✅ **測れている**（2026-09-05〜）。リンク先の**名前**を保存し、集計のたびに解決し直す。内訳の軸は不在と曖昧 |
| 未要約クラスタ数 | 集計 API（運用者・管理者のみ） | ✅ **測れている**（2026-09-11〜）。分母は**日次バッチが検出したクラスタ（コミュニティ）**。内訳の軸は未要約の理由 3 語。**しきい値は持たない** |
| 辺の型ごとの使用件数 | 集計 API（運用者・管理者のみ） | ✅ **測れている**（2026-09-05〜）。観測値 1 件＝辺 1 本で、内訳の軸に型名を載せる |

> **それでも画面（運用ダッシュボード）には出していない。** 集計 API から見ると、
> **Grafana 側で測っている 3 指標は 0 件として並ぶ** —— その 0 は「健全である」ではなく
> 「この経路では測っていない」である。**節を開くかどうかは、測れているかどうかとは別の判断である。**
> 詳細は画面仕様書の §実装しない要素の理由。
>
> ⚠️ **未要約クラスタ数は、要約の生成を有効にするまで、すべてのクラスタを返す。**
> ★［2026-09-11 更新］**要約の生成バッチが入った。ただし既定はオフである**（配備時の構成で有効化する）。
> 有効にするまでは「要約が 1 つも無い」条件に全クラスタが当たる。**実測された件数ではあるが、
> 「要約が追いついていない量」としては読めない。** 有効化した後は差分が意味を持つ。
>
> 🔴 **0 が正常の 2 指標は、他の 6 指標と読み方が違う。** 他は「発生してよい事象の量」を測る
> （多いほど手当てが要る）が、この 2 つは**発生してはならない事象**の件数であり、
> **0 でない値は「量が多い」ではなく規定違反の検出**である。**同じ表に並べているのは
> 「辞書とナレッジがどう使われているか」を 1 か所で突合するためであり、読み方まで同じではない。**

## 2 つの経路が併存する理由

| 経路 | 対象 | 理由 |
| --- | --- | --- |
| **観測値 → 集計 API** | 孤立文書数・陳腐化文書数・解決できないリンク数・辺の型ごとの使用件数・未要約クラスタ数 | **個人資料の除外を受け手が強制する**ため。件数だけを渡すと、除外したかどうかを受け手が確かめられない（未要約クラスタ数だけは**構造的に個人資料を含まない** —— 検出の入力から除いてある） |
| **OTel カウンタ → Grafana** | フォールバック警告・未知タグ・ユニット主体の `project` 欠落 | いずれも**事象が起きた回数**であり、除外すべき主体（文書）を持たない。時系列で見る方が原因に近い |

**混ぜない。** 前者は「いま何件そうなっているか」（状態のスナップショット）、
後者は「これまで何回起きたか」（事象の積算）であり、**同じ数え方に載らない**。

## 計器（Grafana で見る 3 指標）

| 計器 | 属性 | 単位 | 読み方 |
| --- | --- | --- | --- |
| `graph_edge_type_fallback_total` | `graph_fallback_layer`（`explicit` / `contextual`） | `{link}` | **0 が正常。** 0 でない間は辺の型の定義が不足している |
| `ingest_unknown_tag_total` | `ingest_source` | `{tag}` | **0 が正常。** 取り込み経路はタグを生成しないと確定しており、0 でない値は**規定違反の検出**である |
| `documents_unit_project_missing_total` | `documents_client_id`（書き手のクライアント） / `documents_operation`（`create` / `update` / `update_metadata`） | `{document}` | **0 が正常。** ユニットの保存経路は `project` を無条件で付与するため、0 でない値は**その経路を通らない書き込みの検出**である |

- Prometheus 上の名前は OTLP の変換後（`.` → `_`）である。**コード側の計器名とは表記が違う。**
- 🔴 **型名・タグ名を属性にしない。** どちらも書き手が自由に書ける文字列で基数が無界であり、
  系列数が爆発する。**名前はログへ、件数はカウンタへ**分ける。
- 🔴 **文書 ID・題名・利用者識別子も属性にしない**（同じ規律）。3 つ目の計器が載せるのは
  **登録済みの機密クライアント**の識別子だけで、基数は realm の登録数に閉じている。
  取り出せなかったときは `unknown` へ倒す（倒した先も基数 1 である）。

### ダッシュボード

`Platform Overview`（`microservices-platform-overview`）の下段（パネル 5・6・8 の 3 枚）。
**配備の 2 経路（compose / k8s）に同内容で置く** —— 片方だけに置くと、もう一方の経路で
「見に行ける前提の場所へ行けない」状態になる。一致は機械検査が守る。

**［2026-09-09 追記］3 枚目（ユニット主体の `project` 欠落）にはアラートも対で置いた** ——

## ユニットの主体が `project` を持たない文書を保存した件数（2026-09-09 追加）

| 論点 | 決まり |
| --- | --- |
| 母集合 | 🔴 **書き手の側で採る** —— 「ユニットの主体（サービスアカウント）が保存した文書」であり、**「`project` を持たない文書の総数」ではない** |
| 数える契機 | **保存が成立した後**（登録・編集・メタデータ更新の 3 経路）。400 / 404 / 409 / 413 で戻った要求は数えない |
| 主体の識別 | **トークンが名乗る形だけで決める** —— 利用者名が `service-account-` で始まる、または利用者名を持たずクライアント識別のクレームを持つ。🔴 **サービスアカウントの一覧を構成に持たない**（一覧から外すだけで計上を免れられ、抜け道になる） |
| `project` の判定 | キーが無い、または値が空白だけなら「持たない」と読む |
| 止まるか | 🔴 **止まらない。これは統制ではなく計器である。** 計上されても保存は成功する |

🔴 **母集合を「属性を持たない文書」から「ユニットの主体が保存した文書」へ移したことが、この指標の要点である。**
文書側の属性を数えると、**母数がほぼ全件で張り付き、付与漏れの変化を映さない**
（取り込み済みの実データは機密区分以外の属性をほとんど持たない）。**測れるのは書き手の側だけである。**

🔴 **人間の保存は数えない。** 計画は基盤において `project` を**任意**と定めており、
対話ログインの利用者が `project` なしで保存することは**正常**である。ここを数えると指標が
常時非ゼロになり、警報の意味が消える。**判定は迷ったら「無人主体ではない」へ倒す。**

- **クライアント識別のクレームは人間のトークンにも付く**（SPA のクライアント識別子）。
  したがって「そのクレームを持つか」だけで書いた判定は**全利用者を無人主体にする**。
  実装はこれを陽性対照の試験で固定している。
- 🔴 **「0 である」を「穴が塞がっている」と読まない。** 残る穴（ユニットの保存経路を通らない
  書き込み）は塞がっていない。塞ぐには基盤側で `project` を必須にするしかなく、計画は
  既存データと予約値の代償を理由にそれを**しない**と決めた。**本計器は検知だけを足す。**

## 陳腐化文書数の数え方（2026-09-03 追加）

| 論点 | 決まり |
| --- | --- |
| 起点となる時刻 | 🔴 **本文の更新のみ。タグ・属性の更新は起点にしない** |
| しきい値 | **180 日**（初期値。運用開始後の実測で改める） |
| 変更の手段 | **配備時の構成**（環境変数 `KnowledgeHealth__StaleDocumentThresholdDays`。Helm は `services.graph.extraEnv`）。**タグ辞書の実行時管理には載せない** |
| 境界 | **しきい値ちょうどは陳腐でない**（180 日ちょうどは含めない） |
| 表示 | **件数と現在のしきい値を併記する**（集計 API が対で返す） |

🔴 **起点を本文に限る理由は、指標の意味ではなく副作用の側にある。** メタデータを含めると、
**棚卸し作業そのもの（タグ整理）が指標を改善させる** —— 中身が古いままの文書にタグを付け直す
だけで件数が減る。**指標が自分の改善作業で消えるなら、それは測定ではない。**

- 判定に使う時刻は、**本文の指紋が変わったときにだけ前進する**。従来の更新時刻は
  メタデータのみの更新でも前進するため使えない（**「材料は揃う」は成立していなかった**）。
- **しきい値は観測値ではなく報告 1 通の属性として運ぶ。** 観測値の行に持たせると、
  **件数 0 のときは行が 1 つも無く、しきい値も一緒に消える**（0 件こそ表示したい状態である）。
- **不正な構成では既定へ倒し、警告を残す。起動は落とさない**（指標の都合で購読ホストを止めない）。
  🔴 **報告に添えるしきい値も倒した後の値にする** —— 倒したのに構成値を出すと画面が嘘をつく。
- 本欄の新設より前から在る文書には、移行時に**従来の更新時刻を写した**（backfill）。実際の本文更新
  時刻以降の値なので**偽陽性は出ず**、真に陳腐な文書も遅くとも移行から 1 しきい値以内に数えられる。
  「不明として数えない」を採ると、既存文書が本文を編集されるまで恒久的に母集合から外れ、
  **指標がほぼ 0 を返し続ける**（「問題なし」と読める）。

## クラスタ要約の生成（2026-09-11 追加）

**未要約クラスタ数の「分子」を動かすのはこのバッチである。** 検出されたクラスタのうち、
要約が揃っていないもの（要約が 1 つも無い／構成が変わった後に作り直していない／
所属文書が更新された後に作り直していない）を選び、機密区分 4 通りぶんの要約を作る。

| 論点 | 決まり |
| --- | --- |
| 実行 | **日次バッチ**。専用の排他リースを持ち、取れたレプリカだけが走る（検出・健全性とは別の鍵） |
| 既定 | 🔴 **オフである。** 有効化するまで生成の呼び出しは 1 回も起きない |
| 有効化 | **配備時の構成**（環境変数 `ClusterSummary__Enabled=true`。Helm は `services.graph.extraEnv`） |
| 1 周期の上限 | **20 クラスタ**（環境変数 `ClusterSummary__MaxClustersPerRun`）。1 クラスタ = 生成 4 通りであり、初回は全クラスタが対象になるため枠を一度に使い切らせない |
| 選ぶ順序 | クラスタ識別子の昇順（決定的。上限に掛かったクラスタが順番待ちのまま取り残されない） |
| 費用の識別 | 用途名 `graph-cluster-summary` を添えて呼ぶ（リンク・タグの提案生成とは別の用途名である） |
| 失敗したとき | 🔴 **4 通りのうち 1 つでも採れなければ、そのクラスタは 1 行も書かない。** 未要約のまま次周期へ持ち越す |
| 入力 | クラスタの構成員のうち**その機密区分以下のもの**だけ。**個人資料は入らない**（型で強制する） |
| 要約の本文 | 生成時刻の表とは**別の表**に持ち、検索の索引へは登録しない |

🔴 **既定をオフにしているのは費用のためである。** 生成は外部モデルの呼び出しであり、
**有効化の判断（いつ・どの環境で回すか）は配備側が持つ**。指標の側は有効・無効のどちらでも
同じ定義で数える —— 数字の読み方が構成で変わることはない。

## 観測値の報告（孤立文書数・陳腐化文書数）

- **契機**: 知識グラフ側サービスの定期処理（1 時間周期。初回は起動から 1 周期後）
- **経路**: 内部 API への HTTP。**メッセージングは使えない** —— 受け口の契約が
  **指標 1 つ分の全量スナップショット置換**であり、順序保証の無い経路では
  古い方の集合が最終状態として残り得る
- 🔴 **排他リースを取ったレプリカだけが報告する。** 全量置換のため、2 レプリカが同時に走ると
  片方の削除がもう片方の挿入済み行を消し、**恒久的に過少な件数**が残る（自然回復しない）。
  steady state は 1 レプリカだが、**ローリング更新では新旧 2 pod が同時に生きる**
- 🔴 **0 件でも報告する。** 送らないと前回の件数が残り続ける（解消したのに数字が減らない）
- **送出は fail-open である。** 受け口へ届かなくても定期処理も購読ホストも止めない。
  **したがって「届いていない」ことはエラーログにしか現れない** —— 計器は置いていない
  （1 指標・1 時間周期では、ログで足りる規模と判断した）

### 個人資料の扱い

**生産者は個人資料を落とさない。** 各観測値に文書スコープを添えて送り、**除外は受け手が強制する**。
🔴 判定は**集合帰属**で書く（「個人資料である」）。**否定（「組織文書でない」）で書いてはならない** ——
スコープ属性は既存文書へ遡及付与しない方針であり、否定で書くと属性を持たない大多数が
個人資料と見なされ、**指標が一斉に 0 になる**。

## 未決事項

- 解決できないリンク数の数え方と保持先（計画へ裁定を依頼中）。
- **個人資料からの辺が、組織文書の孤立判定を変える。** 現在は計画の字義どおり
  「辺があるかどうか」だけで判定しており、辺の相手のスコープを問わない。
  この結果、**件数の変動から個人資料の存在が推測され得る**（計画が個人資料を除外した理由の 1 つと衝突する）。
  指標の意味に関わるため実装では決めず、計画へ裁定を依頼する。
