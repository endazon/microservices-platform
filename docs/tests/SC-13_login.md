# テスト仕様書: ログイン画面

## 起点となる計画書（トレーサビリティ）

- 画面: ログイン
- ユースケース: ABAC 権限を管理する（認証はその前提となる）
- 受け入れ基準の所在: 認証 UX とアカウント管理の計画 ADR §認証画面の実現方式／計画側の画面設計 §ログイン

## テスト対象・範囲

**対象**: 認証画面を自前で作らず ID プロバイダのテーマ機能で提供する、という確定方針が
**実際に成立していること**。観点は次の 3 つである（1・2 は静的検査、3 は稼働クラスタでの実測）。

1. realm が宣言するテーマ名（`loginTheme` / `accountTheme`）に対応する**実体がリポジトリに存在し、解決できる**こと
2. 言語切替（ja / en）が realm 設定だけで成立していること
3. 🔴 **失敗したログインの応答が、利用者名が登録されているかどうかで区別できない**こと
   （**存在秘匿**）。これは静的検査では言えず、**稼働している ID プロバイダへ実際に投げて測る**。

**対象外**: ロックアウトの発火（**意図的にロックを作ると後段の検査と再実行の前提が変わる**ため、
本仕様書の自動テストでは作らない）・ソーシャル/外部 IdP 連携・画面の見た目（配色・ロゴ）の
視覚的検証。これらは実環境での手動検証・E2E の射程である。

> ［2026-09-11 更新］**「CI は ID プロバイダを起動しない。静的検査のみ」という記述は、
> もはや正しくない。** 統合スタックのワークフローは使い捨てクラスタで ID プロバイダを起こしており、
> 観点 3（存在秘匿）はそこで自動実行される。観点 1・2 は従来どおり静的検査である。

## テスト観点 —— なぜ「宣言したこと」を検査するのか

🔴 **`loginTheme` は名前の文字列でしかない。** 実体が無くても realm import は成功し、
ID プロバイダは既定テーマへ**黙って落ちる**。画面は出るのでヘルスチェックも E2E のログインも緑のままで、
**ブランド適用だけが静かに外れる**。`styles` が挙げる CSS の欠落も同型で、404 を出すだけでログインは成功する。

したがって「テーマを実装した」ことは realm の 1 行では担保されず、**実体との突合が要る**。
本仕様書のテストはすべてこの一点に向いている。

- **宣言と実体の突合**（存在・解決可能性）
- **継承の維持** —— 親テーマを宣言せずテンプレートを複製すると、本体側のセキュリティ修正・
  アクセシビリティ対応・新しい認証フロー（例: WebAuthn 関連画面）へ追随できなくなる（複製した瞬間に固定される）
- **境界** —— 既定ロケールが対応ロケール集合に含まれること／切替先が 2 つ以上あること
- **陽性対照** —— 「そもそも宣言していないから緑」で終わらないこと

## 実装マッピング

- `scripts/check-realm-constraints.js` の検査 4（`collectThemeGaps`）と、その自己試験 8 件（T-01〜T-08）
- 検査本体は CI の静的検査ジョブが実データに対して走らせる

### T-08 について — 「0 件走査の門」

T-08 は**実データを突合して齟齬 0 件**を要求するが、それだけでは
「realm が何も宣言していないので齟齬 0 件」でも緑になる。**先に「自前テーマを指していること」を
確かめてから**齟齬 0 件を要求する形にしてある（走査対象が消えたときに緑を返さないための門）。

### 検出力について

各ケースは擬似ファイルシステムを注入して判定するため、ディスクの実状態に依存しない。
T-02・T-03・T-05・T-06 はいずれも**「壊した状態を与えて検出されること」を直接表明**しており、
T-01・T-04・T-07 が**その裏返し（正常・対象外で鳴らないこと）**を押さえている。

## 存在秘匿（失敗したログインの応答）

計画側は存在秘匿の統制を「**応答の区別不能性**」と定め、**ステータスコード・応答本文・所要時間**の
3 面を挙げたうえで、**射程に認証系の経路（ログイン）を含める**と明文化している。
本節はその実測である。

🔴 **「ID プロバイダの既定挙動だから成立している」は導出であって実測ではない。**
隣のパスワードリセット申請の経路では、同じ既定のままで**実在する利用者名だけ 500・
実在しないものは 200** に分かれる状態が実測されており、その差だけで利用者名を列挙できた。
**ログイン側だけが導出で安全だと言える理由は無い。**

### 測り方 —— 対にするのは「失敗したログイン」である

成功したログインは実在する利用者名にしか起こり得ないので、対にならない
（成功した資格情報の送信は 302 ＋ 空本文になることが実測済み）。したがって対は次になる。

| 側 | 利用者名 | 資格情報 | 役割 |
| --- | --- | --- | --- |
| 実在 | realm 宣言に在る対話利用者 | **誤ったもの** | 陽性対照 |
| 非実在 | realm 宣言と突き合わせて不在を確認した名前 | **同じ**誤ったもの | 陰性対照 |

🔴 **2 つの利用者名はバイト長を一致させる。** 申請した利用者名は応答へそのまま反映されるため、
**長さの違う名前を比べれば本文長は必ず違う** —— それは存在の漏れではなく測り方の誤りである
（隣の経路の測定で 1 度踏んでいる）。長さが合わない組は**測る前に**落とす。

🔴 **繰り返しの回数は realm の失敗回数しきい値から導き、その手前で止める。**
失敗を重ねると実在する利用者だけが一時ロックされ、①測定が途中から別の状態を測ることになり、
②その利用者でログインする他の検査を巻き込む。

### 実装マッピング

- `scripts/check-login-existence-disclosure.js`（本走査）と、その自己試験（純関数・擬似入力）
- 本走査は統合スタックのワークフローで**最後に**走らせる ——
  🔴 **意図的に認証を失敗させるため、失敗回数の計数を消費する。**
  後段に「その利用者で成功するログインを通す検査」を置くと計数が積み上がって一時ロックに触れ得るので、
  **順序そのものを統制にしている。**
- 本文と `Location` の正規化は、パスワードリセット申請側の検査器と**同じ器を借りる**
  （同じ統制の比較器が 2 つあると片方だけが直る）

### 測っていないこと

- 🔴 **ロックアウトそのもの**（失敗回数しきい値に到達させると、実在する利用者だけがロックされる ——
  これはもう 1 つの存在判定器である）。**意図的に作ると測定環境を壊すため、稼働クラスタでの
  実測として別に扱う。**
- 🔴 **所要時間の合否**（T-12。閾値が定まっていない）。
- **利用者ごとの差**（測る対象は realm 宣言から選んだ 1 人である）。
