# テスト仕様書: 文書を管理する

## 本書の位置づけ

**既にあるテストと計画の受け入れ基準を突き合わせた記録である。** 本書を起こした作業はテストを
1 件も足していない。穴は「未実施」節に理由つきで書いた。

## 計画の逐語（本書が写像する対象）

- 概要: 正規化文書の **CRUD・バージョン・メタデータ・ABAC 属性／タグ**を管理する。
- 事前条件: **管理権限を持つ**。
- 事後条件: 文書が更新され、**取り込み・Wiki 同期がトリガされる**。
- 基本フロー: (1) 管理者が文書を登録／更新し、属性・タグを設定する → (2) システムが取り込み
  イベントを発行し、**索引と Wiki へ反映する**。
- 例外フロー: **必須属性が未設定の場合は保存を拒否する**。

## フローの写像

| フロー | 手順 | 検査すること |
| --- | --- | --- |
| 事前条件 | 管理権限 | 書き込みは管理者だけ。**運用者は読めるが書けない**。ロール無しは読める |
| 基本 1 | 登録／更新し属性・タグを設定する | 版が増える。過去版は**後からの変更で書き換わらない**。楽観ロックが外れたら 409 |
| 基本 1（タグ） | タグを設定する | **辞書に無いタグは拒否**する。改名は既存文書に追随し、版を上げない |
| 基本 1（属性） | 属性を設定する | 値域外は拒否。**文書スコープは後から変えられない** |
| 基本 2 | 取り込み・Wiki 同期をトリガする | ライフサイクル事象（公開・アーカイブ・削除）を発行する。本文の実体はオブジェクトストレージに置く |
| 例外 | 必須属性の未設定 | **登録・更新・メタデータ更新の 3 経路とも 400** で拒否する |

### T-13・T-20・T-28 を置く理由

否定形（400・拒否・404）だけでは、**検証そのものが常に落ちる実装**でも緑になる。値域内が通ること・
同送が通ること・範囲内が 200 になることを対で置いて、検出力を担保する。

## 未実施（しない／一部する）

- **Wiki への実反映は本書では測らない。** Wiki 側の同期・ABAC は Wiki 閲覧のテスト仕様書が
  引き受ける。本書が測るのは「事象を発行するところまで」である。
- **索引への実反映も本書では測らない。** 取り込み・索引はデータソース同期のテスト仕様書が持つ。
  **同じ床を 2 箇所に置かない。**
- **実 PostgreSQL / 実 MinIO を通した検査は一部しかしない。** 統合テストは Testcontainers に
  依存し、Docker daemon の無い環境では skip される（skip のまま緑になる）。単体側は代替の
  実装で覆っているが、**「統合テストが緑」を「実体で通った」と読んではならない**。
- **同時編集（複数管理者）の競合は楽観ロックの 409 までしか測らない。** マージ戦略は計画が
  定めていないため、テストで固定しない。
