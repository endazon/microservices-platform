# テスト仕様書: 文書本文の直接受け入れ経路

> 計画の受け入れ基準 ①〜⑩ をテストケースへ写像する。**⑨ は構造のみ・⑩ は依存待ち**であり、
> その理由は下の「対象外」に書く。

## テスト対象・範囲

- **対象**
  - 文書管理サービスの登録口（本文欄つき）と、既存文書への本文投入口
  - 本文の格納先（オブジェクトストレージ）と、DB が持つ参照
  - 本文サイズの上限判定と、上限超過時の応答
  - 所有者ベースの動的束縛による書き込み認可
  - 検索結果の集合と AI 回答のコンテキストの集合を分ける構造（契約側の型）
- **対象外**
  - **3 つのトグル（横断検索／ナレッジグラフ／AI 入力）の既定値**。実装のどの綴りでも存在せず
    （6 形すべて 0 ファイル。陽性対照 `confidentiality` 78 ファイル）、主語が無い状態では
    陽性テストを書けない。トグルを作る側の作業単位が着地してから写像する
  - **索引反映から検索ヒットまでの通し**。ベクトルストアの実体が要り、本環境では Docker が無く
    結合テストが skip される。単体では「取り込みが読む参照先から本文がそのまま取れること」までを見る
  - **画面からの本文編集導線**。当該導線は別条件で保留が継続している

## テスト観点

- **正常系**: 本文つき登録・既存文書への投入・本文なし登録（既存経路を壊さない）
- **境界値**: 上限ちょうど（切り詰めない）／上限 +1 バイト（拒否）／多バイト文字（バイト数で測る）
- **セキュリティ**: 所有者以外の書き込み拒否、所有者不明の文書への書き込み拒否、
  **主体が判定の入力であること**（同じ文書で主体だけ変えると結果が変わる）
- **否定形と陽性対照を対で置く**: 「誰も書けない」実装でも「全員書ける」実装でも落ちるようにする

## テストデータ

- 機密区分は `internal` を用いる（登録の必須検証を通すための最小値）。
- 所有者は `alice` / `bob` の 2 名。**主体はテスト用認証ハンドラのヘッダで差し替える**。
- 上限判定用の本文は ASCII 1 文字 = 1 バイトの反復で作る（多バイト文字の観点は別ケース）。
- 格納先は記録用スタブへ差し替える。本番の縮退実装は本文を保持しないため、
  「切り詰められていない」ことを測れない。
