# テスト仕様書: ユーザーアカウント管理

## テスト対象・範囲

**画面・境界層（`/bff/admin/users`）・後段の管理 API（`/authz/users*`）・身元管理の抽象**である。

**対象外（送り先つき）**:

| 事項 | 理由・送り先 |
| --- | --- |
| 🔴 **自動試験だけでの実 IdP 疎通** | 自動試験（T-30〜T-39）は**スタブした HTTP ハンドラに対する固定**であり、**「緑である」ことは「実 IdP へ反映できる」ことを意味しない**。疎通は稼働クラスタで手動で測る（T-40〜T-42）。実測して初めて出た罠が 2 つあり（部分更新で項目が消える／属性が黙って捨てられる）、いずれもスタブでは出なかった |
| 人事システム連携（自動プロビジョニング・退職者の自動無効化） | 方式が未確定であり、本画面の外である。画面は**その結果**（無効化された利用者）を表示するだけ |
| バックチャネルログアウトの受け口そのもの | 別の作業で実装済み・試験済み（境界層のセッション処理）。本仕様書は「失効を要求する」ところまでを見る |
| 監査記録の保持・閲覧 | 記録は認可基盤の管理イベントであり、閲覧はログ基盤側 |

## テスト観点

1. **ロール限定が 3 層で効くこと**（画面の存在秘匿・境界層・後段）。**陽性対照と対で置く** ——
   「全部拒否」でも否定形だけなら緑になる。
2. 🔴 **描いてはいけないものが無いこと**（新規作成の口）。**型・ルート表・境界層・画面の 4 層**で
   測り、いずれも**陽性対照と対**にする。
3. **入力規則が計画どおりであること**（ロール必須・複数可・定義済みのみ／部門と機密区分上限は必須／
   **タグは任意**）。**「任意である」は過剰拒否の否定側であり、必須化の変異を落とすために要る。**
4. **値域を焼き込んでいないこと**（ロールは認可基盤、属性値は属性体系の定義から引く）。
5. **境界層が状態コードと本文を作り替えないこと**（400 / 404 の透過、不達の 502）。
6. **縮退させないこと**（取得失敗を空の一覧へ潰さない）。
7. **既定の資格情報を持たないこと**（未注入は起動時に落ちる）。

## 無効化した席の失効に対するブラウザ側の反応（［2026-09-05 追記 / #439］置いた）

`platform/frontend/e2e/session-revocation.smoke.spec.ts`。**無効化の起点は本画面のボタンである**
（`POST /bff/admin/users/{id}/disable`）。無効化される利用者はその席に座っている当人にする ——
他人を無効化しても自分のセッションは失効しないため、1 つのブラウザセッションでは観測できない。

| # | 見ていること | 実測 |
| --- | --- | --- |
| E-4 | 無効化の**前**は同じ一覧取得が通り、表が描かれる（★陽性対照） | 緑 |
| E-5 | 無効化の**直後**、次に出た 1 本の保護要求が拒まれ、**その拒否で**再認証へ倒れる（呼び出しの並びが完全一致。間に成功する往復が無い） | 緑 |
| E-6 | 失効後に読み込み直すと未認証として扱われ、保護画面の中身が 1 つも残らない | 緑 |

- 変異試験で **E-5 と E-6 が別々の変異で落ちる**ことを実測した（拒否時の再認証導線を消す／
  無効化成功後に次の要求を出さなくする／身元の問い合わせの扱いを変える）。
- 🔴 **測っているのはブラウザ側の反応だけである。** 認可基盤の利用者が実際に無効になること、
  そこから境界層へ通知が届いてサーバ側のセッションが消えることは**ここでは 1 つも測っていない**
  （応答はネットワーク層のスタブである）。§未決事項 2 はこれで解消しない。
