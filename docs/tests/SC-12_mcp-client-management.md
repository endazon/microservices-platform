# テスト仕様書: MCP クライアント登録管理

## テスト対象・範囲

**画面と、そこから後段へ至る境界層（`/bff/admin/mcp-clients`）である。**

**対象外**: 後段サービスの管理 API そのもの（別のテスト仕様書が覆う。登録・無効化・属性割当の
値域と、無人アカウントへの個人資料属性割当の禁止はあちらで固定されている）／MCP プロトコル面
（`/mcp`）／認可サーバーのクライアント作成（実装していない。画面仕様書 §計画との対応 参照）。

## テスト観点

1. **ロール限定が 3 層で効くこと**（画面の存在秘匿・境界層・後段）。**陽性対照と対で置く** ——
   「全部拒否」でも否定形だけなら緑になる。
2. **境界層が状態コードと本文を作り替えないこと**（400 / 404 / 409 の透過、不達の 502）。
3. **描いてはいけないものが無いこと**（公開ツールの編集口）。**否定形は陽性対照と対で置く。**
4. **入力規則が計画どおりであること**（種別 2 値・無人時の属性必須・定義済みの値のみ）。
5. **縮退させないこと**（取得失敗を空の一覧へ潰さない）。
6. 🔴 **後段の端点が画面から実際に呼ばれること。** 「端点と生成フックが在る」ことは「使える」ことでは
   ない —— 分割代入したプロパティを 1 つ使い忘れても未使用検査は素通りする（属性の差し替えで実際に
   起きた）。**要求が飛ぶことを測る**（呼ばれた形跡ではなく、経路・メソッド・本文で引く）。

## 🔴 満たしていない受け入れ基準（意図的に「満たした」と書かない）

**「無人アカウントの属性が有人アカウントの上限を超えないこと」を検証するテストは無い。実装も無い。**

- 身元を返す契約が**ロールしか返さず、登録者本人の属性上限を返さない**。
- 後段（管理 API）にもこの検証は無い。禁止されているのは個人資料を読ませる割当だけである。
- 画面側だけで近似すると「通ったのに実際は超えている」形になる。**信頼できない検証は無いより悪い**
  （計画自身が別画面で同じ判断をしている）。
- 🔴 **テストを置いて「緑だから満たしている」と読ませることのほうが危険**なので、ここに未充足として
  記録する。**繰り延べであって放棄ではない。**

**「管理操作を監査ログに記録する」ことを検証するテストも無い。実装も無い**（記録の実体は監査記録
基盤側の決定である。**ツールの呼び出し**の監査は後段が既に行っており、別のテスト仕様書が覆う）。

## 🔴 ブラウザ E2E を置いていない（「E2E で固定した」とは書かない）

本画面は**システム管理者ロール限定**であり、ブラウザ E2E はビルド済みプレビューに対して走る。
認証基盤が動いていないため、**認証済みの画面を実走できない**。未認証の遷移だけを見る E2E は
「認証ガードが先に効くこと」しか固定できず、**ルートの実在すら固定できない**（未知パスの受け皿も
認証ガード配下に居るため、ルートを消しても同じ導線になる。先行 issue が実測済み）。
ルートの実在は T-14（ルート木の組み立て）と静的なルートマニフェスト検査が固定する。
