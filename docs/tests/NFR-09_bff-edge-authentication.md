# テスト仕様書: エッジ（BFF）認証の担保

## 起点となる計画書（トレーサビリティ）

- **非機能要件（セキュリティ・Must）**: 「恒久: 全 API で OIDC/JWT 認証。**暫定: エッジ（BFF）で OIDC/JWT を担保**」
- 同 §暫定運用の注記（セキュリティ）: 「暫定期は**エッジ（BFF）で OIDC/JWT 認証を担保し**、
  内部サービスはネットワーク分離を第一防御とする」
- 計画側の画面設計 `:124`: 「**文書管理・データソース管理・変換ジョブ = 閲覧は管理者・運用者**／破壊的操作は管理者限定」
- 同 `:126`: 利用者向けの画面群（検索・チャット／検索結果一覧／文書詳細／Wiki 閲覧／AI 分析ダッシュボード）は「**ABAC の権限内で全利用者が利用できる**」
- Issue: **#656**／実装 ADR: BFF の全端点に認証を要求し、検査器が「無認証」を見分けられるようにする

## テスト対象・範囲

- 対象: `/bff/*` の**端点認可**（認証の要否とロール）。
- **対象外**: 後段サービス（RetrievalService / AiAnalysisService / DocumentService）の認可。
  **#458 が持つ。本仕様が守るのは片側だけである。**
- **対象外**: `/bff/admin/config` の 3 本。`RequireAuthorization` を意図的に使わず、
  ハンドラ内 `AuthorizeAsync` ＋ 404 で**画面の存在ごと**隠す形である（権限外は 404 とする存在秘匿の方針）。
  **認可は在る**ので「無認証」ではない。

## テスト観点

- **拒否の側**: 無認証は 401／権限外は 403。
- **通る側**: 認証済みの一般利用者が従来どおり使える（**狭めすぎていない**）。
  **拒否の側だけでは「全部拒否」でも緑になる**ため、必ず対で置く。
- **存在秘匿を壊さない**: 認証済み・権限外は従来どおり 404（存在秘匿の方針と、401 / 403 を区別するロールゲーティングの決定による）。

> **★ T-20 の文書詳細は当初「403 でも 401 でもない」という弱い主張にしていた。**
> スコープ外・不在が 404 なので環境依存を避けたつもりだったが、**それでは足りない** ——
> **404 が素通りする**ので、口が静かに壊れて全員 404 になっても緑のままになる。
>
> テスト基盤は `/authz/scope` を `Granted=true`・フィルタ空（＝全件許可）で、`/documents/{id}` を
> 文書ありでスタブしている（実測）ので、**200 を直接主張できる**。変異試験で差が出た ——
> **「詳細を常に 404 へ倒す」変異は、弱い主張では素通りし、200 の主張では落ちる**（§変異試験 F）。

## Bearer で受理する主体（セッション方式の迂回を塞ぐ）

`/bff/*` は利用者をセッション Cookie で受け付け、`Authorization: Bearer` は無人の主体（サービス間）だけを受理する。
**利用者のトークンで Bearer を送ると、発行元のクライアントに関わらず 401** である —— ブラウザが取得できる
トークン（public client）はもちろん、BFF 自身のクライアント名義で取った利用者トークンも通さない
（以前は非ブラウザの外形確認のためだけに後者を通していたが、外形確認がセッション Cookie へ移ったので塞いだ）。

## 未決事項

- **後段サービスの認可は本仕様の対象外**。BFF を塞いでも**クラスタ内から後段へ直接到達する
  経路は残る**。「塞いだので安全になった」と読まないこと。
- **検査器は「認証を要求するか」までしか見ない。** 「**正しい**ロールが付いているか」は人が計画を読んで決める
  ——`x-roles` と実効ロールが**どちらも同じように間違っていれば通る**（契約と実効ロールの突合が持つ既知の限界）。
