# テスト仕様書: AI 提案一覧

## テスト対象・範囲

AI 提案の**一覧と導線**（棚卸し用の画面と、それを支える公開 API の読み取り口）。

**対象外**: 承認・却下の状態遷移（別のテスト仕様書が覆う）／提案の生成／却下解除の発火／
文書詳細画面の承認欄（別 issue）。

## テスト観点

1. **一覧が計画どおりの形をしていること**（4 列・同一の表・両端の文書名・根拠）。
2. **絞り込みが URL を単一情報源として機能すること**（既定・4 値・種類・未知の値の縮退）。
3. 🔴 **描いてはいけないものが無いこと**（一括承認・承認/却下の操作・種類ごとの別画面・
   導線を持たない行）。**否定形は必ず陽性対照と対で置く。**
4. **秘匿と縮退**（権限外は件数にも出ない／取得失敗を空の一覧へ潰さない）。

## 🔴 満たしていない受け入れ基準（意図的に「満たした」と書かない）

**「タグ提案がタグ辞書の値域に収まる」ことを検証するテストは無い。実装も無い。**

- 提案の生成は、言語モデルが返したタグ値を trim・重複除去するだけで、辞書と突き合わせていない。
- 辞書は文書サービス側にあり**管理者・運用者限定**である。一般利用者の画面からは引けないため
  （権限不足で拒否される）、**画面側での検証は原理的に不可能**である。
- サーバ間で引くには新しいサービス間依存と認可主体の決め方が要り、生成側の変更単位と
  新しい決定記録（あるいは計画側の裁定）が要る。**本作業では塞がない。**
- 🔴 **テストを置いて「緑だから満たしている」と読ませることのほうが危険**なので、
  ここに未充足として記録する。**繰り延べであって放棄ではない。**

## 🔴 E2E の限界（「E2E で固定する」を満たしていない）

起票時の要求は「一括承認が存在しないことを E2E で固定する」であった。**本リポジトリでは満たせない。**

- ブラウザ E2E はビルド済みプレビューに対して走り、**認証基盤も公開 API も動いていない**。
  既存のスクリーンレベル E2E はすべて「未認証 → ログインへ誘導」だけを見る形である。
- したがって**認証済みの画面を E2E で実走できない。**
- 🔴 **さらに、E2E は「ルートが実在すること」も固定できない**（#918 で実測した）。
  未知のパスの受け皿は認証ガード配下に居るため、**ルートを消しても未認証なら同じくログインへ誘導される。**
  したがって T-29 が固定するのは「認証ガードが先に効くこと」だけである。
  **ルートの実在は T-30（ルート木の組み立て）が固定する。**
- 🔴 **代わりに T-06 / T-15 / T-28 を単体テスト（陽性対照つき）と公開 API のルート表走査で固定した。**
  検出力は変異試験で実測している（下記）。**「E2E で固定した」とは書かない。**
