# テスト仕様書: パスワードリセット

## 起点となる計画書（トレーサビリティ）

- 画面: パスワードリセット
- ユースケース: ABAC 権限を管理する
- 受け入れ基準の所在: 認証 UX とアカウント管理の計画 ADR §パスワード・ロックアウト／メール配信の計画 ADR／計画側の画面設計 §パスワードリセット

## テスト対象・範囲

**対象**: `deploy/keycloak/microservices-platform-realm.json` が認証 UX の計画 ADR のパスワード・ロックアウト・有効期限の確定要件を満たすこと（**静的検査**）と、
**パスワードポリシーの「3 種以上」判定が正しいこと**（正規表現の**単体試験**）。

**対象に加わったもの（2026-09-02）**: **開発環境の捕捉用 MTA が dev 既定で立つようになった**ため、
**申請 → 送出 → 受信 → メール本文**を稼働クラスタに対して機械が通しで測れる（`node scripts/check-password-reset-mail.js`）。
以前「`smtpServer` が未設定であるため原理的に検証できない」と書いていた経路のうち、
**メール送出と、送出経路が生きているときの存在秘匿**はここに移った。

**対象外（実環境が要る）**: 全セッション失効・リンク有効期限の実測（30 分経過の待機）・新パスワード設定画面の表示。
**送出経路が死んでいるときの存在秘匿**は本書の対象だが、**その是正は別 issue の射程**である（§未決事項）。

## テスト観点

- **realm 設定が確定要件と一致すること**（値の一致。自動）
- **「4 種のうち 3 種以上」という選言が正しく判定されること**（**2 種は拒否・3 種は受理**の境界。自動）
- **`resetPasswordAllowed = true` を「実装済み」と数えないこと** —— これは Keycloak の既定値である（回帰防止）
- **開発環境の送出先がクラスタ内の捕捉用 MTA であること**（外部の実リレーを開発環境から指さない。**静的検査**）
- **送出が実際に成立し、本文がリンクと有効期限だけであること**（捕捉用 MTA の API を読む。稼働クラスタ）

## テストデータ

`deploy/keycloak/microservices-platform-realm.json`。パスワードポリシーの境界試験は `--self-test` に埋め込む
（**実際に投入している正規表現そのものを試験対象にする** —— 別の正規表現を書き写すと、投入値が変わったときに試験が追随しない）。

T-10 / T-16 / T-17 が使う**対象利用者・クライアント・有効期限・送出先**は、いずれも
**宣言から走査して得る**（realm JSON と `deploy/local/infra/mailpit.yaml`）。試験側へ書き写さない —— 同じ理由である。
非実在の利用者名は**実行のたびに作り、realm 宣言と突き合わせて不在を確かめる**（偶然の一致で
「非実在のつもりが実在していた」測定になるのを防ぐ）。

## 未決事項

- **T-11 / T-12 / T-14 / T-15 は依然として手動である。** 30 分の待機・全セッション失効の確認方式・
  管理者による一時パスワード発行・新パスワード設定画面のポリシー表示は、いずれも捕捉用 MTA では
  自動化できない（メールの受信ではなく、そのあとの画面と挙動が対象であるため）。
- 🔴 **送出経路が死んでいるときの存在秘匿は、まだ破れている。** T-10 が固定したのは
  **送出経路が生きているとき**だけである。送出に失敗すると**実在する利用者名のときだけ 500 が返り**、
  その差で利用者名を列挙できる（[画面仕様書 §未決事項](../screens/SC-15_password-reset.md)）。
  **別途起票済みであり、同じ比較器（`scripts/check-password-reset-mail.js`）へ退化した状態での
  同値性を足す**予定である。
- **go-live（実リレー）の疎通と文面**は本書の自動試験の対象外である。開発環境の送出先は
  クラスタ内の捕捉用 MTA に固定されており（T-18）、外部の実リレーへは env を明示したときだけ向く。
